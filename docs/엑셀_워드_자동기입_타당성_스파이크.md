# 엑셀 → 워드 자동 기입 — 타당성 스파이크 결과

- **일자**: 2026-10-28 (P3) · **브랜치**: `websphere-migration`
- **판정**: ✅ **LLM 없이 규칙(매핑)만으로 가능하다.** 단, **"안 되는 곳을 조용히 넘어가지 않는 장치"가 구현의 절반**이다(아래 §3).
- **한계**: 샘플을 직접 만들어 검증했다. **실제 양식의 특이점**(복잡한 병합·텍스트 상자 등)과 **실제 Word에서의 렌더링**은 검증하지 못했다(이 PC에 Word·LibreOffice 없음).
- **코드**: `kgi-ggreport-web/src/main/java/com/kbstar/kgi/ggreport/web/docfill/` (신규 6파일, **컨트롤러·화면 없음**), 테스트 `src/test/.../docfill/` 30건.

## 1. 방식

서버(Java)에서 이미 의존성이 있는 **`poi-ooxml 5.2.3`**(XSSF=엑셀, XWPF=워드)만 쓴다. **새 jar·폐쇄망 반입 증가 없음.**

```
규칙(사람이 적는다)                      동작
 키워드 "기관명" ← 시트!B3          → 엑셀 B3 값을 읽어
 키워드 "계약금액" ← [기관명=노원구].계약금액  → 머리글 이름으로 행·열을 찾아 읽어
                                       → 워드에서 키워드를 찾아 "옆"에 적는다
```

"옆"은 두 가지다. ① 표의 **라벨 칸**(글이 키워드뿐, 콜론 허용) → **오른쪽 칸** ② 문단 속 → 키워드(와 콜론) **바로 뒤**. 라벨이 값 위쪽에 있는 세로 배치는 미지원.

## 2. 검증 결과 (계획의 위험 5항목)

| 위험 | 결과 | 비고 |
|---|---|---|
| ① Word가 키워드를 run 여러 개로 쪼갬 | ✅ | 문단의 run을 이어 붙여 찾고, run 한가운데면 **둘로 갈라** 사이에 넣는다. 원래 run·서식 보존 |
| ② 병합 셀·중첩 표·키워드 중복 | ✅ | 가로 병합 OK, **세로 병합은 시작 칸에 기입**, 중첩 표 OK, 머리글·바닥글 OK, 중복은 `ALL`/`FIRST` 선택 |
| ③ 수식·숫자/날짜 서식 | ✅ **단, 결함 1건 수정** | 수식은 계산값, `#,##0` → `1,234,567`, 앞자리 0 문자열 보존, 엑셀 병합 셀 OK. **한글 날짜 서식은 아래 ⚠️** |
| ④ 기존 서식 유지 | ✅ (제한) | 삽입 글자가 **키워드 마지막 글자의 서식**(글꼴·굵기)을 물려받는다 → 굵은 라벨 뒤 값도 굵다. 값을 일반체로 하는 옵션은 아직 없음 |
| ⑤ 한글 파일명·규모 | ✅ | 한글 파일명 왕복 OK. **문단 3,000 + 표 100 + 엑셀 20,000행 + 규칙 20 → 약 1.7초**. 50MB 상한은 HTTP 계층에서 거를 일(미구현) |

### ⚠️ 스파이크에서 실제로 잡힌 문제 3건

1. **POI `DataFormatter`가 한글이 든 날짜 서식을 날짜로 인식하지 못한다.** `yyyy"년" m"월" d"일"` 셀이 `2026년 10월 28일`이 아니라 **`46323.0`**으로 나온다(수식 셀·일반 셀 모두). 한국어 양식에서는 거의 반드시 만나는 서식이다. → `ExcelDateFormat`이 이 경우만 직접 풀어 쓴다(`yyyy-mm-dd` 같은 ASCII 서식은 POI 그대로). 제안서에 `46323.0`이 인쇄되는 사고를 막는 핵심 수정.
2. **XmlBeans DOM은 `getTextContent()`를 지원하지 않는다**(`DOM Level 3 Not implemented`). run의 글은 `XmlCursor`로 읽어야 한다 — 이 기능을 이어받는 사람이 같은 함정을 안 밟도록 코드 주석에 남겼다.
3. **짧은 키워드는 더 긴 단어 안에서도 걸린다**(`라벨1`이 `라벨10`에, `기관명`이 `수요기관명`에). 한국어는 조사가 붙어 단어 경계를 믿을 수 없다. → **`labelOnly(true)`** 옵션: 표 라벨 칸이거나 `키워드:` 꼴일 때만 채운다. 기본은 꺼짐(글자 그대로).

## 3. 안전장치 (구현의 핵심)

값이 틀린 제안서는 빈칸 제안서보다 나쁘다. 그래서 **못 한 것은 전부 `FillReport`에 남고, 조용히 넘어가는 경우가 없다.**

| 상황 | 동작 |
|---|---|
| 키워드가 문서에 없음 | `KEYWORD_NOT_FOUND` — 문서 그대로 |
| 엑셀 시트·머리글·행 없음 / 빈 값 / `#DIV/0!` 같은 오류값 | `SOURCE_PROBLEM` — **문서를 건드리지 않음** |
| 조건에 맞는 행이 **2개 이상**(동명 기관) | 첫 줄을 고르지 않고 `SOURCE_PROBLEM` |
| 기입할 자리에 이미 다른 내용 | 덮어쓰지 않고 `CONFLICT`(표 오른쪽 칸은 규칙이 `overwrite`일 때만) |
| 같은 값이 이미 적혀 있음 | `ALREADY_FILLED` — **두 번 돌려도 결과 동일** |
| 하이퍼링크 안 등 모르는 구조 | 추측해서 끼우지 않고 `UNSUPPORTED` |
| 값 안에 키워드가 들어 있음 | 연쇄로 채우지 않음(한 번 쓴 문단은 다시 훑지 않음) |

호출하는 쪽은 `report.allOk()`가 아니면 **사람에게 알려야 한다**(화면 구현 때의 필수 조건).

## 4. 아직 모르는 것 / 지원하지 않는 것

- **미검증(실제 양식·Word 필요)**: 텍스트 상자·콘텐츠 컨트롤(SDT)·필드 코드 안의 키워드(XWPF가 순회하지 않아 **찾지 못하고 `KEYWORD_NOT_FOUND`로 보고될 것으로 예상**, 실측 안 함), 변경 추적 중인 문서, Word에서의 실제 모양.
- **미지원**: 세로 배치(라벨 위·값 아래), `.doc`(구형 워드; `.docx`만), 문단 안 기존 값 덮어쓰기, 값만 일반체로 쓰기, 표에 행 자동 추가.
- **보안·운영(정식 구현 시)**: 업로드 크기 제한(50MB), 확장자·MIME 검사, 압축 폭탄 방어(POI `ZipSecureFile` 기본값 확인), 파일명 인코딩(`Content-Disposition` RFC 5987), 결과 파일 보관 위치.

## 5. 정식 구현을 한다면 (승인 필요)

1. **규칙 입력 화면**: 사이드바 `엑셀 → 워드 자동 기입`(현재 '준비중') — 엑셀·양식 업로드 → 규칙 표(키워드 / 시트·셀 또는 머리글 조건 / labelOnly) → 실행 → **보고서 표를 먼저 보여 주고** 문제가 없을 때만 내려받기.
2. **API**: `POST /proposals/fill`(multipart: xlsx, docx, rules JSON) → 워드 파일 + 보고서. 규칙 저장(자주 쓰는 양식별 템플릿)은 2차.
3. **권한**: 영업 계열 전용 → `/menus` 키 하나 추가(`server/menus.py`·`Menus.java`·`menu_rules.js`·`nav.js`를 **같이** — `nav.test.js`가 키 누락을 잡는다).
4. **합격 기준**: 실제 양식 1~2개로 위 §4 미검증 항목을 먼저 확인.

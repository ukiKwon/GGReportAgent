## ① 목적 — 무엇이 바뀌었나

sub-project 5는 원래 "기존 dashboard 자산의 Next.js 이관"이었다. 브레인스토밍에서
사용자가 중심 컨셉을 제시하면서 재정의됐다:

> **orchestrator(상위 agent)가 subagent들에게 일을 뿌리는 멀티에이전트 웹서비스.**
> 단, AI가 제안서를 다 쓰는 것이 아니라 — **사람 팀들이 일하는 사이트에서 에이전트가
> 분석·검사·연결을 맡는 협업 시스템.** 9단계 워크플로는 불변.

기준이 된 사용자 시나리오(요약): 영업팀이 사이트에서 입찰상황판을 보고, 대화창에
"올해 도봉구청 입찰 어떻게 생각해?"를 묻는다. 에이전트는 지난 공고문·은행 상황·뉴스거리를
영업/전산/예산 관점으로 분석해 답한다. 영업팀이 노원구청 참여를 확정하면 에이전트가 공고를
분석하고, 불리한 조건을 발견하면 **되물어 재고를 권유**한다(그래도 추진하면 진행). 영업팀은
분석 내용을 담당자들에게 **쪽지(알림)** 로 발송하고 **작업 참여자로 추가**한다. 각 팀이 내용을
확인하고 **업로드**하면 에이전트가 누락·오탈자를 검사하고, 작성물이 **배점표 어디에 해당하는지
웹에서 표기**한다. 영업팀이 최종 확인·**결재** 후 디자이너에게 이관하고, 디자이너 작업물은
에이전트가 오탈자·**개인정보**를 재검사한 뒤 **최고 인사권자 결재**로 올라간다. 최종 승인되면
작업물 일체를 **내부 저장소에 저장**한다. 이 모든 동안 팀들은 대화창으로 계속 대화했고,
**지식시스템**에서 영업별 지식을 검색할 수 있다.

## ③ 3층 구조

- **사람 층** — 영업팀(참여 결정·팀 배정·결재), 전산/예산 담당(작성물 업로드), 디자이너(취합),
  최고 인사권자(최종 결재). 시스템 접점은 **대화창·쪽지(알림)·결재** 세 가지뿐이다.
- **에이전트 층** — Orchestrator(상위 agent) + subagent 6종(§④). 사람을 대체하지 않고
  분석·초안·검사·중개를 맡는다.
- **데이터 층** — registry(SQLite: institutions·bid_cases·tasks·messages·**notifications**),
  corpus(기관 조사자료·공고문·반입 뉴스), graph 체크포인트(`data/graph_checkpoints.db`,
  gitignored), 완료 작업물 아카이브 → FTS 색인(지식시스템).

## ④ 에이전트 층 상세

### Orchestrator 책무 6가지
1. **응대**: 대화창 질의 수신 → 참여검토 분석 디스패치 → 근거 링크와 함께 답변.
2. **계획**: `institutions.stage`·사람 결정 상태를 읽고 다음 일 선택.
3. **디스패치**: task 생성 후 지시. 3관점 초안팀은 `Send` 팬아웃 병렬.
4. **검사**: 업로드·보고를 배점표와 대조. 미달이면 재지시(subagent) 또는 되물음(사람).
5. **중개**: 쪽지 발송, 참여자 추가, 디자이너 이관 패키지 전달.
6. **상신**: 결재 지점(🛑 3곳)에서 `interrupt()` — 정지·체크포인트 저장, 결재가 재개 신호.

### Subagent 정의 (subagent끼리 직접 통신 금지 — 전체 그림은 orchestrator만 안다)
| subagent | 언제 | 하는 일 | 재사용 코드 |
|---|---|---|---|
| 참여검토 분석가 | 대화 질의·참여확정 시 | 지난 공고·재계약 이력·반입 뉴스로 참여 찬반·리스크 분석 | retrieval 검색 + LLM 어댑터 |
| RFI 분석가 | stage 3·4 | 공고 PDF 해부(배점표)·요구사항·불리 조건 | `rfp_extract`·`rfp_analysis` |
| 영업/전산/예산 초안팀 | stage 5·6 (병렬) | **사람 팀을 위한** 초안·근거 생성 | sub-project 4의 3팀 writer 그대로 |
| 패키저 | stage 7 | 승인 작성물+배점표 매핑+PPTX 골격 → 이관 패키지 | `pptx_builder` |
| 검증가 | stage 6 업로드마다 + 8 전체 | 누락(coverage)·오탈자·**PII**·RFI 역대조 | `verification` 확장 |

### LangGraph 구조 (상위 스펙 §⑤ LangGraph 복원)
- supervisor 그래프: orchestrator 노드가 조건부 엣지로 subagent 노드 선택.
- 6단계 3팀: `Send` 팬아웃 + `Annotated[list, operator.add]` reducer 병합
  (sub-project 4의 순수 Python 병합을 그래프 reducer로 이관 — 목표 동작 동일).
- 🛑 결재: `interrupt()` + SqliteSaver 체크포인터, `thread_id` = 기관 ID.
- 실행: 대화 질의는 즉답 그래프(동기), 워크플로는 `POST …/run` 202 백그라운드.
- 실패: LLM 폴백 체인(상위 스펙 §⑥) → 그래도 실패면 task '실패' 기록 후 정지.
- **반입 의존성**: `langgraph`, `langgraph-checkpoint-sqlite` (requirements.txt 추가).
  뉴스 수집은 폐쇄망 밖 DMZ 수집기의 배치 반입 범위 내에서만(실시간 크롤링은 여전히 범위 밖).

## ⑤ 9단계 사람/AI 분담 (워크플로 불변, 결재 🛑 3지점)

| 단계 | 사람 | 에이전트 |
|---|---|---|
| 1 입찰현황 파악 | 상황판 열람·대화 질의 | 반입분으로 상황판 데이터 제공 |
| 2 입찰상황 발생 | 영업팀 참여 **확정** | 참여검토 분석·리스크 **되물음**(비차단) |
| 3 RFI 공시 | — | 공고문 해부(텍스트·배점표) |
| 4 RFI 분석 | — | 요구사항·불리 조건 분석 → 입찰팀 제공 |
| 5 제안서 기획 🛑 | 영업팀 승인 + 쪽지로 참여자 추가 | 골격+팀별 분석 패키지 생성 |
| 6 세부기획(3팀) | 담당자 작성·업로드 | 초안 제공·업로드 즉시 검사·배점표 매핑 |
| 7 취합 🛑 | 영업팀 결재 → 디자이너 작업 | 이관 패키지 전달 |
| 8 검토 🛑 | 인사권자 최종 결재 | 오탈자·PII·역대조 후 결재 상신 |
| 9 제출 | 제출 수행·완료 마킹 | 아카이브 + 지식 색인 갱신 |

되물음(2·4단계)은 결재가 아니라 **권유**다 — 진행을 막지 않고, 기록만 남긴다.

## ⑥ 데이터 모델·API 추가분

**신규 테이블** (기존 `backend/db.py` 멱등 마이그레이션 관행):
```
notifications(notification_id, recipient, kind,        -- 쪽지/되물음/결재요청/이관
              institution_id, task_id, content, link,
              created_at, read_at)
```
업로드 작성물은 기존 `tasks.draft_content`(+파일이면 corpus 산출물 경로)를 쓴다 —
새 테이블을 만들지 않는다.

**신규/변경 API** (기존 라우터 5종에 추가):
```
POST /institutions/{id}/chat          # 대화창 → orchestrator 즉답 그래프
POST /institutions/{id}/run           # 워크플로 기동, 202 백그라운드
POST /institutions/{id}/checkpoint    # 🛑 결재 {approved, by, comment} — 5·7·8만 유효
GET  /institutions/{id}/status        # stage + tasks/messages 최근 + 산출물 존재
PUT  /institutions/{id}               # 화면 편집 서버 반영 (계획 B)
GET/POST /notifications               # 쪽지함 (수신자별 조회·읽음 처리)
POST /tasks/{id}/upload               # 담당자 작성물 업로드(기존 submit 확장)
```
기존 재사용: `tasks` submit/approve(팀 승인), bid_cases `finalize`+`X-User-Id`(최종 결재),
`GET /search`(지식시스템), participation-decisions(참여 확정).

## ⑦ 웹 화면 6종 (vanilla JS 확장, 서버 모드 전용 기능은 file:// 폴백 시 숨김)

① 입찰상황판(지도+예상/확정 배지+확정 버튼 — 기존 확장) ② **에이전트 대화창**(`chat.js`)
③ **워크플로 현황판**(9단계 스테퍼+에이전트/담당자 카드+지시·보고 로그, `workflow.js`)
④ **배점표 매핑 뷰**(작성물↔배점 항목 커버리지 색칠) ⑤ **쪽지함·결재함**(`notify.js`)
⑥ **지식시스템 탭**(FTS 검색). 결합 방식·store 전환은 계획 B(승인된 기존 설계) 그대로:
`create_app(static_dir=…)` 정적 마운트, 서버 모드 병합(name 기준, 서버 필드 우선),
개인 선호만 localStorage.

- **C. 협업 UI**: 화면 6종. 규모가 크면 writing-plans 단계에서 C1(현황판·매핑)/C2(대화창·

## ⑨ 상위 스펙과의 편차 (상위 문서에도 표기)

1. **체크포인트 2곳 → 결재 3곳(5·7·8)**: 사용자 시나리오의 결재 라인(기획 승인 → 이관
   결재 → 최종 결재)이 근거. "체크포인트 최소화" 원칙은 유지하되, 7단계 이관은 사람
   디자이너에게 넘기는 지점이라 결재 없이는 넘어갈 수 없다.
2. **6단계 주체**: AI 3팀 단독 작성 → **사람 팀 작성 + AI 초안·검사 보조**.
3. **LangGraph 복원**: 2026-07-30의 "순수 Python 병합" 편차를 되돌린다 — 멀티에이전트
   중심 컨셉(사용자 확정)이 그래프·체크포인트·interrupt를 실제로 요구하게 됐기 때문.
   sub-project 4 산출물(3팀 writer·role_router)은 그래프 노드로 그대로 이식한다.
4. **Next.js 미채택**: §②·⑦의 Next.js 이관 대신 vanilla JS 확장(폐쇄망 무빌드 원칙).
   Track 2 데모는 정적 호스팅+FastAPI로 충족.

계획 F(`docs/superpowers/plans/2026-08-04-hybrid-search-reindex.md`)로 **17이 채워졌다.**

그 과정에서 **17의 원인 진단이 틀려 있었음이 드러났다.** 위 표에 "FTS 색인 갱신은
수동"이라고 적혀 있었지만, 실제로는 **수동으로 돌려도 안 됐다** — 산출물은
`data/report_archive/`에 쌓이는데(`backend/archive.py:32`) 색인기의 스캔 루트는
`corpus/` 하나였다(`agent/retrieval/indexer.py`). 즉 아카이브물은 **경로상 색인 대상이
아니었다.** 자동화를 붙이기 전에 색인 루트를 둘로 늘리는 일이 먼저였다.

같은 조사에서 하나 더: 파서가 `.txt`뿐이라, 아카이브에서 색인되는 파일은
`rfp_text.txt` 하나였다. **정작 진짜 산출물인 제안서 `.pptx`가 빠지면 17이 이름뿐인
약속**이 되므로 `.pptx` 파서를 함께 넣었다(python-pptx는 이미 의존성에 있었다).

또한 계획 F에서 검색 방식 자체가 **FTS 단독 → FTS + 임베딩 하이브리드(RRF 합성)** 로
바뀌었다. 19번(지식시스템)의 실효가 여기서 크게 올라간다 — `"청년 자립 지원"`처럼
코퍼스와 글자가 안 겹치는 질의가 이전에는 항상 0건이었다.

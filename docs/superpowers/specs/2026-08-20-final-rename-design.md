이를 **재검토 신호 "backend 커밋이 2주간 한 자릿수"** 로 수치화해 두었다.

| 측정일 | 최근 14일 backend 커밋 | 판정 |
|---|---|---|
| 2026-08-06 | 92 | ❌ 미충족 |
| 2026-08-09 | 93 | ❌ 미충족 |
| **2026-08-20** | **1** (최근 7일 **0**) | ✅ **충족** |

- 조건 **ⓑ(잠잠해짐)는 충족**됐다.
- 조건 **ⓐ(사용자 결정 "최종형 됐을 때")는 사용자 몫**이며, 이 스펙의 승인이 곧 ⓐ다.

## ② 목표 — 폴더명이 배포 단위를 그대로 말하게 한다

지금 이름은 2026-07-29에 채택한 **"이름 유지 절충(C안)"** 의 산물이다(재구성 §⑨-1).
그때 전면 개명을 미룬 유일한 이유가 "동시 작업 중인 backend와 충돌"이었고, 그 이유가
①로 사라졌다.

```
backend/     →  server/      (FastAPI 앱 · 배포되는 서버)
dashboard/   →  frontend/    (정적 프런트 — §③에서 확정)
```

`agent/` · `collector/` · `corpus/` · `data/` · `golden/` · `docs/` 는 **그대로 둔다.**
이미 배포 단위를 말하고 있거나(§⑥ collector), 개명 이득이 없다.

## ③ 프런트 폴더 이름 — **`frontend/` 확정** (2026-08-20 사용자)

착수 전 유일한 미결이었고, **해소됐다.** 두 문서의 기록이 갈려 있던 것이 발단이다:

| 출처 | 이름 | 문맥 |
|---|---|---|
| 재구성 스펙 §⑤ | **`web/`** | "`dashboard`가 `web/`(통합 프런트)으로 **흡수**" |
| NEXT.md 항목 2 (2026-07-29 사용자 결정) | **`frontend/`** | "`dashboard/`→`frontend/`는 최종형 개명 스펙 때 함께" |

단순한 취향 차이가 아니다 — §⑤의 `web/`은 **"통합 프런트"**, 즉 RFP팀 화면 등
다른 프런트를 함께 흡수하는 **상위 그릇**을 뜻한다(재구성 §⑧이 "프런트 통합"을
E2E 스펙 sub-project 5의 몫으로 돌려놨다). 그 통합이 실제로 일어난다면
`web/dashboard/`처럼 **한 단계 더 들어가는 형태**가 맞고, 그렇지 않다면 `frontend/`가
평평해서 낫다.

검토한 세 안:

- ⓐ `web/` — §⑤ 원안. 후일 프런트가 더 생기면 `web/` 아래로 모은다.
- **ⓑ `frontend/`** ← **채택.** 사용자가 실제로 말한 이름이고, 지금 프런트가 하나뿐인
  현실에 맞다. 통합 프런트는 **스펙조차 없는 미래 일**이라 지금 그릇부터 만드는 것은
  이른 추상화다.
- ⓒ `web/` 그릇 + 그 아래 `web/dashboard/` — §⑤ 의도에 가장 충실하나 경로가 깊어지고
  `STATIC_DIR` 기본값도 두 단계가 된다.

⇒ **`dashboard/` → `frontend/`.**

§⑤(`web/`)와 어긋나므로 **재구성 스펙 §⑤에 이 결정을 한 줄 적는다**(§⑥-6). 문서끼리
충돌을 남기지 않는 것은 재구성 §⑨-4가 이미 세운 원칙이다. 후일 프런트가 실제로 여러
개가 되면 그때 `frontend/` 아래로 모으면 되고, 그 판단은 통합 스펙이 할 일이다.

## ⑥ 실행 순서 — 한 커밋 원칙

재구성 §⑥이 giganlist 이동 때 요구한 것과 같은 이유로, **경로 이동과 참조 수정을
한 커밋으로 묶는다.** 중간 상태로 커밋하면 그 커밋에서 리포가 깨진다.

1. **사전 확인** — `git status` 클린, 다른 세션 동시작업 없음, 테스트 기준선 기록
   (현재 **pytest 759 · node 244**).
2. `git mv backend server` · `git mv dashboard <③의 이름>`
   (`git mv`여야 이력이 이어진다. 삭제+생성으로 하면 `git log --follow`가 끊긴다.)
3. **파이썬 import 243곳** 치환 — `from backend` → `from server`, `import backend` →
   `import server`. 테스트 포함 전부.
4. **하드코딩 2곳** — `backend/main.py:78`의 `STATIC_DIR` 기본값,
   `backend/demo.py:138`의 `static_dir`.
5. **살아있는 문서·설정** — §⑤의 6개 파일. 실행가이드는 파일명도 함께.
6. **재구성 스펙 §⑤에 한 줄** — §③에서 정한 이름과 그 근거.
7. **검증**(§⑦) 통과 후 **커밋 1개**로 묶어 push.
8. NEXT.md 항목 2 종결 + 해당 일자 summary에 기록.

## ⑦ 검증 기준 (전부 통과해야 커밋)

- `node --test dashboard/test/*.test.js` → **244 passed**(경로 갱신 후).

- `grep -rn 'STATIC_DIR\|static_dir' backend server 2>/dev/null` 로 잔여 기본값 확인.
- **서버 실기동 1회** — `py -3.14 -m server.demo` 후 정적 파일이 실제로 서빙되는지
  (`STATIC_DIR` 오타는 테스트가 아니라 브라우저에서만 드러난다).
- **`golden/` 스냅샷 34건 재캡처 후 diff 0** — 이 작업은 동작을 바꾸지 않아야 하므로,
  골든 파일이 **바로 이 종류의 리팩터링을 위해 만들어진 안전망**이다(항목 9-③).

## ① 배경 — 무엇을 해결하고, 무엇을 폐기하는가

### 해결하려는 구멍

`backend/agent_adapter.py:20-22`의 `_load_team_corpus()`는 기관의 `giganlist_dir`가
없거나 존재하지 않는 디렉터리면 다음 문자열을 근거자료로 반환한다:

```
(자료 없음 — 신규 기관, 조사 결과 미제공)
```

이 상태에서도 `POST /tasks/{task_id}/messages`는 정상 동작한다. 즉 **근거 코퍼스가
전혀 없는 신규 기관에 대해서도 LLM이 제안서 초안을 생성하고, 그 결과가
`draft_content`로 저장되며, 결재를 거쳐 확정까지 갈 수 있다.** 프로젝트 전체가
"본문은 코퍼스에서 조립하고 LLM은 문장만 다듬는다"(상위 스펙 §⑤)는 원칙 위에
서 있는데, 신규 기관 경로에서만 그 원칙이 무너진다.

07-28 스펙 §⑤는 이 문제를 인지하고 "완전 신규 기관은 Task 생성 전에
`spec_research_node`가 코퍼스를 수집해야 한다"고 적어두었으나 **미구현**이다.
현재 코드는 3차 참여 결재가 끝나면 코퍼스 유무와 무관하게 Task 3개를 만든다.

### 폐기하는 것

`2026-07-21-rfp-agent-team-design.md`(구 NEXT.md 항목 1)는 Claude Agent SDK
서브에이전트로 `spec_research_node`를 구현하는 방향이었다. 이 설계는 **폐기**한다.

1. **폐쇄망 제약과 충돌** — Claude Agent SDK는 외부(Anthropic) 네트워크 의존이라
   4~9단계 폐쇄망에서 동작할 수 없다. 이 점은 상위 E2E 스펙이 이미 명시적으로
   해당 결정을 대체한다고 선언해 두었다.
2. **구현물이 리포에 없다** — 당시 워크트리 브랜치 `worktree-rfp-agent-team`과
   커밋 `1504d8e`(`run_subagent`)·`0e759e7`(`rfp_locate_node`)는 로컬·원격
   어디에도 존재하지 않는다(2026-07-29 확인: 브랜치 없음, dangling 커밋 79개
   전수 조회에도 없음). 이어받을 코드가 없으므로 재개가 아니라 신규 설계다.

**본 설계는 `spec_research_node`를 만들지 않는다.** 조사 주체를 사람으로 확정했기
때문에(아래 ②) 자동 조사 노드가 필요 없다.

### 베이스라인 원칙

**`giganlist/` 아래 기존 25개 기관 폴더가 전부 오류 0건으로 통과하는 것이 규칙의
상한선이다.** 이 원칙은 테스트로 강제한다(§⑨).

다만 **"표기 변형"과 "결함"을 구분한다**:

- 기관마다 다를 수 있는 **표기 변형** 때문에 골드 데이터가 떨어지면 → **규칙이 틀린 것**.
  규칙을 완화한다(데이터를 고치지 않는다).
- 골드 데이터 쪽의 명백한 **결함**(오타 등) 때문에 떨어지면 → **데이터를 고친다**.
  규칙을 약화시키면 검증기의 존재 이유가 사라진다.

### 규칙 사전 검증 결과 (2026-07-29, 실제 25개 폴더 대조)

**표기 변형으로 판정 → 규칙 완화**

- `guro/spec` — 번호가 `00 01 02 03 04 05 07 08`로 `06`이 없다 → 규칙 2(경고)로 처리.
- `jung/spec/00` — 파일명이 `00_4개년 계획 & 홈페이지 조사.txt`로 "인덱스"라는 말이
  없다 → 규칙 1은 **`00` 파일의 존재만** 보고 이름은 보지 않는다.

**결함으로 판정 → 구현 시 데이터 수정 (규칙 8 위반, 각 1글자)**

검증 규칙을 실제 데이터에 대조하다 발견한, **기존 리뷰가 놓친 실제 오타 2건**이다.
현재 두 파일 모두 아이디어 15개 중 14개만 `은행 기대효과` 블록을 갖는 상태로 보인다.

- `giganlist/dongjak/bank_ideas_draft.txt:107` — `은행 기대효도:` → `은행 기대효과:`
- `giganlist/gangbuk/bank_ideas_draft.txt:57` — `은행 기대효대과:` → `은행 기대효과:`

이 2건은 **구현 첫 단계에서 수정한다**(수정 없이는 베이스라인 테스트가 통과할 수 없다).
규칙 8을 경고로 낮추는 선택은 하지 않는다 — 이 오타를 잡는 것이 정확히 규칙 8의 목적이다.

### 규칙 7 재정의 (2026-07-29 계획 수립 중 발견)

초안의 규칙 7은 "`bank_ideas_draft.txt` 본문에 실존 금융기관명 0건"이었고 **오류**
등급이었다. 실제 25개 폴더에 대조한 결과 **3개 기관이 걸렸고, 셋 다 정당한 서술이었다**:

- `gangnam` — 문서 제목이 `강남구청 × 은행(KB) 협업 아이디어 초안`이고, 본문의 핵심
  발견이 "**KB가 협약 금융기관 목록에 없다**"이다. 제안 주체를 가리키는 이름이며
  이 프로젝트에서 가장 값진 유형의 경쟁 분석이다.
- `gangseo` — "2026.5.27 **우리은행** 등이 2조원 중 1조9천억원 금융조달을 마무리"
  (`spec/02` 인용 동반). 경쟁 금융기관 기진입 사실이며, 제안 프레임을 바꾸는 근거다.
- `nowon` — "**KB금융노원플라자**(노원구 청년일자리센터 입주건물, `spec/07` 항목24)".
  실재하는 건물명이자 자사 선점 거점 정보다.

corpus-format 스킬이 금지하는 것은 **금융 상품 브랜드명**("Product names are generic
categories … never real financial product brand names")이지 기관명 언급 일반이 아니다.
초안의 규칙 7은 스킬의 요구를 과잉 해석한 것이므로 다음과 같이 재정의한다:

- **등급을 경고로 낮춘다.** 경쟁사 언급은 정당한 서술이므로 반입을 막아선 안 된다.
- **검사 범위를 `구체적 상품/협력 형태` 블록으로 한정한다.** 상품명이 등장하는 곳이
  거기이고, `연계 구청사업/근거`·`은행 기대효과` 블록의 경쟁사 언급은 검사 대상이 아니다.
- **제안 주체(KB/국민은행)는 금지어 목록에서 제외한다.** 자기 이름을 쓰는 것은 위반이 아니다.

이는 §④ 베이스라인 원칙의 "표기 변형 → 규칙을 고친다"에 해당하는 사례다.

**베이스라인 통과 확인됨 (수정 불필요)**

- 규칙 6(인용 해소): 25개 기관의 `spec/NN` 인용이 전부 실재하는 spec 번호를 가리키고,
  `bank_ideas_draft.txt`의 `plan IT-N`/`plan FN-N` 인용도 전부 그 기관 `plan/01`에
  등장함을 확인했다. 규칙 6은 완화 없이 오류 등급으로 유지 가능하다.
- 규칙 1·3·4·5: 25개 전부 통과(spec 8~10개, plan 정확히 6개, 복수형 파일명,
  홈페이지·민원 파일 각 1개).

## ⑤ 데이터 모델 변경

`bid_cases` 테이블에 컬럼 1개를 추가한다.

```sql
research_status TEXT NOT NULL DEFAULT '대기'   -- '대기' | '완료'
```

`BidCase`/`BidCaseDetail` 모델에 같은 필드를 추가해 `GET /bidcases/{id}` 응답으로
노출한다. 프론트가 "코퍼스 대기 중"을 표시할 수 있어야 하기 때문이다.

> **각주 — 07-28 스펙 §⑤와의 차이**: 07-28 스펙은 `research_status`를 4값
> (`대기`|`진행중`|`완료`|`실패`)으로 정의했다. 본 설계는 **`대기`|`완료` 2값으로
> 줄인다.** 그 스펙은 `spec_research_node`가 비동기로 조사를 수행하는 것을
> 전제했으므로 "진행중"과 "실패"를 기록할 주체가 있었으나, 본 설계에서는 조사를
> 사람이 시스템 바깥에서 수행하므로 그 두 상태로 전이시킬 주체가 존재하지 않는다.
> 값이 있으나 아무도 쓰지 않는 상태를 남기지 않기 위해 축소한다. 후일 자동 조사를
> 도입하면 그때 값을 늘린다(기본값이 `대기`이므로 확장은 하위호환).

### 판정 기준

`research_status`의 값은 **`institutions.giganlist_dir`가 채워져 있는가**로 결정한다.

- BidCase 생성 시: 해당 기관의 `giganlist_dir`가 비어 있지 않으면 `완료`, 아니면 `대기`.
- 기존 25개 기관은 `backend/seed.py`가 이미 `giganlist_dir`를 채워두므로 **자동으로
  `완료`** 가 되어 현재 동작이 그대로 유지된다(회귀 없음).

## ⑥ API 계약

```
POST /institutions/{institution_id}/corpus/validate
  body: {"path": "giganlist/<기관>"}
  → 200 {"ok": bool, "errors": [...], "warnings": [...]}      # 상태 변화 없음(검사 전용)

POST /institutions/{institution_id}/corpus
  body: {"path": "giganlist/<기관>"}
  → 200 {"giganlist_dir": str, "activated_bid_cases": [id...], "warnings": [...]}
  → 422 {"detail": {"errors": [...]}}                          # 오류 1건 이상이면 반입 차단
```

`errors`/`warnings` 항목은 `{"rule": <번호>, "file": <상대경로|null>, "message": <설명>}`
형태로 반환해 어느 규칙이 어느 파일에서 걸렸는지 사람이 바로 알 수 있게 한다.

### 경로 안전

`path`는 **리포지토리 루트 기준 상대경로만** 허용한다. 절대경로, `..` 포함,
정규화 후 루트를 벗어나는 경로는 400으로 거부한다. 임의 경로의 파일을 읽어
응답에 실어 보내는 것을 막기 위한 것이다.

### CLI

```
py -3 -m backend.corpus_validator giganlist/<기관>
```

같은 검증 함수를 호출해 리포트를 출력하고, 오류가 있으면 exit 1로 끝낸다.
DMZ 쪽에서 반입 전에 미리 돌려보는 용도다.

## ⑦ 데이터 흐름

```
[DMZ / 인터넷 구역]
  사람이 리서치 에이전트로 giganlist/<신규기관>/ 생성
     └─ (선택) py -3 -m backend.corpus_validator 로 사전 검사
              │
              │  물리적 반입 (USB 등) — 폴더 복사
              ▼
[폐쇄망]
  1. BidCase 생성 → giganlist_dir 없음 → research_status='대기'
  2. 참여 결재 1→2→3차 "참여" → participation_status='참여확정'
       · research_status='대기' 이므로 Task 3개를 생성하지 않음   ← 게이트
  3. 사람이 폴더를 giganlist/ 아래 복사
  4. POST /institutions/{id}/corpus  {"path": "giganlist/<기관>"}
       · 검증 오류 있음 → 422, 아무 상태도 바뀌지 않음
       · 통과 → 한 트랜잭션으로:
           ① institutions.giganlist_dir 갱신
           ② 그 기관의 참여확정 + research_status='대기'인 BidCase → '완료'
           ③ 그 BidCase마다 Task 3개(영업·IT·예산, 상태 '대기') 생성
  5. 이후는 기존 흐름 그대로 — SSE 대화 → 1차 제출 → 2차 승인 → finalize
```

## ⑧ 에러 처리 / 동시성

| 상황 | 응답 |
|---|---|
| `path`가 절대경로·`..` 포함·정규화 후 리포 루트 밖 | 400 |
| `path`가 존재하지 않거나 디렉터리가 아님 | 400 |
| `institution_id`가 레지스트리에 없음 | 404 |
| 검증 오류 1건 이상 | 422 (`errors[]` 포함, **상태 변화 없음**) |
| 경고만 존재 | 200 통과 + `warnings[]` 반환 |
| 이미 코퍼스가 등록된 기관에 재등록 | 200 허용(경로 갱신). Task 생성은 **멱등** — 이미 Task가 있는 BidCase는 건너뛴다. `tasks`의 `UNIQUE(bid_case_id, team)`이 2차 방어선 |
| UTF-8 디코딩 실패 파일 | 예외를 전파하지 않고 규칙 9의 오류 항목으로 보고 |

동시성은 기존 방식을 따른다 — 요청마다 SQLite 커넥션을 열고 한 번에 커밋한다.
등록 API의 ①②③은 같은 커넥션에서 수행 후 단일 `commit()`으로 원자화한다.

## ⑪ 결정 로그

1. **자동 조사를 만들지 않는다** — 25개구 실적에서 품질을 만든 것은 사람의 지시
   (경쟁 금융기관 확인, 타 지자체 수치 전용 차단)였고, 그 판단을 기계로 옮길
   설계를 지금 확신할 수 없다. 검증만 자동화하면 사람의 강점은 남기고 사람이
   반복적으로 틀린 부분만 잡는다.
2. **검증에 LLM을 쓰지 않는다** — 반입 게이트는 같은 입력에 항상 같은 판정을
   내려야 한다. 의미 검증은 사람의 `plan/05_검증결과`가 계속 담당한다.
3. **경고 등급을 둔다** — 자유서술 파싱은 오탐이 나기 마련이고, 오탐 하나로
   반입이 막히면 사람이 검증기를 끄게 된다. 확실한 것만 차단한다.
4. **기존 25개구를 규칙의 상한선으로 삼는다** — 검증기가 골드 데이터를 떨어뜨리면
   그건 데이터가 아니라 규칙이 틀린 것이다.
5. **`research_status`를 2값으로 축소** — §⑤ 각주 참조.
6. **규칙 7을 경고로 낮추고 범위를 좁힘** — 초안대로였다면 경쟁 금융기관 기진입
   분석(이 프로젝트가 가장 값지게 여기는 발견)과 제안 주체 이름 언급이 전부 반입
   차단 사유가 됐다. 규칙을 실제 데이터에 먼저 대조해 본 것이 이 오류를 잡았다.
   §④ "규칙 7 재정의" 참조.

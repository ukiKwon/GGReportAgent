# 리포지토리 재구성 설계 — 통합 사이트·RAG·망 경계를 폴더 구조에 새기기

- **작성일**: 2026-07-29
- **상위 스펙**: `docs/superpowers/specs/2026-07-26-e2e-bid-workflow-system-design.md`
- **직접 관련 스펙**: `docs/superpowers/specs/2026-07-29-institution-corpus-validation-design.md`
  (이하 "코퍼스 검증 스펙" — 본 설계는 그 스펙의 `giganlist/` 경로 전제를 존중하며,
  경로 이동 시점을 그 구현 이후로 명시한다. §⑥ 참조)
- **성격**: 구조 설계 문서. **이 문서 자체는 아무것도 옮기지 않는다** — 실행은 후속
  세션에서 §⑦의 단계를 따라 진행한다.

## ① 배경 — 무엇이 문제인가

리포지토리는 세 세대의 실험이 시간 순으로 쌓인 지층 구조다.

| 층 | 폴더/파일 | 정체 |
|---|---|---|
| 1세대 (7/18~) | `build_report.py`, `build_html_report.py`, `giganlist/`, `report/`, `gigan.zip`, `구청_log.md`, 루트 HTML 3개 | 초기 5개구 보고서 생성 스크립트와 원천 조사 데이터 |
| 2세대 (7/23~) | `dashboard/` | 금고 입찰 대시보드 — 정적, D3, localStorage. 백엔드 연결 없음 |
| 3세대 (7/26~) | `backend/`, `agent/`, `registry.db` | E2E 입찰 워크플로 — FastAPI + SQLite + LLM 파이프라인 |
| 문서/기록 | `docs/superpowers/`, `handoff/`, `log/`, `architecture/` | 프로세스 산출물 |
| 잔해 | `workflow/`(빈 폴더), `tmp/`, `html_한글화_계획.md` 등 | 정리 대상 |

문제는 세 가지다:

1. **제품 형상이 구조에 없다.** "RFP팀이 쓰는 통합 사이트"가 목표인데, 그 사이트의
   서버(backend)·화면(dashboard)·에이전트(agent)가 서로 모른 채 나란히 있다.
2. **RAG의 원료가 흩어져 있다.** 기관 조사(giganlist), 공고문(RFP), 과거 보고서(report)가
   전부 루트에 따로 있고, "코퍼스"라는 개념이 폴더로 존재하지 않는다.
3. **망 경계가 구조에 없다.** 폐쇄망 안에서 돌 것과 밖에서 돌 것이 구분돼 있지 않다.

## ② 확정된 전제 (브레인스토밍 결과)

| 항목 | 결정 |
|---|---|
| 최종 형상 | **하나의 통합 사이트** — 대시보드·태스크 협업·에이전트 채팅이 탭/메뉴로 통합, backend가 전부 서빙 |
| LLM | **내부 서버의 오픈소스 LLM** (`agent/llm.py`의 교체 가능 어댑터 구조 유지) |
| 외부 데이터 반입 | 사내 확인된 선례를 따른다: RPA가 파일서버로 반입 → 담당자가 에이전트가 읽는 서버로 업로드 → 파이썬 파싱 → **캐시 인덱스**로 검색 |
| 검색 방식 | **벡터DB를 전제하지 않는다.** 사내 선례와 같은 "파일 낙하지점 → 파서 → 인덱스" 형태. 구현은 SQLite FTS(추가 인프라 반입 불필요), 검색부는 교체 가능한 부품으로 격리 |
| 실행 방식 | **설계 문서 먼저** (본 문서), 실제 이동은 후속 세션 |

## ③ 에이전트 개입 지점 — 폐쇄망 적합성 지도

"에이전트가 어디에 필요한가"를 금고 입찰 업무 흐름 위에 놓으면 다섯 지점이고,
폐쇄망과 충돌하는 것은 **1번 하나뿐**이다.

| # | 지점 | 하는 일 | 폐쇄망에서 | 현재 코드 |
|---|---|---|---|---|
| 1 | 공고 수집 | 나라장터·지자체 사이트를 순회하며 공고 탐지 | ❌ 망 밖에서만 가능 | 없음 |
| 2 | 문서 구조화 | 반입된 RFP PDF에서 일정·요건·평가기준 추출 | ✅ | `agent/nodes/rfp_analysis.py` |
| 3 | 참여 판단 브리핑 | 과거 추정치·기관정보로 참여심의 자료 요약 | ✅ | 부분 (`agent_adapter`) |
| 4 | 작성 지원 검색 채팅 | 내부 코퍼스를 검색해 근거 있는 답 | ✅ — 코퍼스가 전부 내부 축적물이라 오히려 궁합이 좋음 | 채팅은 있음, 검색 없음 |
| 5 | 조립·검증 | PPTX 생성, 정합성 검증 | ✅ | `agent/nodes/pptx_builder.py`, `verification.py` |

따라서 "에이전트가 사이트 여러 곳을 계속 돌아야 한다"는 문제는 1번을 **망 밖
수집기(collector)로 잘라내는 것**으로 해소되고, 나머지 넷은 협업 워크플로(backend)를
척추 삼아 망 안에 산다. 협업도 강화로 방향을 튼 기존 판단, 그리고 과거 추정치 기반
표시는 모두 "외부 실시간 데이터 없이 성립하는 설계"로서 이 지도와 일관된다.

## ④ 목표 구조

```
GGReportAgent/
├─ backend/        (유지) 통합 사이트의 서버. API + 정적 화면 서빙 + 검색 API
├─ agent/          (유지) 망 안 LLM 파이프라인 (지점 2~5)
│   └─ retrieval/  (신설) 인덱스 빌더 + 검색 — SQLite FTS 기반 "캐시 인덱스"
├─ dashboard/      (유지) 임원용 대시보드. 당장은 그대로, backend가 정적 서빙으로 흡수
├─ collector/      (신설) 망 밖 공고 수집기 자리 (지점 1)
│   └─ SCHEMA.md   수집 산출물 스키마 문서만 먼저 — 코드는 후일
├─ corpus/         (신설) RAG 원료 집결지 — 읽기 전용 원천 데이터
│   ├─ inbox/          반입 파일 낙하지점 (사내 선례의 '업로드 서버' 역할)
│   ├─ institutions/   ← giganlist/ 이동 (25개 구 조사) — §⑥ 시점 제약 참조
│   ├─ rfp/            ← RFP/ 이동 (공고문 PDF)
│   └─ reports/        ← report/ 이동 (과거 보고서·제안서)
├─ data/           (신설) 시스템 생성물 — registry.db, 산출 PPTX. gitignore
├─ archive/        (신설) 1세대 산출물 — build_*.py, gigan.zip, 루트 HTML 3개,
│                   html_한글화_계획.md, 구청_log.md, log/(과거 세션 로그)
├─ docs/ handoff/ architecture/   (유지)
└─ workflow/  삭제 (빈 폴더). tmp/ 내용물(교육자료 HTML)은 archive/로 이동 후 폴더 삭제
```

### 구조가 새기는 두 경계

1. **망 경계**: `collector/`만 망 밖에서 돈다. 망 안(`backend/`·`agent/`)과는 코드를
   공유하지 않고 **파일 스키마로만** 통신한다 — 수집 산출물(JSON/CSV)이 `corpus/inbox/`에
   떨어지는 것이 유일한 접점이다. 이는 코퍼스 검증 스펙의 "DMZ에서 생성 → 물리 반입 →
   검증 → 등록" 흐름과 같은 패턴의 일반화다.
2. **원료/생성물 경계**: `corpus/`는 사람·수집기가 만든 읽기 전용 원료, `data/`는
   시스템이 만든 생성물(DB·PPTX)이다. 백업·gitignore·반입 정책이 서로 다르므로 섞지 않는다.

### 검색(지점 4)의 부품 구조

```
corpus/ ──(파서)──▶ 인덱스(SQLite FTS) ──(검색 인터페이스)──▶ agent_adapter / 질의 API
```

- 인덱스 빌더와 검색을 `agent/retrieval/`에 두고, `agent_adapter._load_team_corpus()`의
  "폴더 통째로 읽기"를 검색 호출로 교체하는 것이 최종 그림이다.
- 검색 인터페이스는 함수 시그니처 하나(질의 → 근거 청크 목록)로 고정한다. 후일 사내
  GPU 서버에 임베딩 모델이 올라오면 **이 부품만** 벡터 검색으로 교체한다.
- 한국어 토크나이징: FTS5 기본 토크나이저는 한국어 형태소를 모르므로 trigram
  토크나이저를 기본값으로 검토한다(부분 문자열 일치로 한국어에서 실용적).

## ⑤ 최종형(후일)과의 관계

위 구조는 "이름 유지" 절충안이다. backend 작업이 잠잠해진 뒤의 최종형은 폴더명이
배포 단위를 그대로 말하는 형태다: `backend→server`, `dashboard`가 `web/`(통합 프런트)으로
흡수. **이 개명은 본 설계의 범위 밖**이며, import 경로 전면 수정이 따르므로 별도
스펙으로 다룬다. 지금 구조에서 최종형으로 가는 길이 막히는 결정은 본 설계에 없다.

## ⑥ 코퍼스 검증 스펙과의 정합 — giganlist 이동 시점 제약

코퍼스 검증 스펙(2026-07-29)은 다음을 `giganlist/` 경로로 전제한다:

- API 계약의 예시 경로 `{"path": "giganlist/<기관>"}`
- 베이스라인 테스트 — `giganlist/` 아래 25개 폴더 전수 통과
- `backend/seed.py`가 채우는 `institutions.giganlist_dir` 값
- `backend/agent_adapter._load_team_corpus()`의 경로 해석

따라서 **`giganlist/ → corpus/institutions/` 이동은 코퍼스 검증 구현이 착지한 뒤**,
위 네 지점 + DB에 이미 저장된 `giganlist_dir` 값 갱신을 한 커밋으로 묶어 진행한다.
검증기·등록 API는 경로를 입력으로 받는 구조라 이동 자체는 값 교체로 끝난다.
그 전까지 `corpus/`는 `rfp/`·`reports/`·`inbox/`만으로 시작해도 된다.

## ⑦ 마이그레이션 순서 (후속 세션용)

각 단계는 독립적으로 완결되며, 이 순서대로 하면 어느 시점에 멈춰도 리포가 깨지지 않는다.

1. **무위험 정리**: `archive/` 신설, 1세대 산출물·`log/`·`tmp/` 내용물 이동.
   `workflow/`(빈 폴더)·빈 `tmp/` 삭제. 코드 참조 없음을 grep으로 확인 후 이동.
2. **`data/` 분리**: `registry.db`·산출 PPTX를 `data/`로 모으고 gitignore. `backend`의
   DB 경로 기본값 1곳 수정.
3. **`corpus/` 신설(부분)**: `RFP/ → corpus/rfp/`, `report/ → corpus/reports/`,
   `corpus/inbox/` 생성. `RFP/` 경로를 읽는 코드·문서 참조 갱신.
4. **giganlist 이동**: §⑥의 시점 제약 충족 후 진행.
5. **`agent/retrieval/` 구현**: 파서 + FTS 인덱스 + 검색 인터페이스. 별도 스펙/플랜으로.
6. **`collector/SCHEMA.md` 작성**: 수집 산출물 스키마 정의. 수집기 코드는 그 다음.
7. **(후일) 최종형 개명**: §⑤. 별도 스펙으로.

## ⑧ 비범위

- 코드 폴더 개명(§⑤) — 별도 스펙
- collector 구현 — 스키마 문서까지만
- 프런트 통합(dashboard의 backend 서빙 흡수, RFP팀 화면) — 상위 E2E 스펙 sub-project 5의 몫
- 검색 품질 튜닝·임베딩 도입 — 검색 인터페이스 뒤의 교체 문제로 격리됨

## ⑨ 결정 로그

1. **이름 유지 절충(C안) 채택** — 전면 개명(B안)은 동시 작업 중인 backend와 충돌하고
   import 전면 수정이 따른다. 의미(망 경계·코퍼스 경계)는 신설 폴더만으로 얻을 수 있다.
2. **벡터DB를 전제하지 않음** — 사내 확인된 선례가 "캐시 인덱스"이고, 폐쇄망 반입
   승인도 기존 스택(SQLite)이 유리하다. 검색부를 부품으로 격리해 후일 교체 가능하게 한다.
3. **수집기를 망 밖 별도 산출물로 분리** — 에이전트 개입 지점 5개 중 폐쇄망과 충돌하는
   것은 공고 수집 하나뿐이다(§③). 이를 잘라내면 나머지 전부가 망 안에서 성립한다.
4. **giganlist 이동을 뒤로 미룸** — 같은 날 커밋된 코퍼스 검증 스펙이 그 경로를 계약에
   쓰고 있다. 문서끼리 충돌을 만들지 않는다(§⑥).
5. **corpus와 data를 분리** — 읽기 전용 원료와 시스템 생성물은 백업·gitignore·반입
   정책이 다르다.

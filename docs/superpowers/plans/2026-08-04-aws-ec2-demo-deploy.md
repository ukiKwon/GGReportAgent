# 계획 G — AWS EC2 데모 시연 배포 (Amazon Linux, CPU 단독)

## Context

지금까지 이 시스템은 **개발 PC의 `localhost`에서만** 돌았다. 사용자가 "곧 aws-ec2에 올려서
외부에서 접근할 수 있도록 하고 싶다"고 해서 배포 계획을 세운다.

- 출처: 2026-08-04 세션 (이 계획서를 만든 그 대화)
- 상위 스펙: `docs/superpowers/specs/2026-07-31-multi-agent-collab-system-design.md`
- 관련: `handoff/NEXT.md` 항목 5 (`gpt-oss-120b` 미검증 — 이 계획은 그 항목을 **해소하지
  않는다**. 아래 §③ 참조)

**이 계획은 애플리케이션 코드를 한 줄도 고치지 않는다.** 순수 배포 작업이다. 따라서
"지도 무수정" 제약도, 스펙 §⑦ 화면 6종도 영향을 받지 않는다.

### 왜 앱 로그인(ⓒ)이 아니라 Basic Auth(ⓑ)인가

사용자가 처음 ⓒ(앱에 로그인 신규 구현)를 제안했고, 아래 세 가지 근거로 ⓑ로 정정했다.
**나중에 운영 전환할 때는 ⓒ가 맞으므로, 그때 이 문단을 뒤집어 읽으면 된다.**

1. **데모 시나리오와 충돌한다.** 이 데모의 핵심 장치가 계정 전환기
   (`dashboard/js/app.js:126`, `GET /accounts`)로 **혼자서 tier 1·2·3 결재를 순차
   재현**하는 것이다(실행가이드 §11). 진짜 로그인은 "신원을 마음대로 바꾸는" 그 기능과
   정면 충돌해, 결재 시연마다 로그아웃/재로그인을 3번 해야 한다.
2. **작업량이 데모에 안 맞다.** `x_user_id`를 요구하는 엔드포인트가 6개
   (`backend/routers/tasks.py` 4곳·`bidcases.py:129`·`workflow.py:64,153`)라
   세션·비밀번호 해시·프론트 로그인 화면까지 새로 짜야 하고, 별도 스펙이 필요한 규모다.
3. **어차피 nginx는 놓는다.** ⓒ만 붙이고 HTTP로 열면 비밀번호가 평문으로 흐른다.
   ⓑ는 그 nginx에 5줄 더 얹는 수준이고 **앱 코드는 안 건드린다.**

⚠️ **알고 넘어갈 것**: 현재 `X-User-Id`는 **자기신고 헤더**다. Basic Auth를 통과한 사람은
그 안에서 누구 이름으로든 결재할 수 있다. 데모에선 그게 오히려 기능(계정 전환기)이지만,
**운영에서는 이것이 결함**이다.

## ② 구성

```
 [시연자 노트북] ──HTTP(Basic Auth)──▶ :80 nginx ──proxy──▶ 127.0.0.1:8000 uvicorn
                                        (EC2 보안그룹이 IP로 1차 차단)         │
                                                                              │ OpenAI 호환
                                                                              ▼
                                                                   127.0.0.1:11434 Ollama
                                                                        llama3.1:8b (CPU)
```

- `backend/demo.py:174`가 **`host="127.0.0.1"`로 고정**돼 있다. 이건 고칠 필요가 없다 —
  nginx가 앞에 서는 구성에서는 **오히려 올바른 기본값**이다(앱 포트가 인터넷에 직접
  열리지 않는다). 보안그룹에서 8000번은 열지 않는다.
- Ollama도 기본이 `127.0.0.1:11434`라 밖으로 안 나간다. **폐쇄망 가정이 구성으로도 성립한다.**

### 인스턴스

| 항목 | 값 | 근거 |
|---|---|---|
| 타입 | **`c7i.2xlarge`** (8 vCPU / 16GB) | 아래 |
| OS | Amazon Linux 2023 | 사용자 보유 |
| 디스크 | gp3 **40GB** | 리포 + 모델 4.7GB + `data/` + 여유 |
| 보안그룹 인바운드 | 22·80 을 **내 IP/32 에만** | 8000·11434는 **열지 않는다** |

**`t3`류(버스터블)를 피한 이유** — LLM 추론은 CPU를 100%로 오래 문다. t3는 CPU 크레딧을
소진하면 baseline(t3.xlarge 기준 40%)으로 **강제 스로틀**되어, 시연 중반부터 급격히
느려진다. "느림을 감수한다"와 "시연 도중 더 느려진다"는 다른 얘기다. `c7i`는 고정 성능에
AVX-512가 있어 같은 값이면 추론이 더 빠르다.

**비용** — 시연 때만 켜므로 실질 비용은 EBS(40GB gp3 ≈ 월 $3~4) + 가동 시간뿐이다.
`c7i.2xlarge`는 대략 시간당 $0.4 안팎(리전·시점에 따라 다르므로 콘솔에서 확인할 것)이라
하루 4시간 시연이면 커피값 수준이다. **정지(stop)를 잊으면 월 $250+가 되므로 §⑥의 종료
절차를 반드시 지킨다.**

| 뺀 것 | 이유 |
|---|---|

| DMZ 수집기(`collector/`, :8001) | 데모 화면과 무관하다. 반입 데모가 필요해지면 별도 계획 |
| 백업·모니터링·오토스케일 | 데모 목적 |

## ④ 작업 (Task)

각 Task는 **끝났는지 눈으로 확인할 방법**을 함께 적는다.

### Task 1 — 인스턴스 준비
- Amazon Linux 2023, `c7i.2xlarge`, gp3 40GB로 기동.
- 보안그룹 인바운드: `22/tcp`·`80/tcp` ← **내 IP/32**. 그 외 전부 차단.
- 확인: `ssh ec2-user@<IP>` 접속되고, 다른 네트워크에서는 안 된다.

### Task 2 — 런타임 설치
- `INSTALL.md`의 **1단계 한 방 블록** 실행 (python3.11·git·nginx·httpd-tools·Ollama).
- 확인: `python3.11 --version`, `ollama --version`, `nginx -v` 셋 다 출력된다.
- 확인: `python3.11 -c "import sqlite3;print(sqlite3.sqlite_version)"` ≥ **3.34**
  (FTS5 trigram 토크나이저가 그 버전부터다 — `agent/retrieval/indexer.py:62`).

### Task 3 — 리포 + 파이썬 의존성
- `git clone` → `/opt/GGReportAgent`, venv 생성, `pip install -r requirements.txt`.
- 확인: `python -m pytest -q` → **478 passed** (실행가이드 §13 기준선).
  여기서 깨지면 배포 문제가 아니라 환경 문제이므로 먼저 해결한다.

### Task 4 — 데이터 재생성 (`data/`는 gitignore라 git에 없다)
순서가 중요하다.
1. `python -m backend.seed` → `data/registry.db` (기관 25건)
2. `python -m agent.retrieval build --no-embed` → `data/corpus_index.db` (**수 초**)
3. `python -m backend.demo --no-serve` → `data/demo.db` + 데모 인덱스

**2번을 건너뛰면 안 되는 이유가 하나 더 있다** — 지식 탭이 죽는 것뿐 아니라
**대화 탭이 극단적으로 느려진다.** `backend/agent_adapter.py`의
`_load_consult_corpus`는 인덱스가 있으면 관련 청크만 발췌하고, **없으면 코퍼스를 통째로
읽어 프롬프트에 넣는다.** CPU 추론에서 그 차이는 수십 초 대 수 분이다.

- 확인: `python -m agent.retrieval search "청년 창업"` 이 결과를 낸다.

### Task 5 — Ollama 모델
- `ollama pull llama3.1:8b` (약 4.7GB).
- **`OLLAMA_KEEP_ALIVE=-1`** 을 systemd 오버라이드로 설정한다. 기본값은 유휴 5분 뒤
  모델을 내려서, 시연 중 질문 간격이 벌어지면 **다음 질문에 재로딩 수십 초**가 얹힌다.
- 확인: `curl -s localhost:11434/api/tags | grep llama3.1`.

### Task 6 — 앱을 systemd 서비스로
- `ggreport-demo.service` — `WorkingDirectory=/opt/GGReportAgent`,
  `ExecStart=<venv>/bin/python -m backend.demo --port 8000`,
  `Environment=LLM_MODEL=llama3.1:8b`, `LLM_BASE_URL=http://127.0.0.1:11434/v1`,
  **`LLM_FALLBACK_MODEL=llama3.1:8b`**.
- ⚠️ **폴백 변수를 굳이 같은 값으로 두는 이유**: `agent/llm.py`의 `_env()`는 빈 문자열을
  미설정으로 보고 기본값을 돌려준다. 즉 `LLM_FALLBACK_MODEL=`로 비우면 오히려 기본값
  `llama-4-scout-17b-16e-instruct`(설치돼 있지 않다)가 살아난다. **1순위와 같은 값을 주면
  코드가 폴백을 건너뛴다**(`agent/llm.py`의 `fallback_model == LLM_MODEL` 분기).
- 확인: `curl -s localhost:8000/institutions | head -c 200` 이 JSON을 낸다.

### Task 7 — nginx 리버스 프록시 + Basic Auth
- `htpasswd -c /etc/nginx/.htpasswd demo` 로 계정 생성.
- ⚠️ **스트리밍 때문에 반드시 필요한 설정 2줄** (`INSTALL.md`에 포함):
  - `proxy_buffering off;` — 없으면 대화 탭 답변을 nginx가 **통째로 버퍼링**해서, 화면이
    한참 멈춰 있다가 끝에 한꺼번에 쏟아진다. 스트리밍 시연이 아예 안 된다.
  - `proxy_read_timeout 300s;` — 기본 60초다. **CPU 추론은 그보다 오래 걸리는 답변이
    흔해서**, 그대로 두면 긴 답변이 504로 잘린다.
- 확인: 브라우저로 `http://<IP>/` → 인증창 → 대시보드. 대화 탭에서 답이 **글자 단위로
  흘러나온다**.

### Task 8 — 시연 리허설 + 문서화
- §⑤의 완화책을 적용한 상태로 전 탭을 한 번씩 연다(§⑥ 체크리스트).
- `INSTALL.md`에 시작/종료 절차를 확정해 넣는다.

## ⑤ CPU 추론이 느린 것에 대한 완화책 (시연 성패가 여기 달렸다)

사용자가 느림을 감수하기로 했지만, 아래 넷은 **공짜로 체감을 크게 바꾼다.**

1. **`OLLAMA_KEEP_ALIVE=-1`** (Task 5) — 모델 상주. 재로딩 수십 초 제거.
2. **웜업**: 시연 시작 5분 전에 대화 탭에 아무 질문이나 한 번 던져 둔다. 첫 호출은
   모델 로드까지 겹쳐 유독 느리다.
3. **인덱스를 반드시 빌드**(Task 4-2) — 프롬프트 길이가 줄어 추론 시간이 직접 줄어든다.
4. **질문을 짧게, 미리 정해둔 것으로** — 프롬프트가 길수록 선형으로 느려진다.

시연 대본 상의 안전장치: **대화 탭은 마지막에 보여준다.** 지도·워크플로·입찰상황판·
쪽지함·지식 탭은 전부 LLM과 무관하게 즉시 뜨므로, 느린 것 하나 때문에 시연 전체의
인상이 좌우되지 않게 배치한다.

## ⑥ 시연 당일 절차

**시작 (약 3~5분)**
1. 콘솔에서 인스턴스 **start** → 퍼블릭 IP 확인(Elastic IP를 안 붙였으면 **매번 바뀐다**).
2. 보안그룹의 허용 IP를 **오늘 있는 장소의 IP**로 갱신 (시연장 와이파이는 사무실과 다르다).
3. `sudo systemctl start ollama ggreport-demo nginx`
4. 웜업 질문 1회.

**종료 (잊으면 과금)**
1. 인스턴스 **stop**. 종료(terminate)가 아니라 정지다 — EBS가 남아 다음에 그대로 쓴다.
2. 확인: 콘솔에서 상태가 `stopped`인지 눈으로 본다.

**시연 전 확인 체크리스트**

| 화면 | 확인할 것 | LLM 필요? |
|---|---|---|
| 대시보드(지도) | 25개 구 색, 클릭 시 퀵뷰 | ✗ |
| 입찰상황판 | 공고 2건, 임박도 색 | ✗ |
| 워크플로 탭 | 9단계 스테퍼·참여자 카드·지시/보고 로그·배점표 매핑 | ✗ |
| 참여 결정 | 계정 전환기로 tier 1·2·3 순차 결재 | ✗ |
| 쪽지함 | 배지, 발송 | ✗ |
| 지식 탭 | 검색 결과(`score_kind`=`bm25`), 원문 열기 | ✗ |
| **대화 탭** | 답이 **글자 단위로** 흐른다 | **✓** |
| 워크플로 '실행' | 오케스트레이터 기동 | **✓** (느림 — 시연 비권장) |

## ⑦ 위험과 대응

| 위험 | 신호 | 대응 |
|---|---|---|
| 대화 답변이 끝에 한꺼번에 나옴 | 스트리밍 안 보임 | `proxy_buffering off;` 누락 (Task 7) |
| 긴 답변이 502/504로 잘림 | 1분쯤 뒤 오류 | `proxy_read_timeout 300s;` (Task 7) |
| "모델을 찾을 수 없습니다" 말풍선 | `failure_notice`의 404 문구 | `LLM_MODEL`이 `ollama list`와 다르다 |
| 지식 탭이 503 빌드 안내 | 인덱스 부재 | Task 4-2 미수행 |
| 답변 품질이 나쁨/숫자를 지어냄 | — | **알려진 한계다.** `llama3.1:8b`는 배점표 배점을 지어낸 실측 전력이 있다(NEXT.md 항목 5). 시연에서 "수치는 사람 검수 대상"이라고 미리 말한다 |
| 답변이 문맥을 잊음 | 긴 코퍼스에서 엉뚱한 답 | Ollama 기본 컨텍스트가 프롬프트보다 짧으면 **조용히 잘린다**. 필요하면 Modelfile로 `num_ctx`를 올린다(이번 범위 밖) |
| 요금 폭탄 | — | §⑥ 종료 절차. 정지 확인을 눈으로 |

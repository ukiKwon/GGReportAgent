## 4. uploader 2 — ⚠️ **MySQL 전용. Oracle DDL 이 없다**

`uploader/database_table 생성query.txt`. 매퍼는 `InstitutionMapper.xml`·`UploadedFileMapper.xml`.

| 테이블 | 컬럼 |
|---|---|
| `UPLOADED_FILE` (PK `ID`) | `ID` `BIGINT` **AUTO_INCREMENT** · `ORIGINAL_NAME` `VARCHAR(500)` · `STORED_PATH` `VARCHAR(1000)` · `FILE_YEAR` `VARCHAR(4)` · `INSTITUTION_NAME` `VARCHAR(200)` · `CATEGORY` `VARCHAR(100)` · `STATUS` `VARCHAR(20)` DEFAULT `UNCLASSIFIED` · `UPLOADED_AT` `DATETIME` · `CLASSIFIED_AT` `DATETIME` |
| `INSTITUTION` (PK `ID`, UNIQUE `NAME`) | `ID` `BIGINT` AUTO_INCREMENT · `NAME` `VARCHAR(200)` · `CATEGORY` `VARCHAR(100)` · `MODIFIED_AT` `DATETIME` |

**단계 6 전에 정해야 하는 것 두 가지**:

1. **`INSTITUTION`(uploader) vs `INSTITUTIONS`(본체)가 같은 개념인데 키 체계가 다르다** —
   전자는 `BIGINT` 자동증가 + `NAME`, 후자는 `VARCHAR2` 문자열 키(`dobong`) + `NAME_KO`.
   ⓐ 두 테이블 유지 ⓑ uploader 를 본체 참조로 변경 — **둘 중 하나를 골라야 한다.**
2. **`UPLOADED_FILE.INSTITUTION_NAME` 이 FK 가 아니라 이름 문자열**이다.
   기관명이 바뀌면 **오류 없이 조용히 끊긴다.**

**Oracle 이식 시 바꿔야 할 것**: `BIGINT AUTO_INCREMENT` → `NUMBER GENERATED BY DEFAULT
AS IDENTITY`(본체 `002` 와 같은 방식, ⚠️ **12c 이상**) · `DATETIME` → 본체와 맞추려면
`VARCHAR2(40)` ISO 문자열(본체가 시각을 전부 문자열로 저장한다) · `ENGINE`·`CHARSET` 절 제거.

## 6. 검증 상태 — **여기가 가장 중요하다**

| | 상태 |
|---|---|
| MySQL 미러 | ✅ `001`~`006` 실제 MySQL 에 적용 실측(2026-08-27) |
| H2 (테스트) | ✅ `001`·`002`·`004`·`005`·`006` + 시드 `003`, 테스트 222건이 이 위에서 돈다 |

⚠️ `002`·`005` 의 `IDENTITY` 는 **Oracle 12c 이상 전제**다. 11g 면 시퀀스+트리거로

## 7. 테이블 간 **의미가 겹치는 컬럼** — 합칠 때 걸리는 자리

같은 이름인데 뜻이 다른 것이 진짜 위험하다. **오류가 안 나고 조용히 틀리기** 때문이다.

### ⚠️ ① `ROLE` — **네 곳에서 네 가지 뜻**

| 테이블 | 값의 예 | 뜻 |
|---|---|---|
| `MESSAGES.ROLE` | `human`·`agent`·`orchestrator` | **누가 쓴 기록인가** |
| `CHAT_MESSAGES.ROLE` | `user`·`agent` | **대화의 화자** (위와 어휘도 다르다) |
| `ROLE_MENUS.ROLE` | `영업팀장`·`디자이너` | **사람의 역할 문자열** |
| `ORCH_STEP.ROLE` | `영업`·`전산`·`예산` | **팀 이름**(팬아웃 대상) |

한 화면에서 두 개를 같이 다루면 헷갈리기 쉽다. 특히 `MESSAGES.ROLE`(`human`)과
`ROLE_MENUS.ROLE`(`영업팀장`)은 **이름만 같고 값 공간이 전혀 겹치지 않는다.**

### ⚠️ ② `SEQ_NO` — **생성 방식이 두 가지**

| 테이블 | 방식 |
|---|---|
| `BID_CASES`·`TASKS`·`MESSAGES`·`NOTIFICATIONS` | **DB 가 매긴다**(IDENTITY). SQLite `rowid` 대체 = *삽입 순서* |
| `ORCH_STEP.SEQ_NO` | **앱이 매긴다**(`NUMBER NOT NULL`, `UNIQUE(RUN_ID, SEQ_NO)`) = *실행 안의 단계 번호* |

→ `ORCH_STEP` 에 `INSERT` 하면서 `SEQ_NO` 를 안 채우면 **다른 넷과 달리 실패한다.**

### ⚠️ ③ `STAGE` — **현재값 vs 그때의 스냅샷**

| 테이블 | 뜻 |
|---|---|
| `INSTITUTIONS.STAGE` | **지금** 그 기관이 몇 단계인가 (계속 바뀐다) |
| `MESSAGES.STAGE` · `NOTIFICATIONS.STAGE` | **그 기록을 남길 당시**의 단계 (안 바뀐다) |
| `ORCH_RUN.STAGE` | 그 실행이 다루는 단계 |

→ 조인해서 "단계별 쪽지"를 세면 **어느 쪽 STAGE 인지에 따라 답이 달라진다.**
과거 기록은 스냅샷 쪽이 맞다.

### ④ `STATUS` — 어휘가 테이블마다 다르다

`TASKS.STATUS`(`대기`→`작성중`→`1차완료`→`2차완료`→`최종완료`) ·
`BID_CASES.PARTICIPATION_STATUS`(`검토중`/`참여확정`) · `BID_CASES.RESEARCH_STATUS`(`대기`…) ·
`ORCH_RUN.STATUS` · `ORCH_STEP.STATUS` · `UPLOADED_FILE.STATUS`(`UNCLASSIFIED`, **영문**).

→ 공통 상태 enum 을 만들고 싶어지는 자리지만 **하지 말 것** — 값 공간이 실제로 다르고,
합치면 한쪽 어휘가 바뀔 때 다른 쪽이 끌려간다.

### ⑤ 사람 이름이 **다섯 컬럼에 흩어져 있다**

`TASKS.ASSIGNEE`·`APPROVER`·`FINAL_APPROVER` · `MESSAGES.AUTHOR` ·
`NOTIFICATIONS.SENDER` · `CHAT_MESSAGES.AUTHOR` · `BID_CASES.FINALIZED_BY`.

전부 `VARCHAR2(100)` **자유 문자열**이고 **사용자 테이블이 없다**(§5-②). 같은 사람의
이름이 바뀌면 과거 기록은 옛 이름으로 남는다 — 지금은 의도된 설계지만, 인증이 생기면
(문의 6-ⓒ) 이 일곱 자리가 전부 후보다.

### ⑥ `INSTITUTION_ID` — 같은 뜻인데 **FK 가 걸린 곳이 절반뿐**

FK 있음: `BID_CASES`·`ORCH_RUN`.
**FK 없음**: `NOTIFICATIONS`·`CHAT_MESSAGES`·`CHUNKS`.

→ 원본이 SQLite 3파일(registry / corpus_index / 체크포인트)로 나뉘어 있어 **DB 를
넘는 참조는 FK 를 걸 수 없었던** 흔적이다. Oracle 로 합치면서 테이블은 한 스키마에
들어왔지만 **제약은 따라오지 않았다.** 특히 `CHUNKS.INSTITUTION_ID` 는 색인 재빌드가
기관 삭제와 무관하게 도는 구조라, FK 를 거는 것이 **오히려 재빌드를 막을 수 있다** —
지금 상태가 실수라고 단정하면 안 된다.
⚠️ `NOTIFICATIONS.TASK_ID` 도 FK 가 없다(`MESSAGES.TASK_ID` 는 있다).

### ⑦ 경로 컬럼이 여섯 개 — 뿌리가 다르다

`INSTITUTIONS.GIGANLIST_DIR`(코퍼스) · `RFP_PATH`·`PPTX_PATH`(산출물) ·
`CHUNKS.PATH`·`FILES.PATH`(색인 대상) · `UPLOADED_FILE.STORED_PATH`(업로드 보관).

→ **기준 디렉터리가 서로 다르다**(`corpus/` vs `outputRoot` vs uploader 보관소).
경로 문자열만 보고 같은 규칙으로 다루면 안 된다.

### ⑧ 시각 — **본체는 문자열, uploader 는 DATETIME**

본체는 전부 `VARCHAR2(40)` ISO 문자열이고 `004` 가 그 폭을 확정했다.
uploader 원본은 `DATETIME` 이다. **합치면 두 모듈의 시각을 한 정렬에 태울 수 없다** —
`007_uploader.sql` 초안이 `VARCHAR2(40)` 로 맞춘 이유다.

### ⑨ 기관 이름/분류가 두 벌

`INSTITUTIONS.NAME_KO` ↔ uploader `INSTITUTION.NAME` ·
`INSTITUTIONS.TYPE` ↔ uploader `INSTITUTION.CATEGORY` ↔ `UPLOADED_FILE.CATEGORY`.

→ §4 의 [결정 필요] 와 같은 문제다. ⓑ(본체 참조)를 고르면 앞의 두 쌍이 사라진다.
`UPLOADED_FILE.CATEGORY` 는 **파일의 분류**라 기관 분류와 다른 개념이니 남는다.

②(`SEQ_NO` 생성 방식 — 코드에서 이미 다르게 다룬다) · ⑧(시각 타입 — `007` 에서 해결) ·
⑨(기관 두 벌 — 단계 6 결정)이다. ③~⑦ 은 **알고 있으면 되는 것**이지 고칠 대상이 아니다.

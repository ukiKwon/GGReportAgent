## [사내 공용 LLM API 관련 — 담당: AI/정보화 부서]

### 1. 사내 공용 LLM API의 호출 규격이 OpenAI 호환입니까?

- **여쭙는 이유**: 시스템이 문서 요약·검증에 LLM을 호출합니다. OpenAI 호환
  (`POST /v1/chat/completions`, JSON 스키마 구조화 출력 지원)이면 어댑터를 얇게
  구현할 수 있고, 독자 규격이면 요청/응답 변환 계층을 추가로 설계해야 합니다.
- **구체 확인 사항**:
  - ⓐ 엔드포인트 URL 형식 (예: `https://llm.내부도메인/v1/chat/completions`)
  - ⓑ 인증 방식 (Bearer 토큰 / API Key 헤더 / 사내 SSO 연동 등)
  - ⓒ 구조화 출력(JSON schema 강제) 지원 여부
  - ⓓ 사용 가능한 모델 이름 목록과 컨텍스트 길이
- **답변** (2026-08-30, 내부 담당자): **해당 없음 — 사내 공용 LLM API가 없다.**
  폐쇄망이라 밖으로 나가는 API 호출이 일절 불가하고, 사내에 공용으로 열린 LLM
  엔드포인트도 없다. ⇒ **모델 자체 호스팅으로 전환**(위 "바뀐 전제" 참조).
  ⓐ~ⓓ는 그 결과 **우리가 정하는 값**이 된다 — 자체 호스팅 런타임이 OpenAI 호환
  엔드포인트를 제공하므로 어댑터는 계획대로 얇게 간다.

### 2. 사내 API가 임베딩(embedding) 엔드포인트를 제공합니까?

- **여쭙는 이유**: 현 시스템의 문서 검색은 "전문검색 + 의미(벡터) 검색"
  하이브리드입니다. 임베딩 API가 **없으면 의미 검색을 포기하고 전문검색
  단독**이 되며, 검색 품질이 현 시스템보다 낮아집니다 — 이 경우 품질 저하를
  감수할지 사전 합의가 필요해 미리 여쭙습니다.
- **구체 확인 사항**: 임베딩 엔드포인트 유무, 있다면 모델명·차원 수·호출 규격.
- **답변** (2026-08-30, 내부 담당자): **사내 임베딩 API도 없다**(1번과 같은 이유).
  **다만 이 문항이 걱정하던 "의미 검색 포기"는 일어나지 않는다** — 자체 호스팅이면
  임베딩 모델을 함께 올리면 되기 때문이다. 현 Python 시스템이 이미 쓰는
  **`bge-m3`(1.2GB, 1024차원)** 를 그대로 올리면 지금과 같은 벡터를 얻는다.
  ⇒ **계획 Task 3.3(벡터 검색) 존치. 품질 저하 합의는 불필요.**

### 4. Oracle 버전은 무엇입니까? (11g / 19c / 23ai)

- **여쭙는 이유**: 11g면 `IDENTITY` 컬럼과 일부 JSON 함수를 쓸 수 없습니다.
  현 스키마는 애플리케이션이 PK를 생성하는 방식이라 영향이 크지는 않지만,
  DDL 작성 전에 버전을 못 박아야 재작업이 없습니다.
- **답변** (2026-08-30, 내부 담당자): **11g.**
  ⇒ `IDENTITY` 컬럼·일부 JSON 함수 사용 불가. 현 스키마는 애플리케이션이 PK를
  만들어 넣는 방식이라 영향은 국소적이지만, **DDL 정본을 11g 기준으로 1회
  검토해야 한다**(계획 매핑표가 예고한 "11g면 DDL 리뷰 1회 추가"가 발동).
  ⚠️ 특히 `VARCHAR2` 상한이 11g에서는 **4000바이트**다(12c의 확장 32767 불가) —
  설계 §5-(B)가 긴 텍스트를 CLOB으로 정한 결정이 **선택이 아니라 필수**가 됐다.

## [WAS/인프라 관련 — 담당: 인프라/미들웨어]

### 5. WebLogic 버전은 무엇입니까? (12.2.1.x / 14.1.1 / 기타)

- **여쭙는 이유**: 12.2.1.x는 Servlet 3.1, 14.1.1은 Servlet 4.0입니다. 실시간
  진행 표시(SSE)는 둘 다 가능하지만 `weblogic.xml` 설정과 프록시 타임아웃
  값이 버전에 따라 달라집니다.
- **답변** (2026-08-30, 내부 담당자): **12 버전대로 기억하나 정확하지 않음 —
  소버전 미확인.** ⇒ 계획의 기존 가정(12.2.1.x / Servlet 3.1)을 **그대로 유지**한다.
  구조가 바뀌는 항목이 아니므로 차단되지 않으나, `weblogic.xml` 값을 확정하기
  전에 한 번 확인할 것. **미회신으로 남긴다.**

### 5-1. 애플리케이션이 WorkManager(CommonJ)를 사용할 수 있습니까?

- **여쭙는 이유**: 문서 생성 등 오래 걸리는 작업을 요청 스레드 밖에서 돌려야
  하는데, **WAS에서 애플리케이션이 스레드를 직접 만드는 것은 금지**이므로
  WebLogic이 제공하는 WorkManager를 통해 실행하도록 구현했습니다. JNDI 조회가
  실패하면 요청 스레드에서 그대로 실행하는 폴백이 동작하는데, 이 상태로 운영에
  올라가면 **WAS 스레드 풀이 마르는 장애**로 이어집니다. 저희 개발 환경에는
  WebLogic이 없어 이 경로만은 **행내 환경에서만 검증이 가능**합니다.
- **구체 확인 사항**:
  - ⓐ 기본 WorkManager를 JNDI로 조회할 수 있는지, 조회 이름은 무엇인지
    (예: `java:comp/env/wm/default`)
  - ⓑ 애플리케이션 전용 WorkManager를 별도로 정의해야 하는지, 정의한다면
    신청 창구와 지정 가능한 값(최소·최대 스레드 등)
  - ⓒ 배포 전에 이 경로만 확인해 볼 수 있는 시험 환경(개발/스테이징)이 있는지

- **구체 확인 사항**: 요청/응답 형식(공통 헤더·응답 봉투 구조), 오류 코드 체계,
  URL·파라미터 명명 규칙, 페이징·대용량 응답 처리 규약, 첨부/바이너리 전송 방식,
  API 문서화(스웨거 등) 제출 요건.
- **답변**:

### 7. 경유지의 응답 버퍼링·유휴 타임아웃 설정값과, 변경을 요청할 창구를 알려주십시오.

- **여쭙는 이유**: 시스템의 대화 화면이 답변을 **여러 청크로 나눠 흘려보내는
  스트리밍 응답**을 씁니다(HTTP 응답 본문을 끊지 않고 조금씩 내려보내는 방식).
  앞단 프록시가 **응답을 버퍼링하면 실시간 표시가 멈추고**, **유휴 타임아웃이
  짧으면 답변 도중 연결이 끊깁니다**(참고로 저희
  검증 환경에서는 타임아웃 60초 설정에서 응답이 잘리는 것을 확인했고, 300초로
  늘리고 버퍼링을 끄는 것으로 해결했습니다).
- **구체 확인 사항**: 현재 버퍼링·타임아웃 설정값, 특정 경로에 한해 조정이
  가능한지, 조정을 요청하는 창구와 절차.
- **답변** (2026-08-30, 내부 담당자): **본인이 본 구성은 web-was 일체형 —
  앞단에 별도 웹서버를 분리해 두지 않았다.** 사실이라면 **사용자 유입 경로에
  프록시 버퍼링·유휴 타임아웃 문제가 없다**(이 문항의 걱정이 해소된다).
  ⚠️ **단, 이 답과 2026-08-25 개정("경유지를 반드시 거치는 구조")이 어긋난다.**
  둘이 다른 층위일 가능성이 크다 — **경유지 = 우리가 밖으로 나갈 때 거치는
  관문**, **앞단 웹서버 = 사용자가 들어올 때 거치는 것**. 오늘 답은 후자에 대한
  것이다. 1번 회신으로 "밖으로 나갈 일"(LLM 호출)이 사라졌으므로 **경유지가
  대화 스트리밍 경로에 실제로 끼어 있는지**만 확인하면 이 문항은 닫힌다.

# 보안 점검 — 2026-10-28

- **범위**: `kgi-ggreport-web`(Java 서버) + `frontend/`(화면). 코드를 읽고 확인한 것만 적었다. 실제 공격 시험·의존성 취약점 스캔은 하지 않았다.
- **원칙**: 이 문서는 **목록과 권고만** 담는다. 코드는 고치지 않았다(수정 여부는 항목별로 결정).
- **한 줄 결론**: 입력 검증(경로·업로드·화면 출력)은 대체로 단단하다. **가장 큰 위험은 서버에 인증이 없다는 것** — 사번 로그인과 접근 이력이 생겼지만 사번은 여전히 자기신고다.

## 1. 서버 인증 부재 · 신원 위조 — 높음

- **근거**: `web/Actor.java` — `getRemoteUser()`(컨테이너가 검증한 주체)가 7자리 사번이면 `verified=true`, 아니면 헤더 `X-Emp-No` 값을 **그대로** 받아 `verified=false`로 기록한다. 헤더는 누구나 보낼 수 있다.
- **영향**: 마스터 사번(`8203417`)을 알면 `curl -H 'X-Emp-No: 8203417'`만으로 `/sysadmin/**`(사용자 등록·권한 변경·이력 열람)을 쓸 수 있다. 접근 이력의 사번도 위조될 수 있다(화면에 "자기신고"로 표시해 두었다).
- **현재의 완화**: `AdminGuard`가 호출자 사번의 `admin` 권한을 DB로 다시 확인하고, 실패는 `DENIED`로 기록한다. 하지만 사번을 아는 사람은 통과한다. 사번은 비밀이 아니다.
- **권고**: WebSphere/앞단(SSO, 회사 공통 게이트웨이)이 인증한 주체를 `getRemoteUser()`로 받도록 연동하고, 운영에서는 **`verified=true`일 때만** 관리 API를 허용한다. 연동 전까지 운영 노출 금지(사내 폐쇄망·IP 제한 전제).

## 2. 비밀번호 없는 로그인 · localStorage 세션 — 높음

- **근거**: `frontend/js/login.js:60` `authenticate(id /* , password */)` — 비밀번호를 받지 않는다. `POST /auth/login`도 사번 존재·상태만 확인한다. 세션은 `localStorage`(`store.js`)에 있고 서버 세션·토큰이 없다.
- **영향**: 사번만 알면 로그인된다. 브라우저 저장소를 고치면 다른 사람·역할로 보이게 할 수 있다(화면 노출만 바뀌고 서버는 #1·#3 기준).
- **권고**: #1과 같은 해법(SSO)이 정답이다. 자체 인증을 두려면 비밀번호 해시(bcrypt/argon2)·서버 세션·`HttpOnly`/`Secure`/`SameSite` 쿠키가 한 묶음으로 필요하다.

## 3. 일반 API 전부 무인증 — 높음

- **근거**: `/sysadmin/**`만 `AdminGuard`가 있다. 나머지 컨트롤러는 호출자 확인이 없다. 대표적으로 `MenuController.put`(`PUT /menus`, 역할×메뉴 권한 변경)은 누구나 호출할 수 있고, 작업·결재·기관·입찰 API도 `X-User-Id` 헤더(자기신고, 20곳에서 사용)만 본다.
- **영향**: 서버를 직접 호출하면 화면의 메뉴 숨김은 아무 방어가 되지 않는다. `PUT /menus`로 역할 권한을 바꾸면 이후 `AdminGuard`의 판정도 영향을 받는다(권한 상승 경로).
- **권고(우선순위)**: ① `PUT /menus`를 `AdminGuard` 뒤로(`/menus` GET 계약·골든은 그대로). ② 결재·작업 변경 API도 호출자 사번의 권한을 서버에서 확인. 둘 다 #1이 해결돼야 의미가 있다.

## 4. `/documents` · 코퍼스 등록의 경로 입력 — 중간

- **근거**: `DocumentService.resolve`는 허용 루트(코퍼스·아카이브) 안인지 `normalize()` 후 `startsWith`로 확인한다. `CorpusService`(96~113행)도 같은 방식이고 `..` 우회 주석이 있다. `InboxService`는 배치 ID 정규식으로 `/`·`\`·`..`을 막는다. 심볼릭 링크는 `normalize`가 풀지 않는다(`toRealPath` 아님).
- **영향**: 경로 이탈은 막혀 있다. 다만 허용 폴더 안의 파일은 **인증 없이**(#3) 본문이 읽힌다.
- **권고**: 허용 폴더 안에 외부에서 반입한 심볼릭 링크가 생기지 않게 운영 절차에 명시하거나 `toRealPath()` 비교로 보강. 열람 API에 로그인·권한 확인(#3).

## 5. 업로드 — 중간

- **근거**: `support/TaskFiles.java` — 최대 50MB, 확장자 허용 목록(`.pptx .ppt .pdf .png .jpg .jpeg .zip`), 경로 구분자·`.`/`..`·숨김파일 거부, 저장 경로 정규화 후 루트 이탈 검사(이중 방어). 다운로드는 `attachment` + `application/octet-stream`이라 브라우저가 실행·렌더하지 않는다.
- **미검사**: ⓐ 파일 **내용**(확장자만 본다 — 이름만 `.pdf`인 실행 파일 가능) ⓑ ZIP·PPTX 압축 폭탄(`ZipSecureFile`·`setMinInflateRatio` 설정 없음; 서버가 PPTX/PDF를 파싱하는 `PdfText`·`PptxBuilder`·`DocumentService`가 영향권) ⓒ `file.getBytes()`로 전체를 메모리에 올림(50MB × 동시 요청) ⓓ 바이러스 검사 ⓔ 같은 이름이 조용히가 아니라 `replaced`로 알리며 덮어씀(정상 동작이나 되돌릴 수 없음).
- **권고**: 파싱 전 POI `ZipSecureFile` 비율·크기 제한 지정, 매직 바이트 확인, 스트리밍 저장, 서버 `max-file-size`/`max-request-size` 명시(현재 Spring 기본 1MB/10MB가 적용되는지 운영 설정 확인 필요 — 50MB 상한과 어긋날 수 있음). 사내 바이러스 검사 연동 여부 확인.

## 6. 보안 헤더 · CORS · CSRF — 중간

- **근거**: 소스 전체에서 `CrossOrigin`·`Access-Control`·`X-Frame-Options`·`Content-Security-Policy`·`nosniff`·`csrf` 검색 결과 **없음**. Spring Security 의존성도 없다.
- **영향**: 같은 출처 정책이 기본 방어(다른 출처의 읽기 차단)이지만, 쿠키 인증이 아니라 헤더 자기신고라서 CSRF 자체는 현재 구조에서 영향이 작다. 반면 클릭재킹(`X-Frame-Options` 없음)·MIME 스니핑·XSS 2차 방어(CSP 없음)는 비어 있다.
- **권고**: 필터 하나로 `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, 가능하면 CSP(현재 화면이 인라인 `<script>`·`<style>`을 쓰면 `unsafe-inline` 필요 → 효과 제한적, 먼저 인라인 분리 검토). SSO 쿠키를 도입하면 그때 CSRF 토큰·`SameSite` 필요.

## 7. 접근 이력의 무결성 · 보존 — 중간

- **근거**: `ACCESS_LOG`는 코드에 UPDATE/DELETE 경로가 없다(`AccessLogMapper`는 insert·조회만). `AccessLogService`는 `REQUIRES_NEW`로 비즈니스 롤백과 무관하게 남기고, 제어문자 제거·길이 제한을 한다. 본문·쿼리값·비밀번호는 기록하지 않는다(인터셉터 제외 규칙).
- **한계**: ⓐ DB 계정은 앱과 같아서 DB에 직접 접속하면 고치거나 지울 수 있다 ⓑ 해시 체인·외부 전송이 없어 변조 탐지 불가 ⓒ 보존 기간·삭제 정책 미정(`USER_AGENT`·IP는 개인정보성) ⓓ 사번이 자기신고(#1)라 "누가"의 신뢰도가 낮다 ⓔ CSV 내보내기는 현재 쪽만, IP 마스킹, 수식 시작 칸 무력화(구현 완료).
- **권고**: 운영 DB에서 앱 계정에 `ACCESS_LOG`/`PERM_CHANGE_LOG`의 `UPDATE`·`DELETE`를 부여하지 않고(DDL 헤더에 주석으로 명시함) 정기 아카이브를 별도 저장소로 보낸다. 후속으로 행마다 이전 행 해시를 포함하는 해시 체인. 보존 기간은 내부 규정에 맞춰 확정.

## 8. 화면 출력(`innerHTML`) — 낮음

- **근거**: `frontend/js`에 `innerHTML` 76곳, `esc()` 171곳. 사용자·서버 값이 들어가는 곳을 확인했다: `chat.js`(`esc(r.label)`, `esc(r.content)`), `knowledge.js` 문서 본문(`highlight(esc(...))` — 이스케이프 후 강조), `admin.js`(새로 만든 4개 화면 모두 `esc` 사용, 접근 이력의 `detail`·`req_path` 포함). 점검한 범위에서 이스케이프 누락은 찾지 못했다.
- **한계**: 76곳을 전부 한 줄씩 추적하지는 않았다. `workflow.js`·`designer.js`·`notify.js`·`approvals.js`는 표본만 봤다.
- **권고**: `innerHTML` 조립부에 값 삽입 시 `esc` 누락을 잡는 정적 검사(간단한 grep 테스트)를 `node --test`에 추가. CSP(#6)와 함께 2중 방어.

## 9. 설정 · 비밀 관리 — 낮음

- **근거**: 실제 로컬 설정 `config/application.properties`는 `.gitignore`에 있다(`git check-ignore` 확인). 추적되는 `config-envs/*/application.properties`의 DB 비밀번호 값은 자리표시자로 보이며(값은 확인했으나 이 문서에 적지 않는다), `prod`는 비어 있다. 운영은 WebLogic/WebSphere 콘솔의 JNDI DataSource에 비밀번호를 둔다고 `web.xml` 주석에 적혀 있다.
- **권고**: 추적 파일에 자리표시자가 아닌 값이 들어가지 않도록 커밋 전 검사(pre-commit) 권장. 로컬 DB 비밀번호가 문서·로그에 나온 적이 있다면 교체.

## 10. 로그인 시도 제한 — 낮음

- **근거**: `USERS.FAILED_LOGINS` 컬럼은 있으나 비밀번호가 없어 사용하지 않는다. 사번 대입(열거) 시도는 `LOGIN_FAIL`로 기록만 되고 제한이 없다. 실패 사유도 `unknown employee`로 구분되어 기록된다(이력은 관리자만 열람).
- **권고**: SSO 도입 후에는 그쪽 정책을 따른다. 그 전이라면 IP·사번별 분당 실패 횟수 제한과 접근 이력의 실패 급증 경보.

## 11. 오류 메시지 — 낮음

- **근거**: `ApiException`의 메시지가 응답 `detail`로 나간다. 일부는 서버 경로를 포함한다(`DocumentService`의 "파일이 없습니다: " + 요청 경로(입력값 반사), `InboxService`의 `manifest.json을 읽을 수 없습니다: ` + 예외 메시지).
- **권고**: 운영에서는 내부 예외 메시지·절대경로를 응답에서 빼고 로그에만 남긴다. 500은 일반 문구로.

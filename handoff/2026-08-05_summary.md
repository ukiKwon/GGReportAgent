### 1. INSTALL.md를 실제 인스턴스(m7i-flex.large) 기준으로 교정 (main `df9e0a9`)

사용자가 EC2를 **t3.small → m7i-flex.large**로 올렸다. 그 과정에서 두 번 교정했다.

- **t3.small은 불가**임을 먼저 알렸다 — RAM 2GB에 `llama3.1:8b`(실행 시 5~6GB)는 OOM으로
  죽는다. "느려도 감수" 범위가 아니다. 다만 시연 8개 화면 중 **6개는 LLM이 필요 없고**,
  대화 탭은 계획 F 후속(G1)에서 실패 사유를 화면에 띄우게 해둬서 깨지지 않는다는 점도 함께.
- **m7i-flex.large(2 vCPU/8GB)로는 RAM 벽은 넘지만 CPU가 병목** — 8b는 답변 1건에 수 분
  예상. 그래서 기본 모델을 **`llama3.2:3b`(~2GB)** 로 내렸다(사용자 확정).
- 문서에 **"RAM=올라가는가 / vCPU=쓸 만한가"** 두 벽을 분리해 서술하고, 8b·1b·qwen 대안과
  c7i 원안(4배 요금)을 선택지로 남겼다. 스토리지 40→20GB, 비용 문단($0.4/h·월 $250 →
  $0.10/h·월 $70)도 실제 유형에 맞췄다.
- **문서를 코드와 대조해 사실오류 3건도 함께 고쳤다**: ①pytest 기준선 478 → **526**(실측)

  `langchain_openai` 누락(없으면 화면은 뜨는데 대화만 죽는다).

### 탐색·구현 중 드러난 것 4가지 (되돌리지 않도록)

- **`task_update`로 디자이너 Task를 열면 작업이 지워진다.** `packager`는 최종반려 때
  다시 도는데(subagents.verifier의 F7 주석), `task_update`는 `status='대기'·progress=0`을
  덮어쓴다. 디자이너가 파일을 올려둔 뒤 최종반려가 나면 상태가 초기화되는 셈이다.
  → `task_open`을 따로 냈고, **회귀 테스트가 이 계획의 핵심 방어다.**
- **"최종 승인난 산출물만" 거르면 화면이 빈다.** 그래프에서 팀 Task는 `1차완료`까지만

  게다가 감추면 디자이너가 다 받은 줄 안다 → 전부 주고 상태 태그로 구분한다.
  다만 **에이전트 전용 단계(RFI분석·취합·검증)는 뺐다** — 실기동에서 빈 카드 3개로
  올라오는 것을 보고 `backend/teams.AGENT_TEAMS`로 걸렀다.
- **`X-User-Id`의 ASCII 제약이 여기서 실제 장애가 됐다.** 담당자가 '최 디자이너'면
  자기 작업에 파일 하나 못 올리고 403이었다. `CheckpointIn.by`와 같은 관행으로
  본문 `by`를 신원으로 받아 풀었다(`_actor(by, x_user_id)`).
- **제출이 아무에게도 알리지 않는 구멍이 있었다** — 상태만 바꾸고 끝이라 제출해도
  아무 일이 안 일어났다. 영업팀 결재요청 알림을 붙였고, **디자이너뿐 아니라 모든 팀의

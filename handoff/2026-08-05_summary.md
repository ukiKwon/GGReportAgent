### 1. INSTALL.md를 실제 인스턴스(m7i-flex.large) 기준으로 교정 (main `df9e0a9`)

사용자가 EC2를 **t3.small → m7i-flex.large**로 올렸다. 그 과정에서 두 번 교정했다.

- **t3.small은 불가**임을 먼저 알렸다 — RAM 2GB에 `llama3.1:8b`(실행 시 5~6GB)는 OOM으로
  죽는다. "느려도 감수" 범위가 아니다. 다만 시연 8개 화면 중 **6개는 LLM이 필요 없고**,
  대화 탭은 계획 F 후속(G1)에서 실패 사유를 화면에 띄우게 해둬서 깨지지 않는다는 점도 함께.
- **m7i-flex.large(2 vCPU/8GB)로는 RAM 벽은 넘지만 CPU가 병목** — 8b는 답변 1건에 수 분
  예상. 그래서 기본 모델을 **`llama3.2:3b`(~2GB)** 로 내렸다(사용자 확정).
- 문서에 **"RAM=올라가는가 / vCPU=쓸 만한가"** 두 벽을 분리해 서술하고, 8b·1b·qwen 대안과
  c7i 원안(4배 요금)을 선택지로 남겼다. 스토리지 40→20GB, 비용 문단($0.4/h·월 $250 →
  $0.10/h·월 $70)도 실제 유형에 맞췄다.
- **문서를 코드와 대조해 사실오류 3건도 함께 고쳤다**: ①pytest 기준선 478 → **526**(실측)

  `langchain_openai` 누락(없으면 화면은 뜨는데 대화만 죽는다).

## Session 13:40 — 계획 I: 역할·결재 라인과 메뉴 권한

계획서: `docs/superpowers/plans/2026-08-05-role-approval-menus.md`.
계획 H를 화면으로 확인하던 사용자가 **결재 라인이 통째로 빠져 있다**고 짚은 데서 출발.

### 사용자 확정 4건

역할은 **소속 값을 늘려서** 표현 · `인사권자`→`본부장` 개명 · 권한 관리는 **화면까지
(DB 저장)** · 디자이너 제출물은 **알림 + 각 팀 화면에서 열람**.

### 만든 것

| 층 | 무엇 |
|---|---|
| 어휘 | `backend/teams.py` — `ROLES`·`team_of`·`lead_of`·`is_lead`·`FINAL_APPROVER` |
| 권한 | `role_menus` 테이블 · `backend/menus.py`(정의·기본값) · `GET/PUT /menus` |
| 결재 | `GET /approvals?role=` · `POST /tasks/{id}/approve`에 반려 알림 |
| 화면 | `approvals.js`(결재함) · `admin.js`(권한관리) · `menu_rules.js`(노출 규칙) |

### 범위를 크게 줄인 발견 2가지

- **`handoff`는 이미 "자기 팀을 뺀 나머지"를 준다.** 그래서 "각 팀 화면에서 디자이너
  작업물 열람"은 새 화면이 아니라 **디자이너 탭의 노출 조건을 푸는 일**이었다 —
  탭 이름만 `작업함`으로 바꾸고 조회 팀을 소속에서 유도하니 팀원 화면이 거의 공짜로 나왔다.
- **결재는 전부 같은 모양**이다(제출→승인). `POST /tasks/{id}/approve` 하나로
  팀 작업도 디자이너 작업도 끝나고, 결재자만 다르다.

### 구현 중 드러난 것 3가지

- **`inbox_name`이 팀장 역할 때문에 깨졌다.** `startswith`로 아무거나 고르던 탓에
  `전산` → `전산팀장`이 걸려, 데모에서 **권 차장(전산 팀원)이 전산팀장으로** 나왔다.
  아는 팀이면 `팀` 접미사를 붙이도록 고쳤다(알림 이력 유무로 소속이 흔들리면 안 된다).
- **`agent/` 층은 `backend`를 import할 수 없다**(ports.py의 분리 관행). `FINAL_APPROVER`를
  쓰려다 걸려 `subagents.py`는 리터럴 `"본부장"`으로 두고 근거를 주석에 남겼다.
- **자물쇠가 꼭 필요했다** — `권한관리`를 모든 역할에서 끄면 아무도 그 화면에 못
  들어가 되돌릴 수 없다. 화면·서버 양쪽에서 막는다.

### 제출 조건 강화 (계획 H의 타협을 바로잡음)

계획 H는 결재할 화면이 없어 '작업 중이 아닐 것'으로 약하게 잡았다. 팀장 결재함이
생기면서 **`승인완료`(2차완료) 기준으로 올렸다.** 계획 H가 고정해 둔 테스트 4건이
정확히 그 지점에서 걸렸고, 새 규칙으로 갱신했다.

## Session 18:17 — 역할 모델 수정 (소속 3그룹 · 영업부장 최종결재)

계획 I를 화면으로 확인한 사용자가 역할 모델을 바로잡았다:

> "소속은 영업팀/전산팀/예산팀 3 그룹이 있다고 보고, 디자이너의 결재는 영업팀장한테
> 가는걸로 수정해줘. 위의 소속 구분에 '전산팀장'으로 되어있는건 잘못 된표기야.
> 최종 디자이너 산출물이 나오면, 영업팀장이 영업부장에게 그 결과물을 결재올리는걸로
> 종료할께. 본부장 개념은 없앨께."

### 확정 결정 4건 (AskUserQuestion)

| 물음 | 답 |
|---|---|
| 팀장·부장을 어떻게 고르나 | **소속 + 직책 2필드** (소속 3개 × 직책) |
| 디자이너의 소속 | **영업팀 소속** |
| 영업부장의 결재 범위 | **디자이너 최종본 + 8단계 최종결재 게이트** |
| 영업부장 기본 메뉴 | **전국지도 · 결재함 · 대화** 셋 |

### 새 결재 라인

```
팀원 ──제출──▶ 그 팀의 팀장 ──승인──▶ (3팀 전부 승인) ──▶ 디자이너 ──제출──▶
   영업팀장 ──승인(=상신)──▶ 영업부장 ──승인──▶ 최종완료(종료)
```

### 핵심 설계 판단

- **저장은 여전히 역할 문자열 하나.** 소속×직책은 *화면에서 고르는 방식*이고,
  `compose`/`split_role`이 잇는다. 프로필을 둘로 쪼개 저장하면 이미 쌓인 알림
  수신자와 `role_menus`의 키가 전부 갈라진다.
- **결재자 칸을 둘로 나눴다** (`approver` = 팀장, `final_approver` = 부장,
  `TASK_MIGRATIONS`로 컬럼 추가). 한 칸이면 1차를 본 영업팀장이 최종 결재까지
  잠가버려 영업부장이 403을 받는다 — 실제로 이 순서로 발견했다.
- **`_queue_for`가 (team, status) 쌍을 준다.** 팀만으로 거르면 같은 디자이너
  작업이 팀장·부장 결재함에 **동시에** 떠서 누가 볼 차례인지 알 수 없어진다.
- **영업팀장의 승인이 곧 상신이다.** 별도 상신 버튼을 두면 "승인해 놓고 안 올린"
  상태가 생긴다.
- **`split_role`은 모르는 값에 소속을 지어내지 않는다** — 옛 `본부장` 프로필에
  `영업팀/팀원`을 끼워 넣으면 사용자의 신원이 조용히 바뀐다. 화면은 그 값을 소속
  칸에 임시 항목(`data-legacy`)으로 그대로 보여준다.
- **부장·디자이너는 영업팀에만.** 없는 자리(`전산부장`)를 고를 수 있게 두면 그
  사람의 결재가 갈 곳을 잃는다.
- **`teamOf` 규칙 복제를 걷어냈다** — `designer.teamOf`가 `roles.teamOf`에
  위임한다. `부장` 접미사가 생겼을 때 한쪽만 고쳐지는 것을 실제로 겪은 자리다.

### ① `uploader/` — 사용자가 외부에서 만들어 온 Java 서비스

들였다. 스택이 이관 목표와 정확히 일치한다 — Spring Boot 2.7.18 · JDK 1.8 ·

ojdbc8 · **PDFBox 2.0.29** · **POI 5.2.3**.

설계가 "직접 만들어야 한다"고 적어둔 PDFBox·POI 경로가 **이미 동작 코드로 들어와

- 232파일 중 **73파일만 추적**. `.gitignore`에 `target/` · `*.class` · `.idea/` ·

**들여온 상태 그대로의 알려진 문제 4건** (계획 Task 1.1에 함정으로 기록):

### ② eGovFrame 제약 폐기 — 설계의 전제 하나가 틀렸었다

2026-08-05 브레인스토밍에서 **"eGovFrame 4.x 준수 필수"를 확정 제약으로 받아
적었다**(`2026-08-05_summary.md` 제약 4번). 그 한 줄이 설계 **제목** · **Spring Boot
배제** · **문의서 6번**까지 끌고 갔다.

이번 세션에서 사용자가 **"eGovFrame? 은 뭔지 모르겠다"** 고 해서 재검토했고,
**잘못 받은 확정**임이 드러났다 — eGovFrame은 행안부의 **공공기관 정보화사업 전용**
프레임워크인데 이관 목적지는 **당행 내부 표준 플랫폼**이라 적용 대상이 아니다.
제안 대상이 구청·지자체라는 점에서 혼선이 있었던 것으로 보인다.

⚠️ **되살아나는 조건**: 이 시스템을 지자체·공공기관에 **납품**하기로 하는 경우.
각 문서에 이 조건을 명시했다.

**폐기의 이득 2가지:**
1. **문의 항목 하나가 통째로 사라졌다** — 종전 6번(eGovFrame 표준 템플릿의
   `async-supported`). `web.xml`을 우리가 소유하게 되어 물을 게 아니라 **Task 1.2에서
   직접 켜면 되는 설정**이 됐다.
2. **`uploader/`가 단계 1(골격)의 실물 출발점**이 됐다. Spring Boot 구조를 그대로
   쓸 수 있어 빈 템플릿에서 시작하지 않는다.

### ③ 경유지 + OAuth — 확정 사실로 들어왔다

사용자가 알려준 인프라 구조: **모든 서비스 간 호출이 회사 공통 API 게이트웨이
(경유지)를 거치고 OAuth 인증을 수행**한다. uploader는 **당행 망 내부**이고, 망 내부
업로드 파일은 신경 쓰지 않아도 된다.

이걸로 **어제까지의 지적 3건이 무효가 됐다** — ⓐ`collector/SCHEMA.md` §① 단방향
계약 위반 우려(uploader는 수집기가 아니라 망 내부 동료 서비스다) ⓑeGovFrame vs
Spring Boot 충돌 ⓒ파일명 규칙 vs `manifest.json` 계약. **`collector/` 아래 두자던
추천도 철회했다.** 유효하게 남은 것은 **기관 ID 이중 진실** 하나뿐이다(망 경계와
무관한 순수 데이터 모델 충돌).

**대신 새로 생긴 것:**
- 설계 §2에 **서비스 간 통신 행 신설**, §3 다이어그램에 게이트웨이 추가.
- **§6-C에 OAuth 토큰 계층 신설** — 개정 전 설계는 엔드포인트를 직접 부르는 전제라
  토큰 처리 자리가 **아예 없었다**. 토큰 획득·캐시·선제 갱신 + 401 재시도, 로그·
  `messages`·예외 메시지에 토큰 금지.
  ⚠️ **폴백과 인증 실패를 구분**해야 한다 — 1순위 실패가 401/403이면 2순위도 똑같이
  실패하므로 폴백을 태우지 말고 즉시 사람에게 알린다. 안 그러면 **토큰 만료가
  "모델 2개가 다 죽었다"로 보고된다.**
- **문의 7번의 성격이 바뀌었다** — "앞단에 웹서버를 두는 구성인가"(유무 확인)에서

  가설이 아니라 확정 리스크다.

### ⑥ uploader 붙이기 = 이관 후 단계 6 (사용자 확정)

처음에 **순서를 거꾸로 제안했다** — `server/`(Python)에 중계 라우터를 만들자고 했다.
사용자가 바로잡았다: **전제는 "Java로 간다"이고 uploader는 이미 Java다. 아직 Python인
것은 기존 프로젝트뿐이니, 그걸 먼저 변환하고 나면 uploader를 붙이는 건 일도 아니다.**

맞는 지적이었다. 이관 전에 붙이면 브라우저에 서비스 토큰을 실을 수 없어 `server/`가
중계할 수밖에 없고, 그 코드는 이관 때 통째로 버려진다.

⚠️ 단 **`frontend/` 쪽 작업은 버려지지 않는다** — 설계 §3 원칙 1이 "화면은 손대지
않는다(WAR 정적 리소스로 그대로)"라, 아래 조사 결과는 이관 후에도 그대로 유효하다.

**사용자 요구사항**: `IT담당자`·`RPA`가 접속하면 파일 업로드 상태가 화면에 보이면
좋겠다. 화면은 uploader의 Thymeleaf가 아니라 **기존 `frontend/` 디자인**으로.
붙이는 방식은 **`frontend/`에 새 탭 + uploader API 호출**(사용자 확정 '1안').

**사전 조사 결과 (계획 단계 6 + NEXT.md 항목 17에 기록 — 다시 조사하지 말 것):**
- **역할 추가 0건.** `server/menus.py`에 `out["전산팀"][ADMIN_MENU] = True`가 이미
  있다 — **IT담당자 = 전산팀 팀원/팀장**으로 존재한다(사용자 확정).
  ⚠️ 역할 체계는 건드리지 말 것 — 소속 3그룹은 사용자 확정이고 역할은 합쳐진 문자열
  하나로 저장되므로, 새 소속을 끼우면 알림 수신자·`role_menus` 키가 갈라진다.
- **`RPA`는 역할 목록에 넣지 않는다.** `roles.ALL`은 결재 라인(`approverOf`·
  `lead_of`)과 알림 수신자의 근거라, 프로그램이 섞이면 "RPA의 결재자는 누구인가"가
  생긴다. RPA는 **파일을 올리는 쪽**이고 화면을 보는 것은 IT담당자다.
- **탭 추가는 6곳**(`menus.py` / `menu_rules.js` / `index.html` / `app.js` / 신규
  `uploads.js` / 테스트). **권한관리 화면은 자동으로 따라온다** — `admin.js`가
  `GET /menus` 목록을 그대로 그려 **열이 저절로 생긴다.**
- ⚠️ **함정**: 탭 key와 section id가 어긋난 전례가 있다(`tasks` 키 ↔ `tab-designer`).
  새 탭은 키와 id를 같게 맞출 것. 또 기본값을 코드에 둬야 한다 — "DB에 행이 없다는
  것은 '꺼짐'이 아니라 '아직 정하지 않음'"이라 기본값이 없으면 아무도 못 본다.

**확인이 필요한 미해결 2건:**
1. **`UPLOADED_FILE`에 업로드 주체 컬럼이 없다** — 사람이 올린 것과 RPA가 올린 것을
   화면에서 구분할 수 없다. 구분이 필요하면 컬럼 추가가 선행된다.
2. **`GET /api/files/search`가 목록용으로 무겁다** — 결과마다 파일 본문 전체 텍스트를
   담고(PDF를 전부 파싱) **페이징이 없다.** 문의 6-2 회신 때 함께 정리하기로 했다.

### 곁가지 — 커밋 메시지 사고 1건

`Bash` 도구에서 PowerShell here-string 문법(`@'…'@`)을 써서 커밋 메시지 앞뒤에 `@`
문자가 들어갔다. `--amend`로 heredoc(`<<'MSG'`)을 써서 고쳤다. **Bash 도구에서는
heredoc, PowerShell 도구에서만 here-string.**

**보고: 시스템 관리에 메뉴 순서 바꾸기를 넣을 수 있나**

결론: 가능합니다. 개인별(브라우저 저장)이면 서버 변경 없이 화면 쪽만으로 됩니다. 전사 공통이면 서버 저장 API가 새로 필요합니다. "순서만 바꾸기"와 "대분류까지 옮기기"는 범위가 크게 다릅니다.

**대상·방법·못 본 것**
- 읽은 파일: frontend/js/nav.js, admin.js, app.js(paintNav 부근), test/nav.test.js·admin.test.js(grep 위주), NEXT 54.
- 읽지 않은 것: server/menus.py와 /menus 응답 스키마(① 일부는 추측), 사이드바 DOM(drawNav)이 순서를 built 배열 그대로 쓰는지.
- 서버 화면은 열지 않았습니다.

**① 현재 정의와 동결 키와의 관계**
- 메뉴 순서와 구성은 전부 코드 상수입니다. nav.js:32의 nav.CATEGORIES가 대분류 7개와 하위 항목을 정의하고, 정의 순서가 업무 흐름 순서입니다.
- 서버 /menus는 권한(어느 역할이 어느 키를 보는지)만 줍니다. 순서는 주지 않습니다(nav.js·admin.js 코드 기준, 서버 스키마는 미확인). app.js:666이 nav.build(visible, ctx)로 상수 정의와 서버 권한을 합쳐 사이드바를 만듭니다.
- nav.build(nav.js:70)의 정렬은 세 단계입니다. 정의 순서가 기본이고, 카테고리 안에서는 구현 항목이 준비중 항목보다 위이며, 카테고리는 "구현 있음 → 준비중뿐 → 시스템 관리(last)" 순입니다. 이 규칙(nav.js:13의 4번 원칙)과 사용자가 바꾼 순서가 충돌하므로 결정이 필요합니다(② 참조).
- 동결 키 8개와 순서는 서로 독립입니다. 순서를 바꿔도 key·view가 그대로면 권한·골든 테스트는 건드리지 않습니다.
- 관리 화면 격자의 열 순서(admin.menuColumns, admin.js:184)도 CATEGORIES를 따르므로, 순서를 바꾸면 격자 열 순서도 같이 바뀝니다. 의도된 동작인지 확인이 필요합니다.

**② 화면에서 바뀌는 곳**
- 관리 화면 UI: admin.js의 VIEWS(admin.js:55)에 4개 보기(사용자·권한·메뉴·접근 이력)가 있습니다. 두 가지 중 하나로 넣습니다.
  - (a) 기존 '메뉴 관리'(paintMenus) 아래에 "메뉴 순서" 구역을 추가합니다.
  - (b) 보기를 새로 추가합니다. 이러면 nav.js의 sys 항목과 nav.test.js:166 부근 테스트도 바뀝니다.
  - (a)를 권합니다.
- UI 모양: 대분류별 목록에서 항목마다 위·아래 버튼을 두는 방식을 권합니다. 드래그는 접근성과 테스트 면에서 부담입니다. 맨 아래에 "기본 순서로 되돌리기"와 저장 버튼을 둡니다. 확인은 confirm()이 아니라 인라인으로 합니다. 디자인 규격은 design-reviewer 몫입니다.
- nav.js가 저장된 순서를 읽는 방식: 순수 함수 nav.applyOrder(categories, orderMap)를 새로 만들고, nav.build가 저장된 순서를 선택 인자로 받도록 합니다.
  - 저장 형식은 {카테고리id: [항목id,…]} 한 가지입니다.
  - 저장 목록에 없는 새 항목은 기본 위치에 붙이고, 정의에서 사라진 id는 버립니다. 이 규칙이 새 준비중 탭이 추가될 때를 지켜 줍니다.
  - nav.CATEGORIES 자체는 바꾸지 않고 정렬 결과만 만듭니다. 기본 순서가 항상 남습니다.
- 키 없는 준비중 항목도 순서 대상에 넣을 수 있습니다. 준비중 항목 id는 'soon:' + 라벨(nav.js:84)이고, 이미 탭·하이라이트에서 쓰는 안정 키입니다. 라벨이 정의 전체에서 유일하다는 테스트(nav.test.js:238)가 지켜 줍니다. 그래서 이 id를 순서 저장 키로 그대로 씁니다. 주의: 준비중 라벨을 바꾸면 저장된 순서가 끊깁니다(위 규칙대로 기본 위치로 붙음).
- 정할 점: 준비중 항목을 구현 항목 위로 올릴 수 있게 할지. 허용하면 nav.js:13의 4번 원칙과 충돌합니다. 보수적인 쪽은 구현 그룹과 준비중 그룹 안에서만 이동을 허용하는 것입니다(기획·디자인이 정함).
- 3단 구조와의 관계: NEXT 54의 3단 재편은 CATEGORIES의 모양 자체를 바꿉니다. 지금 2단 기준으로 저장 형식을 만들면 재편 때 다시 만들어야 합니다. 순서 기능은 3단 확정 뒤에 만들기를 권합니다. 급하면 저장 형식을 "부모 id → 자식 id 배열"의 재귀 맵으로 만들어 단수 변경에 견디게 합니다.

**③ 저장 위치 선택지**
- 브라우저 저장(localStorage, 개인별): store.js 패턴(LS() + try/catch, store.js:11·116)으로 충분합니다. 서버 영향이 없고(키 8개·/menus 동결과 무관) 되돌리기도 쉽습니다. 단점은 사람마다 그 PC에서만 적용되어, 사용자가 "시스템 관리 기능"으로 기대한 것과 어긋날 수 있다는 점입니다.
- 서버 저장(전사 공통): 새 엔드포인트와 설정 저장 위치가 필요합니다(백엔드 몫). /menus 계약을 건드리지 않으려면 별도 경로로 둡니다. 읽기는 로그인한 모두, 쓰기는 전산팀, 실패 시 기본 순서로 폴백하도록 정해야 합니다. 프런트는 초기 로드 시 요청이 하나 늘어납니다.
- 사용자의 목적이 전사 공통일 가능성이 큽니다(추측). 권장은 단계적 접근입니다. 1단계로 nav.applyOrder와 UI를 브라우저 저장으로 먼저 만들고, 2단계에서 저장소만 서버로 바꿉니다. 이때 UI를 그대로 쓰도록 저장소를 한 쌍의 함수(loadOrder/saveOrder)로 감쌉니다. 다만 목적이 전사 공통이면 1단계는 중간 산출물일 뿐이므로 먼저 사용자에게 확인합니다.

**④ 규모 추정과 위험(추정)**
- JS 규모: nav.js 약 40~60줄(applyOrder, build 연동, 정규화), admin.js 약 80~120줄(순서 구역 UI·위/아래 이동·저장·되돌리기), app.js 약 10~20줄(저장된 순서를 paintNav에 전달), index.html 스타일 약 20~30줄. 합계 약 150~230줄.
- 테스트: nav.test.js에 applyOrder 케이스 8~12건, admin.test.js에 이동 로직 4~6건. 합계 약 12~18건.
- 깨질 기존 테스트: nav.test.js:166-184는 CATEGORIES 정의 순서를 못 박지만, 기본 정의를 안 바꾸므로 안 깨집니다. 순서 인자가 없을 때 build가 지금과 똑같이 동작하게 해서 build 정렬 테스트를 지킵니다.
- 키 변경 위험: 이 설계는 key·view를 건드리지 않습니다. 순서 저장에 쓰는 id는 key 또는 key:view, 준비중은 soon:라벨입니다. 위험은 두 가지입니다.
  - 준비중 라벨 변경이나 3단 재편으로 라벨이 이동하면 저장된 순서가 조용히 어긋납니다(새 항목은 기본 위치에 붙임).
  - 사용자가 admin(시스템 관리)을 위로 올려 헷갈리게 하는 경우입니다. last:true와 admin 접근 경로는 이동 대상에서 제외하기를 권합니다.
- 활성 메뉴·탭: navActiveId·탭·openCat이 모두 id 기준이라 순서를 바꿔도 안 깨집니다.
- 되돌리기: 저장값을 지우면 기본으로 돌아갑니다. "기본 순서로 되돌리기" 버튼과 저장 형식 버전 값(예: v:1)을 두고, 버전이 다르면 무시합니다.
- 가장 큰 위험은 3단 재편(NEXT 54)과의 충돌입니다. 순서 기능을 먼저 만들면 저장 형식과 UI를 다시 손봐야 합니다.

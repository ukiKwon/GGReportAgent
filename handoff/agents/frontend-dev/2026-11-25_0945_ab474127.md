## 2. 원인·요구 요약

**1번(구분값이 사라짐)과 4번([수정하기]가 안 보임)은 같은 원인이다.**
- 구분 칩 자체는 서버의 `tag_name`으로 그려진다. 응답에는 "신규유치 도전"이 들어 있어서, 표의 칩은 있어야 한다. 사라진 것은 칩을 눌렀을 때 뜨는 메뉴 안의 구분 선택지(RETAIN·REGAIN·NEW 라디오)로 보인다. 표 칸이 비어 보인 것이 아니라면 이 해석이 맞다. 화면으로 확인하지 못했으니 사용자에게 어느 쪽인지 물어보면 정확하다.
- kbboard.js:2102 `canValueEdit(r)`는 목표 줄이면 `gs.data.value_edit_mode === 'DIRECT'`이거나 `goalMode() === 'DIRECT'`일 때만 참이다. 옛 서버는 이 키를 안 주고 모드는 APPROVAL이라 거짓이 된다.
- kbboard.js:2032 `openMenu`는 거짓이면 `tags: []`를 넘긴다. 그래서 메뉴에 구분 선택지가 없고, `canMemo: false`, `canMove: true`, `approval: true`로 "결재 필요 / 내 관심으로… / 목표에서 빼기… / 협약 개시일 적기…"만 남는다. 사용자가 본 창이 바로 이것이다.
- kbboard.js:2689 `paintSel`은 `canBulkEdit()`(kbboard.js:2691)이 같은 키를 보고, 거짓이면 `#hb-seledit`을 숨긴다. 그래서 띠의 오른쪽 끝에 [수정하기…]가 없다.
- 띠 마크업은 tchange.js:313-319 `selbarHtml`이고 CSS는 index.html:2435-2448인데, 레이아웃이 깨진 것은 아니다. 숨김 판정(`hidden`) 문제다.

**서버를 재기동해 현재 소스로 올리면 1·4번은 사라질 가능성이 높다.** 단, 이 가설은 아직 확인하지 못했다. 옛 서버에서는 구분 저장 요청도 결재 경로로 거절되므로, 프런트만 고쳐서는 해결되지 않는다.

**현재 구조 (2·3·5번)**
- 구분 바로 저장 경로: `changeTag`(kbboard.js:2076) → `kbb.valueBody`(kbboard.js:1492)로 현재 값 전체에 `tag_cd`만 덮어쓴 본문을 만들고 → `kbb.saveTarget` → `POST /institutions/{id}/bid-targets`(BidTargetController.java:62), 버튼 이름은 `kbb.BTN.tag`(감사 이름 change_target_tag)다. 서버는 `BidTargetRules.valueOnlyEdit`(BidTargetService.java:346)가 참이면 결재 없이 저장하고 `direct_basis=VALUE_EDIT`을 돌려준다.
- 메뉴 항목 조립은 `kbb.menuHtml`(kbboard.js:1029-)이다. 구분 → 메모 고치기 → 협약 개시일 적기 → (결재 필요) 옮기기·빼기 순이다.
- **5번 [수정하기…]는 이미 다건이다.** `#hb-seledit`을 누르면 `openChange({kind:'edit'})`(kbboard.js:3163, 2852)가 열린다. 고른 줄 전부(최대 `tc.MAX_ITEMS`=20곳)를 담은 `tc.editDialogHtml`(tchange.js:426)이 뜨고, 줄마다 구분·메모 칸과 "구분 한꺼번에 정하기" 선택(`#tc-alltag`, 2곳 이상일 때)이 있다. 저장은 `kbb.submitChanges(…, tc.BTN.values)` → `POST /bid-targets/changes`(BidTargetController.java:122)로 간다. 서버 `TargetChangeService`(123-143행)는 모든 항목이 구분·메모만 고치는 EDIT이면 `valueOnly`로 보고 결재 없이 바로 반영한다. 지난해 목표는 결재(180행), 관심이 섞이면 [수정하기]가 숨는다. 따라서 **다건에 서버 변경은 필요 없다.** 사용자가 못 쓴 것은 4번(버튼이 숨음)과 같은 원인이다.
- 고른 상태 구조: `gs.sel = tc.newSel()` = `{ ids: [기관 id…], by: { [기관id]: entry } }`다. 기관 하나에 한 줄이고, entry는 `tc.entryOfRow(r)`로 만든다.
  - entry 필드: `id, name, regionName, kind('GOAL'|'WATCH'), targetNo, revNo, year, tagCd, tagName, memo, ownerEmpNo, moveYear, closed`.
  - 보조 변수는 `gs.selMsg`(띠 알림 글)다.
  - 도우미(tchange.js): `tc.selCount(sel)`, `tc.isPicked`, `tc.pick`, `tc.unpickRow`, `tc.clearSel`, `tc.kindCounts`, `tc.pickedMap`.
  - DOM: 줄 체크박스 `input[data-pick="기관id"]`, 머리 체크박스 `#hb-pickall`, 고른 줄 `tr.picked`, 띠 `#hb-selbar`·`#hb-seln`·`#hb-selclr`·`#hb-seledit`.
  - 그리기: `syncPickDom()`(kbboard.js:2666)과 `paintSel()`(2676)이 DOM과 띠를 고친다. 표를 다시 그리는 `renderGoals`(1837)는 `paintSel`(1877)을 호출하고, 목록을 다시 받으면 `tc.reconcile`(kbboard.js:1854)이 고른 줄의 revNo 등을 새 값으로 제자리 갱신한다.
  - 선택은 탭·연도·거르기를 바꿔도 유지된다. 화면 밖에 고른 줄은 `paintSel` 안의 `off`로 센다.
  - **[제안 사전준비]**: 켜는 조건은 `tc.selCount(gs.sel) === 1`로 하고, 그 기관 id는 `gs.sel.ids[0]`이다. `paintSel`에서 `hb-seledit`을 켜고 끄는 줄(2689) 옆에서 같이 켜고 끄는 것이 자연스럽다. 툴바 마크업은 별도 작업이다.

## 3. 구현안

**P0. 코드 아님 — 8080 서버를 현재 작업 트리 빌드로 재기동한다(호출자·사용자 영역).** 재기동 뒤 응답에 `"value_edit_mode":"DIRECT"`가 오는지 확인한다. 이것으로 1·4번은 풀릴 가능성이 높다. 풀리지 않으면 그때 프런트 판정을 다시 본다.

**P1. 2번 — 구분 메뉴를 구분 선택만 남긴다(kbboard.js openMenu, 2032-2035행).**
적용 순서는 시험(아래 4절) 먼저, 그다음 구현이다. 관심 줄 메뉴는 그대로 둔다(관심 줄의 [내 관심에서 빼기…]는 결재가 아니고 다른 입구가 없다).
```
old:
    wrap.innerHTML = kbb.menuHtml(r, { tags: canValueEdit(r) ? tagList() : [], def: kbb.fitTag(kbb.defaultTag(r.rec, gs.sum[r.id], tagOpts()), tagList()), canCancel: r.canCancel,
      canMove: r.kind !== 'WATCH' && !noWatchNow(), cancelText: r.kind === 'WATCH' ? '내 관심에서 빼기…' : '',
      canTerm: r.kind !== 'WATCH' && !!r.judgeFrom && !r.pend, judgeText: tc.judgeText(r),   // judge_from이 있는 서버만 협약 개시일 항목
      canMemo: canValueEdit(r), approval: isApproval() && r.kind !== 'WATCH' });
new:
    const goalRow = r.kind !== 'WATCH';   // 목표 줄 구분 칩 = 구분 선택만(사용자 11-25). 메모·협약 개시일·옮기기·빼기는 이 메뉴에 두지 않는다
    wrap.innerHTML = kbb.menuHtml(r, { tags: canValueEdit(r) ? tagList() : [], def: kbb.fitTag(kbb.defaultTag(r.rec, gs.sel_unused_placeholder, tagOpts()), tagList()), canCancel: !goalRow && r.canCancel,
      canMove: false, cancelText: goalRow ? '' : '내 관심에서 빼기…',
      canTerm: false, judgeText: goalRow ? '' : tc.judgeText(r),
      canMemo: !goalRow && canValueEdit(r), approval: false });
```
주의: 위 `new`의 `gs.sel_unused_placeholder`는 오타 방지용 표시일 뿐이다. 적용할 때는 원문 그대로 `gs.sum[r.id]`를 유지한다. 자동 제안(`def`) 머리글 줄은 유지하는 안이다. 이것도 지울지는 질문 1에 있다.

**부작용(중요)**: 위 패치로 목표 줄에서 [목표에서 빼기…]·[내 관심으로…]·[협약 개시일 적기…]·[메모 고치기…]로 가는 입구가 사라진다. 7163e0a9 이후 띠에는 결재 단추가 없고(tchange.js:314 주석: "결재 동작은 줄의 구분 메뉴에서 한다"), 입찰 종료 줄은 `closedActsHtml`에 자체 단추가 있어 괜찮다. 그 밖의 줄은 다른 입구가 없다. 메모는 [수정하기…] 창에서 고칠 수 있다. 빼기·옮기기·협약 개시일의 새 자리는 기획·디자인 결정이 필요하다(이관·질문 참고).

**P2. 3번 — 구분을 바꾸면 그 줄 체크박스를 자동으로 체크한다(kbboard.js changeTag, 2086-2090행).**
saved 분기에서 `loadGoals()` 앞에 한 줄을 추가한다. 20곳 한도에 닿으면 체크하지 않고 띠에 알린다.
```
old:
        gs.just = { inst: r.id };   // 바뀐 줄 잠깐 강조(.hb-just)
        loadGoals();
new:
        gs.just = { inst: r.id };   // 바뀐 줄 잠깐 강조(.hb-just)
        if (tc.pickable(r) && r.kind !== 'WATCH') { const pk = tc.pick(gs.sel, tc.entryOfRow(r)); gs.selMsg = pk.ok ? '' : pk.msg; }   // 구분을 바꾼 줄은 자동으로 고른다(사용자 11-25) — 이어서 [수정하기]로 메모·다른 기관까지
        loadGoals();
```
- `loadGoals` → `renderGoals`가 `paintSel`과 `picked` 맵으로 체크박스와 띠를 그린다. `tc.reconcile`이 entry의 revNo·tagCd를 새 값으로 맞춘다.
- 이미 골라 둔 줄이면 `tc.pick`은 ok를 돌려줄 뿐 아무것도 바꾸지 않는다.
- 관심 줄까지 자동 체크할지는 질문 2에 있다. 위 패치는 목표 줄만 체크한다.
- 못 확인한 것: 목록 재조회가 실패하면 entry의 revNo가 옛 값으로 남아 [수정하기] 저장이 409 STALE이 될 수 있다. 그 경우 기존 stale 처리 문구가 뜨고 목록이 다시 읽힌다.

**P3. 4번 — 코드 변경 없음(P0로 해결).** 선택 사항으로, `canBulkEdit`과 `canValueEdit`이 서버 키가 없는 옛 서버에서도 거짓이 되지 않게 하려면 `can_edit`를 쓰는 방법이 있다. 하지만 옛 서버는 어차피 결재 경로라 저장이 거절되므로 권하지 않는다.

**P4. 5번 — 코드 변경 없음, 서버 변경 없음.** 이미 다건이다. 사용자가 "한 건만 되는 것처럼" 느꼈다면 버튼이 숨었던 것이 원인이다. 별도로 "구분만 한꺼번에 바꾸는 더 단순한 창"을 원하는지는 질문 3에 있다.

## 7. 열린 질문
1. 구분 메뉴에서 윗줄의 "자동 제안: …" 설명 줄도 지울까, 둘까? 둘 경우 메뉴가 "설명 + 구분 3개"가 된다.
2. 구분을 바꾸면 자동 체크하는 대상에 내 관심 줄도 넣을까? 현재 안은 목표 줄만이다. 관심 줄은 [수정하기]가 숨는 줄이라 체크해도 쓸 곳이 적다.
3. [수정하기…] 창에 이미 "구분 한꺼번에 정하기"가 있다. 그 창 말고 띠에서 곧바로 구분만 고르는 더 간단한 입구가 필요한가?
4. 1번에서 사라졌다는 것이 "표의 구분 칩 글자"인지 "칩을 눌렀을 때 메뉴의 선택지"인지 사용자에게 확인이 필요하다. 서버 재기동 뒤에도 같으면 알려 달라.

## 2. 원인
- **팝오버 머리 배지.** `render.js`의 `popoverHtml`이 `logic.formatDDay(rec, today)`를 쓴다. 이 함수는 `effectiveBid`만 보기 때문에 공고일 2026-10-29가 지난 날짜로 계산돼 `D+15`가 나온다.
- **팝오버 '입찰 예정일' 줄.** 같은 함수에서 `bid.date`와 확정 표기를 그대로 보여준다. `noticeState`는 보지 않는다.
- **순위표 줄.** `drawRankingPanel`의 `logic.formatBidDateLabel(r)`가 `2026-10-29(확정)`을 만든다.
- **현황판과의 차이.** `dashboard.js`의 `mdDot`, `ddText`, `noticeNote`는 모듈 안의 비공개 함수다. `render.js`는 node 테스트에서 `dashboard.js`를 로드하지 않으므로 직접 재사용할 수 없다.
- **재사용 방식.** 규칙은 순수 함수라서 `logic.js`에 둔다. `dashboard.js`는 건드리지 않고, 표현은 같은 문구로 맞춘다. 이 중복은 이관 메모에 적었다.

## 3. 구현안 (적용 순서: 테스트 → logic → render)

### 패치 A. `frontend/js/logic.js`
`logic.noticeSummary`의 닫는 `};` 바로 뒤, 즉 `// 경과 판정:` 주석 위에 추가한다.

```js
  // 지도 팝오버·순위표용 공고 진행 한눈 표현(dashboard.js의 칩·noticeNote와 같은 용어). 진행 중이 아니면 null.
  // badge: 접수 마감 전 '마감 D-n' / 마감일 미확인(30일 이내) '공고 진행 중' / 마감 지남·미확인 30일 초과 '결과 확인'.
  // cls: 팝오버 배지 색 계열(.dg-day) — 접수 마감 전만 urgent, 나머지는 unknown(무채색).
  // detail = '2026-10-29 · 접수 11.16~11.19', line = '공고 ' + detail.
  logic.noticeBrief = function (rec, today) {
    const ns = logic.noticeState(rec, today);
    if (!ns) return null;
    const md = function (s) { const m = /^\d{4}-(\d{2})-(\d{2})$/.exec(String(s || '')); return m ? m[1] + '.' + m[2] : ''; };
    let badge, cls;
    if (ns.phase === 'receiving') { badge = '마감 ' + (ns.deadlineDays === 0 ? 'D-day' : 'D-' + ns.deadlineDays); cls = 'urgent'; }
    else if (ns.check) { badge = '결과 확인'; cls = 'unknown'; }
    else { badge = '공고 진행 중'; cls = 'unknown'; }
    let span;
    if (ns.receiveFrom && ns.receiveTo) span = '접수 ' + md(ns.receiveFrom) + '~' + md(ns.receiveTo);
    else if (ns.receiveTo) span = '마감 ' + md(ns.receiveTo);
    else span = '마감일 미확인';
    const detail = rec.contractEnd + ' · ' + span;
    return { badge: badge, cls: cls, detail: detail, line: '공고 ' + detail, phase: ns.phase, state: ns };
  };
```

현재는 '현 유치 은행', '임직원 수', '기관장' 세 줄이 모두 `unk`(미확인 자리표시)다. 기관장 줄만 바꾼다.

- `.pop-unk`의 점선 테두리 스타일을 재사용하므로 CSS 변경은 없다.
- 아래 `pop-note`('미확인 칸은 … 채워집니다.')는 현 유치 은행·임직원 수에 계속 맞는다.

**최소안과 연결안 비교**

| | 최소안(자리표시 문구 변경) | 연결안(GET /institutions/{id}/head) |
|---|---|---|
| 변경 범위 | 문구 한 줄 | `render.js`에서 `headcard.js`를 호출하고 비동기 렌더, 로딩·권한 실패 처리, 서버 모드 분기 |
| 열람 감사 기록 | 없음 | 마커·순위표를 훑을 때마다 head_card 열람이 기록될 수 있다. 0.4초 debounce만으로는 훑기 노이즈를 막기 어렵다 |
| 비서버(정적) 모드 | 그대로 동작 | 서버가 없으면 숨기거나 대체 문구가 따로 필요하다 |
| 테스트 | `prep.test.js:634` 한 줄 | 서버 모의, 권한, debounce 테스트 추가 |

- 권장은 최소안이다. 연결하려면 '팝오버 열림'이 아니라 '[기관장 보기] 버튼 클릭'처럼 사용자가 명시한 동작에서만 호출해야 한다. 그래야 감사 기록이 의미 있는 열람만 쌓인다.
- 그 전에 기획의 결정이 필요하다. 지도 팝오버에 기관장을 노출해도 되는지, 노출한다면 어떤 권한과 열람 목적 문구가 필요한지다.

## 5. 위험·되돌리는 법
- **마커 색과 순위 정렬.** `render.js` 마커 라벨·▲·색은 이미 `noticeState`를 반영한다. 이번 패치는 팝오버와 순위표 줄의 글만 바꾸므로 지도 렌더 코드는 건드리지 않는다.
- **`type` null 처리.** 위 B-2에 적었다. 실제 데이터에서 `type`이 null인 레코드가 있는지만 한 번 확인한다.
- **`.dg-day.urgent`의 의미.** 팝오버에서 '접수 마감 전'을 빨강으로 쓰는데, 현황판 칩 `open`도 빨강이라 일관된다. '결과 확인'은 무채색이다.
- **중복 구현.** `dashboard.js`의 `noticeNote`와 `noticeChipHtml`이 별도 문구를 갖는다. 문구를 바꾸면 두 곳을 같이 고쳐야 한다.
- **되돌리기.** 패치 A·B·C를 되돌리면 된다. 변경은 `logic.js` 1개 함수, `render.js` 4곳, 테스트 2곳이고 데이터 스키마와 DOM id는 바뀌지 않는다.

## 6. 이관 메모
- **[이관: 기획]** 팝오버에 기관장을 연결할지 결정해야 한다. 노출 범위와 권한, 열람 목적 문구, '버튼 클릭 시에만 호출' 방식이 맞는지를 정해 달라. 기다리는 것은 기획의 결정이다. 근거는 headcard가 0.4초 debounce와 `X-Screen-Id head_card`로 열람을 감사 기록하기 때문에 훑기마다 기록이 쌓인다는 점이다.
- **[이관: 디자인]** 팝오버 공고 줄의 dt를 '공고 진행'으로 쓰고 배지 색을 마감 전 빨강, 그 외 무채색으로 한 것을 규격과 대조해 달라. 기다리는 것은 design-reviewer의 확인이다. 근거는 `dashboard.js`의 `db-chip.open/.wait` 색 규칙을 따랐다는 점이다.
- **[이관: 프런트 후속]** `dashboard.js`의 `noticeNote`와 `noticeChipHtml`을 `logic.noticeBrief`로 통합하면 문구 중복이 사라진다. 이번 범위 밖이다.

## 2. 확정한 사실(코드 근거)
- **ack 본문 키**: 전역 SNAKE_CASE다(`DocCheckAckIn.java:5` 주석). 키는 `{acked, sha256, items:[{inst_id, loc_kind, loc_no}]}`이고 규격 6-3과 일치한다. `by`는 받지 않는다.
- **오류 본문**
  - 코드 오류: `{"detail":{"code":"…","message":"…"}}`(`DesignReviewService.coded`가 detail 객체에 `code`를 넣는다. `ApiException.withDetail`도 같은 방식이다).
  - 평문 오류: `{"detail":"문장"}`. 401·403·404·400 일반 검증은 평문이다(`DocCheckService.deniedOwner`, `ApiException.notFound`·`badRequest`).
  - 코드가 붙는 것: 409 `TASK_LOCKED`, 409 `DOC_CHECK_STALE`, 503 `DOC_CHECK_BUSY`, 400 `ACTIVE_CONTENT`(TaskFileService.java:109·112, PrepAttachInspector).
- **state**: `DONE`, `PARTIAL`, `NOT_CHECKED`, `ERROR`(`TaskDocExtractor.java:41-44`). 낡은 결과는 `NOT_CHECKED` + reason `STALE`이다.
- **reason 전체**(코드에서 grep): BUSY, TIMEOUT, STALE, INTERNAL, ARCHIVE, IMAGE_ONLY, FORMAT_UNSUPPORTED, FORMAT_MISMATCH, ENCRYPTED, BROKEN, TOO_LARGE, NO_TEXT, TEXT_CAP, TOO_MANY_PAGES, HIT_CAP, ACTIVE_CONTENT, ATTACHMENT. 규격 표의 17개와 정확히 일치하고 모르는 코드는 없다.
- **허용 헤더**(`DocCheckUiIds`): 화면은 `design_work`, `task_work`. 단추는 `doc_check_ack`, `doc_check_unack`, `doc_check_recheck`, `doc_check_submit_anyway`, `submit`, `design_complete`. 규격 6-6과 일치한다.
- **파일 상태**
  - `designer.js`는 CRLF다(467줄 모두 `\r`). `index.html`은 LF다.
  - `designer.js`의 여러 줄 old는 LF로 쓰면 편집 도구가 못 찾을 수 있다. old·new 줄바꿈을 CRLF로 맞춰 적용해야 한다. new를 LF로만 넣으면 줄바꿈이 섞이니 같이 맞춘다.
  - `index.html` 패치는 전부 한 줄 old이거나 LF라 안전하다.
- **0d 충돌 회피**: `index.html` 패치 앵커는 `#tab-designer`(2937·2944줄), 작업함 CSS(1193·1204줄), 모달 삽입점(`<!-- 순수 로직 -->` + `dlg.js` 줄), `designer.js` script 줄이다. `#ov-pop`·`overdue` 영역은 건드리지 않는다. `dlg.js`는 `open(overlay,{focus,restoreFallback,onClose})`, `close(overlay,{restore:false})`, `requestClose`, `setDisabled`만 쓰고 고치지 않는다.

## 5. 위험·되돌리는 법
- **CRLF**: `designer.js`는 CRLF다. 여러 줄 old가 안 맞으면 old·new를 CRLF로 맞춘다.

## 6. 의심 지점·규격과 다르게 한 곳
1. **P1**: 오류 응답이 JSON이 아닌 경우(프록시 HTML 등)에도 `readErr`가 상태 코드만으로 처리한다. `upload`는 `r.json().catch`로 감쌌다.
2. **P2**: 점검 요약이 모두 0이어도 확인해 둔(acked) 건이 있으면 제목 옆이 `찾은 이름 없음(파일 n개)`로 나온다(규격 6-1 글자대로). 사실과 다를 수 있어 `확인함 n건` 한 줄을 더할지 디자인 확인이 필요하다.
3. **P2**: 규격에 없는 자리는 기존 문구를 유지했다.
   - 올리기·제출·삭제의 일반 실패 `업로드 실패 (n)`·`제출 실패 (n)`·`삭제 실패 (n)`.
   - 제출 연결 실패 `서버 연결 실패 — 제출되지 않았습니다.`
   - 올리기 평문 사유(허용 확장자·크기)는 서버 문장을 그대로 보여 준다(기존 동작 유지, 코드 오류 문구만 서버 message를 안 쓴다).
   - 새로 만든 것은 `처리 실패 (n)` 하나(다시 점검·문맥의 403 등)다.
4. **P3**: 규격 5-1 PARTIAL 행의 "사유 문구"는 행에 쓰지 않고 펼침 칸 안내 줄에 쓴다. 행이 길어지기 때문이다. 모르는 PARTIAL 사유는 문구를 지어내지 않고 비운다.
5. **P3**: 규격 CSS의 `.dc-hits th`가 `#eef1f5`(새 hex)다. 같은 규격의 "새 hex 없음"과 어긋난다. 규격 글자대로 두었으니 `var(--panel2)`로 바꿀지 디자인이 정한다.
6. **P3**: 컨텍스트 줄에 `“ ”`를 씌웠다(규격 그림대로). 서버 `InstNameMatcher.context`가 이미 따옴표나 말줄임을 넣는지는 확인하지 않았다.
7. **P3**: 업로드 결과의 `{파일명}을`은 받침 판정 없이 규격 글자대로 쓴다. `dlg.withObj`(조사 도우미)가 있으니 바꿀지 디자인이 정한다.
8. **P3**: `isLocked`는 `task.team === '디자이너'`를 기준으로 하고 `X-Screen-Id`도 같은 기준이다. 규격의 "디자이너면"을 작업 쪽으로 해석했다. 세 팀 작업은 화면 잠금이 없고 서버가 `ack` 담당 여부를 막는다.
9. **P3**: 제출 성공 뒤 포커스는 `dlg.close`의 복귀(`#dg-submit`, 이미 비활성)라 사실상 어디에도 가지 않는다. 규격에 없어 손대지 않았다.
10. 삭제 `confirm`·`alert`, 이모지 아이콘(`📎`·`📦`)은 범위 밖이라 그대로다.

# 화면별 진입 URL 구분 — 현황 조사와 구현 선택지 (패치 없음)

## 1. 대상·방법·못 본 것
- 대상은 `frontend/index.html`, `frontend/js/{app,landing,nav,store,portal,dashboard,prep,workflow}.js`, 서버 `WebConfig.java`·`StaticCacheFilter.java`·README §4~5입니다. 읽기와 grep만 했습니다.
- 작업 폴더는 다른 세션의 미커밋 중간 상태입니다(`app.js`, `render.js`, `index.html` 등이 `M`). 줄 번호는 이 스냅샷 기준이라 바뀔 수 있습니다.
- 못 본 것은 다음과 같습니다.
  - 서버를 열어 실제로 새로고침·뒤로가기를 해 보지는 않았습니다. 아래는 코드 근거입니다.
  - 영향받는 시험 파일은 대조까지는 못 했습니다. 시험 파일 수는 grep 결과를 그대로 적었습니다.
  - WebLogic 실배포 설정(`web.xml`, 배포 서술자)은 확인하지 않았습니다.
  - Spring Boot 기본 동작 중 "`/`는 `index.html` 환영 페이지"와 "없는 경로는 404"는 코드가 아니라 일반 지식입니다. `WebConfig`에 뷰 컨트롤러·리소스 핸들러가 없다는 것까지만 확인했습니다.

| 항목 | 확인 결과 | 근거 |

**판정**
- **hash 방식(`#/login`, `#/board`):** 서버 변경 0입니다. 서버는 항상 `/`(`index.html`)만 받습니다. WebLogic 컨텍스트가 붙어도 상관없습니다. 단 기존 절대경로 `fetch('/menus')`는 컨텍스트 경로가 붙으면 이미 깨지므로, 운영이 컨텍스트 경로 없이 서빙된다는 전제가 이미 깔려 있습니다. 이 사실이 확실치 않으면 "필요한 맥락"으로 확인해야 합니다.
- **path 방식(`/login`, `/board`):** 서버 변경이 필요합니다.
  - 없는 경로의 404를 `index.html`로 forward하는 fallback(`addViewControllers`, 또는 알려진 화면 경로 목록만 forward)이 필요합니다.
  - `<base href>` 또는 스크립트·글꼴 경로를 절대경로로 바꾸는 작업이 필요합니다.
  - `StaticCacheFilter`와 접근 이력 인터셉터가 화면 경로를 어떻게 취급하는지 재확인해야 합니다.
  - WebLogic 컨텍스트 경로 때문에 `/ggreport/login` 꼴이 되면 `fetch('/…')` 36곳이 `<base>`와 무관하게 깨집니다(절대경로는 `<base>`를 따르지 않음).

## 7. 로그인 상태 판정 (6번 항목의 근거)
- **로그인 판정은 서버가 아니라 브라우저입니다.** `store.loadSession()`이 localStorage `tbd.session`을 읽습니다(`store.js:91-95`). 주석도 "인증이 아니라 이 브라우저에서 로그인 화면을 지났는가"라고 밝힙니다(`store.js:89-90`).
- `landing.js:46-52`의 `hasSession`이 같은 판정을 따로 복제합니다. `landing.test.js`가 `SESSION_KEY`를 대조합니다(`landing.js:9` 주석).
- 서버 쪽은 `X-Emp-No` 헤더가 자기신고 값이고 권한은 DB로 다시 확인합니다(`app.js:1099-1100`). 메뉴 권한 `/menus`가 화면 노출을 결정합니다.
- 둘러보기(guest) 모드도 세션 `mode:'guest'`로 "로그인 화면을 지난 것"으로 칩니다(`store.js:93`, `app.js:1182-1185`).

**URL 직접 진입 시 처리 원칙 (제안)**
- 세션이 없고 내부 화면 URL이면 랜딩이나 로그인으로 보냅니다. 이때 원래 목적지를 메모리에 두고, 로그인 성공 후(`enterApp` 이후 `applyHome` 자리) 그 화면으로 열어야 합니다.
- 세션은 있으나 `/menus` 권한이 없는 화면 URL이면 `app.openNavItem(id)`가 `findNavItem`으로 걸러 `false`를 주므로(`app.js:736-739`) 그 결과로 시작화면 또는 지도로 폴백하고 안내를 띄웁니다.
- `/menus` 응답이 오기 전에는 `navBuilt`가 비어 있습니다. 라우터가 "메뉴 권한 도착 후" 시점에 열어야 합니다. `applyHome`과 같은 시점이며 `pendingHome` 패턴을 재사용할 수 있습니다.
- 서버 보안이 아니라 화면 라우팅 수준의 접근 제어입니다. 서버 권한 검사는 그대로입니다.

**권장: A. hash 라우팅**
1. 서버·배포를 안 건드립니다. 폐쇄망·WebLogic 컨텍스트 경로 이슈를 피합니다.
2. 현재 구조(`<script>` 직접 로드, 한 페이지, 탭 보관)와 같은 결로 붙습니다. `activateItem`/`syncNavActive`가 이미 모든 화면 전환의 공통 경유점(`app.js:680-692`)이라, 여기서 `location.hash`를 쓰고(전환 → hash) `hashchange`로 `app.openNavItem(id)`를 부르는(hash → 전환) 양방향 연결을 만들 수 있습니다.
3. 랜딩/로그인은 hash로 `#/` 또는 `#/landing`과 `#/login` 두 값으로 나누고, `landing.show/hide`·`app.showLogin`/`enterApp`에서 hash를 맞춥니다. 사용자가 원한 "랜딩과 로그인 URL 구분"을 가장 싸게 충족합니다.
4. 상세 id 라우팅은 2단계로 나눕니다. 1단계는 메뉴 화면만(`#/board`, `#/prep`, `#/notice` …), 2단계는 필요한 상세(`#/prep/<bid>`)입니다. 상세는 각 모듈이 진입 API를 이미 갖고 있습니다(`prep.openCase`, `plans.openInstitution`, `dash.openDetail`).
5. 나중에 path 방식이 필요해지면 라우터 모듈 한 곳(`router.js`)만 교체하면 되게 `parse`/`format`을 분리합니다.

## 9. 이관 메모
- **[이관: 기획]** 화면별 URL 이름(예: `#/login`, `#/prep`)과, 상세 id까지 URL에 넣을지의 우선순위를 정해야 합니다. 기다리는 것은 1단계 범위(메뉴 화면만 vs 상세 포함) 결정입니다. 근거는 §4(상세는 모듈 내부 상태).
- **[이관: 개발: 백엔드]** 운영 WebLogic에 컨텍스트 경로가 붙는지, 붙는다면 현재 `fetch('/…')`가 어떻게 동작하는지 확인이 필요합니다. 기다리는 것은 운영 배포 구성 확인입니다. 근거는 `StaticCacheFilter.java:60`의 "WebLogic 컨텍스트 경로 대응"과 `fetch('/…')` 36곳. A안은 무관하지만 B안 선택 여부를 정하는 근거입니다.
- **[이관: 디자인]** 해당 없음. 새 화면이 없고 시각 변경이 없습니다. 단 뒤로가기로 랜딩이나 로그인이 다시 보이는 동작의 문구·안내가 필요하면 디자인과 협의합니다.

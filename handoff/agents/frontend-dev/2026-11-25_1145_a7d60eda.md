# frontend-dev 보고서 (자동 보존)

> SubagentStop 훅이 에이전트의 최종 메시지를 그대로 저장했다(2026-11-25 1145 KST, agentId a7d60eda2af416a24). 에이전트 출력이므로 사용자 결정이 아니다. 지시 내용·주제는 이 파일에 없다 — 필요하면 handoff/NEXT.md 항목이나 커밋 메시지로 찾는다.

## 1. 대상·방법·못 본 것
- 코드 읽기: kbboard.js, dashboard.js, prep.js, PrepService.java.
- playwright로 http://localhost:8080을 열람만 했다. 이미 김영업(emp 3918264, sales.member)으로 로그인돼 있었다. GET만 두 번 보냈고 저장·확정은 하지 않았다.
- **못 본 것**: 사용자가 실패한 순간의 서버 상태. 확정 시각과 담당자 지정 이력은 열람 권한이 없어 못 읽었다. 그래서 원인은 "현재 상태와 코드 규칙이 일치하는 가장 유력한 경로"로 짚었고, 100% 재현은 아니다.

## 2. 원인
**실측**
- `GET /preps`가 사립학교교직원연금공단(bc-ce16f966)을 돌려준다. `state_cd=IN_PROGRESS`, `assignee_names=["이영업"]`, **`can_view:false`**.
- `GET /bidcases/bc-ce16f966/prep`는 **404 `{"detail":"prep not found"}`**.
- 서버 `PrepService.canSee`(971-996): 영업팀원은 CONFIRMED일 때만 모두 열람한다. IN_PROGRESS부터는 현재 담당자만 열람한다. 확정자라도 담당자가 아니면 열람하지 못한다. 열람 불가는 없는 건과 같은 404다(962).
- 바로 확정한 직후(CONFIRMED)에는 김영업도 200으로 볼 수 있다(981). 확정 직후의 404가 아니라 "이미 IN_PROGRESS이고 담당자가 이영업인 건"을 연 것이다.

**프런트 경로**
- 문구가 뜨는 곳은 `prep.js:953`이다. `errorInfo`에서 where==='view'이고 404일 때다.
- 실제로 화면에 그려지는 곳은 `prep.js:1179-1180`이다. `loadDetail`(1313-1340)의 catch가 `S.detail.err`를 만들고, `paintCase`가 404이면 `T.noView`를 보인다.
- 1345(`selectCase`의 `row.canView`)는 이 경로가 아니다. `openCase`는 `selectCase`를 거치지 않고 `refresh()`(1368)가 `loadDetail`을 바로 부른다. 그래서 목록 행의 can_view는 판정에 쓰이지 않았다.
- `openCase` 인자는 정상이다. `goPrep`(dashboard.js:1537)이 `prep.bid_case_id`를 넘기고 `GET` 주소는 `/bidcases/{id}/prep`(prep.js:992)다. 404는 id 오류가 아니라 열람 권한 때문이다.
- 타이밍·캐시(30초 `cache`, prep.js:1016)는 원인이 아니다. `postConfirm`이 `invalidateCache()`를 부른다(1036).
- db 세션의 `preptask.caseHtml`(prep.js:1188)은 404에서 진입하지 않는다. `paintCase`는 `d.err` 처리(1176-1182)가 먼저다. 새 화면 탓이 아니다.

**이 상태가 되는 유력한 경로 (둘 다 `goPrep`으로 간다)**
- (a) 김영업이 확정한 뒤 담당자를 이영업으로 지정했다. 그러면 확정자인 김영업은 열람 권한을 잃는다(canSee 995). 이어서 현황판에서 다시 누르면 `/preps`에 건이 있어 `prepState`가 act='open'을 주고(`prep.js:302-306`은 can_view를 보지 않는다), `goPrep`이 열람 불가 건으로 간다.
- (b) 다른 사람이 이미 진행 중인 기관을 눌렀다. `st.preps`가 오래돼 '확정' 버튼이 떴고, 서버가 409 PREP_ALREADY_ACTIVE를 줬다. 그러면 kbboard.js:2749-2750의 `openPrepOf`가 같은 건으로 간다.
- 사용자는 "확정하고 이동"이라 했으니 (b)에 더 가깝다. (a)는 같은 계정이 흐름 전체를 한 경우다. 어느 쪽이든 원인은 한 곳이다. 현황판이 열람 권한을 확인하지 않고 사전준비 화면으로 보낸다.

**우리 변경과의 관계**
- 권한 규칙은 기존(서버 11-11 결정)이고 우리가 만든 게 아니다.
- 다만 '확정 뒤·이미 진행 중이면 사전준비 화면으로 이동'(kbboard.js `doPrepStart` 2743, `openPrepOf` 2720-2723, dashboard.js `goPrep` 1533)은 이번 미커밋 변경이라, 이 이동 때문에 증상이 처음 드러났다. 이전에는 현황판에 머물러서 안 보였다.
- 지도 팝업의 `db-open`(dashboard.js:1929·2039)도 같은 `goPrep`이라 같은 증상이 난다.

## 3. 구현안 (제안, 한 패치는 한 가지 일)
**패치 A — 이동 전에 can_view를 확인하고, 안 되면 이유를 말한다 (프런트, 핵심)**

`dashboard.js` `goPrep`(1533-1539):
```js
// old
  function goPrep(prep) {
    const P = root.prep, A = root.app;
    if (!P || !A || !A.openNavItem || !P.SOON_ID) return false;
// new
  function goPrep(prep) {
    const P = root.prep, A = root.app;
    if (!P || !A || !A.openNavItem || !P.SOON_ID) return false;
    if (prep && prep.can_view === false) return false;   // 열람 권한 없는 건은 가지 않는다(서버가 404로 돌려 '볼 수 없습니다'만 뜬다)
```
호출부 문구도 맞춘다. 지금은 false이면 "열지 못했습니다. 메뉴에서 여세요"가 나온다. 메뉴로 가도 같은 건이라 못 보므로 안내가 틀리다.
- `kbboard.js:2728`, `2750`, 2744(`dash.goPrep` 실패 분기)의 문구를 "이 건은 담당자(이영업)가 진행 중이라 상세를 볼 수 없습니다. 영업팀장·영업부장에게 문의하세요" 식으로 바꾼다. 담당자 이름은 `p.assignee_names`로 넣는다.
- 같은 문구를 `dashboard.js:1756·1935·2039`에도 적용한다.
- 문구는 기획·디자인 확인 후 확정한다(이관 메모).

**패치 B — 버튼 상태에 반영 (선택)**
- `kbboard.js` `prepState`(2695-2705)의 'open' 분기에서 `p.can_view===false`이면 `on:false`로 둔다.
- `why`에 "이영업 담당으로 진행 중입니다."를 넣는다.
- 눌러서 막히기 전에 이유를 보여 주기 위해서다.

**패치 C — 404 문구 구분 (선택)**
- `prep.js:1179-1180`의 `openCase` 경로 404는 `T.noView`가 맞다. 지금 문구는 "확정됨 건은 영업팀이 본다"로 읽혀 방금 확정한 사람에게 모순돼 보인다.
- 열람 불가 건에는 "이 건은 담당자가 진행 중이라…"로 줄이는 안이 있다.

## 4. 테스트
- 추가할 테스트:
  - `goPrep({bid_case_id:'x', can_view:false})`는 false를 반환하고 `openNavItem`을 부르지 않는다. 같은 입력에서 `can_view:true`나 필드가 없으면 true다(`dashboard.test.js` 또는 `hb-prep-1125.test.js`).
  - `openPrepOf`: 목록 행이 can_view:false이면 flash 문구가 담당자 안내다.
- 깨질 기존 테스트는 못 찾았다. 다만 `grep goPrep frontend/test`로 호출 기대(특히 `hb-prep-1125.test.js`, `kbboard-*.test.js`)를 확인해야 한다. `can_view`가 없는 픽스처는 통과한다.
- 실행: `node --test "frontend/test/*.test.js"`

## 5. 위험·되돌리는 법
- `can_view===false`만 막고 undefined는 통과시키므로 기존 동작이 안 바뀐다.
- 되돌리기: 추가한 한 줄을 지운다.
- 안내 문구는 담당자 이름을 보인다. 서버가 이미 `/preps`로 주는 값이다.

## 6. 이관 메모
- **[이관: 기획]** 확정자(김영업)가 담당자를 다른 사람으로 지정하면 그 건의 상세를 못 보는 것이 의도인가? — 기획의 결정을 기다린다. 의도가 아니면 서버 `canSee`에 "확정자는 CONFIRMED 이후에도 열람" 또는 `confirmed_by` 열람을 넣어야 한다. 근거: PrepService.java:971-996.
- **[이관: 개발: 백엔드]** 위 결정이 "확정자도 본다"이면 `canSee` 변경이 필요하고, 그 뒤에는 프런트 패치 A는 보조 방어로만 남는다.
- **[이관: 디자인]** 열람 불가 안내 문구와 비활성 버튼 모양(패치 A·B). 근거: 시각 결정은 디자인 담당.

## 7. 열린 질문
- 사용자가 실패했을 때 그 기관을 누가 먼저 확정했나? 김영업 본인이 확정하고 이영업을 담당자로 지정한 뒤였나, 아니면 이미 이영업이 진행 중이던 건이었나? 이 답이 있으면 (a)/(b)가 확정되고 정책 이관 방향이 정해진다.
- 8080을 건드리지 않고 재현하려면 별도 DB의 새 기관으로 "확정만 하고 이동"을 시험하면 된다. 그 경우는 CONFIRMED라 정상(200)이어야 한다.

## 2. 서버 계약 (읽어서 확인한 것)
- `GET /plan-collect/status` 응답: `{can_request, items, last_closed:[{institution_id, status_cd(FAILED|EXCLUDED), closed_at, close_reason}]}` (Service.java 약 255~272행).
  - 열린 요청이 있는 기관은 `last_closed`에서 빠진다.
  - `close_reason`은 `can_request`가 true일 때만 채워진다. 디자이너는 null이다.
- 4xx 본문은 `{"detail":{"code","message"}}` (Service.java `err()`). 이름은 아래 코드를 모두 확인했다.
  - 요청·취소: `CONCURRENT`(409), `NO_REQUEST`(404), `ALREADY_RUNNING`(409), `STATE_CHANGED`(409), `NOT_FOUND`(404).
  - 처리 화면: `REASON_REQUIRED`, `REASON_TOO_LONG`, `REASON_FORMAT`, `REASON_PII`(모두 400), `BAD_KEYS`, `BAD_SCOPE`.
- 컨트롤러의 403(`수집 요청 현황은 영업부서·개발부서만…`)은 `new ApiException(403, "문자열")`이라 detail이 문자열이다. 그래서 code가 없고 상태 문구로 떨어진다.
- 실행 결과 코드 `TOO_SOON`은 Service.java 546행에서 나온다.
- 화면 쪽:
  - plancollect.js의 `errCode(j)`/`call()`은 이미 `r.code`를 만든다.
  - plans.js의 `postEmpty`는 아직 code를 안 만든다.
  - plans.js의 `fetchJson`은 401·403을 둘 다 `'denied'`로 돌려준다.
  - 지금도 403이면 `CS.state='denied'`라 `collectOf`가 null을 주고, 요청 줄·칩은 안 그려지고 flash도 없다. 다만 `ensureStatus`가 불릴 때마다 다시 요청하므로 "재시도 반복"이 남아 있다.

## 5. 위험·되돌리는 법
- `forbidden`이 굳는 시점은 한 번 403을 받은 뒤부터 계정 전환(`resetStatus`)이나 새로고침 전까지다. 영업부서 사용자가 중간에 권한을 얻는 경우는 새로고침 전까지 줄이 안 보인다. 서버가 `can_request`와 별개로 403을 주는 건 재무부서뿐이라 이 정도는 허용 범위로 본다.
- 401은 굳히지 않는다. 로그인이 풀렸다 다시 로그인하면 그대로 복구된다.
- `last_closed`가 없는 옛 서버 응답도 안전하다. `closedMap`이 `{}`를 돌려준다.
- 되돌리기: plans.js의 A1~A7과 plancollect.js의 B1·B2를 `git revert`하면 된다. 시험은 신규 5건만 지우면 된다. 서버 계약은 건드리지 않았다.

## 6. 이관 메모
- `[이관: 디자인] 디자이너(can_request=false)에게 닫힌 요청 칩(실패/제외됨 + 날짜, 사유·버튼 없음)을 보여주는 게 맞는지 확인 — 기다리는 것: design-reviewer 확인 — 근거: 서버가 디자이너에겐 close_reason을 null로 주고 코드 주석에 "디자이너는 상태 칩만"이라 적혀 있어 그대로 구현했다. 규격 6-2 원문의 "요청 가능할 때만 줄"과 어긋나면 A4의 `!can` 가지를 한 줄 빼면 된다(열린 요청이 없고 can=false면 줄 없음 유지).`
- `[이관: 백엔드] 없음 — 서버 코드명(REASON_*, ALREADY_RUNNING, CONCURRENT, NO_REQUEST, NOT_FOUND, TOO_SOON, forbidden 403)은 모두 읽어서 확인했다. 다만 컨트롤러의 403은 `detail`이 문자열이라 `code`가 없다. 화면은 상태 코드로 처리하므로 통일할 필요는 없다.`

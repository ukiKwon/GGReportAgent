## 정정 보고

앞서 보고한 결론("승인 경로에 문제 없음, 다른 화면의 지연")은 틀렸습니다. 승인한 팀장 본인 화면이라는 답을 받아 가설 3개를 다시 확인했고, 그 결과를 아래에 적습니다. 서버와 프런트 모두 코드와 SQL만 읽었고, 실행·네트워크 관찰·승인 동작은 하지 않았습니다.

### 가설 1. tchange.js에 자체 승인 단추가 있다: 아니오
- `tchange.js`에는 `fetch`, `approval-requests`, `decide`, `refreshAppr`가 한 건도 없습니다. 표시 도우미(`cardItemsHtml`)만 있습니다.
- 목표 결재 카드의 승인 단추는 일반 카드와 같은 `.ap-req-ok`입니다(`approvals.js:459`, `:526`). 이 단추는 `act()`(`:683`)를 거쳐 `loadRequests()`(`:714`)로 갑니다.
- `loadRequests()`는 inbox를 다시 받고, `paintRequests()`와 `notify.refreshAppr()`를 부릅니다(`:725-726`).
- 일괄 승인 경로는 없습니다.

### 가설 2. 탭 배지 = inbox + 작업함(taskCount)이라 '1'이 작업함 몫이다: 가능성 큼
- `approvals.js:478-479`에서 탭 배지는 `inboxRows.length + taskCount`이고, `taskCount`는 `GET /approvals`의 `items`입니다.
- 이 작업함은 목표 결재와 무관합니다. `ApprovalsService.forRole`이 팀 작업과 디자이너 작업의 1차완료 건을 결재 대상으로 내려주는 별도 목록입니다.
- 목표 결재 승인은 이 목록을 만들지도 줄이지도 않습니다. `applyApproved`는 `targetChanges.apply`만 호출하고, `recordAct`는 로그만 남깁니다.
- 그래서 팀장에게 작업함 대기 건이 하나 있으면, 목표 결재를 승인해도 탭 배지는 '1'로 남습니다. 이것은 버그가 아니라 두 목록의 합산 표시입니다.
- **진짜 프런트 결함 하나가 따로 있습니다.** 작업함 건을 승인하면 `sendDecision`(`approvals.js:356`)이 `load()`를 부릅니다. 그런데 `load()`는 `paint()`만 하고 `paintRequests()`는 부르지 않습니다. 그래서 탭 배지가 낡은 채로 남습니다. 머리 띠 배지는 `refreshAppr`로 갱신되므로 두 배지가 어긋납니다.

### 가설 3. 영업부장 headOverride·can_head_reject 건이 남는다: 팀장에게는 해당 없음
- `headOverride`는 `ROLE_HEAD="영업부장"`일 때만 true입니다(`TargetChangeService.java:69-72`).
- 결재선은 팀원이면 영업팀장, 영업팀장이면 영업부장입니다(`:190`). 팀장 계정에는 `can_head_reject` 건이 생기지 않습니다.
- 승인한 사람이 영업부장이고 결재선 밖이었다면, 승인 단추가 없고 반려만 가능합니다(`approvals.js:462`). 이 경우 '승인했다'는 말과 맞지 않습니다.

### 새로 찾은 원인 후보 (서버)
- `TargetChangeService.apply`(`:246-273`)는 반영할 수 없으면 409로 던집니다. 던지는 경우는 요청자가 비활성이거나 영업부서가 아닐 때(`REQUESTER_INACTIVE`), 항목이 그 사이 바뀌었을 때(`ITEM_CHANGED` 등), 항목이 없을 때입니다.
- 이때 `decide`는 트랜잭션째 롤백됩니다. 요청은 PENDING으로 남고 inbox에도 그대로 있으므로 '1'이 줄지 않습니다.
- 프런트는 카드 안 `.ap-err`(`index.html:1627`, 12px 붉은 글씨)에 서버 문장을 보이고 버튼을 다시 켭니다(`approvals.js:694-698`). 다만 화면에서는 눈에 잘 안 띕니다. 사용자는 '승인했다'고 느꼈지만 실제로는 승인이 실패했을 가능성이 있습니다.
- SQL(`selectPending`)과 서버 inbox 집계는 정상입니다. 승인에 성공한 건은 APPROVED가 되어 `STATUS='PENDING'`에서 빠집니다.

### 확정을 위한 관찰 요청
사용자나 메인이 승인 직후 다음 중 하나만 보면 원인이 갈립니다.
- 카드에 붉은 오류 문구가 있는가. 있으면 서버 409입니다.
- 승인한 카드가 목록에서 사라졌는데 '1'만 남았는가. 그러면 작업함 몫이거나 위의 `paintRequests` 누락입니다.
- 네트워크 탭에서 `POST /approval-requests/{id}/decide`의 상태 코드와 이어서 오는 `GET /approvals` 응답을 확인합니다.

### 원인별 최소 패치

**패치 1. 작업함 승인 뒤 탭 배지를 다시 그린다.** 한 가지 일만 하는 패치입니다.

`frontend/js/approvals.js`, `sendDecision`:
```js
// old
      return load().then(function () { if (root.notify && root.notify.refreshAppr) root.notify.refreshAppr(); });
// new
      return load().then(function () { paintRequests(); if (root.notify && root.notify.refreshAppr) root.notify.refreshAppr(); });
```
`paintRequests`는 `reqs.inbox`가 비어 있어도 안전하게 그려집니다(`(reqs.inbox || {}).items`).

**패치 2. 승인 실패 문구를 눈에 띄게 한다.** 서버 원인 후보 때문입니다.

`approvals.js:696`에서 `.ap-err` 텍스트를 쓸 때 카드를 스크롤해 보이게 합니다.
```js
// old
        card.querySelector('.ap-err').textContent = e.message || '서버 연결 실패 — 처리되지 않았습니다.';
// new
        const er = card.querySelector('.ap-err');
        er.textContent = e.message || '서버 연결 실패 — 처리되지 않았습니다.';
        if (er.scrollIntoView) er.scrollIntoView({ block: 'nearest' });
```

색이나 크기(`index.html:1627`)를 키우는 일은 시각 결정이므로 `[이관: 디자인]`으로 넘깁니다.

**앞서 낸 패치(포커스·가시성 갱신)는 보류**합니다. 원인이 승인한 본인 화면이라고 확정됐기 때문에 효과가 없습니다.

### 시험안
- `approvals.js`의 `sendDecision`을 직접 호출하는 시험은 어렵습니다. 대신 `paintRequests`가 `payload.items.length`를 탭 배지(`.ap-badge`)에 합산하는지 DOM 스텁으로 확인합니다. `inbox.items=[]`, `payload.items=[{…}]`이면 `#ap-tab-inbox .ap-badge`가 '1', 작업함이 비면 배지가 없어야 합니다.
- `sendDecision` 성공 뒤 `load()`가 `/approvals` 빈 목록을 받으면 배지 요소가 사라지는지 확인합니다. 이것이 패치 1의 시험입니다.
- 기존 `frontend/test/*.test.js` 중 approvals 시험이 `load()` 호출 횟수나 `el('ap-tabs')` 내용을 단언하는지는 읽지 않았습니다. 메인이 `grep -n "ap-tabs\|ap-badge" frontend/test/*.js`로 확인해 주세요.
- 서버: `TargetChangeService.apply`가 409를 던질 때 `decide` 후 요청이 PENDING으로 남는지는 기존 서버 시험(ApprovalRequestService 관련)을 grep해 확인하고, 없으면 `data-auditor`가 아니라 `backend-dev`에 이관합니다.
- 실행: `node --test "frontend/test/*.test.js"`

### 위험·되돌림
- 패치 1은 `paintRequests` 호출 한 번 추가입니다. 결재 카드의 의견 입력 중 텍스트가 사라질 수 있습니다. 작업함 승인 직후이므로 실제 영향은 적고, `mount`도 같은 순서로 그립니다.
- 패치 2는 `scrollIntoView` 한 줄입니다. 지우면 되돌아갑니다.

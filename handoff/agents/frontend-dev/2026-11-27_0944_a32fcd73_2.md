## 결론
코드상 결함은 찾지 못했고, 의도된 동작일 가능성이 높습니다. 4단계의 '파일 올리기'는 4단계가 따로 갖는 단추가 아니라 T3 과제 줄 안에 붙어 있는 단추입니다. T3 과제 줄 자체가 건이 "준비 시작" 상태에 들어가야 생기므로, 영천시청이 아직 시작 전이면 이 단추도 없습니다. 원인을 확정하려면 응답 키 한두 개를 봐야 합니다(ⓔ).

## 2. 올리기 입구와 나타나는 조건

ⓐ 올리기 입구의 위치와 이름
- 4단계 '수익성분석' 화면의 준비 과제 목록에 있는 `수익성 분석표 확정본` 줄(T3) 안, '수익성 분석표 파일' 머리 줄에 `파일 올리기` 단추가 있습니다(prep.js 662~664, 호출은 prep.js 835·842).
- `확정본 지정`은 이 파일표의 각 행에 있는 `확정본으로 지정` 단추(prep.js 642)로 옮겨졌습니다.
- 4단계 [다음]을 누르면 뜨는 확인 창(pt.confirmAskFiles, preptask.js 1256)은 올리기 입구가 아닙니다. 이미 올린 파일 중 확정본이 없을 때 지정만 묻습니다.
- 4단계 화면은 preptask.js 1243~1248의 auto 분기입니다. tasksBlock(617)이 taskItemHtml(prep.js 824)을 부르고, 그 안에서 filesHtml이 단추를 그립니다.

ⓑ 안 보이게 되는 조건 (앞의 것이 먼저 걸립니다)
1. 서버 응답 tasks가 빈 배열입니다. preptask.js 622의 tasksBlock은 이때 안내 문구만 냅니다. 문구는 prep.js 62 '담당자를 지정하면 준비 과제가 열립니다.'(새 시작 흐름) 또는 53의 옛 문구입니다. 과제 행은 건 상태가 IN_PROGRESS·APPROVAL_PENDING·WRITABLE·WRITING일 때만 있습니다(서버 TASK_STATES, PrepService 72). 확정(CONFIRMED)·개설 대기(OPEN_PENDING) 단계에는 과제 줄이 없습니다. can_start_prep가 false이면 준비를 시작할 수 없어 이 상태가 계속됩니다(PrepService 1382~1385: 목표 기관이 아니거나 GOAL_CHANGE_PENDING이면 막힘).
2. attach 목록이 null입니다. loadDetail(prep.js 1809)은 tasks.length > 0이고 담당자·부장·팀장일 때만 /attachments를 부릅니다. 이 호출이 실패하거나 담당자가 아니면 m.attach가 비어 showFiles(835)가 거짓이 됩니다.
3. T3 과제의 상태가 TODO나 DONE이 아닙니다(prep.js 835). 시드상 T3는 선행 없음·ready_yn=1이라 보통 해당하지 않습니다(024_bid_prep.sql 108).
4. viewer.can_upload가 false입니다(prep.js 662). 서버는 can_upload = assignee && TASK_STATES.contains(state)(PrepService 1390)로 계산합니다. 즉 김영업이 이 건의 활성 담당자가 아니거나, 건이 취소·중단(CANCELLED)이면 단추가 없습니다. can_check는 완료 단추용이라 올리기와 무관합니다.
5. 담당자가 아닌 사용자는 preptask.js 627의 '읽기 전용' 안내 줄도 보입니다.

영천시청·김영업에 해당할 가능성이 큰 순서
1. 건이 준비 시작 전입니다(조건 1). 시작 전에는 과제 줄 자체가 없습니다.
2. 준비는 시작됐지만 김영업이 활성 담당자가 아닙니다(조건 4). 본인이 시작하지 않았거나, 담당 변경·중단 해제가 있었던 경우입니다.
3. 영천시청이 목표 기관이 아닙니다(NOT_GOAL_TARGET, 5a328494). 이 경우 시작 단추가 막혀 조건 1로 이어집니다.

ⓒ 의도 여부
- 조건 1~4는 모두 서버 규칙과 일치하는 의도된 동작입니다. 코드에서 규칙 불일치는 찾지 못했습니다.
- 한 가지는 UX 허점입니다. 4단계 상단 profitHint(preptask.js 133)는 "xlsx를 올리면 …"이라고 안내하는데, 올릴 수 없는 사용자에게는 이유 안내가 약합니다. 조건 4일 때는 note(prep.T.readonly)가 뜨지만, 담당자인데 attach만 실패한 경우(조건 2)에는 아무 안내도 없습니다. 실제로 이게 원인이면 결함에 가깝습니다.

## 3. 최소 패치안
원인이 조건 2일 때만 필요하며, 지금은 원인을 확정하지 못해 보류를 권합니다. 원인이 확정되면 prep.js 835의 showFiles 거짓 분기에서 '첨부 목록을 불러오지 못했습니다. 새로 고친 뒤 다시 시도하세요' 줄을 내는 방식입니다. 시험은 prep.taskItemHtml에 m.attach=null, T3가 TODO인 입력을 주고 그 문구가 있는지, filesHtml은 없는지 확인하면 됩니다. 기존 시험은 영향이 없을 것으로 봅니다.

## 4. 확인할 것 (ⓔ)
브라우저 개발자 도구의 Network 탭입니다. 읽기만 하며 건 상세 GET(base(id))의 응답을 봅니다.
- state_cd: CONFIRMED나 OPEN_PENDING이면 조건 1입니다.
- tasks가 빈 배열인지, 그리고 viewer.can_start_prep와 viewer.start_blocked_reason(NOT_GOAL_TARGET·GOAL_CHANGE_PENDING)을 봅니다.
- viewer.is_assignee가 false이면 조건 4입니다.
- viewer.can_upload가 false이면 단추가 없는 직접 원인입니다.
- GET .../attachments의 상태 코드가 200이 아니면 조건 2입니다.
- tasks 중 T3 항목의 상태가 TODO나 DONE인지도 같이 봅니다.

읽기 전용 SQL입니다. 테이블명은 확인하지 못했으니 024_bid_prep.sql을 보고 맞추십시오. 영천시청 건의 STATE_CD와 BID_CASE_ID를 조회하고, 그 BID_CASE_ID에 김영업(3918264)이 활성 담당자(isActiveAssignee)로 있는지 담당자 테이블에서 대조합니다. 목표 기관 여부는 PrepService.goalStatus가 읽는 목표 테이블에서 확인합니다.

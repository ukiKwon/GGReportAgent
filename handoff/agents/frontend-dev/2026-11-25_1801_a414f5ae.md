## 2. 요구 요약과 근거

- **현재 구조**
  - 띠 [수정하기…](`tchange.js` `selbarHtml`)가 두 칸 창 `tc.editDialogHtml`을 연다(`kbboard.js` `case 'hb-seledit'` → `openChange({kind:'edit'})`).
- **판단한 것**
  - **재사용할 부품**: `dlg.confirm`은 본문이 텍스트 한 단락뿐이라 사유 칸과 기관 목록을 넣을 수 없다.
    - 그래서 `tc.memoDialogHtml`과 같은 틀(공통 `.dlg` + `.dlg-bar` `[취소][실행]` + `.dlg-note` + `.dlg-body`)로 확인 상자 마크업 함수 하나(`tc.bulkDialogHtml`)를 만든다.
    - 기관 목록은 기존 `.tc-items/.tc-item/.tc-ih`, 필수 표시는 `.dlg-req`, 칸 경고는 `dlg.invalid`를 그대로 쓴다.
    - 새 CSS는 `#tc-bd .dlg-body > p` 한 줄과 띠 단추 3줄뿐이다.
  - **구분 대기의 범위**: 구분 대기(`gs.draft`)는 `canValueEdit(r)`이 참인 목표 줄에만 생긴다.
    - 구분·메모는 어느 모드에서도 결재가 없다(`tc.APPROVAL_NOW_MSG`).
    - 그래서 요청하신 "바로 반영 모드가 아니면 '결재 요청하시겠습니까?'" 갈래는 지금 코드에서 만들어질 수 없다.
    - 이 갈래는 만들지 않고, 보낼 때 `canBulkEdit()`이 거짓이면 이유를 보이고 막기만 한다.
    - 구분 수정까지 결재를 거치게 하려면 별도 결정이 필요하다(7절).
  - **모든 오류·성공 처리**는 상자 안에서 한다(오류는 상자 위 `.dlg-err`, 칸 오류는 `dlg.invalid`).
    - 상자는 새 슬롯 없이 기존 `chd` 슬롯을 쓴다. 다른 창과의 동시 열림 차단과 `closeChangeDlgs`·`chClosed`가 그대로 적용된다.

### 사유 처리 (7절 열린 질문과 연결)

- 지금 "빼기" 결재에는 사유 입력이 두 개 필수다(`tc.validate`).
  - 결재 사유 `reason`(APPROVAL일 때만): 비면 "사유를 적으세요."
  - 줄별 빼는 사유 `cancelCd`(서버 코드표 `codes.cancel_reasons`): 비면 "빼는 사유를 고르세요."
- 요구가 "사유 칸 하나"여서, 상자에는 **빼는 사유 선택 칸 하나**(필수, 선택한 모든 줄에 공통, "기타"면 입력칸 하나 더)만 둔다.
- 결재 사유 `reason`은 그 선택에서 자동으로 만든다. 예: `목표에서 빼기 — 사유명: 기타 내용`.
  - 개인정보 검사(422)에는 걸리지 않는 고정 문구다.
  - 대신 결재자가 읽는 사유가 사용자가 쓴 자유 글에서 사유 이름으로 바뀐다. 결재자가 자유 서술을 원하면 7절 Q1 B안으로 간다.

## 4. 요구 항목별 결과

### 4-1. [수정하기]

- 확인 상자 본문은 **"선택한 n곳에 대하여 수정하시겠습니까?"**이고, 아래에 줄마다 `이전 구분 → 새 구분`이 나온다.
- 대기가 없는 줄과 관심 줄은 **"바뀐 내용 없음 — 제외"**로 보이고 보내지 않는다.
  - 이때 질문은 "선택한 3곳 중 바뀐 2곳을 수정하시겠습니까?"로 바뀐다.
- [수정]이면 `tc.BTN.values`(`save_target_values`)로 일괄 저장한다.
- 바뀐 줄이 0이면 `aria-disabled`와 이유 문장이 나온다. 단추를 누르면 상태 줄에 이유가 나오고, Tab으로 닿는다.
- 결재 필요 갈래는 2절대로 지금 코드에서 만들어질 수 없어 구현하지 않았다.

### 4-2. [삭제하기]

- 위치는 [수정하기] 오른쪽, 즉 띠의 맨 오른쪽이다.
- 확인 상자 본문은 **"선택한 n곳을 올해 목표에서 빼도록 팀장 결재를 요청하시겠습니까?"**다.
  - 결재 역할은 요청자가 팀원이면 "팀장 결재", 팀장이면 "부장 결재"로 바뀐다.
  - 해당하지 않으면 "결재"로 보이고, 대상 목표가 올해가 아니면 "올해"는 빠진다.
  - 영업부장(바로 반영 모드)이면 "…바로 빼시겠습니까?"에 [빼기](`dlg-danger`)다. 이 모드는 결재 경로가 아니라 즉시 반영이라 7절 Q2로 확인이 필요하다.
- 사유는 "빼는 사유" 선택 칸 하나(필수, "기타"면 입력칸)다.
- 관심 줄이 섞이면 그 줄은 "관심 기관 — 제외"로 보이고, 안내는 단추 이유 문장에 있다(`tc.DEL_WATCH`).
- 결재 중인 줄은 원래 고를 수 없다(`pickable`). 열린 사이 잠긴 줄은 `reconcile`이 선택에서 빼고, 상자는 `bulkRepaint`로 다시 구한다.
- `cancel_reasons`가 비면 단추가 꺼지고 `tc.DEL_NOREASON`을 보인다.

### 4-4. qa 지적 반영

- **P2-1** (결재 칸에서 줄을 빼면 대기가 알림 없이 사라짐)
  - 줄 단위 "이번 수정에서 빼기"와 전체 `clearSel`이 모두 없어진다.
  - 삭제 성공 때는 **보낸 줄만** 선택에서 빠지고, 그 줄의 대기는 상자 목록에서 "바뀐 구분은 버림"으로 미리 알린다.
  - 보내지 않은 줄의 선택과 대기는 그대로다.
- **P2-2** (관심 줄이 섞이면 띠 문구와 실제가 어긋남)
  - [수정하기]는 대기 줄만 보낸다. 대기 줄은 관심이나 지난해 목표일 수 없다(`canValueEdit`).
  - 그래서 관심 줄이 섞여도 막히지 않고 "제외"로 보인다. 띠 문구 "[수정하기]로 저장"과 동작이 일치한다.
- **P3-2** (STALE 뒤 덮어쓰기 구간): `reconcile`이 `revNo`를 갱신한 뒤에도 사용자가 다시 눌러야 한다. 갱신된 이전→이후를 `bulkRepaint`로 먼저 보여 주므로 확인 지점이 생긴다. 서버 쪽 낙관적 락 검사는 이관 대상이다.
- **P3-1**(자동 체크를 손으로 풀면 대기가 알림 없이 사라짐)과 **P3-3**(모드가 없어도 닫기 경고가 계속 뜸)은 이 패치 범위 밖이라 남았다.

### 4-5. 성공/실패 뒤 처리

- **서버 처리 방식의 판단**: 클라이언트 코드만으로는 **all-or-nothing 가정**이 맞다.
  - 오류 응답은 `item_no` 하나만 가리킨다(`tc.errorOf`).
  - 성공 응답은 `mode`·`applied` 숫자뿐이고 줄별 성공 목록이 없다(`tc.resultOf`).
  - 옛 `finishChange`도 전부 성공만 처리하고 `clearSel`했다.
  - 서버가 실제로 한 트랜잭션인지, 부분 성공이 가능한지는 못 열어 봤다. 확인은 이관 메모로 넘긴다.
- **새 동작(구분 수정·삭제 모두)**
  - 2xx이면 보낸 줄만 `unpickRow`하고 `dropDraftChips`로 대기를 정리한다. 안 보낸 줄은 그대로다.
  - 실패하면 선택·대기를 비우지 않는다.
    - 오류는 상자 위(`tc-bd-err`)에 "n번째 ○○을 확인하세요. …" 식으로 나온다.
    - STALE·CHANGE_PENDING·`NOT_WATCH_OWNER`이면 `loadGoals` 뒤 `bulkRepaint`로 목록을 새로 그린다.
  - 상자를 이미 닫은 뒤에 늦게 온 실패는 `say(...)` 띠로만 알린다.

## 6. 위험과 되돌리는 법

- **dead code 증가**: 두 칸 창 코드가 호출되지 않는 채로 남는다.
  - 되돌리기는 쉽다. `case 'hb-seledit'`를 옛 줄로 되돌리면 옛 창이 열린다.
- **`gs.draft`와 `chd` 공유 상태**: 새 상자는 `chd` 슬롯을 같이 쓴다. `chClosed`의 `d.added`를 `[]`로 줘서 다룬다.
  - `chd`를 쓰는 곳은 가드와 `closeChangeDlgs`뿐임을 확인했다.
- **사용자 입력 글**: 기관명·사유명은 `esc()`로 이스케이프한다(이스케이프 시험을 포함했다). `confirm()`은 쓰지 않았다.
- **서버 감사 버튼 이름**: 삭제는 기존 `submit_target_change`로 간다. 서버에서 삭제 전용 이름을 요구하면 이관 메모다.
- **두 칸 창을 되살리려면** 패치 4(b)와 패치 1의 `selbarHtml`만 되돌리면 된다. 새 테스트 파일은 지워도 다른 테스트에 영향이 없다.
- **적용 시 충돌 주의**: 패치 4(c)는 `kbboard.js`에서 "제안 진행" 패치(`prepEntries`·`stagesHtml`·`stageCellHtml`·`renderGoals` 3줄)와 겹치지 않는 구간이다.

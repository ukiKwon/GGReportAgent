## 3. 발견 목록

**P3-1. 같은 해 안의 순서가 웹 카드와 Word에서 다를 수 있다**
- 근거
  - 화면 `frontend/js/headcard.js:244-246`: 비교 전에 연도만 있는 값을 연-월로 맞춘다(끝은 YYYY-12, 시작은 YYYY-01).
  - 서버 `HeadDocBuilder.java:506-510`: 원래 문자열을 그대로 비교한다. 연도만 있는 끝값 "2018|"과 연-월 끝값 "2018-12|"를 비교하면, 구분자 '|'(0x7C)가 '-'(0x2D)보다 커서 연도만 있는 값이 늘 위로 간다.
  - `HeadDocBuilder.java:494`의 주석("키·문자열 비교 모두 headcard.js sortPeriod 와 같다")은 이제 사실이 아니다.
- 순서가 달라지는 경우
  - 끝값이 연도만인 줄과 같은 해 12월인 줄: A(시작 2010, 끝 2018)와 B(시작 2015, 끝 2018-12).
    - 웹: 끝값이 둘 다 "2018-12"로 같아져 시작값으로 가린다. B가 위.
    - Word: A가 위.
  - 끝값이 같고 시작값만 "2018"과 "2018-01"로 다를 때.
    - 웹: 둘이 같은 값으로 보여 원래 순서를 지킨다.
    - 서버: "2018"이 "2018-01"보다 작아 순서가 정해진다.
- 다르게 나오지 않는 경우: 끝값이 2018과 2018-06처럼 12월이 아닐 때는 양쪽 모두 연도만 있는 줄이 위로 간다. head-card.test.js:1575의 시험(2022와 2022-06)이 이 경우라 차이가 드러나지 않았다.
- 영향
  - 학력·경력은 모두 확정 기록이므로 데이터가 망가지지는 않는다.
  - Word는 연도만 찍으므로 "2010 ~ 2018"이 "2015 ~ 2018"보다 위에 보인다. 끝 연도가 같아 크게 틀려 보이지는 않는다.
  - 1장에 맞추려고 줄을 뺄 때(oldestIndex)는 서버 순서를 따른다. 빈 끝값을 "9999-99"로 보는 처리는 양쪽이 같아 지금 일하는 경력이 먼저 빠지지는 않는다.
- 재현(단위 시험 수준): 경력 [A(2010, 2018), B(2015, 2018-12)]를 웹 카드에 그린 순서와 Word 표의 행 순서를 비교한다. 기대는 같은 순서, 실제는 반대다.

**P3-2. 마우스 사용자도 내려받기가 끝나면 포커스가 단추로 끌려간다**
- 근거: `headcard.js:1177-1183`. 지금 포커스가 없거나 body에 있으면 "단추에 있던 것"으로 본다. 이 판정은 내려받기를 시작할 때(1207)와 끝날 때(1216, 1223) 쓰인다.
- 부작용이 생기는 상황
  - 내려받는 몇 초 사이에 본문 글자나 빈 곳을 클릭하면 포커스가 body로 간다. 사용자는 단추를 떠난 것인데 끝나면 1220줄 focusPane이 단추로 다시 끌어온다. `focus()`는 기본으로 단추가 보이게 스크롤하므로, 스크롤해 둔 사용자는 화면이 단추 쪽으로 튄다.
  - 지도 상세 팝업(#dm-box)을 닫아 포커스가 body로 빠지면, 화면 아래 현황판(#hc-sec)의 같은 단추가 보이는 경우 그쪽으로 포커스와 스크롤이 옮겨갈 수 있다.
  - 클릭해도 단추에 포커스가 가지 않는 브라우저(Mac Safari·Firefox)에서는 시작 시점부터 포커스를 끌어온다. 이때 포커스 링이 보이는지는 측정하지 못했다.
  - 409 대체 순서(1229-1230): 기관장 정보를 다시 읽은 뒤의 then에 `V !== mine`(그 사이 다른 기관으로 옮겼는지) 확인도, 포커스 재확인도 없다. 그 사이 다른 기관으로 옮겼다면 새 카드의 [기관장 추가]·[편집]으로 포커스를 끌어올 수 있다.
- 재현
  1. 기관장 상세에서 [워드 내려받기]를 마우스로 누른다.
  2. 바로 본문 빈 곳을 클릭하고 화면을 아래로 스크롤한다.
  3. 내려받기가 끝나면, 기대는 포커스와 스크롤이 그대로인 것이고, 실제로는 단추로 포커스가 가고 화면이 스크롤된다. 서버 응답이 느릴 때 잘 드러난다.

**P3-3. 같은 해 기간이 Word에서 "2018 ~ 2018"로 찍힌다**
- 근거: `HeadDocBuilder.java:467-477`.
- 시작 2018-03·끝 2018-11, 시작 2018-07·끝 2018(이번에 허용된 조합)은 Word에 "2018 ~ 2018"로 나온다. 결함이라기보다 표기 정책 문제다. 이관 메모로 넘긴다.

**확인했고 문제없는 것**
- 칼럼 길이: MySQL `VARCHAR(7)`(db/mysql/026_inst_head.sql:45-46), Oracle `VARCHAR2(7 CHAR)`(db/oracle/026_inst_head.sql:58-59). 4자리 연도가 들어가고, 칼럼 주석도 이미 "YYYY 또는 YYYY-MM"이다.
- DB 정렬: VAL_FROM·VAL_TO로 ORDER BY 하거나 비교하는 SQL은 없다(resources 전체 검색).
- 입력 경로: 학력·경력 시작·끝을 넣는 서버 경로는 InstitutionHeadService:358·363 한 곳뿐이다.
- 공백: 화면은 시작·끝을 trim해서 보낸다(headcard.js:624-625). startMonthOk가 " 2018 "을 통과시켜도 서버가 400을 내지 않는다.
- 시작·끝 순서 검사(periodInOrder): 끝만 연도인 경우(2018-07 ~ 2018)는 허용되고, 2019 ~ 2018-12와 2019-01 ~ 2018은 막힌다. HeadTextTest:199-205와 API 시험(InstitutionHeadDocxSourcePhotoApiTest:246-254)이 이를 덮는다.
- Word 표기: yr() 변경은 학력·경력 기간에만 쓰인다. 임기는 ym, 첫 취임일은 ymd를 그대로 쓴다(HeadDocBuilder:445-492).
- 충돌 판정(conflictOf): 학력·경력은 대상이 아니어서 이번 변경과 무관하다(InstitutionHeadService:245-248).
- 화면 쪽 시작·끝 순서 검사는 원래 없다. 순서가 틀리면 서버가 400 "시작이 끝보다 늦을 수 없습니다."를 돌려준다. 이번 변경으로 생긴 공백은 아니다.

   - 시작 시 단추에 있다가 내려받는 중 body로 옮기면 → 지금 구현은 단추로 끌어온다. 이 동작을 시험으로 고정하거나 의도를 명시하는 시험이 필요하다.
3. **409 대체 순서**
   - 409를 받고 다시 읽은 뒤 내려받기 단추가 없으면 → [기관장 추가]에 포커스.
   - 그것도 없으면 → [편집], 그다음 [새로 고침] 순.
   - 다시 읽는 사이 기관이 바뀌면 → 포커스를 옮기지 않음.
   - 지금 head-card.test.js에서 이 순서를 확인하는 시험은 찾지 못했다(1171-1228 근처에 없음).
4. **Word 같은 해 표기**: 시작 2018-03·끝 2018-11 → Word "2018 ~ 2018". 기획 판단에 따라 기대값을 고정한다.
5. **서버 시작값 경계**
   - requireStart(" 2018") → 400. 서버는 trim하지 않는다는 계약을 명시하는 시험.
   - "1899", "2101" → 400.
   - HeadTextTest:189 근처에 실패 목록이 있어 일부는 이미 덮였을 수 있다. 줄 단위로 확인하지는 않았다.

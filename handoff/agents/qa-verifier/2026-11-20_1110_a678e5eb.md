### 3. 발견 목록

**회귀 확인 (문제 없음)**
- 단건 요청: `request()`는 `doRequest(id, actor, ui, true).out`을 돌려준다(:144). 쪽지는 기존처럼 `notify && freshNote`일 때 같은 트랜잭션 안에서 IT_INBOXES 두 곳에 간다(:203-207). 문구·조건·응답 키는 그대로이고 `quiet`·`fresh`는 응답에 섞이지 않는다(시험 :102-109).
- 트랜잭션 경계: 기관마다 `tx.execute` 하나씩이다(:243). 쪽지는 별도 트랜잭션이다(:293). 연결·트랜잭션 계열 장애는 루프를 끊고 다시 던진다(:251-253).
- 감사 버튼 id `plan_collect_request_batch`는 26자로 `BUTTON_ID VARCHAR(30)`(034 mysql :86, oracle :93) 안에 든다.
- B의 SQL은 ANSI LEFT JOIN, WHERE 안의 EXISTS·NOT EXISTS, `IN (부질의)`, SUBSTR, RowBounds만 쓴다. 11g에서 문제가 되는 구문(FETCH FIRST, ON 안의 부질의)은 없다.

**P2-1 (B) 결과 창 [Y, Y+1] 때문에 한 약정이 이웃한 두 해 목표에 함께 잡힌다.** `TargetResultRules.java:46`
- 재현
  1. 같은 기관을 Y−1 목표와 Y 목표로 둘 다 둔다.
  2. 약정 줄 하나를 시작 `Y-01`, 국민은행으로 넣는다.
  3. `?year=Y-1`과 `?year=Y`를 각각 연다.
- 기대: 이 약정은 한 해의 성과로만 잡힌다.
- 실제: 두 해 모두 SUCCESS로 나온다.
- 같은 이유로, 시작이 Y년 1월인 약정(실제로는 Y−1 입찰 결과일 가능성이 큼)이 Y 목표의 성과로 셈해진다. 사용자 답 "Y 목표는 Y년에 달성한 것만"과 어긋날 수 있다.
- 결정일 칸이 없어서 생긴 설계 한계다. 기획 확인이 필요하다(이관).

**P2-2 (A) 루프가 중간에 끊기면 이미 커밋된 새 요청의 개발부서 쪽지가 영영 나가지 않는다.** `PlanCollectService.java:251-253, 270`

**P3-1 (A) 커밋 뒤 `label(id)`가 실패하면 같은 기관이 이중으로 셈해진다.** `PlanCollectService.java:245-250, 263-266`
- `requested`로 세고 `req++`를 한 다음 `label()`의 DB 조회가 실패하면, 바깥 `catch RuntimeException`이 같은 `r`을 `error`로 덮고 `err++`를 한다.
- 결과: 요청은 생겼는데 응답에는 error로 나오고 숫자 합이 맞지 않는다. 감사는 OK와 ERROR가 둘 다 남는다.

**P3-2 (A) 장애 판정이 좁다.** 연결 장애가 `DataAccessResourceFailureException`이나 `TransactionException`이 아닌 다른 형태로 오면(예: MyBatisSystemException, UncategorizedSQLException) 루프가 끊기지 않는다. 그러면 50곳을 모두 두드리고 감사 ERROR가 50행 남는다.

- 함께 볼 점: 전년도 말에 확정했지만 Y 입찰용인 제안은 prep 칸이 `NONE`으로 나온다(열린 질문 2).

**P3-4 (B) 주석이 코드와 어긋난다.** `TargetResultService.java:23`의 javadoc에는 "사용자 답 전까지 true"라고 남아 있는데, 실제 값은 false다(:24).

**P3-5 (B) 정렬과 잘림 대상이 DB마다 다를 수 있다.** XML :58 `ORDER BY i.NAME_KO`에서 NAME_KO가 NULL이면(기관 행 없음) MySQL은 앞에, Oracle은 뒤에 둔다. 한글 정렬 규칙(collation)도 다르다. 그래서 2,000건을 넘을 때 잘려 나가는 기관이 DB마다 다르다. 순서만의 문제다.

**P3-6 (B) '뺀 곳'에 같은 기관이 여러 번 나올 수 있다.** 한 기관에 목표 번호가 여럿이고 모두 뺀 상태면 `removed_items`와 `removed_n`에 그 수만큼 들어간다(:81-87). 의도인지 확인이 필요하다.

### 4. 테스트 공백과 추가 제안

**A (103)**
- 쪽지 생성 실패. `notes.create`가 예외를 던지게 하고 일괄 요청 → 200, `note_sent=false`, 요청 행과 감사 OK는 남음. 설계 시험안에는 있었는데 빠졌다.
- 동시 요청. `DuplicateKeyException`(모의) → 그 기관만 `error`/`CONCURRENT`, 감사 BLOCKED, 나머지 기관은 처리.
- 독립 트랜잭션. 2번째 기관에서 일반 RuntimeException(모의) → 1·3번째는 커밋, 2번째만 `SERVER_ERROR`.
  - API 시험은 `@Transactional`이라 바깥 트랜잭션에 합류한다. 그래서 기관별 독립성을 실제로 검증하지 못한다.
- 장애 전에 커밋된 새 요청. 1번째 성공 후 2번째에서 연결 장애 → 1번째 요청은 남고 쪽지는 0통(P2-2의 현재 동작을 못 박기).
- 접근 이력. `ACCESS_LOG.DETAIL`이 `plan-collect batch n=2 requested=2 joined=0 already=0`이고 기관 id·사번이 없음.
- 본문 크기. 16KB를 넘는 본문으로 `/plan-collect/batch` → 413. `BoardWriteLimitFilterTest`에 batch 단언이 없다(grep 0건).
- 쪽지 문구 경계. 새 요청 4곳 → 문구에 "외 1곳"과 "새로 4곳"이 있음. 3곳일 때는 "외"가 없음.

**B (104)**
- 순위 집계. JOINT 순위의 국민은행 성공 → `success_n=1`, `success_first_n`과 `success_second_n`은 0.
- 제안 상태. 같은 해 확정 제안이 CANCELLED이거나 진행 중인 기관 → `prep.kind`가 CANCELLED 또는 ACTIVE. 현재 시험은 NONE만 본다.
- 약정 건수 상한. LINE_MAX를 넘으면 409(상수를 시험용으로 줄이거나 모의).
- 올해 공고 근거. 올해 공고 종료 기록이 있는 기관 → `bid_basis.basis_cd=NOTICE_CLOSED`이고 결과가 UNREGISTERED. 이 판정은 Rules 단위 시험에만 있다.
- 이웃 연도 이중 계산(P2-1). Y−1과 Y 목표 + 시작 `Y-01` 국민은행 줄 → 현재 동작이 두 해 모두 SUCCESS임을 못 박거나, 기획 결정에 맞춰 바꾼다.
- 연도 경계(P3-3). `CONFIRMED_AT='(Y-1)-12-31T15:30:00Z'`(한국 시각 Y년 1월 1일) → 기대는 기획이 정할 일이다.

### 2. 판정

### 3. 발견 목록

**P2: 계정 전환 직후 예산팀에게 "사업계획 / 불러오는 중…" 절이 남을 수 있다**
- 근거: `app.js:247`의 `plans.onProfileChange()`가 `app.js:248`의 `applyMenuPermissions()`보다 먼저 실행된다.
  - `applyMenuPermissions()`는 `/menus`를 받은 뒤 비동기로 사이드바를 다시 그린다.
  - 그런데 `plans.menuVisible()`(`plans.js:415–421`)은 `#side-nav [data-nav]` DOM을 읽는다.
  - 그래서 `onProfileChange` 안의 `refreshSlots()`(`plans.js:778`)는 **전산팀 시절 사이드바**를 보고 "보임"으로 판정한다.
  - 그 직전에 `resetStatus()`로 상태가 idle이 됐으므로, 절은 "불러오는 중…"으로 다시 그려진다.
  - 사이드바를 다시 그리는 `paintNav`(`app.js:762–785`)는 `refreshSlots`를 부르지 않는다. `refreshSlots`는 현황 요청을 보내지 않으므로 이 상태가 그대로 굳는다.
- 재현 절차
  1. 전산팀 계정으로 현황판 상세에서 기관을 하나 연다(사업계획 절이 보이는 상태).
  2. 계정 전환기에서 예산팀 계정을 고른다.
  3. 기대: 사업계획 절이 사라진다. 예상 실제: `<h3>사업계획</h3>`과 "불러오는 중입니다…"가 남는다.
  4. 확인 방법: `document.querySelector('.pl-slot').innerHTML`을 본다.
- 참고: 반대 방향(예산팀에서 전산팀)으로 바꾸면 절이 없다가, 상세를 다시 열 때까지 계속 안 보인다. 이쪽은 P3이다.
- 이전부터 있던 정체("불러오는 중"이 멈춤)와 같은 뿌리지만, 11-17 숨김 요구가 이 경로에서 깨진다.

**P3: 늦게 실행되는 revealKey**
- 현황이 도착하기 전에 사용자가 할 수 있는 동작 가운데 `select`만 revealKey를 지운다. 목록을 손으로 스크롤하거나, 검색어·지역·상태·기간 창(3/6/12/all)을 바꿔도 지워지지 않는다. 그래서 현황이 도착하면 선택 행 쪽으로 화면이 한 번 끌려간다.
  - 바꾼 조건에서 선택 행이 빠졌으면 `revealRow`가 아무것도 하지 않으므로 무해하다.
  - 행이 남아 있으면 `block:'nearest'`로 선택 행까지 한 번 이동한다. 피해는 작다.
  - 기간 창·검색·지역·상태를 바꾸는 쪽(`plans.js:727,733–735`)에서도 지우면 원천 차단된다.
- 현황이 도착하기 전에 다른 탭으로 나가는 경우: `onStatus`가 `!host`에서 바로 돌아가므로(`plans.js:573`) revealKey가 S에 남는다. 다음에 일반 진입하면 그때 선택 행으로 스크롤한다. 선택 행 자체는 이어 가는 값이라 결과는 무해하지만, "pendingId로 들어올 때만"이라는 의도와는 다르다.
- 오프라인일 때는 `ensureStatus`가 `onStatus`를 부르지 않는다(`plans.js:371`). 그래서 revealKey가 사용자가 행을 고를 때까지 남는다. 무해하다.
- 계정 전환: `S = null`(`plans.js:774`)로 지워지므로 문제없다.
- `pl-retry` 클릭(`plans.js:704`)은 `onStatus()`를 바로 불러 revealKey를 먼저 써 버린다. 오류 상태에서만 일어나는 일이라 무해하다.

**P3: `freshState`에 `revealKey` 기본값이 없다**
- undefined는 falsy라 동작에는 문제가 없다. 다만 다른 키들은 `pendingId: ''`처럼 모두 기본값이 선언돼 있어 일관성이 깨지고, 상태 키를 셀 때 빠뜨리기 쉽다.

**P3: 빈 `.pl-slot`은 문제없음**
- `paneSection`은 `menuVisible`이 false면 div를 만들기 전에 ''를 돌려준다(`plans.js:437`). 그래서 div 자체가 생기지 않는다.
- `refreshSlots`가 비운 슬롯은 `index.html:1956`의 `.pl-slot:empty { display:none; }` 규칙으로 가려진다.
- 단, 첫 로드 때 `/menus`가 오기 전에는 사이드바가 비어 있고, 이때 `menuVisible`이 true로 판정된다(`plans.js:419`). 그 사이에 상세가 그려지면 예산팀도 현황 요청을 1회 보내고 403을 받는다. 표시는 denied 뒤 ''가 되어 숨겨진다. 이 요청은 "요청 전 차단"이라는 의도의 예외로 남는다.

**P3: mount 시 scrollIntoView의 부수 효과**
- `scrollIntoView`는 `#pl-scroll`만이 아니라 스크롤 가능한 바깥 컨테이너까지 함께 움직일 수 있다.
- 메인 측정(상자 327..534, 행 464..534)으로는 문제가 보이지 않았다. 창 높이가 작을 때(예: 768px)만 확인이 필요하다.

**회귀:** 버튼 분기를 줄였어도, 절이 보이는 사용자는 곧 `menuVisible`이 true인 사용자이므로 결과가 같다. `openInstitution`을 부르는 곳은 `data-pl-open` 버튼(`plans.js:785`) 하나뿐이라 함께 바뀐다. 다른 회귀는 찾지 못했다.

### 4. 테스트 공백과 추가 제안
- 새 시험 대부분은 소스 정규식이다(`plans.test.js` +140–151). 공백·중괄호 배치까지 고정하고 있어 리팩터링에 약하고, 실제 동작은 증명하지 못한다.
- 계정 전환 순서에 대한 시험이 없다. 제안: `menuCheck`를 true → false로 바꾼 뒤 `onProfileChange`에 해당하는 흐름을 돌린다. 이때 기대값은 "`sectionInner`는 ''"이다. 지금은 DOM 순서에서 생기는 문제라 node 시험으로는 잡기 어렵고, Playwright로 확인하는 편이 맞다.
- revealKey가 지워지는 경로 시험이 없다. 제안: mount(pending) 뒤 기간 창 변경 → status 도착. 기대값은 "scrollTop이 사용자 값 그대로"이다(지우기를 추가할 경우).
- `nav.teamIn` 경계 시험(`nav.test.js` +86–102)은 적절하다.

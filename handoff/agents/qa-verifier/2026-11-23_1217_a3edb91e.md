## QA 검토: #tm-modal을 .dlg로 옮긴 변경 (미커밋)

**1. 대상·방법·못 본 것**
- 대상: `frontend/js/team.js`(456-479, 770-939), `frontend/index.html`(3391, 1324-1325), `frontend/test/team.test.js`(322-361, 424-447), 공통 모듈 `frontend/js/dlg.js` 전체, `frontend/js/app.js`(149-168, 664-668).
- 방법: 코드만 읽었다. 테스트 결과는 메인이 돌린 1795/1795를 그대로 믿는다.
- 못 본 것: 브라우저 실화면(Playwright 안 씀), 실제 422·409 응답 흐름.

**2. 판정: 커밋해도 된다.**
P0·P1은 없다. P2 하나는 한 줄이면 고쳐지니 같은 커밋에 넣기를 권한다.

**3. 발견 목록**

- **P2-1 보내는 중에 닫으면 확인 상자 문구가 안내 줄과 어긋난다**
  - 근거: `team.js:805`의 `isDirty`는 `m.busy`를 보지 않는다. 그래서 보내는 중에도 [취소]·Esc를 누르면 "닫으면 고른 담당자와 적은 사유가 사라집니다"(T.dirtyText, `team.js:60`)가 뜬다. 같은 창 위쪽에는 "창을 닫아도 신청은 계속 보내지고…"(`team.js:62`)가 이미 보인다.
  - 위험: 사용자가 신청이 취소된 줄 알고 다시 올리면 CHANGE_PENDING 오류를 만난다.
  - 재현: 해제할 사람 1명 체크 → 사유 입력 → [변경 신청 올리기] → 응답 전에 Esc.
    - 기대: 확인 없이 닫히거나 신청이 계속된다는 문구가 뜬다.
    - 실제: "사라집니다" 확인 상자가 뜬다.
  - 패치 후보: `isDirty: function () { return !m.busy && !!(m.rm.length || m.add.length || m.reason.trim()); }`

- **P3-1 보내는 중에 닫았는데도 나중에 커서를 가져간다**
  - 근거: `team.js:853`은 `S.modal !== m`이어도 `S.refocus = true`로 둔다.
  - 결과: 닫은 뒤 검색창(#tm-q)에 입력하던 커서를 응답 뒤 `afterDetail`(`team.js:673-681`)이 [담당자 변경 신청]으로 옮긴다.
  - 다만 loadDetail이 오른쪽을 다시 그려 원래 단추가 사라지면 커서가 body로 떨어지므로, 다시 잡는 것 자체는 필요하다.
  - 패치 후보: `activeElement`가 body이거나 `#tm-case` 안일 때만 refocus.

- **P3-2 닫고 다시 연 창에 앞 신청의 결과가 들어간다**
  - 보내는 중에 닫고 바로 다른 창(m2)을 열면, 앞 요청의 실패 응답이 m2의 `#tm-m-err`로 간다(`team.js:858` → `864`, `!!S.modal`이 m2 기준이다).
  - closeReload 응답이면 m2를 닫아 버린다(`865`).
  - 패치 후보: `handleWriteError`에 원래 창 m을 넘겨 `S.modal === m`일 때만 창 안에 표시한다.

- **P3-3 낡은 주석 두 곳**
  - `team.js:301`의 "모달 .ap-err"는 이제 `.dlg-err`다.
  - `app.js:153`의 "team.js·prep.js가 직접 처리"는, #tm-modal에 대해서는 이제 dlg.js가 처리한다.

**지정한 8개 점검 결과**
- ① 덮개: 창이 열리면 `setInert`(`dlg.js:60-69`)가 body의 다른 자식을 모두 막아, 사용자 조작으로는 탭을 옮길 수 없다. 로그아웃은 `resetScreens`의 `closeAll`(`app.js:667`), 계정 변경은 `dropModal`(`team.js:966`), 화면 재진입은 `mount`의 `dropModal`(`954`)로 창이 닫힌다. 다른 화면 위에 창이 남는 경로는 찾지 못했다. Esc는 dlg가 캡처 단계에서 `stopPropagation`하므로 app·prep의 document Esc 처리기까지 가지 않는다.
- ② 두 번 처리: #tm-modal은 #tm-root 밖에 있다(`index.html:3391`, 테스트 `team.test.js:356-359`). 창 안의 클릭은 #tm-root까지 올라가지 않는다. 확인 상자 단추는 id가 없어 `onClick`에서 그냥 지나간다. 문제없다.
- ③ `S.modal === m` 가드(`852`, `857`)는 맞게 들어가 있다. 남은 점은 P3-1·P3-2.
- ④ `setDisabled`: 열 때는 dataset이 없어 바로 적용되고, 확인 상자가 떠 있는 동안 실패가 오면 `dlgWas`만 바뀌었다가 상자를 접을 때 적용된다. 확인 상자가 떠 있으면 사유 칸 경고(`invalid`)가 커서를 빼앗지 않는다(`dlg.js:256`). 정상이다.
- ⑤ `restoreFallback`: inert를 먼저 풀고 `seen` 검사 → fallback 순서다. 단추가 사라지거나 막혔으면 선택된 목록 항목으로 간다. 정상이다.
- ⑥ 422는 `after:'reason'`이라 사유 칸에 경고가 붙고 커서도 간다. 그 밖의 오류는 `.dlg-err`에 `noStatus`를 거쳐 들어가고, 비어 있으면 `:empty`로 접힌다(`index.html:2893`). 정상이다.
- ⑦ 성공하면 `closeModal(false)` → onClose가 창 안을 비우고 → loadDetail의 then·catch 양쪽에서 `afterDetail`이 불린다. closeModal이 `innerHTML`·`S.modal`을 onClose와 중복으로 비우지만 해는 없다.
- ⑧ 시험 공백은 아래 4절.

**4. 테스트 공백과 추가 제안**
지금 연결부 테스트(`team.test.js:424-447`)는 소스 문자열을 정규식으로 맞춰 보는 방식이라 구현 세부에 강하게 묶여 있고, 동작은 검증하지 않는다. 아래 케이스를 jsdom 수준이나 dlg 가짜 객체로 추가하기를 제안한다.
- 보내는 중(`busy=true`)에 `requestClose` → 확인 상자 없이 바로 닫힌다(P2-1 고친 뒤).
- 보내는 중에 닫음 → 실패 응답 → `#tm-perr`에 문구가 나오고, 창(`#tm-modal`)은 비어 있다.
- 422 응답 → `#tm-reason`에 `aria-invalid="true"`와 `#tm-reason-ferr`가 생기고, `#tm-m-err`는 빈 문자열이다.
- 500 응답 → `#tm-m-err`에 "(500)" 대신 "잠시 뒤 다시 시도하세요."가 나온다.
- 확인 상자가 떠 있을 때 실패 응답 → [계속 작성]을 누르면 `#tm-m-go.disabled`가 false다.

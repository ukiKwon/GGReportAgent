## 3. 발견 목록

**[P2-A] 요청 전체 마감이 64KB 조각 안에서는 걸리지 않는다** (httpclient.py:175-178)
- 원인: `resp.read(n)`은 표준 라이브러리 내부에서 n바이트를 채울 때까지 소켓을 여러 번 읽는다(http.client 응답 읽기 → BufferedReader.readinto). 소켓 시간 초과 45초는 한 번 읽을 때마다 새로 시작한다.
- 결과: 서버가 40초에 1바이트씩 흘리면 첫 64KB를 다 받을 때까지 마감 검사(176행)에 한 번도 닿지 않는다. eminwon 목록·상세 HTML은 대개 64KB 이하라 실제로 쓰이는 경로에서 마감이 걸리지 않는다.
- 헤더 단계(`opener.open`)도 마감 밖이다. 헤더 한 줄마다 45초 안에만 오면 계속 기다린다.
- 시험이 이 결함을 못 잡는다: test_hardening.py:103-112의 가짜 응답은 read 한 번에 시계를 한 칸 올린다. 실제 BufferedReader가 한 번의 read 안에서 여러 번 기다리는 동작을 흉내 내지 않아 통과한다.
- 수정안(택1):
  - 한 번에 소켓을 한 번만 읽는 `resp.read1(READ_CHUNK)`으로 바꾼다.
  - 또는 매 조각 전에 소켓 시간 초과를 `min(timeout, 남은 마감)`으로 다시 건다.
  - 시험은 "read 한 번 안에서 내부 읽기가 여러 번 일어나는" 가짜로 바꾼다.
- 재현 절차: 로컬에서 1바이트씩 30초 간격으로 보내는 HTTP 서버를 띄우고 `HttpClient(timeout=45).get(...)`을 부른다.
  - 기대: 약 135초에 FetchTimeoutError.
  - 실제(추정): 본문이 끝날 때까지 기다린다.
- 덧붙임: 마감으로 끝난 오류도 FetchTimeoutError라서 eminwon.py:244가 30초·90초 뒤 다시 시도한다. 느린 호스트 하나가 요청당 약 9분을 쓸 수 있다(P3).

**[P3-B] 알려진 실패 판정이 호스트 단위라 다른 원인의 실패도 0으로 묻힌다** (pipeline.py:40-41)
- 예: 도봉의 인증서가 바뀌었는데 이번에는 DNS 실패나 HTTP 500이 나도 `hosts_failed_known`으로 분류돼 종료 코드 0이 된다.
- `known_failing_since`는 적어 두기만 하고 만료·재검토 경고가 없다. 한 번 표시하면 계속 조용히 넘어간다.
- 수정안(택1):
  - 알려진 실패를 오류 종류로 좁힌다(예: 인증서 검증 실패일 때만 known).
  - 또는 등록일 + N일이 지나면 warnings에 올린다.

**[P3-C] 알려진 호스트만 대상으로 돌리면 종료 코드가 문서와 다르다** (cli.py:3 vs cli.py:131-132)
- 예: `--hosts 11|도봉구청`처럼 알려진 호스트만 지정하면 hosts_ok가 0이라 1을 돌려준다.
- 그런데 cli.py:3 설명은 "알려진 실패 호스트만 실패한 경우 0"이라고 적혀 있다. 문서를 고칠지, `hosts_failed_new`가 비면 0을 줄지 하나로 정해야 한다.

**[P3-D] 잠금 회수 경쟁과 Windows 삭제 예외** (cli.py:58-84)
- 경쟁: A와 B가 동시에 오래된 잠금을 보면, A가 지우고 새로 만든 잠금을 B가 81행에서 다시 지운다. 둘 다 실행된다(토큰은 해제 쪽만 보호한다).
- `_unlock` 65행과 `_lock` 81행의 `unlink`가 PermissionError(백신·색인이 파일을 잡은 경우)를 잡지 않는다.
  - `_unlock`에서 나면: finally 안에서 예외가 원래 종료 코드를 덮어쓴다.
  - `_lock`에서 나면: 종료 코드 4 대신 traceback과 1로 끝난다.
- 잠금 파일 mtime을 실행 중 갱신하지 않는다. max_run_sec(3h)은 재시도만 막고 1차 순회는 계속되므로, 호스트가 많고 느리면 6시간을 넘겨 다른 실행이 잠금을 회수할 수 있다. 이때 토큰 덕에 서로의 잠금을 지우지는 않는다.
- 수정안:
  - 회수 직전에 내용(토큰·at)을 다시 읽어 같을 때만 지운다. 또는 rename으로 원자적으로 회수한다.
  - unlink를 `try/except OSError`로 감싼다.

**[P3-E] 작업 스케줄러의 "마지막 실행 결과"는 g2b 종료 코드다** (run_weekly.cmd:15-19)
- echo와 endlocal은 ERRORLEVEL을 바꾸지 않아 스크립트의 마지막 코드가 g2b 것이 된다. eminwon의 3·1은 로그에만 남는다. 정책 판단 사항이라 이관한다.

**[P3-F] 작은 것들**
- eminwon.py:76 주석은 "연결 실패 재시도"라고 되어 있지만, 실제로는 시간 초과만 재시도한다(244행).
- store.py:76에서 OSError가 나면 `.tmp-*` 폴더가 남는다. 다음 write가 55행에서 지우므로 해는 없다.

### 요청 항목별 확인 결과
- **(1) FetchTimeoutError가 다른 오류로 바뀌는지**: 바뀌지 않는다.
  - 계층이 FetchTimeoutError → FetchConnError → FetchError → Exception이라 OSError·HTTPException·URLError·SSLError 어느 except에도 걸리지 않는다(httpclient.py:30-52, 184-195).
  - 시험도 이를 실제로 가른다. 만약 OSError 갈래로 잡혔다면 `_conn_error`가 "timed out"이 없는 문구를 FetchConnError로 만들어 test_hardening.py:132가 실패한다.
- **(2) known 호스트가 2nd pass로 회복될 때**: 정합하다.
  - 355행에서 hosts_failed를 지운 뒤 `_mark_ok`가 "표시 해제 검토" 경고를 남긴다. known/new 분리는 list_new가 끝난 뒤 pipeline.py:40에서 계산한다.
  - 서울 3곳은 인증서 검증 오류(FetchTlsError)라 retry_later에 들어가지 않는다. 그래서 실제로는 2nd pass 대상이 아니다.
  - `--limit`으로 중간에 break하면 report가 부분값이다(기존 동작).
- **(3) 11-16 첫 주간 실행(run_weekly.cmd)의 eminwon 종료 코드**:

  | 상황 | 종료 코드 |
  |---|---|
  | 실패가 서울 3곳뿐 | 0 |
  | 다른 호스트 실패가 하나라도 있음(TLS 회복 실패 1곳 등) | 3 |
  | 상세·첨부 저장 실패(`failed`)가 있음 | 3 |
  | 전부 실패(망 끊김) | 1 |
  | 잠금이 잡혀 있음 | 4 |
  | 포장 중 BatchError | 1 |

  11-12 실측에서 회복 대상 11곳 중 1곳이 접속하지 못했으므로, 그대로라면 첫 실행은 3일 가능성이 높다.
- **(4) 잠금 회수 경로와 토큰**: 해제는 자기 토큰일 때만 하므로 정상이다. 회수 단계의 경쟁과 예외는 P3-D에 적었다.

## 4. 테스트 공백과 추가 제안
| 입력 | 기대 |
|---|---|
| read 한 번에 내부 읽기가 여러 번 일어나는 가짜 응답(<64KB, 각 20초) | FetchTimeoutError (지금은 결함이 드러날 것) |
| known 호스트가 1차 FetchConnError → 2nd pass 성공 | hosts_failed_known={}, hosts_ok에 포함, 경고 1건, 코드 0 |
| known 호스트만 `--hosts`로 지정, 실패 | 코드 1(현행) 또는 0(문서) — 하나로 정해 고정 |
| known 호스트 실패 + 다른 호스트 공고 저장 실패(failed) | 코드 3 |
| 오래된 잠금에서 `path.unlink`가 PermissionError | 종료 코드 4 또는 명확한 오류(traceback 아님) |
| `.bak` 삭제가 두 번째 시도에 성공 | 정상 교체 |

추가로 볼 점:
- test_hardening.py:82-86은 `pytest.raises(Exception)`이라 너무 넓다. SourceError로 좁히고, 빈 문자열·300자 초과·문자열이 아닌 known_failing을 거부하는 케이스를 더한다.
- 기존 시험 `_Http`는 base FetchError를 던져서 retry_later 경로를 지나지 않는다.

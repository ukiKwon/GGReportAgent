## 3. 발견 목록

**① 서버·화면 판정 일치 — 문제 없음**
- 서버 `can_check`는 `mine && CHECK_STATES`이다(PrepBoardService.java:229). 저장 쪽은 ⑥ 상태 검사에서 같은 집합을 쓴다(:376). `ended`는 CANCELLED일 때만 참이다(:209).
- 화면 `preOpen`은 `!ended && state ∈ {CONFIRMED, OPEN_PENDING}`이다(prepboard.js:22–25).
- 상태는 7개다. 개설 전 2개 + CHECK_STATES 4개 + CANCELLED 1개로 빈틈없이 나뉜다. 그래서 화면이 preOpen으로 보는 줄은 서버에서 항상 can_check=false다.
- CHECK_STATES는 이제 PrepService.TASK_STATES(:65–66)와 같은 원소를 갖는다. 주석대로 따로 둔 것은 괜찮다.
- **P3(결합)**: 화면이 상태 코드 2개를 하드코딩해 서버 판정을 따로 흉내 낸다. 서버에 개설 전 상태가 새로 생기면 화면만 어긋난다. design-reviewer가 이미 이관으로 올린 '이유 필드(`check_block`)' 안건과 같은 뿌리다.

**② readOnlyAll 의미 변경 — 회귀 없음, 다만 P3 하나**
- 지금 동작(:273–285):
  - 끝난 줄만 있으면 안내를 숨긴다.
  - 개설 전 줄과 남의 담당 줄이 섞이면 '보기만' 안내를 띄운다.
  - 살아 있는 줄이 모두 개설 전이면 readOnlyPre 안내를 띄운다.
  - preOnly와 readOnlyAll은 서로 배타다(preOnly면 개설 뒤 줄이 0개라 readOnlyAll이 거짓).
- 옛 시험(prepboard.test.js:221–223)도 그대로 통과하는 식이다(row() 기본 상태가 IN_PROGRESS).
- **P3**: `pb.reset()`(:783–790)은 `#pb-ro`와 `#pb-legend`를 비우지 않는다. 계정을 바꾼 뒤 다음 `show()` 전까지 옛 계정의 안내 문구와 빗금 범례가 남는다. 다음 `load()`의 paintAll/paintMeta가 바로 덮으므로 영향은 작다. `#pb-ro`가 남는 문제는 이번 변경 전부터 있었고, 범례가 남는 것만 새로 생겼다.
  - 재현: 개설 전 줄이 있는 계정 A로 표를 연다 → 계정을 바꿔 reset을 부른다 → show 전 화면을 본다.
  - 기대: 범례에 기본 항목만 있다. 실제: 빗금 견본 항목이 남아 있다.

**⑤ 감사 경로 변화 — 실제 흐름은 그대로**

## 4. 테스트 공백과 추가 제안
1. **D24 감사 줄의 세부를 고정하지 않는다.** 지금은 BLOCKED 개수만 센다. 추가 제안: `actByCol(bid,"DASH_CHECK","BLOCKED","CK_FIN_COMMITTEE") == 2`와, 감사 STATE_CD가 각각 CONFIRMED·OPEN_PENDING으로 남는지 확인한다.
2. **승인 후 목록이 바뀌는지 묶어 본 시험이 없다.** 입력: confirm → 개설 신청 → 승인. 기대값: 같은 건의 `can_check`가 false에서 true로 바뀌고, 승인 전 PUT은 403, 승인 후 PUT은 200이다. 기존 `opened()` 헬퍼로 일부는 덮이지만, 한 시험에서 전과 후를 함께 보지는 않는다.
3. **화면 배선 시험이 소스 문자열에 묶여 있다.** :409는 `'pb.legendHtml(!!(B.data'`라는 문자열이 있는지만 본다. 변수 이름만 바꿔도 깨지고, 실제로 범례가 다시 그려지는지는 검증하지 못한다. 대안: hasPre를 계산하는 부분을 `pb.hasPre(rows)` 같은 순수 함수로 빼서 `[pre,end] → true`, `[end(CONFIRMED)] → false`를 시험한다.
4. **방어 조합 시험이 없다.** 입력: `cellModel(PT, row({state_cd:'CONFIRMED', can_check:true}))`. 기대값: 현재 구현은 `button:true, pre:true`이다. 서버가 그런 줄을 주지 않는다는 전제를 의도로 고정할지는 팀이 정한다.
5. **chip 시험 :371은 비현실 입력을 쓴다.** CONFIRMED이면서 is_mine:true인 줄이다. 우선순위 시험으로는 괜찮지만, 실제 흐름 입력(is_mine:false, assignee_names:[])으로 '담당 미정'이 함께 나오는지 보는 시험도 하나 있으면 좋다.

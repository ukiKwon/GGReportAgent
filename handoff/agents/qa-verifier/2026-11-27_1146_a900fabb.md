### 4. 테스트 공백과 추가 제안
1. **옛 값 다시 고르기 통합 시험이 없다.** BID_PREP_CHECK에 RESULT=DONE(REV 1)을 직접 넣는다.
   - GET /preps → result_cd=UNDECIDED, result_recheck=true, stage5≠CONTRACT_PLANNED.
   - GET /prep-board 행 → result_recheck=true.
   - PUT RESULT WON(base_rev 1) → 200, 다시 읽으면 recheck=false, PREV_MARK_CD=DONE.
   - PUT RESULT DONE(base_rev 1) → 400 BAD_MARK. 같은 값이라도 SAME이 아니다.
2. **끝난 건 시험**: CANCELLED + RESULT DONE → PUT WON은 409 STATE_CHANGED. P2-2 규칙이 정해지면 그 규칙의 기대값을 고정한다.
3. **API 시험의 기본값이 구분되지 않는다.** PrepScriptApiTest:386의 기본값 시험은 합계(6.00)와 출연금+예비비(6)가 같아서 기본이 TOTAL로 바뀌었는지 가려내지 못한다.
   - 합계 9 ≠ 출연금+예비비 6인 건에서 amount_mode 없음 → 문서에 '9억원'.
   - `amount_mode:"EXCL_IT"` → '6억원'.
   - `amount_mode:"X"` → 400.
4. **BoardScriptFigures**: 합계="9.000"(숫자 아님) + 세 항목 숫자일 때의 기대값. P2-5가 정해지면 null이든 계산값이든 그대로 단언한다.
5. **ScriptDraftPrompt**: amount_mode=EXCL_IT일 때 자료에 실리는 금액(P2-4가 정해지면). `boardSent`는 합계·순이익이 null이고 출연금+예비비만 있을 때 false여야 한다.
6. **preptask.test.js**:
   - columns[].marks가 없는 옛 서버 응답에서도 RESULT 단추가 WON·LOST인지(P2-1 방향이 정해지면 그대로).
   - LOST일 때 defaultIdx의 기대값.
7. **배포 점검 시험**: test properties가 065~068을 이미 올려서 '065 없는 DB'는 시험으로 잡을 수 없다. 배포 확인 질의로 대신한다(5절).

### 5. 호출자에게 요청할 실행

- 로컬 MySQL 재기동 전 점검:
  - `SELECT COUNT(*) FROM information_schema.COLUMNS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='BID_CASES' AND COLUMN_NAME='BID_RANK_CD';` → 1(0이면 065를 먼저 적용).

- 옛 값 수(앞선 QA에서 요청했으나 결과를 받지 못함):
  `SELECT p.STATE_CD, k.MARK_CD, COUNT(*) FROM BID_PREP_CHECK k JOIN BID_PREP p ON p.BID_CASE_ID=k.BID_CASE_ID WHERE k.COL_CD='RESULT' AND NOT EXISTS (SELECT 1 FROM BID_PREP_CHECK n WHERE n.BID_CASE_ID=k.BID_CASE_ID AND n.COL_CD='RESULT' AND n.REV_NO>k.REV_NO) GROUP BY p.STATE_CD, k.MARK_CD;`

- **8080 재기동 뒤 실화면 확인** (쓰기는 시험 건에서만, 재기동 전에 브라우저 캐시를 비운다):

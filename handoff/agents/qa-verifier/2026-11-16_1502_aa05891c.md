## QA 검토: 공사판 테마 커밋 4개(447e7db·e9769c8·29f5337·e54b541)

### 1. 대상, 방법, 못 본 것
- 셸이 없어 `git show`를 돌리지 못했다. 그래서 커밋별 diff가 아니라 **현재 HEAD의 파일**을 읽었다. 대상은 `agent-dashboard/site.js` 전체와 `agent-dashboard/app.js`의 THEME 분기(54-56, 243, 286-388, 409-479, 556, 913-1022)다.
- **트랙 회귀(④)는 현재 코드만 보고 판정했다.** 커밋 전 코드와는 대조하지 못했다.
- 테스트와 화면은 실행하지 않았다. 메인이 보고한 "139 통과"와 "150초 감지 0건"은 출력을 직접 보지 못했다. 그 감지 스크립트는 저장소에 없다(아래 5절).

### 2. 판정
**조건부 통과.** 엘리베이터가 영구히 막히거나 E.busy가 새는 경로는 찾지 못했다. 다만 감지 시험이 지나간 시나리오 밖에서 백엔드가 사라지거나 위치가 튀는 경우 2건(P2), 정류장 작업 누락(P3)이 있다.

### 3. 발견

**P2-1. 추가 백엔드(백엔드#2 이상)가 리프트에서 내려오는 도중에 화면에서 사라진다(①)**
- 근거:
  - 내려오는 동안 화면 위치는 `r.lp`다. `r.lp`가 실제 `r.x/y`를 120px/s로 쫓는다(site.js:82-87, 151).
  - 그동안 실제 상태 기계는 계속 진행된다(toRest → drink → rest → 벤치, app.js:340-347, 290-296).
  - 추가 인스턴스는 `rest && settled`가 되는 순간 `runners.splice`로 빠진다(app.js:1011). 이때 `ovK`나 `lp`가 남아 있는지는 보지 않는다.
- 계산: 하강에 4초(0.8/0.2), 리프트(1066,584)에서 벤치(약 82,752)까지 약 1000px를 120px/s로 걸어 약 8초, 합해 약 12초다. 실제 경로는 출구에 가까우면 약 7초 만에 벤치에 앉는다.
- 재현:
  1. 백엔드 2개를 활성화한다.
  2. 백엔드#2가 꼭대기(ovK=1)에 오른다.
  3. 출입구 근처를 걸을 때 백엔드#2를 비활성으로 바꾼다.
  - 기대: 걸어서 벤치까지 간 뒤 빠진다.
  - 실제: 마당이나 리프트 앞을 걷던 중에 사라진다.

**P2-2. 층이 오르면 크레인 운전석과 꼭대기에 있는 백엔드가 한 번에 18px 이상 점프한다(①, 감지 기준 15px 초과)**
- 근거:
  - `cabSpot().y = jibY()+21`이고 `topSpot().y = mainTopY()`다(site.js:137-140). 둘 다 `floors()`에 따라 계단식으로 바뀐다(39-40).
  - 자연 증가 때는 한 층에 18px씩 움직인다. `+100` 버튼(app.js:1090)을 누르면 수백 px가 한 번에 바뀐다.
  - 건물과 크레인도 같이 점프하므로 장면 안에서는 어긋나 보이지 않는다. 다만 150초 시험이 maxMain(16층) 이상 상태에서 돌았다면 이 경로는 검출되지 않았다.
- 재현: 16층 미만에서 백엔드가 운전석에 있을 때 `+100`을 누르거나 공정 1회(3바퀴)를 완료시킨다.
- 이건 의도된 연출인지 판단이 필요하다. 이관 메모를 보라.

**P3-1. 다시 활성화된 뒤 1회차(lap 0)에서 직전 정류장 하나를 건너뛴다(③)**
- 근거:
  - toStart가 `r.t = startT`로 소수부만 남겨 `floor(r.t)`가 0으로 돌아간다(app.js:302).
  - 그런데 `r.workKey`와 `r.elKey`는 지워지지 않는다(site.js:298, 339).
  - 그래서 직전 출근이 lap 0에서 끝났다면, 마지막으로 한 정류장의 키 `'0:k'`가 다음 출근 때 그대로 일치한다.
- 재현:
  1. planner를 짧게 활성화해 한 바퀴만 돌게 한다. 정류장 0, 1, 2를 수행해 workKey가 `'0:2'`가 된다.
  2. 휴식 뒤 다시 활성화한다.
  - 기대: '자재 일정 확인'(정류장 2)을 수행한다.
  - 실제: 그냥 지나친다. 엘리베이터 판단도 같은 방식으로 한 번 생략된다(계단 이용, 무해).

**P3-2. 첫 바퀴의 첫 정류장을 놓치는 슬롯이 있다(③)**
- 근거:
  - 시작점이 `s = 6 + slot*5 (+2)`로 최대 43이다(site.js:281).
  - security의 첫 정류장은 s=24이고 작업 창은 [22, 38]이다. backend 첫 정류장은 s≈28, 창은 [26, 42]다.
  - 시작 s가 창 끝보다 큰 슬롯(7·14·15 등)은 첫 바퀴의 첫 작업을 하지 않는다.

**P3-3. 엘리베이터 안이나 작업 중에는 기어가기·휠체어 자세가 '서기/걷기'로 바뀐다**
- 근거: `place()`가 `pose`를 'stand'·'walk'로 덮어쓴다(site.js:145-146, app.js:919).
- 피로 15 이상(휠체어)이어도 `elCheck`가 `active`나 피로를 보지 않고 탑승시킨다(site.js:333이 334보다 먼저 실행됨). 그래서 휠체어 사용자가 엘리베이터 안에서 일어선다.

**P3-4. 리프트에 탄 백엔드도 CCTV 모니터에는 건물 안 점으로 나온다**
- 근거: 모니터는 숨겨진 실제 `r.x/y`를 쓴다(site.js:477). 정렬(app.js / site.js:682)도 `r.y` 기준이라 그리는 순서에 쓰이는 위치가 화면 위치와 다르다.

**P3-5. 방어 분기가 실행되지 않는다(②의 취약성)**
- 근거:
  - `hold()`의 `if (r.state !== 'run') { busy=null }`(site.js:331)은 실행되지 않는다. `hold`는 run일 때만 불린다(app.js:307).
  - 지금 E.busy가 새지 않는 이유는 구조 때문이다. `r.el`이 있으면 `hold`가 계속 true를 돌려 run을 벗어날 수 없다. 또 run 밖에서 state를 바꾸는 외부 코드(wake·amb·away)는 모두 run이 아닌 대상만 다룬다.
  - 앞으로 "강제 휴식"처럼 run 중인 선수의 state를 바깥에서 바꾸는 코드가 생기면 E.busy가 영구히 막힌다. QA 하자 표시(`until: 1e9`, site.js:318)도 같은 조건에서 빨간 채로 남는다.

**확인했지만 문제없음**
- 정류장 작업 중 setActive(false): 작업을 마친 뒤 걸어 나간다.
- wheelOut, down, toRest 전환: 모두 `walk()`로 이어진다.
- 리프트 앞을 걷던 중 want를 토글: `lp`를 유지한 채 방향만 바뀐다(79-88).
- 엘리베이터 출구 위치: `rtPos(outS, laneR)`와 `rolePos(r.R)`가 같다. R은 항상 laneR로 수렴한다.
- 경로 한 바퀴 끝(s=len→0): 두 점이 모두 ENT라 연속이다.
- 한 step의 dt 상한이 0.033이라 한 step에 최대 약 5px 움직인다. 작업 창 16px 안에서는 건너뛰지 않는다.
- 트랙 회귀: 현재 코드 기준으로 track 경로(pathLen, pathPos, startPt, inExit, AMB_T0, 청소부 시작점, drawCoach() 기본값)는 모두 THEME 가드 밖에서 기존 공식 그대로다. 단, diff 대조는 못 했다.
- 성능(⑤): 프레임당 선수 최대 16명 × (계단 6개 + 정류장 4개 + 경로 점 약 20개 선형 탐색). CCTV는 3 × 16. 무시할 수준이다. 단면도는 오프스크린 캐시(348)에서 그린다. 부담이 남는 곳은 drawBg의 fillRect 200회 정도다.

### 4. 테스트 공백
`agent-dashboard/test/`에는 site.js 로직 테스트가 없다. server.test.js:9와 198은 파일을 서빙하는지만 확인한다. site.js는 IIFE 안에서 전역(`runners`, `simTime`, `c`)에 묶여 있어 vm 샌드박스가 필요하다. 추가 제안:
- `buildRoute(JOBS.qa)` → 계단 4번, `stops[k].s` 오름차순, `rtPos(0)`과 `rtPos(len)`이 같은 점(ENT).
- 엘리베이터를 탄 선수를 run 상태로 N초 진행 → `E.busy === null`이고 `r.el === null`이며, `r.t`의 소수부 × len이 `q.s1`과 같다.
- workKey가 `'0:2'`로 남은 planner를 toStart한 뒤 lap 0 진행 → 정류장 2에서 `startWork`가 불린다. 지금은 실패할 것으로 예상한다(P3-1).
- extra 백엔드: ovK=1에서 비활성 → splice 시점에 `ovK === 0`. 지금은 실패할 것으로 예상한다(P2-1).
- 프레임 간 그리는 위치 차이 ≤15px 검사를 다음 시나리오로 확장한다(P2-2 확인): 16층 미만 상태, `floors()` 증가 시점, `+100` 클릭.

## 3. 상태 전이·사용자 결정 대조 (통과 항목)
- 제안 확정은 결재 없이 영업팀·팀장이 한다(`PrepService.java:175-210`).
- 개설은 누구나 상신·지명 → 팀장 승인이고, 신청자나 지명자 중 팀장이 있으면 부장이 승인한다(`:285-305`, `:333-373`).
- 중단은 팀장만, 사유 필수, 결재 없음이다(`:237-252`).
- 기획승인 결재자는 부장 고정이고 승인 시 재판정한다(`:478-502`).
- 확정→개설 대기→진행→기획승인 중→작성 가능→작성 중의 조건부 UPDATE는 전부 `WHERE STATE_CD=기대값 [AND *_REQ_ID=?]`이다.
- 반려·회수 후크는 해당 요청 번호일 때만 되돌린다(`PrepMapper.xml:55-80`).
- **승인 경합**: `updateStep ... AND STATUS='PENDING'`의 행 잠금과 `updateRequest` 조건부 갱신 덕분에 decide와 cancel 중 한쪽만 통과한다.
- **같은 기관 동시 확정**: `INSTITUTIONS FOR UPDATE` 잠금 뒤에 count한다. MySQL RR에서도 첫 일관 읽기가 잠금 뒤라 유효하다. 다만 순서에 의존하는 구조다(P3-8).
- **DDL 짝**: 표 5개의 칸·길이·NULL·기본값·인덱스, 시드 6행, 코드 32행이 Oracle과 MySQL에서 1:1로 일치한다. MySQL에 COMMIT이 없는 것은 기존 미러와 같은 관례다. integrity Q16 8개 쿼리도 양쪽이 같다.
- **매퍼 방언**: ANSI JOIN, `FOR UPDATE`, `COALESCE`, `0 AS DONE_YN`만 써서 두 방언 모두 호환으로 본다. `selectRfpPath`는 T4가 준비중이라 테스트에서 실행되지 않았다.
- **기존 유형 회귀**: `decide`·`cancel`·`all`·`view`에는 `else if`/`||`만 덧붙였다. 기존 분기 순서와 조건은 바뀌지 않았다.

## 6. 테스트 공백과 추가 제안 (입력 → 기대값)
1. 이사회 자료 CONFIRMED 실물 → 상세: T5 AUTO_DONE(DONE_BY null) → 재작성 요구 → AUTO_UNDONE 1행. 지금은 `makeReady`가 T5를 OPTIONAL로 낮춰 BOARD_CONFIRMED 판정이 검증되지 않는다.
2. WRITABLE에서 T5 미완료로 전환 → `can_start_writing=false`, start-writing 409 (P2-2를 고친 뒤).
3. 스위치 열림 상태에서 CONFIRMED 건에 `POST /bidcases/{bid}/assignments` → 409 또는 403, BID_ASSIGNMENT 0행 (P2-3).
4. confirm에 `bid_case_id`를 넘기는 경로:
   - 다른 기관의 건 → 404
   - 이미 BID_PREP가 있는 건 → 409
   - 존재하는 건 정상 → 201이고 새 BID_CASES는 생기지 않음
5. 중단:
   - APPROVAL_PENDING → 409 PLAN_PENDING
   - OPEN_PENDING → 409
   - WRITABLE·WRITING → 200
   - 사유에 `010-1234-5678` → 422
6. 개설 의견과 사전준비 결재 의견에 개인정보·제어문자 → 422 / 400.
7. NOMINEE_CHANGED: 상신 뒤 지명자를 비활성으로 바꾸고 승인 → 409, 배정 0행, 상태 OPEN_PENDING.
8. APPROVER_ROLE_MISMATCH: 상신 뒤 신청자 역할을 영업팀장으로 바꾸고 팀장이 승인 → 409.
9. 대결 금지: LEAD의 대결자로 등록된 사람이 BID_OPEN 승인 → 403. PREP_APPROVAL에서도 같다.
10. 관리자 `box=all`에 BID_OPEN·PREP_APPROVAL이 나오지 않음. 관리자가 PREP_APPROVAL 회수 → 403.
11. 비확정 영업팀원(MEMBER2)이 MEMBER가 확정한 건에 개설 신청 → 201(현재 동작 고정). 상세 정책은 기획 답을 받은 뒤 단언.
12. `X-Screen-Id: prep_detail` + `X-Button-Id: check` → UI_VALID=1. 허용 목록 밖 값 → UNKNOWN·0.
13. taskCd 25자 → 404, BID_PREP_ACT의 TASK_CD는 잘리거나 null (P3-1).
14. 목록 진척이 상세 동기화 전후로 일치 (P3-4).
15. 동시성: `@Transactional` 없는 별도 테스트에서 두 스레드로 같은 기관 확정 → 201 하나 + 409 하나. 같은 BID_OPEN에 decide와 cancel 동시 실행 → 한쪽만 200.

테스트 구조: 실패 케이스를 "앞에서 쓴 것이 없는 순서"로만 단언하는 것은 구현 순서에 결합돼 있다(`PrepApiTest.java:32`). 위 7·8번은 롤백 여부를 단언할 수 없으므로, 트랜잭션 없는 클래스로 분리하는 편이 낫다.

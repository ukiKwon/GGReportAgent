## 2. 판정
**조건부 통과.** 요청한 1~5번은 대체로 의도대로 구현됐고 누수나 회귀는 찾지 못했다. 다만 확정 확인 상자의 포커스 강제 이동(P2-1)은 의도치 않은 [확정하기]로 이어질 수 있다. 재무 메뉴가 빈 채로 남는 경우(P2-2)도 확인이 필요하다.

## 3. 발견 목록

### P2-1. 확인 상자가 열린 동안 다시 그릴 때마다 포커스가 [확정하기]로 끌려간다
- **근거**: `dashboard.js:1757` `if (m.confirm && act === 'confirm') { const b = m.el.querySelector('#db-do'); if (b) b.focus(); }`
  - 이 줄은 상자가 펼쳐지는 순간 한 번이 아니라 dmRender가 불릴 때마다 실행된다.
  - 바로 위 1750~1755에서 포커스를 [취소]나 본문 링크로 되돌려 놓아도 이 줄이 덮어쓴다.
- **다시 그리게 만드는 비동기 경로**: nrm.onChange(1882), loadGoals(1880), dmLoadPreps(1776), 금고 약정 bankWatch·bankToggle, 기관장 카드(headcard).
- **재현**
  1. 영업팀으로 지도 상세 팝업을 연다.
  2. [제안 확정]을 누른다(포커스는 [확정하기]).
  3. Tab으로 [취소]에 간다. 또는 본문의 `<details>`(금고 약정 절 등)를 펼쳐 약정 응답이 오게 한다.
  4. 응답이 도착해 다시 그려진다.
  5. 기대: 포커스가 [취소]에 남는다. 실제(코드상): [확정하기]로 옮겨진다. 이때 Enter를 누르면 확정 요청(POST)이 나간다.
- **영향**: 되돌릴 수는 있지만 사전준비 건이 생기고 감사 기록이 남는다.
- **비교 대상**: 현황판의 `dashboard.js:1220`(renderPane)도 같은 모양이다. 이번 커밋 전부터 있었는지 diff로 확인해 달라.

### P2-2. 재무는 메뉴 키 하나(tasks)만 꺼져도 사이드바가 비고, 메뉴에 없는 지도에 남는다
- **근거**
  - `nav.js:81` `ROLE_CATS['예산팀']=['plan']`
  - 이사회 자료 작성 항목은 `visibleWithTasks`(`nav.js:97`, `build` 223행)라서 서버 tasks 키가 있어야 보인다.
  - tasks가 꺼지면 plan 분류가 통째로 빠진다. scan(지도)은 limitToRole이 잘라 내므로 사이드바에는 sys(관리 키가 있을 때)만 남거나 아무것도 없다.
  - 화면은 `resetScreens`가 누른 지도(`app.js:617`)에 그대로 남고, `homeItemId`는 null을 돌려준다(`nav.js:156`).
  - `menu_rules.activeFallback`은 limitToRole 이전의 서버 키만 보므로 이 상태를 바로잡지 않는다.
- **재현**
  1. 권한 관리에서 예산팀의 '작업함' 키를 끈다(또는 서버 응답에 tasks가 없게 한다).
  2. 예산팀으로 로그인한다.
  3. 기대: 시작화면이나 안내가 보인다. 실제(코드상): 사이드바는 비거나 sys만 있고, 지도와 탭 없는 화면이 남는다. 제목을 눌러도 지도뿐이다(`goHome` 696행).
- 업무상 일어날 수 있는 설정인지는 기획 판단이다(→ 이관).

### P3-1. 계정 전환기나 내 정보의 소속 변경으로 역할이 바뀌면 고정 탭 위치가 어긋난다
- `onProfileChanged`는 `resetScreens`도 `pendingHome`도 걸지 않는다(`app.js:241-259`, 의도된 동작).
- 영업에서 재무로 바꾸면 이전에 연 [이사회 자료] 탭이 중간 위치 그대로 고정(×) 탭이 된다. `drawTabs`(720행)가 위치가 아니라 id로 고정 탭을 판정하기 때문이다.
- 지도를 보던 중이었다면 재무에게는 탭 없는 지도가 남는다.
- 데모 전용 전환기와 프로토타입 프로필 편집에서만 생기므로 P3이다.

### P3-2. '남은 날' 정렬에서 '추정' 줄이 화면에 보이지 않는 값으로 섞인다
- `portal.js:282`는 `r.days`(추정 날짜의 일수)로 정렬하는데, 화면의 그 칸은 '추정'으로 표시된다(`rowHtml` 412행).
- '날짜' 정렬은 그 달 1일(`sortDate`, 241행)을 쓰므로 두 열의 순서가 서로 다를 수 있다.
- 시험(`portal.test.js:212·214`)은 두 결과가 우연히 같은 자료만 쓴다.

### P3-3. 제목 단추를 빠르게 연속으로 누르면 누를 때마다 서버 요청 5~6개와 `nrm.load()`가 다시 나간다
- 화면은 `S.seq`로 늦게 온 응답을 버리므로 안전하다. 다만 이전 요청을 취소(abort)하지 않아 서버 부하가 생긴다(`portal.js:639-649`, 739행).
- 구독은 새지 않는다
  - `unmount`가 `offNr()`와 `ac.abort()`로 리스너를 해제한다(742-749행).
  - `board.mount`를 다시 불러도 `bd-form`이 있으면 목록만 다시 받는다(`board.js:2391-2399`).
  - 활성 상태의 고정 탭을 누르는 기존 경로(`app.js:886`)와 같은 효과다.

### P3-4. 마스터가 이미 지도에 있을 때 제목을 눌러도 반응이 없다
- `app.js:696`. 주석(689행)의 "눌러도 반응이 없으면 고장처럼 읽힌다"와 어긋난다.

### P3-5. 재무가 이사회 화면에 있으면 aria-current="page"가 두 곳에 붙는다
- 머리 제목 단추(798행)와 사이드바 항목(788행) 둘 다다. 낭독기에서 '현재 페이지'를 두 번 듣는다.

### P3-6. 확정 요청 중(busy)에 포커스가 body로 빠질 수 있다(이전부터 있던 것으로 추정)
- `#db-do`가 disabled로 다시 그려지면 focus()가 실패해 포커스가 body로 간다.
- 이 상태에서는 오버레이(ov)의 Esc·Tab 처리(1833행)가 키를 받지 못하고, 포커스가 모달 밖으로 나간다.
- 실패 응답 뒤 다시 그릴 때도 포커스를 복원하지 않는다(inPane=false).

### P3-7. 디자이너 시드 이름이 화면과 서버에서 다르다
- `login.js:33`은 '박디자이너', `009_seed_users.sql:13`(mysql·oracle)은 같은 사번 7130526에 '최디자이너'다.
- 머리 줄 이름과 서버가 기록하는 이름이 달라진다(구현자가 이미 이관 메모로 남김).

### P3-8. 낡은 주석

- `render.js:946`: "3겹 선택" — 지금은 2겹이다.

## 4. 테스트 공백과 추가 제안
- **P2-1**: DOM 시험. 팝업 confirm=true에서 #db-cancel에 포커스를 둔 뒤 dmRender를 부르는 경로(nrm.onChange 발화 등)를 만든다. 기대: activeElement가 #db-cancel 그대로다.
- **P2-2**: `nav.homeItemId(nav.limitToRole(nav.build({map:true,regions:true}, {role:'예산팀'}), ctx), 'map', [], ctx)`. 지금은 null이다. 기대값은 기획 결정을 따른다. limitToRole 결과가 비는 경우도 단언한다.
- **P3-2**: 추정 줄의 days와 그 달 1일 기준 순서가 엇갈리는 자료로 date 정렬과 days 정렬 결과를 비교한다.
- **결합도**: `portal.test.js:488-504`는 app.js 소스 문자열 정규식(`gh.split('return;').length === 2` 등)에 묶여 있다. 동작은 같은데 리팩터링만 해도 깨진다. goHome·applyHome에는 행동 시험(가짜 DOM과 nav)이 없다.
- **추가 제안**: 정렬 머리 클릭 뒤 포커스와 aria-sort를 확인하는 DOM 시험(지금은 순수 함수와 소스 단언뿐).

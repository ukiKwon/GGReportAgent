## 3. 발견 목록

**P2-1 · 내 TO_WATCH 결재 중에 [관심 추가](단건 save)가 통과해 승인 때 ALREADY_WATCH로 막힘 (기본 설정에서 생기는 회귀)**
- 근거:
  - `BidTargetService.java:451`의 `requireNoPending(inst, cur)`은 cur==null이면 아무것도 막지 않는다. `:453`의 `checkWatchOverlap`은 지금 살아 있는 행만 본다.
  - ♥ 켬(`watchOn`, `:854-856`)에는 '내가 올린 TO_WATCH 결재 중이면 409' 검사가 있지만, save()의 WATCH 경로에는 없다.
  - 예전에는 `countPendingByInst`가 기관 단위로 막았다.
  - 승인 때 `TargetChangeService.java:402-403`의 `checkWatchOverlap`이 ALREADY_WATCH를 던진다. NEXT 117 P3-a가 막으려던 상황과 같고, 들어오는 경로만 다르다.
- 재현(스위치 꺼짐, baseSeed):
  1. SALES가 `change(req("목표를 관심으로", item("mapo","TO_WATCH","target_no",1,"base_rev_no",1)))`를 보낸다 → 200.
  2. SALES가 `POST /institutions/mapo/bid-targets`를 `{kind_cd:WATCH, tag_cd:NEW}`, 버튼 `add_watch_target`로 보낸다 → 기대 409 CHANGE_PENDING, 실제 201.
  3. LEAD가 승인한다 → 409 ALREADY_WATCH. 결재자는 반려 말고는 할 수 있는 게 없다.
- 판단: `:220` 시험을 '결재 중 관심 저장 201'로 바꾼 판단 자체는 1737 표 ⓐ, 그리고 화면규칙 21행 "결재 잠금도 건 단위"와 맞는다. ADD 결재 중에 관심을 넣으면 승인 뒤 목표와 관심이 함께 남는데, 이는 061 규칙상 허용이다. 빠진 것은 watchOn과 같은 '내 TO_WATCH 결재 중' 검사가 save() WATCH 경로에도 있어야 한다는 점이다.

**P2-2 · (스위치 켬에서만) 한 요청에 같은 기관 TO_WATCH 두 건이 모두 통과해 같은 사람의 관심이 2행 생김**
- 근거:
  - 스위치를 켜면 `lockAll`(`:100-105`)이 같은 기관 여러 항목을 허용한다.
  - `planItem :245`와 `replan :403`의 `checkWatchOverlap`은 둘 다 반영 전의 살아 있는 행만 본다. 그래서 같은 요청 안의 다른 TO_WATCH는 보지 못한다.
  - `write :450-453`은 다시 검사하지 않는다.
- 재현: `multi-subject=true`로 둔다. 1금고(T1)와 2금고(T2)가 있는 기관에 `[TO_WATCH T1, TO_WATCH T2]`를 상신하고 승인한다 → 같은 WATCH_EMP_NO의 관심 2행이 생긴다. '사람마다 기관당 1개' 규칙이 깨진다.
- 기본값이 false라 지금 운영 영향은 없다. **스위치를 켜기 전에 반드시 고쳐야 한다.**

## 4. 테스트 공백과 추가 제안 (⑧ — 지금 꼭 필요한 것부터)
1. **[필수] P2-1 재현 시험**: 내 TO_WATCH 결재 중 → `add_watch_target` 409 CHANGE_PENDING, 행 수는 그대로.
2. **[필수] SLOT_PENDING(스위치 꺼짐, TargetChangeApiTest의 change·decide 도우미로 쓸 수 있음)**: T1 연도 Y→Y+1 EDIT 상신 → 다른 사람이 ADD Y+1 → 409 SLOT_PENDING, `latest` null. ADD Y+2 → 200. 첫 요청 승인 → 200(자기 요청은 칸에서 빠짐).
3. **[필수] 건 단위 잠금(스위치 켬)**: T1(1금고)이 결재 중일 때 같은 기관 T2(2금고) 메모 고치기 → 201, T1 메모 → 409 CHANGE_PENDING.
4. **[권장] 연결 비우기(security ④)**: `UPDATE INST_BID_TARGET SET BID_CASE_ID='bt-test-case'` 뒤 move TO_WATCH → 새 REV의 `BID_CASE_ID IS NULL AND BID_SUBJECT_CD='MAIN_BANK'`. CANCEL REV와 결재 승인 TO_WATCH·CANCEL 경로도 같다.
5. **[권장] ITEM_NO=1 조인**: 두 기관 요청을 승인한 뒤 2번 항목 기관 줄의 `requested_by_name`이 요청자인지, 줄 수가 중복 없이 1인지.

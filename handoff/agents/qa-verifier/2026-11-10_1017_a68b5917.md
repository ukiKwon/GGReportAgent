## 3. 발견 목록
**P2-1 정적 JS 캐시 무효화가 없어 배포 직후 옛 결재 화면이 뜬다**
- 근거: 첫 접속 때 `#wf-controls`가 옛 마크업이었다.
  ```
  <input id="wf-by" placeholder="결재자 이름" value="박영업"> … <button id="wf-approve">승인</button>
  ```
  aria-label·이유 문구가 없었다. 같은 순간 `fetch('/js/workflow.js',{cache:'no-store'})`는 새 코드였다(gateAccess 있음, wf-by 없음).
- `/js/workflow.js` 응답에는 Cache-Control도 ETag도 없고 Last-Modified만 있다. 브라우저가 휴리스틱 캐시로 옛 파일을 재사용한다. `frontend/index.html:1382`는 `<script src="js/workflow.js">`로 버전 쿼리가 없다.
- 영향: 서버가 막으므로 권한 우회는 아니다. 하지만 사용자는 없어진 결재자 칸을 보고, 비영업부장에게 버튼이 열려 있다가 403을 받는 혼란을 겪는다. 다른 JS(app.js·approvals.js)도 같은 위험이 있다.
- 재현: ① 이전 버전으로 한 번 연 브라우저에서 ② 서버를 새 코드로 재기동하고 ③ 일반 새로고침 후 제안서 진행 현황을 연다.
  - 기대: 결재자 칸이 없다.
  - 실제: 결재자 칸이 보인다. 강제 새로고침을 해야 새 화면이 나온다.

**P3-1 로그아웃해도 로그인 폼에 직전 사번이 남는다**
- 로그아웃 직후 `#login-id`="1857403", `#login-role`="budget.member" 그대로였다.
- 비밀번호를 확인하지 않는 프로토타입이라, 공용 PC에서 다음 사람이 '로그인'만 누르면 직전 사람으로 들어간다. 실제로 이 경로로 정예산 계정에 다시 들어갔다.
- 재현: 정예산으로 로그인 → 로그아웃 → 로그인 화면에서 바로 '로그인'을 누른다.
  - 기대: 빈 칸이다.
  - 실제: 정예산으로 로그인된다.

**P3-2 `/approvals` 사번 처리가 형식에 따라 다르다**
- 형식이 틀린 사번(`abc`)은 200 빈 목록, 등록되지 않은 7자리(`9999999`)는 403이다. 보안상 문제는 아니고 일관성 문제다(설계 의도라면 무시).

**P3-3 이유 문구 줄바꿈 위치**
- 929px 이하에서 이유 문구가 승인·반려 옆이 아니라 다음 줄 맨 왼쪽(목록 버튼 아래)으로 떨어진다. 동작은 문제없다. 위치가 적절한지는 디자인 판단 몫이다.

## 4. 테스트 공백과 추가 제안
- `gateAccess`는 workflow.test.js:439-456에 있다(영업부장 허용, 4개 역할 거부, 둘러보기·사번 없음·세션 없음). 아래 케이스가 없다.
  - `syncButtons` DOM 결합: `pending_gate` 있음 + 영업팀장 → `#wf-approve.disabled===true`, `#wf-gate-hint`='영업부장만 승인할 수 있어요', title도 같음.
  - `pending_gate` 없음 + 영업부장 → 둘 다 disabled, hint=''.
  - `renderControls` 마크업: `#wf-by` 없음, `#wf-comment[aria-label="결재 의견"]`, `aria-describedby="wf-gate-hint"`.
  - `gateAccess({team:' 영업부장 '}, OK_S)` → allowed(trim 경계). `emp:'123456'`(6자리) → 비활성.
  - `onProfileChange`: 영업부장 → 로그아웃 시 hint가 '로그인한 영업부장만…'으로 바뀜(이번에 실화면으로 확인함).
- 서버: `GET /approvals?role=X` + X-Emp-No(영업부장) → role=영업부장. 헤더 없음 → 200 `{role:"",items:[]}`. 커밋에 테스트가 있는지 호출자 출력으로 확인이 필요하다.
- 정적 리소스 캐시 헤더나 버전 쿼리를 확인하는 테스트는 없다.

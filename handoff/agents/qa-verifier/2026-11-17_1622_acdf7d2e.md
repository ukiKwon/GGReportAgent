## 4. 테스트 공백과 추가 제안
- **트랜잭션 경계를 검증하지 못한다**: `PlanCollectApiTest`·`PlanCollectRunApiTest`가 둘 다 `@Transactional`이다. 그래서 TransactionTemplate이 바깥 시험 트랜잭션에 합류하고, '커밋 뒤 트랜잭션 밖 HTTP'와 ③ 실패 경로가 실제로 검증되지 않는다.
  - 비트랜잭션 시험에 정리 코드를 두고 다음 3건을 추가할 것을 제안한다.
  - ⓐ 가짜 수신기가 래치로 멈춘 동안 다른 스레드가 같은 기관을 반입 → 기대: 반입 201, 상태 APPLIED, 래치를 풀면 결과 감사 SENT, JOB_ID null, 데드락 없음.
  - ⓑ 두 스레드가 같은 기관에 동시에 요청 → 기대: REQ 1행, 요청자 2행, 전산 쪽지 2통(받는 곳 2개 × 1회).
  - ⓒ 수신기가 11초 지연 → 기대: AGENT_UNREACHABLE, 상태 REQUESTED.
- **P2-1 방침이 정해지면**: NotificationCommandService가 예외를 던지는 모의 객체로 반입 → 기대값은 정한 방침대로(201 유지 또는 500+롤백).
- **P3-2**: 실행이 거절된 뒤 `GET /plan-collect/status` → `run_at`이 어떻게 나와야 하는지 기대값을 명시한다.
- **CSV 수식 주입**: 기관명이 `=cmd`로 시작 → CSV 칸이 `"'=cmd"`.
- **기관 ID 대소문자**: `POST /institutions/JONGNO/plan-collect` → 201, institution_id는 `jongno`.
- **닫힌 키 내보내기**: 닫힌 키만 export → 머리줄만 있고, 감사 ITEM_COUNT=0.
- **권한 경계**: 요청자가 아닌 영업 사용자가 cancel → 404. 디자이너가 cancel → 403 + DENIED 감사.
- **약한 단언**: `PlanCollectApiTest.java:268`의 `assertEquals(1, count(...) >= 1 ? 1 : 0)`은 모양이 어색하다. `assertTrue(count>=1)`로 의도를 드러낼 것을 권한다(결함은 아님).

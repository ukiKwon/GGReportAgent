- **볼 곳**: 시간 초과(TimeoutError)와 그 밖의 연결 실패를 나눌지 security·backend가 정한다.

**[P2-3] 읽기 시간 상한이 사실상 없다(느린 응답)**
- **근거**: `httpclient.py:152-153`. urllib의 timeout은 소켓 호출 하나마다 적용된다. 45초 안에 조금씩 보내는 서버는 20MB까지 무한정 붙잡을 수 있다. 청주처럼 "핸드셰이크 뒤 읽기 시간 초과" 서버가 조금씩 보내면 이 경로를 탄다.
- **볼 곳**: 요청 전체의 마감 시각(deadline)을 두고 `read`를 나눠 읽으며 확인하기.

**[P3-1] 로더가 `schemes: ["https","http"]` 조합을 아직 허용한다(현재 설정에는 해당 호스트 없음)**
- **근거**: `eminwon.py:144-146`은 TLS 예외가 없는 호스트에 혼합 조합을 허용한다. `_get`(`eminwon.py:248-252`)은 이 조합에서 다음처럼 동작한다.
  - https가 `FetchConnError`로 3회 실패(약 4.3분)하면 http로 내려간다.
  - 일반 `FetchError`(IncompleteRead·RemoteDisconnected·"응답이 너무 큽니다")는 재시도 없이 바로 http로 내려간다.
  - 이후 `_scheme` 우선순위가 http로 굳어 그 실행 동안 계속 http를 쓴다.
- **현재 설정 확인**: 광진·서해는 `["http"]` 단독이다(`eminwon_hosts.json:729-738, 1035-1044`). 그래서 질문 (2)의 "스킴 루프와 재시도가 겹친 강등"은 **현재 설정으로는 일어나지 않는다**. 핸드셰이크·인증서 오류는 `FetchTlsError` 하위라 강등되지 않는 것도 확인했다(`eminwon.py:248-249`).
- **볼 곳**: 설정 주석(2행)의 원칙대로 로더가 혼합 조합 자체를 거부할지 정한다.

**[P3-2] 백신 판정이 "마지막으로 성공한 스킴" 기준이다(혼합 스킴일 때만)**
- **근거**: `eminwon.py:379,385`. 혼합 스킴 호스트에서 첨부 A는 http로, 첨부 B는 https로 받으면 `_scheme`가 https로 남는다. 그러면 http로 받은 파일이 들어 있어도 "생략"이 나올 수 있다.
- 현재 설정에서는 재현되지 않는다. P3-1이 막히면 함께 해소된다.

**[P3-3] 본문을 읽다가 난 SSL 오류(SSLEOFError 등)가 "핸드셰이크 실패"로 분류된다**
- **근거**: `httpclient.py:161-162`와 `_tls_error`(79-83). 재시도 1회는 괜찮지만 보고 문구가 원인을 잘못 가리킨다.

**[P3-4] ca_extra 인증서의 유효기간을 확인하지 않는다**
- **근거**: `eminwon.py:105-109`는 `is_ca`·`self_issued`·개수만 본다. 중간 CA가 만료되면 접속 때 검증 실패로만 드러나고, 보고에는 "인증서 오류"로만 남는다.
- **기억 의존(직접 확인 못 함)**: RapidSSL·Thawte TLS RSA CA G1의 만료가 2027-11 전후로 기억한다. 재검토일(2027-05-12)보다 늦어 당장 문제는 아닐 것이다. 5절 요청 1로 확인이 필요하다.

**[P3-5] 이름 비교 방식의 사소한 허점**
- `self_issued`를 발급자·주체 DER 바이트로 비교한다(`tlscert.py:119`). 같은 이름을 다른 문자열 형식으로 인코딩한 루트는 자체 발급이 아닌 것으로 통과할 수 있다. 드문 경우다.
- `host_matches`가 `*.go.kr`처럼 공공 접미사 바로 아래 와일드카드를 허용한다(`tlscert.py:130`, 점 2개 이상 조건). 지문 고정 경로에서만 쓰여 영향은 작다.

**[P3-6] 종료 코드 3이 매주 고정된다**
- 도봉·중구·강남(만료된 사설 인증서, 예외 없이 실패 유지)이 매번 `hosts_failed`에 들어간다. 그래서 `run_weekly` 로그의 `eminwon exit=3`이 늘 나온다(`cli.py:121-122`). 새 실패와 구분하는 신호가 없다.

**[P3-7] `limit`으로 중간에 멈추면 2nd pass가 돌지 않는다**
- `pipeline.py:30-31`에서 break하면 제너레이터가 닫힌다. 1차에 실패한 호스트는 재수거 없이 실패로 남는다. 의도라면 문서화만 하면 된다.

**질문 (1) 상태·보고 정합 점검 결과: 이상 없음**
- 2nd pass 성공 시 `hosts_failed`에서 지우고 `hosts_ok`에 추가한다(`eminwon.py:331-332`). 1차와 2nd pass 사이에 겹침은 없다.
- 1차가 전부 실패하고 2nd pass에서 일부 회복하면 `hosts_ok`가 비지 않아 종료 코드 1이 아니게 된다. 정합하다.
- 공고 저장 실패는 `mark_seen`을 하지 않아 다음 실행에 다시 시도한다(`pipeline.py:32-37`). 정합하다.
- 남은 점: 첨부 일부만 실패해도 공고는 '본 것'이 되어 그 첨부는 다시 받지 않는다(기존 동작, `eminwon.py:358-362`).

**질문 (4) tlscert 해석기 점검 결과**
- 확장 구조를 바르게 해석한다. critical 필드가 있어도 `kids[-1]`로 값을 잡는다. basicConstraints의 cA가 없고 pathLen만 있으면 `is_ca=False`다(`tlscert.py:99-114`).
- SPKI 지문은 SubjectPublicKeyInfo TLV 전체의 sha256으로, 표준 pin과 같다.
- R46 교차 서명본은 발급자(USERTrust)와 주체(R46)가 달라 `self_issued=False`가 맞다. 로더 통과와도 일치한다.
- R46을 cafile에 넣어도, PARTIAL_CHAIN을 끈 상태(`httpclient.py:61-62`)에서는 자체 서명이 아닌 신뢰 인증서가 신뢰 앵커가 되지 못한다. 그래서 USERTrust RSA 루트까지 올라가야 성공한다. 이 PC 저장소 상황(R46 루트 없음, USERTrust 있음)과 맞는 구성이다.

### 4. 테스트 공백과 추가 제안(입력 → 기대값)

1. **`test_eminwon.py:182-197`(`test_tls_error_does_not_fall_back_to_http`)는 이제 아무것도 검증하지 않는다.** hosts 파일에 schemes가 없어 기본값 `("https",)`가 되므로 http가 애초에 후보에 없다. 다음 두 경우로 바꾼다.
   - schemes `["https","http"]` + `FetchTlsHandshakeError` → 호출 URL이 모두 `https://`.
   - schemes `["https","http"]` + `FetchConnError`×3 → 4번째 호출이 `http://`. 강등을 허용하는 것이 정책이면 이 테스트로 명문화하고, 아니면 로더 거부 테스트로 바꾼다.
2. **HttpClient 예외 분류**(monkeypatch로 `do_open`·소켓 대체). 모두 테스트가 없다.
   - `URLError(socket.gaierror)` → `FetchConnError`
   - `getresponse` 중 raw `TimeoutError` → `FetchConnError`
   - `URLError(SSLCertVerificationError)` → `FetchTlsError`이면서 `FetchTlsHandshakeError`가 아님
   - `RemoteDisconnected` → `FetchError`(Conn 아님)
   - 본문 읽기 중 `SSLEOFError` → 현재 `FetchTlsHandshakeError`
3. **`build_context`**
   - ciphers `"ALL"` → `ValueError`
   - pins와 ca_file 동시 → `ValueError`
   - 반환된 ctx의 `verify_flags`에 PARTIAL_CHAIN이 없음
   - 같은 TlsPolicy면 같은 ctx, 다른 정책이면 다른 ctx(호스트별 격리)
4. **실제 PEM 속성**: `collector/config/ca/*.pem` 각 인증서마다 `is_ca`, `not self_issued`, 그리고 `not_after` ≥ 그 파일을 쓰는 호스트의 `tls_review_by`.
5. **재시도 순서 섞기**: `[C, H, C]` → sleeps `[30, 90]`, 성공. `[H, C, C, C]` → 1차 실패 후 2nd pass.
6. **fetch_raw 재시도**: 상세 `[C, C]` 뒤 성공 → 원문 저장, sleeps `[30, 90]`. 첨부 `[C, C, C]` → `attachment_errors`에 기록되고 공고는 저장.
7. **2nd pass 회복 뒤 cli 종료 코드**: 단일 호스트 `[C, C, C]` → `main` 반환 0, `hosts_failed` 비어 있음. cli 경로는 sleep을 주입할 수 없다(`with_config`가 sleep을 넘기지 않음, `cli.py:101-102`). 실제로 120초를 잔다는 점도 함께 확인해야 한다.
8. **잠금**: 잠금이 6시간을 넘긴 뒤 두 번째 실행이 회수한 경우, 먼저 끝난 실행이 두 번째의 잠금을 지우지 않아야 한다. 현재는 지우므로 실패할 테스트다.

### 5. 호출자에게 요청할 실행
1. **PEM 내용 확인**(저장소 루트에서):
   `python -c "from pathlib import Path; from collector.tlscert import pem_certs, parse_cert; [print(p.name, i.is_ca, i.self_issued, i.not_before.date(), i.not_after.date(), i.common_names) for p in sorted(Path('collector/config/ca').glob('*.pem')) for i in map(parse_cert, pem_certs(p.read_text('ascii')))]"`
   - 기대: 줄 4개. 모두 `True False`. sectigo 파일은 2줄(DV R36, R46).
   - not_after가 모두 2027-05-12 이후여야 한다.
2. **오프라인 시간 실측**(선택): 네트워크를 끈 상태에서 `python -m collector collect --source eminwon --hosts eminwon.buan.go.kr,eminwon.cs.go.kr --out-root <임시폴더>`.
   - 기대: 약 2×(120 + 3) + α ≈ 4분 남짓, 종료 코드 1.
   - 이 값×93/2가 P2-1의 "즉시 실패 최악 시간"이다.
3. 4절 제안 테스트를 추가한 뒤 `pytest collector -q`. 기대: 1번은 수정 후 통과, 8번은 현재 코드로는 실패.

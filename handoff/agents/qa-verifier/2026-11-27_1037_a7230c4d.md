**확인 결과 문제 없음(지시 흐름별)**
- **흐름 1**: 첫 진입 → wireRoute가 `#/intro`로 교체 → [로그인] → MO가 `#/login`을 push → 뒤로 → onRouteHash가 show → `routeTopPrev`를 동기로 'intro'로 맞춤 → 그 뒤 MO가 now=prev라 반환. **맴돌기 없음.**
- **흐름 2**: resetScreens의 지도 click 시점에는 세션 저장 전이고 routeReady=false라 쓰기가 없습니다. login-view의 class MO는 enterApp이 끝난 뒤 실행됩니다. 로컬 모드에서는 pendingRoute가 이미 소모된 상태(routeReady=true), 서버 모드에서는 pendingRoute=true·routeReady=false 상태입니다. 두 경우 모두 prev='login'·now=null이라 아무 일도 하지 않습니다. `#/login` 칸은 routeSettleHash가 교체합니다(기록 1칸 유지).
- **흐름 3**: 서버 모드에서 settled=true인 paintTabs는 /menus 응답 한 번뿐이고, 이후 호출은 pendingRoute=false라 다시 열지 않습니다. 실패(settled=false)는 소모하지 않습니다.
- **흐름 4**: 메뉴 클릭은 hash push로 끝나고, 뒤이은 hashchange는 skipSame 'ok'로 다시 마운트하지 않습니다. onRouteHash가 이벤트 값이 아니라 현재 `location.hash`를 읽으므로 빠른 연속 클릭에도 안전합니다. routeQuiet 구간은 동기라 그 안에서 생기는 hashchange가 없습니다.
- **흐름 6**: routeFallback → goHome → replace 한 번 → hashchange가 유효 주소로 'ok'. 시작화면이 없는 계정(마스터)은 지도로 갑니다. navActiveId에 이름이 없으면 쓰지 않으므로 무한 반복은 없습니다.
- **흐름 9**: `location.replace('#/…')`도 hashchange를 냅니다(표준). 코드는 이를 전제로 맞게 처리합니다.
- **보안**: 주소 값이 href·innerHTML·선택자에 들어가지 않고 Map 조회만 거칩니다. `__proto__` 같은 값은 거부합니다(security ①④ 충족).

  5. 로그인한 채 사이드바 A→B→C → 뒤로 2번 = A, 앞으로 1번 = B. 매번 활성 탭과 제목이 일치해야 합니다.
  6. `#/board-writing`에서 F5 → 같은 화면이 탭 1개로 열립니다(서버 모드에서는 메뉴가 늦게 와도 한 번만).
  7. 주소창에 `#/abc`, `#/admin/users`(재무), `#/login`, `#/` → 각각 시작화면 + 해당 안내, `#/login`·`#/`은 안내 없이 시작화면.
  8. `#/admin`(관리 권한 계정) → 첫 하위 화면, 주소가 `#/admin/users` 등으로 교체됩니다.
  9. `#/my-info`(계정) → 내 정보. 둘러보기에서는 권한 안내.
  10. 로그인한 채 `#/intro` → 랜딩이 덮고 Tab이 뒤 앱으로 새지 않음 → [로그인] → 시작화면, 주소 교체.
  11. 탭 10개를 채운 뒤 탭 클릭·활성 탭 닫기(주소 교체)·닫힌 화면으로 뒤로(안내 + 주소 복원).
  12. 로그아웃 → `#/login`. 뒤로 → 내부 화면이 안 보여야 합니다. **그대로 다른 계정으로 로그인했을 때 어느 화면이 열리는지 기록합니다(F2).**
  13. **[둘러보기] → 프로필 칩 → 영업팀 로그인 → 시작화면이 열리는지 확인합니다(F1, 지금 코드로는 예상 공고현황이 열릴 것으로 봄).**

## 7. 이관 메모
- [이관: 프런트] F1(guest→로그인 시 hash 목적지 한정), F2(로그아웃 뒤 traversal은 routeNext로 받지 않기), F3(세션 없음 분기를 login-view 기준으로)를 고친 뒤 qa에 다시 맡깁니다. F6–F9는 선택입니다. 근거: 이 보고서 3절.
- [이관: 보안] F4. `tab-btn-myinfo` 직접 click을 ②의 예외로 승인할지 확인합니다. security ①은 "권한 없는 화면은 조용히 시작화면"이고 planner §5는 "안내 표시"인데, 구현은 planner를 따랐습니다. 이 차이도 확인합니다.
- [이관: 기획] F5. 로그인 뒤 뒤로 가기에 랜딩이 다시 덮는 것을 허용할지, `#/intro` 칸을 남길지 정합니다.
- [이관: 디자인] 안내(#tab-notice, 2.5초)가 로그인 직후 화면 전환과 겹쳐 읽히는지 봅니다. 로그인 상태 랜딩의 [로그인] 단추 문구를 정합니다(frontend-dev §9와 같음).

## 3. 발견 목록

**P2-1 파일을 바꿔 다시 미리보기 하면 고친 발언이 같은 번호의 다른 줄에 붙는다(규격 6-2와 다름)**
- 근거: `board-minutes.js:345-350` `mergeFix`는 seq 번호가 새 응답에 있기만 하면 고친 발언을 유지한다. `orig`는 이전 파일의 글 그대로다.
  - 규격 6-2는 "원래 글이 새 응답과 같을 때만 유지"였다. 시험 `board-minutes.test.js:296-304`이 이 다른 동작을 오히려 굳혀 두었다.
  - 서버는 seq만 맞으면 그 줄의 본문을 고친 글로 바꾼다(`MinutesParse.java:170-174`). 그래서 새 파일 그 줄의 원래 발언은 경고 없이 사라진다.
  - 이후 화면의 `lostMasks` 기준(`pvEdit`의 `fe.orig`, :1106)이 낡은 글이라, 서버 EDIT_MASK_REMOVED와 판정이 어긋날 수 있다.
- 계약 공백: 미리보기 응답은 고친 줄에 대해 고친 결과만 준다. 그래서 화면은 새 원래 글과 비교할 방법이 없다(이관: 백엔드).
- 재현:
  1. 원문 A로 미리보기를 하고 발언 12를 고친 뒤 [반영]한다.
  2. 원문 칸을 다른 회의 파일 B로 바꾸고 [다시 미리보기]를 누른다.
  3. 기대: 고친 발언을 버리고 "n건을 지웠습니다"가 뜬다. 실제: B의 12번 줄이 A에서 고친 글로 바뀌고 '고침' 배지만 남는다.

**P2-2 미리보기 요청이 나가 있는 동안 고치면 표식(stale)이 틀어진다**
- 근거: `doPreview`(:1633)는 요청 시점의 `u.fix`로 form을 만든다. 그런데 응답을 받은 뒤 `u.pvSig = mn.signature(u)`(:1646)를 **응답 시점** 상태로 계산한다.
  - 요청 중에도 미리보기 영역(이름표 select·[고치기])은 다시 그려진 채 조작할 수 있다(`buildUpload`:1565, busy 중 비활성 없음).
- 결과:
  - 요청 중에 이름표를 바꾸면 stale이 풀리고 [저장]이 켜진다. 저장하면 409 PREVIEW_CHANGED가 난다(서버가 막으므로 안전 문제는 아니다).
  - 요청 중에 새로 고친 발언은 `mergeFix`가 `shown`을 응답의 원래 글로 덮는다. 그래서 '고침' 배지는 있는데 화면에는 원래 글이 보인다.
- 재현:
  1. 느린 네트워크에서 [다시 미리보기]를 누른다.
  2. 응답 전에 참석자 2의 역할을 고른다.
  3. 기대: 응답 뒤에도 stale이 유지된다. 실제: stale이 풀리고 [저장]이 켜진 뒤 409가 난다.
- 이미 있던 같은 경쟁(회의일·제목 입력)이 이번에 고친 내용까지 넓어진 경우다.

**P2-3 고친 발언에 보이지 않는 제어문자가 있으면 미리보기가 통째로 사라지고 '파일' 문구가 뜬다**
- 근거:
  - 서버는 `CONTROL_CHAR`를 `slot=edit, target_no=seq`로 다시 싸서 보낸다(`MinutesParse.java:292-294`). 시험도 있다(`MinutesParseEditsTest:110`).
  - 화면 `isEditFail`(:354-357)에는 CONTROL_CHAR가 없다. 그래서 `u.pv = null`(:1650)로 미리보기와 이름표 표가 사라진다.
  - `errorText`의 CONTROL_CHAR 분기(:153)는 slot이 edit이면 이름이 비어 "파일에 … 메모장에서 그 줄을 지우고 다시 저장해 올리세요"를 'box' 자리에 띄운다. 오류가 그 발언 줄에 달리지 않는다.
- 재현:
  1. 발언 하나를 고치면서 U+202E(RLO)가 섞인 글을 붙여 넣고 [반영]한다.
  2. [다시 미리보기]를 누른다.
  3. 기대: 그 줄에 오류가 달리고 미리보기는 남는다. 실제: ②가 비고 파일 오류 문구가 뜬다.

**P2-4 상세 [이름표 저장]이 중간에 실패하면 앞서 저장된 것을 알리지 않는다**
- 근거: `saveLabels`(:1219-1259)는 번호별로 순서대로 PUT한다. 성공할 때마다 rev가 하나씩 올라간다(서버 `editSpeaker` :1146-1155).
  - i번째에서 실패(REV_CHANGED·422)하면 `lb.err`만 보이고 `saved`는 알리지 않는다.
  - 원문 목록(`drawTr`)도 다시 그리지 않는다. 앞 번호는 이미 DB에 반영됐는데 화면은 옛 이름표로 남는다.
  - REV_CHANGED 뒤 [새로 불러오기]를 누르면 `cur.lbl = null`로 남은 초안도 버린다.
- 재현:
  1. 탭 A·B에서 같은 회의록 상세를 연다.
  2. A에서 참석자 1·2·3 이름표를 바꾼다.
  3. A의 첫 PUT과 둘째 PUT 사이에 B에서 발언 하나를 고쳐 저장한다.
  4. 기대: "n명 저장, 참석자 2부터 저장하지 못했습니다". 실제: "다른 사람이 먼저 고쳤습니다…"만 뜨고, 참석자 1은 이미 바뀌어 있다.
- 같은 함수의 부수 문제(P3):
  - 저장 중에도 select를 막지 않는다. 그래서 저장 중에 바꾼 값은 성공 처리의 `delete lb.draft[no]`로 지워진다.
  - 저장 중 [고치기 끄기]를 누르면(`cur.lbl=null`) 실패 오류가 화면에 남지 않는다.

**P2-5 상세에서 [발화자 이름표 바꾸기]를 열면 포커스를 잃는다(코드 추정, 실측 필요)**
- 근거: `toggleLbl`(:1181-1190)은 첫 소속 select에 포커스를 준다. 그 뒤 원문이 아직 없으면 `loadTranscript(cur, then)`이 끝나면서 `drawLbl(cur)`(:1189)가 표를 통째로 지우고 다시 그린다. 포커스를 되돌리는 코드가 없다.
- 기대: 포커스가 `#mn-lb-aff-{첫번호}`에 남는다. 예상 실제: `document.body`로 간다. 키보드·화면낭독 사용자는 자리를 잃는다.

**P3 목록**
- **P3-1** `revertAll`(:1093-1101): 고쳤다가 다시 미리보기 없이 모두 되돌리면 표식이 미리보기 때와 같아진다. 그래서 `#mn-stale`이 숨는다. 그런데 `focusById('mn-restale')`는 숨은 버튼을 겨눠 포커스를 잃는다. 문구 FIX_REVERTED("[다시 미리보기]를 눌러…")도 보이지 않는 버튼을 가리킨다.
- **P3-2** 앞뒤 공백만 다른 수정: 화면은 고침 1건과 배지로 친다(`text !== orig`). 서버는 `trim` 뒤 원문과 같으면 고친 것으로 치지 않는다(`MinutesParse.java:309`). 그래서 저장 뒤에는 '고침' 표시가 없다. 원래 글과 공백만 다른 수정은 표시가 어긋난다.
- **P3-3** 이름표 칸에 소속만 남기고 역할을 비우면 안내는 "역할을 고르세요"다. 그런데 `commit`은 `''`을 받아 이름표를 지운 것으로 반영한다(:1048-1053). 상세라면 저장 때 라벨 삭제 PUT이 나간다. 안내와 실제 동작이 다르다.
- **P3-4** 이력: 라벨을 지운 REV는 `new_text=null`이라 '고친 뒤' 줄이 빠진다(:1464-1466). "지움"이 드러나지 않는다.
- **P3-5** 요약 항목 편집기에는 화면 `lostMasks` 검사가 없다(frontend 보고 3-4). 서버는 ITEM에도 EDIT_MASK_REMOVED를 건다(:1078-1082). 화면에서는 저장을 눌러야 422로 알게 되고, 이 경로를 확인하는 API 시험도 없다(아래 4절).
- **P3-6** 이름표 PUT만 `X-Screen-Id: board_write`이고 같은 상세의 발언·항목 PUT은 `board_minutes`다. 서버 허용 목록에는 둘 다 있다(`MinutesUiIds:17`). 감사 화면 값이 한 상세 안에서 갈린다(frontend 보고의 이관과 같은 건).
- **P3-7** 범위 밖, 같은 부류: 저장 후 제목 수정(`editMeta` :1177-1186)에는 가림 토큰 보존 검사가 없다. 업로드 때 가린 제목의 `[이름]`을 외부인 실명으로 바꿔 쓰면 통과한다. security B1은 UTTER·ITEM만 다뤘다.

**확인한 것(문제 없음)**
- 계약
  - 미리보기·저장 모두 `edits` JSON 파트를 쓴다. 저장 때만 `options.edits_digest`를 보낸다.
  - 서버는 `editsDigest`가 null인데 화면이 값을 보내면 409를 낸다(:931-935). 화면은 응답이 null이면 보내지 않는다(:417, :1642).
- 응답 키
  - 미리보기에는 `speakers[{speaker_no, speaker, label, utter_cnt}]`, `speaker_label_rules`, `transcript[].speaker_no/speaker_label/edited`가 있다.
  - 상세는 `d.edit`일 때만 rules를 준다. 화면 `buildPvSpk`·`drawLbl`이 쓰는 키와 같다.
- 오류: `target_no`는 LABEL_*과 EDIT_*에서 실린다. 화면 `failUpload`(:1603-1608)가 label이면 번호 칸, edit이면 발언 줄에 단다.
- 가림 우회
  - 저장 전: 별도 세션 `base.mask(o)`와 정규화한 고친 글을 비교한다(:282, :305). security B1 그대로다.
  - 저장 후: 잠금 뒤 저장된 `old`와 비교하고 UTTER·ITEM 공통이다.
  - 화면 `lostMasks`도 같은 종류별 판정이다. 토큰을 옮기는 우회(F3)는 그대로 남은 위험이다.
- 정적 계약: 서버 글은 `textContent`/`textNodes`로만 넣는다. 자유 입력과 datalist가 없다. `:root`와 새 색을 건드리지 않았다(CSS 338–358).

## 4. 시험 공백과 추가 제안
- 화면(`board-minutes.test.js`)
  - `mergeFix` 파일 교체 시나리오: `fix.utt[2].orig='a'`이고 새 응답 줄 2의 원래 글이 다르면 버려야 한다. 지금 시험(:296)은 반대 동작을 굳힌다. 서버 계약을 정한 뒤 고친다.
  - `isEditFail({code:'CONTROL_CHAR', slot:'edit'})` → true. `errorText(422,{code:'CONTROL_CHAR',slot:'edit',target_no:3})`.field → 'edit'.
  - `doPreview` 경쟁: 요청 뒤, 응답 전에 `u.fix.labels[2]`를 바꾸면 응답 후 `pvSig !== signature(u)`여야 한다. 가짜 `doFetch`로 지연시켜 시험한다.
  - `saveLabels` 부분 실패: PUT 1은 200, PUT 2는 409라면 `cur.data.speakers[0].label`이 갱신되고 부분 성공 안내가 있어야 한다.
  - 지금 화면 시험은 순수 함수와 소스 검사뿐이다. 컨트롤러 흐름(포커스·순차 PUT) 시험은 없다.
- 서버
  - `BoardMinutesApiTest`: 저장 후 **항목**(PUT items)에서 `[이름]`을 지우면 422 EDIT_MASK_REMOVED가 나는지 시험이 없다. utter만 있다(:875).
  - **저장(upload)** 경로의 EDIT_MASK_REMOVED: 미리보기만 시험한다(:863). 파싱은 같지만 409와의 순서를 확인할 가치가 있다.
  - 라벨 어휘 × 실제 직원 명단: `SpeakerLabelsTest:52`은 빈 사전으로 시험한다. 예를 들어 '차장'·'위원'은 성 + 한 글자 이름으로 읽힐 수 있어, 실제 USERS에 그런 이름이 있으면 어휘 안의 라벨이 LABEL_INVALID{name}으로 막힌다.

## 5. 호출자에게 요청할 실행
- Playwright가 비면 실화면을 실측해 달라(아래 '실화면 확인 필요'). 브라우저를 쓰는 다른 세션이 끝나야 한다.
- `cd kgi-ggreport-web && mvn -q -o test -Dtest=BoardMinutesApiTest,MinutesParseEditsTest,SpeakerLabelsTest` → 전부 통과가 기대값이다(이미 전체 통과라고 받았다. 4절 시험을 더한 뒤 다시 돌린다).

### 실화면 확인 필요(이번에 못 본 것)
1. 미리보기에서 이름표를 고르면 해당 번호 줄만 바뀌고 포커스가 select에 남는지. `#mn-fix` 요약, stale 표시, [저장] 비활성을 확인한다.
2. 발언 [고치기]에서 `[이름]`을 지우면 즉시 오류가 뜨고 [반영]이 꺼지는지. Esc를 누르면 포커스가 [고치기]로 돌아오는지.
3. [다시 미리보기] 요청에 `edits` 파트가 있고, 응답 뒤 고친 줄이 서버가 가린 글로 보이는지. 응답 전에 이름표를 바꾸면 P2-2가 나는지.
4. 미리보기 [원문 보기]·[발언 보기]가 상자 안에서 스크롤·`.is-target`·포커스를 하는지. 버튼 높이가 28px 이상인지 측정한다.
5. 상세 [발화자 이름표 바꾸기]를 처음 열 때 포커스를 잃는지(P2-5) `document.activeElement`로 측정한다.
6. 880px 이하에서 이름표 표의 select가 넘치는지, 96px 화자 칸에 '기관 구청장 2'가 몇 줄로 꺾이는지.
7. 이력 표시: '발화자 이름표 바꿈 (참석자 N)'과 라벨을 지운 경우의 표시(P3-4). 저장 버튼을 쓰지 않고는 이력 데이터가 없을 수 있다.

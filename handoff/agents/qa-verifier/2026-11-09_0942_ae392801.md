## 3. 발견 목록

**F1 (P2, 보안 목적 미달, 확신도 중)**: 파싱 전 계수는 이름이 고정된 파일에만 적용된다.
- 근거: `ZipGuard.java:109-111`의 `isSheetXml`은 `xl/sharedstrings.xml`와 `xl/worksheets/*.xml`만 대상으로 본다.
- POI는 시트와 공유 문자열 파일을 위치가 아니라 `xl/_rels/workbook.xml.rels`의 관계 유형으로 찾는다(이 부분은 추정이며 실행으로 확인 필요).
- 따라서 `xl/ws1.xml`이나 `xl/strings.xml`처럼 이름을 바꾸면 칸·행·글자 수 사전 계수를 모두 건너뛴다. 그러면 security 2-a(POI가 메모리에 다 올린 뒤에야 세는 문제)가 그대로 남는다.
- 2차 방어는 남아 있다: 사후 `cellCount`(`XlsxBook.java:158`)와 `kindsOf`의 32,767자 거부(`:350`). 행 수는 사후 검사가 없다.
- 재현 절차:
  1. 정상 xlsx에서 `xl/worksheets/sheet1.xml`을 `xl/s1.xml`로 바꾼다.
  2. rels의 Target과 `[Content_Types].xml`의 Override도 같이 고친다.
  3. 빈 `<row/>` 30만 개를 넣는다.
  4. `maxRows=200000`으로 업로드한다.
  - 기대: 422 `TOO_MANY_CELLS`
  - 실제(추정): ZipGuard를 통과하고 POI가 끝까지 파싱한다.
- 볼 곳: 대상 판정을 파일 이름 대신 `[Content_Types].xml`의 content type이나 rels로 할지는 백엔드와 security가 판단한다.

**F2 (P3, 정상 파일 오탐 가능)**: 행 수 상한이 새로 생겼고, 걸리면 칸 문구가 나온다.
- 전에는 행 수 제한이 없었다. 이제 `<row>` 합계가 200,000을 넘으면 거부한다(`ZipGuard.java:133-136`).
- 엑셀은 칸이 없어도 서식이나 높이를 준 행을 `<row>`로 저장한다. 수십만 행에 서식을 입힌 실무 파일이 거부될 수 있다.
- 이때 사용자는 "칸이 너무 많습니다"(`BoardWriteService.java:227`)를 보게 되는데, 행이 원인인 경우와 맞지 않아 혼란스러울 수 있다.

**F3 (P3)**: 글자 수를 XML 원문 기준으로 센다.
- `getElementText().length()`(`ZipGuard.java:144`)는 `_x000D_` 같은 OOXML 이스케이프를 풀지 않은 길이다. 엑셀은 CR을 이렇게 7글자로 쓴다.
- 그래서 32,767자에 가까운 정상 칸에 CR이 많으면 실제 글자 수는 한도 안인데 `CELL_TOO_LONG`이 날 수 있다. 드문 경우다.

**F4 (P3, 성능 참고)**:
- `XMLInputFactory.newInstance()`를 대상 파일마다 다시 부른다(`:116`). 매번 서비스 조회 비용이 든다.
- 시트 하나를 모아 둘 때 `ByteArrayOutputStream`과 `toByteArray()` 복사본이 함께 생겨 최대 약 40MB를 쓴다. 동시 처리 2건이면 약 80MB다.

**확인한 항목 ① 정상 파일 오탐 여부** (코드상 문제없음, 샘플 파일 자체는 미확인)
- 파일 이름 대소문자: 70행에서 소문자로 바꾼 뒤 비교하므로 `xl/SharedStrings.xml`도 잡힌다.
- 네임스페이스 접두사: `getLocalName()`을 쓰므로 `x:si`나 `x:t` 같은 접두사가 붙어도 같게 처리된다. Strict OOXML도 같다.
- rPh(발음 표기): `<rPh>` 안의 `<t>`는 세지 않는다. 다만 rPh는 `<si>` 안에서 본문 `<t>`/`<r>` 뒤에 오므로 순서상으로도 문제없다.
- 시트 XML에서 로컬 이름이 `c`, `row`, `t`인 다른 요소는 확인한 범위에서 없었다.
- `profit_sample.xlsx`(테스트 자원)는 `BoardProfitSampleTest:205`에서 `BoardSourceFixture.open`을 거쳐 새 ZipGuard를 통과한다.
- 다만 이 테스트는 자원 파일이 있으면 `docs/samples`를 읽지 않는다(`:46-60`). 그래서 `빈양식`과 `머리글다름`은 새 경로로 검증된 적이 없다.

**확인한 항목 ② 개인정보 탐지 의미 변화**: 실제 위험은 만들지 않는다.
- 왼쪽부터 찾을 때 첫 일치는 수정 전과 같다. 이유는 두 가지다.
  - 로컬부 문자 집합에 `@`가 없어서, 연속열의 맨 앞에서 시도하는 것과 중간에서 시도하는 것의 결과가 같다.
  - 앞에 붙은 뒤돌아보기 조건(lookbehind)은 그 맨 앞 위치에서는 항상 통과한다.
- 놓치는 경우는 앞 일치가 연속열 중간에서 끝났을 때뿐이다. 예: `a@b.com.x@y.com`, `a@b.com_x@y.com`, `a@b.co1x@y.com`의 두 번째 주소.
- 그래도 같은 문자열에서 첫 이메일은 반드시 잡힌다. 그래서 칸 단위 판정(`XlsxBook` Set)과 `BoardFormService.java:477`(하나라도 있으면 거부)은 결과가 바뀌지 않는다.
- 달라지는 것은 초안의 `kinds[].count`(`BoardWriteService.java:198-200`)가 1 줄 수 있다는 점뿐이다.
- 선형성: 시작 가능한 위치는 로컬부 연속열의 맨 앞뿐이다. 도메인 문자 집합은 로컬부의 부분집합이고 `@`를 포함하지 않는다. 따라서 `a@a@a@…`나 `a@`+`a.`×n 같은 입력도 선형으로 끝난다.

**확인한 항목 ③ 거부 경로의 슬롯 반납·자원 정리**: 결함 없음.
- `upload()` 102-111행: 슬롯을 잡은 뒤의 모든 처리가 try-finally 안에 있어 슬롯이 반납된다.
- ZipGuard에서 거부되면 `pkg`를 만들기 전이라 정리할 것이 없다.
- `scanPii`에서 `Rejected`가 나면 `process`가 `ApiException`으로 바꿔 던진다. 이어서 try-with-resources의 `close()`(`pkg.revert`)가 돌고, 그다음 finally에서 슬롯이 반납된다.
- `countXml`의 `Rejected`는 checked 예외라 158행의 catch(`XMLStreamException|RuntimeException`)에 잡히지 않는다. 그래서 거부 코드가 BROKEN으로 바뀌지 않는다. reader는 finally에서 닫힌다.

## 4. 테스트 공백과 추가 제안
1. **docs/samples 3개 전부**: 각 파일을 `ZipGuard.check(bytes, 20MB, 40MB, 200000, 200000, 32767)`과 `XlsxBook.open`(운영 한도)에 넣는다 → 거부 없이 열려야 한다. 지금은 `profit_sample.xlsx` 하나뿐이다.
2. **rPh 제외**: `<si><t>abc</t><rPh><t>`+40,000자+`</t></rPh></si>` → 통과해야 한다. 지금 테스트 없음.
3. **접두사**: `<x:sst xmlns:x=NS><x:si><x:t>`+32,768자 → `CELL_TOO_LONG`. 같은 형태로 `<x:c>` 칸 수 초과 → `TOO_MANY_CELLS`.
4. **sharedStrings 이름 대소문자**: `XL/SharedStrings.XML` 이름으로 32,768자 → `CELL_TOO_LONG`. 지금은 worksheets 쪽 대소문자만 테스트한다(`ZipGuardTest:110`).
5. **F1 확인용**: 고정 경로가 아닌 시트 파일(rels로 연결)을 `XlsxBook.open`으로 연다 → 현재 동작이 어떤지 기록하는 테스트.
6. **XlsxBook 2차 방어 분기**: `kindsOf`의 32,767자 초과 분기(`:350`)와 총량 2천만자 분기(`:358`)는 ZipGuard가 먼저 막아서 지금 어떤 테스트도 지나가지 않는다.
   - 패키지 내부 단위 테스트로 만들거나, F1 경로를 써서 `scanPii` → 422를 확인한다.
   - 그때 `BoardWriteService.process` catch(`:132-134`)를 지난 뒤 슬롯 수가 2인지도 확인한다. 현재 `CELL_TOO_LONG` 서비스 테스트는 open 경로만 지난다.
7. **메모**: 같은 긴 문자열을 칸 1,000개가 가리킬 때 검사 글자 수에 한 번만 더해지는지 확인한다. 상한을 낮춰 주입할 수 없다면 이 테스트는 어렵다(상수가 고정돼 있다).
8. **Pii 의미 기록**: `Pii.scan("a@b.com_x@y.com")` → 이메일 1건(변경된 동작을 테스트로 고정). 선형성 보강용으로 `"a@".repeat(50000)`과 `"a@"+"a.".repeat(50000)`이 1초 안에 끝나는지.
9. `PiiTest`의 `timeout=1000`은 느린 CI에서 흔들릴 수 있다. backend-dev도 같은 점을 적었다.

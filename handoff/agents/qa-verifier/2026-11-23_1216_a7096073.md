# QA 독립 검토: NEXT 102 대시보드(36eecc98, 983b5a64)

## 1. 검토 대상, 방법, 못 본 것
- **대상**: 서버 PrepBoard{Service,Controller,Columns,Mapper.xml,UiIds}·PrepBoardIn·054(mysql·oracle), PrepService 읽기 창 3개(1282-1300행)·PrepUiIds, 시험 PrepBoardApiTest·PrepBoardServiceTest·PrepBoardDdlPairTest·CommonCodeSchemaTest. 화면은 frontend/js/prepboard.js 전체, prep.js 연결부(985-1033, 1182-1194, 1741-1791), index.html #pp-root.
- **방법**: 코드를 읽기만 했다. git 명령은 실행하지 못해 `--stat` 대신 Glob으로 파일을 찾았다.
- **화면은 열지 못했다**: Playwright 브라우저를 다른 세션이 쓰고 있어 "Browser is already in use" 오류가 났다. 실측(대비·포커스·넘침) 값이 없다.
- **테스트 결과는 메인이 보고한 값을 그대로 옮긴다**: 서버 20/20 등, node 통과. 나는 아무것도 실행하지 않았다.
- **깊이 대조하지 못한 것**: design-reviewer 규격(ae4db5c1) 5·6절과 화면의 문구·CSS 대조.

## 2. 판정: 조건부 통과
권한·감사·입력 검증의 뼈대는 설계대로 구현됐고 시험으로 덮여 있다. P1은 없다. 다만 화면에 계정이 바뀔 때 생기는 경쟁 조건이 있고(P2), 결재 끝난 건(WRITABLE·WRITING)의 체크 감사를 시험이 직접 확인하지 않는다(P2).

### 권한 확인 결과(물어본 항목)
- **다른 담당자 건 체크**: 막힌다. save()는 건 행을 잠근 뒤 `isActiveAssignee`가 아니면 403을 낸다(PrepBoardService.java:280-283). 팀장·부장도 담당이 아니면 403이다(D12).
- **다른 팀**: 막힌다. 목록은 `canList`가 영업팀·팀장·부장만 통과시킨다(83-87). 디자이너·관리자는 403이고 거부 감사가 남는다(D5). 화면도 prep.gateOf가 VIEW_ROLES로 먼저 막는다.
- **종료(CANCELLED) 건**:
  - 서버: 담당이면 409 STATE_CHANGED, 담당이 해제됐으면 403. 실패 감사가 남는다(D20).
  - 화면: ended 행은 단추를 만들지 않는다(prepboard.js:160).
- **DB 길이**: 감사 칸 'CK_'+17자는 20자로 BID_PREP_ACT.TASK_CD(20)에 맞는다. ACTION_CD는 30자 칸에 최대 15자(DASH_LIST_ENDED·DASH_CHECK_SAME)다.
- **기존 화면 영향**: BID_PREP_ACT를 읽는 기존 질의가 없다. DASH_ 줄이 섞여 기존 화면에 보이는 회귀는 없다.

## 3. 발견 목록

### P2-1. 계정을 바꾸면 이전 계정의 표가 새 계정 화면에 남을 수 있다(prepboard.js)
- **근거**:
  - `fresh()`가 `seq: 0`으로 초기화한다(395-396행).
  - `pb.reset()`은 `B = fresh()`로 통째로 바꾼다(753-754행).
  - `load()`의 응답 판정은 `token !== B.seq`다(536·539행).
  - 그래서 이전 계정 요청(token 1)이 진행 중일 때 계정을 바꾸면 새 첫 요청도 token 1이 된다. 이전 계정 응답이 늦게 도착하면 그대로 받아들여진다.
- **결과**: 이전 사람의 is_mine·can_check·"내 담당" 표시가 새 계정 화면에 남는다. 데이터 손상은 없다 — 그 상태로 칸을 저장하면 서버가 403을 내고 DENIED 감사가 남는다.
- **재현**:
  1. 개발자도구에서 네트워크를 느리게(Slow 3G) 둔다.
  2. 김영업으로 대시보드를 연다.
  3. 응답이 오기 전에 다른 영업 계정으로 바꾼다.
  4. 기대: 새 계정 기준의 표. 실제: 응답 순서에 따라 이전 계정 기준의 표가 남을 수 있다.
- **수정 방향**: 요청 번호를 `B` 밖의 모듈 변수로 두어 계속 늘린다. prep.js의 `freshState`/`S.seq`도 같은 방식인지 확인이 필요하다.

### P2-2. 결재 끝난 건의 체크 감사를 시험이 직접 확인하지 않는다
- 사용자 불변 규칙("결재 끝난 건은 누가·어느 화면·어느 버튼")의 대상은 WRITABLE·WRITING 건이다.
- 그런데 PrepBoardApiTest D8~D19는 모두 `opened(INST)`(사전준비 중으로 보임) 상태만 쓴다. 승인 뒤 상태에서 저장과 감사가 되는지 확인하는 시험이 없다.
- 코드상으로는 같은 경로로 남는다(PrepBoardService.java:316·325). 회귀를 막을 시험만 비어 있다. 추가 케이스는 4절 T1.

### P3-1. 계정을 바꿀 때 열려 있던 칸 메뉴가 닫히지 않는다
- `pb.reset()`(753-756행)이 `B = fresh()`를 먼저 하고 `closeMenu(false)`를 부른다. 이때 `B.menu`가 이미 null이라 바로 돌아가고, 메뉴 DOM은 이전 계정 내용으로 화면에 남는다.
- 그 메뉴를 눌러도 `pick()`이 `B.menu` null에서 멈춰 저장은 되지 않는다.
- **재현**: 담당 칸 메뉴를 연 채로 계정을 바꾼다. 기대: 메뉴 닫힘. 실제: 메뉴가 남는다.
- **수정 방향**: closeMenu를 B 교체보다 먼저 부른다.

### P3-2. 저장 중에 [새로 고침]을 누르면 칸이 옛 값으로 보일 수 있다
- `load()` 성공 시 `B.pending = {}`로 비우고 B.data를 새로 바꾼다(544행).
- 진행 중이던 PUT의 then은 분리된 옛 row 객체에만 결과를 쓴다(658행).
- GET이 커밋 전 값을 읽었다면 저장은 성공했는데 표에는 옛 값이 보인다. 다음에 고르면 409 STALE_CHECK가 나고 새로 고치면 회복된다.
- **재현**: 칸을 저장하는 중(네트워크 느리게)에 [새로 고침]을 누른다.

### P3-3. 목록 감사에 '어느 건을 보았는지'가 없다
- DASH_LIST는 건 번호 NONE으로 한 줄만 남는다(Controller:74).
- 대시보드는 결재 끝난 건의 진척(자동 칸 완료일·손 칸 체크자 이름·담당자)을 영업팀 전원에게 보여 준다. 상세 열람(VIEW)과 달리 건 단위 기록이 없다.
- 규칙의 "모든 행위"에 목록 열람이 들어가는지는 정책 판단이다 → 이관(기획).

### P3-4. 노출 기준이 칸마다 다르다
- 상세를 못 여는 종료 건에서 확정자 이름만 가린다(Service:175, security F3).
- 같은 행의 `assignee_names`와 손 칸 `by_name`(체크한 사람)은 그대로 나간다(176·242행).
- 의도된 것인지 확인이 필요하다 → 이관(기획·security).

### P3-5. 체크 권한에 역할 확인이 없다
- save()는 `canList`를 보지 않는다. 담당 배정이 남은 채 역할이 영업 밖(디자이너 등)으로 바뀐 사용자도 체크할 수 있다.
- 업무 규칙 수준의 가장자리다. 막으려면 save 앞에 `canList(me)`를 두고 같은 403을 내면 된다.

### P3-6. 기존 목록 화면의 접근 경로가 줄었다(회귀 위험)
- 표가 있으면 왼쪽 목록 `#pp-list`를 숨긴다(prep.js:1002).
- 대시보드는 기관당 1줄이라(Service:118-127), 같은 기관의 예전 확정 취소 건은 이 메뉴에서 열 수 없다. 옛 '진행/끝난' 탭으로 보던 건들이다.
- **재현**: 한 기관을 확정→취소→재확정한 뒤 [취소·중단한 건도 보기]를 켠다. 기대: 옛 취소 건을 열 수 있음. 실제: 활성 건 1줄만 보인다.
- 의도라면 기획 확인이 필요하다.

### P3-7. 기관을 열 때 불필요한 목록 요청이 나간다
- 표에서 기관 이름을 누르면 `enterCase`가 숨겨진 목록용 `loadList()`를 부른다(prep.js:1021).
- 이 요청은 `GET /preps`에 머리 `prep_list/refresh`를 싣는다. 사용자는 대시보드에서 눌렀는데 접근 이력에는 다른 화면으로 남는다. BID_PREP_ACT에는 남지 않는다.

### P3-8. 행마다 DB 질의가 반복된다
- `currentBanks`가 행마다 질의한다(255행).
- `boardCanSee`도 영업팀원이면 행마다 `isActiveAssignee`를, 종료 건이면 `countEverAssigned`도 추가로 질의한다(PrepService:736·754).
- 기관 수가 백 단위를 넘으면 느려진다. 이미 주석으로 알려진 비용이다.

### P3-9. 'bid_expected_date'가 실제로는 현재 약정 종료일이다
- 값은 `BidPrep.contractEnd`다(101-104행). 화면은 "입찰 예정일(추정)"이라고 표시한다(prepboard.js:194).
- 표시는 정직하다. 다만 엑셀의 '입찰 예정일'과 같은 뜻인지는 기획 확인이 필요하다.

## 4. 테스트 공백과 추가 제안

| # | 입력 | 기대값 |
|---|---|---|
| T1 | 사전준비 승인을 거쳐 WRITABLE이 된 건에서 담당이 PUT FIN_COMMITTEE DONE(base 0) | 200. BID_PREP_CHECK에 SCREEN_ID=prep_dashboard·BUTTON_ID=dash_check·UI_VALID=1. BID_PREP_ACT에 DASH_CHECK OK, STATE_CD=WRITABLE, ACTOR_EMP_NO=담당 |
| T2 | T1과 같고 상태만 WRITING | 같은 결과, STATE_CD=WRITING |
| T3 | CONFIRMED(또는 OPEN_PENDING) 건에 담당이 PUT | 409 STATE_CHANGED, 행 0, BLOCKED 감사 1 (D7은 목록의 can_check만 본다) |
| T4 | X-Screen-Id·X-Button-Id 없이 PUT | 200, SCREEN_ID=UNKNOWN·UI_VALID=0이 두 표 모두에 남음 |
| T5 | 400(BAD_MARK)·404·409 NOT_MANUAL 각각 | BID_PREP_ACT에 INVALID·HIDDEN·BLOCKED 줄이 1개씩, TASK_CD=CK_{열} (형식 밖 열이면 NULL) |
| T6 | 서로 다른 base로 동시 PUT 2건(D11 번호가 비어 있음) | 하나는 200, 하나는 409 STALE_CHECK, 행 1 |
| T7 | 활성 건이 있는 기관과 종료 건만 있는 기관, include_ended=true | 기관당 1줄, 활성 기관은 ended=false |
| T8 | 화면(node, DOM 모의): 요청 A 진행 중 reset() → 요청 B → A 응답이 B보다 늦게 도착 | B.data가 B 응답이어야 함(P2-1 재현) |
| T9 | 화면: 메뉴가 열린 상태에서 reset() | 메뉴 DOM이 display:none이어야 함 |

시험이 구현에 과하게 묶인 곳은 없다. U4(잠금 순서 확인)는 의도된 결합이다.

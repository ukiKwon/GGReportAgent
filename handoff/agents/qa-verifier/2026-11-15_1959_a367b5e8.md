## 3. 발견 목록
**[권고 P3, 보안 판단에 따라 P2로 올라갈 수 있음] 경로 중간에 `;`가 있으면 그 뒤가 전부 잘린 채 기록된다**
- 근거: `config/StaticCacheFilter.java:69-72`. `p.indexOf(';')`부터 끝까지 버린다. 세그먼트 단위로 `;…`만 떼지 않는다.
  - 변경 후 AccessLogInterceptor(`:44,51`)가 이 값으로 skip을 판정하고 REQ_PATH에도 이 값을 쓴다.
- 영향: Boot 2.7의 기본 경로 매칭(PathPatternParser)은 세그먼트별 경로 매개변수를 무시하고 라우팅한다. 그래서 정상으로 처리된 API 호출이 잘린 경로로 기록된다.
- 재현 절차(시험 형태):
  1. `fire("GET","", "/tasks;x=1/1/files/a.xlsx")`
  2. 기대: REQ_PATH `/tasks/1/files/a.xlsx`
  3. 실제(코드상): `/tasks`. `POST /approval-requests;x/assignee-change`도 `/approval-requests`로 기록된다.
- 정적·auth 판정으로 기록 자체를 빼먹게 만들 수 있는지(예: `/auth/x;/../../tasks/…`)는 컨테이너가 `..`를 어떻게 정규화하는지에 달려 있다. 확정하지 못했다. 변경 전에는 원 URI를 그대로 기록했으므로 이번 변경으로 새로 생긴 동작이다.
- `;jsessionid`처럼 끝에 붙는 일반적인 경우는 정상으로 처리된다.

**policyFor 회귀: 없음**

**ApiException 관례: 맞음**
- 같은 패키지(`web.ApiException`)를 쓴다. 문구 "입찰 건을 지정하세요."는 서비스 `ApprovalRequestService.java:122`와 같다.
- 가드(`:77`)가 앞에 있어서 401·403이 400보다 먼저 나온다. 시험 `:115-116`이 이 순서를 고정한다.
- 작은 차이: `{"reason":""}`(사유와 건 번호 둘 다 없음)를 보내면, 예전에는 사유 문구가 나왔고 이제는 건 번호 문구가 나온다. 화면 영향은 미미하다.

**required=false와 JSON 파싱 오류: 바뀌지 않음**
- required=false는 본문이 비었을 때만 null을 넘긴다. 깨진 JSON은 여전히 HttpMessageNotReadableException이다.
- ApiExceptionHandler는 이 예외를 잡지 않는다(`:27-28` 주석대로 의도된 것). 그래서 스프링 기본 400이 나간다.
- 단, 응답 본문이 `{"detail":…}` 형식이 아닐 수 있다. 이건 이번 변경 전부터 그랬다.

**AccessLogContextPathTest 간섭: 문제없음**
- pom에 parallel·forkCount 설정이 없다.
- `LOG_ID > base`로 정리하는 방식은 HeadPhotoRollback·InstitutionHeadConcurrency·PrepRollback 시험과 같다.
- record가 REQUIRES_NEW(동기)이므로 커밋 직후 바로 조회된다.

**공허한 시험 여부: 대체로 아님**
- 1·2번 시험(0건 단정)에는 같은 메서드 안에 '기록이 실제로 된다'는 대조군이 없다. 대신 같은 클래스의 3~5번이 기록 동작을 보장하므로 허용 범위다.
- `AssigneeChangeApiTest:114`(빈 본문 `""`)는 상태 400만 보고 문구는 보지 않는다. 예전 기본 400과도 구분되지 않는다.

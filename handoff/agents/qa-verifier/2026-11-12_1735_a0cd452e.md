## 3. 요청한 네 가지와 발견 목록

**(1) 서울 3곳이 실패하면 종료 코드 0인가 — 3곳만 보면 그렇다.**
- 분류 경로: 만료 인증서 오류(`ssl.SSLCertVerificationError`)가 나면 urllib이 이를 `URLError(reason=...)`로 감싼다. `httpclient.py:221-222`가 이를 `_tls_error`로 넘기고, `:110-111`에서 `FetchTlsError`가 되며, `:70`에서 `"tls_verify"`로 분류된다.
- 실측 근거: 11-12 로그 2행에 세 곳 모두 `[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certific…`가 찍혀 있다. 이 문구는 Python이 `SSLCertVerificationError`로만 낸다. 따라서 실제 경로로 확인된 셈이다.
- 재시도 없음: `tls_verify`는 재시도와 2nd pass 대상이 아니다(`eminwon.py:364`). 설정의 `known_failing_kind`도 `"tls_verify"`(json:20·608·1043)라서 `_is_known`이 참이 되고(`pipeline.py:42-43`), 세 곳은 종료 코드 3에서 빠진다.
- **[P3-1] 그래도 "11-16 종료 코드 0"은 보장되지 않는다.** 11-12 실행은 25곳 실패, `eminwon exit=3`이었다(로그 3행). 그중 시간 초과 12곳은 알려진 실패로 등록돼 있지 않아 다시 나면 3이 된다. 이것이 의도된 동작이라면 결함은 아니다. 다만 "서울 3곳 때문에 3이 나오지 않는다"와 "0이 나온다"를 구분해서 보고해야 한다.
- **[P3-2] 문구와 실제 오류가 어긋난다.** `tls_reason`과 `known_failing`은 "만료(verify 10)"라고 적었지만, Python 실측 문구는 자체 서명 루트(verify 19)다. 분류는 오류 클래스로 하므로 동작에는 영향이 없다. 재검토하는 사람이 헷갈릴 수 있으니 사유 글에 두 사실을 같이 적을 것을 권한다.

**(2) `_reclaim`의 Windows 동작 — 대체로 안전하다.**
- 살아 있는 주인이 6시간을 넘겨도 지워지지 않는다. `os.open`(CRT)은 삭제 공유 권한 없이 파일을 열고, 주인은 `main`이 끝날 때까지 fd를 쥔다(`cli.py:184`). 그래서 남이 지우려 하면 `PermissionError`가 나고 `False`가 되어 "다른 실행 중"(4)으로 처리된다(`:117-119`). 회수하는 쪽이 내용을 비교한 뒤 지우기 전 틈에 새 잠금이 생겨도, 새 주인이 fd를 쥐고 있어 Windows에서는 지워지지 않는다.
- **[P3-3] 표식이 남는 경로가 두 가지다.** ⓐ `finally`에서 표식을 지울 때 백신 등이 잡고 있으면 실패한다(`:122-125`). ⓑ 회수 도중 프로세스가 죽는다. 그 뒤 다시 오래된 잠금이 생기면, 첫 실행은 600초 넘은 표식을 지우고 바로 `False`를 돌려준다(`:99-103`). 주간 실행이라 한 주를 잃는다(4로 종료). 수정안: 오래된 표식을 지운 뒤 같은 호출 안에서 표식 생성을 한 번 더 시도한다.
- **[P3-4, 이번 변경 전부터 있던 결함] `_lock`의 `os.open(O_EXCL)`(`cli.py:76`)은 `FileExistsError`만 잡는다.** eminwon이 끝나며 `_unlock`으로 지운 직후 g2b가 바로 시작한다. 그 사이 백신이 공유 삭제 핸들로 파일을 잡고 있으면 파일이 "삭제 대기" 상태로 남는다. 이때 `CREATE_NEW`는 `ERROR_ACCESS_DENIED`, 즉 `PermissionError`를 낸다. 결과는 traceback과 종료 코드 1이고, 최종 코드도 1이 된다. 드물지만 이 PC(1809)에서 가능하다. 수정안: `PermissionError`를 잡고 짧게 기다린 뒤 다시 시도하거나 4로 처리한다.

**(3) cmd 배치의 ERRORLEVEL 처리 — 문제없다.**
- `set RC_E=%ERRORLEVEL%`(15·19행)는 괄호 블록 밖의 단독 줄이다. 직전 명령이 끝난 뒤 해석되므로 지연 확장이 필요 없다. `>> 2>&1` 리다이렉트는 ERRORLEVEL을 바꾸지 않는다. `endlocal & exit /b %FINAL%`(34행)는 `endlocal` 전에 값이 펼쳐지는 표준 관용구다.
- 순위 매핑(23-32행)과 같은 순위일 때 eminwon 쪽 코드가 이기는 것은 주석과 일치한다. 9009(python 없음) 같은 그 밖의 코드는 가장 나쁜 순위로 올라간다.
- **[P3-5, 이번 변경 전부터 있던 결함]** powershell이 실패하면 `SINCE`가 비어 `--since`만 남는다. 이 경우 argparse가 2로 끝나고, 로그 파일 이름도 `_weekly.log`가 된다. 최종 코드는 2로 드러나므로 낮은 우선순위로 둔다.

**[P3-6] 테스트 파일 `test_hardening.py:452-453`의 문자열 이스케이프.** `'"C:\dev\python\python.exe"…'`에서 `\d`·`\p`는 유효하지 않은 이스케이프라 3.12에서 `SyntaxWarning`이 난다. 지금은 통과하지만 `-W error`로 돌리면 깨진다. 수정안: 원시 문자열(r'')로 바꾼다.

## 4. 테스트 공백과 추가 제안
1. **실제 감싸기 경로 시험이 없다.** 지금 시험(`:333`)은 `_tls_error`를 직접 부를 뿐이다. 제안: `_patch_opener`가 `urllib.error.URLError(ssl.SSLCertVerificationError(1,"certificate verify failed: self-signed certificate in certificate chain"))`를 던지게 한다 → `HttpClient.get`이 `FetchTlsError`를 내고 `FetchTlsHandshakeError`는 아니며, `error_kind`가 `"tls_verify"`인지 확인한다.
2. 알려진 호스트가 `FetchTlsHandshakeError`로 실패하는 경우가 없다. `:339` 매개변수에 `(FetchTlsHandshakeError("x"),"tls_handshake")`를 더한다 → 2nd pass를 거친 뒤에도 종료 코드 3, 실패 종류 `tls_handshake`여야 한다.
3. 2nd pass에서 실패 종류가 바뀌는 경우: 알려진 호스트(`tls_verify`)가 1차에 `conn`, 2차에 `tls_verify`로 실패한다 → 최종 종류 `tls_verify`, 종료 코드 0.
4. 회수 표식 삭제 실패: 표식 삭제만 실패하도록 패치한다 → 이번 `_lock`은 성공하고 표식이 남는다. 다음에 오래된 잠금이 생기면 몇 번째 실행에서 회복되는지 확인한다.
5. Windows 전용: 다른 fd가 쥔 오래된 잠금 → `_lock`이 `None`을 돌려주고 파일이 남는지 확인한다.
6. cmd 시험에 `(9009,0,9009)`와 `(2,1,2)`(같은 순위일 때 eminwon 우선)를 더한다.

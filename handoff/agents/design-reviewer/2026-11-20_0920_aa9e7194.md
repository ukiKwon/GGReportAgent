## 기관 사업계획 화면에 '목표/관심' 필터를 넣는 배치 3가지 안 (design-reviewer, 읽기 전용)

### 1. 무엇을 보고 어떻게 봤나, 못 본 것
- **본 방법**: 소스만 읽었습니다. Playwright로 화면을 열지 않아서 측정값은 없습니다. 8080 서버를 써도 된다는 허락을 받지 못했기 때문입니다.
- **읽은 곳**:
  - `frontend/js/plans.js`: `SKELETON`, `visibleRows`, `listRows`, `filterByStatus`, `stateChipsHtml`, `groupLabelHtml`, `footHtml`, `renderList`, `renderFoot`, `freshState`, `onChange`
  - `frontend/index.html`: `.pl-work`, `.pl-pers`, `.db-per`
  - `frontend/js/dashboard.js`: `setGoals`, `loadGoals`
  - `frontend/js/kbboard.js`: `/bid-targets`, `watch_items`
  - `PlanCollectController.java`의 엔드포인트, `PlanCollectService.java`의 MAX 상수
  - `handoff/NEXT.md` 98번
- **못 본 것**:
  - 실제 1280px 화면에서 필터 줄이 몇 줄로 접히는지. 목록 칸은 380px입니다.
  - 1280×720에서 목록 높이가 얼마나 줄어드는지.
  - `/bid-targets`를 디자이너 계정으로 실제 받을 수 있는지(98번에 '디자이너 열람 2e7b366'이라는 기록만 있음).
  - `docs/design_history`. 이번은 시안이라 전/후 장은 대상이 아닙니다.

### 2. 근거로 확인한 사실
- **목표·관심 기관의 저장 위치**: 서버 표 `INST_BID_TARGET.KIND_CD`(GOAL/WATCH, 044)입니다.
  - 조회는 `GET /bid-targets?year=` 하나입니다. 응답 `items`가 그해 목표, `watch_items`가 관심입니다(관심은 연도 없음).
  - 화면에 보이는 곳은 입찰 현황판(`kbboard.js`)의 '올해 목표 기관'과 '관심 기관' 탭입니다.
  - `dashboard.loadGoals`는 [제안 확정]을 할 수 있는 역할만 받고, `watch_items`는 일부러 읽지 않습니다(dashboard.js 348줄). plans.js가 그대로 가져다 쓸 수는 없습니다.
- **plans.js 목록은 '입찰 임박 기관'**입니다. 행은 진행 중 공고와 기간 창(`windowItems`: 3개월·6개월·1년·전체, 기본 6개월)으로 만들어집니다.
  - '전체'도 날짜를 아는 곳만 담습니다(`groupLabelHtml`의 '전체(날짜를 아는 곳)').
  - '결과 확인' 기관(마감 지남 등)은 목록에서 뺍니다.
  - **그래서 목표·관심 기관이라도 입찰일을 모르거나 이미 지났으면 지금 목록에 나오지 않습니다.** 세 안을 가르는 가장 큰 기준이 이것입니다.
- **조회 조건 지금 구조**(`.db-list-head`, 380px 칸 안):
  - 1줄: `.pl-pers` 안에 기간 묶음 `#pl-win` [3개월|6개월|1년|전체]과 상태 묶음 `#pl-stat` [모두|자료 있음|자료 없음]. 이 줄은 flex-wrap이라 380px에서는 이미 두 줄로 접힐 가능성이 높습니다(실측 못 함).
  - 2줄: 검색 `#pl-q`와 지역 `#pl-region`.
  - 그 아래 `#pl-g` 요약줄: "6개월 안 n곳 · 자료 없음 m곳 · 가까운 순".
  - 목록 바닥 `#pl-foot`: 결과 확인 안내와 CSV 줄("목록에 담을 기관 n곳 · 자료 없는 기관 내려받기(CSV)").
- **목록 3행 칩**(`stateChipsHtml`): 칩은 최대 4개입니다.
  - 자료 없음: 점선 칩, 그리고 수집 실패/수집 제외 칩이 붙을 수 있음. 열린 요청이 있으면 '사업계획 요청됨'/'사업계획 수집 중' 칩 하나만.
  - 자료 있음: '사업계획 n건' + new + 기간 지남 + 오래됨 + 요청됨/수집 중(또는 실패·제외).
  - option 안에는 버튼을 둘 수 없습니다(규격 P1-1).
- **서버**:
  - 수집 요청은 기관 한 곳씩만 됩니다(`POST /institutions/{id}/plan-collect`). **일괄 요청 엔드포인트는 없습니다.**
  - 요청할 수 있는지는 `/plan-collect/status`의 `can_request`(CS.can)로 정해집니다. 디자이너는 false, 재무부서는 403입니다.
  - 관리용 일괄 처리는 키 50개 한도(`MAX_KEYS`)입니다.

│ [기관명 검색        ][전체 지역 ▾] ││                               │

- **② 동작**:
  - 라디오 묶음(`.db-per` 모양 그대로)이고 기본값은 '모든 기관'입니다.
  - '목표·관심'은 둘의 합집합, '목표'와 '관심'은 각각입니다. '목표'는 올해 목표만 뜻합니다.
  - 기간·상태·검색·지역과 모두 함께 거릅니다(교집합).
- **③ 일괄 요청 버튼**:
  - 위치: 바닥 CSV 줄 아래 한 줄입니다.
  - 보이는 조건: 대상이 '모든 기관'이 아니고, CS.can=true이고, 대상 기관이 1곳 이상일 때만.
  - 문구: [자료 없음·오래됨 n곳 수집 요청]
  - 확인 상자는 공통 팝업 `.dlg`를 씁니다(아래 6절 규격).
- **④ 장점**: 지금 구조에 가장 적게 손댑니다.
- **④ 단점**:
  - 기간 밖, 날짜 미상, 결과 확인 기관인 목표·관심 기관이 빠집니다. 그래서 '전체 세팅' 목적을 채우지 못합니다(**치명적**).
  - 묶음이 세 줄이 되어 380px 칸의 목록 높이를 더 잡아먹습니다.
  - 선택지 4개 묶음이 3개 겹치는 인지 부하가 있습니다.
- **⑤ 구현 영향**:
  - `freshState`에 `tgt`, `SKELETON`에 `#pl-tgt` fieldset을 더합니다.
  - `plans.tgtHtml`을 새로 만들고, `visibleRows`에서 걸러 냅니다.
  - `onChange`에서 `pl-tgt`를 처리합니다.
  - `footHtml`에 인자와 버튼을 더합니다.
  - 목표·관심 집합을 받는 캐시를 새로 만듭니다(`/bid-targets`).

#### B안: 목록 제목을 두 보기로 나눈다, [입찰 임박 기관 | 목표·관심 기관] (권장)

```
┌──────────────────────────── 380px ┐┌ 상세 ─────────────────────────┐
│ ┏입찰 임박 기관┓ 목표·관심 기관 17 ││                               │
│ ────────────────────────────────── ││                               │
│ [모두 17|목표 9|관심 8]            ││                               │
│ [모두|자료 있음|자료 없음]         ││                               │
│ [기관명 검색        ][전체 지역 ▾] ││                               │
│ 목표·관심 17곳 · 자료 없음 3 · 오래됨 2 · 자료 상태 순               │
│ ┌ 확인 필요 5곳 ──────── [5곳 수집 요청] ┐                          │
│ └──────────────────────────────────────┘ │                         │
│ ┌──────────────────────────────┐ ││                               │
│ │ ○○구청   목표  D-34          │ ││                               │
│ │ 서울 · 2027-01-02 …          │ ││                               │
│ │ [자료 없음]                  │ ││                               │
│ ├──────────────────────────────┤ ││                               │
│ │ △△대학교 관심  날짜 미상     │ ││                               │
│ │ 경기 · 입찰 예정일 미상      │ ││                               │
│ │ [사업계획 4건][오래됨]       │ ││                               │
│ └──────────────────────────────┘ ││                               │
│ 담을 기관 3곳 · 자료 없는 기관 내려받기(CSV)                          │
└──────────────────────────────────┘└───────────────────────────────┘
```

- **② 동작**:
  - **목록 제목 자리**: 지금의 `h2#pl-lt`가 탭 두 개(`role=tablist`)가 됩니다. 기본은 '입찰 임박 기관'이라 지금 모양이 그대로 남습니다.
  - **'목표·관심 기관' 탭의 행**: 올해 목표와 관심을 모두 담습니다. 기간 창·결과 확인 제외를 적용하지 않습니다(**입찰일과 무관하게 전부**).
  - **기간 묶음 자리**: [모두 n|목표 n|관심 n]으로 바뀝니다. 기본은 '모두'이고, 건수를 함께 보여 둘을 나눠 볼 수 있습니다.
  - **그대로 쓰는 조건**: 상태 묶음·검색·지역.
  - **정렬**: 자료 상태 순입니다. 자료 없음 → 오래됨 → 기간 지남 → 요청됨/수집 중 → 자료 있음 순이고, 같은 칸 안에서는 입찰이 가까운 순입니다. 요약줄 끝 문구도 '가까운 순' 대신 '자료 상태 순'으로 바꿉니다.
  - **목표/관심 표시**: 행 1줄 기관명 옆에 글자 칩을 붙입니다. 3행에는 넣지 않습니다(3행은 상태 칩 전용).
    - 목표: `pp-neutral`, 글자 '목표'
    - 관심: 점선 `pop-unk`, 글자 '관심'
    - 색만으로 구분하지 않습니다.
  - **날짜 칩**: 행 1줄 오른쪽에 둡니다. 입찰일을 모르면 지금 있는 '날짜 미상' 칩을, 지났으면 D+를 씁니다.
- **③ 일괄 요청 버튼**:
  - 위치: 요약줄 `#pl-g` 바로 아래, 스크롤 영역 맨 위에 붙는 '확인 필요 n곳' 띠(`.pl-chk`)에 둡니다.
  - 문구: [n곳 수집 요청]. n은 지금 걸러진 기관 중 아래 두 조건을 모두 갖춘 곳의 수입니다.
    - 자료 없음 또는 오래됨
    - 열린 요청 없음, 서버 등록됨(`ID_RE` 통과)
  - n=0이면 띠에 "확인 필요한 기관이 없습니다."만 쓰고 버튼은 뺍니다.
  - 확인 상자는 6절 규격입니다.
  - 디자이너에게는 띠에 "확인 필요 5곳"까지만 보이고 버튼은 없습니다(지금 `reqLineHtml`의 can=false 원칙과 같음).
- **④ 장점**:
  - '전체 세팅'이라는 목적을 그대로 담습니다. 입찰일과 무관하게 목표·관심 기관이 하나도 빠지지 않습니다.
  - '입찰 임박' 보기는 영업부서가 쓰던 그대로 남습니다.
  - 버튼이 걸러진 결과 바로 위에 있어서, 눌렀을 때 대상이 무엇인지 눈에 보입니다.
- **④ 단점**:
  - 두 보기가 생겨 상태 관리가 늘어납니다(탭마다 묶음이 바뀜).
  - 띠 한 줄만큼 목록 높이가 줄어듭니다. 1280×720 실측이 필요합니다(QA 11-16 '목록이 행 2개로 눌림' 전례).
- **⑤ 구현 영향**:
  - `SKELETON`: 제목을 탭으로, `#pl-win` 자리를 두 용도로 씁니다.
  - `freshState`: `view`·`tgt`를 더합니다.
  - `visibleRows`/`listRows`: 목표·관심 보기용 행 만드는 함수 `plans.targetRows`를 새로 만듭니다. `dataList()`의 rec과 `/bid-targets` id를 묶고, 날짜는 `dashboard`의 item 모양을 그대로 씁니다.
  - `groupLabelHtml`: 보기별 문구.
  - `rowHtml`: 목표/관심 칩.
  - `renderList`: 정렬과 띠.
  - `onClick`: 탭과 일괄 버튼.
  - `onKey`: 탭 좌우 화살표.
  - `/bid-targets` 캐시를 새로 만듭니다.
  - `footHtml`은 그대로 둡니다. CSV는 지금 보기 기준입니다.

#### C안: 작업 칸 위 전폭 '점검 띠' + 목록 필터 토글 하나

```
┌ 기관 사업계획 — 입찰이 가까운 기관부터 … ──────────────────────── 1280 ┐
│ 목표·관심 기관 사업계획 점검   목표 9곳: 자료 없음 2·오래됨 1           │
│                                관심 8곳: 자료 없음 1·오래됨 1           │
│                      [목록에서 보기]  [5곳 수집 요청]                   │
└────────────────────────────────────────────────────────────────────────┘
┌ 입찰 임박 기관 ───────────── 380px ┐┌ 상세 ─────────────────────────┐
│ [3개월|6개월|1년|전체]             ││                               │
│ [모두|자료 있음|자료 없음]         ││                               │
│ [기관명 검색   ][전체 지역 ▾][☐ 목표·관심만]                         │
│ 6개월 안 n곳 · …                   ││                               │
```

- **② 동작**:
  - **띠 숫자**: 기간·필터와 무관한 전체 목표·관심 기준입니다.
  - **[목록에서 보기]**: '목표·관심만' 체크와 기간 '전체'를 켭니다. 단, 날짜 미상·결과 확인 기관은 여전히 빠지는 문제가 A안과 같습니다.
  - **'목표·관심만'**: 체크박스 하나라서 목표·관심을 각각 보지는 못합니다. 각각은 띠의 숫자로만 봅니다.
- **③ 일괄 요청 버튼**:
  - 위치: 띠 오른쪽입니다. 대상은 '전체 목표·관심 중 확인 필요'이고, 화면 필터와 무관합니다.
  - 문구: [n곳 수집 요청]
  - 확인 상자는 6절과 같습니다.
  - 디자이너에게는 띠에 숫자만 보이고 버튼은 없습니다.
  - 확인 필요가 0곳이면 띠를 "목표·관심 기관 17곳 모두 최신입니다." 한 줄로 접습니다.
- **④ 장점**:
  - 처음 한 번 하는 세팅에는 가장 빠릅니다. 화면에 들어오자마자 숫자와 버튼이 보입니다.
  - 목록 칸(380px)을 거의 건드리지 않습니다.
- **④ 단점**:
  - 버튼 대상(전체)과 목록에 보이는 행(기간으로 걸러진 것)이 달라, 무엇을 요청하는지 한눈에 맞춰 보기 어렵습니다.
  - 세팅이 끝난 뒤에도 띠가 매일 높이를 차지합니다.
  - 띠가 페이지 전체에 걸쳐 있어 위계가 '입찰 임박 기관'보다 위로 올라갑니다. 기본 업무(입찰 임박 확인)가 밀려납니다.
- **⑤ 구현 영향**:
  - `SKELETON`: `.pl-work` 앞에 `#pl-chk`를 둡니다.
  - `renderCheckBand`를 새로 만들고, `onStatus`·`onCollect`에서 다시 그립니다.
  - `#pl-tgt` 체크박스와 `visibleRows`에서 거르는 처리를 더합니다.
  - `/bid-targets` 캐시를 새로 만듭니다.

### 4. 권장: B안
- **목적과 맞습니다**: 요청은 "목표·관심 기관이 최신인지 한 번에 확인하고 수집 요청"하는 것입니다. 지금 목록은 정의부터 '입찰 임박'이라, 기간이 지났거나 날짜를 모르는 목표·관심 기관은 A·C안으로는 나오지 않습니다. B안만 대상 집합을 목표·관심 표 그대로 씁니다.
- **영업부서 일상 화면을 지킵니다**: 기본 보기는 지금 그대로라 영업부서에 새로 설명할 것이 없습니다. 세팅용 보기는 탭 하나로 따로 떼어 둡니다.
- **버튼과 대상이 같은 자리에 있습니다**: 걸러진 결과 바로 위 띠에 버튼이 있고, n이 화면 필터를 따라 바뀝니다. "무엇을 요청하는지 보이는 버튼"이라는 원칙에 맞고, C안처럼 숫자와 행이 어긋나지 않습니다.
- **목표·관심 둘 다, 각각 모두 됩니다**: [모두|목표|관심] 묶음은 지금의 `.db-per` 모양을 다시 쓰므로 새 부품이 없습니다.

- **요약줄**: "목표·관심 17곳 · 자료 없음 3곳 · 오래됨 2곳 · 자료 상태 순"

  - 요청 가능한 사람: "확인 필요 5곳 — 자료 없음 3 · 오래됨 2" + [5곳 수집 요청]

### 6. 규격: 일괄 요청 확인 상자 (세 안 공통)
- **모양**: 공통 팝업 `.dlg`(NEXT 0d 진행 중)를 씁니다.
  - 제목: "사업계획 5곳 수집 요청"
  - 본문 1줄: "개발부서에 아래 기관의 사업계획 수집을 요청합니다."
  - 목록: 기관명 + 이유 칩(자료 없음/오래됨). 최대 높이 240px에서 스크롤합니다.
  - 버튼: [5곳 요청](주 버튼, 틸) [취소]
- **포커스**: 열면 [취소]에 둡니다. 여러 곳을 한 번에 보내는 일이라 실수 방지를 위해서입니다. ESC로 닫고, 닫으면 띠 버튼으로 돌아갑니다.
- **보내는 중**: 버튼 글자를 "요청 중… 2/5"로 바꾸고 상자 안 버튼을 막습니다. 지금 `reqLineHtml`의 '요청 중…' 모양을 이어 씁니다.
- **한도**: 서버 한도가 정해지면, 한도를 넘을 때 "한 번에 50곳까지 요청할 수 있습니다. 앞 50곳만 요청합니다."를 본문에 더합니다. 숫자는 개발 결정을 기다립니다.

### 7. 이관 메모
- [이관: 개발] **일괄 수집 요청 방식**. 디자인은 확인 상자의 진행 표시(n/m)와 일부 실패 문구가 이 결정에 따라 정해집니다.
  - 지금 서버는 기관 한 곳씩만 받습니다(`POST /institutions/{id}/plan-collect`).
  - 정할 것: 한 곳씩 n번 보낼지 새 일괄 엔드포인트를 둘지, 한 번에 몇 곳까지(관리용 `MAX_KEYS`=50 참고), 일부 실패 응답의 모양.
- [이관: 개발] **plans.js가 `/bid-targets`를 받을 권한·캐시**. B안은 디자이너도 띠의 숫자를 봐야 합니다.
  - `dashboard.loadGoals`는 [제안 확정] 역할에만 받고 `watch_items`를 버립니다. kbboard의 캐시를 함께 쓸지, 따로 받을지 정해야 합니다.
  - 디자이너가 `/bid-targets`를 읽을 수 있는지는 98번 '디자이너 열람(2e7b366)'으로만 추정했습니다. 확인이 필요합니다.
- [이관: 기획] **'오래됨'의 기준과 '기간 지남'을 일괄 대상에 넣을지**. 띠의 n 정의가 이 결정에 따라 정해집니다.
  - 칩의 '오래됨'은 서버 `st.stale` 값을 그대로 보여 줄 뿐이고, 기준(몇 개월)은 화면에서 알 수 없습니다.
  - '기간 지남'(계획 기간 종료)도 최신이 아니라고 볼지 정해야 합니다.

### 8. 질문 후보 (planner → pm → 메인 경로로)
- '목표'에 내년 목표도 넣나요, 올해 목표만인가요?
  - 현황판은 연도별 목표(`target_year`)이고 관심은 연도가 없습니다.
  - 올해만 넣으면 '다음 회차 준비' 내년 목표 기관은 이 점검에서 빠집니다.
- 요청자는 누구로 기록되나요? 일괄 요청은 누른 사람 사번으로 n건이 생깁니다.
  - '처음 한 번 전체 세팅'을 하는 사람이 영업부서 계정이 아니라 개발부서·관리자 계정이라면, 요청자 표시('n명 요청')가 영업부서에 어떻게 보여도 괜찮은지 확인이 필요합니다.
- '결과 확인' 기관(마감 지남)인 목표·관심 기관도 점검 대상인가요?
  - B안은 기본으로 포함합니다. 입찰이 끝난 기관의 사업계획을 다시 받을 필요가 없다면 제외 규칙이 필요합니다.
- 세팅이 끝난 뒤 '목표·관심 기관' 보기를 영업부서에게도 보여 주나요, 세팅하는 사람만 보나요?
  - B안은 모두에게 보이는 탭으로 그렸습니다. 숨기려면 권한 기준이 필요합니다.

## 2. 한 줄 총평 + 가장 큰 기회
서버는 결재가 아닌 '의견 회차' 흐름을 잘 갖췄는데, 화면에는 `[제출]`과 `제출됨/승인완료` 태그뿐이라 그 흐름이 보이지 않는다.

**가장 큰 기회**: **'회차 카드' 하나를 세 곳에서 똑같이 쓰는 것**이다. 회차 카드 = 받는 사람별 응답 + 의견 목록 + 내 행동. 세 곳은 디자이너 작업함 안, 쪽지에서 연 검토 창, 결재함에서 연 검토 창이다. 그러면 디자이너·담당자·팀장·부장이 같은 화면을 보며 말하게 된다.

## 3. 점수표 / 잘 된 점
- **점수표는 매기지 않는다.** 화면이 아직 없어 근거 없는 점수가 된다.
- **잘 된 점**
  - 서버가 `viewer.can_*` 7개를 준다. 화면이 역할을 다시 판정하지 않고 단추를 보이고 숨기기만 하면 된다(PRODUCT 원칙과 맞음).
  - 오류가 전부 `{code,message}`이고 이름·사번이 실리지 않는다. 코드별 화면 문구를 붙이기 쉽다.
  - 상태 값(TASKS.STATUS)을 그대로 두고 `phase_cd`만 더해 기존 결재함·테스트를 깨지 않는다.

## 4. 우선순위 이슈 (화면을 붙일 때 고칠 것)

**P1-1. 디자이너 상태 태그가 세 부서 태그와 표를 함께 쓴다**
- 근거: `designer.js:66-71`의 `TAGS`를 `statusTag`가 쓰고, `handoffRows`(:89)도 같은 표로 세 부서 산출물 태그를 그린다.
- 왜: 디자이너 작업에 '의견 받는 중(n차본)'을 넣으면, 받은 산출물 카드의 영업·개발·재무 부서 '1차완료'도 함께 바뀐다.
- 수정: 디자이너 작업용 `designer.PHASES`(phase_cd 기준)를 따로 둔다. 기존 `TAGS`는 세 부서 산출물에만 쓴다.

**P1-2. 돌려보낸 뒤 이유가 화면에 남지 않는다**
- 근거: 최종 단계 돌려보내기는 회차가 이미 FORWARD로 닫혀 있다(설계 3-1). 사유는 쪽지에만 실린다(`DesignReviewService:609-611`). `GET design-review` 응답에는 사유가 없다.
- 왜: 디자이너는 '디자인 작업 중'으로 돌아온 이유를 쪽지함에서 따로 찾아야 한다. 영업팀장 반려(LEAD_RETURN)도 마찬가지다.
- 수정: 응답에 `last_return {by_role, reason, at}`를 더해 상태 띠 아래 '돌려받은 사유' 줄로 보인다(textContent). → 이관(개발)

**P1-3. 의견 요청 쪽지에서 검토 화면으로 갈 길이 없다**
- 근거: `notifications.create(..., taskId, null /*link*/ ...)`(:367, :446, :609). `notify.destination`은 `link`가 허용 목록(`notify.js:17-20`)에 있어야 이동 단추를 그린다.
- 왜: 받는 사람의 대부분은 영업·개발·재무 부서 담당자·팀장이고 디자이너 화면이 없다. 쪽지를 읽고도 의견을 남길 곳에 갈 수 없다.
- 수정: 서버가 `link:'design:review'`를 싣고, 화면은 `DESTINATIONS['design:review'] = {label:'디자인 검토'}` + `task_id`로 검토 창을 연다. → 이관(개발). 서버가 고치기 전 임시로는 `kind==='쪽지' && task_id`일 때만 단추를 둔다.

**P1-4. 보낸 사람이 비면 '시스템'으로 보인다(위조 차단과 반대)**
- 근거: `notify.js:34` `from: n.sender || '시스템'`.
- 왜: 서버는 시스템 쪽지에 sender '시스템'을 직접 박고, 빈 sender는 '보낸 사람 미상'이라는 규칙이다. 지금 화면은 빈 값을 시스템으로 보여 위조 차단 효과를 지운다.
- 수정: `n.sender || '보낸 사람 미상'`으로 바꾼다. `sender === '시스템'`이면 사람 이름 자리 대신 무채색 칩 `시스템`을 그린다(6-4).

**P2-1. 영업팀장 결재 카드의 [반려]와 의견 흐름이 겹친다**
- 근거: `approvals.js:300-305`는 모든 작업 카드에 의견 입력 + 승인 + 반려를 그린다.
- 왜: 사용자 결정(11-19)은 "의견 → 다시 수정 반복(결재 아님) → 영업팀장 검토 끝 → 부장". 팀장에게 [반려]가 있으면 돌려보내는 길이 두 개가 된다(의견 남기기 vs 반려).
- 수정: 디자이너 1단계 카드에는 [검토 화면 열기]와 [영업 검토 완료·부장께 올림]만 둔다. 반려 API는 남긴다. → 기획 확인(이관), 팀 기본값은 숨김.

**P2-2. 단계 동작이 브라우저 대화상자로 확인을 받는다**
- 근거: 지금 디자이너 제출이 `alert`/`confirm`(`designer.js:438,446`)을 쓴다.
- 왜: KRDS 원칙과 맞지 않는다. 오류 문구가 대화상자로 뜨고 사라져 다시 볼 수 없고, 화면 읽기 도구에서도 맥락이 끊긴다.
- 수정: 새 동작은 모두 단추 아래에 확인 줄(헤드카드의 `pendingHtml` 방식)을 펼치고, 결과는 `role="status"` 줄로 알린다.

**P2-3. 서버 오류 문구가 '팀' 이름을 쓴다**
- 근거: `TEAMS_NOT_DONE` = "아직 승인되지 않은 팀이 있습니다: 영업팀…"(:836). 받는 사람 사유는 `reason_cd`로 온다.
- 왜: 부서 이름 결정(11-17: 영업부서·개발부서·재무부서)과 어긋난다.
- 수정: 화면이 코드별 자체 문구를 쓰고 서버 message는 쓰지 않는다(5절 표). 부서 목록은 서버가 `teams:[...]` 배열로 주면 화면이 부서 이름으로 바꾼다. 없으면 부서 목록 없이 문장만 보인다. → 이관(개발)

**P3-1. 디자이너 화면의 이모지·포인트색이 DESIGN.md 계약과 어긋난다(이번 화면 손볼 때 같이)**

### 5-7. 접근성 요건(구현 확인 항목)
- **security M6 — 의견 본문·이름·사유는 모두 `textContent`로 넣는다.** 회차 카드는 문자열 HTML이 아니라 `createElement` 조립 함수로 만든다. `innerHTML`은 고정 틀(빈 컨테이너)에만 쓴다.
- **본문**: `white-space:pre-wrap; overflow-wrap:anywhere`. 긴 URL이 가로로 넘치지 않게 한다.
- **검토 창(모달)**
  - `role="dialog" aria-modal="true" aria-labelledby="dr-title"`
  - 열면 제목으로 포커스, Tab 가둠(`headcard.js:903`과 같은 방식), Esc로 닫고, 연 단추로 포커스를 되돌린다.
  - 쪽지 창에서 열 때는 쪽지 창을 먼저 닫는다(모달을 겹치지 않는다). 포커스는 머리 띠의 쪽지 단추로 돌린다.
- **비활성 단추에는 사유를 보이는 글로 둔다**(`aria-describedby`). `title`만 쓰지 않는다. 예: can_forward=false이고 본인 담당이면 "본인이 담당한 건이라 영업부장이 검토합니다."
- **의견 입력칸**
  - 보이는 label "{n}차본에 남길 의견"
  - 글자 수 `0/1000`(모노, `aria-live="polite"`는 900자부터만)
  - 도움말 "개인정보(주민등록번호·전화번호)는 적지 마세요. 들어 있으면 저장되지 않습니다."
- **크기**: 단추 높이 32px 이상(작업 영역 단추 12px 글자 + 위아래 7px). 좁은 화면(880px 이하)에서 행동 단추는 44px.
- **결과 줄**: `role="status"`. 오류는 `role="alert"`이고 단추 바로 아래에 둔다.

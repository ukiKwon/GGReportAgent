## 2. 한 줄 총평
기록 칸 자체는 기존 부품(`.db-dl`·`.db-per` 분절·`.ov-stamp` 3단 모양)으로 거의 다 만들 수 있다. 위험은 두 곳이다. 하나는 **'공고 진행 중'이라는 같은 말이 자동 판정과 담당자 판정 양쪽에 쓰인다**는 점이다. 다른 하나는 **기록 칸이 긴 상세의 맨 아래**에 있어 경과 탭의 주된 일과 멀다는 점이다.

가장 큰 기회: 경과 탭의 기간 버튼 자리(경과 탭에서는 이미 숨겨짐)를 **상태 보기 [미처리|지연·재공고 대기|처리됨]**로 바꾸는 것이다. 지도 패널, 팝업, 배지가 같은 '미처리' 셈을 쓰게 된다.

## 3. 점수표 / 잘 된 점
- **채점은 생략한다.** 새 기능 규격이고 렌더 화면을 보지 않았으므로 점수의 근거가 없다.
- **잘 된 점 1:** Overdue Stamp Rule에 3단 모양이 이미 정의돼 있다. 시안 `2026-11-09_경과패널_시안.html:57-64`의 `.ov-stamp`(잉크) / `.is-line`(테두리) / `.is-plain`(흐림)이다. 새 색 없이 상태를 모양으로 나눌 수 있다.
- **잘 된 점 2:** 경과 탭은 기간 fieldset을 이미 `hidden`으로 숨긴다(`dashboard.js:818`). 상태 보기를 넣을 자리가 비어 있다.
- **잘 된 점 3:** 팝업 요약 문구 "예정일이 지났는데 공고 진행 여부가 아직 기록되지 않은 건입니다"(`overdue.js:115`)가 2단계의 뜻과 이미 맞는다. 바꿀 필요가 없다.

## 4. 우선순위 이슈

**P1-1 '공고 진행 중'이 두 가지 뜻으로 쓰인다.**
- 근거:
  - 목록 묶음 제목: `noticeGroupLabel` → "공고 진행 중 n곳"(`dashboard.js:385`). 공고 자료로 자동 판정한 것이다.
  - 새 담당자 판정 3종에도 같은 '공고 진행 중'이 들어간다.
- 왜 문제인가: 경과 행에 "공고 진행 중"이 보이면, 공고 자료가 들어온 것인지 영업 담당자가 그렇게 적은 것인지 알 수 없다. 판정 이름은 사용자가 정했으므로 바꾸지 않는다.
- 수정: 화면에서 **출처를 앞에 붙인다.**
  - 기록 칸 요약: `공고 자료` / `담당자 기록` 두 줄로 나눈다.
  - 목록 행: 판정은 `기록: 공고 진행 중`처럼 '기록:'을 붙인다.
  - 자동 판정은 지금처럼 칩(마감 D-n·공고 후 n일·D+n)으로만 보인다.

**P1-2 기록 칸이 상세 맨 아래에 있다.**
- 근거: `paneHtml` 순서는 head → 공고 진행/약정 주기 → 기관 정보 → 현재 금고 → 기관장 → 사업계획 → **기록**(`dashboard.js:721`).
- 왜 문제인가: 1280×800에서 상세 칸 높이는 약 560px이다. 기관장·사업계획 카드를 지나야 기록 칸이 나온다. 경과 탭에서 영업팀이 하는 일은 하나, 기록뿐이다.
- 수정: 순서를 head → 공고 진행/약정 주기 → 기관 정보 → **공고 상태 기록** → 현재 금고 → 기관장 → 사업계획으로 바꾼다. 기록이 공고 사실 바로 뒤에 붙고, 첫 화면에서 기록 칸 머리가 보인다(약 450px 지점). 내 11-16 규격(6-C, 맨 아래)을 이 이유로 고친다.

**P1-3 '미처리'를 어디서 세느냐가 갈라질 수 있다.**
- 근거:
  - 배지와 팝업은 `ov.count()` = `overdueSummary(activeRegions 안)`(`overdue.js:156-159`)로 센다.
  - 경과 탭 숫자는 `M.overdue`를 필터한 것이다(`dashboard.js:829`).
  - 2단계에서 미처리에서 빠지는 기준(기록 여부)이 새로 생긴다.
- 왜 문제인가: 배지 9, 탭 11, 팝업 7처럼 서로 다르면 기록을 마쳤는지 믿을 수 없다.
- 수정: '미처리' 판정을 함수 **하나**에 둔다(7절 이관: 개발). 화면 규칙은 이렇다. 미처리 = 이번 회차 기록 없음 **또는** 지연·재공고 대기인데 다음 확인일 ≤ 오늘. 네 곳(배지·팝업·지도 패널·경과 탭)이 같은 값을 보인다.

**P2-1 배지가 엉뚱한 메뉴에 붙어 있다.**
- 근거: `overdue.js:200`.
- 수정: 배지를 `nav.NOTICE_ID`('입찰 공고 현황') 항목으로 옮긴다. sr 문장은 그대로 `공고 예정일 경과 미처리 n건`이다.

**P2-2 저장하지 않은 입력이 사라진다.**
- 근거: 행을 고르면 `select` → `renderPane()`이 상세 칸을 통째로 다시 그린다(`dashboard.js:912-914`).
- 수정:
  - 회차 키별로 입력 초안을 화면 상태(`st.drafts[key]`)에 둔다. 다시 고르면 되살린다.
  - 저장 버튼 옆에 `저장하지 않은 내용이 있습니다.`(12px muted)를 띄운다.
  - 확인 창(confirm)은 쓰지 않는다.

**P2-3 지도·현황판 팝업에서 기록을 쓰지 못하는 이유가 안 보인다.**
- 수정:
  - 두 팝업에는 **읽기 요약 한 줄**만 넣는다. `담당자 기록: 지연·재공고 대기 · 홍길동 2026-11-14` + [입찰 공고 현황에서 기록]
  - 쓰는 곳을 공고 현황 하나로 두면 감사 기록의 '화면'이 `bid_notice` 하나로 유지된다.

**P3-1 세는 말을 섞지 않는다.** 목록 숫자는 기관 단위 '곳', 팝업·배지는 '건'이다. 지금 쓰임을 그대로 둔다. '회차'라는 말은 기록 칸 안에서만 쓴다.

### 접근성
- **판정:** `<fieldset><legend>담당자 판정</legend>` 안에 진짜 `<input type="radio" name="rec-state">` 3개를 둔다. 방향키 이동은 브라우저 기본이다. 모양은 `.db-per` 분절과 같고, 라벨 높이는 32px 이상이다. 설명 1줄은 `aria-describedby="rec-state-help"`로 연결하고 `aria-live="polite"`이다.
- **필수 표시:** 글자 `(필수)` + `aria-required="true"`. 별표만으로 표시하지 않는다.
- **오류:** 필드 아래 `<p id="rec-…-err">`를 둔다. 필드에는 `aria-invalid="true"`와 `aria-describedby="…-help …-err"`. 글자는 `--red` 12px에 경고 삼각형 ICON을 붙인다(빨강 테두리만으로 알리지 않는다). 저장을 누르면 **첫 오류 필드로 포커스**한다. 서버 오류 줄은 `role="alert" tabindex="-1"`이고 포커스를 받는다.
- **저장 뒤 포커스:** 상세를 다시 그려도 `#db-rec-save`로 포커스를 되돌린다. 완료 문구는 `#db-flash`(role=status)에 띄운다.
- **이력:** `<details>`/`<summary>`. 목록은 `<ol>`이고 최신이 먼저다.
- **목록 행 상태:** 판정을 글자(`기록: …`)로 meta 줄에 넣는다. 그러면 listbox option의 접근 이름에도 상태가 들어간다. 도장 모양만으로 상태를 전하지 않는다.
- **대비(계산값, 새 색 0개):**
  - `--fg` on panel 약 13:1
  - `--muted` #98a1af on panel #181e29 6.4:1
  - `--red` 글자 on panel 5.6:1, 입력 우물 #0d1117 위 빨강 테두리 약 6.3:1
  - 흐림 도장 `.is-plain` muted 6.4:1, 테두리 도장 `.is-line`의 muted 테두리 6.4:1 (3:1 기준 충족)
- **opacity 금지:** 흐린 상태는 `--muted` 색으로만 낮춘다(DESIGN).

### 6-A 상세의 기록 칸 (`dash.recordSecHtml(it, rec, ctx)`로 확장)
- **위치:** `paneHtml`에서 `info` 바로 뒤로 옮긴다(P1-2). 넘기는 곳은 지금처럼 공고 현황만이고, 개원 확인 필요 기관에는 넣지 않는다(`dashboard.js:898`).
- **1280 치수:** 본문 약 992 − 목록 380 − 간격 20 = 상세 칸 약 592px. 안쪽은 padding 24×2를 빼면 약 544px이다. 요약 dl은 `.db-dl`(110px | 1fr)을 그대로 쓴다. 입력 칸도 같은 110px 라벨 열에 맞춘다.
- **입력 크기:**
  - 판정 분절: 13px 기준 약 330px. 422px 열 안에 들어간다.
  - date 입력: 160px.
  - textarea: 폭 100%, 3줄(min-height 64px), `resize:vertical`.
  - 버튼 줄: `[기록 저장](.db-next 틸 테두리, 채움 없음) [되돌리기]`. 오른쪽에 저장 안 됨 표시.
- **높이:** 영업팀 입력 상태가 약 360px, 읽기 상태가 약 150px이다.
- **≤880px:** `.db-dl`과 입력 그리드를 한 열로 쌓는다(라벨 위, 칸 아래).

| 상태 | 모양 |
|---|---|
| 서버 미연결 | 절 제목 + `.db-empty` 한 줄 |

### 6-B 회차 이력 펼침
- `<details class="db-rec-hist">`는 기본 접힘이다. 펼치면 두 묶음이 나온다.
  1. **공고 차수.** 재공고가 있을 때만 보인다. `1차 공고 2026-09-01 · 유찰` / `2차 공고 2026-10-20 · 접수 10-21~10-30`. 유찰은 읽기 전용이고 출처는 입찰 결과 등록이다. 그 화면이 준비중인 동안에는 줄을 두지 않는다.
  2. **판정 변경.** 최신이 먼저다. 한 건 = 1줄 `날짜시각(mono) 이름` + 2줄 `이전 → 이후`(이후만 `--fg` 700) + 바뀐 경우에만 의견·다음 확인일 줄.
  - 2차 공고가 있으면 각 기록 앞에 `.hb-slot` 칩 `1차`/`2차`를 붙인다.
- 화면과 버튼 이름은 감사 기록에만 남기고 화면에는 보이지 않는다.

## 7. 이관 메모
- **[이관: 기획]**
  - '미처리'의 정확한 정의 — 디자인은 "회차 기록 없음 또는 지연인데 다음 확인일 ≤ 오늘"로 그렸고, 지시문·planner aeec666f와 맞는지 확인을 기다린다. 근거는 `overdue.js:7` "모든 경과 건이 미처리".
  - 처리됨(진행 중·종료) 회차를 경과 탭에 계속 둘지, 다음 회차 예정일이 생기면 빠질지 — 처리됨 보기가 끝없이 늘어날 수 있다.
  - 예정일 전 회차(다가오는 입찰 탭)에도 판정을 허용할지 — 디자인은 개원 확인 필요를 뺀 모든 상세에 칸을 두었다.
  - 자동 '접수 중'인데 담당자가 '공고 종료'로 적는 것처럼 둘이 어긋날 때를 허용할지, 경고할지 — 디자인은 둘 다 그대로 보이게만 했다.
  - 다음 확인일에 오늘을 허용할지 — 디자인은 내일부터로 했다.
  - 제안 진행 중인 회차를 '공고 종료'로 바꿀 때 확인 창이 필요한지 — NEXT 30에 남은 질문이다.
- **[이관: 개발]**
  - 회차 식별자와 저장 칸: 판정·의견·다음 확인일·기록자·시각, 이전 값 감사(`bid_notice` 화면, '기록 저장' 버튼).
  - 동시 저장 충돌(409) 처리 여부. 문구는 5절에 있다.
  - 의견 글자 수 상한(시안은 500자).
  - '미처리'를 세는 함수 하나를 배지(`ov.count`)·팝업·패널·경과 탭이 같이 쓰게 하기(P1-3).
  - 배지 위치를 `NOTICE_ID`로 옮기기(P2-1).
  - 마이그레이션 번호 확인(NEXT 30: 036까지 씀).
- **[이관: 데이터]**
  - 1차·2차 공고 이력의 출처 — 지금 기관 레코드에는 공고가 하나뿐이다. 근거 없는 '1차' 표시를 만들지 않도록, 재공고 자료가 들어오기 전에는 차수 칩을 두지 않는다.

# 디자인 검토: '입찰 현황판'과 '입찰 공고 현황'의 메뉴 위치와 서로 오가는 링크

## 1. 대상·방법·못 본 것
- **본 방법**: 소스만 읽었습니다. `nav.js`, `dashboard.js`, `overdue.js`, `index.html`의 팝업 마크업, `DESIGN.md`, `PRODUCT.md`, `NEXT.md` 30번(11-09 사용자 답)입니다.
- **화면은 못 봤습니다**: Playwright 브라우저를 다른 세션이 쓰고 있어서("Browser is already in use") 열지 못했습니다. 그래서 1280폭에서 공고 띠 머리줄에 링크 하나를 더했을 때 줄이 넘치는지 측정하지 못했습니다.
- **impeccable 컨텍스트 런처**는 Bash가 없어 실행하지 못했습니다. 대신 PRODUCT.md와 DESIGN.md를 직접 읽었습니다.

## 2. 한 줄 총평
두 메뉴를 다른 중분류에 둔 것은 맞습니다. 중분류가 '기관'과 '입찰 공고'로, 무엇 하나를 단위로 보는지에 따라 나뉘기 때문입니다. 헷갈리는 원인은 위치가 아니라 **이름**입니다.
- 중분류 소제목은 영업 계열이 아닌 사람에게는 보이지 않습니다(`nav.js:18` 규칙: 보이는 중분류가 2개 이상이고 각각 항목이 2개 이상일 때만 표시). 그래서 소제목만으로는 구분되지 않고, 항목 이름 자체가 서로 달라야 합니다.
- **가장 큰 기회**: 아직 만들지 않은 '입찰 공고 현황'의 이름을 지금 바꾸는 것입니다. 이미 쓰고 있는 화면이 아니라서 바꾸는 비용이 거의 없습니다.

**점수표는 생략합니다.** 화면이 없고 렌더링도 보지 못해, 근거 있는 점수를 매길 수 없습니다.

**잘 된 점**
- 중분류의 기준이 무엇을 단위로 보느냐(기관 / 공고)로 맞춰져 있어, 두 화면을 나눈 사용자 결정과 그대로 맞습니다.
- 공고 띠의 카드가 `<button aria-pressed>`이고 목록 행이 `role=option`으로, 역할이 깔끔합니다. 링크를 넣을 자리도 이 구조가 정해 줍니다(아래 P2-3).
- 경과 상태를 보이는 규칙(미처리는 잉크 칩, 지연은 테두리 칩, 처리됨은 흐린 글자)이 DESIGN.md "Overdue Stamp Rule"에 이미 있습니다. 2단계에서 현황판 목록에 상태를 보일 때 새 모양이 필요 없습니다.

## 4. 우선순위 이슈

**P1-1. 두 이름이 비슷하고, 소제목이 안 보이는 사람에게는 구분할 단서가 없음**
- **근거**: `nav.js:61`은 '입찰 현황판', `nav.js:64`는 '입찰 공고 현황'입니다. 둘 다 '입찰'로 시작하고 둘 다 '현황'이 들어갑니다.
  - 영업팀에게는 '기관 / 입찰 공고' 소제목이 보입니다.
  - 그런데 공고 현황이 실화면이 되어 다른 팀(전산·재무)에게도 열리면, 그 사람들에게 '입찰 공고' 중분류는 1항목입니다. 그러면 showSubs 조건에 걸려 전체가 평평한 목록이 됩니다. 결과는 「입찰 현황판 / 전국 지도 / 전국 지역별 / 입찰 공고 현황」처럼 소제목 없이 나란히 놓입니다.
- **왜 문제인가**: 사용자가 비슷한 이름 둘 중 어디서 기록하는지 매번 생각해야 합니다. 11-09 결정(영업팀이 처리하면 타팀에도 공유)대로라면 이 평평한 목록이 실제로 생깁니다.
- **수정 방향**: 이름에 단위(공고 1건)와 동작(처리)을 넣고 '현황'을 뺍니다.
  - 1순위 **'공고 건별 관리'**. 사용자가 정의한 "공고 1건 단위"를 그대로 옮긴 말이고, 제품 안에서 이미 쓰는 단위 말('미처리 건', '준비 건')과 같습니다.
  - 2순위 '공고 처리 기록'.
  - '입찰 현황판'은 영업팀의 첫 화면으로 이미 자리 잡은 이름이라 그대로 둡니다.
  - 위치는 지금처럼 '입찰 공고' 중분류의 맨 앞에 둡니다.

**P1-2. 로그인 경과 팝업의 버튼이 영업팀을 첫 화면(현황판)에서 지도로 끌고 감**
- **근거**:
  - `nav.js:100`(`expectsDashHome`)은 영업팀·팀장·부장의 경우 현황판이 열릴 때까지 팝업을 미룹니다. 그래서 팝업은 현황판 위에 뜹니다.
  - 그런데 `index.html:2244`의 [경과 패널에서 전체 보기]는 `overdue.js:385`에서 `openPanel`을 부르고, 이것이 `goMap()`(`:272`)으로 지도 탭으로 옮깁니다.
- **왜 문제인가**: 사용자가 내려앉은 첫 화면을 버리고 다른 화면으로 순간이동합니다. 현황판에도 같은 경과 목록이 이미 있습니다(`dashboard.js:795`, `showPast()` `:1087`).
- **수정 방향**: 4번 질문 답에서 다룹니다.

**P2-1. 경과 건이 보이는 곳이 이미 5곳이고, 처리할 기준 화면이 없음**
- **근거**: 지금 보이는 곳은 지도의 경과 패널(`index.html:1972`), 현황판의 D+ 칸(`dashboard.js:515`), 현황판의 경과 묶음(`:795`), 로그인 팝업, 사이드바 배지입니다.
- 여기에 11-09 사용자 답 ②로 "공고 현황 화면에 경과 강조 패널"이 더해질 예정입니다.
- **수정 방향**: 2단계에서 상태를 저장하게 되면 **처리는 공고 건별 관리 한 곳**에서만 합니다. 나머지는 개수와 바로가기만 남깁니다(3번 질문 답).

**P2-2. 추정으로 날짜가 지난 기관은 '실제 난 공고'가 아님**
- **근거**: `dashboard.js:332`. 추정 날짜가 지난 경우 문구가 "공고가 났는지 확인이 필요합니다"이고, 확정 공고는 "공고 후 n일 · 결과 미확인"입니다.
- **왜 문제인가**: 사용자 정의상 공고 현황은 실제 공고 1건 단위인데, 추정으로 경과한 기관은 공고 레코드가 없습니다. 이 건을 어디서 처리하는지 정해지지 않으면 링크 목적지가 갈립니다.
- 이관 메모 기획 1로 넘깁니다.

**P2-3. 링크를 띠 카드나 목록 행 안에 넣을 수 없음**
- **근거**: `dashboard.js:389`의 카드는 `<button>`이고, `:472·:483`의 행은 `role=option`입니다.
- **왜 문제인가**: 버튼이나 option 안에 링크를 넣으면 접근성 트리가 깨지고, 키보드로 갈 곳이 두 겹이 됩니다.
- **수정 방향**: 링크는 **띠 머리줄, 경과 묶음을 펼친 아래 안내줄, 상세의 '공고 진행' 칸** 세 곳에만 둡니다(6절 규격).

**P3-1. 경과 묶음의 기본 상태가 주석과 다름**
- `dashboard.js:787` 주석은 "경과(접힘)"인데, `:699`는 `pastOpen: true`(펼침)입니다. 어느 쪽이 의도인지 확인이 필요합니다. 3번 질문 답에서는 접힘을 권합니다.

**P3-2. 팝업 제목과 1단계 기능이 어긋남**
- 팝업 제목은 "공고 예정일이 지난 미처리 건"인데(`index.html:2237`), 1단계에는 처리할 수단이 없습니다.
- 2단계 전까지는 버튼 문구로 '처리'를 약속하지 않습니다(아래 문구 목록).

## 질문별 답

**1. 메뉴 위치**
- 지금처럼 다른 중분류에 두는 것이 맞습니다.
- 현황판 중분류로 옮기면 '기관' 중분류 안에 공고 단위 화면이 섞입니다. 그러면 중분류 기준이 무너지고, "한 화면은 한 항목"(`nav.js:15`)의 위치 감각도 흐려집니다.
- 헷갈림은 배치가 아니라 이름(P1-1)으로 풉니다.
- 중분류 순서는 '기관' 다음 '입찰 공고'를 유지합니다. 예측에서 실제 공고로 가는 업무 순서와 맞습니다.

**2. 링크 지점과 문구**

| 지점 | 자리 | 문구 | 조건 |
|---|---|---|---|
| 공고 띠 | 머리줄 끝(지금의 `#db-nb-wait` 자리) | **공고 건별 관리에서 전체 보기** | 공고 건별 관리가 실화면이고, 그 사람에게 메뉴가 보일 때만 |
| 경과 묶음 | 펼친 목록 위 안내 한 줄 | "처리 상태는 공고 건별 관리에서 기록합니다." + **공고 건별 관리에서 처리** | 2단계(상태 저장) 이후에만 |
| 상세 '공고 진행' 칸 | `dl`에 '처리 상태' 줄 추가 | 기록 없음 → **공고 건별 관리에서 기록** / 기록 있음 → 상태와 처리자 + **기록 보기** / 조회만 가능 → **기록 보기** | 진행 중인 공고와, 확정 공고로 경과한 건 |
| 공고 건별 관리 → 현황판 | 공고 행의 기관명 옆 | **현황판에서 이 기관 보기** | 현황판 메뉴(서버 map 키)가 보일 때 |

- 개별 공고 카드에는 링크를 달지 않습니다. 카드를 누르면 지금처럼 기관이 선택되고, 상세 칸의 링크로 넘어갑니다.
- 문구에 '→'를 붙이지 않습니다. 이미 있는 [경과 패널에서 전체 보기]와 같은 '목적지 + 동작' 형식입니다.

**3. 띠와 경과 묶음을 둘 것인가, 줄일 것인가**

**공고 띠는 그대로 둡니다.** 영업팀의 첫 화면에서 '마감 D-n'은 가장 급한 신호입니다(PRODUCT 원칙 3). 줄이면 공고 건별 관리를 따로 열어야만 마감을 보게 됩니다. 바꾸는 것은 머리줄의 링크 하나뿐입니다.
- 단, '결과 확인' 건(마감 지남)은 바로 공고 건별 관리가 할 일(공고 종료 기록)입니다.
- 그래서 공고 건별 관리가 실화면이 되면 `#db-nb-wait`(같은 화면 안으로 이동)을 위 링크로 **교체**합니다. 머리줄 끝의 버튼은 1개로 유지합니다.

**경과 묶음은 목록으로 남기되, 2단계 이후에는 접힘을 기본**으로 합니다. 경과 기관도 고르면 상세와 [제안 확정]을 봐야 하므로 목록에서 빼지는 않습니다.
- 토글 문구는 "공고 예정일 경과 **미처리 n**곳 · 전체 m곳"으로 바꾸는 것을 제안합니다. 무엇을 셀지는 기획이 정합니다.
- 행의 둘째 줄에 상태를 보이고, 칩은 Overdue Stamp Rule대로 씁니다.
- 현황판에서 상태를 편집하는 기능은 넣지 않습니다.

**4. 경과 팝업의 목적지**
- **지금(1단계)**: 목적지를 **"지금 있는 화면"**으로 둡니다.
  - 현황판 위에 뜬 경우(영업팀·팀장·부장): 버튼은 **[현황판에서 경과 건 보기]**입니다. 팝업을 닫고, 경과 묶음을 펼치고, 그 목록에 포커스를 줍니다. 이미 있는 `showPast()` 동작을 그대로 씁니다.
  - 지도 위에 뜬 경우(디자이너·마스터): 지금의 [경과 패널에서 전체 보기]를 유지합니다.
- **2단계 이후**: 모든 사람의 목적지를 **[공고 건별 관리에서 처리]** 하나로 모읍니다. 제목의 "미처리 건"과 버튼의 동작이 그때 맞아떨어집니다.
- 지도 경과 패널의 '관심 지역' 묶음은 현황판 경과 묶음에 없습니다. 이 기능 손실을 받아들일지는 열린 질문 1번입니다.

## 5. 문구 / 접근성

**문구**
- '입찰 공고 현황' → '공고 건별 관리'(P1-1).
- 동작 이름을 끝까지 같게 씁니다. 링크의 '기록'과, 공고 건별 관리 화면의 저장 버튼·완료 알림 문구를 '기록'으로 맞춥니다. '저장'과 '기록'을 섞지 않습니다.
- 1단계 팝업 버튼에는 '처리'라는 말을 쓰지 않습니다(P3-2).
- 외부로 나가는 링크(`공고 원문 열기 (인터넷 PC에서 열림)`, `dashboard.js:460`)와 안에서 화면을 옮기는 링크를 **다른 줄**에 둡니다. 같은 줄에 있으면 어느 쪽이 브라우저 새 창인지 헷갈립니다.

**접근성**
- 화면 안 이동은 `<a href="#">`가 아니라 `<button type="button" class="link-btn">`으로 만듭니다(팝업의 `#ov-pop-skip`과 같은 방식).
- 누를 수 있는 높이는 **최소 24px**(WCAG 2.2 AA 2.5.8)로 합니다. 12px 글자라면 `padding:4px 2px` 이상입니다.
- 이동한 뒤의 포커스:
  - 공고 건별 관리로 가면 → 해당 공고 행 또는 화면 제목(`tabindex=-1`).
  - 현황판으로 돌아오면 → 기관을 선택한 뒤 `#db-name`(이미 `tabindex=-1`, `dashboard.js:646`).
- 상세 칸 링크는 기관명과 연결합니다. `aria-describedby="db-name"`을 달아 화면낭독기에서 "송파구 … 공고 건별 관리에서 기록"처럼 읽히게 합니다.
- 링크는 틸 글자색만 쓰고 채움은 쓰지 않습니다(One Teal Rule. 채운 주버튼 예외 3곳에 더하지 않습니다).

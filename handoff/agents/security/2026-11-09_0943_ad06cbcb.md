## 결론
- **①은 막혔다.** 이메일 정규식이 이제 입력 길이에 비례해서만 느려진다. 칸 길이 32,767자 거부, 같은 문자열 메모, 검사 총량 2천만 자 상한도 들어갔다. 다만 같은 긴 문자열을 반복해서 읽고 비교하는 비용은 아직 칸 수만큼 든다(유한하지만 수십 초 규모로 추정, 중).
- **②는 일부만 막혔다.** 표준 경로에 있는 시트에서는 칸·행 수를 파싱 전에 센다. 그런데 계수 대상을 **파일 경로 이름**으로 고른다. POI는 경로가 아니라 관계(rels)로 시트를 찾기 때문에 경로만 바꾸면 계수를 통째로 건너뛸 수 있다고 추정한다(중, 시험 필요). 공유문자열 개수, 병합, 스타일, 메모 같은 다른 XML 요소의 개수도 파싱 전에 세지 않는다.
- **새로 찾은 것:** 표시 서식 문자열을 칸마다 처음부터 다시 훑는다(`sections()`). 서식 길이 상한이 없어 CPU를 오래 붙잡을 수 있다(중, 실현 가능성은 추정).
- **StAX 설정은 대체로 안전하다.** DTD와 외부 엔티티를 끄고, JDK 기본 엔티티 확장 한도도 있다. 다만 DOCTYPE을 명시적으로 거부하지 않고, 그것을 확인하는 시험도 없다(하).

## 3. 권장 조치 순서
1. **N1+N2(한 번에 처리):** ZipGuard 계수를 경로가 아닌 내용으로 고른다. 내용이 `<`(BOM 허용)로 시작하는 엔트리는 모두 StAX로 훑는다. 칸·행·문자열 길이 계수는 요소의 로컬 이름으로 그대로 하고, 여기에 **모든 XML 파트의 시작 요소 총수 상한**(예: 200만, 설정 키 신설)을 더한다. 경로 우회, 공유문자열·병합·스타일·메모 개수를 함께 막는다. 회귀 시험: 시트를 비표준 경로로 옮긴 xlsx가 TOO_MANY_CELLS로 거부되는지 본다.
2. **N3:** `sections`/`hiddenNumber`의 결과를 서식 문자열별로 메모한다(XlsxBook 인스턴스 Map). 그리고 formatCode 길이 상한을 둔다(예: 255자 초과는 숨김 아님으로 판정하거나 BROKEN).
3. **N4:** 메모 적중까지 포함한 "방문 글자 수" 총량 상한(예: 5천만)을 두거나, 공유문자열 색인 기준으로 메모한다.
4. **N6:** `ev == XMLStreamConstants.DTD`이면 BROKEN으로 거부하는 한 줄을 넣고, DOCTYPE과 엔티티 시험을 추가한다.
5. N5·N7·N8·N9는 1번 작업과 같이 처리하거나 보류해도 된다.

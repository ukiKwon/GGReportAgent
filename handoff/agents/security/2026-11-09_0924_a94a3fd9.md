# 보안 점검: NEXT 48번 ①(개인정보 정규식 ReDoS)과 ②(XSSF 칸 수 사전 계수)

## 결론
- ①은 실제로 문제가 있다. 개인정보 정규식 중 이메일 패턴 하나가 입력 길이의 제곱에 비례해 느려진다. 업로드 경로에는 칸 길이 상한, 검사할 총 글자 수 상한, 시간 제한이 모두 없다. 엑셀 한 건으로 처리 자리 2개 중 하나를 사실상 무기한 붙잡아 둘 수 있다. 심각도 상.
- ②도 문제가 있다. 칸 수 상한(200,000)은 POI가 통합문서 전체를 메모리에 올린 **뒤에** 센다. 파싱 전에 막는 것은 파일 크기와 압축 해제 크기뿐이다. 메모리를 크게 쓰게 만드는 시트를 넣을 수 있다. 심각도 중(서버 메모리 상한이 작으면 상).

## 3. 패치 후보
아래는 적용할 수 있는 형태의 초안이다. 최종 구현은 backend-dev가 한다.

**① ReDoS. 세 겹 모두 권장. (a)만으로는 1-b의 공유 문자열 반복 검사를 막지 못한다.**

(a) `Pii.java:26-27`: 시작 위치를 로컬 부분이 시작되는 곳으로 제한하고, 둘째 반복을 되돌아오지 않게(possessive) 바꾼다. 전체가 선형이 된다.
```java
private static final Pattern EMAIL = Pattern.compile(
        "(?<![A-Za-z0-9._%+-])([A-Za-z0-9._%+-])([A-Za-z0-9._%+-]*+)@([A-Za-z0-9.-]+\\.[A-Za-z]{2,})");
```
- 둘째 반복의 문자 집합에 `@`가 없으므로 되돌아오지 않게 해도 결과는 같다.
- 의미가 달라지는 곳은 한 군데다. 이메일 바로 뒤에 구분자 없이 이어 붙은 둘째 이메일(예: `a@b.com.x@y.com`의 `.x@y.com`)은 따로 잡지 않는다. 칸 단위 판정(Set)에는 영향이 없고, draft의 종류별 건수만 1 줄 수 있다.
- PiiTest에 시험 2개를 추가한다. 회귀 시험: `"a".repeat(100_000)`이 1초 안에 끝나야 한다. 같은 의미인지 보는 시험: 기존 케이스가 그대로 통과해야 한다.

(b) `XlsxBook.kinds`를 인스턴스 메서드로 바꾸고 값별 메모(memo)와 총량 상한을 둔다.
```java
public static final int MAX_CELL_CHARS = 32767;            // 엑셀 자체 칸 한계
static final long MAX_SCAN_CHARS = 20_000_000L;            // 업로드 1건의 PII 검사 총 글자 수
private final Map<String, Set<String>> piiMemo = new HashMap<>();
private long scanned;
// kinds(a,b) 안에서: 길이 > MAX_CELL_CHARS → throw new Rejected(422, "CELL_TOO_LONG", null)
// piiMemo.get(s) 있으면 재사용, 없으면 scanned += s.length(); scanned > MAX_SCAN_CHARS → Rejected(422, "TOO_MANY_CELLS", null)
```
- `scanPii()`에 `throws Rejected`를 붙이고, `BoardWriteService.process:127`에서 받아 `fail(r.status, r.code, message(r.code))`로 바꾼다.
- `message()`에 `CELL_TOO_LONG` 문구를 추가한다.
- 잘라서 검사하지 않고 거부하는 이유: 자르면 개인정보를 놓칠 수 있다.

(c) 선택 사항. 시간 제한용 CharSequence 래퍼(`charAt`에서 마감 시각을 넘으면 예외)로 `Pii.scan`을 감싼다. (a)와 (b)가 들어가면 없어도 된다.

**② 파싱 전 계수. `ZipGuard` 확장**

ZipGuard가 이미 항목을 하나씩 풀어 읽고 있으므로 같은 자리에서 StAX로 센다.
- 대상 항목: `xl/worksheets/*.xml`, `xl/sharedstrings.xml`
- 셀 때 DTD와 외부 엔티티는 끈다.
```java
// check(...) 엔트리 루프 안: 시트/공유문자열 XML이면 바이트를 세는 FilterInputStream(close 무시)으로 감싸 아래를 돌린 뒤 남은 바이트 소진
XMLInputFactory f = XMLInputFactory.newInstance();
f.setProperty(XMLInputFactory.SUPPORT_DTD, false);
f.setProperty(XMLInputFactory.IS_SUPPORTING_EXTERNAL_ENTITIES, false);
XMLStreamReader r = f.createXMLStreamReader(countingIn);
while (r.hasNext()) {
    int ev = r.next();
    if (ev == START_ELEMENT) {
        String ln = r.getLocalName();
        if (sheet && "c".equals(ln) && ++cells > maxCells) throw new Rejected("TOO_MANY_CELLS");
        if (sheet && "row".equals(ln) && ++rows > maxRows) throw new Rejected("TOO_MANY_CELLS");
        if ("si".equals(ln) || "is".equals(ln)) textLen = 0;          // 공유/인라인 문자열 1개 단위
    } else if ((ev == CHARACTERS || ev == CDATA) && inStringItem) {
        if ((textLen += r.getTextLength()) > maxCellChars) throw new Rejected("CELL_TOO_LONG");
    }
}
```
- `check` 시그니처에 `maxCells, maxRows, maxCellChars`를 더하고, `XlsxBook.Limits`로 넘긴다.
- 새 설정 `ggreport.board-write.max-rows`(기본값 후보는 maxCells와 같은 200000)를 추가한다.
- 기존 사후 `cellCount`(146)는 2차 방어로 남긴다.
- ZipGuard가 바이트 상한을 세는 방식(`size`, `total`)은 감싼 스트림에서 그대로 유지한다.

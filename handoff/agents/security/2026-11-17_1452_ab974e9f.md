# 사업계획 수집 [실행] 버튼에서 망 밖 agent를 직접 HTTP 호출하는 설계: 보안 검토

## 결론
감사 테이블은 036 대신 034의 `INST_PLAN_ACT`(`PlanAudit`)를 쓰는 편이 맞습니다. 권한은 기존 `MenuGuard.require("map")`(요청)과 `AdminGuard.require`(실행)로 충분합니다. 그런데 이 기능은 망 안 서버가 인터넷으로 접속하는 첫 경로입니다. 그래서 다음 두 가지가 가장 큰 위험입니다.
- 망분리 규정과 충돌할 수 있습니다(정보보호 확인 필요).
- 지금 신원 확인은 화면이 보내는 사번(`X-Emp-No`)을 그대로 믿는 방식이라 위조할 수 있습니다. 이 위조로 실제 외부 호출까지 일으킬 수 있게 됩니다.

## 3. 권장안 (질문 1~7에 대한 답)

### 1) 외부 호출 경계 — 필수
- **주소는 설정 하나로 고정합니다.** `plan-agent.url`은 기동할 때 한 번 검증합니다.
  - 스킴은 `https`만 허용합니다(로컬 개발 프로필만 `http://localhost` 예외).
  - 주소에 사용자 정보(`userinfo`)나 쿼리가 있으면 거부합니다.
  - 호스트는 별도 키 `plan-agent.allowed-host`와 정확히 같아야 합니다.
  - 요청이나 DB에서 온 값으로 주소를 만들지 않습니다. 경로도 서버 상수로 둡니다(예: `/v1/plan-jobs`).
  - 주소가 비었거나 검증에 실패하면 [실행]은 503과 고정 문구로 막습니다(초안대로).
- **리다이렉트를 끕니다.** `HttpClientBuilder.disableRedirectHandling()`을 쓰고, 3xx 응답은 실패로 처리합니다.
- **자동 재시도를 끕니다.** `disableAutomaticRetries()`를 쓰고, 쿠키 저장소도 끕니다(`disableCookieManagement()`).
- **타임아웃**: 연결 3초, 응답 대기 10초, 커넥션 풀 대기 2초(값은 팀이 정할 일). 전체 상한도 둡니다.
- **TLS**: 신뢰 저장소를 지정하고 TLSv1.2 이상만 씁니다. "모든 인증서 신뢰" 설정이나 호스트 이름 검증 끄기는 금지합니다.
- **프록시**: 시스템 프록시를 자동으로 따르지 않습니다. 필요하면 명시적 설정 키로만 씁니다.
- **응답 처리**:
  - 2xx(가급적 202)이고 `Content-Type: application/json`일 때만 읽습니다.
  - 본문은 최대 4KB까지만 읽고, 넘으면 실패로 처리합니다.
  - 고정 DTO로 받되 모르는 필드는 무시합니다.
  - 읽는 값은 `job_id` 하나뿐이며 `[A-Za-z0-9-]{1,64}`에 맞아야 합니다. `accepted` 같은 다른 문자열은 DB·화면·로그에 쓰지 않습니다.
  - 화면에는 서버 고정 결과 코드(`SENT`/`AGENT_UNREACHABLE`/`AGENT_REJECTED`/`BAD_RESPONSE`)만 보여 줍니다.
- **결과 반입**: 지금의 inbox/관리자 업로드 경로만 씁니다. 응답이 반입이나 데이터를 대신할 수 없습니다.

### 2) 보내는 값 — 필수
- **보내는 값**: `institution_id`, 기관명, 서버가 만든 무작위 요청 키(UUID, 같은 요청을 한 번만 처리하게 하는 키) 세 가지뿐입니다.
- **보내지 않는 값**: 사번, 요청자 이름, 요청 사유 자유기입란, DB 일련번호.
- **값의 출처**: 기관 ID와 이름은 [실행] 요청 본문에서 받지 않고, 저장된 요청 행에서 서버가 읽습니다(파라미터 변조 방지).
- 기관 ID는 `PlanCsv.validId`(`PlanCsv.java:32`) 형식으로 다시 검증합니다.

### 3) 인증 비밀 — 필수
- **토큰 보관**: `plan-agent.token`은 `config/application.properties`(git 미추적)에만 둡니다.
  - `config-envs/out-local`에는 키만 빈 값으로 둡니다.
  - dev/stg/prod에는 기존 관례대로 `<PROD-PLAN-AGENT-TOKEN>` 같은 자리표시자를 둡니다.
- **보내는 방법**: `Authorization: Bearer` 헤더로만 보내고, URL 쿼리에는 넣지 않습니다.
- **로그·출력 금지**:
  - 토큰과 요청 헤더는 어떤 수준의 로그에도 찍지 않습니다.
  - `org.apache.http.wire`·`org.apache.http.headers` 로거는 WARN 이상으로 고정합니다(DEBUG면 헤더 원문이 찍힙니다).
  - 토큰을 담는 설정 객체의 `toString`에서 토큰을 빼거나 가립니다.
  - 기동 로그에는 "url 설정됨/비었음"만 남깁니다.
- 토큰이 비었으면 [실행]을 막습니다. 토큰 없이 호출하지 않습니다.

### 4) 권한 — 필수
- **요청**: `guard.require(req, "map")`. `InstitutionPlanController.VIEW_MENU`(`InstitutionPlanController.java:39`)와 같은 문지기라서 "사업계획을 볼 수 있는 사람"과 정확히 일치합니다.
- **실행**: `admin.require(req)`. 전산팀원·전산팀장이 모두 관리자입니다(`033_...sql:3`, `Menus.java:112`).
  - DENIED 감사는 `InstitutionPlanController.requireAdmin`(107-121행) 패턴을 그대로 씁니다.
  - `requireInstitutionEdit`는 영업 계열도 통과시키므로 쓰지 않습니다(같은 파일 29행 주석과 같은 이유).
- **알려진 한계**: 자기신고 사번 위조가 그대로 남습니다. 완화책은 다음과 같습니다.
  - 실행 대상은 이미 저장된 요청 행에서만 고릅니다.
  - 서버 전체에서 외부 호출은 동시에 1건만 허용합니다(HWP 보조 추출의 Semaphore 패턴, 커밋 `6a352d4`).
  - 실행 간격에 상한을 둡니다(예: 같은 기관 24시간에 1회, 전체 분당 N회).
  - SSO가 붙으면 [실행]은 `actor.isVerified()`가 참일 때만 허용하도록 전환하는 것을 NEXT 35에 적어 둡니다.
- **CSRF(권장)**: 실행 API는 `Content-Type: application/json`과 사용자 정의 헤더가 있어야만 받습니다.

### 5) 감사 — 필수
- 036이 아니라 **034의 `INST_PLAN_ACT`와 `PlanAudit.record`를 재사용**합니다.
  - 기관 ID, 동작 코드, 결과, 사번, 신원 확인 여부(`EMP_VERIFIED`), 화면·버튼 칸이 이미 있습니다.
  - 화면·버튼 값은 서버 고정값입니다(`PlanUiIds.java:3`).
- **추가할 것**:
  - `PLAN_ACTION` 코드 `COLLECT_REQUEST`·`COLLECT_RUN`: Oracle·MySQL 양쪽에 넣고, `InstPlanDdlPairTest`가 두 INSERT 블록이 같은지 대조합니다.
  - `PlanUiIds`에 `plan_collect`/`plan_collect_request`/`plan_collect_run` 추가
- **`OUTCOME`(VARCHAR(20)) 값**: `OK`/`DENIED`/`BLOCKED_NO_URL`/`AGENT_FAIL`/`DUPLICATE` 같은 고정 코드만 넣습니다. 응답 본문이나 예외 메시지 원문은 싣지 않습니다.
- **기록 시점**: 외부 호출 **전에** "실행 시작"을 남기고, 호출이 끝난 뒤 결과를 남깁니다. 감사 쓰기에 실패하면 호출하지 않습니다(`missing.csv`의 "감사 먼저" 선례, `InstitutionPlanController.java:92`).

### 6) 동시성 — 필수
- **요청 표 신설**(예: `PLAN_COLLECT_REQ`): 상태는 `REQUESTED → RUNNING → SENT|FAILED`, 칸은 요청 키·요청 시각·`RUNNING` 시작 시각입니다.
- **요청 중복 막기**: 기관당 진행 중 요청은 1건으로 제한합니다.
  - MySQL: 생성 칼럼에 유일 인덱스
  - Oracle: 함수 기반 유일 인덱스
  - 아니면 서비스에서 조건부 INSERT
- **실행 순서**:
  1. `UPDATE ... SET STATUS='RUNNING', RUN_AT=? WHERE REQ_ID=? AND STATUS='REQUESTED'`의 영향 행이 1일 때만 진행합니다. 0이면 409를 돌려주고 `DUPLICATE`로 감사합니다.
  2. 이 커밋을 끝낸 **뒤** 트랜잭션 밖에서 HTTP를 겁니다.
  3. 결과는 다시 조건부 UPDATE(`WHERE STATUS='RUNNING'`)로 반영합니다.
- **멈춘 요청 처리**: `RUNNING`이 N분을 넘으면 관리자가 `FAILED`로 되돌릴 수 있게 합니다(별도 버튼과 감사).
- 같은 요청 키를 agent에 보내 망 밖에서도 한 번만 처리되게 합니다.

### 7) 심각도별 목록과 SCHEMA 문구 초안

**필수(구현 전)**
1. 정보보호 부서의 망분리·외부 접속 승인. 방화벽은 목적지 1곳·443 포트만 엽니다.
2. 주소 고정·https·리다이렉트 끄기·재시도 끄기·타임아웃
3. 응답 4KB 상한, `job_id`만 읽음
4. 송신 값 3종만
5. 토큰은 git 미추적 설정에만 두고 로그에 남기지 않음
6. 요청 = `map` 조회 권한, 실행 = `AdminGuard`
7. `INST_PLAN_ACT` 감사(호출 전에 기록)
8. 조건부 UPDATE 상태 전이, HTTP는 트랜잭션 밖

**권장**
- 외부 호출 동시 1건과 실행 간격 상한
- JSON 본문과 사용자 정의 헤더 필수(CSRF 대비)
- SSO 이후 [실행]은 확인된 신원만 허용

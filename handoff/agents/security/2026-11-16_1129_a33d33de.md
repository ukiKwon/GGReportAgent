### 2. 다섯 관점별 판정
1. **admin_by_line을 요청 본문으로 넣을 수 있나 — 막혀 있다(확인).**
   - `ApprovalIn.PermRequest`(54-62)에는 reason과 changes 두 필드뿐이다.
   - payload는 서버가 새 LinkedHashMap으로 만든다(349-354). changes 항목도 menu·view·write·edit·approve·before 키만 다시 담는다(313-327).
   - 매퍼에는 payload를 갱신하는 문장이 없고 INSERT만 있다(`ApprovalRequestMapper.xml:13-14`).
   - adminByLine()은 PERM_REQUEST 유형에서만 이 키를 읽는다(711).
2. **역할 문자열로 팀을 판정하는 데서 생기는 우회 — 우회 경로는 없다(확인). 다만 범위가 결정보다 넓다(하, 아래 F1).**
   - 역할은 관리자만 바꿀 수 있고, 정해진 목록(`Teams.ROLES`) 안에서만 고른다(`UserAdminService.java:132`).
   - 상위 결재자 지정도 관리자 전용이다(`SysAdminController.java:101-104`).
   - 사용자별 예외로 관리자 권한을 줄 수 있지만, 그것도 관리자만 할 수 있다.
3. **상신 뒤 관리자 해제나 대결자 변경 — 결재 시점에 다시 따진다(확인).**
   - 결재하는 사람이 본인이든 대결자든, 결재 시점에 canAdmin이어야 한다(eligibility 701). canAdmin은 활성 상태, 사용자 예외, 역할 기본값을 그때 읽는다(`PermissionService.java:101-108`).
   - 대결자 알림도 관리자에게만 간다(527).
   - 해제된 건은 아무도 결재할 수 없게 걸려 있다. ADMIN 단계가 없고 다른 관리자는 결재선 밖이다. 상신자나 관리자가 취소할 수는 있지만 상신자에게 알림이 가지 않는다(F3).
4. **list·view·decide 세 경로의 판정 일치 — 일치한다(확인).** 셋 다 같은 eligibility(…, r)를 부른다(411, 600, 927).
5. **시험 7건 — 핵심 경로는 고정했다.** 1단계 완결, 관리자 아닌 전산팀장일 때 ADMIN 단계 유지, 영업팀은 그대로, 관리자 아닌 대결자 403과 알림 없음, 상신 뒤 관리자 해제 시 403과 결재함에서 빠짐을 확인한다. 빠진 시험은 F2에 적었다.

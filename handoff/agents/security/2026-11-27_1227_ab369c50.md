### 3. 권장 조치 순서

1. **패치를 조정해 적용**
   - 완화 조건을 "hwpx이고, 이름이 `.xml/.hpf/.rels/.xsd/.rdf`가 아닐 때"로 한다(`.rdf` 추가).
   - 기존 인자 묶음은 그대로 두고 완화 끔(false)으로 이어지게 한다.
   - 주석에 지킬 조건을 적는다: "서버가 XML로 해석하는 항목 이름 ⊂ 엄격하게 검사하는 이름. 이름이 `.xml`이 아닌 항목을 XML로 읽는 코드를 새로 만들면 이 완화를 다시 본다."
2. **더 좁은 대안과 비교**
   - `Preview/` 아래만 또는 `.txt`만 완화하는 안은 보안상 얻는 것이 거의 없다(지킬 조건이 이미 성립한다). 대신 가설이 조금만 빗나가도 고쳐지지 않는다(Scripts·BinData의 SVG·텍스트 같은 경우).
   - 표준 항목 이름 허용 목록 안은 한컴 판마다 이름이 달라 오탐 위험이 있다.
   - 더 깔끔한 대안은 외부 확인 반입처럼 이름으로 판정하는 것이다. `.txt`는 XML로 파싱하지 않고 글자로 풀어 개인정보 검사에 포함한다. 변경 범위가 커지므로 선택 사항으로 둔다.
3. **가설 확인 뒤 적용** (5절)
4. **이전부터 있던 hwpx 스크립트 틈을 별도 항목으로 판단** (이관 메모)

### 4. 시험으로 고정할 것
- hwpx에 `Preview/PrvText.txt`를 UTF-16LE+BOM 바이트(`<붙임> 입찰공고`)로 넣는다 → 201. UTF-8 판도 같은 결과여야 한다.
- 이름이 `.txt`이고 맨 앞이 `<!DOCTYPE x [<!ENTITY …>]><x/>`인 항목 → 400(맨 앞 DOCTYPE은 여전히 거부). 이것으로 JDK StAX의 DTD 이벤트 동작도 함께 고정된다.
- 깨진 `Contents/section0.xml`, 깨진 `Contents/content.hpf`, 깨진 `META-INF/container.rdf`(목록에 넣은 경우) → 400.
- 이름이 `.txt`인 항목에 시작 요소 3000만 개 초과 → 여전히 TOO_MANY_CELLS(400). 비용이 크면 한도를 낮춘 ZipGuard 단위 시험으로 대신한다.
- 대소문자만 다른 중복 이름(`Preview/PrvText.txt`와 `preview/prvtext.txt`) → 400.
- 같은 PrvText.txt를 넣은 xlsx·docx → 400(기본값 false). XlsxBook 경로도 같은 항목으로 거부되는지 본다.
- 이름에 `activex`가 든 hwpx → ACTIVE_CONTENT 400(완화와 무관함을 고정).
- 한 바퀴: 완화로 통과한 hwpx에서 평가표 읽기(ScoringTable)가 section 표를 정상으로 읽는지 본다.

### 5. 가설이 틀렸을 때 사용자 파일로 확인할 것
- `unzip -l 파일.hwpx`: `Preview/PrvText.txt`가 있는지, 대소문자만 다른 중복 이름이 있는지, 항목 수.
- `unzip -p 파일.hwpx Preview/PrvText.txt | xxd | head -2`: BOM(`ff fe`) 다음 첫 글자가 `3c 00`(`<`)인지.
- `.xml`이 아닌 다른 항목 중 `<`로 시작하는 것이 있는지(`Scripts/*`, `BinData/*.svg`, `META-INF/*.rdf`).
- `zipinfo -v`: STORED 방식 항목에 데이터 디스크립터 표시(bit 3)가 있는지. 그렇다면 한컴이 아닌 도구로 만든 파일이고, 이 패치로는 고쳐지지 않는다.
- `Contents/section0.xml` 앞부분에 `<!DOCTYPE`이 있는지.
- 원인을 확정하려면 `Rejected.code`(BROKEN 등)만 로그에 남기는 임시 패치가 안전하다. 파일 이름·내용은 남기지 않는다.

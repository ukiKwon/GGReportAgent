# NEXT 39 점검: uploader의 POI 진입점에 ZipGuard 적용 방안 (security, 읽기 전용)

**결론:** 진입점 6곳 모두 열기 전 검사가 없습니다. 그보다 급한 문제가 하나 있습니다. HWPX 본문 파서가 외부 엔티티(XXE)를 막지 않아, 서버 파일 내용이 조회 API 응답으로 새어 나갈 수 있습니다. 코드 경로로 확인했고 실제로 돌려 보지는 않았습니다. 그래서 2026-11-02의 "폐쇄망 영향 하" 판단은 그대로 유지하기 어렵습니다.

## 1. 대상·방법·못 본 것
- **본 것:** NEXT 39 항목, web의 `docfill/ZipGuard.java`(41eb111 기준)·`XlsxBook.java`·`PoiLimitsConfig.java`, uploader의 `InstitutionService`·`FileContentService`·`PptExtractor`·`RfpExtractor`·`DocumentParseService`·`FileUploadService`·`FileSearchApiController`·`KGI13410`·`DocumentType`·`UploadedFile`·`UploadedFileMapper.xml(search)`·`pom.xml`·multipart 설정을 정적으로 읽었습니다.
- **못 본 것:**
  - hwpxlib 1.0.9·hwplib 1.1.11 내부(zip을 `ZipFile`로 여는지, XML 파서 설정이 어떤지). jar 안이라 확인하지 못했습니다.
  - WebLogic에서 POI 클래스로더가 war마다 따로인지.
  - 실행 재현은 하지 않았습니다.
  - uploader 인증 방식(`SystemUserInterceptor`)은 범위 밖이라 보지 않았습니다.
- **바로잡을 점:** 지시에 "압축률" 검사가 있었는데, 현재 ZipGuard에는 비율 검사가 없습니다. 실제로 읽은 바이트의 절대 상한(entry별·합계)만 봅니다. 절대 상한이 비율 검사를 포함하는 효과는 냅니다. 비율 하한(0.01)은 web에서 `PoiLimitsConfig`가 POI 전역값으로 따로 겁니다.

## 4. 진입점별 적용 지점과 패치 후보(한 줄씩)
1. **공통:**
   - uploader에 ZipGuard를 복사하고 `Path` 판을 추가합니다.
   - web `PoiLimitsConfig`도 복사합니다(비율 0.01, entry 100MB).
   - 동시 파싱을 세마포어 2개로 제한하는 것을 검토합니다(web은 concurrency=2).
2. **`PptExtractor.extract`(27행 앞):** 앞 4바이트가 `PK`이면 `ZipGuard.check(file, entry상한, 합계상한, MAX, MAX, MAX, 2_000_000)`을 부릅니다. 지금처럼 `SlideShowFactory.create(InputStream)`으로 열면 S5도 막힙니다. .ppt는 크기 상한만 겁니다.
3. **`RfpExtractor.extractHwpx`(115행 앞):** ZipGuard를 부르면 DOCTYPE 파트가 BROKEN으로 거부되므로, hwpxlib 내부 파서가 무엇이든 XXE의 1차 방어가 됩니다. hwpxlib가 `ZipFile`을 쓴다면 가드가 모은 이름 집합과 `ZipFile.entries()` 이름 집합을 대조하는 검사를 추가합니다.
4. **`FileContentService.extractHwpxText`:**
   - SAX 파서에 `disallow-doctype-decl=true`, `external-general/parameter-entities=false`, `load-external-dtd=false`, `FEATURE_SECURE_PROCESSING=true`를 겁니다. ZipGuard도 앞에 둡니다.
   - 151행은 null을 반환하고 로그만 남기게 바꿉니다.
   - 이 수정은 39와 별개로 먼저 처리해야 합니다(S1).
5. **`FileContentService.extractExcelText`(89행):** xlsx이면 ZipGuard를 부르고, `WorkbookFactory.create(InputStream)`으로 바꿉니다(S5).
6. **`InstitutionService.importFromXlsx`(98행):**
   - 컨트롤러에서 크기 상한(예: 2MB)을 겁니다.
   - `ZipGuard.check(xlsx, 10MB, 20MB, 100_000칸, 50_000행, 1_000자, 500_000)`을 부릅니다.
   - `deleteAll`(100행)은 전체 파싱이 끝나 목록이 만들어진 뒤로 옮깁니다.
7. **`FileSearchApiController.search`:** 본문 추출을 빼거나 페이징·건수 상한을 겁니다. 아니면 주석대로 API를 삭제할지 결정합니다.
8. **거부 코드 연결:** 거부되면 `markParseFailed`로 처리합니다. 화면에는 web `BoardWriteService:235-237` 문구를 재사용하고, 사유는 로그에만 남깁니다(스택·경로 노출 금지).

## 5. 위험 정리
- **메모리:** 남는 위험은 파일 `byte[]`(최대 100MB), 가드가 보관하는 XML 파트(최대 entryMax), POI의 문서 객체가 동시에 올라가는 경우입니다. 업로드 여러 건을 한 요청에서 순차로 처리하고 조회 API가 반복 파싱까지 하므로, `Path` 판과 동시성 제한이 필요합니다.
- **zip bomb:** 절대 해제량 상한(가드)과 비율 0.01·entry 100MB(POI 전역)를 2중으로 겁니다.
- **XXE:** 가드의 DOCTYPE 거부와 SAX 설정 강화를 2중으로 겁니다. StAX 쪽은 web ZipGuard가 이미 끔(166-167행)을 확인했습니다.
- **POI 전역값:** `ZipSecureFile` 설정은 static입니다. WebLogic에서 POI를 war마다 따로 싣지 않고 공유 라이브러리로 쓰면 두 앱 설정이 서로 덮어씁니다(추정, 확인 필요).

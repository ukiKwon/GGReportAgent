## 3. 권장 조치 순서
1. **F1** — 패치 후보: `changeDirect` 앞에서 팀장 호출자를 "건 담당자 중 누군가(또는 확정자)의 `sameTeamLead`가 나"로 좁힌다(`hasStartAuthority`와 같은 기준). 팀장이 자기를 추가하는 경우나 팀장이 관련된 변경까지 결재 없이 둘지는 기획 결정이 필요하다.
2. **F2** — 패치 후보: 사전준비 시작처럼 `PrepService.changeAssignees` 안에서 `audit.record(..., "OK", ..., ui)`를 같은 트랜잭션에 쓰고, 컨트롤러는 `okInService=true`로 부른다. 이때 ui 판정은 `PrepUiIds.forAssigneeChange`(prep_detail/assignee_change만 유효)를 새로 만들어 쓴다. F6도 함께 해소된다.
3. **F3** — 패치 후보: 평가표 분석을 `PrepAttachInspector`의 `PDF_POOL`·시간 상한 방식으로 감싼다. 읽을 파일 수를 최근 N개(예: 3개)로 줄이고, 결과를 `attach_id`+sha 기준으로 캐시한다. 파일 읽기·분석은 트랜잭션 밖에서 한다(`readOnly` 해제 또는 목록 조회만 트랜잭션으로).
4. **F4·F5** — 패치 후보: 일정 등록은 화면 전용 버튼 id(예: prep_detail/meeting_save)를 `BoardUiIds`에 더해 감사가 사실대로 남게 한다. SUBMITTED 중 변경 허용 여부와 결재 중 담당 변경 시 처리는 기획이 판정한다.

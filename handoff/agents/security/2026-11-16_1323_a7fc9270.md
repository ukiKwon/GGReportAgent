### 2. 점검 항목별 판정 (①~⑥)
- **① 본인 변경 차단**
  - 사용자 정보·상태·결재자·개인 권한 네 경로는 막혔다(확인): `UserAdminService.java:96,124`, `ApproverService.java:112`, `PermissionService.java:194`.
  - 대소문자·공백 우회는 안 된다(확인).
    - Actor 쪽 사번은 trim 뒤 ASCII 숫자 7자리만 받는다(`Actor.java:34`, `MenuPerms.java:48-57`).
    - 경로 쪽 사번은 trim 없이 엄격히 7자리여야 해서, `" 8203417"`은 404로 끝난다(`UserAdminService.java:142`, `ApproverService.java:113`).
  - 사용자 등록 때 본인 사번을 넣으면 이미 있는 사번이라 409다(`:62`).
  - 결재 반영(applyApproved)은 결재자와 상신자가 같으면 eligibility가 null을 돌려준다(`ApprovalRequestService.java:688`). 본인 권한 신청은 반드시 다른 사람의 결재를 거친다(확인).
  - 남은 구멍은 아래 표의 중-1과 하-1이다.
- **② 증적 칸에 민감값이 들어가는지**
  - 화면·버튼은 허용 목록에 있으면 원값, 없으면 UNKNOWN이다(`AdminUiIds.java:25-31`).
  - item은 MENU_KEYS 허용 목록에 고정 접두어를 붙인 값이고, TARGET_ROLE은 `Teams.ROLES` 허용 목록 값이다(`MenuService.java:96-101`).
  - 결재 단계 tier는 int이고 서비스가 검증한다.
  - 요청 본문·쿼리값·비밀번호는 기록하지 않는다(확인).
  - 기록되는 개인정보는 user:NAME의 직원 이름뿐이고, 기존 변경 이력과 같은 수준이다.
- **③ 036 마이그레이션**
  - 11g에서 되는 문법만 쓴다: ADD … DEFAULT … NOT NULL, MODIFY NULL, 인덱스 이름 30자 미만. MySQL의 MODIFY도 원래 정의(`VARCHAR(7)`)와 같다(확인).
  - 되돌리기는 역할 행을 DELETE해야 하므로 이력이 사라진다. 머리 주석에 "운영 금지"가 적혀 있다.
  - 배포 순서 위험은 하-5에 적었다.
- **④ S6 BID_PREP_ACT 기록 실패**
  - 결정·확정은 서비스에서 이미 커밋된 뒤라, 기록이 실패하면 응답은 500인데 결과는 반영돼 있다(`BidCaseController.java:140-142, 208-210, 248-255`).
  - 서버 로그에는 ERROR 한 줄이 남고, ACCESS_LOG에는 사번이 남는다. 설계 문서가 이 동작을 알고 받아들였다(하-4).
- **⑤ 코퍼스**
  - 등록은 관리자 전용이 됐다(`InstitutionController.java:244`). 401·403 시험도 있다(`CorpusApiTest.java:234-237`).
  - 남은 것은 하-6, 하-7이다.
- **⑥ 시험**
  - 고정된 것: S1 네 경로, S3, S4(화면·버튼·`<script>`), S5, S7, S9, S10.
  - 고정되지 않은 것: S2, S6, 서비스 단위의 마지막 관리자 보호(중-2).

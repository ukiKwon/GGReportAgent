- **트랜잭션**: `PrepAudit.record`는 `@Transactional`(REQUIRED)이다. 그래서 서비스 안의 성공 줄은 저장과 같은 트랜잭션에 묶인다(`PrepAudit.java:31-49`). 실패 줄은 트랜잭션이 없는 컨트롤러에서 따로 커밋된다. 설계 의도대로다.
- **기록 내용**: DETAIL·감사에는 상태·날짜·이름·쿼리값이 들어가지 않는다. LOG.error에는 건 번호와 예외 종류만 남는다.
- **날짜**: `LocalDate.parse`(ISO_LOCAL_DATE, STRICT)에 2000-01-01~오늘(KST) 범위를 건다. 상태는 허용 목록 4개다. `in==null`이면 BAD_STATUS가 먼저 나서 NPE가 생기지 않는다.
- **DDL**: IDENTITY·FETCH FIRST·CHECK·외래키가 없고 `DEFAULT 0 NOT NULL` 순서가 맞아 11g와 호환된다. 인덱스 이름 `IDX_BPC_ACTOR`는 기존 소스와 충돌하지 않는다(grep 0건). 권한을 SELECT·INSERT만 주는 것도 적절하다.
- **묶음 2 검증**

  - 자기 자신을 고를 수 없다. 신청자가 팀장이면 HEAD_APPROVES로 막히고, 영업팀원은 `isLead`에서 막힌다.

  - `approver_pick`은 서버가 만든 값이다. 오류 문구는 하나라서 어느 조건에서 걸렸는지 드러나지 않는다.
- **자기신고**: X-Emp-No 자기신고는 이미 수용한 위험이다. 결재자 선택 칸이 새 사칭 경로를 만들지는 않는다. 사칭하려는 사람은 원래 팀장 사번을 직접 신고할 수 있다.

2. **(적용 전) 5번을 고친다.** 패치 후보: 이름이 비면 사번으로 대체한다(`me.getName()==null||isEmpty ? me.getEmpNo() : name`). 또는 DDL에서 ACTOR_NAME의 NOT NULL을 뺀다(헤더에 이유를 적는다).
3. **(적용 전·기획) 2번 범위를 정한다.** 패치 후보: `chosenLead`에 "신청자 결재 체인(`ApproverRules.chain`) 안의 팀장이거나 같은 팀(`Teams` 소속)" 조건을 더한다. 결재함 상세에는 `approver_pick=REQUESTER`를 보여 결재자가 신청자 지정임을 알게 한다.
4. **(적용 때) 4번을 시험으로 고정한다.** 패치 후보: PrepBoardApiTest에 "PK 중복이면 409 STALE_CHECK, BID_PREP_CHECK 행 수 그대로, 감사 BLOCKED" 시험을 하나 추가한다. 보고서 주석 "세 겹"에 "MySQL에서는 PK가 실제 방어선"을 한 줄 더한다.

### 4. 이관 2건 판정(권장안)
- **(a) 401·비활성 403을 BID_PREP_ACT에 남길지**: 권장안은 **`PrepController`에 맞춰 둘 다 남기지 않는 것**입니다.
  - 이유 1: BID_PREP_ACT는 "등록된 활성 사용자가 이 건에 한 시도"로 읽혀야 합니다. 비활성·미등록 사번까지 들어가면 위조 사번 줄이 섞입니다.
  - 이유 2: 401과 비활성 403은 이미 ACCESS_LOG에 남습니다. 지금은 `AccessLogInterceptor` 덕분에 API 이벤트와 상태 코드가 남고, 아래 (b)를 하면 DENIED로 남습니다.
  - 패치 후보: 컨트롤러가 서비스를 부르기 전에 `guard.requireActiveUser(req)`를 부르고, try 밖에 둡니다(`PrepController.java:239`와 같은 모양). 이러면 (b)의 401·비활성 부분도 함께 해결됩니다.
  - 다만 이렇게 하면 다른 결재 유형에서도 401·403 응답 문구는 같지만 ACCESS_LOG 이벤트가 API에서 DENIED로 바뀝니다. 그러니 (b)와 묶어 한 번에 하십시오.
- **(b) 결재 경로 403의 ACCESS_LOG DENIED 추가 · 머리글 필수화(NEXT 68 S8)**
  - **DENIED 추가는 적용을 권장합니다(하).**
    - 지금도 ACCESS_LOG에 상태 코드 403이 API 이벤트로 남으므로 빠진 기록은 아닙니다. 사전준비·이사회 쪽과 이벤트 분류를 맞추는 일관성 문제일 뿐입니다.
    - 패치 후보: `auditPrepFailure` 뒤에서 `e.getStatus()==403`이면 `throw guard.denied(req, e)`. 모든 결재 유형에 적용해도 응답은 바뀌지 않고 이벤트 유형만 바뀝니다.
    - 성공 시 `AccessLogInterceptor.DETAIL`(`prep case=…`)도 같이 넣으면 `PrepController`와 대칭이 됩니다. 이것은 선택입니다.
    - 급하지 않으니 다음 묶음으로 미뤄도 됩니다.
  - **머리글 필수화는 지금 적용하지 않기를 권장합니다.**
    - 결재 엔드포인트는 사전준비가 아닌 결재도 함께 쓰므로, 400으로 막으면 머리글을 보내지 않는 다른 화면·호출이 깨질 위험이 있습니다.
    - 머리글도 자기신고 값이라 필수로 만들어도 보안 경계가 되지는 않습니다. 지금은 `UNKNOWN`·`ui_valid=0`으로 식별되므로 충분합니다.

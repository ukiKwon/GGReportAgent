**설계가 물은 5가지에 대한 답**
1. **문맥 저장**: DB에 저장하지 않는 쪽이 맞다(대외비가 DB·백업에 복제되지 않음). 다만 with_context에는 **담당 검사 대신 `requireActiveUser` + 동시 실행 제한**을 건다(S2). 담당만 보게 하면 디자이너·검토자 흐름이 깨진다. 노출되는 글은 내려받기 수준 이하다. 진짜 위험은 인증 없이 큰 계산을 일으키는 것이다.
2. **상한**: 3,000,000자·500쪽·20초는 받아들일 만하다. 다만 pptx에도 시간 상한을 두고, 전체 추출에 세마포어를 걸고, PDF 대기열에 한도를 두어 BUSY면 바로 NOT_CHECKED로 처리한다(S3·S4). 작업함 전용 ZipGuard 인자는 항목 하나 100MB를 **30MB 안팎으로 낮추기**를 권한다. 정상 슬라이드 XML이 수 MB를 넘는 일은 드물다(추정).
3. **ack 권한**: 디자이너는 `designerWriteActor`면 충분하다. 세 팀은 S7대로 `me`(USERS 행) 기준으로 담당을 비교하고, 잠긴 작업(디자이너 1차완료 이후)에서는 ack를 막기를 권한다.
4. **rejectUnsafe**: 지금처럼 기본 off로 둔다. 켤 때 범위는 pptx 매크로·ActiveX와 PDF JavaScript·Launch로 한정한다. EmbeddedFile은 거부하지 말고 `NOT_CHECKED/ATTACHMENT`로 둔다(S10). 어느 경우든 S1을 먼저 고친다.
5. **acked_by 노출**: 인증 없는 GET에서는 이름만 싣고, 사번은 `requireActiveUser`를 통과한 경우에만 싣는다(S11).

**문제없음으로 본 것**
- **zip slip**: 디스크에 풀지 않고 `.zip`은 열지 않으므로 해당 없음.
- **XXE**: ZipGuard 방식(`SUPPORT_DTD`·`IS_SUPPORTING_EXTERNAL_ENTITIES` false + DTD 거부)을 따르면 막힌다. 조건은 S6.
- **로그**: 예외 종류만 남기는 원칙은 적절하다. PDFBox 자체 경고 로그에 글 조각이 섞일 가능성은 추정 수준으로 낮다.
- **SQL**: MyBatis `#{}`로 묶으면 주입 위험이 없다. `${}`는 금지.

## 3. 권장 조치 순서 (적용 전 반드시 고칠 것: 1~6)
1. **S1**: 위험 검사를 `TaskFiles.save` **전에** 메모리에서 끝낸다(추출은 저장 전, DB 기록은 저장 후). 아니면 이번 패치에서 rejectUnsafe 스위치를 뺀다.
2. **S2·S3·S4**: 추출 전체(업로드·재검사·with_context)에 공통 세마포어(예: 2)를 걸고, 기다리지 않고 바로 `NOT_CHECKED/BUSY`로 처리한다. pptx에도 deadline을 둔다. PDF 풀은 `ThreadPoolExecutor` + 작은 고정 대기열 + 거부하면 BUSY로 바꾼다. with_context에는 `requireActiveUser`를 건다.
3. **S5**: 파일당 HIT 행 상한(예: 2,000)을 두고, 넘으면 `PARTIAL/HIT_CAP`으로 둔다.
4. **S6·S12**: 2차 읽기는 `ZipInputStream`으로 하고 DTD 이벤트가 나오면 BROKEN으로 처리한다. `extract`를 Throwable(Error 제외) catch-all로 감싸고, 9999를 넘는 번호는 `OTHER`/0으로 바꾼다.
5. **S7**: 세 팀 ack는 `me`(USERS 행 이름 또는 사번)와 담당을 비교한다. `by`는 쓰지 않는다.
6. **S8**: ack·해제를 덧붙이기 방식 이력으로 남긴다(`ACK_SEQ` 또는 기존 감사 표 양식). 제출 때 미확인 건수 기록 여부는 기획이 결정한다.
7. S9(화면 textContent), S11, S14(ack 경로 16KB 필터), S10, S13(작업·이름 단위 잠금 또는 요약 때 sha 대조), S15·S16은 같은 패치에 넣거나 다음 패치로 넘긴다.

## 결론: 푸시를 막을 '상' 등급 문제는 없습니다

`origin/kgi-report-web-dev..HEAD` 범위를 실제 코드로 확인했습니다. 비밀값·실존 개인정보 유출, innerHTML 이스케이프 누락, 새 API의 서버 권한 우회는 찾지 못했습니다. 아래는 모두 '중' 이하입니다. 단, 앞단 인증이 아직 X-Emp-No 자기신고라서 모든 역할 검사는 실수를 막는 업무 규칙일 뿐, 사칭을 막는 보안 경계가 아닙니다. 이 한계는 원래 알려진 것이고 그대로 남습니다.

### 3. 지시받은 네 가지 점검 결과
1. **비밀값·개인정보**:
   - `config-envs/*`의 비밀번호는 전부 `<...-DB-PASSWORD>` 자리표시자입니다.
   - 테스트 코드의 주민번호·휴대폰(`900101-1234567`, `010-0000-0000`, `010-1234-5678`)은 개인정보 검출기를 시험하는 가짜 값입니다.
   - handoff 보고서의 7자리 사번(5047192 등)은 `009_seed_users.sql:4`에 "전부 임의로 만든 가상 데이터"라고 적힌 시드 사번입니다.
   - 실제 인물 정보는 발견하지 못했습니다.
2. **esc 누락**: 없습니다.
   - `approvals.targetsHtml`(184-188)은 `kind`·`text`를 모두 esc합니다. `assigneeLines`는 순수 문자열만 만들고 출력은 `targetsHtml`이 맡습니다.
   - `team.js`의 HTML 조각 함수 전부(296-457)는 서버·사용자 값에 esc를 씁니다. 사용자가 입력한 검색어(`noMatchUser`, 입력칸 value 속성)도 esc합니다.
   - esc하지 않은 채 들어가는 값은 고정 집합 값뿐입니다: `ddayClass`, `tone`, `t.key`, `previewHtml`의 숫자.
   - `logic.esc`는 따옴표 두 종류까지 처리하므로 속성 안에서도 안전합니다.
3. **새 API 권한 우회**: 없습니다.
   - 배정 관련 API 5개는 모두 `requireActiveUser`(401/403, 접근 이력에 DENIED 기록)를 거친 뒤 서비스에서 역할을 검사합니다.
   - 최초 배정은 영업팀장만 할 수 있고, 변경 신청은 현재 담당자나 영업팀장만 할 수 있습니다. 결재선은 서버가 계산하고 본문의 결재자 값은 받지 않습니다.
   - 승인 시 결재자가 수혜자인 경우를 두 번 막습니다(`applyChange` 331·343).
   - 영업팀장이 관련된 건은 영업부장만 승인합니다(367). 대결은 막혀 있습니다(`eligibility` 483).
   - 담당자 변경 요청은 관리자 전체 목록에서 빠지고 관리자도 취소할 수 없습니다(270·403·629).
   - `/me/assignments`는 본인 사번만 조회합니다.
   - SQL에 `${}` 문자열 치환은 없습니다(전부 바인딩).
4. **`/assignment-candidates` 열람 노출**: 지금 전제(사무실 PC 전용, 같은 부서)에서는 **받아들여도 된다고 판정합니다**.
   - 이름·직위는 같은 영업팀 사람들이 배정 표(`assigneeMaps`)와 이력에서 이미 보는 정보입니다.
   - 연락처 같은 추가 개인정보는 없고, 다른 팀·디자이너·관리자는 403입니다.
   - 사번은 화면에 글자로 보이지 않고 data 속성에만 있습니다(`team.js:338`).
   - 줄일 여지는 있습니다. 배정 권한이 없는 열람자(영업팀원·영업부장)에게는 화면상 필요가 없는데, 영업팀원은 변경 신청을 위해 후보가 필요합니다. 그래서 막을 대상은 사실상 영업부장뿐이라 효과가 작습니다.

### 4. 권장 조치 순서
1. 푸시를 진행합니다(차단 사유 없음). `server8080.log`는 커밋하지 않습니다(경로 지정 커밋 규칙 유지).
2. `BidCaseController`의 생성·조회 3곳에 가드를 붙입니다(다음 1단계 묶음에서).
3. `StaticCacheFilter`가 API 경로를 정책 대상에서 빼도록 합니다.
4. `requestChange`의 본문이 null일 때 400으로 응답합니다.
5. 7월 summary의 번호 원문은 기획이 판단합니다(이력에서 지우려면 이력 재작성이 필요해 되돌리기 어렵습니다).

### 5. 패치 후보(각 한 줄)
- `BidCaseController.create`·`forAssignee`·`detail`: `HttpServletRequest req`를 인자로 받고 첫 줄에서 `guard.requireActiveUser(req)`를 호출한다. 생성은 필요하면 역할도 확인한다.
- `StaticCacheFilter.policyFor`: 정적 자원 경로가 아니면(예: `/tasks/`·`/institutions/`·`/bidcases/`로 시작) null을 돌려준다. 또는 다운로드 응답에 `Cache-Control: no-store`를 붙인다.
- `BidAssignmentController.requestChange`: `if (in == null) throw new ApiException(400, "입찰 건을 지정하세요.");`를 `requireActiveUser` 바로 뒤에 둔다.

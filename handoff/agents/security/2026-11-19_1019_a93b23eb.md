## 3. 항목별 판단과 설계 반영 요구사항

**① 외부 클라우드 STT(S1·S2)**: 시스템 기능은 개발해도 되지만, **운영에서 켜는 것은 정보보호부서 확인 뒤**로 둘 것을 권장한다. 시스템이 통제하지 못하는 외부 사본이 생기는 일이라 코드로 막을 수 없다.

사용자에게 물을 질문 안(업무 언어, PM이 질문 장부에 매칭):
- **Q-S1. 회의 녹음을 네이버 클로바 노트(회사 밖 인터넷 서비스)에 올려도 되는지 정보보호부서 확인을 받았나요?**
  - 무엇이 달라지나: 녹음과 받아쓴 글은 우리 시스템에 들어오기 전에 네이버 서버에 먼저 저장됩니다. 그 사본은 은행이 지울 수도, 누가 봤는지 확인할 수도 없습니다. 회의에는 실명·금리·타 은행 정보 같은 대외비가 나옵니다.
  - 선택지
    - ① 정보보호부서에 문의해 허용 여부와 조건을 받은 뒤 운영에서 켠다. 개발은 병행한다. **(권장)**
    - ② 이미 허용돼 있다. 근거 문서나 담당 부서를 알려 주세요.
    - ③ 외부 서비스는 쓰지 않는다. 사내 녹취 수단이나 직접 쓴 회의록만 올린다.
- **Q-S2. 이사회 참석자 중 은행 밖 사람(기관 담당자·위원 등)이 있나요? 참석자에게 녹음 사실을 알리나요?**
  - 무엇이 달라지나: 은행 밖 사람의 음성을 외부 서비스에 올리려면 그 사람들의 동의가 필요할 수 있습니다. 또 그 사람들의 이름은 우리 직원 명단에 없어 자동으로 가려지지 않습니다.
  - 선택지
    - ① 은행 직원만 참석하고 녹음을 미리 알린다.
    - ② 외부인도 참석한다. 이 경우 녹음 동의 절차를 정보보호부서와 함께 정한다. **(권장)**
- 운용 수칙 안(질문이 아니라 안내로 함께 전달): 클로바 노트의 공유 링크는 쓰지 않는다. 회사 계정 또는 지정 계정을 쓴다. 텍스트를 내보낸 뒤 클로바 노트의 녹음·기록과 담당자 PC의 원본 파일을 지운다. 데이터 활용 동의는 끈다(이 설정이 있는지는 확인 필요).

**② 업로드 재검사(S6·S7·S8·S12·S13)**: 아래 R1~R8.
- **R1 형식**: 텍스트 파일만 받는다.
  - 확장자 `.txt`이면서 내용에 NUL 바이트가 없어야 한다.
  - 내용이 바이너리 서명(PK·%PDF·MZ·D0CF11E0·{\rtf)으로 시작하면 거부한다.
  - 확장자만 보고 판정하지 않는다.
- **R2 크기**
  - 파일당 2MB 안팎으로 둔다(32분 회의 원문은 수십 KB로 추정).
  - 요청당 파일은 3개(원문 1 + 요약 2)까지만 받는다.
  - 줄 수와 줄 길이(예: 4,000자)에 상한을 둔다.
  - 파서 정규식은 되돌아가지 않는 형태로 쓰고, 시간 예산을 둔다(`Pii.scanExternal`의 Budget 방식).
- **R3 인코딩**
  - BOM을 제거한 뒤 UTF-8을 **엄격하게** 디코딩한다.
  - 실패하면 CP949를 **엄격하게**(`CodingErrorAction.REPORT`) 디코딩한다.
  - 둘 다 실패하면 거부한다. `InstitutionCsv.decode`의 관대한 대체 경로는 가져오지 않는다.
  - UTF-16은 거부한다. 다만 클로바 노트 내보내기 형식이 UTF-16이면 다시 검토한다.
- **R4 문자**: NFKC 정규화를 한다.
  - 허용: `\t \n \r`(CRLF는 LF로 통일).
  - 거부: 그 밖의 C0 제어문자, DEL, C1(U+0080~009F), 양방향 제어문자.
  - 제거: 폭 없는 문자(U+200B~200F, 본문 중간의 U+FEFF) — 가림 대조 **전에** 지운다.
- **R5 파일명**: 저장하지 않는다. 화면에 다시 보여 주지 않는다. 경로를 만드는 데 쓰지 않는다.
- **R6 원본 미보관**: 원본은 메모리에서만 다룬다. 임시 파일·로그·예외 메시지에 원본이나 원문 줄을 남기지 않는다. 파싱 오류는 줄 번호만 알려 준다.
- **R7 미리보기와 확정**
  - 서버는 원본을 들고 있지 않는다(stateless).
  - 미리보기는 가린 결과와 가림 후보 목록을 돌려준다.
  - 확정할 때 화면은 파일과 함께 ① 추가로 가릴 단어 ② 해제할 후보를 POST 본문으로 다시 보내고, 서버가 결정적으로 다시 가린다.
  - 추가 가림 단어는 저장하지 않고, 질의 문자열에도 싣지 않는다.
- **R8 화면 표시**: 원문·요약·검색 강조는 모두 `textContent`로 그린다. 시간대 이동용 앵커 id는 숫자로만 만든다.

**③ 실명 가림(S4·S5)**: 아래 R9~R15.
- **R9 대조 목록**
  - USERS.NAME 전체를 쓴다. 상태와 관계없이 퇴직자도 포함한다.
  - **성+이름 전체**만 대조하고, 이름만 대조하지 않는다. '지원'·'정원'처럼 흔한 단어가 이름이기도 해서 오탐이 많아진다.
  - 두 글자 이름은 뒤에 공백·조사·'님'·직함·문장부호가 올 때만 대조한다.
- **R10 성+직함 규칙**: 성 1자 + (공백) + 직함 목록(부장·팀장·차장·과장·대리·본부장·행장·국장·과장·주무관·위원·위원장·의원·구청장 등)을 찾아 성을 가린다.
- **R11 담당자 지정**: 미리보기에서 담당자가 단어를 지정해 추가로 가린다. 외부인 이름 누락은 이 단계에서만 막을 수 있다.
  - 화면에 "우리 직원 명단에 없는 사람(기관·타 은행)은 직접 지정해야 함" 안내를 고정한다.
- **R12 해제 범위**: 오탐 해제는 이름 사전으로 걸린 후보만 허용한다. 정규식으로 잡은 개인정보(휴대폰·주민·이메일·카드, `Pii.scanLoose`/`scanExternal`)는 해제할 수 없다.
- **R13 가림 표기**: 고정 문자열 `[이름]`으로 바꾼다. 성이나 글자 수를 남기지 않는다. 회의 안에서 '인물1'처럼 가명을 일관되게 붙이는 방식도 1차에서는 쓰지 않는다. 사람을 이어 붙일 수 있게 되기 때문이다.
- **R14 화자 짝짓기 금지**
  - `참석자 N`과 사번·이름을 잇는 칸·테이블·화면을 두지 않는다.
  - 화자 이름을 자유 입력으로 바꾸는 기능도 두지 않는다(사실상 짝짓기가 된다).
- **R15 저장 때마다 재검사**: 원문 수정, 요약 수정, 다음 할 일 메모, 클로바 요약 2종 반입 때 매번 R9~R12와 PII 검사를 다시 돌린다. 걸리면 422로 막고, 응답에 값은 돌려주지 않는다.

**④ 권한·공개범위·감사(S3·S9·S10·S11)**: 아래 R16~R22.
- **R16 열람 규칙은 서버가 정한다**
  - 기본 열람: 결재 등급 TEAM_LEAD·DEPT_HEAD·EXECUTIVE 중 무엇까지, 그리고 영업 계열만 볼지는 planner·PM이 정한다.
  - 등급만으로 열면 전산팀장·예산팀장도 열람하게 된다. 이것이 의도인지 확인이 필요하다.
  - 공개범위로 지정된 사람만 더한다.
  - 020 열람 권한을 물려받지 않는다. 회의록 API마다 따로 검사한다.
  - 권한이 없으면 404로 응답해 존재 자체를 숨긴다.
  - 020 목록·상세 응답에 회의록 유무나 건수를 싣지 않는다.
- **R17 공개범위 지정**
  - 넓히거나 줄일 수 있는 사람은 부장급(DEPT_HEAD 이상)뿐이다. 등록자는 넓힐 수 없다.
  - 대상은 ACTIVE 사용자의 개별 사번이다. 역할 단위로 통째 지정하지 않는 것을 권장한다.
  - 종료일 지정을 권장한다. 회수는 즉시 반영한다.
  - 등록자(업로드 담당자)를 자동으로 포함할지는 결정이 필요하다. 권장은 '등록 후 N일 동안 수정 목적으로 포함하고 감사'다. 등록자는 이미 원본을 갖고 있다.
- **R18 감사**: `BoardMaterialAudit`와 같은 방식으로 남긴다.
  - 남길 행위: 목록·상세·원문 보기·요약 보기·업로드·수정·삭제·공개범위 변경.
  - DENIED·HIDDEN·INVALID 결과도 남긴다.
  - 읽기는 응답 **전에** 기록한다(fail-closed). 공개범위 변경은 같은 트랜잭션 안에서 변경 전·후 사번 목록을 남긴다.
  - 본문·가림 단어는 기록하지 않는다.
- **R19 감사 열람**: 부장과 시스템 관리자로 한정한다.
- **R20 운영 보호 장치(S3)**: 다음 중 하나를 택한다.
  - (a) 운영에서는 `Actor.isVerified()`가 참일 때만 회의록 API를 연다.
  - (b) 앞단 인증(NEXT 35) 전까지는 운영에서 기능 플래그로 끈다.
  - 둘 다 받아들이지 않으면 수용 위험으로 문서화한다.
- **R21 삭제·보존**: 삭제는 부장급만 한다. 보존 기간은 결정이 필요하다.
- **R22 다운로드·내보내기**: 1차에서는 원문 다운로드·내보내기를 두지 않는다.

**⑤ '대외비·참고용' 표지(S14)**: 아래 R23~R25.
- **R23 화면 표지**: 상세 화면 맨 위에 '대외비 · 참고용(음성 자동 변환이라 오인식이 있을 수 있음)'을 고정한다. 접거나 닫을 수 없게 한다.
  - 020 탭 머리와 목록 행에도 짧은 표지를 붙인다.
- **R24 인쇄**: `@media print`에도 표지를 넣는다. 열람자 사번과 열람 시각 워터마크를 권장한다(유출 추적용).
- **R25 캐시**: 회의록 API 응답에 `Cache-Control: no-store`를 붙인다.

## 4. 권장 조치 순서
1. Q-S1·Q-S2를 사용자에게 묻는다. 그 사이 개발은 병행하되, 운영에서 켜는 것은 답을 받은 뒤로 한다.
2. backend 설계에 R16~R20(권한·공개범위·감사·운영 보호 장치)과 R1~R7·R9~R15를 함께 넣는다.
3. design-reviewer 규격에 R11 안내, R13 표기, R23~R24 표지를 넣는다. frontend는 R8을 지킨다.
4. 설계안이 나오면 security가 한 번 더 본다. 구현 뒤에는 data-auditor가 실제 1건으로 가림 누락·오탐을 표본 검수한다.

## 5. 이관 메모
- [이관: 기획] 회의록의 기본 열람 대상을 결재 등급 기준(전산·예산 팀장 포함)으로 할지, 영업 계열 팀장·부장으로 할지 정한다. 등록자 자동 포함 여부와 보존 기간도 정한다. 기다리는 것: 없음. 근거: S9, R16·R17·R21.
- [이관: 기획→PM] Q-S1·Q-S2를 질문 장부에 매칭해 사용자 질문으로 올린다. 기다리는 것: 없음. 근거: S1·S2.
- [이관: 백엔드] R1~R7, R9~R22를 설계에 반영한다. 기존 코드 재사용은 다음과 같다.
  - `Pii.scanExternal`: 시간 예산과 함께 쓴다.
  - `BoardMaterialAudit`: fail-closed 방식을 따른다.
  - `InstitutionCsv.decode`: 관대한 대체 경로는 가져오지 않는다.
  - 기다리는 것: 기획의 열람 대상 결정. 근거: S3~S12.
- [이관: 프런트] 다음을 지킨다.
  - 원문·요약·검색 강조는 `textContent`로 그린다(R8).
  - 가림 단어는 POST 본문으로만 보낸다(R7).
  - 화자 이름 입력 칸을 두지 않는다(R14).
  - 표지와 인쇄 표지를 넣는다(R23·R24).
  - 탭 숨김은 보조 수단일 뿐이다. 서버가 404로 막는 것이 기준이다(R16).
  - 기다리는 것: 디자인 규격. 근거: S10·S13·S14.
- [이관: 데이터] 1차 구현 뒤 실제 회의 1건으로 표본 검수한다. 볼 것은 외부인 이름 누락, 성+직함 누락, 두 글자 이름 오탐, 수정 저장 때 재검사가 도는지다. 기다리는 것: 1차 구현. 근거: S4·S5.

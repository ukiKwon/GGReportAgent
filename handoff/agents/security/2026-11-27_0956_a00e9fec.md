## 3. 설계에 넣을 규칙(적용 조건)

**① 되돌아갈 화면(next) — R2·R9**
- 값은 화면 이름 하나뿐이다. 형식은 `^[a-z][a-z0-9-]{0,31}$`, 디코드는 1번만 한다.
- 고정 대응표(`Object.freeze(Object.create(null))` 또는 `Map`)에 `has`로 있을 때만 받는다. 대응표 값은 nav 항목 id(`soon:…` 같은 한글·콜론 id는 주소에 그대로 쓰지 않는다).
- `/`·`\`·`:`·`%`·공백·`.`이 들어 있거나 비어 있으면 버리고 시작화면(`homeId()`)으로 간다.
- 받은 값으로 `location.href`·`a.href`·`window.open`·`location.replace(next)`를 쓰지 않는다. 항상 `app.openNavItem(대응표[next])`로만 연다.
- 로그인 뒤 `findNavItem`이 null이면(그 역할에 안 보이는 화면) 조용히 시작화면으로 간다.
- next는 주소보다 메모리(또는 sessionStorage)에 두는 쪽을 권장한다. 주소에 둔다면 `#/login?next=prep` 형태로만 둔다.

**② 메뉴 권한 — R1·R5·R6·R7**
- 라우터 진입점은 `app.openNavItem(id)` 하나다. `tab-btn-*`.click()·`admin.showView`·`tab-btn-myinfo`를 주소에서 직접 부르지 않는다.
- 세션이 없으면 로그인 화면만 보인다. `/menus` 응답이 `settled`된 뒤에 주소를 해석한다(`applyHome`과 같은 문).
- 주소 라우팅은 화면 노출만 바꾸고 서버 경계는 바꾸지 않는다. 숨은 화면이 주소로 열려도 데이터는 서버 문지기에 막혀야 한다는 것을 전제로 둔다. 기존 구멍(R5·R6·자기신고)은 라우팅 작업 범위 밖이며 NEXT 35(SSO)에서 다룬다.

**③ 주소에 남기는 값 — R12**
- 화면 이름과 숫자·코드 ID만 남긴다. 기관명·사람 이름·사번·검색어·자유 서술은 넣지 않는다.
- 제안 건 ID처럼 내부 값은 꼭 필요할 때만 넣고, hash 쪽에 둔다.

**④ 주소 값으로 화면 그리기 — R8·R9**
- ID 조각은 형식 검사(예 숫자면 `^[0-9]{1,12}$`, 기관 ID 형식은 백엔드 확인 필요)를 통과한 것만 쓰고 길이 상한을 둔다.
- API 경로에는 `encodeURIComponent`로만 넣는다(`approvals.js:382`와 같은 방식).
- DOM에는 `textContent` 또는 `logic.esc`로만 넣는다. 선택자에 이어 붙이지 말고 `CSS.escape`를 쓰거나 `dataset` 비교로 고른다.
- 해석에 실패하면 예외를 내지 말고 시작화면으로 간다.

**⑤ 경로 방식일 때만 — R3·R4**
- 되돌림 조건은 모두 만족해야 한다: GET이고, `Accept`에 `text/html`이 있고, 마지막 마디에 점이 없고, **화면 이름 허용 목록의 앞머리(예 `/app/…` 하나로 모음)**와 일치할 것.
- "모르는 주소 전부"는 되돌리지 않는다. `/auth`·API 루트들·정적 폴더·`/error`·actuator(지금 의존성 없음 — 생기면 제외)는 절대 가로채지 않는다.
- 오류 응답(4xx/5xx)을 index.html로 바꾸지 않는다.
- forward 대상은 상수 `/index.html` 하나로 고정한다. 요청 경로로 파일을 찾지 않는다. `;`·`%2e`·`%5c`·`..`가 든 경로는 되돌림 대상에서 뺀다(`stripContext` 뒤에 판정).
- index.html에 `<base href>`를 넣거나 스크립트를 절대 경로로 바꾸고, WebLogic 컨텍스트 경로와 맞는지 확인한다.

**⑥ 로그아웃·뒤로 가기 — R10**
- 모든 주소 변경 처리(hashchange/popstate)의 첫 줄에서 `loadSession()`을 다시 확인한다. 없으면 `resetScreens()`를 하고 로그인 화면을 보인다.
- 로그아웃은 `location.replace('#/login')`(경로 방식이면 `history.replaceState`)로 현재 항목을 덮는다.
- `pageshow`에서 `event.persisted`면 세션을 다시 확인하고 화면을 초기화한다.
- 다른 탭 로그아웃 전파는 `storage` 이벤트로 받는다(권장, 기존 문제).
- index.html을 `no-store`로 바꾸는 것은 304 이점을 잃는 대신 bfcache를 줄인다. 브라우저별 효과는 확인 필요하므로 선택 사항으로 둔다.

## 4. hash/경로 방식 차이 — 한 줄 결론
**hash 방식은 서버 변경이 없고, 주소 값이 서버 로그와 Referer에 남지 않으며, API 이름 공간 충돌(R3)과 경로 탐색·상대 경로 문제(R4)가 없다. 보안 관점에서는 hash 방식을 권장한다.** 경로 방식은 ⑤의 조건을 모두 갖춰야 하고, API가 루트에 붙어 있는 지금 구조에서는 화면 주소를 별도 앞머리로 모으는 것이 전제다.

## 5. 권장 조치 순서
1. 설계 문서에 ①(next 허용 목록)과 ②(진입점은 `openNavItem` 하나, 세션·권한 응답 뒤 해석)를 필수 규칙으로 넣는다.
2. 방식 결정: hash면 ⑤를 생략하고, 경로면 ⑤를 서버 작업 범위에 넣는다.
3. ④·⑥을 구현 기준과 시험 항목에 넣는다(prototype 키, `javascript:`·`//`·`\` next, 로그아웃 후 뒤로 가기, 다른 탭).
4. 기존 위험 R5·R6·R11은 라우팅과 따로 NEXT 35·백엔드로 넘긴다.

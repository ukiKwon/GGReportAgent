## 4. 다음 작업 순서(정함)
**순서: ⑤ → ① → ⑥ → ③ → ② → ④ → ⑦.** 기능마다 "인터뷰 → 범위·규칙 → 시안 → 구현 → 검증 → 랜딩 장면 교체" 순서로 갑니다. 인터뷰는 한 번에 한 기능만 하고, 앞 기능이 다른 세션 때문에 막혔을 때만 다음 기능 인터뷰를 엽니다.

**첫 기능은 ⑤ '기관별 서술' 4칸 초안입니다.** 이유:
- 설계·보안이 이미 진행 중입니다.
- 서버는 새 파일 12개뿐이라 다른 세션과 겹치지 않습니다.
- Ollama 어댑터가 ⑥·③·②·④·⑦이 모두 쓰는 바닥이라 막힘을 푸는 효과가 가장 큽니다.
- 다만 랜딩이 약속한 '장마다'와 범위가 달라서 인터뷰를 먼저 해야 합니다.

**① 이 둘째인 이유**: LLM 없이 규칙으로만 하는 일이고, 인터뷰 몫이 문구 하나뿐이며, b3가 idle이라 `portal.js`가 곧 풀릴 가능성이 높습니다. ⑤ 화면이 6e S3a를 기다리는 동안 들어갑니다.

**⑥ 이 셋째인 이유**: ⑤의 서버 몫을 재사용하지만 `instsummary.js`가 6e 파일이라, ⑤ 화면과 같은 시점에 6e와 묶어 맞춥니다.

**뒤 넷(③→②→④→⑦)**: 사용자 자료가 필요 없는 것부터 갑니다. ③은 파일을 고치는 일이라 보안 설계가 큽니다. ②는 샘플, ④는 쪽수 자료를 다시 모아야 하고, ⑦은 Java 이관이 큽니다.

**⑤ 진행 단계**:
1. planner 초안 + 아래 ⓐ로 인터뷰.
2. 보안 결과 반영.
3. 인터뷰 답을 설계에 반영 — backend-dev(Opus, 프롬프트·칸 규칙만 보충).
4. backend-dev-write로 적용 → mvn(8080 확인) → security 적용본 확인.
5. design-reviewer 시안: 초안 표시·채우는 방식·최대 8분 기다림. 시안 먼저 원칙.

## 읽기 전용 조회문 (NEXT 125 · NEXT 114 ⑤)

데이터 값 검수가 아니라 SELECT 작성 건입니다. DB에는 접속하지 않았고, 아래 SQL은 DB에 돌려 보지 않았습니다. 기준은 DDL·매퍼 원문이고, 파일은 하나도 고치지 않았습니다.

### 근거 (표·칸 이름)
- INST_BID_TARGET은 043(기본 칸), 044(KIND_CD, 기본값 GOAL), 056(APPROVAL_REQ_ID·CARRY_FROM_NO·CARRY_BASIS_CD), 061(WATCH_EMP_NO), 063(AIM_RANK_CD) 순으로 만들어집니다.
  - 기본 칸은 INSTITUTION_ID·TARGET_NO·REV_NO·ACTION_CD·TARGET_YEAR(044부터 NULL 허용)·TAG_CD(063부터 NULL 허용)·CANCEL_REASON_CD입니다.
- "살아 있음" 판정은 BidTargetMapper.xml의 `latest`(같은 INSTITUTION_ID·TARGET_NO에서 더 큰 REV_NO가 없음)와 `ACTION_CD<>'CANCEL'`입니다.
- 결재 표는 056의 INST_BID_TARGET_REQ_ITEM(REQ_ID, INSTITUTION_ID, ITEM_NO, OP_CD …)이고, 상태는 APPROVAL_REQUEST.STATUS(012: PENDING/APPROVED/REJECTED/CANCELLED)에 있습니다. 매퍼의 `countPendingByInst`·`selectPendingItems`가 같은 조인을 씁니다.
- BID_CASES의 기관 칸은 INSTITUTION_ID입니다(001).
- "제안 준비" 표 이름은 BID_PREP입니다(024, BID_CASE_ID 하나에 한 행). PrepMapper.xml이 "진행 중"으로 보는 STATE_CD는 CONFIRMED, OPEN_PENDING, IN_PROGRESS, APPROVAL_PENDING, WRITABLE, WRITING 6개입니다. CANCELLED는 제외입니다.
  - 매퍼에서 "종료"로 보이는 별도 상태 코드는 찾지 못했습니다. 024는 상태 7종을 두고, 그 뒤 마이그레이션(048·054·062)에서는 STATE_CD 값 변경을 찾지 못했습니다. 이 부분은 확인 못 한 항목이 아니라 "코드 존재 안 함"으로 읽었습니다.

### SQL (한 파일로 이어 붙여 실행 가능)

```sql
-- ===== 공통: 살아 있는 최신 목표 행 = 최대 REV_NO 이고 ACTION_CD<>'CANCEL' =====

-- ① 살아 있는 목표 행의 KIND_CD / TARGET_YEAR / AIM_RANK_CD별 건수
SELECT b.KIND_CD, b.TARGET_YEAR, COALESCE(b.AIM_RANK_CD,'(비어 있음)') AS AIM_RANK_CD, COUNT(*) AS CNT
  FROM INST_BID_TARGET b
 WHERE b.ACTION_CD <> 'CANCEL'
   AND NOT EXISTS (SELECT 1 FROM INST_BID_TARGET n
                    WHERE n.INSTITUTION_ID = b.INSTITUTION_ID AND n.TARGET_NO = b.TARGET_NO AND n.REV_NO > b.REV_NO)
 GROUP BY b.KIND_CD, b.TARGET_YEAR, COALESCE(b.AIM_RANK_CD,'(비어 있음)')
 ORDER BY b.KIND_CD, b.TARGET_YEAR, 3;

-- ②-a 첫 REV(REV_NO=1)가 ACTION_CD='CARRY'인 목표의 KIND_CD별 건수 (현재 살아 있는지 여부로 쪼갬)
SELECT f.KIND_CD,
       CASE WHEN l.ACTION_CD = 'CANCEL' THEN '현재 취소됨' ELSE '현재 살아 있음' END AS NOW_STATE,
       COUNT(*) AS CNT
  FROM INST_BID_TARGET f
  JOIN INST_BID_TARGET l
    ON l.INSTITUTION_ID = f.INSTITUTION_ID AND l.TARGET_NO = f.TARGET_NO
   AND l.REV_NO = (SELECT MAX(x.REV_NO) FROM INST_BID_TARGET x
                    WHERE x.INSTITUTION_ID = f.INSTITUTION_ID AND x.TARGET_NO = f.TARGET_NO)
 WHERE f.REV_NO = 1 AND f.ACTION_CD = 'CARRY'
 GROUP BY f.KIND_CD, CASE WHEN l.ACTION_CD = 'CANCEL' THEN '현재 취소됨' ELSE '현재 살아 있음' END;

-- ②-b 같은 목표의 기관 목록 (LIMIT 50)
SELECT f.INSTITUTION_ID, i.NAME_KO, f.TARGET_NO, f.KIND_CD, f.TARGET_YEAR, f.CARRY_FROM_NO, f.CARRY_BASIS_CD,
       l.ACTION_CD AS LATEST_ACTION, l.CANCEL_REASON_CD AS LATEST_CANCEL_REASON, f.SAVED_AT AS CARRIED_AT
  FROM INST_BID_TARGET f
  JOIN INST_BID_TARGET l
    ON l.INSTITUTION_ID = f.INSTITUTION_ID AND l.TARGET_NO = f.TARGET_NO
   AND l.REV_NO = (SELECT MAX(x.REV_NO) FROM INST_BID_TARGET x
                    WHERE x.INSTITUTION_ID = f.INSTITUTION_ID AND x.TARGET_NO = f.TARGET_NO)
  LEFT JOIN INSTITUTIONS i ON i.INSTITUTION_ID = f.INSTITUTION_ID
 WHERE f.REV_NO = 1 AND f.ACTION_CD = 'CARRY'
 ORDER BY i.NAME_KO, f.TARGET_NO
 LIMIT 50;

-- ②-c CANCEL_REASON_CD='CARRY_REVOKED' 행 수 (전체 REV 행 수 / 서로 다른 목표 수)
SELECT COUNT(*) AS CARRY_REVOKED_ROWS,
       COUNT(DISTINCT CONCAT(INSTITUTION_ID,'#',TARGET_NO)) AS CARRY_REVOKED_TARGETS
  FROM INST_BID_TARGET
 WHERE CANCEL_REASON_CD = 'CARRY_REVOKED';

-- ③-a BID_CASES가 2건 이상인 기관 수
SELECT COUNT(*) AS INST_WITH_2PLUS_CASES
  FROM (SELECT INSTITUTION_ID FROM BID_CASES GROUP BY INSTITUTION_ID HAVING COUNT(*) >= 2) t;

-- ③-b 그 기관 목록 (LIMIT 50, 건수 많은 순)
SELECT c.INSTITUTION_ID, i.NAME_KO, COUNT(*) AS CASE_CNT,
       MIN(c.TITLE) AS ANY_TITLE_MIN, MAX(c.TITLE) AS ANY_TITLE_MAX
  FROM BID_CASES c
  LEFT JOIN INSTITUTIONS i ON i.INSTITUTION_ID = c.INSTITUTION_ID
 GROUP BY c.INSTITUTION_ID, i.NAME_KO
HAVING COUNT(*) >= 2
 ORDER BY CASE_CNT DESC, i.NAME_KO
 LIMIT 50;

-- ④ 기관별 "진행 중" 제안 준비(BID_PREP) 건 수가 2 이상인 기관 (진행 중 = CANCELLED 아님, 매퍼의 6개 상태)
SELECT p.INSTITUTION_ID, i.NAME_KO, COUNT(*) AS ACTIVE_PREP_CNT,
       GROUP_CONCAT(p.STATE_CD ORDER BY p.CONFIRMED_AT SEPARATOR ',') AS STATES
  FROM BID_PREP p
  LEFT JOIN INSTITUTIONS i ON i.INSTITUTION_ID = p.INSTITUTION_ID
 WHERE p.STATE_CD IN ('CONFIRMED','OPEN_PENDING','IN_PROGRESS','APPROVAL_PENDING','WRITABLE','WRITING')
 GROUP BY p.INSTITUTION_ID, i.NAME_KO
HAVING COUNT(*) >= 2
 ORDER BY ACTIVE_PREP_CNT DESC, i.NAME_KO
 LIMIT 50;

-- ⑤-a 목표 변경 결재 중 대기(PENDING) 건수와 항목 수
SELECT COUNT(DISTINCT r.REQ_ID) AS PENDING_REQS,
       COUNT(*)                 AS PENDING_ITEMS,
       COUNT(DISTINCT x.INSTITUTION_ID) AS PENDING_INSTS
  FROM INST_BID_TARGET_REQ_ITEM x
  JOIN APPROVAL_REQUEST r ON r.REQ_ID = x.REQ_ID
 WHERE r.STATUS = 'PENDING';

-- ⑤-b 대기 항목의 동작(OP_CD)·종류별 분포 (LIMIT 50)
SELECT x.OP_CD, x.BASE_KIND_CD, x.BASE_YEAR, x.TO_YEAR, COUNT(*) AS ITEM_CNT
  FROM INST_BID_TARGET_REQ_ITEM x
  JOIN APPROVAL_REQUEST r ON r.REQ_ID = x.REQ_ID
 WHERE r.STATUS = 'PENDING'
 GROUP BY x.OP_CD, x.BASE_KIND_CD, x.BASE_YEAR, x.TO_YEAR
 ORDER BY ITEM_CNT DESC
 LIMIT 50;

-- ⑤-c 대기 항목이 걸린 기관 목록 (LIMIT 50)
SELECT x.REQ_ID, x.INSTITUTION_ID, i.NAME_KO, x.ITEM_NO, x.OP_CD, x.TARGET_NO, x.TO_YEAR, x.REQUESTER_EMP_NO, r.CREATED_AT AS REQ_CREATED_AT
  FROM INST_BID_TARGET_REQ_ITEM x
  JOIN APPROVAL_REQUEST r ON r.REQ_ID = x.REQ_ID
  LEFT JOIN INSTITUTIONS i ON i.INSTITUTION_ID = x.INSTITUTION_ID
 WHERE r.STATUS = 'PENDING'
 ORDER BY x.INSTITUTION_ID, x.REQ_ID, x.ITEM_NO
 LIMIT 50;

-- ⑥(보조) 같은 기관에 살아 있는 GOAL 목표가 2건 이상인 곳 = 옮길 때 중복 목표 위험
SELECT b.INSTITUTION_ID, i.NAME_KO, COUNT(*) AS LIVE_GOALS,
       GROUP_CONCAT(CONCAT(b.TARGET_YEAR,'/',COALESCE(b.AIM_RANK_CD,'-')) ORDER BY b.TARGET_NO SEPARATOR ', ') AS YEAR_RANK
  FROM INST_BID_TARGET b
  LEFT JOIN INSTITUTIONS i ON i.INSTITUTION_ID = b.INSTITUTION_ID
 WHERE b.KIND_CD = 'GOAL' AND b.ACTION_CD <> 'CANCEL'
   AND NOT EXISTS (SELECT 1 FROM INST_BID_TARGET n
                    WHERE n.INSTITUTION_ID = b.INSTITUTION_ID AND n.TARGET_NO = b.TARGET_NO AND n.REV_NO > b.REV_NO)
 GROUP BY b.INSTITUTION_ID, i.NAME_KO
HAVING COUNT(*) >= 2
 ORDER BY LIVE_GOALS DESC, i.NAME_KO
 LIMIT 50;
```

### 결과 해석 가이드
- **① 살아 있는 행 규모**: 총합이 NEXT 125에서 옮길 자료의 기본 규모입니다.
  - KIND_CD가 GOAL인 행이 0이면, 옛 GOAL을 옮기는 처리와 그에 대한 질문이 필요 없습니다. WATCH만 남은 경우 WATCH는 TARGET_YEAR가 NULL이고 WATCH_EMP_NO(담당자)에 묶여 있으니 따로 다룹니다.
  - AIM_RANK_CD가 "(비어 있음)"인 GOAL 행은 063 이전부터 있던 행입니다. 1금고/2금고를 알 수 없으므로 값을 추정해 채우지 말고 비어 있음으로 보고합니다.
  - TARGET_YEAR가 여러 해에 걸쳐 있으면 해마다 옮길지를 정해야 합니다.
- **② 자동 이월 행(NEXT 114 ⑤)**
  - ②-a에서 KIND=GOAL이고 "현재 살아 있음"이 0이면 옛 이월 행은 이미 정리된 것입니다.
  - ②-a가 0건이고 ②-c(CARRY_REVOKED)가 0이면 114 ⑤는 해당 자료가 없다고 닫을 수 있습니다.
  - CARRY_REVOKED는 056이 만든 코드(이름 "이월 자동 취소", ENABLED=0)입니다. 숫자가 있으면 "이월했다가 자동 취소된" 이력이 이미 있다는 뜻입니다. 이 행들은 삭제·수정하지 않고 보존 대상으로 보고합니다(INSERT만 하는 설계라 UPDATE·DELETE 문장이 없습니다).
  - ②-a의 "현재 살아 있음"이 0보다 크면 ②-b 목록을 사용자에게 확인합니다. KIND=WATCH인 이월 행이 있으면 위 표의 의미(관심 기관)와 다르므로 따로 봅니다.
- **③ BID_CASES 2건 이상 기관**
  - 이 기관들은 "1·2금고 분리 공고"일 가능성이 있습니다. 제목(ANY_TITLE_MIN/MAX)이 서로 다르면 별개 입찰 건입니다. 반대로 같은 공고의 중복 반입이면 SOURCE_SLUG와 NOTICE_ID가 같은지 따로 봅니다(UNIQUE 키가 있어 같은 값으로는 이중 반입이 안 됩니다).
  - 한 기관에 한 건뿐인 기관은 "기관 = 입찰 건"이라 옮길 때 1:1로 대응됩니다.
  - ③이 0기관이면 한 줄 = 입찰 건으로 바꿔도 1:1로 옮길 수 있습니다.
- **④ 진행 중 제안 준비가 2건 이상인 기관**: 한 기관에 입찰 건이 여럿 동시에 진행 중이라는 뜻입니다. 이 기관은 목표 한 건(기관 단위)과 준비 여러 건의 연결 방식을 정해야 합니다. 0이면 연결 모호성이 없습니다.
  - ④의 건수는 ③의 BID_CASES 2건 이상 기관 중 진행 중인 곳과 겹쳐서 보면 됩니다.
- **⑤ 대기 결재**: ⑤-a의 PENDING_REQS가 0이면 옮기는 도중 결재가 끊길 위험이 없습니다.
  - 0보다 크면 옮기기 전에 그 결재를 먼저 처리하거나 옮기는 시점을 미뤄야 합니다. 결재 항목은 BASE_REV_NO·TARGET_NO로 목표의 특정 REV를 가리키므로, 옮겨서 REV 번호나 키가 바뀌면 승인 시점에 맞지 않을 수 있습니다.

### 옮길 때 위험
1. **대기 결재**: 결재 항목이 TARGET_NO·BASE_REV_NO(그 시점의 REV)를 붙잡고 있습니다. PENDING이 있는 채로 목표 키를 바꾸면 승인 시 어긋납니다(⑤).
2. **중복 목표**: 같은 기관에 살아 있는 GOAL이 둘 이상이면(⑥) "한 줄 = 입찰 건"으로 바꿀 때 어느 쪽이 어느 입찰 건에 붙는지 정해야 합니다. 기관 단위 저장이 입찰 건 단위로 바뀌면 한 기관의 GOAL이 1:N으로 갈라집니다.
3. **옛 REV 이력 보존**: INST_BID_TARGET은 INSERT 전용 이력 표입니다. 옮긴다면 기존 행을 고치는 대신 새 REV나 새 표를 쓰는지 백엔드가 정해야 하고, 이 보고서는 설계하지 않습니다.
4. **AIM_RANK_CD 비어 있음**: 063 이전 행은 비어 있어 1금고/2금고를 알 수 없습니다. 추정해 채우지 않습니다.
5. **CARRY 행**: 첫 REV가 CARRY이고 이미 CARRY_REVOKED로 취소된 목표를 새 구조로 되살리지 않도록 ②-c의 대상은 제외합니다.
6. **실행 환경**: 모두 읽기 전용 SELECT입니다. 표 이름은 MySQL 미러 기준이고, 별칭 `AIM_RANK_CD` 열 이름이 "(비어 있음)" 문자열과 섞이므로 정렬 시 3번째 열 번호로 정렬했습니다. 위 SQL은 MySQL 8 기준(GROUP_CONCAT 사용)입니다.

### 이관 메모
- [이관: 백엔드] 매퍼에서 "종료"라는 BID_PREP 상태가 없으므로 ④의 "취소·종료 아닌" 조건은 CANCELLED 제외로 해석했습니다. 종료 상태가 따로 생긴다면 알려 주세요(024 이후 STATE_CD 변경 DDL은 찾지 못했습니다).
- [이관: 기획] ③과 ④ 결과를 기준으로 "한 기관 = 목표 1건"과 "한 줄 = 입찰 건"의 대응 규칙을 정해야 합니다. 값 규칙 설계는 하지 않았습니다.

## 3. 용어 정의 후보
**'전체 팀'**
- ⓐ 그 건의 세 팀 지정 담당자 + 세 팀 팀장 (권장)
  - 예: 노원구 건이면 노원 담당 영업·전산·예산 3명과 팀장 3명이 받는다.
- ⓑ 세 팀 역할의 쪽지함. 지금 코드가 이렇게 동작한다.
  - 영업팀 전원(팀장·부장 포함), 전산팀 전원, 예산팀 전원이 받는다. 다른 기관을 맡은 사람도 받는다.
  - 쪽지가 팀당 한 건이라서 한 사람이 읽으면 팀 전체에 '읽음'으로 바뀐다(NEXT 27 미결 '단체 쪽지 사람별 읽음').
- ⓒ ⓐ + 영업부장
  - 부장이 의견 단계부터 본다. 다만 부장은 마지막에 어차피 다시 보므로 중복이다.

**'문자'**
- ⓐ 시스템 쪽지(기존 쪽지함 + 화면 배지) (권장)
- ⓑ 실제 휴대폰 SMS
  - 저장소에 SMS 연동 코드가 없다.
  - 폐쇄망에서 사내 SMS 시스템 연동, 휴대폰 번호(개인정보) 보관, 외부 발송 승인이 필요하다.
- ⓒ 둘 다. 쪽지는 지금 만들고, SMS는 사내 연동 가능 여부를 확인한 뒤 별도 항목으로 한다.

**'디자인 작업 완료'**
- 결재 제출이 아니라 "이번 회차 디자인본을 다 같이 보라"는 공지다. 회차를 매긴다(1차본, 2차본 …). 같은 기관에서 여러 번 반복되기 때문이다.

## 4. 상태 흐름(권장안)과 기존 재사용·빈 곳
```
디자인 작업 중 ──[디자인 작업 완료](디자이너)──▶ 의견 받는 중(n차본)
   ▲                                              │ 세 팀: [의견 남기기] / [확인함]
   └──[다시 수정](디자이너, 결재 없음)──────────────┤
                                                  │ 영업팀장: [영업 검토 완료·부장께 올림]
                                                  ▼
                                    영업부장 검토 ──[제출본 확정]──▶ 제출본 확정
                                          └─[돌려보내기(사유)]─▶ 디자인 작업 중
```

| 단계 | 재사용(코드에 있음) | 빈 곳(새로 필요) |
|---|---|---|
| 작업 시작 조건 | 세 팀 `2차완료` 확인(`requireTeamsDone`) | 없음 |
| [디자인 작업 완료] | 제출 동작·`1차완료` 상태, 세 팀 쪽지 발송 | 화면 이름표를 '의견 받는 중'으로. 회차 번호. 받는 사람을 그 건 담당자 중심으로(3절 ⓐ) |
| 의견 남기기 | 작업별 기록(MESSAGES, 작성자·시각 있음), 쪽지에 작업 번호 연결 | 세 팀이 남기는 '의견' 종류와 회차 연결. 디자이너가 보는 의견 목록. '확인함(의견 없음)' 표시 |
| [다시 수정] | 반려 시 `작성중`으로 되돌리는 동작 | **결재자가 아니라 디자이너 본인이** 반려 없이 `의견 받는 중 → 작업 중`으로 돌리는 동작(지금은 영업팀장 반려로만 가능). 다시 완료하면 n+1차본 알림 |
| 영업 검토 끝 | 영업팀장 승인 = 상신(`2차완료`, 영업부장에게 결재요청) | 버튼 이름. 상신 뒤에는 디자이너가 [다시 수정]을 못 하게 막기 |
| [제출본 확정] | 영업부장 최종 결재 → `최종완료`, 반려 → `작성중` | 화면 이름표를 [제출본 확정]으로 |
| 알림 | NotificationCommandService | 담당자 개인 앞 발송. 단체 쪽지를 사람별로 읽음 처리 |

- 상태 값(`1차완료` 등)은 화면·골든·DB가 쓰는 계약이다. 그래서 **값은 그대로 두고 화면 이름표만 바꾸는 쪽**을 권한다. 판단은 개발자 몫이다.
- 의견은 결재가 아니므로 '의견이 다 모일 때까지 영업 검토를 막는' 규칙은 두지 않는다. 대신 누가 확인했는지와 누가 아직인지를 보여 준다(팀 결정, 되돌리기 쉬움).

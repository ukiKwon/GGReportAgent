## 2. 요구 요약
**지금 코드의 실제 흐름(확인한 것)**
```
목표 등록(팀장 결재*) ─┐
지도·공고 현황 ────────┴→ [제안 확정] 결재 없음 → CONFIRMED(확정됨, 과제 없음)
  → [개설 신청] 팀장 결재 → IN_PROGRESS(담당자 배정 + 사전준비 과제가 이때 처음 생김)
  → [사전준비 승인] 결재(코드는 영업부장, NEXT 111에서 팀장으로 바꿀 예정) → WRITABLE
  → [작성하기] → WRITING
```
*목표 넣기·연도·주 담당만 결재입니다. 영업부장은 바로 바꿀 수 있고, 결재를 끄는 스위치도 있습니다(BidTargetService 84·312).
- 결재 횟수: 바로 확정 2회(개설 + 사전준비 승인), 목표를 거치면 3회(목표 + 2회).
- **공고 확인은 화면에만 있습니다.** 서버 `confirm()`은 공고도 목표 여부도 보지 않습니다(NEXT 94 ④에서 이미 지적).

**11-19 예외는 4번 문제를 임시로 메운 것이 맞습니다.** Q-2026-11-19-22 원문이 "공고가 난 기관에만 버튼이 보여서 수익성 분석·이사회 자료 준비도 공고 뒤에야 시작돼요"였고, 답으로 "올해 목표 기관만 공고 전 확정"을 받았습니다. 그래서 지금은 올해 목표 기관만 공고 전에 확정 → 개설 → 사전준비를 밟을 수 있습니다. 관심 기관이나 목표 밖 기관은 공고 전에 사전준비를 시작할 길이 없습니다. 근본 원인은 "공고가 났는지 보는 자리가 단계 맨 앞([제안 확정])에 있다"는 것입니다.

- 확정된 전제(사용자 11-24 밤): 사실 1~5, [제안 확정]에는 결재 없음, 목표를 거치면 결재가 1건 더 생기는 것은 받아들임, 개설 결재 생략은 보류(Q-92).
- 새로 정할 것: 공고 확인 자리를 어디로 옮길지, '제안 확정'이라는 단계를 남길지.

## 3. 용어 정의 후보
- **사전준비 시작**: ⓐ지금의 [제안 확정]과 [개설 신청]을 합친 한 번의 동작(권장안) ⓑ지금의 [제안 확정] 이름만 바꾸기.

4. 사실 2·3·5를 그대로 지킵니다(목표 결재, 개설 = 시작 결재, 작성 전 결재).

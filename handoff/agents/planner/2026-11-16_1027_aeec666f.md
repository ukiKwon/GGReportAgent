## 3. 용어·데이터 의미 정의 후보

### '공고 1건'(공고 현황의 행)
| 후보 | 정의 | 예 |
|---|---|---|
| **R1 입찰 회차**(권장) | 한 기관이 금고를 한 번 새로 뽑는 일. 재공고는 그 행 안의 이력(1차·2차 공고)으로 둔다 | 마포구 2027 금고 지정 1행 = 1차 공고 → 유찰 → 재공고 |
| R2 공고문 1건 | 공고번호 하나가 한 행. 재공고는 새 행 | 마포 1차와 마포 재공고가 각각 한 행 |
| R3 R1 + 공고 전 경과 건 | 아직 공고가 확인되지 않았어도 예정일이 지난 회차는 '공고 확인 필요' 행으로 들어온다 | 예정일 10-01, 공고 미확인 → 행 있음, 상태 칸 비어 있음 |

- R2로 하면 '지연·재공고 대기' 상태를 붙일 대상 공고가 없습니다.
- NEXT 30 2단계도 이미 '회차(예정일)별 상태 저장'으로 잡혀 있습니다.
- **그래서 R1+R3을 권장합니다.** 이렇게 해야 '경과 건 강조 패널'을 같은 화면에 둘 수 있습니다.

### 상태
두 층으로 나누는 것을 권장합니다.
- **자동 표시(계산)**: 데이터에서 계산합니다. `logic.noticeState`가 이미 계산하는 것과 같습니다. 담당자는 고칠 수 없습니다.
  - 접수 중 D-n
  - 마감 지남(결과 확인)
  - 마감일 미확인
  - 예정일 경과 D+n
- **담당자 판정**: 확정된 3종입니다. 영업팀이 기록합니다.

### 담당자명
| 후보 | 뜻 | 입력 방식 |
|---|---|---|
| ⓐ 처리자 | 마지막으로 기록한 사람 | 로그인 사용자로 자동 |
| ⓑ 기관 담당 영업직원 | 그 기관을 맡은 사람 | 별도 입력 |
| ⓒ 둘 다 | ⓐ와 ⓑ를 모두 둔다 | ⓐ 자동 + ⓑ 입력 |

사용자 11-09 ⑥의 '담당자명'이 이 중 어느 것인지는 모릅니다. 확인이 필요합니다.

## 4. 선택지 비교와 권장안

### 4-1 경계 규칙 (권장)
- **현황판에 속하는 것**: "아직 공고는 없지만 올 것 같은" 기관입니다. 예정일 기준 다가오는 목록, 월별 막대, 기관 상세·기관장, [제안 확정].
- **공고 현황에 속하는 것**: "공고가 실제로 났거나, 났어야 하는데 확인이 필요한" 회차입니다.
  - 공고 정보, 자동 표시, 담당자 판정·의견·이력, 경과 강조 패널이 여기 있습니다.
  - 상태 입력은 이 화면에서만 합니다.
- **[제안 확정]은 현황판에만 둡니다.**
  - 공고 현황에서는 "기관 상세에서 제안 확정" 링크로 보냅니다.
  - 감사 기록의 '어느 화면·어느 버튼'이 한 곳으로 유지됩니다(bid_board/confirm).
- **낙찰·유찰 결과는 '입찰 결과 등록'(꼭 필요 메뉴)에 둡니다.** 공고 현황에는 결과를 읽기 전용으로 보여 주고 결과 등록 화면으로 링크합니다.

### 4-2 현황판의 '공고 난 기관' 띠·경과 묶음
| 선택지 | 바뀌는 곳 | 비용 | 위험 | 되돌리기 |
|---|---|---|---|---|
| **A 유지 + 상태 읽기 표시 + 링크**(권장) | dashboard.js 카드와 묶음 행에 담당자 판정 칩(읽기)과 '공고 현황에서 보기' 링크 추가. 묶음 머리에 '미처리 n곳' | 작음 | 같은 회차가 두 화면에 보임. 입력은 한 곳이라 기록이 갈라지지 않음 | 쉬움 |
| B 요약 숫자 + 링크로 축소 | 띠는 'n곳' 타일 하나, 경과 묶음은 '경과 n곳 · 미처리 m곳 → 공고 현황' 한 줄로. 화면 테스트와 디자인 이력 영향 | 중간 | 11-11·11-12에 확정된 결정(묶음 기본 펼침, 띠 승인)을 뒤집음. 제안 확정 판단에 필요한 맥락이 한 번 더 이동해야 보임 | 중간 |
| C 현황판에서 제거 | 띠와 묶음 삭제 | 작음 | 확정을 뒤집음. 현황판이 '예측'만 남아 첫 화면에서 진행 중인 공고를 놓침(성공 기준 '임박을 한눈에'와 충돌) | 쉬움 |

- **권장은 A입니다.**
  - 확정 결정을 다시 열지 않습니다.
  - 띠와 묶음은 '보기'로만 남고 '기록'은 공고 현황 하나로 모입니다.
  - B는 사용자가 원할 때만 고려하는 선택지입니다.
- 1단계에서 팀이 정한 경과 패널 위치(전국 지도 화면)는 공고 현황 화면이 생기면 그쪽으로 옮깁니다. 사용자 11-09 ②와 맞습니다. 지도 쪽 패널을 남길지는 디자인 판단으로 넘깁니다.

## 5. 공고 현황 화면 범위 초안

**행**
- R1 입찰 회차 + R3 공고 전 경과 회차
- 화면 맨 위에 '경과·확인 필요' 강조 패널을 두고, 그 아래에 전체 목록을 둡니다.

**열 (읽기)**
- 기관(종류·지역)
- 회차 기준(약정 만료 추정인지, 확정 공고인지)
- 공고일, 공고번호·원문 링크(인터넷 PC에서 열림), 접수 기간
- 자동 표시
- 제안 진행(제안 확정 여부·사전준비 단계, 링크)
- 입찰 결과(입찰 결과 등록에서 읽기, 링크)
- 최근 처리자·처리 일시
- 출처: 공고 정보는 sources가 필수입니다(원칙 1).

**입력 칸 (영업팀)**
- 상태: 3종
- 담당자 의견: 공고 종료·지연 대기일 때 필수(NEXT 30 팀 기본값)
- 다음 확인일: 지연 대기일 때 필수(팀 기본값)
- 담당자명: 3절 후보 중 하나
- 영업팀이 공고를 직접 등록할 수 있게 할지(수집기가 못 잡은 공고)는 질문으로 둡니다.

**권한**
- 수정은 영업팀 전원입니다(NEXT 30, 10-30 확정). 다른 팀은 열람만 합니다.

**결재**
- 공고 상태 기록은 결재 대상이 아닌 것으로 권장합니다. 사실 기록이고 되돌리기 쉬우며 변경 이력이 남기 때문입니다.
- 다만 '결재 끝난 건 감사 기록' 원칙과 같은 형식으로 저장 행위마다 누가·어느 화면·어느 버튼을 남기고, 이전 값도 남깁니다.
- 제안이 결재 중이거나 끝난 회차를 '공고 종료'로 바꿀 때 막을지, 경고만 할지는 질문 Q4로 둡니다.

**두 화면 링크**
- 현황판의 띠·경과 행 → 공고 현황의 그 회차
- 공고 현황 행 → 현황판 기관 상세([제안 확정])
- 로그인 경과 팝업의 '전체 보기' → 공고 현황 경과 패널
- 사이드바 미처리 배지 → 공고 현황

**뒤로 미룸**
- 낙찰·유찰 입력(입찰 결과 등록 몫)
- 공고 자동 수집 화면(별도 메뉴)
- 알림

  - ⓑ 여기서 '낙찰·유찰'을 상태로 함께 고른다

  - ⓐ 마지막으로 기록한 사람(자동)
  - ⓑ 그 기관을 맡은 영업 직원(직접 입력)

  - ⓒ 팀장만 바꿀 수 있음

## 7. 현업 확인 질문 문안 (11-20 요구사항 자료용)

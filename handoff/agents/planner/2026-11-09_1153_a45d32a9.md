**어느 단계에도 안 맞는 메뉴**
- 이사회 자료: 9단계 문서에 없다. 업무 위치는 모름(5절 Q3).
- 영업 메모·활동 이력, 일정·마감 알림: 단계를 가로지르는 상시 업무.
- 대화·지식 검색: 공통 도구인데 '제안서 작성'에만 붙어 있다.
- 시스템 관리: 지원 메뉴라 문제없음.

**같은 일을 하는 중복·겹침**
- 결재가 4곳에 흩어져 있다: 결재함 / 진행 현황 결재 3곳 / 작업함 팀 승인(`tasks/approve`) / 이사회 상신(예정).
- 소통이 4곳이다: 대화 / 쪽지함 / 작업함 메시지 / '요청 이력·소통'(준비중).
- 팀 배정 메뉴가 둘이다: '팀원 배정 요청·일정'과 '팀원 지정·진행 알림'.
- 검토 메뉴가 둘이고 8단계와도 겹친다: '질의사항 정리·내부 검토'와 '검토 의견·대응 방향'.
- 협약이 양 끝에 갈라져 있다: '기관 이력·협약 현황'(첫 묶음)과 '협약 등록·사후관리'(끝 묶음). 같은 협약 데이터다.
- 진행 현황 3중: 제안서 진행 현황 / 공용 보고서 R2(NEXT 34) / 기관 상세(NEXT 33).
- NEXT 30이 연결하라고 한 '입찰 공고 현황' 화면은 사이드바에 없다. '공고 검색'·'공고 자동 수집'과 겹칠 후보다.

### ③ 일관성·연관성이 없다고 느끼실 만한 지점 후보

1. **묶음 이름의 기준이 섞여 있다.** 대상(기관 현황·입찰 공고), 행위(제안팀 구성·제안서 작성), 상태(진행·승인), 단계(제출·결과)가 한 목록에 있다.
2. **"구현된 것 위로" 정렬이 업무 순서를 깬다.** 영업팀에게는 기관 현황 → 제안서 작성 → 제안 진행·승인 → 입찰 공고 → 제안팀 구성 → 제출·결과 순으로 보인다. 공고가 작성 뒤에 나온다(`nav.js` 89~93행).
3. **일이 일어나는 화면과 메뉴 소속이 다르다.** 참여 결정·결재·작성물 업로드가 모두 '제안서 진행 현황'과 '작업함' 안에 있다(②의 어긋남 4건).
4. **팀마다 보이는 메뉴의 근거가 흐리다.** 전산·예산팀은 자기 앞으로 올 '기술·데이터 지원 요청'을 볼 수 없다. 최종 결재자(영업부장)는 진행 현황이 꺼져 있다.
5. **화면 이름과 권한 표 이름이 다르다.** 워크플로/제안서 진행 현황, 대화/대화(질의), 지식/지식 검색, 권한관리/시스템 관리 4화면(NEXT 32 ⓐ). 메뉴 관리 화면에서 다른 이름이 보인다.
6. **키 하나에 다른 일이 붙어 있다.** `tasks` 키가 작업함과 이사회 자료를 함께 묶는다. 실제로 동작하는 이사회 자료가 '준비중' 꼴로 정의돼 있다.
7. **기관이라는 축이 메뉴를 잇지 못한다.** 제안 1건은 기관 1곳(NEXT 33)인데, 기관 상세 허브가 없어 같은 기관의 공고·진행·대화·결과가 메뉴마다 따로 떨어져 있다.
8. **LLM이 붙기 전에는 '제안서 작성' 묶음의 실동작 메뉴 두 개(지식 검색·대화)가 내부망에서 비어 있다.** 업무 서비스 우선 방침과 어긋난다.

## 6. DB 관점 (FK 없는 기준)

### 6-1. 지금 마이그레이션 방식과 회사 기준의 차이

**현재 방식**
- Oracle이 정본, MySQL이 미러이고 같은 커밋에서 같이 고친다(`db/README.md`).
- **FK를 의도적으로 실제로 걸고 있다**(README ② "외래키를 실제로 건다").
- Oracle 기준 FK 18개:

| 파일 | FK |
|---|---|
| 001 | `BID_CASES→INSTITUTIONS`, `TASKS→BID_CASES`, `MESSAGES→TASKS`, `VECTORS→CHUNKS` |
| 006 | `ORCH_RUN→INSTITUTIONS`, `ORCH_STEP→ORCH_RUN` |
| 008 | `USER_MENU_PERMS→USERS` |
| 010 | `USERS.APPROVER→USERS` |
| 012 | 결재 대결·요청자·단계 4개 |
| 014 | 이사회 양식 6개 |

- MySQL도 같은 FK를 건다.
- 코드 값은 CHECK 10개로 DB가 강제한다:
  - 결재 등급(`NONE/TEAM_LEAD/DEPT_HEAD/EXECUTIVE`)
  - 사용자 상태(`ACTIVE/LOCKED/RETIRED`)
  - 결재 요청·단계 상태, 결재 종류(`LINE/ADMIN`)
  - 양식 상태(`ACTIVE/ARCHIVED`) 등
- 업무 상태값(공고 참여 상태 '검토중'…'제출완료', `TASKS.STATUS`, `ORCH_RUN.STATUS`)은 CHECK도 코드 테이블도 없이 코드 안의 문자열이다.

**회사 기준과 부딪히는 지점**
- ⓐ 18개 FK는 회사 DB에서 쓸 수 없다. **DBA 적용 대기 중인 `oracle/014`(FK 6개)와 작성만 된 008~013(FK 6개)이 그대로 가면 거부될 수 있다.** 발송 전 수정이 필요하다.
- ⓑ MySQL은 FK에 인덱스를 자동으로 만든다. FK를 빼면 참조 칼럼 인덱스가 사라지므로, 두 DB 모두 명시 인덱스가 필요하다(README ④는 Oracle에만 인덱스를 둠).
- ⓒ README ②는 "앱이 고아 행을 만들면 FK가 잡는다"에 기대고 있다. FK가 없으면 앱 검증과 정기 정합성 점검이 그 역할을 맡는다. `ConsistencyController`(`GET`)가 있지만 무엇을 점검하는지는 확인 안 함.
- ⓓ CHECK·UNIQUE 허용 여부는 모름. 특히 `UK_ORCH_RUN_ACTIVE`(한 기관에 실행 하나, 동시성 보장)는 DB 제약에 기대므로, 금지라면 다른 보장 수단이 필요하다.
- ⓔ MySQL 미러에는 `007_uploader`가 없다(Oracle만 있음).

**FK 없이 표현할 수 있는가: 가능하다.** 참조 관계는 세 종류다.
- 업무 계층(기관→공고→작업→메시지, 실행→단계): 앱이 저장 전에 부모가 있는지 확인하고, 삭제는 논리 삭제나 삭제 금지로 처리.
- 사람 참조(사번, 11곳 이상): 저장할 때 `USERS`에 있고 재직 중인지 확인.
- 코드 값: 코드성 테이블에서 조회해 검증.

어느 쪽도 DB 제약 없이 서비스 로직으로 구현 가능하다. 구현 방법은 백엔드에 넘긴다.

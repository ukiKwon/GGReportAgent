## 결론 (약 1500자)
사용자가 승인한 원칙 ①~⑤를 전제로, 파이프라인을 8단계로 나눈다. 외부 쪽 4단계는 프로그램이 돌고, 내부 쪽 4단계는 서버와 사람이 맡는다.
- 외부: 수집 → 추출 → 포장 → 운반
- 내부: 반입 검증 → 후보 표 → 확정 → 데이터 반영
- 수집 프로그램 실행은 **CLI 하나**로 한다. 작업 스케줄러·RPA·에이전트는 이 CLI를 부르기만 한다.
- 사람이 하는 일은 운반(1단계), 반입 버튼, 확정, 값 충돌 해소다.
- LLM은 판정만 한다(공고 종류 분류, 금고 공고인지 여부, 기관 매칭 제안). 날짜·은행 값을 지어내지 않는다.

계약 v2의 레코드는 **두 종류**로 나눈다.
- **공고(notice)**: 사실 기록이다. 원문에 있는 것만 담는다. 키는 (출처, 공고번호)다.
- **기관 일정 후보(candidate)**: 기관 하나의 칸 하나(lastBid·term·contractEnd·contractExpiry·은행)에 넣을 값 하나다. 반드시 근거(공고 키, 또는 행안부 xlsx 같은 자료의 행)를 가리킨다.
- 관계는 공고 1건 → 후보 0~N건이다. 공탁금 지정 공고 1건이 법원 여러 곳으로 펼쳐지는 경우가 이 구조로 담긴다.

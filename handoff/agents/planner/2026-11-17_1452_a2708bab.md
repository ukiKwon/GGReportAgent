## 3. 용어·데이터 의미 정의 후보

**"반영됨"**
- **A (권장)**: 실행한 뒤 그 기관에 **수집 반입(IMPORT) 판이 새로 1건 생기면** 자동으로 반영됨. 시드 반입(SEED)은 세지 않는다.
  - 예: 11-18 10시에 실행 → 11-19에 도봉 import 9번이 들어옴 → 반영됨.
- B: 새 판이 들어오면 '반영 확인 대기'로 바꾸고, 요청자가 화면을 보고 [확인]해야 반영됨.
- C: 담당자가 손으로 [반영 완료]를 누른다. 자동 연결이 없어 실제 반입과 어긋날 수 있다.

**"실행 중"**
- 망 밖에서 진행 상황을 되받는 길이 없다(단방향).
- 그래서 "망 밖이 접수했다고 답했고, 결과 반입을 기다리는 중"으로 정의한다. 화면 표기 후보는 **"수집 중(반입 대기)"**다.

**"실패"**
- ⓐ 호출 자체가 실패한 경우(연결 안 됨, 거절): 자동으로 실패, 다시 실행할 수 있다.
- ⓑ 결과가 오지 않는 경우: 담당자가 사유를 적고 [실패로 표시]를 누른다.
- 자동 기한(며칠 뒤 실패)은 근거 있는 숫자가 없어 두지 않는다. 경과 일수만 보여 준다.

**"중복 기관"**: 같은 기관 ID에 열린 요청(요청됨·수집 중)이 이미 있는 경우.

## 4. 선택지 비교표와 권장안

### 4-1. 상태 단계

| 안 | 단계 | 장점 | 위험 |
|---|---|---|---|
| **S1 (권장)** | 요청됨 → 수집 중 → 반영됨 / 실패 / 취소됨 (+담당자가 뺀 건은 '제외됨') | 단방향 구조와 맞고, 반영을 자동으로 판정 | 결과가 늦게 오면 '수집 중'에 오래 머문다(경과 일수 표시로 보완) |
| S2 | S1 + '반영 확인 대기' | 요청자가 결과를 확인함 | 단계와 알림이 하나씩 늘어난다 |
| S3 | 요청됨 → 처리됨 | 단순 | 실패와 반영이 구분되지 않는다 |

### 4-2. 담당자(실행 권한)

| 안 | 누가 | 근거 | 되돌리기 |
|---|---|---|---|
| **R1 (권장)** | 시스템 관리 권한(admin 키)을 가진 사람 = 전산팀원·전산팀장·마스터 | 033에서 사용자가 "전산팀원·팀장 모두 시스템 관리자"로 답함(11-15). 반입 API도 이미 `AdminGuard`라 반입하는 사람과 실행하는 사람이 같다 | 쉬움(권한관리 화면에서 키 조정) |
| R2 | 전산팀장만 | 실행 책임이 한 사람에게 모임 | 반입 권한(팀원 포함)과 어긋남 |
| R3 | 전산팀 전원이되, admin 키와 별개인 새 메뉴 키 | 따로 조정할 수 있음 | 키 1개가 늘어나 Menus 골든·격자를 고쳐야 함 |

### 4-3. 요청·취소 권한 (팀 결정 제안)

- **요청**: 기관 사업계획 화면을 보는 사람 중 디자이너를 뺀 사람. 기억해 둔 결정(디자이너 기본값은 보기)을 따랐다.
- **취소**: 요청자 본인이 '요청됨' 상태일 때만. 담당자는 [제외]로 뺄 수 있고 사유가 필수다.
- **실행 뒤**: 취소할 수 없다. 망 밖은 이미 돌고 있다.

### 4-4. 중복 묶음 (팀 결정 제안)

- 같은 기관에 열린 요청이 있으면 새 건을 만들지 않고 **요청자만 덧붙인다**("3명 요청"). 반영·실패 알림은 덧붙은 요청자 전원에게 간다.
- '수집 중'인 기관도 같다. 다시 실행하지 않고 요청자만 덧붙인다.
- 최근 반영된 기관은 막지 않는다. 요청 버튼 옆과 담당 화면에 "마지막 반입 YYYY-MM-DD"를 보여 주고, 뺄지는 담당자가 판단한다. 막는 기준일 수(N일)는 근거가 없어 두지 않는다. 사용자가 원하면 질문 Q2로 정한다.

### 4-5. 알림 (기존 체계 재사용 권장)

지금 있는 것:
- 쪽지함: `notifications` 테이블, 미읽음 배지를 30초마다 확인한다(`app.js:1024`).
- `NotificationGuard.ownNames`는 사번·이름·역할에 더해, 팀장·부장이면 소속 팀 이름까지 받는다. 그래서 받는 사람을 `'전산팀'`으로 하면 전산팀원(역할 '전산팀')과 전산팀장 모두 받을 것으로 보인다. `Teams.teamOf` 반환값은 확인이 필요하다.
- 사이드바(nav) 배지.

권장:
- **새 기관 요청이 생길 때(덧붙임이 아닐 때) 시스템 쪽지 1통**을 받는 사람 '전산팀'으로 보낸다.
- 담당 화면 메뉴에 **열린 건수 배지**를 단다.
- 반영·실패 때는 요청자에게 쪽지를 보낸다.
- 주의: 사람이 보내는 쪽지는 종류가 '쪽지'로 고정이고, 시스템 종류는 서버만 만들 수 있다(`NotificationCommandService:20`). 새 시스템 종류(예: '수집요청')는 서버가 만들어야 하며, 그 방식은 백엔드에 넘긴다.

### 4-6. 망 밖으로 보내는 값 (최소 범위 권장)

- **보낸다**: 실행 번호, 기관 ID, 기관 표기명, 찾을 자료 종류(사업계획). 기관 ID는 결과 파일 이름 `{기관ID}_{확인일}`에 되돌아와야 해서 필요하다. ⑩-2는 망 밖이 ID를 *지어내는* 것을 막는 규칙이라 전달은 괜찮다.
- **보내지 않는다**: 요청자·담당자 사번과 이름, 요청 메모, 임박일·약정 만료·현 금고은행, 참여 여부 등 영업 판단, 되받을 주소(콜백 URL).
- **응답**: '접수 여부'만 받는다. 응답 안의 자료는 반입하지 않는다. 결과는 파일 반입 하나로만 들어온다(⑩-6의 범위를 호출 한 방향으로 좁힌다).
- **설정**: 주소·인증값은 설정 파일로 두고, 비어 있으면 [실행]을 막고 안내만 띄운다.
- 이 설계는 security 검토가 먼저다. CLAUDE.md 5절과 SCHEMA ⑧(자격증명은 계약 밖)에 따른 것이다.

### 4-7. 이름·문구 후보

- **담당 화면 이름**: ① "사업계획 수집 요청" (권장. 기존 '기관 사업계획'과 이어짐) ② "수집 요청함" ③ "외부 수집 관리"
- **메뉴 위치**: 시스템 관리 아래(admin 키와 맞음)를 권장한다.
- **요청하는 쪽 버튼**: [수집 요청] (확정) / 요청한 뒤 "요청됨 · 3명" / [요청 취소]
- **담당 화면 버튼**: [수집 실행] (권장. 그냥 [실행]보다 대상이 분명) / [제외] / [실패로 표시] / [다시 실행]

## 5. 결정이 필요한 질문 (업무 의미만)

**Q1. 요청한 기관 목록이 은행 밖 인터넷으로 나가도 되나?**
- 배경: 요청 목록은 곧 "우리 은행이 관심 있는 금고 기관 목록"이다. 실행할 때 기관 이름이 망 밖 수집 프로그램으로 넘어간다.
- 달라지는 것: 무엇을 보내느냐에 따라 밖에서 알 수 있는 영업 정보의 양이 다르다.
- ⓐ **(권장)** 기관 이름과 찾을 자료 종류만 보낸다. 마감일·현 은행·요청자는 안 보낸다.
- ⓑ 이것도 안 되면 요청 기관에 무관한 기관을 섞어 보낸다. 비용과 잡음이 늘어난다.
- ⓒ 사내 보안 담당 확인 전까지 [수집 실행]을 막아 둔다.

**Q2. 최근에 계획 자료를 이미 받은 기관을 또 요청하면?**
- 달라지는 것: 같은 기관을 반복해서 수집하는지 여부.
- ⓐ **(권장)** 막지 않고 "마지막 반입일"을 보여 준다. 뺄지는 전산 담당이 판단한다.
- ⓑ 정한 기간 안이면 요청 버튼을 막는다. 기간을 함께 알려 주셔야 한다.
- ⓒ 요청은 받고 담당 화면에 "최근 받음"으로 따로 묶는다.

**Q3. [수집 실행]은 누가 누르나?**
- 달라지는 것: 실행 책임과, 반입 권한과의 일치 여부.
- ⓐ **(권장)** 전산팀 전원(팀원·팀장). 지금 시스템 관리자 권한과 같고, 결과 자료를 반입하는 사람과도 같다.
- ⓑ 전산팀장만.

**Q4. 요청은 어느 시점에 '끝난 것'인가?**
- ⓐ **(권장)** 그 기관의 새 계획 자료가 시스템에 들어오면 자동으로 끝나고, 요청자에게 쪽지가 간다.
- ⓑ 자료가 들어온 뒤 요청자가 직접 [확인]을 눌러야 끝난다.

나머지는 팀이 결정했다: 디자이너 요청 불가, 중복 덧붙임, 취소·제외 규칙, 쪽지와 배지로 알림, 실패는 담당자가 손으로 표시, 이름·문구.

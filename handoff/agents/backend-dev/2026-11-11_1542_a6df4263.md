## 3. 구현안

### 설계 요지
1. **성공한 회수·승인·반려(OK 행)**: `ApprovalRequestService.decide/cancel` 안, 상태 전이가 모두 끝난 뒤 `PrepAudit.record`로 1행을 씁니다.
   - 같은 `@Transactional`(REQUIRED)에 들어가므로 승인 후처리가 409 등으로 실패하면 감사 행도 함께 롤백됩니다.
   - 화면·버튼은 컨트롤러가 `PrepUiIds.of(req)`로 걸러 새 오버로드로 넘깁니다. 기존 3인자 시그니처는 `unknown()`으로 위임하므로, 테스트(`AssigneeChangeApiTest:562,578`)가 직접 부르는 기존 호출은 그대로 동작합니다.
2. **실패한 시도(DENIED·BLOCKED·INVALID·ERROR)**: 서비스 트랜잭션이 롤백되므로 안에서는 남길 수 없습니다. 그래서 컨트롤러가 ApiException을 잡아, 요청이 사전준비 유형이면 따로 커밋해 1행을 남깁니다(PrepController.run과 같은 방식).
   - 사전준비가 아닌 유형과 404(요청 없음)는 기록하지 않습니다.
   - 401(사번 없음)은 PrepController처럼 남기지 않습니다.
   - 결과적으로 시도 1번에 정확히 1행이 남습니다(성공은 서비스 안, 실패는 컨트롤러).
3. **행위 코드**: `OPEN_|PLAN_` 뒤에 `WITHDRAW|APPROVE|REJECT`를 붙입니다. decision 값이 잘못된 400은 `*_DECIDE`입니다.
   - STATE_CD에는 행위 직전 건 상태(`prep.stateOf`)를 넣습니다.
   - 행위(무엇이 일어났나)와 버튼(어느 버튼으로)은 따로 기록됩니다. 예: 결재함에서 취소하면 `OPEN_WITHDRAW` + `approvals_mine/cancel_request`.
4. 다단계 결재의 중간 승인도 같은 줄을 남기지만, BID_OPEN과 PREP_APPROVAL은 1단계뿐이라 해당되지 않습니다.

    private void auditPrep(ApprovalRequest r, String bid, String verb, String before, Actor actor, BoardUiIds.Ui ui) {
        if (bid == null || bid.isEmpty()) {

        }

    public static final class PrepRef {
        private final String reqType;
        private final String bidCaseId;
        private final String stateCd;

        PrepRef(String reqType, String bidCaseId, String stateCd) {

        public String getReqType() { return reqType; }

     * 컨트롤러의 실패 감사용 — 결재 요청이 사전준비 유형(BID_OPEN·PREP_APPROVAL)이면 그 건과 지금 상태, 아니면(없음·다른 유형·payload 불량) null.

    @Transactional(readOnly = true)
    public PrepRef prepRefOf(Long id) {
        ApprovalRequest r = id == null ? null : requests.selectById(id);
        if (r == null || !ApprovalTypes.isPrep(r.getReqType())) {
            return null;
        }
        String bid;
        try {

        return bid.isEmpty() ? null : new PrepRef(r.getReqType(), bid, prep.stateOf(bid));

## 5. 보안·위험·되돌리는 법
- **자기신고 한계**: 사번(`X-Emp-No`)과 화면·버튼은 모두 클라이언트가 스스로 보내는 값입니다. 서버가 확인할 수 있는 것은 "허용된 이름인가"뿐이고, `ui_valid=1`은 "목록 안의 이름"이라는 뜻이지 검증됐다는 뜻이 아닙니다.
- **기록하지 않는 것**: 의견·사유·decision 원문·머리글 원문은 저장하지 않습니다(목록 밖 값은 UNKNOWN).
- **403 경로·응답 계약**: 권한 판정은 바뀌지 않습니다. 기존 `/approval-requests` 응답(상태 코드·본문)과 `/approvals`·`/tasks/{id}/approve`도 그대로입니다. 사전준비가 아닌 유형은 BID_PREP_ACT를 건드리지 않습니다(성공 경로는 `isPrep` 분기, 실패 경로는 `prepRefOf`가 null).
- **위험 ①** 감사 INSERT가 실패하면:
  - 성공 경로: 결재 전체가 롤백되고 500이 납니다(fail-closed, 의도한 동작).
  - 실패 경로: 원래의 403·409가 500으로 바뀌어 보일 수 있습니다. PrepController.run과 같은 성질입니다.
- **위험 ②** 실패 경로에서 `prepRefOf`가 요청 행을 한 번 더 조회합니다. 내부 조회일 뿐 응답에는 싣지 않으므로 존재 여부가 새지 않습니다.
- **위험 ③** 403 DENIED를 ACCESS_LOG에 남기는 `guard.denied`와 ACCESS_LOG DETAIL(`prep case=…`)은 이 컨트롤러에 넣지 않았습니다. 기존 `/approval-requests` 접근 이력 동작을 바꾸지 않기 위해서입니다. 필요하면 security 판단 뒤 따로 하겠습니다.
- **위험 ④** 결재 의견 등 쓰기는 결재와 같은 트랜잭션이라, 감사 줄과 결재 결과가 서로 어긋나는 상태는 생기지 않습니다.
- **되돌리는 법**: DB 변경이 없으므로 위 4개 파일과 테스트를 git으로 되돌리면 끝입니다. 이미 쌓인 BID_PREP_ACT 행(OPEN_/PLAN_ 계열)은 남아도 무해합니다.

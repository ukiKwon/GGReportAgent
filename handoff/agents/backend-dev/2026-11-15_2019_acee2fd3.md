### 감사 화면·버튼 식별자
- **새로 만들지 않습니다.** 세 경로를 부르는 화면이 없기 때문입니다.
- `PrepUiIds.of(req)`를 **호출만** 합니다(파일은 고치지 않음). 지금 들어오는 호출은 모두 `UNKNOWN/UNKNOWN, UI_VALID=0`으로 남고, 이는 "화면 밖 직접 호출"이라는 신호가 됩니다.
- 감사 표는 `BID_PREP_ACT`(PrepAudit.record 7인자 호출만)이고 새 행위 코드는 `CASE_CREATE`·`CASE_LIST`·`CASE_VIEW`입니다.
  - 이 표는 쓰기 전용입니다(PrepMapper에 select 없음). 무결성 점검 SQL도 이 코드를 보지 않습니다.
  - **DB 마이그레이션은 없습니다**(mysql/oracle 모두 해당 없음).
- 기록 규칙(선례와 같음):
  - 사번이 확인된 앞단 403 → DENIED 줄
  - 401 → ACCESS_LOG에만
  - 서비스가 낸 403 → guard.denied로 ACCESS_LOG DENIED
  - 404/409/400 → HIDDEN/BLOCKED/INVALID 줄
  - 일반 예외 → ERROR 줄
  - 실패 감사가 터지면 WARN 한 줄만 남기고(예외 종류만) 원래 응답을 유지
  - 성공한 읽기는 응답 전에 기록(fail-closed)
  - 건 칸은 caseKey(형식 밖이면 NONE), 목록은 반환한 건마다 한 줄
  - ACCESS_LOG DETAIL에는 `bidcase case=… code=…` 또는 `n=`만 넣고 team·assignee 값은 넣지 않습니다.

    private <T> T front(Supplier<T> check, String key, String action, Actor actor, BoardUiIds.Ui ui) {
        try {
            return check.get();
        } catch (ApiException e) {
            if (e.getStatus() == 403) {

    private <T> T audited(HttpServletRequest req, String key, String action, Actor actor, BoardUiIds.Ui ui,
                          Supplier<T> call) {
        try {
            return call.get();
        } catch (ApiException e) {
            if (e.getStatus() != 401) {
                auditFailure(key, action, PrepAudit.outcomeOf(e.getStatus()), actor, ui);
            }
            if (e.getStatus() == 403) {
                throw guard.denied(req, e);
            }
            throw e;
        } catch (RuntimeException e) {   // DB 오류 등 — ERROR 로 남기고 그대로(전역 처리기가 500)
            auditFailure(key, action, "ERROR", actor, ui);
            throw e;
        }
    }

    /** 실패 줄. 기록이 실패해도 원래 응답을 덮지 않는다 — 서버 로그에 예외 종류만(메시지·스택 없음). */
    private void auditFailure(String key, String action, String outcome, Actor actor, BoardUiIds.Ui ui) {
        try {
            String st = NO_CASE.equals(key) ? NO_CASE : prep.stateOf(key);
            audit.record(key, action, outcome, st, null, actor, ui);
        } catch (RuntimeException ex) {
            LOG.warn("입찰 건 실패 감사를 남기지 못했다: action={} outcome={} cause={}", action, outcome, ex.getClass().getSimpleName());
        }
    }

    /** 감사 칸용 건 번호 — 형식([A-Za-z0-9._-]{1,64})이면 그 값, 아니면 NONE(PrepController.caseKey 와 같은 규칙). */
    static String caseKey(String bid) {
        String b = bid == null ? "" : bid.trim();
        return b.matches("[A-Za-z0-9._-]{1,64}") ? b : NO_CASE;
    }

    /**
     * 담당자 목록 열람 판정. 본인 이름(USERS.NAME)이 assignee 와 같으면 언제나 허용.
     * 옛 흐름이 열려 있으면 그 팀의 팀장(team 은 '영업'·'영업팀' 둘 다 받는다)과 영업부장도 허용한다.
     */
    static boolean mayList(SysUser me, String team, String assignee, boolean legacyOpen) {
        String name = me.getName() == null ? "" : me.getName().trim();
        String who = assignee == null ? "" : assignee.trim();
        if (!name.isEmpty() && name.equals(who)) {
            return true;
        }
        if (!legacyOpen) {
            return false;
        }
        String role = me.getRole() == null ? "" : me.getRole().trim();
        String lead = Teams.leadOf(Teams.teamOf(team == null ? "" : team.trim()));
        return Teams.FINAL_APPROVER.equals(role) || lead.equals(role);
    }
}

## 5. 보안·위험·되돌리는 법
- **403 경로**:
  - 상세: MenuGuard.require(workflow)
  - 목록: requireActiveUser 뒤 mayList → guard.denied
  - 생성: AdminGuard
  - 모두 ACCESS_LOG DENIED에 남고 본문·쿼리값은 넣지 않습니다. 사번이 확인된 403은 BID_PREP_ACT에도 DENIED로 남고, 401은 ACCESS_LOG에만 남습니다.
- **자기신고 한계**: X-Emp-No·화면·버튼은 위조할 수 있습니다. 목록 판정은 **이름 문자열 일치**라 동명이인과 TASKS.ASSIGNEE 자유 문자열 한계가 있습니다(S-1 사번화 때 함께 고칩니다).
- **결합 위험**: BidCaseController가 PrepAudit.record(7인자)·PrepService.stateOf·PrepUiIds.of·AccessLogInterceptor.DETAIL을 **호출만** 합니다. 3d 세션이 이 시그니처를 바꾸면 컴파일이 깨지므로 병합 뒤에 적용해야 합니다.
- **생성 성공 뒤 감사 기록이 실패하는 경우**: 건은 이미 만들어졌는데 응답은 500이 됩니다(PrepController.confirm과 같은 한계).
- **1단계에서 남는 구멍**: 열림 상태의 `POST /bidcases` 무가드는 그대로 남습니다(ACCESS_LOG에만 남음). 2단계(패치 C)로 닫습니다.
- **운영 영향**: 화면 호출처가 없어 화면이 403을 받는 경로는 **없습니다**. 사번 없이 상세·목록·생성을 부르던 외부 스크립트나 수동 curl이 있다면 401/403이 됩니다(저장소 안에서는 찾지 못했습니다).
- **되돌리는 법**: BidCaseController와 시험 2개를 되돌리면 됩니다. DB 변경은 없습니다. 이미 쌓인 CASE_* 감사 줄은 추가 전용이라 그대로 둬도 무해합니다.

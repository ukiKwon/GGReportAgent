### 1. 고친 파일 (모두 `kgi-ggreport-web/` 아래)

**main**
- `boarddoc/BoardLegacyKeys.java` (신규): CATALOG_VER 1의 옛 key → 새 key 번역표를 상수로 얼려 둔 클래스.
  - 표 A는 `{0,1,2,3},{0,1,2,3},{1,2},{1,2},{1,2,3}`처럼 행별 격자 시작 열을 상수로 둔다.
  - 살아 있는 카탈로그에서 계산하지 않으므로, 카탈로그가 나중에 바뀌어도 옛 버전은 항상 같은 칸으로 번역된다.
  - 모르는 버전·표·위치는 null을 돌려준다. 옛 모양 정규식은 앞자리 0을 거부한다.
- `boarddoc/BoardDocSpec.java`
  - **Cell**: `input`, `rowId`, `colId`를 추가했다. `getKey()`는 `rowId_colId`다. 복사 메서드는 `withIds`, `withText`, `withInput`. 6인자 생성자는 그대로 두었다.
  - **Table**: `rowIds`, `colIds`, `nextR`, `nextC`를 추가했다. 기본 생성자는 행 id `r{행}`, 열 id `c{격자열}`, 카운터 100(`FIRST_NEW_ID`)을 쓴다.
  - 명시 id를 받는 두 번째 생성자도 두었다. id 개수·정규형·중복·카운터 범위를 검증하고, 위반하면 IllegalStateException(입력값은 싣지 않는다).
  - 병합 칸의 key는 앵커(왼쪽 위) 칸의 행id/열id다. `layout`은 `layoutOf`로 분리해 Table 생성 전에도 쓴다.
  - 상수: `FORM_FMT=2`, `FIRST_NEW_ID=100`, `MAX_ID_NUM=9999`. `CATALOG_VER`는 1 그대로다.
  - 추가 함수: `isValidRowId`, `isValidColId`, `isValidCellKey`(정규형 `^r(0|[1-9][0-9]{0,3})$` 등, PR-2가 쓴다), `cellKey(String,String)`, `legacyToKey`, `resolveKey`, 공개 `mappedKeys`. `editableKeys`는 새 key 기준으로 바꿨다.
  - `build`/`withValues`는 `withText`와 명시 id 생성자를 써서 key를 보존한다.
  - `clean()`이 Cf(서식) 문자를 거부한다. ZWJ(U+200D)도 포함해 전부 거부한다. 오류 문구는 고정이다.
  - `getNextR`/`getNextC`는 `@JsonIgnore`라 `/board-docs` 응답에 나가지 않는다. 칸에는 `row_id`, `col_id`, `input`이, 표에는 `row_ids`, `col_ids`가 추가로 나간다.
- `boarddoc/BoardFormJson.java` (다시 씀)
  - 저장은 `{"fmt":2,"catalog_ver":1,"tables":[{ref,title,cols,rows[{id,cells[{c,t,cs,rs,h,i,a}]}],next_r,next_c,cells:{옛 r{행}c{순번}}}]}`다.
  - 연결 칸의 `t`는 항상 `""`이다(sample 여부와 무관하게 JSON이 같다). 옛 cells 맵은 롤백 안전용이다.
  - 읽기: fmt가 없으면 `legacyToKey`로 번역한다. fmt 2는 구조(cols, 행 id, 칸 속성, 카운터)를 카탈로그와 대조한 뒤 편집 가능한 칸의 문구만 꺼낸다.
- `boarddoc/BoardExcelMap.java`
  - `mapCatalogVer` 필드를 추가했다.
  - `cells`/`blocks`/`sums.of`/`total`/`derive_sum.of`의 옛 key를 `newKey`(`resolveKey`)로 번역한다. 번역하지 못하면 기동 실패다.
  - `lines.row`와 cells 위치 순서는 `cat.getRows().get(row).get(idx).getKey()`로 번역한다. 비교는 `BoardDocSpec.mappedKeys`로 한다.
- `service/BoardFormService.java`
  - `view()`에 `key`, `row_id`, `col_id`, `input`, `editable`(`!mapped`)과 표의 `row_ids`, `col_ids`를 추가했다.
  - 새 상수 `MAX_JSON_BYTES=240000`(UTF-8 바이트 기준)을 쓴다.
  - `fmt` 검증: 생략 또는 정수 1·2만 허용하고, 그 밖이면 400.
  - `Pii.scan`: 양식 이름(저장·복제), 표 제목, 비연결 칸 문구에 적용한다. 검출되면 422 고정 문구이며 검출값은 싣지 않는다.
  - `verifyRoundTrip`: 저장 직전에 toJson → parse → build → toJson을 한 번 돌려 같지 않으면 ISE(500)로 막는다.
  - `changed:false` 비교는 현재 버전을 읽어 새 포맷으로 정규화한 JSON과 비교한다. 옛 포맷 버전도 같은 내용이면 새 버전이 생기지 않는다.
- `dto/BoardFormIn.java`: `Save.fmt`를 `Object`로 받는다. Integer로 받으면 1.5가 조용히 1로 깎이고, `"2"`·`true`도 통과하기 때문이다.
- `config/BoardWriteLimitFilter.java`
  - PUT `board-forms/{id}`는 512KB, POST `board-forms/copy`는 16KB로 제한한다. 정규식은 `board-forms/+[^/]+/*$`와 `board-forms/+copy/*$`로, `//`도 같은 경로로 친다(지시한 정규식보다 약간 넓다).
  - 길이가 없으면 411, 한도 초과면 413 `BODY_TOO_LARGE`(`max_kb` 포함)이다.
  - 중첩 클래스 `CountingRequest`/`CountingStream`이 실제 읽은 바이트를 센다. 한도를 넘는 순간 `ApiException.withDetail(413, …)`을 던진다. 이 예외는 RuntimeException이라 Jackson을 통과해 기존 advice 두 곳이 그대로 413 객체로 응답한다.
  - 엑셀 multipart 경로에는 래퍼를 쓰지 않는다. 컨테이너 파싱에 영향을 줄 위험이 있어서다.

### 3. 지시와 달리 판단한 것 (숨기지 않는다)
1. **모르는 `catalog_ver`의 옛 JSON → 닫힌 실패(IllegalStateException → 500).** 기본 구조 폴백은 택하지 않았다. 폴백하면 엉뚱한 문구가 보이고, 그 위에 저장하면 오염되기 때문이다. 복구는 가능하다. 현재 버전이 읽히지 않으면 `normalizedJson`이 null을 돌려 "같지 않음"이 되므로, 다음 PUT이 새 버전을 정상 포맷으로 만든다. 이 흐름을 테스트로 고정했다.
2. **fmt 2의 구조는 카탈로그와 같아야 읽힌다.** PR-1에는 구조 편집이 없으므로 어긋나면 닫힌 실패다. PR-2에서 이 검증을 구조 복원으로 바꿔야 한다.
3. **Cf는 ZWJ(U+200D)까지 전부 거부했다.** 한글 문구에 ZWJ가 필요한 경우를 찾지 못했다. 이모지 시퀀스가 필요해지면 U+200D만 예외로 풀면 된다.
4. **옛 모양 key를 PUT으로 보내면 번역하지 않고 400**이다("수정할 수 없는 칸이 포함되어 있습니다." 고정 문구). 낡은 화면이 엉뚱한 칸에 적용되는 것을 막는 설계 의도다.
5. **Pii 검출 시 422**를 골랐다(400이 아님).
6. `MAX_JSON_BYTES=240000`. 정상 최대 입력은 약 30KB라서, 이 상한은 사실상 이상 입력만 막는다. 칸 수·글자 수 상한은 PR-2(구조 편집)에서 정한다.
7. 필터 정규식을 `board-forms/+`로 넓혔다(`//` 대응).
8. 테스트에서 500 응답의 detail 문구는 단정하지 않았다. 로컬 설정 `ggreport.errors.detail=true`이면 원문이 나가기 때문이다.

### 4. 남은 위험
- **컴파일·테스트를 돌리지 못했다.** IDE 진단은 편집 중간 상태 오류만 있었고 최종 상태는 확인하지 못했다. 새 테스트의 기대값은 손으로 계산했다(표 B `r2_c5`, C-3 `r4_c5` 등). 실패하면 기대값 오타부터 의심하라.
- `CountingRequest`는 MockMvc 경로 대신 단위 테스트로 검증했다(MockMvc는 `Content-Length`가 항상 정확하다). 실제 chunked 요청은 운영 서블릿 컨테이너에서 한 번 확인할 만하다.
- 롤백 안전용 옛 cells 맵은 PR-1에서만 정확하다. PR-2에서 구조 편집이 들어오면 삭제해야 한다(설계 요약과 같다).
- 한 요청을 `Table`로 복원할 때 `nextR`/`nextC`는 카탈로그 값(100)과 일치해야 한다. PR-2에서 사용자 행·열이 생기면 이 대조 조건을 풀어야 한다.

### 5. 프런트 호환 확인 (grep만 했다)
- `frontend/js`에 `r\d+c\d+` 정규식으로 key를 파싱하는 코드는 없다. key는 불투명 문자열이다.
- 프런트 테스트(`board-write.test.js`, `board-edit.test.js` 등)는 `r0c0`, `r1c1`, `h0`, `a0`, `x1` 같은 자체 가짜 key로 만든 fixture를 쓰고, 서버 응답을 가정하지 않는다. 따라서 변경이 필요 없다.
- `board-write.js`의 `srcIndex`는 엑셀 주소(`gridPos`)에서 오고 key를 분해하지 않는다.
- 호환 조건: 프런트가 PUT에 보내는 `cells`의 key는 서버가 내려준 새 key여야 한다. 같은 배포 단위로 나가면 문제없다.

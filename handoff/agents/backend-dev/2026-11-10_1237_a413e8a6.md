# backend-dev 보고서 (자동 보존)

> SubagentStop 훅이 에이전트의 최종 메시지를 그대로 저장했다(2026-11-10 1237 KST, agentId a413e8a63de5d56db). 에이전트 출력이므로 사용자 결정이 아니다. 지시 내용·주제는 이 파일에 없다 — 필요하면 handoff/NEXT.md 항목이나 커밋 메시지로 찾는다.

## 1. 대상·방법·못 본 것

- **대상**: `ApprovalRequestService`, `ApprovalRequestMapper`(.java/.xml), `BidAssignmentService`, `BidAssignmentMapper`(.java/.xml), `AssigneeChangeApiTest`를 줄 단위로 읽었습니다. 보고서 원문(`handoff/agents/security/2026-11-10_*`)은 읽지 않았고, 지시문의 요약만 근거로 했습니다.
- **못 본 것**: 서버와 DB를 실행하지 못해 아래 테스트는 직접 돌려 보지 못했습니다. Oracle에서 `UPDATE ... AND STATUS='PENDING'`이 행 잠금을 기다린 뒤 재평가하는 동작은 표준이라 가정했습니다.
- **DDL**: 변경이 없어 `db/mysql`·`db/oracle` 스크립트는 추가하지 않습니다. 기존 DB를 이어 갈 작업도 없습니다.
- **`PENDING_REQ_ID`에는 외래키가 없습니다**(`019_bid_assignment.sql:12`). 그래서 `releasePending`이 다른 요청의 선점을 건드리지 않는다는 보장은 SQL 조건(`AND PENDING_REQ_ID = reqId`)이 맡습니다.

## 2. 원인 요약

- **중-1**: `decide`와 `cancel`은 `selectById`로 읽은 상태(`ApprovalRequestService.java:221`, `:272`)만 믿습니다. 쓰는 문장은 상태 조건이 없습니다(`ApprovalRequestMapper.xml:42-52`, `WHERE REQ_ID=` / `WHERE STEP_ID=` 뿐). 반환 행 수도 아무도 확인하지 않습니다(`:244-259`, `:277`). 동시에 들어오면 취소된 요청이 승인되거나, 승인된 요청이 취소로 덮어써질 수 있습니다. 취소 때 `BID_ASSIGN_CASE.PENDING_REQ_ID`를 풀지 않아(`:275-283`) 낡은 선점이 남습니다. 낡은 선점은 `planChange`가 교체하므로(`BidAssignmentService.java:261-266`) 기능상 막히지는 않습니다. 다만 선점 상태가 요청 상태와 어긋납니다.
- **하-1**: `applyChange`는 결재자가 영업팀장 또는 영업부장인지만 확인합니다(`BidAssignmentService.java:297`). 영업팀장 관련 건(상신자·현 담당자·추가 대상 중 팀장이 있는 건)은 부장이 결재해야 한다는 규칙은 `planChange`가 상신 때 한 번만 계산합니다(`:244-258`). 결재선이 바뀌거나 어긋난 경우 승인 때 다시 막는 곳이 없습니다.
- **하-4·5**: `planChange`는 `requireBidCase`(404)를 먼저 합니다(`:215`). 그 결과 디자이너·관리자도 입찰 건 존재 여부를 404와 403으로 구분해 알 수 있습니다. 담당자 여부만 보기 때문에(`:219`) 역할이 영업 계열이 아닌 담당자도 통과합니다.

### 테스트를 쓸 때 유의한 점

- **`영업팀장_상신자_건도_...` 메서드**: 이름과 달리 대조군입니다. 영업부장 역할자(EXEC)가 결재하면 승인이 통과함을 확인합니다. 이름이 어색하면 `영업부장_역할자는_팀장_상신_건을_승인한다`로 바꿔도 됩니다.
- **1차 캐시**: 두 가지를 고려했습니다.
  - 경합 재현은 1차 캐시를 일부러 이용합니다. `selectById`로 PENDING을 읽어 두고 JdbcTemplate으로 상태를 바꾼 뒤, 서비스 호출 전에 MyBatis 쓰기가 없도록 했습니다.
  - 결재선을 JdbcTemplate으로 바꾼 케이스에서는 `flushCache()`를 호출합니다. `submitOk`가 `selectSteps`를 캐시해 두기 때문입니다.
- **서비스 예외 후 같은 테스트 안의 상태**: 서비스가 던진 예외는 외부 테스트 트랜잭션을 rollback-only로 표시하지만, 테스트는 어차피 마지막에 롤백합니다. 그 안에서 JdbcTemplate 조회는 계속 동작합니다. 다만 위 두 테스트에서 `skipRest` 등이 이미 쓴 값은 되돌려지지 않으므로, 단계 상태는 단언하지 않고 요청 상태와 선점만 확인합니다.
- **접근 이력**: `ACCESS_LOG`는 테스트 롤백과 무관하게 남아 다른 테스트와 섞입니다. 그래서 기존 방식(같은 호출 직후 `REQ_PATH=?` 최신 1건)을 따랐습니다. 문자열 단언은 이번 테스트가 만든 `no-such-case`로 좁혔습니다.
- **`Actor.claimed(LEAD)` 서비스 직접 호출**: 의도적입니다. `X-Emp-No` 자기신고 경로와 같은 `callers.require`를 거칩니다.

## 5. 보안·위험·되돌리는 법

- **중-1이 막는 것**: 승인·반려·취소가 서로 덮어쓰지 못합니다. 두 요청이 동시에 들어와도 먼저 커밋한 쪽만 성공합니다.
  - 나중 쪽은 행 잠금을 기다린 뒤 조건이 맞지 않아 0행이 되고, 409로 롤백됩니다.
  - 마지막 단계 승인에서 `applyChange`와 `permissions.save` 같은 후처리도 0행 409가 함께 되돌립니다.
  - 단일 DB 트랜잭션에 의존합니다. MySQL REPEATABLE READ에서도 UPDATE는 현재 읽기를 하므로 유효합니다.
- **`releasePending`은 취소에만 걸었습니다.** 반려는 종전대로 낡은 선점을 두고 `planChange`가 교체합니다. 반려에도 풀어 줄지는 정책이 아니라 정합성 선택입니다. 원하면 `decide`의 반려 분기에 `if (ASSIGNEE_CHANGE) assignments.releasePending(r)` 한 줄을 더하면 됩니다. 이번 범위에서는 "기존 동작 불변"을 우선했습니다.
- **하-1의 409는 의도된 동작입니다.** 에러 문구에 사번·이름을 싣지 않았습니다.
  - 운영에서 이 409가 나면 결재선이 어긋난 신청입니다. 반려하거나 취소한 뒤 다시 신청하면 `planChange`가 부장으로 결재선을 다시 계산합니다.
  - 영업부장 역할자(박영업·백수아)는 어느 경우에도 통과합니다.
- **하-4·5**: 영업 계열이 아닌 역할은 입찰 건 존재와 무관하게 403입니다. 영업팀 전원은 이미 `view`로 존재를 조회할 수 있어 정보 누출이 늘지 않습니다. 영업부장이 상신하는 경우는 종전에도 담당자가 될 수 없어 사실상 403이었고, 지금은 더 일찍 403이 됩니다.
- **한계**: 이 모든 검사는 `X-Emp-No` 자기신고를 전제로 한 업무 규칙입니다. 사칭 방지가 아니며 접근 이력의 `emp_verified`는 사실만 적습니다.
- **되돌리는 법**: 변경 파일은 소스 4개, 매퍼 XML 2개, 테스트 1개입니다. 커밋을 되돌리면 끝나고 DDL과 데이터 변경은 없습니다.

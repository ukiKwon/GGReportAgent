## 컴파일 때 메인이 볼 의심 지점
1. `BoardWriteApiTest`의 `draftBody`는 이제 인스턴스 메서드입니다. static 문맥(람다·static 메서드)에서 호출하는 곳이 있으면 컴파일 오류가 납니다. 그 밖에 `bid_case_id` 없이 직접 `rawPost`하는 보안 케이스(약 530–650줄)가 실패할 수 있습니다.
2. `BoardMaterialService`는 `BidAssignmentService`의 `LEAD_ROLE`·`HEAD_ROLE`(package-private)과 `anyActiveLead`·`resolveApprover`를 같은 패키지에서 씁니다. 가시성은 맞춰 두었습니다. 사용하지 않는 import가 남아 있으면 경고만 납니다.
3. `new BidAssignmentService(` 직접 생성이 테스트에 있으면 생성자 인자가 늘어 컴파일 오류가 납니다. `grep -rn "new BidAssignmentService(" kgi-ggreport-web/src/test`로 확인하세요.
4. H2(Oracle 모드)에서 `020_board_material.sql`이 도는지 확인이 필요합니다. 대상은 `GENERATED BY DEFAULT AS IDENTITY`, CLOB, `ALTER TABLE BID_ASSIGN_LOG ADD FROM_EMP_NO VARCHAR2(7 CHAR)`, `COMMIT`입니다. `DdlRulesTest`는 FK 단어가 주석에도 없는지 봅니다.
5. `BoardMaterialApiTest`가 가정한 시드(사번 7742059·2189346·2674805, HEAD가 영업팀장 상신을 승인)와 `ACCESS_LOG` 열 값은 확인하지 못했습니다. 실패하면 이 가정이 첫 의심 대상입니다. 숫자 칸 검증과 전각 주민번호의 PII 탐지도 마찬가지입니다.
6. `BoardWriteController.requireCaseWriter`는 `guard.denied(req, new ApiException(403, WRITE_DENIED))`를 씁니다. `ApiException(int,String)` 생성자 공개 여부와 `withDetail` 반환 형을 확인하세요(둘 다 같은 `web` 패키지입니다).
7. 지금 서버가 떠 있는 상태에서 코드를 먼저 올리면 배정 이력 조회가 500입니다. 020 DDL을 먼저 적용하세요.

## 메인이 실행할 명령
1. DDL 적용(사용자 터미널, v1 020을 돌린 적이 있으면 N2 헤더의 되돌리기를 먼저): `cd kgi-ggreport-web && mysql -u root -p --default-character-set=utf8mb4 ggreportdb < src/main/resources/db/mysql/020_board_material.sql`
2. `mvn -q -o compile`
3. `mvn -q -o test -Dtest=DdlRulesTest,MapperStatementBindingTest,BoardMaterialApiTest,BoardWriteApiTest,BidAssignmentApiTest,AssigneeChangeApiTest,BoardWriteLimitFilterTest`
4. 통과하면 `mvn -q -o test` 전체를 돌리고, 8080 서버가 같은 `target/`을 쓰면 재기동합니다.

기대 결과는 컴파일 성공, 위 7개 테스트 통과, 전체 테스트 통과입니다.

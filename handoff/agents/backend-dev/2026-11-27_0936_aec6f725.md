# backend-dev-write 보고서 (자동 보존)

> SubagentStop 훅이 에이전트의 최종 메시지를 그대로 저장했다(2026-11-27 0936 KST, agentId aec6f725a6dd4bc98). 에이전트 출력이므로 사용자 결정이 아니다. 지시 내용·주제는 이 파일에 없다 — 필요하면 handoff/NEXT.md 항목이나 커밋 메시지로 찾는다.

---

제안 준비 중인 기관의 제외(CANCEL)·관심 이동(TO_WATCH)을 서버에서 막았고 시험 4개를 추가했습니다. 빌드와 시험은 하지 못했습니다(Bash 없음).

**1. 판정과 상태 집합**
- 진행 중 = BID_PREP.STATE_CD 가 `CONFIRMED, OPEN_PENDING, IN_PROGRESS, APPROVAL_PENDING, WRITABLE, WRITING` 중 하나인 건입니다.
- 이 집합은 기존 `PrepMapper.countActiveByInstitution` 과 `selectActiveStatesByInstitution`, 그리고 `PrepNobidService.ACTIVE_STATES` 와 같습니다. 화면도 이 집합을 쓰면 됩니다.
- `CANCELLED`, 종결, 협약 완료 같은 상태는 집합에 없어 막지 않습니다.
- 기관 단위로 봅니다.
- `PrepMapper.selectActiveCaseIdsByInstitution(institutionId)` 를 새로 만들었습니다.
  - 파일: `PrepMapper.java`(약 35줄), `src/main/resources/mapper/PrepMapper.xml`(약 45줄).
  - 활성 건의 BID_CASE_ID 를 돌려주며, 응답에 bid_case_id 를 싣기 위해 추가했습니다.
- `BidTargetService.requireNoActivePrep(inst)` 가 이 조회로 판정합니다(`BidTargetService.java` 약 92~110줄).
  - 409 `PREP_ACTIVE` 를 던집니다. 메시지는 지시하신 문구 그대로입니다.
  - detail 에 `institution_ids:[inst]` 와 `bid_case_ids:[...]` 를 싣습니다.

**2. 막는 지점**
- ⓐ 결재 요청 제출: `TargetChangeService.planItem` 의 CANCEL, TO_WATCH case 에서 막습니다.
- ⓑ 승인 시점: `TargetChangeService.replan` 의 CANCEL, TO_WATCH case 에서 다시 막습니다. 승인 요청은 전체 롤백되고 요청은 PENDING 으로 남습니다.
- ⓒ 부장 즉시 경로:
  - 일괄 요청은 ⓐ와 같은 `plan` 을 거치므로 함께 막힙니다.
  - 단건은 `BidTargetService.cancel` 에서 막습니다. 목표 기록일 때만, `requireDirect` 뒤에 검사합니다.
- ⓓ `move`: `BidTargetService.move` 에서 `toWatch` 일 때 `requireDirect` 뒤에 검사합니다. 컨트롤러는 그대로 두었습니다.
- 관심 기록을 빼는 것은 막지 않습니다. 제외 대상은 목표 기관이기 때문입니다.
- ADD·EDIT·TO_GOAL 은 건드리지 않았고, 기존 `ALREADY_CANCELLED`, `STALE`, `CHANGE_PENDING` 순서도 그대로입니다.
- 일괄 요청은 기존 관례대로 첫 실패에서 전체 거부(fail-fast)입니다.
  - detail 에 막힌 항목의 `item_no` 가 따라오고, `institution_ids` 에는 그 항목의 기관 하나만 담깁니다.
  - 막힌 기관 전체 목록이 필요하면 `plan()` 에서 모아 던지도록 바꿔야 합니다. 지금은 하지 않았습니다.

**3. 시험**
- `BidTargetApiTest`
  - `진행_중_제안_준비가_있으면_목표_빼기는_409_PREP_ACTIVE_중단된_건만_있으면_201`
  - `진행_중_제안_준비가_있으면_목표를_관심으로_옮기기는_409_PREP_ACTIVE_관심에서_목표는_통과`
  - 도우미 `activePrep2` 를 추가했습니다.
- `TargetChangeApiTest`
  - `진행_중_제안_준비가_있으면_CANCEL_TO_WATCH_상신은_409_PREP_ACTIVE_중단된_건만_있으면_통과`: 일괄 요청의 item_no 확인과 CANCELLED 후 통과(200)를 함께 봅니다.
  - `결재_승인_시점에도_진행_중_제안_준비가_있으면_409_PREP_ACTIVE_하나도_반영_안_됨`
  - `영업부장_바로_반영과_단건_빼기_옮기기도_진행_중_제안_준비가_있으면_409_PREP_ACTIVE`
  - 도우미 `prep(caseId, inst, state)` 를 추가했습니다.

**4. 메인이 실행할 것**
- `cd kgi-ggreport-web && mvn -q -o test -Dtest=TargetChangeApiTest,BidTargetApiTest`
- 이어서 전체 `mvn -q -o test`
- 기대 결과: 모두 통과. 전체 테스트가 386건 안팎이면 정상입니다.

**5. 판단과 확인 요청**
- **지시 밖 변경:** `PrepMapper.xml` 과 `PrepMapper.java` 에 조회를 추가했습니다. 응답에 bid_case_id 를 싣기 위해서입니다. DB 변경은 없습니다.
- **판단:** `cancel` 에서 PREP_ACTIVE 검사를 `requireDirect` 뒤에 두었습니다. 권한 없는 사용자는 403 APPROVAL_REQUIRED 를 먼저 받습니다.
- **가정:** 시험에서 BID_PREP 에 'CANCELLED' 상태 값 삽입이 제약 없이 되고, 시험 DB 에 BID_CASES 외래키가 없다고 가정했습니다. 기존 시험 `activePrep` 이 같은 방식으로 넣고 있어 문제없을 것으로 봅니다. 실패하면 알려 주세요.
- **이관 [프런트]:** 화면은 409 `detail.code == "PREP_ACTIVE"` 를 받아 `detail.message` 를 보여 주면 됩니다. 단건·일괄·승인 화면 모두 같은 코드가 옵니다.

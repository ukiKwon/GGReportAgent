### 3. 지시와 달라진 점·판단
1. **의견 검증 범위(S2)**: 코디네이터 문구는 `decide` 전체였지만 `BOARD_SUBMIT`일 때만 적용했습니다. 권한 신청 등 기존 유형의 동작(의견 검증)을 바꾸면 "되돌리지 말 것"에 걸립니다. 전 유형에 적용하려면 `ApprovalRequestService.decide`의 `if (BOARD_SUBMIT…)` 조건만 빼면 됩니다. 기존 테스트 영향은 확인하지 못했습니다.
2. **`planSubmit`** 의 `@Transactional(readOnly=true)`를 `@Transactional`로 바꿨습니다. 락 걸린 읽기(FOR UPDATE)를 읽기 전용 트랜잭션에서 하지 않으려는 안전 조치입니다.
3. `BoardMaterialService` 생성자 인자가 늘었습니다(`BoardMaterialAudit`). `new BoardMaterialService(` 직접 호출은 없습니다(grep 확인).
4. 열람 규칙(S4)은 `BoardAccess` 쪽 문서에 "결재선 열람은 review 경로"라고만 있어 그대로 두었습니다.

### 4. 불확실한 곳
- **S5 테스트(`담당에서_빠진_신청자의_결재_취소는_막힌다`)**: SUBMITTED인 자료가 있는 입찰 건에 담당자 변경 신청을 `requestChange`로 올리고 부장이 승인하는 흐름입니다. 019 쪽이 이를 막으면 `requestChange`의 201 단정에서 먼저 실패합니다.
  - 그러면 `BidAssignmentService.applyChange`의 SUBMITTED 처리를 확인해야 합니다.
- 테스트 7은 LEAD 단독 담당과 `assign(bc, MEMBER, LEAD)`, 결재자=HEAD, ADMIN의 `box=all` 200을 시드가 그대로 따른다고 가정했습니다. 안 맞으면 시드와 어긋난 가정부터 보십시오.
- 테스트 8의 "과거 회차 결재자"는 시드에 두 번째 팀장이 없어 `jdbc`로 req2의 단계 결재자를 HEAD로 바꿔 재현했습니다. 다른 팀장 사례는 넣지 못했습니다.
- 테스트 4의 `from_result_name`은 history 응답의 이름 컬럼이 비지 않는다고 가정했습니다.
- `ApprovalIn.Decision.comment`가 null 또는 생략일 때 동작은 기존 `decide` 헬퍼(comment:null)와 같은 경로입니다. `approveAs`는 comment를 생략하므로, 문제가 있으면 `"comment":null`로 바꾸십시오.
- `ApprovalRequestService`는 `BoardMaterialIn.Rework`을 파라미터로 받습니다. dto→service 의존이 이미 있어 문제는 없습니다.

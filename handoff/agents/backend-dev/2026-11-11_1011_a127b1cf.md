`InboxServiceLimits.MANIFEST`는 가짜 이름이다. 적용 시 `(8 * 1024 * 1024) + 1`로 바꾸거나, `InboxService.MAX_MANIFEST_BYTES`를 쓴다. 이 필드는 package-private이고 테스트는 `web` 패키지라 접근할 수 없으니, 리터럴 `8 * 1024 * 1024 + 1`을 쓰는 편이 간단하다.

## 5. 보안·위험·되돌리는 법
- **자기신고 한계**: 가드는 `X-Emp-No` 위에 선 업무 규칙이다. 남의 영업팀 사번을 헤더에 넣으면 반입할 수 있다. 가드를 달았다고 "검증된 반입자"가 되지는 않는다. 앞단 인증이 붙기 전까지의 한계이고 NEXT 35와 같다.
- **접근 이력**: 401·403은 `DENIED`로 남고 본문과 쿼리값은 넣지 않는다(고정 문구, `MenuGuard`와 동일 호출). 성공 호출의 사번 기록은 `AccessLogInterceptor`가 맡는다. 이 기록이 실제로 남는지는 못 봤으니, security가 확인해야 한다. 반입한 사람과 배치 해시를 별도 감사 행으로 남기는 일(C6)은 이번에 넣지 않았다.
- **트랜잭션 범위**: DB는 롤백되지만 파일 이동은 롤백되지 않는다. 기존 설계 그대로 "DB 먼저, 파일 나중" 순서를 지켰다. 첨부 이동 중 실패하면 DB는 커밋되고 배치는 inbox에 남는다. 다시 부르면 upsert라 안전하다.
- **S5 한계**:
  - Windows junction은 못 잡는다.
  - 첨부는 형식·크기 제한과 sha256 대조가 없다(C6 잔여).
  - 첨부 `REPLACE_EXISTING`(S9 후반)도 그대로다.
  - `BatchSchema.validate` 안의 첨부 `isRegularFile`은 링크를 따라가지만, `precheck`가 링크를 먼저 거부해서 문제가 되지 않는다.
- **동시 반입**: 같은 배치를 두 사람이 동시에 반입하는 경합은 막지 않았다. 늦은 쪽은 DB를 두 번 upsert하거나 파일 이동에서 500이 난다. 영업팀 누구나 누를 수 있으므로 현실적인 위험이다. 후속 항목으로 둔다.
- **되돌리는 법**: `InboxController` 가드 호출 2줄을 지우면 S1 이전 상태이고, `InboxDbApplier`와 `InboxService` 변경을 되돌리면 S4 이전 상태다. DB 스크립트 변경은 없고(mysql/oracle 쌍 불필요) 응답 계약도 안 바뀐다. 다만 `archived_to`가 중복 시 `_2`를 달고, 크기 초과나 링크 배치는 새 오류 문구를 돌려준다.

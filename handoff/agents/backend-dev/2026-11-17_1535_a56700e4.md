## 2. 원인 (근거)
확정된 사실:
- 실패 응답은 `originals_deleted:true`에 "배치를 보관하지 못했습니다."입니다. 이 문구는 InboxService:361의 `catch (IOException)` 한 곳에서만 나옵니다. 409 문구(:354)는 아닙니다.
- `originals_deleted:true`는 ExtCheckImporter.scrub(:549)가 성공했다는 뜻입니다. 즉 삭제는 끝났고 `Files.move(batchDir, destination)`(InboxService:358)만 실패했습니다.
- 이름 충돌은 원인이 아닙니다. 시험마다 고유 base 폴더를 쓰고, :352의 루프가 `_2..` 접미사로 충돌을 피합니다.

핸들 누수 후보를 점검한 결과, 코드에서는 누수를 찾지 못했습니다.
- 원본(`files/*`)을 여는 곳은 `copyToTemp`(Importer:371) 한 곳이고, try-with-resources로 닫힙니다.
- Inspector는 서버 임시 폴더의 사본(`extchk-*`)만 엽니다(Inspector:305, :326, :332). 사본은 batchDir 안에 있지 않습니다. TIMEOUT 뒤에 계속 도는 스레드가 있더라도 batchDir의 핸들은 아닙니다.
- `Files.walk`(InboxService:117)와 `DirectoryStream`(Importer:551, :569)은 모두 try-with-resources입니다. FileInputStream은 main에 없습니다.
- 그래서 앞 시험의 TIMEOUT·hwplib 스레드나 Windows 전용 "원본 못 지움" 시험이 이 시험의 batchDir 핸들을 남길 경로는 보이지 않습니다. 앞 시험은 다른 base 폴더를 씁니다.

가장 유력한 원인:
- Windows는 디렉터리를 rename할 때 안쪽 파일에 **다른 프로세스나 스레드의 열린 핸들**이 있거나, 삭제 대기 상태(pending-delete) 파일이 남아 있으면 `AccessDeniedException`으로 실패합니다.
- 이 시험은 방금 `files/`에 PDF를 쓰고, 읽고, 지웠습니다. 이 시점에 Windows Defender 같은 백신이나 검색 인덱서가 그 파일을 잠깐 쥐고 있을 수 있습니다.
- 순서를 바꾸면 JIT·클래스 로딩·디스크 캐시 상태가 달라져 이 시간 간격이 어긋나므로 순서에 따라 나타납니다.
- 이 추정이 맞다면 운영 서버에서도 같은 일이 일어날 수 있습니다. 운영 코드가 이동 실패에 아무 대응이 없다는 점이 결함입니다.

**운영 결함:** 원본은 이미 지웠고 DB도 이미 저장됐는데, 이동 한 번이 일시 실패하면 500을 돌려줍니다. 이때 batch_id는 이미 반입된 것으로 남아 재시도가 불가능합니다(BATCH_ALREADY_IMPORTED).

```java
     * 복사 폴백은 원본 폴더를 못 지워도 보관본을 우선한다(남은 폴더는 로그만 남기고 사람이 정리).
     */
    private static void moveBatchDir(Path src, Path dst) throws IOException {
        IOException last = null;
        for (int attempt = 0; attempt < 6; attempt++) {
            try {
                Files.move(src, dst);
                return;
            } catch (java.nio.file.FileAlreadyExistsException e) {
                throw e;                                   // 경합 — 덮어쓰지 않는다
            } catch (IOException e) {
                last = e;
                try {
                    Thread.sleep(100L * (attempt + 1));
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
        }
        // 폴백: 새 폴더에 일반 파일만 복사(링크는 따라가지 않는다 — 외부 확인 배치는 scrub 후 manifest.json 뿐)
        try {
            Files.createDirectory(dst);
            try (java.nio.file.DirectoryStream<Path> ds = Files.newDirectoryStream(src)) {
                for (Path p : ds) {
                    if (Files.isRegularFile(p, LinkOption.NOFOLLOW_LINKS)) {
                        Files.copy(p, dst.resolve(p.getFileName().toString()));
                    }
                }
            }
        } catch (IOException e) {
            ExtCheckImporter.deleteTree(dst);              // 반쪽 보관본을 남기지 않는다
            throw last != null ? last : e;
        }
        if (!ExtCheckImporter.deleteTree(src)) {
            log.warn("배치 보관은 복사로 끝냈지만 inbox 의 원래 폴더를 지우지 못했습니다(수동 정리 필요).");
        }
    }
```

## 4. 시험
- 시험 수정은 필요 없습니다. 운영 패치만으로 해결될 것으로 봅니다.
- 시험 쪽 위험은 `InboxTestRoots.close()`가 못 지운 폴더를 조용히 넘기는 것뿐입니다. 이건 의도된 동작이라 유지합니다.
- 추가 시험(선택): 이동을 강제로 실패시키는 건 Windows에서만 가능합니다. `batches/<id>` 쪽이 아니라 **batchDir 안 파일을 FileInputStream으로 연 채** import를 부르는 시험은 FileInputStream이 FILE_SHARE_DELETE 없이 열리면 scrub이 먼저 실패해서 이동 단계에 도달하지 않습니다. 따라서 단위 시험은 만들기 어렵고, 재시도 경로는 확인 명령으로 확인하는 쪽을 권합니다.
- 호출자가 실행할 명령(8080 서버가 같은 target/을 쓰면 먼저 멈추고, 시험 뒤 재기동):
  1. `cd kgi-ggreport-web && mvn -q -o test -Dsurefire.runOrder=reversealphabetical -Dtest="InboxApiTest,InboxExtCheckApiTest,InboxTxRollbackTest"` — 패치 전에 한 번 돌려 `target/surefire-reports`나 콘솔에서 `배치 보관 실패 ... <예외 클래스명>`을 확인합니다. 패치 전 코드에는 이 로그가 없으므로, 패치를 먼저 적용하고 돌린 뒤 로그에 예외명이 찍히는지 보세요. AccessDeniedException이면 위 추정이 맞습니다. 재시도로 통과하면 확정입니다.
  2. 같은 명령을 3~5회 반복해 재현이 사라졌는지 확인합니다.
  3. 정순서 전체: `mvn -q -o test` (380건).
- 확인이 필요하면: 실패가 계속되면 `target/inbox-test-run/r-*/inbox/<id>` 폴더를 Sysinternals `handle.exe`나 리소스 모니터로 열어 누가 쥐는지 봐 주세요.

## 5. 보안·위험·되돌리는 법
- 새 권한 경로는 없습니다. 403 경로와 접근 이력 기록은 그대로입니다.
- 로그에는 batch_id(형식 검사 통과값)와 예외 클래스 이름만 남깁니다. 경로·메시지·값은 남기지 않습니다. 응답 문구도 그대로입니다.
- 폴백 복사는 링크를 따라가지 않고(NOFOLLOW) 일반 파일만 복사하며, 원본 삭제는 기존 deleteTree(링크는 링크만 지움)를 씁니다.
- 되돌리기: moveBatchDir 호출을 `Files.move(batchDir, destination)`로 되돌리면 이전 동작입니다.
- 자기신고 인증(X-Emp-No)의 한계는 이번 변경과 무관합니다.

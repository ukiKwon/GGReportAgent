     * (BoardMaterialController·InstitutionHeadController 와 같음, 기존 동작 유지), 사번 없는 401 은 ACCESS_LOG 에만 남긴다.
     * 서비스가 낸 403 은 ACCESS_LOG DENIED(고정 문구)로도 남긴다. 응답(상태·본문)은 바꾸지 않는다.
     */
    private Map<String, Object> audited(HttpServletRequest req, Long id, String verb, BoardUiIds.Ui ui,
                                        Supplier<Map<String, Object>> call) {
        try {
            guard.requireActiveUser(req);
        } catch (ApiException e) {
            if (e.getStatus() == 403) {
                auditPrepFailure(id, verb, "DENIED", req, ui);
            }
            throw e;
        }
        try {
            return call.get();
        } catch (ApiException e) {
            auditPrepFailure(id, verb, PrepAudit.outcomeOf(e.getStatus()), req, ui);
            if (e.getStatus() == 403) {
                throw guard.denied(req, e);
            }
            throw e;
        } catch (RuntimeException e) {   // DB 오류 등 — ERROR 로 남기고 그대로 던진다(전역 처리기가 500)
            auditPrepFailure(id, verb, "ERROR", req, ui);
            throw e;
        }
    }

    /**
     * 사전준비 결재의 실패 시도를 따로 커밋해 남긴다. 사전준비가 아닌 유형·없는 요청은 남기지 않는다.
     * 기록이 실패해도 원래 응답을 덮지 않는다 — 서버 로그에 예외 종류만 남긴다(본문·값 없음).
     */
    private void auditPrepFailure(Long id, String verb, String outcome, HttpServletRequest req, BoardUiIds.Ui ui) {
        try {
            ApprovalRequestService.PrepRef ref = requests.prepRefOf(id);
            if (ref == null) {
                return;
            }
            prepAudit.record(ref.getBidCaseId(), PrepAudit.approvalAction(ref.getReqType(), verb),
                    outcome, ref.getStateCd(), null, Actor.of(req), ui);
        } catch (RuntimeException ex) {
            LOG.warn("사전준비 결재 실패 감사를 남기지 못했다: verb={} outcome={} cause={}", verb, outcome, ex.getClass().getSimpleName());
        }
    }

**테스트 위험**
- 세 번째 테스트는 영업팀으로 바꾼 DESIGNER를 지명자로 넣는다. 개설 신청·승인 검증이 지명자의 직위나 결재선까지 보면 201·200이 나오지 않을 수 있다. 그때는 DESIGNER 대신 직접 넣은 BID_ASSIGNMENT 행으로 공동 담당자를 만든다.
- ACCESS_LOG는 REQUIRES_NEW라 테스트가 끝나도 남는다. 경로에 요청 번호가 들어가 다른 테스트와 겹치지 않는다고 봤지만, 실행 결과로 확인이 필요하다.
- ERROR 경로와 감사 실패 격리는 지금 테스트 기반(@MockBean 금지, AppTest 단일 컨텍스트)으로는 일으킬 방법이 없다. 코드 리뷰로 확인한다.

## 5. 보안·위험·되돌리는 법 (security가 볼 포인트)
1. **가림 범위가 선례보다 넓거나 좁지 않은지**
   - 공동 담당자(PLAN_REJECT)와 옛 담당자(CANCEL)는 지금 못 본다. fail-closed로 둔 것이고 열린 질문 1이다.
   - ATTACH_VOID 사유는 가리지 않았다.
   - 첨부 무효 사유 외에 BID_ASSIGN_LOG의 RELEASE·ADD 사유는 다른 API로 나가며 이번 범위 밖이다.
2. **결재함 경로로 같은 사유가 새는지**: 확인하지 못했다. 예를 들어 `/approval-requests?box=mine` 응답에 반려 의견이 실리는지는 보지 않았다. 그쪽은 결재 당사자 기준이라 이력 가림과 범위가 다를 수 있다.
3. **비활성 403의 BID_PREP_ACT 기록**: security 1637은 "401·비활성은 BID_PREP_ACT에 남기지 않는다, PrepController와 맞춘다"였다. 이 안은 비활성 403을 **남긴다**.
   - 이유 ①: 지금도 서비스 403 경로로 남고 있어, 빼면 감사가 줄어든다.
   - 이유 ②: Board·InstitutionHead 컨트롤러가 이미 남긴다.
   - 이유 ③: 사용자 목표가 "모든 행위 기록"이다.
   - 그러면 반대로 PrepController.run이 비활성 403을 안 남기는 쪽이 어긋난다. 판정을 요청한다.
4. **접근 이력 DENIED의 why**: 서비스의 사용자용 고정 문구를 그대로 쓴다(PrepController와 같다). 사번·이름·사유 값은 넣지 않는다.
5. **감사 실패 로그**: 예외 클래스 이름만 남기고 메시지(SQL·값)는 남기지 않는다.
6. **인증 한계**: 모든 판정은 X-Emp-No 자기신고 위의 업무 규칙이다. 사칭을 막지 않고, 사유 가림도 사번을 위조하면 뚫린다. 화면·버튼 식별자도 자기신고다.
7. **되돌리기**: 두 파일과 테스트 4건을 git revert하면 된다. DB·스키마는 바뀌지 않고 BID_PREP_LOG 원본도 그대로다.

## 7. 열린 질문
1. 확정 취소·중단·사전준비 승인 반려 사유를 **그 건의 담당자**에게도 보일지 정해야 한다. 공동 담당자는 사전준비 승인 반려 의견이 대상이고, 옛 담당자는 중단 사유가 대상이다.
   - 이 안은 선례대로 "당사자(신청자·작성자·확정자)·팀장·부장"만 보게 해 두었다.
   - **권장: 보이기.** 반려 의견은 담당자들이 고쳐야 할 내용이다. 중단 사유는 옛 담당자가 이미 읽기 전용으로 기록을 보는 범위(사용자 답 11-11)의 일부다.
   - 답이 오면 `canSeeReason`에 `assignments.isActiveAssignee`·`mapper.countEverAssigned` 조건 한 줄을 더하고, 테스트 두 곳의 기대값을 뒤집는다.
2. 첨부 무효 사유(ATTACH_VOID)를 지금처럼 이력을 볼 수 있는 사람 모두에게 둘지 정해야 한다. 권장: 유지(작업 메모 성격).

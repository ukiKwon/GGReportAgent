## 2. 요구 요약과 판단 (근거 파일:줄)

**공고 정보를 사전준비 상세 응답에 함께 싣는다.** 상세 응답에 `nobid_notice`를 더하고 별도 GET은 만들지 않는다. 이유는 셋이다.
1. 팝업은 사전준비 상세에서 건 하나를 열 때만 뜬다(디자인 6-1). 디자인은 "상세와 공고 정보가 둘 다 도착한 뒤에만 띄운다"고 했다. 응답이 하나면 도착 순서를 맞출 필요가 없다.
2. 열람 규칙을 상세와 똑같이 쓴다(`PrepService.visible`, `PrepService.java:715-721`, 못 보면 404). 그래서 새로 노출되는 길이 생기지 않는다.
3. 장애를 상세와 분리한다. 공고 정보는 별도 빈·별도 트랜잭션에서 읽고, 컨트롤러는 `DataAccessException`만 잡아 `nobid_notice=null`로 둔다. 표가 아직 없는 DB(배포 순서를 어긴 경우)에서도 상세는 그대로 나간다. "공고 정보를 못 불러오면 팝업도 사실 줄도 없다"는 디자인 규칙과 맞는다.
- 대가: 쓰기 응답(과제 체크 등, `PrepService.view` 재사용)에는 이 필드가 없다. 프런트가 직전 값을 유지해야 한다(이관).

**경로는 건 기준이다.** `POST /bidcases/{id}/prep/nobid-ack`로 둔다. 기관은 서버가 BID_PREP에서 읽으므로 경로에 기관 id가 없다. 그래서 보안 권장의 "없는 기관 404"는 "없는 건·못 보는 건 404"로 바뀐다. 역할 403은 그보다 먼저 판정한다.

**취소 판정은 한 곳에 둔다(보안 중-1).** `viewer.can_unconfirm`·`can_cancel`(`PrepService.java:1013-1020`)의 식을 package static 메서드 `canUnconfirm`·`canCancel`로 꺼냈다. viewer와 새 서비스가 이 둘을 함께 쓴다. HeadRules는 쓰지 않는다. 동작은 바뀌지 않는다(식이 같다).

**본문에는 `handled_at` 대신 `rev_no`를 받는다(보안 권장 4를 바꾼 부분).**
- 권장 3에 따라 `handled_at`은 map 권한자에게만 내준다. 그러면 map이 없는 수신자는 그 값을 POST할 수 없다.
- 그래서 본문은 `{round_seq, rev_no}`(정수 1~999999)만 받는다. 서버는 이 둘로 최신 여부를 확인하고, INSERT 값(handled_at·rev·건·상태)은 모두 서버가 다시 읽은 값을 쓴다.
- 닫힌 NO_BID 회차에는 새 기록이 붙지 않는다(`NoticeRoundService.java:191-198`). 따라서 (round, rev)로 최신 여부를 판정해도 충분하다.
- 보안 재확인이 필요하다(이관).

**받는 사람**(디자인 권장, 호출자 지시): 담당자·정리 권한자·영업팀장·영업부장. 단 디자이너는 담당자여도 제외한다(POST 역할 403과 일치시킨다).

    /** 활성 건 + 그 기관의 입찰 없음 닫힌 마지막 회차 + 기관 자료가 넘어가지 않음. 아니면 null. */

        if (!ACTIVE_STATES.contains(p.getStateCd())) {
            return null;
        }
        List<NoticeRoundView> rows = rounds.selectClosedNoBidOne(p.getInstitutionId());
        if (rows.isEmpty()) {
            return null;
        }

        String base = v.getClosedLastBid() != null ? v.getClosedLastBid() : v.getAnchorLastBid();   // NoticeRoundService.current() 와 같은 기준

    /** 팝업 받는 사람 — 영업 계열(디자이너 제외) 중 팀장·부장, 활성 담당자, 개설 전 건의 확정 취소 권한자(design 11-19 권장). */
    private boolean isRecipient(SysUser me, BidPrep p) {
        if (!PrepService.isSalesOrHead(me)) {
            return false;
        }
        if (PrepService.isLeadOrHead(me)) {
            return true;
        }
        if (assignments.isActiveAssignee(p.getBidCaseId(), me.getEmpNo())) {
            return true;
        }
        String st = p.getStateCd();
        return (PrepService.CONFIRMED.equals(st) || PrepService.OPEN_PENDING.equals(st))
                && PrepService.hasUnconfirmAuthority(me, p);
    }

    /** [제안 진행 정리하기] 버튼 판정 — 실행은 기존 unconfirm·cancel API 가 다시 판정한다. 막힌 상태 코드는 언젠가 정리할 권한이 있는 사람에게만. */
    private static String tidyAction(SysUser me, BidPrep p) {
        if (PrepService.canUnconfirm(me, p)) {
            return TIDY_UNCONFIRM;
        }
        if (PrepService.canCancel(me, p)) {
            return TIDY_CANCEL;
        }
        if (PrepService.OPEN_PENDING.equals(p.getStateCd()) && PrepService.hasUnconfirmAuthority(me, p)) {
            return TIDY_OPEN_PENDING;   // 개설 신청을 먼저 회수·반려
        }
        if (PrepService.APPROVAL_PENDING.equals(p.getStateCd()) && PrepService.hasCancelAuthority(me)) {
            return TIDY_PLAN_PENDING;   // 사전준비 승인 요청을 먼저 회수·반려
        }
        return TIDY_NONE;
    }

    private static int checkedNo(Integer v) {
        if (v == null || v.intValue() < 1 || v.intValue() > NO_MAX) {
            throw coded(400, "BAD_VALUE", "확인한 공고 기록 번호(round_seq·rev_no)가 올바르지 않습니다.");
        }
        return v.intValue();
    }

    private static ApiException coded(int status, String code, String message) {
        Map<String, Object> d = new LinkedHashMap<String, Object>();
        d.put("code", code);
        d.put("message", message);
        return ApiException.withDetail(status, d);
    }

    private static final Path DB = Paths.get("src/main/resources/db");
    private static final String FILE = "0NN_prep_nobid_ack.sql";
    private static final String TABLE = "PREP_NOBID_ACK";
    private static final String PK_COLS = "(EMP_NO, INSTITUTION_ID, ROUND_SEQ, NOTICE_HANDLED_AT)";

    private static String read(String d) throws IOException {
        Path f = DB.resolve(d).resolve(FILE);
        assertTrue(f + " 가 없다 — 작업 디렉터리가 kgi-ggreport-web/ 인지 확인", Files.exists(f));
        return new String(Files.readAllBytes(f), StandardCharsets.UTF_8).replaceAll("--[^\\r\\n]*", "");   // 주석 제거
    }

    private static List<String> columns(String d) throws IOException {
        List<String> out = new ArrayList<>();
        Set<String> skip = new HashSet<>(Arrays.asList("PRIMARY", "KEY", "CONSTRAINT", "UNIQUE", "INDEX", "FOREIGN", "CHECK"));
        Pattern word = Pattern.compile("^([A-Z][A-Z0-9_]*)\\b.*");
        boolean in = false;
        for (String raw : Files.readAllLines(DB.resolve(d).resolve(FILE), StandardCharsets.UTF_8)) {
            String line = raw.trim();
            if (line.startsWith("CREATE TABLE " + TABLE + " (")) { in = true; continue; }
            if (!in) continue;
            if (line.startsWith(")")) break;
            Matcher m = word.matcher(line);
            if (m.matches() && !skip.contains(m.group(1))) out.add(m.group(1));
        }
        return out;
    }

    @Test
    public void 칸_이름과_순서가_같고_일련번호_칸이_없다() throws IOException {

        assertTrue(read("mysql").contains("PRIMARY KEY " + PK_COLS));
    }

    @Test
    public void Oracle은_11g_문법이고_MySQL은_utf8mb4를_먼저_지정한다() throws IOException {
        String o = read("oracle");
        assertFalse(o.contains("GENERATED BY"));
        assertFalse(o.contains("FETCH FIRST"));

## 5. 보안·위험·되돌리는 법
- **권한 순서**
  - POST: 활성 사용자(401/403 DENIED) → 역할(영업팀·영업팀장·영업부장, 403 DENIED) → 본문(400 BAD_VALUE) → 건 열람(404, 상세와 같은 규칙) → 받는 사람(403 DENIED) → 대상 여부(409 NOT_APPLICABLE) → 최신 여부(409 NOTICE_CHANGED) → INSERT(중복이면 200 saved=false).
  - GET은 상세의 열람 규칙을 그대로 쓴다.
  - 남는 한계: JSON 문법 자체가 깨진 본문은 기존 엔드포인트와 똑같이 컨트롤러 앞에서 400이 된다(역할 검사보다 먼저).
- **기록**
  - 성공·실패 모두 `BID_PREP_ACT`(NOBID_ACK, OK·DENIED·HIDDEN·BLOCKED·INVALID·ERROR)에 남는다.
  - 성공은 `PREP_NOBID_ACK` 한 줄로 남는다.
  - 접근 이력 DETAIL:
    - 성공 `nobid-notice ack inst=<기관>`
    - 실패 `nobid-notice ack <상태> <CODE>`
    - 상세 `… code=VIEW nobid=Y|N|-`
  - 공고 시각·기록자 이름·본문은 어느 기록에도 넣지 않는다.
- **노출**
  - `handled_at`·`handler_name`·`emp_verified`·`can_view_notice`는 `canView(emp,"map")`일 때만 싣는다(중-4).
  - 다른 사람의 ack 기록은 응답에 없다.
- **자기신고 인증의 한계(수용 위험, 하-5)**: `X-Emp-No`를 바꿔 POST하면 다른 사람의 알림을 끌 수 있다. 사칭 방지가 아니고 업무 규칙이다. `EMP_VERIFIED=0`이 정상값이며, 어떤 화면에서도 '본인 확인됨'으로 표시하지 않는다.
- **위험**
  1. 배포 순서를 어기면(DB가 서버보다 늦으면) 상세는 정상이고 알림만 빠진다. POST는 500이 된다.
  2. 판정이 `INSTITUTIONS.LAST_BID`에 의존한다. 기관 자료가 넘어가면 알림이 사라진다. `current()`와 같은 동작이다.
  3. 쓰기 응답(과제 체크 등)에는 `nobid_notice`가 없다. 프런트가 덮어쓰면 사실 줄이 사라진다(이관).
  4. 같은 기관에 활성 건이 둘 있는 비정상 데이터에서는 건마다 따로 판정된다. 기록 키는 기관 단위라 한 번 누르면 둘 다에서 꺼진다.
- **되돌리기**
  - 코드: 새 파일 5개(서비스·매퍼 2·시험 3)를 지운다. PrepController·PrepService·PrepUiIds·NoticeRoundMapper·PrepIn·properties·PrepAuditIsolationTest의 diff를 되돌린다.
  - DB: `DROP TABLE PREP_NOBID_ACK;`(기록 소멸, 운영 금지). 코드만 되돌리면 표는 읽히지 않을 뿐 해가 없다.

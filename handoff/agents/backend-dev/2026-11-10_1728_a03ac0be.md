## 2. ① 표 설계 (DDL 초안, 번호 024·025)
**번호**: 마지막 파일은 `020_board_material`이다. NEXT가 021(제출 흐름)·022(MENU_ORDER)·023(approval_step_verified)을 예약해 두었으므로 **024_bid_prep**(과제 정의·상태·진행·이력·감사)과 **025_bid_prep_attach**(첨부)로 제안한다. 둘 다 019의 `COMMON_CODE`에만 의존하고 021~023과 독립이다. 이미 020까지 적용한 MySQL은 024, 025를 번호 순서로 한 번씩 이어서 실행한다(멱등 아님). 테스트 `application.properties`의 H2 체인에 번호순으로 덧붙이는 일은 020a가 끝난 뒤 한다(§5). Oracle은 정본 작성까지만 하고 적용은 DBA 몫이다.

**설계 결정**
- **'기획승인 가능'은 저장하지 않고 파생한다.** 필수 과제가 모두 완료됐는지를 읽을 때마다 계산한다. 저장 상태를 따로 두면 T3·T5 같은 사실 판정과 어긋날 수 있어서다.
  - 저장하는 상태는 7개다: `CONFIRMED`·`OPEN_PENDING`·`IN_PROGRESS`·`APPROVAL_PENDING`·`WRITABLE`·`WRITING`·`CANCELLED`.
  - planner의 상태표(6개)와 한 칸 다르다. 응답에 `plan_approval_ready`(참/거짓)를 따로 준다.
- 건별 과제 진행(`BID_PREP_TASK`)은 **개설 승인 시 정의를 복사(스냅샷)**한다. 그러면 정의를 나중에 고쳐도 진행 중 건에는 영향이 없다(planner 권장 "새로 개설되는 건부터"). `READY_YN`(준비중)만 정의를 실시간으로 읽는다. T4·T6 실물이 오면 진행 중 건에도 켜진다.
- 사실 판정 과제(T3·T4·T5)는 `DONE_YN`에 **마지막 판정값**을 저장한다. 건 상세를 읽을 때와 기획승인 상신·승인 때 판정값과 비교한다. 달라졌으면 조건부 UPDATE와 `AUTO_UNDONE` 이력(행위자 NULL=시스템)을 남긴다. security E의 "자동 미완료 전환 기록"을 이렇게 맞춘다. 020 상태가 바뀔 때 부르는 후크는 020b 뒤에 붙인다.
- T1·T2의 '체크 전제'(저장본 ≥1, 인물 ≥1+출처)는 **서버 쪽 저장본이 아직 없다.** 기관 요약·프로필의 서버 저장은 NEXT 72에서 정해진다. 그래서 `PRECOND_KEY`는 칸만 만들고 시드는 NULL로 둔다. 이 상태에서는 담당자가 체크하면 통과한다. 이는 security A3("전제를 서버가 확인")의 일부 미충족이며 이관 메모에 적었다.
- 외래키·CHECK·UNIQUE는 없다(PK와 인덱스만). 기관+회차당 진행 건 1개는 **INSTITUTIONS 행 `FOR UPDATE` 잠금 + 활성 상태 존재 확인**으로 직렬화한다(security A3, UNIQUE는 DBA 답 대기).
- 열람 감사는 020의 `BOARD_MATERIAL_ACT`를 일반화하지 않고 **같은 모양의 `BID_PREP_ACT`를 따로** 둔다. 020a가 아직 변하는 중이라 의존을 만들지 않으려는 것이다. 합칠지는 020a 리뷰 뒤 다시 정한다.

## 3. ③ 019 재사용 범위와 개설 대기 저장 위치
**개설 대기 저장 위치**
- 지명자 목록은 **결재 요청(`APPROVAL_REQUEST.payload`)에만** 둔다. `{bid_case_id, nominee_emp_nos[1..10], comment}`는 4000자 안에 들어간다.
- 진행 중 신청 1건의 선점은 `BID_PREP.OPEN_REQ_ID`가 한다. 019는 `BID_ASSIGN_CASE.PENDING_REQ_ID`를 썼다. 개설 대기 중에는 `BID_ASSIGN_CASE`가 없다(배정 머리 행은 승인 때 처음 생긴다).
- `BID_ASSIGNMENT`는 개설 대기 중 한 행도 쓰지 않는다. 그래서 `isActiveAssignee`가 판정하는 사전준비·020 권한이 지명자에게 자동으로 없다(security A4). 테스트로 확인한다(§6).
- 끝난 요청(반려·회수)은 `OPEN_REQ_ID`가 가리켜도 PENDING이 아니면 비어 있는 것으로 본다. 019와 같은 읽기 방식이며, 거기에 반려·회수 후크로 `CONFIRMED` 복귀를 더한다(020 v2 `backToDraftByReq` 패턴).

**재사용하는 것**
- 결재자 계산(`resolveApprover`). 상신자나 지명자 중 영업팀장이 있으면 영업부장이다. 019와 달리 "현재 담당자"는 없다.
- 지명 대상 검증(`requireAssignable`·`normalize`·인원 1~10), 배정 행 insert와 `ASSIGN` 이력(`insertAssignment`·`insertLog`).
- `NO_PROXY`(대결 금지). 새 유형 `BID_OPEN`과 `PREP_APPROVAL`을 여기에 넣는다.
- 승인자≠상신자·승인자∉지명자 방어(`applyChange`의 승인자=수혜자 규칙).

**새로 만드는 것**
- `BidAssignmentService`에서 `create`의 핵심(머리 행+배정 행+ASSIGN 로그)을 `assignInitial(bid, empNos, byEmp, verified, reqId)`로 뽑는다. `applyOpen`이 그것을 부른다. 팀장 직접 최초 배정 경로(B2)는 이 메서드를 부르지 않고 닫는다. **이 수정은 020a 파일이라 020a 뒤에 한다.**
- 개설 승인 처리(`applyOpen`, 같은 트랜잭션)
  1. 조건부 UPDATE `BID_PREP SET STATE=IN_PROGRESS WHERE STATE=OPEN_PENDING AND OPEN_REQ_ID=?`. 0행이면 409.
  2. 지명자 활성·역할 재검사(승인 전에 바뀐 경우 409).
  3. `assignInitial`.
  4. `PREP_TASK_DEF`를 `BID_PREP_TASK`로 복사.
  5. 이력 `OPEN_APPROVE`.
- 담당자 변경 신청(019 `planChange`)은 `NOT_ASSIGNED` 409 때문에 개설 전에는 자동으로 막힌다. 개설 대기 중 변경 신청 불가라는 planner 규칙과 같다.

**첨부 검사 순서(71, D1~D5 반영)**
1. 본문 상한(필터)
2. 확장자 허용 목록: xlsx·docx·pdf·hwpx. `.hwp`·xlsm·docm·xls·doc·zip은 거부.
3. 매직 바이트: OOXML·hwpx는 `PK`, pdf는 `%PDF`. HWP(`D0CF11E0`)는 400.
4. OOXML·hwpx는 `ZipGuard.check`(엔트리·합계 상한, 중복 엔트리, DOCTYPE 거부)와 `vbaproject`·`activex` 엔트리 거부. pdf는 pdfbox를 임시 파일 모드·페이지 수와 시간 상한으로 열고 `/JavaScript`·`/Launch`·`/EmbeddedFile`이 있으면 거부.
5. 텍스트 추출 후 `Pii.scan`. **차단은 주민등록번호·외국인등록번호·카드번호만**이다(Finding.kind). 이메일·휴대폰은 경고 후 저장하고 `PII_NOTE`에 종류·건수만 남긴다. 텍스트가 안 나오는 스캔 PDF는 `PII_STATE=UNCHECKED`로 저장해 목록에 표시한다. 전각 숫자는 정규화한다(security D5).
6. 서버가 만든 32자리 키로 임시 파일→이동으로 저장한다. 정규 경로가 저장 루트 아래인지 확인한다. DB insert가 실패하면 파일을 지운다. 크기 기본값은 파일당 30MB, 건당 합계 300MB·50개다.
- 저장 위치는 파일 시스템(`ggreport.prep-attach-dir`)이 기본 제안이다. 대안은 Oracle BLOB이다. 백업에 이 폴더가 들어가야 한다(열린 질문 2).

- **자기신고 한계**: 모든 판정(활성 담당자·영업팀장·영업부장·상신자)이 `X-Emp-No` 위에 있다. 앞단 인증이 없으면 남의 사번으로 행세할 수 있다. 이 설계는 실수 방지와 사후 추적(`EMP_VERIFIED`·`UI_VALID`)이지 사칭 방지가 아니다. 근본 해결은 SSO(NEXT 35)다.
- **스위치 위험**: `ggreport.legacy-flow.open=true`가 운영 설정에 남으면 B1·B5가 통째로 풀린다. 기본값 false, 켜면 기동 시 WARN을 남기고, README에 쓴다. 테스트용 `setOpenForTest`는 `@After` 복구를 빼먹으면 이후 테스트가 닫힘 상태로 돌아 연쇄로 깨진다(try/finally로 막아야 한다).
- **B1 닫는 타이밍**: 위 0-2. 프런트 카드 제거 없이 닫으면 기존 화면에서 410 오류가 보인다.
- **`forAssignee`의 이름 일치**는 사번이 아니다. 동명이인이면 서로의 담당 건을 볼 수 있다. 이 경로는 프런트가 안 쓰므로 영향이 작다. 쓰지 않으면 삭제가 정답이고, 삭제는 골든 25 개정이 따라야 한다(열린 질문 1).
- **B4는 영업부장을 차단**한다(security 조건대로). 지금 화면의 ▶ 실행 버튼을 영업부장이 쓰고 있었다면 막힌다. planner·사용자 확인이 필요하다(열린 질문 3).
- **J-3 공고 전 확정**: '확정'이 공고 없는 건을 만들면 공고 반입이 둘로 갈린다. 반입 쪽 수정(§5)이 같은 릴리스에 들어가야 한다. 안 하면 한 기관에 두 건이 생긴다. 회차(입찰 건이 끝났다고 보는 시점)를 어디로 볼지는 planner 몫이다. 73(결과 등록)이 없는 지금은 활성 상태(`CONFIRMED`~`WRITING`)가 계속된다.
- **5번 게이트와 그래프**: `orchestrator.resume`은 게이트가 대기 중일 때만 동작한다(없으면 409 `no pending gate`). 부장이 기획승인을 눌렀을 때 분석이 아직 5번 게이트에 도달하지 않았을 수 있다. 권장은 "승인 기록을 남기고 게이트 도달 시 자동 통과"이고 `OrchestratorService` 수정이 필요하다(이번에 읽지 못했다).
- **파일 저장**: 서버 디스크가 정본이 된다. 디스크 용량·백업·접근 권한(OS 수준)이 필요하고, DB 롤백과 파일이 어긋난 고아 파일을 정리해야 한다. pdfbox 2.0.29를 신뢰할 수 없는 PDF에 쓰는 데 이후 CVE가 있는지는 확인이 필요하다(security 참고사항).
- **계정 데이터 전제**: 테스트 시드에 영업팀장 2명(5047192·5640327)·영업부장 2명(2674805·1473958)이 있다. 019의 "그 역할 활성이 정확히 1명이 아니면 `APPROVER_NOT_RESOLVED`" 규칙은 상신자의 `approverEmpNo`가 있으면 그것을 먼저 쓴다. 개설 결재 상신에서도 같은 방식으로 풀리는지 구현 때 확인한다.
- **되돌리는 법**: 코드는 커밋 단위로 되돌린다. 스위치 설정으로 B1·B5 효과만 즉시 되돌릴 수 있다. 024·025는 헤더의 `DROP TABLE`·`DELETE`(데이터 소멸, 운영 금지)로 되돌리고, 먼저 진행 중 `BID_OPEN`·`PREP_APPROVAL` 요청을 취소한다.

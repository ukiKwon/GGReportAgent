## 2. 원인
- uploader/src/test/resources/application.properties:18-19는 `spring.sql.init.schema-locations=classpath:schema-mysql.sql`, `mode=always`만 지정한다. **`spring.sql.init.encoding`이 없다.**
- Spring Boot의 SQL 스크립트 초기화는 encoding을 지정하지 않으면 JVM 기본 charset(`file.encoding`)으로 읽는다. 이 PC의 JDK 8은 기본값이 MS949로 추정되므로, UTF-8 한글 컬럼명이 `?뾽濡쒕뱶…`로 깨진다. 이 때문에 H2에서 구문 오류가 나고 ApplicationContext 로드가 실패한다.
- 옛 PC는 기본 인코딩이 UTF-8이었거나 환경변수(JAVA_TOOL_OPTIONS 등)로 맞춰져 있었을 가능성이 크다. 추정이다.
- 비교: kgi-ggreport-web/src/test/resources/application.properties:41에는 `spring.sql.init.encoding=UTF-8`이 이미 있어서 같은 문제를 피한다. uploader 쪽에만 빠져 있다.
- H2 `MODE=MySQL`(12줄)은 이미 설정돼 있어 원인이 아니다.
- uploader/pom.xml에는 surefire argLine이나 file.encoding 설정이 없다(grep 결과 없음).
- 운영 영향: 이 properties는 테스트 클래스패스에만 있고 WAR에는 들어가지 않는다(파일 1-5줄 주석). schema-mysql.sql 자동 실행은 테스트(H2)에서만 일어난다(README 396줄, DEPLOY.md 37줄). 운영 WebLogic과 out-local은 영향이 없다.

## 3. 구현안 (시험 설정만 고침, 본 설정은 건드리지 않음)
파일: c:\github\GGReportAgent\uploader\src\test\resources\application.properties
```
 # H2 스키마 초기화
 spring.sql.init.schema-locations=classpath:schema-mysql.sql
 spring.sql.init.mode=always
+# 스크립트를 JVM 기본 인코딩(Windows JDK8 = MS949)이 아닌 UTF-8로 읽는다 — 한글 컬럼명 깨짐 방지
+spring.sql.init.encoding=UTF-8
```
- 이 한 줄이 최소 수정이다. DB 스크립트 변경이 없으므로 mysql/oracle 쌍과 마이그레이션은 해당 없다.
- 선택 사항(권장하지 않음): pom surefire에 `-Dfile.encoding=UTF-8`을 더하면 다른 곳의 기본 charset 의존(파일 읽기 등)까지 가린다. 그러나 pom은 운영 빌드와 공유되므로 이번에는 넣지 않는다. 같은 증상이 다른 테스트에서 또 나올 때만 검토한다.
- 한글이 든 파일이라 PowerShell로 재작성하면 안 된다(CLAUDE.md 7절). 이 한 줄은 Edit 도구로 추가한다.

## 4. 테스트
- 깨질 기존 테스트는 없다. 고쳐질 대상은 ApplicationContextTest 3건이다.
- 호출자가 돌릴 명령: `cd c:\github\GGReportAgent\uploader && mvn -q -o test`. 8080 서버가 같은 target을 쓰면 테스트 뒤에 재기동한다.
- 그래도 실패하면 아래를 확인한다.
  1. schema-mysql.sql에 BOM이 있는지, 파일이 UTF-8인지(`file` 명령 또는 에디터 하단 표시).
  2. 컨텍스트 로드가 H2에서 다른 구문으로 실패하는지(surefire 리포트 `Caused by`의 `[*]` 위치).
- 보조 확인: `mvn -q -o test -Dfile.encoding=UTF-8`로 한 번 돌려 본다. 통과하면 원인이 인코딩이라는 점이 확정되고, 패치 뒤에는 이 옵션 없이도 통과해야 한다.

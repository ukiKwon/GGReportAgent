## 2. 요구·근거 요약

**047의 Oracle IDENTITY**
- 047은 IDENTITY를 3곳에 쓴다(`047:14,115,132`). 048·051·045는 머리 주석에 "11g 호환: IDENTITY 없음"이라고 적었다(`048:12`, `051:17`, `045:19`).
- 그런데 회의록의 부모 표 020이 이미 IDENTITY다(`020:23,61,82`). 024·026·034도 같고, 002·005·007은 "12c 이상 전제"라고 적었다(`002:26`).
- 그래서 11g에서는 020부터 만들 수 없다. 037 이후의 "11g 호환"은 새 표에 대한 권장일 뿐 전체 전제는 아니다.
- 권장: 047은 IDENTITY를 그대로 둔다. Oracle 파일 머리에 근거 한 줄만 더한다(주석만 바뀌고 MySQL은 바꾸지 않음).
- 바꾸지 않는 이유
  - MINUTES_ID를 자연 키로 바꾸면 자식 7표의 PK가 모두 바뀐다.
  - 추가 전용인 LOG·ACT를 MAX+1로 매기면 전역 잠금이 필요하다.

**020 코드는 바꾸지 않는다**
- 020 판정은 `BoardAccess.java:30-46`, 감사는 `BoardMaterialAudit.java:52-127`, 공통 관문은 `BoardMaterialController.java:189-237`다.
- 회의록은 같은 모양을 새 클래스로 복제하고, 020 클래스는 읽기 호출만 한다.

**크기 필터**
- `BoardWriteLimitFilter`의 `MAT_SMALL`은 `board-materials(/{id}/(submit|withdraw|rework|result))?`만 잡는다(`:55-56`).
- 그래서 `/board-materials/{mid}/minutes`는 `limit=-1`로 통과한다(`:123-128`). 새 필터가 맡아도 기존 필터와 충돌하지 않는다.
- 같은 패키지(`config`)라서 `normalize`와 `CountingRequest`(패키지 전용 static)를 고치지 않고 재사용할 수 있다.

**부장급(H) 판정**
- `ApproverRules.levelByGradeRole(u) >= 2`로 한다. DEPT_HEAD·EXECUTIVE 등급이거나 역할이 `Teams.FINAL_APPROVER`(영업부장)이면 해당된다(`ApproverRules.java:57-69`).
- 역할 상수 `BidAssignmentService.LEAD_ROLE`·`HEAD_ROLE`은 패키지 전용이다(`BidAssignmentService.java:59-61`). 그래서 Access는 `service` 패키지에 둔다.

**`MinutesException` 처리**
- 이 예외는 전역 처리기가 없다(grep 결과 `minutes/` 밖 사용 0).
- 컨트롤러 공통 관문에서 `ApiException.withDetail(e.getStatus(), e.toDetail())`로 바꾼다.

**시각 비교**
- `Times.nowIso()`는 UTC 고정 폭이다(`Times.java:28-47`). 그래서 등록자 기간 컷오프를 SQL에서 문자열로 비교해도 된다.

**digest 성질**
- digest는 가리기 전 정규화 내용으로 만든다(`MinutesParse.java:183,197-239`). 그래서 `PREVIEW_CHANGED`는 파일이 바뀌거나 RULE_VER가 바뀔 때만 난다.
- 가림 단어나 해제 목록을 바꿔도 409가 나지 않는다. 의도된 동작이다.

**이미 적용한 DB 이어 가기**: 바꿀 것 없음. MySQL 047은 손대지 않는다.

**`decide` 판정** (위에서부터 처음 맞는 것)

| 조건 | Via | 허용 |
|---|---|---|
| head가 삭제됨 | 부장급이면 HEAD, 관리자이면 ADMIN, 아니면 NONE | `acts`만, 다른 권한은 모두 false |

  - `stats`, `masked`

- `editMeta`

  - meeting_date이면 엄격한 날짜이고 미래가 아니어야 한다.

**`scopeAdd`·`scopeRemove`** (H만)
- `emp_no`는 `MenuPerms.isEmpNo`를 통과하고 USERS에 ACTIVE로 있어야 한다. 아니면 400 `SCOPE_TARGET_INVALID`이고 값은 되돌려 주지 않는다.
- `grant_until`은 엄격한 yyyy-MM-dd이고 오늘(KST)부터 오늘+365 사이다. 아니면 400 `GRANT_UNTIL_INVALID`.
- 대상이 `isDefaultViewer`이면 200 `{changed:false, reason:"ALREADY_DEFAULT"}`.
- 트랜잭션 처리
  1. `lockHead`
  2. `before = selectScope`로 사번 목록을 읽어 정렬하고 쉼표로 잇는다.
  3. 판정
     - 새 사람이고 이미 30명이면 422 `SCOPE_CAP`.
     - 이미 있고 종료일이 다르면 `updateScopeUntil`(이벤트 SCOPE_EXTEND).
     - 이미 있고 종료일도 같으면 `changed:false`.
  4. 그 밖에는 `insertScope`(SCOPE_ADD).
  5. LOG에 `SCOPE_BEFORE`·`SCOPE_AFTER`(사번 목록만)를 같은 트랜잭션에서 남긴다.
- remove는 없는 사람이면 `changed:false`다.

**`delete`** (H만)
- 본문은 `{rev_no}`. 트랜잭션 처리
  1. `lockHead`, REV 확인
  2. utters·segs·items·scopes·revs를 DELETE
  3. `markDeleted`
  4. LOG DELETE
- 사유 칸은 두지 않는다.

**`history`** (H·U)
- `logs`: `[{event, rev_no, target_kind, target_no, actor_name, at, scope_before_cnt, scope_after_cnt}]`
- `revs`: `[{rev_no, target_kind, target_no, field, old_text, new_text, edited_by_name, edited_at}]`

- 최대 200행.

**`detail` 응답**

```java
private <T> T run(HttpServletRequest req, Ctx ctx, String action, boolean uiRequired, BiFunction<SysUser, Decision, T> call) {
    if (!settings.isEnabled()) throw new ApiException(404, "찾을 수 없습니다.");     // 1. 꺼져 있으면 존재를 숨긴다(ACT 없음)
    Actor actor = Actor.of(req); BoardUiIds.Ui ui = MinutesUiIds.of(req);
    SysUser me;
    try { me = guard.requireActiveUser(req); }                                      // 2. 401·403(ACCESS_LOG DENIED)
    catch (ApiException e) { if (e.getStatus() != 401) audit.record(ctx, action, "DENIED", Via.NONE, actor, ui); throw e; }
    if (settings.isRequireVerified() && !actor.isVerified()) {                       // 3. R20
        audit.record(ctx, action, "DENIED", Via.NONE, actor, ui);
        throw guard.denied(req, ApiException.withDetail(403, detail("VERIFIED_REQUIRED", "이 기능은 사내 인증을 거친 접속에서만 쓸 수 있습니다.")));
    }
    Decision d = ctx == null || ctx.minutesId == null ? null : access.decide(me, mapper.selectHead(ctx.minutesId));
    Via via = d == null ? Via.NONE : d.via;
    try {
        if (uiRequired && !ui.isValid()) throw uiRequired();                         // 4. 400 UI_ID_REQUIRED
        T out;
        try { out = call.apply(me, d); }
        catch (MinutesException e) { throw ApiException.withDetail(e.getStatus(), e.toDetail()); }   // 코드·칸·줄 번호만
        catch (ApiException e) { if (e.getStatus() == 403) throw guard.denied(req, e); throw e; }
        audit.record(ctx, action, "OK", via, actor, ui);                              // 읽기는 응답 전(fail-closed)
        return out;
    } catch (ApiException e) { audit.record(ctx, action, BoardMinutesAudit.outcomeOf(e.getStatus()), via, actor, ui); throw e; }
      catch (RuntimeException e) { audit.record(ctx, action, "ERROR", via, actor, ui); throw e; }
```

**multipart 처리** (preview·upload, M5)
1. `req`가 `MultipartHttpServletRequest`가 아니면 400 `BAD_REQUEST`.
2. `getFileMap().keySet()`이 {transcript, timeline, summary, options}에 들어가야 하고 파일은 4개 이하여야 한다. 아니면 400 `TOO_MANY_PARTS`. transcript가 없으면 422 `TRANSCRIPT_REQUIRED`.
3. 서비스의 업로드 자격 확인(403)이 바이트 읽기보다 먼저다. 컨트롤러는 `MultipartFile` 참조만 넘기고 서비스가 다음 순서로 다룬다.
   - `f.getSize() == 0` → 422 `EMPTY_FILE`
   - `f.getSize() > settings.getMaxFileBytes()` → 413 `FILE_TOO_LARGE` (`getBytes()` 전에 본다, M5)
   - `MinutesText.checkFileName(f.getOriginalFilename(), slot)`
   - 그다음에야 `f.getBytes()`
4. options는 파일 파트(application/json Blob)로 받고, 16KB가 넘으면 400이다. Jackson으로 `MinutesOptions`를 읽고, 실패하면 400 `OPTIONS_INVALID`. 원문은 되돌려 주지 않는다.

## 5. 보안·위험·되돌리는 법

**자기신고 인증**
- 모든 판정의 사번은 `X-Emp-No` 자기신고다. 헤더만 바꾸면 부장 행세를 할 수 있다.
- 위 규칙은 업무 규칙(실수 방지)이지 사칭 방지가 아니다.
- 운영은 `enabled=false`·`require-verified=true`가 코드 기본값이다. 앞단 인증(NEXT 35) 없이 켜면 수용 위험으로 문서화해야 한다.

**403/404 경로**
- 볼 수 없는 회의록은 404로 존재를 숨기고, 존재하는 건이면 ACT HIDDEN을 남긴다.
- 볼 수는 있으나 권한이 없으면 403이다. ACCESS_LOG DENIED와 ACT DENIED가 남는다.
- 020 탭 목록은 늘 200이다.
- 업로드는 자료가 없으면 404, 자료는 있으나 자격이 없으면 403이다. 그래서 020 자료 번호의 존재가 드러나는데, 020 API도 이미 드러내므로 정도는 같다.

**M2에 남는 위험**
- 사전 밖의 이름(외부인)을 수정 저장으로 가린 경우, OLD_TEXT에는 그 이름이 남는다. 현재 규칙으로 다시 가려도 사전에 없는 이름은 잡히지 않는다.
- 노출은 이력 열람자(H·U)로 줄어들지만, 지울 방법은 회의록 삭제뿐이다.
- 이 정정 장치(아래 열린 질문 1)를 둘지는 security와 함께 정한다.

**그 밖의 위험**
- 쓰기 감사는 커밋 뒤에 기록한다. 기록이 실패해도 쓰기를 되돌리지 못한다(020과 같은 한계). 업로드·공개범위·삭제·수정의 LOG는 같은 트랜잭션이다.
- multipart 임시 파일: `file-size-threshold` 기본값 0이면 Tomcat이 파트를 요청 동안 디스크에 잠깐 쓴다. 전역 키라 바꾸지 않았다. 보안 판단으로 넘긴다.
- 이름 사전을 요청마다 USERS 전체 SELECT로 만든다. 사용자가 수천 명을 넘으면 캐시를 검토한다.

**되돌리는 법**
- 기능만 끄기: `ggreport.minutes.enabled=false`.
- 코드: 새 파일만 추가하므로 해당 커밋을 revert하고 Binding 숫자를 되돌린다.
- DB: 047은 그대로 둔다. 표만 남고 쓰이지 않는다.

## 2. 설계와 달라진 점
- 패치 A 교체본의 "기존 그대로" 부분은 현재 파일을 부분 수정하는 방식으로 살렸다(B1·B5 가드 보존).
- 생성자 인자가 바뀌어도 깨질 곳은 없다. new BidCaseController(를 직접 쓰는 시험은 새 격리 시험뿐이고 나머지는 스프링이 주입한다.
- 패치 C는 하지 않았다. LegacyFlowGuardApiTest와 BidCaseGuardApiTest는 1단계에서 그대로 통과해야 해서 고치지 않았다.
- 설계 §4를 한 시험 파일로 옮기며 단순화했다.
  - 상세 200 역할 확인의 예산팀원은 1857403(시드 009에서 확인).
  - "새 CASE 코드만 쓴다" 시험은 상세 한 번 호출 후 CASE_VIEW 줄이 1 늘어나는지만 본다.
  - 전산팀장 6295038이 닫힘 상태에서 생성 200이 되는 현재 동작을 고정하는 시험을 추가했다. 설계 이관 메모의 "전산팀 전원 관리자"를 시험으로 박은 것이라, 기획이 뒤집으면 이 시험도 함께 고쳐야 한다.
- PrepUiIds·AccessLogInterceptor는 읽기만 했다. 호출 시그니처가 최신 파일과 맞는다(PrepUiIds.of(req), AccessLogInterceptor.DETAIL, PrepAudit.record 7인자).

## 4. 컴파일·런타임 의심 지점
- BidCaseReadGuardApiTest의 ACCESS_LOG 조회가 REQ_PATH를 쿼리 없는 경로(/bidcases, /bidcases/{id})와 정확히 비교한다. 실제 저장 형식이 다르면 denied403 단언 두 곳이 실패한다.
- 예산 팀장 판정은 Teams.AUTHORING_TEAMS에 "예산"이 들어 있다는 가정(leadOf("예산")=예산팀장).
- 시드 이름(3918264=김영업, 5047192≠dave)은 H2 시드가 MySQL 009와 같다는 가정.
- 격리 시험이 쓰는 시그니처는 모두 기존 코드에서 확인했다: Actor.HEADER, SysUser의 setName·setRole·setEmpNo·setStatus, new BidCase(), new BidCaseDetail().
- 격리 시험에서 prep.stateOf를 "NONE"으로 스텁했다. 그래서 상세 404 감사 줄이 NONE 상태로 검증된다.

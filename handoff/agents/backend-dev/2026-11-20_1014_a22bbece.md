## 2. 질문 2·3의 답 (근거)
**오래됨(stale) 판정 (질문 2)**
- 기준은 **기관 사업계획 문서의 `checked_on`(확인일)이 오늘(KST)보다 12개월 넘게 앞선 것**이다. 정확히 12개월이면 오래된 것이 아니다("초과").
  - 상수: `InstitutionPlanService.java:67` `STALE_MONTHS = 12`.
  - 판정식: `:548-550` `LocalDate.parse(checkedOn).isBefore(today.minusMonths(STALE_MONTHS))`.
- 기관 목록 칩이 쓰는 값은 `GET /institution-plans/status`(`InstitutionPlanController.java:57`)가 만든다.
  - 기관별 최신 반입(IMPORT) 판의 문서 중 **하나라도** stale이면 그 기관은 `stale=true`다(`:231-243`).
  - 같은 응답에 `stale_doc_count`와 최상위 `stale_months`(12)도 들어 있다(`:244`, `:254`).
- 기관 한 곳의 문서 목록은 `GET /institutions/{id}/plans`에서 문서별 `stale`로 나간다(`:321`).
  - 화면 경고 문구 "12개월 넘게"는 `frontend/js/plans.js:209`에 하드코딩돼 있다. 서버 값 `stale_months`로 바꾸는 것은 프런트 몫이다.
  - 목록 칩 조건은 `plans.js:240`이다.
- SQL 조건이 아니라 **Java 비교**다. 날짜 계산은 서버에서 하며 DB는 `checked_on` 문자열만 준다.
- 수집 요청이 열려 있는 기관은 "오래됨"을 뺀다는 규칙은 프런트(`plans.js:240`)에 있다. 서버 판정은 건드릴 필요가 없다.

**목표·관심 기관 두 해치 읽기 (질문 3)**
- `GET /bid-targets?year=`는 `guard.require(req, "map")`(`BidTargetController.java:40-42`, `:29`)만 거친다. `map` 메뉴를 볼 수 있으면 디자이너도 읽는다. 쓰기만 `canEdit`(영업 계열)으로 막는다.
- 올해+내년을 받으려면 **두 번 부르면 된다**.
  - `year` 생략하면 올해. `yearParam`은 4자리 숫자만 받고 1990~2100 범위다(`BidTargetService.java:401-408`).
  - 선택 가능한 연도는 올해부터 +2년까지(`:410-414`, `BidTargetRules.YEARS_AHEAD = 2`).
- **관심 기관(`watch_items`)은 연도와 무관하게 매번 같은 목록으로 응답에 들어간다**(`:101-111`, `:119`). 두 번 부르면 관심 기관이 중복된다. 프런트가 `institution_id`로 합쳐야 한다.
- 아래 두 값은 올해(`year == thisYear`)일 때만 채워진다.
  - `bid_closed`: 서버 근거(공고 상태·금고 약정)로 공고 종료 여부를 판단한 값.
  - 공고 정보: `if (year == thisYear)`(`:84-88`)로 읽는 공고 정보.
- 변경 제안(BidTarget* 은 fa 세션 소유, 이번엔 제안만): 두 번 호출로 충분하므로 **변경하지 않기를 권한다**. 정말 한 번으로 줄이려면 `years=2026,2027` 파라미터를 추가하면 되는데, 응답 모양이 바뀌어서 비추천이다.

## 3. 일괄 창구 비교와 권장
**비교**
- 화면이 단건 `POST /institutions/{id}/plan-collect`를 n번 부르는 안:
  - 서버 변경은 없다.
  - **쪽지가 n통** 간다. 새 요청이 생길 때마다 `IT_INBOXES` 두 곳에 한 통씩이라 최대 2n통이다(`PlanCollectService.java:191-196`).
  - 요청 n건이 연달아 나가서 중간에 끊기면 일부만 처리된다. 그 상태를 화면이 알아야 한다.
  - 접근 이력·감사는 기관당 1행이라 지금과 같다.
- 새 일괄 창구를 두는 안:
  - 쪽지를 한 묶음으로 보낼 수 있다.
  - 응답 한 번에 기관별 결과가 모두 들어온다.
  - 한도·검증이 서버 한 곳에 모인다.
  - 코드가 늘고 DB 변경은 없다(기존 `doRequest` 재사용).

**권장: 새 일괄 창구.** 사용자 지시(쪽지 과다)를 충족하고 구현은 얇다.

**설계 결정**

| 항목 | 결정 |
|---|---|
| 경로 | `POST /plan-collect/batch`, 본문 `{"institution_ids":[…]}`. JSON 전용(`@RequestBody`). |
| 한도 | 1~50곳(`MAX_KEYS` 선례). 범위 밖·비어 있음·id 형식 오류(`PlanCsv.validId`)는 전체 400 `BAD_IDS`. 같은 id는 중복 제거. |
| 본문 크기 | `BoardWriteLimitFilter`의 `PLAN_COLLECT` 정규식(`:67-68`)에 `batch` 추가. 16KB 한도에 id 50개면 충분. |
| 권한 | 단건과 같다. `requireRequester`가 `map` 권한과 `canRequest`(영업·개발부서, 디자이너·재무부서 403)를 본다. 403은 접근 이력 DENIED와 감사 DENIED(`institution_id`는 NONE). |
| 감사 | **기관당 1행**. `doRequest`가 `INST_PLAN_ACT`에 `COLLECT_REQUEST`, 결과 OK/JOINED/DUPLICATE를 남기는 것을 그대로 쓴다. 화면 id는 기존 `collectRequest()`와 같고, 버튼만 새로 `plan_collect_request_batch`로 구분한다(제안). |
| 트랜잭션 경계 | **기관별 독립 트랜잭션**(`tx.execute`)이다. 전체 한 트랜잭션은 안 쓴다. 이유는 아래. |
| 쪽지 | 새로 생긴 요청(`created && !quiet`)의 기관 이름만 모은다. 루프 뒤 `IT_INBOXES`당 **한 통씩** 보낸다. 단건 요청의 쪽지(기관당 최대 2통)는 그대로다. |

**트랜잭션을 기관별로 나누는 이유**
- 기관마다 `INSTITUTIONS` 행 `FOR UPDATE` 잠금을 잡는다. 50곳을 한 트랜잭션에 묶으면 잠금을 오래 쥐고 데드락 위험이 커진다.
- 한 곳 실패가 나머지를 지우면 화면 결과가 설명하기 어렵다.

**쪽지 한 통은 트랜잭션 밖에서 보낸다.** 쪽지 실패가 이미 커밋된 요청을 지우면 안 되기 때문이다. 실패하면 로그 한 줄(고정 코드·건수·예외 종류만)만 남긴다. 단건 경로는 쪽지가 같은 트랜잭션이라 실패하면 요청도 롤백되는데, 일괄은 의도적으로 다르다.

**응답 모양 (snake_case)**
```json
{
  "requested_count": 3, "joined_count": 1, "already_count": 1, "error_count": 0, "not_found_count": 0,
  "note_sent": true,
  "results": [
    {"institution_id":"I001","result_cd":"requested","status_cd":"REQUESTED","requester_count":1},
    {"institution_id":"I002","result_cd":"joined",   "status_cd":"RUNNING","requester_count":2},
    {"institution_id":"I003","result_cd":"already"},
    {"institution_id":"X999","result_cd":"not_found"},
    {"institution_id":"I005","result_cd":"error","code":"CONCURRENT"}
  ]
}
```
- 결과값 매핑:
  - `doRequest`의 `OK`는 `requested`.
  - `JOINED`는 `joined`(기존 열린 요청에 내가 덧붙임).
  - `DUPLICATE`는 `already`(이미 내가 요청 중).
  - `ApiException 404`는 `not_found`.
  - `DuplicateKeyException`은 `error`와 `code=CONCURRENT`.
  - 그 밖의 `RuntimeException`은 `error`(내부 정보는 싣지 않음). 감사 `ERROR`는 기록하고 다음 기관으로 계속한다.
- 한 곳이라도 요청이 생기면 **HTTP 200**을 쓴다. 단건은 새로 생기면 201(`Controller:55`)이지만 일괄은 혼합이라 200이 맞다. 항목별 결과로 구분한다.
- `excluded`는 현재 코드에 이 창구가 막을 근거가 없다. 열린 질문 1 참조.

**접근 이력 DETAIL**: `plan-collect batch n=5 requested=3 joined=1 already=1`처럼 건수만 쓴다. 기관 id·사번·본문은 넣지 않는다.

**(b) 새 메서드 `requestBatch`**(상수 `MAX_BATCH = 50`, `KIND_REQUEST` 재사용)
```java
static final int MAX_BATCH = 50;
static final int NOTE_NAMES = 3;

public Map<String, Object> requestBatch(List<String> raw, Actor actor) {
    BoardUiIds.Ui ui = PlanUiIds.collectRequestBatch();
    List<String> ids;
    try {
        ids = batchIds(raw);
    } catch (ApiException e) {
        failed(null, ACTION_REQUEST, "INVALID", actor, ui);
        throw e;
    }
    List<Map<String, Object>> rs = new ArrayList<>();
    List<String> fresh = new ArrayList<>();   // 새로 만든 요청의 기관 표시
    int req = 0, joined = 0, already = 0, nf = 0, err = 0;
    for (String rawId : ids) {
        String inst = rawId;
        Map<String, Object> r = new LinkedHashMap<>();
        r.put("institution_id", rawId);
        try {
            final String id = canonicalId(rawId);
            inst = id;
            r.put("institution_id", id);
            Map<String, Object> o = tx.execute(st -> doRequest(id, actor, ui, null));   // 쪽지는 doRequest 가 아니라 아래서 한 통
            // → 실제 구현: 위 (a)의 batchNew 대신 o 의 created/quiet 로 판단
            String oc = String.valueOf(o.get("outcome"));
            if ("OK".equals(oc)) { r.put("result_cd", "requested"); req++; if (!Boolean.TRUE.equals(o.get("quiet"))) fresh.add(label(id)); }
            else if ("JOINED".equals(oc)) { r.put("result_cd", "joined"); joined++; }
            else { r.put("result_cd", "already"); already++; }
            r.put("status_cd", o.get("status_cd"));
            r.put("requester_count", o.get("requester_count"));
        } catch (ApiException e) {
            if (e.getStatus() == 404) { r.put("result_cd", "not_found"); nf++; }
            else { r.put("result_cd", "error"); r.put("code", "FAILED"); err++; }
            failed(inst, ACTION_REQUEST, HeadAudit.outcomeOf(e.getStatus()), actor, ui);
        } catch (DuplicateKeyException e) {
            r.put("result_cd", "error"); r.put("code", "CONCURRENT"); err++;
            failed(inst, ACTION_REQUEST, "BLOCKED", actor, ui);
        } catch (RuntimeException e) {
            r.put("result_cd", "error"); r.put("code", "SERVER_ERROR"); err++;
            failed(inst, ACTION_REQUEST, "ERROR", actor, ui);
        }
        rs.add(r);
    }
    boolean sent = notifyBatch(fresh);
    Map<String, Object> out = new LinkedHashMap<>();
    out.put("requested_count", req); out.put("joined_count", joined); out.put("already_count", already);
    out.put("not_found_count", nf); out.put("error_count", err);
    out.put("note_sent", sent);
    out.put("results", rs);
    return out;
}
```
- 위 의사코드에서 `doRequest`가 `quiet`를 응답 map에 넣도록 `out.put("quiet", quiet)`를 추가한다(단건 `request`의 응답에서는 제거하거나 무시).
- 결과에는 `name_ko`를 넣지 않았다. 화면은 이미 기관 이름을 갖고 있다.
- 오류 결과의 `code`는 고정 코드만 쓴다.

```java
/** 일괄 쪽지 — 새로 만든 요청이 있을 때만, 개발부서 두 수신처에 한 통씩. 실패는 요청을 되돌리지 않는다. */
private boolean notifyBatch(List<String> fresh) {
    if (fresh.isEmpty()) return false;
    StringBuilder who = new StringBuilder();
    for (int i = 0; i < fresh.size() && i < NOTE_NAMES; i++) {
        if (i > 0) who.append(", ");
        who.append(fresh.get(i));
    }
    String text = "[사업계획 수집 요청] " + who + (fresh.size() > NOTE_NAMES ? " 외 " + (fresh.size() - NOTE_NAMES) + "곳" : "")
            + " — 사업계획 수집 요청이 새로 들어왔습니다(" + fresh.size() + "곳). 개발부서 처리 화면에서 확인해 주세요.";
    try {
        tx.execute(st -> {
            for (String inbox : IT_INBOXES) notes.create(inbox, KIND_REQUEST, text, null);
            return null;
        });
        return true;
    } catch (RuntimeException e) {
        LOG.warn("plan-collect batch note not created code=NOTE_FAILED n={} err={}", fresh.size(), e.getClass().getSimpleName());
        return false;
    }
}

static List<String> batchIds(List<String> raw) {
    if (raw == null || raw.isEmpty() || raw.size() > MAX_BATCH) throw err(400, "BAD_IDS", "기관은 1~" + MAX_BATCH + "곳이어야 합니다.");
    LinkedHashSet<String> out = new LinkedHashSet<>();
    for (String s : raw) {
        if (s == null || !PlanCsv.validId(s)) throw err(400, "BAD_IDS", "기관 ID 형식이 올바르지 않습니다.");
        out.add(s);
    }
    return new ArrayList<>(out);
}
```
- 쪽지 한 통의 길이는 기관 이름 3곳까지로 제한했다. 알림 내용 길이 제한을 확인하지 못했으니, 구현 때 `NotificationCommandService`와 알림 DDL의 내용 길이를 확인해야 한다.
- 취소 뒤 10분 안에 다시 요청한 기관(`quiet`)은 쪽지에서 뺀다. 단건과 같은 규칙이다.

같은 파일 `:66` 주석의 경로 목록에도 `batch`를 더한다.

## 5. 시험안

**깨질 기존 테스트**
- `doRequest` 시그니처 변경은 private이라 영향이 없다.
- `PlanCollectRulesTest`·`PlanCollectApiTest`·`PlanCollectTxTest`·`DesignReviewTxTest`는 단건 경로를 그대로 쓰므로 안 깨질 것으로 본다. 실행해서 확인해야 한다.
- `BoardWriteLimitFilter`를 직접 시험하는 테스트가 있으면 정규식 변경으로 영향이 갈 수 있다.

**추가할 테스트** (`PlanCollectApiTest` 선례를 따라 `PlanCollectBatchApiTest` 신설)

| 입력 | 기대 |
|---|---|
| 영업팀 사번, 새 기관 2곳 | 200. `requested_count=2`, `INST_PLAN_ACT`에 `COLLECT_REQUEST`/`OK` 2행. 개발부서 쪽지 수신처당 **1통**(합 2통). |
| 이미 내가 요청한 기관 포함 | 그 기관은 `already`, 감사 `DUPLICATE`, 쪽지에는 안 들어감. |
| 남이 먼저 연 요청이 있는 기관 | `joined`, 감사 `JOINED`, 쪽지 없음. |
| 없는 기관 id 섞임 | 나머지는 처리, 해당 항목은 `not_found`. 200. |
| 새 요청이 하나도 없는 일괄 | `note_sent=false`, 쪽지 0통. |
| 디자이너 | 403, 접근 이력 DENIED. 감사 DENIED 1행(`institution_id`는 NONE), 요청 행 0건. |
| 재무부서(예산팀) | 403. |
| 사번 없음 | 401(감사 표 증가 없음, 선례). |
| `institution_ids` 51개 / 빈 배열 / 본문 없음 | 400 `BAD_IDS`. 감사 `INVALID` 1행. |
| id에 `../x`·공백 | 400 `BAD_IDS`. |
| 같은 id 두 번 | 한 번만 처리(중복 제거). |
| Content-Type이 JSON이 아님 | 415. |
| 본문 16KB 초과 | 413(필터). |
| 쪽지 생성 실패 모의 | 요청·감사는 커밋, `note_sent=false`, 응답 200. |
| 접근 이력 DETAIL | `plan-collect batch n=…` 건수만, 기관 id·사번 없음. |

**호출자가 실행할 명령**: `cd kgi-ggreport-web && mvn -q -o test -Dtest=PlanCollect*Test` 후 전체 `mvn -q -o test`. 이번 변경은 DB를 건드리지 않아 **mysql·oracle 스크립트 쌍은 필요 없다**. 8080 서버가 같은 `target/`을 쓰면 테스트 뒤 재기동한다.

## 6. 보안·위험·되돌리는 법
- **자기신고 인증의 한계**: 사번은 `X-Emp-No` 자기신고다. `canRequest`는 업무 규칙이지 사칭 방지가 아니다. 이 사실을 가리는 "검증됨" 문구를 쓰지 않는다.
- **403 경로**: `requireRequester`가 그대로 DENIED 감사와 접근 이력을 남긴다. 디자이너는 읽기 `GET /bid-targets`는 되지만 `POST /plan-collect/batch`는 403이다.
- **부하·남용**: 한 번에 50곳이면 기관 잠금 50회와 감사 50행이다. 요청 횟수 제한은 단건과 같고 새로 만들지 않았다.
- **쪽지 폭주**: 요청 한 번에 쪽지는 최대 2통(수신처 둘)이다. 반복 호출은 `DUPLICATE`가 되어 쪽지가 안 간다.
- **개인정보**: 응답·쪽지·접근 이력에 사번·이름을 싣지 않는다. 쪽지에는 기관 이름만 들어간다.
- **ID 열거**: `not_found`로 기관 존재 여부를 알 수 있지만, 기관 ID는 이미 `map` 권한자에게 공개된 값이다.
- **일관성 위험**: 일괄은 쪽지를 트랜잭션 밖으로 빼서, 쪽지 실패 시 단건과 달리 요청이 남는다. 개발부서는 처리 화면 목록에서 요청을 보므로 이를 허용하는 쪽이 안전하다고 판단했다.
- **되돌리기**: 컨트롤러 메서드와 `requestBatch`를 지우고 필터 정규식의 `|batch`만 빼면 된다. 단건 경로와 DB는 그대로다. 새 감사 버튼 `plan_collect_request_batch`로 쓴 감사 행은 남는다(삭제 불가, 감사 이력).
- **보안 검토가 필요한 지점**
  1. 쪽지 한 통에 기관 이름이 들어가는 것(길이 제한, 줄바꿈·제어문자 없음 확인).
  2. 일괄 감사 버튼 이름이 화면 id 화이트리스트(`BoardUiIds`)와 맞는지.
  3. 실패 응답에 내부 정보가 없는지(`error.code` 고정값).
  4. 한도 우회(대소문자만 다른 id를 같은 기관으로 정규화하는 `canonicalId`) — 중복 제거는 원문 기준이라, 서로 다른 원문이 같은 기관이면 두 번째는 `already`가 된다. 이것이 허용되는지 확인.

## 7. 이관 메모
- `[이관: 프런트]` 일괄 요청 호출·결과 표시. 응답의 `results[].result_cd`(requested·joined·already·not_found·error)와 `note_sent`로 문구를 정한다. 두 해치 `GET /bid-targets`를 부르면 `watch_items`가 중복되니 `institution_id`로 합쳐야 한다. 경고 문구 "12개월"은 서버 `stale_months`로 바꾸길 권한다. 기다리는 것: 이 설계 승인 — 근거: 2절·3절.
- `[이관: 기획]` 일괄 요청 쪽지 문구와 한 통에 보이는 기관 수(제안 3곳), 개발부서 두 수신처에 모두 보낼지. 기다리는 것: 문구 확정 — 근거: `PlanCollectService.java:80-81`, 4-2절 `notifyBatch`.
- `[이관: 디자인]` 일괄 결과 안내 문구(일부만 처리됨, 오류가 난 기관 표시). 기다리는 것: 화면 규격 — 근거: 3절 응답 모양.

## 8. 열린 질문
1. 요청한 응답값 `excluded`(개발부서가 제외한 기관)의 의미를 확인해야 한다. 현재 코드는 제외된 기관도 새 요청을 받는다(`doRequest`는 EXCLUDED를 막지 않음, `status`의 `last_closed`로 사유만 보여 줌). 일괄에서도 제외 기관을 막아야 하는가? 막는다면 `excluded` 결과를 추가하고 30일 창구를 정해야 하며, 막지 않으면 이 값은 응답에서 뺀다. 기획이 답할 일이다.
2. 일괄 요청의 한도를 50곳으로 확정해도 되는가(목표 기관 올해+내년과 관심 기관이 합쳐 50곳을 넘는 경우가 있는지).
3. 일괄 요청 쪽지 한 통을 개발부서 두 수신처(전산팀, 전산팀장)에 모두 보낼지.

### 3-0. 설계 결정
**CAN_WRITE: 배정 테이블 직접 조회를 권장한다(사용자 예외 행은 쓰지 않음).**

**복수일 때 주체 규칙(권장안)**
- 담당자 변경 상신: 활성 담당자 1명 이상 또는 영업팀장(A3).
- 제출 1차 확인(021): 활성 담당자 1명.

**영업팀장 관련 결재(A4)**
- 영업팀장이 상신자이거나 현재 활성 담당자이거나 추가 대상이면 결재자는 영업부장이다. 아니면 영업팀장이다.

- 이 규칙으로 본인 결재(`eligibility :412`)와 승인자=수혜자 겹침(security 26)이 막힌다.

**대결 금지(A8):** `ASSIGNEE_CHANGE`는 결재자 본인만 승인한다.

**최초 배정:** 영업팀장만 가능하고 관리자는 403이다(security 28). 담당자는 1~10명이며, 변경 결과가 0명이면 400이다.

## 4. 테스트
**깨질 수 있는 것**
- `eligibility` 시그니처 변경은 `decide`·`list` 두 호출을 같이 고친다(컴파일 오류로 드러남).
- `/approval-requests/types`가 1건 늘지만 길이를 단정하는 테스트는 없는 것으로 보인다(구현 때 grep 재확인).
- 골든 04·05와 `/menus`는 영향이 없다. `DdlRulesTest`는 FK·CHECK를 쓰지 않았으므로 통과 여부를 호출자가 확인한다.

**추가 테스트(입력 → 기대)**
- 최초 배정
  - 영업팀장 `POST {emp_nos:[A,B]}` → 201, 로그 ASSIGN 2건.
  - 영업팀원·관리자·디자이너 → 403.
  - 재요청 → 409 `ASSIGNED_ALREADY`.
- 입력 검증
  - 11명·0명·중복 사번 → 400.
  - 비활성·비영업·영업부장 사번 → 400.
  - 사번 형식 오류 → 400.
- 열람
  - 영업팀원·영업부장 → 200이고 `viewer.is_assignee`가 맞다.
  - 디자이너·관리자 → 403.
- 변경 상신·승인
  - 담당자 A가 `{add:[C]}` 상신 → 결재자 영업팀장, 배정은 불변.
  - 담당자 아닌 영업팀원 → 403.
  - 두 번째 상신 → 409 `CHANGE_PENDING`.
  - 반려(의견 없음) → 400. 반려(의견 있음) 후 재상신 → 성공.
  - 영업팀장 승인 → C 활성, `group_ver+1`, 로그 ADD에 `req_id`.
  - 승인 직전 담당자 집합이 바뀌면 승인이 되돌아가고 409.
  - 결과 0명이 되는 요청 → 400 `NO_ASSIGNEE_LEFT`.
- 영업팀장 관련
  - 영업팀장 상신 → 결재자 영업부장.
  - 영업팀장이 담당자(또는 추가 대상)인 건을 팀원이 상신 → 영업부장.
  - 영업팀장이 본인 건을 직접 승인 시도 → 403.
  - 영업부장 0명·2명 이상인 DB → 400 `APPROVER_NOT_RESOLVED`.
- 대결
  - 같은 직급 대결자가 `ASSIGNEE_CHANGE` 승인 시도 → 403.
  - 기존 PERM_REQUEST 대결 테스트는 그대로 통과해야 한다.
- 그 밖
  - 해제된 사람의 `isActiveAssignee`는 false다(단위 테스트).
  - 접근 이력 detail에 사번 목록·사유·이름이 없다.
  - `/me/assignments`는 자기 활성 건만 보여 준다.

**호출자가 실행할 명령**
- 사용자 터미널에서 015~018 적용 여부를 확인하고 019 SQL을 로컬 MySQL에 적용한다(비밀번호는 사용자).
- 그 뒤 `cd C:\github\GGReportAgent\kgi-ggreport-web && mvn -q -o test`를 돌린다. 8080 서버가 같은 `target/`을 쓰면 테스트 뒤 재기동한다. 한 번에 한 세션만 쓴다.

## 5. 보안·위험·되돌리기
**security 요구 매핑**
- 1 신원: 전 API가 `Actor`와 USERS ACTIVE 대조. `by`·`role` 본문은 받지 않는다.
- 2: `BID_ASSIGN_LOG.EMP_VERIFIED`로 반영. `ACTED_VERIFIED`는 023으로 분리.
- 3: 응답에 "검증됨"이 없고, 화면은 verified=0에 "자기신고"를 붙인다.
- 4: 배정 테이블 직접 조회, 관리자 예외 없음.
- 5: 열람은 영업 계열(부장 포함)만이다.
- 9: 영업팀장 담당이면 영업부장 결재다.
- 22: 판정이 요청마다 `ACTIVE_YN`을 조회해 해제가 즉시 반영된다.
- 26: 유형 `ASSIGNEE_CHANGE`(security는 `ASSIGN_CHANGE`로 썼으나 사용자 확정 용어를 따름), 서버가 결재선을 계산한다.
- 27: 한 트랜잭션 갱신, 이력 보존, 진행 중 변경 1건, 대기 `FINAL_SUBMIT` 취소는 021 후크.
- 28: 최초 배정은 영업팀장만이고 로그 ASSIGN을 남긴다.
- A8: `NO_PROXY`로 대결 승인을 막는다.
- 10~14: 2026-11-10 커밋에서 해소됐고 019는 새 약점을 만들지 않는다.

**자기신고 인증의 한계:** 담당자·팀장 판정이 모두 `X-Emp-No` 위에 있다. 앞단 인증이 없으면 남의 사번으로 행세할 수 있다. `EMP_VERIFIED=0`은 사후 추적용이고 이 설계는 실수 방지이며 사칭 방지가 아니다. 근본 해결은 SSO(NEXT 35)다.

**위험**
1. 영업팀장이 최초 배정에서 자기 자신을 넣으면 결재 없이 팀장 단독 결정이다(질문 1).
2. 영업팀장·영업부장이 DB에 정확히 1명이 아니면 결재선을 정할 수 없다(400).
3. 같은 직급 대결 금지로 결재자 부재 시 변경이 막힌다. 우회는 영업팀장 상신과 부장 승인뿐이다.
4. `PENDING_REQ_ID`는 취소·반려 후크 없이 "끝난 요청이면 비워진 것"으로 본다. 서비스가 매번 요청 상태를 다시 읽어야 한다.
5. `eligibility` 시그니처 변경은 `NO_PROXY` 유형에만 걸리게 해 기존 결재 동작을 보존했다. 기존 결재 테스트가 통과해야 한다.

**되돌리기:** 코드는 커밋 단위로 되돌린다. DB는 DDL 헤더의 `DROP TABLE`과 코드값 `DELETE`를 쓴다(데이터 소멸, 운영에는 쓰지 않음). 진행 중인 `ASSIGNEE_CHANGE` 요청이 있으면 먼저 취소한다.

## 2. 요구·원인 요약(근거)
- 지금 흐름: 확정(CONFIRMED) → [개설 신청]
  - `planOpen`: PrepService.java:418–446. 자격 → 상태 → `validateTargets` → 의견 → 결재자(같은 팀 팀장, 팀장이 관련되면 부장)
  - `claimOpen`: PrepService.java:450–455. CONFIRMED → OPEN_PENDING
  - 승인 `applyOpen`: PrepService.java:474–525. `markOpened`로 상태를 바꾸고 `assignInitial`로 배정하고 과제를 복사하고 OPEN_APPROVE 이력을 남긴다.
  - 상신: ApprovalRequestService.java:190–216
- **찾은 위험 (1): 목표 밖 옛 확정 건이 결재 없이 시작될 수 있다.**
  - 확정은 목표 기관만 된다(PrepService.java:232, `requireGoalTarget` 287–298).
  - 그러나 이 규칙 이전에 확정된 목표 밖 건은 소급하지 않는다(PrepService.java:284 주석 "이미 확정된 건(목표 밖 '준비 중')은 건드리지 않는다").
  - 결재 없는 시작이 목표를 다시 보지 않으면 이 건들은 **팀장 결재를 한 번도 거치지 않고** IN_PROGRESS가 된다.
  - 그래서 시작 때도 기관을 잠근 뒤 `requireGoalTarget`을 다시 판정한다. 확정 뒤 목표에서 빠진 경우도 같이 막힌다.
- **찾은 위험 (2): 시험 컨텍스트는 하나로 캐시된다.**

## 3. 결정(①~⑦)
1. **API·감사 이름·알림**
   - 새 API `POST /bidcases/{bid}/prep/start`, 200을 돌려준다. 본문은 기존 `PrepIn.Open`을 재사용한다(`emp_nos`, `comment`, `approver_emp_no`는 무시).
   - 기존 `planOpen`은 고치지 않고 스위치로 새 상신만 막는다(409 `OPEN_APPROVAL_CLOSED`).
   - 이력 이벤트·감사 행위는 둘 다 `OPEN_START`('사전준비 시작'). 감사 화면·버튼은 `prep_detail`/`open_start`.
   - 알림은 쪽지 종류 `사전준비알림`. 받는 사람:
     - 시작한 사람의 같은 팀 팀장(`sameTeamLead`)
     - 시작한 사람이나 지명자에 팀장이 있으면 영업부장(`resolveApprover(me,true)`, 옛 결재자 규칙과 같다)
     - 본인은 제외
   - 받는 사람을 못 정해도 시작은 막지 않는다. 응답에 `notified_count`를 실어 화면이 알릴 수 있게 한다.
2. **권한**
   - 영업팀·영업팀장 가운데 **확정한 사람 또는 영업팀장**. `hasUnconfirmAuthority`와 같은 식이다.
   - 부장·디자이너는 403. 역할 검사(403)를 건 조회(404)보다 먼저 한다(security F4).
   - 지명 대상 검증(`validateTargets`: 1~10명, ACTIVE, 영업팀·영업팀장만, 부장 불가, 중복 불가)은 그대로 둔다.
   - 옛 흐름은 영업팀 누구나 신청할 수 있었다. 결재가 빠지므로 범위를 좁혔다. 정책 확정은 기획 이관.
3. **옛 OPEN_PENDING 건**
   - 끝까지 처리한다. 승인·반려·회수·대결(`applyOpen`·`afterOpenEnded`·`mayDeputizeOpen`)은 스위치와 무관하게 그대로 동작한다.
   - 반려·회수로 CONFIRMED가 되면 새 `start`로 이어 간다(목표 판정 포함).
   - OPEN_PENDING에서 `start`를 부르면 409 `OPEN_PENDING`.
   - BID_OPEN 유형·카탈로그·`LEAD_DEPUTY_ONLY`는 지우지 않는다(0057과 같은 원칙).
4. **영향**
   - 대결(NEXT 110): 옛 대기 건에만 남는다. 대기 건이 0이 되면 쓰이지 않는 코드가 되며, 지금은 지우지 않는다.
   - 집계(102·113): `SCOPE_OPENED_STATES`·`CHECK_STATES`는 값이 그대로다. 뜻만 '개설 승인 뒤'에서 '사전준비 시작 뒤'로 바뀐다(주석만 고침). 시작할 때 `OPENED_AT`을 채우므로 끝난 건 범위 판정(`inScope`)과 재확정 차단(PrepService.java:246)도 그대로 맞는다.
   - '결재 끝난 건' 감사: `AUDIT_ROW_STATES`를 IN_PROGRESS 이후로 넓히는 안을 **선택 패치 B**로 따로 둔다. NEXT 118과 같은 결정이고 D29 시험이 바뀐다.
   - 시작 행위 자체는 `BID_PREP_ACT`(누가·어느 화면·어느 버튼)와 `BID_PREP_LOG`에 남는다.
5. **두 요청으로 둔다(권장)**
   - 확정: 기존 `POST /preps`, 화면 `bid_board`·버튼 `confirm`
   - 지정: 새 `POST …/prep/start`, 화면 `prep_detail`
   - 사용자가 말한 화면 흐름("확정 후 그 기관의 담당자 지정 화면으로 이동")과 같다.
   - 확정 계약·감사 화면 제한(`PrepUiIds.forConfirm`)·확정 시험을 건드리지 않는다.
   - 지명이 잘못돼도 확정은 남는다. 확정만 하고 떠난 건은 지금처럼 CONFIRMED로 남아 확정 취소할 수 있다.
6. **DB**: 062 쌍 하나. `COMMON_CODE PREP_EVENT 'OPEN_START'` 한 행뿐이고 스키마는 바뀌지 않는다. 이력 조회가 LEFT JOIN(PrepMapper.xml:196)이라, 062가 없어도 서버는 돌고 이름 칸만 빈다.
7. **시험**: 4절.

    /**
     * 사전준비 시작 — CONFIRMED → IN_PROGRESS. 결재 없이 확정한 사람(또는 영업팀장)이 담당자 1~10명을 정하면 바로 시작하고,
     * 같은 팀 영업팀장에게 알림 쪽지만 보낸다(시작한 사람·지명자에 팀장이 있으면 영업부장에게도 — 옛 결재자 규칙과 같은 대상).
     * 순서: 역할(403) → 스위치(409) → 건 잠금(404) → 상태(409 OPEN_PENDING·STATE_CHANGED) → 권한(403 확정자·영업팀장) → 기관 잠금 →
     * 목표 조건(409 NOT_GOAL_TARGET·GOAL_CHANGE_PENDING — 소급하지 않은 목표 밖 옛 확정 건이 결재 없이 시작되지 않게) → 지명(400) → 의견(400/422)
     * → 전이·배정·과제·이력·알림(한 트랜잭션, 하나라도 실패하면 모두 되돌아간다).
     * ⚠️ 첫 DB 읽기는 잠금 읽기(lockPrep)다 — 이 위에 일반 SELECT 를 끼우지 않는다(MySQL RR 첫 일관 읽기, confirm 의 qa P3-8 과 같은 이유).
     * ⚠️ X-Emp-No 자기신고 위의 업무 규칙이다(사칭 방지 아님). 오류 문구에 사번·이름·기관명을 싣지 않는다.

    public Map<String, Object> start(SysUser me, Actor actor, String bidCaseId, PrepIn.Open in) {
        requireSales(me);
        if (openApproval.isOn()) {
            throw coded(409, "OPEN_APPROVAL_ON", "지금은 개설 신청(팀장 결재)으로 사전준비를 시작합니다.");
        }
        BidPrep p = bidCaseId == null || bidCaseId.isEmpty() || bidCaseId.length() > 64 ? null : mapper.lockPrep(bidCaseId);
        if (p == null) {
            throw ApiException.notFound("prep not found");
        }
        if (OPEN_PENDING.equals(p.getStateCd())) {
            throw coded(409, "OPEN_PENDING", "개설 신청(결재)이 진행 중입니다. 결재가 끝나거나 회수된 뒤 다시 하세요.");
        }
        if (!CONFIRMED.equals(p.getStateCd())) {
            throw stateChanged();   // 상태가 맞지 않으면 기관을 잠그기 전에 끝낸다(잠금 순서 BID_PREP→INSTITUTIONS 가 되살리기와 엇갈리지 않게)
        }
        if (!hasStartAuthority(me, p)) {
            throw new ApiException(403, "확정한 사람 또는 영업팀장만 사전준비를 시작할 수 있습니다.");
        }
        if (mapper.lockInstitution(p.getInstitutionId()) == null) {
            throw ApiException.notFound("prep not found");
        }
        requireGoalTarget(p.getInstitutionId());
        List<String> targets = assignments.validateTargets(in == null ? null : in.getEmpNos());
        String note = BoardMaterialService.checkedText(in == null ? null : in.getComment(), 200, "의견", false);
        String now = Times.nowIso();
        requireTransit(mapper.markStarted(bidCaseId, me.getEmpNo(), now));
        int verified = BoardMaterialService.verified(actor);
        assignments.assignInitial(bidCaseId, targets, me.getEmpNo(), verified, null);   // 머리 행이 이미 있으면 409 ASSIGNED_ALREADY(롤백)
        for (BidPrepTask def : mapper.selectEnabledDefs()) {
            mapper.insertTask(bidCaseId, def);
        }
        log(bidCaseId, OPEN_START, CONFIRMED, IN_PROGRESS, null, null, note, me, actor);   // 의견은 사유 칸 — 공개 범위는 canSeeReason(팀장·부장)
        int notified = notifyStart(me, bidCaseId, targets);
        Map<String, Object> out = stateOut(bidCaseId, IN_PROGRESS);
        out.put("assignee_count", targets.size());
        out.put("notified_count", notified);   // 0 이면 화면이 '팀장에게 알림이 가지 않았습니다(결재선 지정 필요)'를 띄운다
        out.put("can_view", isLead(me) || targets.contains(me.getEmpNo()));   // 시작한 영업팀원이 담당이 아니면 상세는 404(기존 열람 규칙)
        return out;
    }

    /** 시작 알림 — 같은 팀 영업팀장(+ 팀장이 관련되면 영업부장). 본인 제외. 못 정하면 건너뛴다(알림은 관문이 아니다). 받은 사람 수. */
    private int notifyStart(SysUser me, String bid, List<String> targets) {
        boolean leadInvolved = isLead(me);
        for (String e : targets) {
            SysUser u = users.selectByEmpNo(e);
            if (u != null && isLead(u)) {
                leadInvolved = true;
            }
        }
        Set<String> to = new LinkedHashSet<>();
        if (!isLead(me)) {
            SysUser lead = assignments.sameTeamLead(me);   // 수동 지정 결재선의 같은 팀 팀장만(다른 팀 팀장으로 넘기지 않음)
            if (lead != null) {
                to.add(lead.getEmpNo());
            }
        }
        if (leadInvolved) {
            try {
                to.add(assignments.resolveApprover(me, true).getEmpNo());
            } catch (ApiException e) {
                // 영업부장을 정할 수 없으면 알림만 건너뛴다 — 시작은 막지 않는다
            }
        }
        to.remove(me.getEmpNo());
        String inst = mapper.selectInstitutionNameByBid(bid);
        String body = "[사전준비 시작] " + me.getName() + "님이 '" + (inst == null ? "" : inst)
                + "' 제안 사전준비를 시작했습니다(담당자 " + targets.size() + "명). 제안 준비 현황에서 확인하세요.";
        for (String emp : to) {
            notes.create(emp, KIND_START_NOTICE, body, null, null, null, null, me.getName());   // institution_id 를 싣지 않는다(타임라인에 섞이지 않게)
        }
        return to.size();
    }

## 6. 보안·위험·되돌리는 법
- **권한(403 경로)**:
  - 역할(영업팀·영업팀장)은 건 조회 전에 본다.
  - 확정자·영업팀장 판정은 건을 잠근 뒤에 한다.
  - 403은 컨트롤러 `run`이 `guard.denied`로 접근 이력 DENIED와 BID_PREP_ACT DENIED를 남긴다.
  - 사번은 `X-Emp-No` 자기신고다. 확정자 판정은 업무 규칙(실수 방지)이지 사칭 방지가 아니다. `emp_verified`는 사실만 적는다.
- **결재가 빠져 생기는 감독 공백**:
  - 팀장이 직접 확정하고 자기를 담당으로 정해도 사전 확인이 없다. 영업부장 알림과 감사가 사후 확인만 한다.
  - 다른 팀 영업팀원을 담당으로 지명해도 서버가 막지 않는다. 옛 흐름에서는 같은 팀 팀장 결재가 걸러 주던 부분이다. security·기획 확인 거리다.
- **목표 판정**:
  - 시작 때 다시 판정하므로, 목표 밖 옛 확정 건이나 확정 뒤 목표에서 빠진 건은 409다.
  - 목표 변경 결재가 진행 중이면 409 `GOAL_CHANGE_PENDING`이다.
  - 문구가 "제안 확정할 수 있습니다"로 나오는 점은 디자인 이관.
- **잠금 순서**:
  - BID_PREP(FOR UPDATE) → INSTITUTIONS 순이다. 상태가 CONFIRMED가 아니면 기관 잠금 전에 끝나므로 확정의 되살리기(INSTITUTIONS → BID_PREP, CANCELLED 건)와 엇갈리지 않는다.
  - 목표 변경 반영 경로가 BID_PREP를 잠그는지는 못 봤다(qa 확인).
- **감사 칸**:
  - 접근 이력 DETAIL은 `prep case=… state=CONFIRMED code=OPEN_START`뿐이다.
  - 의견 원문은 BID_PREP_LOG.REASON에만 둔다(`checkedText`가 개인정보면 422). 감사 표와 쪽지에는 싣지 않는다.
  - 쪽지에는 기관명이 들어간다(결재 제목과 같은 수준). 수신자 개인 쪽지라 institution_id는 비운다.
- **배포 위험(중요)**:
  - 서버만 먼저 올리면 지금 prep.js [개설 신청]이 409 `OPEN_APPROVAL_CLOSED`를 받아 담당자를 지정할 수 없다.
  - 방법 ①: 화면과 같은 커밋으로 배포한다.
  - 방법 ②: 서버를 먼저 올려야 하면 운영 설정에 `ggreport.prep.open-approval.enabled=true`를 두었다가 화면 배포 뒤 지운다.
- **되돌리는 법**:
  - 코드: 설정 `ggreport.prep.open-approval.enabled=true` 후 재기동하면 옛 결재 흐름이 돌아오고 `start`는 409가 된다. 데이터를 바꿀 필요는 없다.
  - 이미 결재 없이 시작된 건은 그대로 둔다. 이력 OPEN_START로 가려낼 수 있다.
  - 062는 머리말의 DELETE 한 줄로 되돌린다.

## 7. 이관 메모
- [이관: 기획] **시작 권한 범위**: 확정자·영업팀장(권장, 구현안)인지, 영업팀 누구나(옛 신청 범위)인지 정해야 한다. **담당자 같은 팀 제한**도 둘지 정해야 한다(NEXT 110 남은 기획 이관과 같은 질문). 기다리는 것: 기획 답. 근거: PrepService 1297–1299, BidAssignmentService 566–580.
- [이관: 기획] **'결재 끝난 건' 감사 범위**를 IN_PROGRESS 이후로 넓힐지(패치 B) 정해야 한다. NEXT 118과 한 번에 정하는 것을 권장한다. 기다리는 것: 기획 답. 근거: PrepBoardService 59–60, planner 0057 3절 ①.
- [이관: 기획] **팀장 알림을 못 보낼 때**(결재선 자동 지정 등)도 시작을 허용할지 정해야 한다. 구현안은 허용하고 `notified_count` 0을 화면에 알린다. 기다리는 것: 기획 답. 근거: BidAssignmentService 671–685.
- [이관: 프런트] prep.js [개설 신청] 영역을 [사전준비 시작]으로 바꾼다.
  - 호출: `POST /bidcases/{bid}/prep/start {emp_nos, comment}`, 머리글 `X-Screen-Id: prep_detail`, `X-Button-Id: open_start`.
  - 버튼 표시: `viewer.can_start_prep`
  - 응답 `can_view=false`면 목록으로 돌아가고, `notified_count=0`이면 안내한다.
  - 승인 팀장 고르기(`approver_emp_no`)는 없앤다.
  - kbboard·dashboard의 [제안 사전준비]는 `POST /preps` 뒤 `goPrep(bid)`로 간다. 이미 확정된 기관(409 PREP_ALREADY_ACTIVE)이면 `/preps` 목록의 `bid_case_id`로 이동한다.
  - notify.js `KIND_CLASS`에 '사전준비알림'을 더한다.
  - 기다리는 것: 이 서버 패치 적용과 디자인 규격. 근거: PrepService 1122, notify.js 13–20.
- [이관: 디자인] 상세 단계 막대의 '개설 승인(팀장)' 칸 이름과 '사전준비 시작' 문구, 목표 밖 건 시작 409 문구(지금은 '제안 확정' 문구 재사용)를 정한다. 기다리는 것: 기획 답. 근거: PrepService 81–82.
- [이관: 데이터] 운영의 진행 중 OPEN_PENDING 건수와, 목표 밖인데 CONFIRMED인 건수를 센다(시작이 409가 될 건). 기다리는 것: 없음. 근거: integrity_check.sql 151–153, PrepService 284.
- [이관: security] 결재 없는 지정의 감독 공백, 잠금 순서, 쪽지 내용을 검토한다. 기다리는 것: 이 설계. 근거: 6절.
- **NEXT 118과의 충돌**: 같은 PrepService view의 viewer 줄(1122–1125, 118은 1124–1125를 바꾼다)과 `AUDIT_ROW_STATES`가 겹친다. 118이 보류이므로 이 패치를 먼저 적용하고, 118은 그 위에 다시 맞춘다.

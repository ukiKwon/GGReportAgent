## 2. 설계와 다르게 한 것 (숨긴 것 없음)

1. **설정 위치**: 지시대로 `AppProperties` 중첩 클래스(`ggreport.inst-head.*`)에 두었다. `InstHeadSettings`는 그 위의 얇은 창구이고 `setEnabled`와 `requireEnabled`를 가진다. 설계의 `@Value` 방식은 쓰지 않았다.
2. **디코더 입력 설정**: `reader.setInput(iis, false, true)`로 했다. 설계는 `(true, true)`였다. 메타데이터를 읽지 않는 목적은 그대로다. 앞으로만 읽기를 끈 이유는 JPEG 리더가 헤더 뒤에 되감기(seek)를 할 때 실패할 수 있어서다. 입력은 이미 메모리에 있다(5MB 이하).
3. **감사 결과 코드**: `HeadAudit.outcomeOf`는 PrepAudit 규칙에 503→BUSY를 더했고, 413도 INVALID로 매핑했다. PrepAudit에서는 413이 ERROR다.
4. **잠금 순서**: 칸 확정·기각·무효에서 칸을 먼저 잠그고 머리를 잠근다. 설계는 머리 → 칸이다. 모든 쓰기가 기관 행을 먼저 잠그므로 교착은 없다.
5. **응답 모양 (설계에 없던 세부)**
   - A2는 `{institutions:[{institution_id,open_count,conflict_count,field_cds}], unmatched_count}`.
   - A1의 `open_candidates`는 열린 후보 **칸 수**다. `last_checked_on`은 단일 칸의 확정값 기준이다.
   - A3 후보에 `reject_block_code`를 더했다. `candidate_heads[]`에는 `items`를 더했다.
   - A4·A5 응답에 `state`·`conflict`를 넣었고, 컨트롤러가 이 값으로 201/202를 가른다.
   - U1·P1은 `{items, truncated}`다.
6. **목록 칸(EDU·CAREER) 입력**: 충돌 개념이 없어 항상 바로 CONFIRMED다. 중복 검사는 없고, 상한(10·20·열린 50)만 있다. 단일 칸에서 확정값이 없는데 열린 후보가 있으면 새 값도 후보로 들어간다.
7. **403 코드**
   - 복원(A14)·P1의 팀원 거부는 코드 `LEAD_ONLY`를 재사용한다.
   - 복원할 사진 파일이 없으면 409 `FILE_MISSING`을 추가했다.
8. **감사 기록 범위**
   - 사번 없는 401은 ACT에 남기지 않는다(감사 표 스팸 방지). 사번이 있는 미등록·비활성 403은 남긴다.
   - ApiException 밖의 예외(DB 등)는 ACT에 ERROR로 남기고 그대로 던진다.
9. **U3 합치기**: 이름이 같은 것으로 보면 칸 전부(NAME 포함)를 현 머리의 후보로 옮긴다. NAME 후보는 확정값과 같은 값이라 충돌 없이 남는다.
10. **롤백 테스트(55)**: 실패 주입을 H2 임시 CHECK 제약(`EVENT_CD <> 'PHOTO_ADD'`)으로 했다. `@Transactional`을 붙이지 않았고, 뒤정리에서 제약·행·접근 이력을 지운다. 기관은 `dongjak`을 쓴다.
11. **설정 키 범위**: `config-envs`는 out-local만 고쳤다(지시). 코드 기본값이 있어 다른 4축에는 필수가 아니다. 각 PC의 `config/application.properties`는 안 건드렸다. 테스트는 pom의 `spring.config.location` 격리 덕에 PC 설정의 영향을 받지 않는다.

## 4. 예상 실패 지점

실행으로만 확인되는 가정이 있다.

1. **JDK ImageIO 동작**
   - `HeadPhotoInspectorTest`의 `requireCleanJpeg`가 JDK가 쓴 JPEG에 통과하는지(마커가 E0·DB·C0·C4·DA뿐인지)는 실행해 봐야 안다. 다른 마커가 나오면 허용 목록을 조정한다.
   - 잘린 JPEG(앞 200바이트)가 IMAGE_UNREADABLE인지, 머리글만 50000×50000인 PNG가 1초 안에 IMAGE_TOO_LARGE_DIM인지도 같다. `HeadPhotoApiTest.형식_확장자_크기_검사`의 깨진 JPEG 케이스도 해당한다.
   - ICC·APP13 세그먼트가 든 JPEG 디코드도 포함한다.
2. **금지어 정규식 표**: `HeadForbiddenTest`, `InstitutionHeadInputApiTest`. 통과 표·차단 표를 설계 그대로 옮겼다. 한글 낱말 경계에서 어긋나면 이 테스트가 먼저 깨진다.
3. **H2**
   - `HeadPhotoRollbackApiTest`의 `ALTER TABLE ... ADD CONSTRAINT ... CHECK` 문법.
   - `LENGTH()` 사용.
   - `SELECT ... FOR UPDATE`는 PrepMapper와 같은 모양이다.
4. **ACCESS_LOG 오염**: ACCESS_LOG는 REQUIRES_NEW라 테스트 롤백과 무관하게 남는다. 그래서 DENIED는 증가량(delta)으로 단언했다. `HeadPhotoApiTest`에는 `LIKE '%원래%'` 단언이 하나 있는데, 다른 기능의 이력과 겹치면 깨질 수 있다.
5. **MockMvc**: 6MB 사진 413은 MockMvc가 `MultipartHttpServletRequest`를 만들어 필터를 건너뛰므로 서비스 검사가 막는다. 필터 쪽 413은 `BoardWriteLimitFilterTest`가 따로 본다.
6. **개수 기대값**: `MapperStatementBindingTest`의 Mapper 21개는 현재 mapper 인터페이스가 20개인 것을 세어서 얻은 값이다.

## 5. 보안·위험 메모

- 스위치를 끄면 DB를 건드리지 않고 404 `FEATURE_OFF`다. 테스트는 `finally`에서 반드시 true로 되돌린다.
- 모든 대상 id는 `INSTITUTION_ID = ? AND X_ID = ?`로 묶어 조회한다. 행이 없으면 404, 상태가 다르면 409다.
- 서비스가 던진 403의 접근 이력 사유는 고정 코드(`head LEAD_ONLY` 등)뿐이다. 이름·값·파일 이름은 이력·감사 표·오류 응답에 넣지 않는다.
- 서버는 출처 URL을 열지 않는다.

## 6. 이관 메모

- [이관: 기획] 금지어 초기 목록 7종의 단어 확정과 오탐 범위. 부장이 "팀장 부재 조건 없이" 충돌을 해소하는 것이 업무에 맞는지.
- [이관: 프런트] 사진은 fetch → blob → objectURL로 띄우고 다 쓰면 revoke한다. 출처 링크는 `textContent`로 쓴다. `*_verified=false`면 '검증됨'을 표시하지 않는다. A1이 404 `FEATURE_OFF`면 카드를 숨긴다. 응답 모양은 위 2-5항을 따른다.
- [이관: 운영·DBA] Oracle 026 적용과 DB 권한(다섯 표 모두 DELETE 없음, LOG·ACT는 UPDATE도 없음). 운영 `photo-dir`은 웹 루트 밖 절대경로로 두고 DB와 함께 백업한다. JVM 옵션 `-Djava.awt.headless=true`와 JDK 8 업데이트 번호를 확인한다.
- [이관: cleaner] `HeadPhotoService`와 `PrepAttachService`의 저장·경로·롤백삭제 코드 중복.
- [이관: 데이터] 2단계 `importRows`(수집 반입)는 이번 범위가 아니다. 기관코드 → INSTITUTION_ID 매칭 DDL은 027 이후다.
- 옛 사진·이전 기관장 값 보존 기간은 설정 자리(`photo-retention-days=-1`)만 있다. 삭제 작업은 없다.

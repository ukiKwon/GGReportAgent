### 3-3. ③ 새 파일 `M/support/ScoringCache.java`
(support 패키지인 이유: `ScoringTable.Result` 생성자가 package-private이라 시험에서 만들려면 같은 패키지여야 한다.)
```java
package com.kbstar.kgi.ggreport.web.support;

import java.util.Iterator;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/**
 * 선정 평가표 읽기 결과 기억(NEXT 121 하-2) — 항목 수 상한 + 글자 수 예산. 넘으면 가장 오래 안 쓴 것부터 버린다.
 * 항목 수만으로는 메모리가 묶이지 않는다(한 결과 최악 수백만 자: 행 200×칸 12×2000자 + 병합 칸).
 * 결과 null(읽었지만 표 없음)도 기억한다(무게 0, 항목 수에는 든다). 한 항목이 예산의 1/8 을 넘으면 기억하지 않는다. 메서드는 모두 synchronized.
 */
public final class ScoringCache {

    /** 기억해 둔 값 — getResult() 가 null 이면 '읽었지만 표 없음'. */
    public static final class Hit {
        private final ScoringTable.Result result;
        private final long weight;

        Hit(ScoringTable.Result result, long weight) {
            this.result = result;
            this.weight = weight;
        }

        public ScoringTable.Result getResult() { return result; }
    }

    private final int maxEntries;
    private final long budget;
    private final long entryMax;
    private final LinkedHashMap<String, Hit> map = new LinkedHashMap<String, Hit>(64, 0.75f, true);
    private long total;

    public ScoringCache(int maxEntries, long budgetChars) {
        if (maxEntries < 1 || budgetChars < 8) {
            throw new IllegalArgumentException("bad cache limits");
        }
        this.maxEntries = maxEntries;
        this.budget = budgetChars;
        this.entryMax = budgetChars / 8;
    }

    /** 없으면 null. 있으면 최근 사용으로 옮긴다. */
    public synchronized Hit get(String key) {
        return map.get(key);
    }

    /** 기억했으면 true. 한 항목이 예산의 1/8 을 넘으면 false(다음 요청이 다시 읽는다 — 파일당 30MB·파싱 시간 상한은 그대로). */
    public synchronized boolean put(String key, ScoringTable.Result r) {
        long w = weigh(r);
        remove(key);
        if (w > entryMax) {
            return false;
        }
        map.put(key, new Hit(r, w));
        total += w;
        Iterator<Map.Entry<String, Hit>> it = map.entrySet().iterator();
        while ((map.size() > maxEntries || total > budget) && it.hasNext()) {
            Map.Entry<String, Hit> e = it.next();
            if (e.getKey().equals(key)) {
                continue;   // 방금 넣은 것(맨 뒤)은 남긴다 — w <= entryMax <= budget 이라 여기까지 오지 않는다
            }
            total -= e.getValue().weight;
            it.remove();
        }
        return true;
    }

    synchronized int size() { return map.size(); }

    synchronized long totalChars() { return total; }

    private void remove(String key) {
        Hit old = map.remove(key);
        if (old != null) {
            total -= old.weight;
        }
    }

    /** 무게 = 글자 수 + 문자열마다 1(빈 칸도 센다). 행·병합 칸·후보 표 머리를 모두 센다. */
    static long weigh(ScoringTable.Result r) {
        if (r == null) {
            return 0;
        }
        long w = 0;
        if (r.getRows() != null) {
            for (List<String> row : r.getRows()) {
                if (row != null) {
                    for (String s : row) { w += len(s); }
                }
            }
        }
        if (r.getCells() != null) {
            for (ScoringTable.Cell c : r.getCells()) { w += len(c == null ? null : c.getText()); }
        }
        if (r.getCandidateHeads() != null) {
            for (String h : r.getCandidateHeads()) { w += len(h); }
        }
        return w;
    }

    private static long len(String s) {
        return 1L + (s == null ? 0 : s.length());
    }
}
```

## 5. 보안·위험·되돌리는 법 (security가 볼 점)
- **권한**: 바뀌지 않는다. 403 경로, 담당 판정, base_rev, 잠금은 그대로다. 새 코드는 감사 칸에 넣을 고정 문자열만 고른다. 머리글 원문은 저장하지 않고, 허용 목록 밖은 UNKNOWN이다. 접근 이력 DETAIL도 바뀌지 않는다.
- **자기신고의 한계**: X-Emp-No·X-Screen-Id·X-Button-Id는 모두 위조할 수 있다. 이 패치는 정직한 화면이 정확한 이름을 남기게 할 뿐이다. prep_detail/dash_check는 칸 제한이 없어서 현황판 이름과 같은 강도(어느 칸이든 유효)다. 위조로 얻는 것은 감사 줄의 화면 이름 하나뿐이다.
- **board_view 범위**: LIST·VIEW만 유효하다. 확정본 내려받기·결재 같은 다른 행위에서는 UNKNOWN이고 기존 400 관문을 탄다. 시험 5에서 단언한다.
- **결과 기억(③)**:
  - 메모리 상한이 생긴다(약 16MB + 객체 부담).
  - 대신 100만 자를 넘는 결과는 기억하지 않아 요청마다 다시 파싱한다. 이 비용은 기존 상한(최근 5개, 파일당 30MB, 15초, 일꾼 2개)이 묶는다. 이 맞바꿈이 받아들일 만한지 security 판단이 필요하다.
  - 정적 캐시는 시험 사이에 공유된다(기존과 같음).
- **⑥**: 매퍼 INFO로 바인딩 값 노출이 사라진다. 대신 dev에서 SQL을 진단하려면 그때만 한 매퍼를 DEBUG로 올려야 한다. 로그 파일 접근 범위(누가 개발 서버 로그를 보나)는 여전히 확인되지 않았다.
- **write-guard**: `config-envs/dev/application.properties`에는 `spring.datasource.password=<DEV-DB-PASSWORD>` 자리표시 키가 있어서 훅이 비밀번호 설정 파일로 막을 수 있다. 막히면 우회하지 말고 메인 판단을 받는다.
- **되돌리는 법**: 서버 3파일 + 새 파일 1개 + 설정 1개 + prep.js 두 조각을 `git revert`한다. DB 변경이 없고, 이미 쌓인 새 이름 행은 읽는 데 지장이 없다.

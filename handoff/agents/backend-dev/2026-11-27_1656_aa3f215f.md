# backend-dev 설계 지시서: 입찰 현황판 '구분' 4값 재정의 (DB 072, 서버)

이 설계는 Opus로 올려서 했다. 옛 데이터를 한꺼번에 바꾸고 코드표를 고치는 일이라 되돌리기 어렵기 때문이다. 파일은 쓰지 않았고 테스트도 돌리지 않았다.

**호출자 지시와 다른 점이 하나 있다.** 지시는 "코드표에 4행 추가, 옛 3행은 사용 안 함"이었다. 나는 RETAIN·NEW 코드는 그대로 두고 이름만 바꾸는 방식을 골랐다(근거는 2절 ①). 호출자 확인이 필요하다.

## 2. 요구·원인 요약

**① 저장 방식: 한 칸 코드 4개로 하고, 기존 코드를 재사용한다(내 선택)**
- 코드표 TARGET_TAG는 다음처럼 된다.
  - `RETAIN` → 이름만 '재유치 입찰'
  - `NEW` → 이름만 '신규 입찰'
  - `RETAIN_PRIVATE` '재유치 수의계약', `NEW_PRIVATE` '신규 수의계약' 추가
  - `REGAIN`은 ENABLED=0. 지우지 않는다(옛 결재 문서가 이름을 읽는다).
  - 순서: 재유치 입찰 1, 재유치 수의계약 2, 신규 입찰 3, 신규 수의계약 4.
- 근거
  - 사용자 결정 "RETAIN→재유치 입찰, NEW→신규 입찰"은 뜻이 1:1이다. 그래서 행을 바꿀 필요 없이 이름만 바꾸면 된다.
  - 실제로 바뀌는 행은 REGAIN뿐이다. 이 코드는 11-23(059)에 생겨서 행이 적을 것이다.
  - 새 코드 4개를 만들면 INST_BID_TARGET 전체와 결재 항목(REQ_ITEM) 전체를 UPDATE해야 한다. 그러면 승인이 끝난 결재 문서에 "재유치 입찰 → 재유치 도전" 같은 가짜 변경이 생긴다. 또 `TargetResultRules`, 테스트 수십 곳(`"NEW"`·`"RETAIN"`을 씀), 화면 코드가 함께 바뀌어야 한다.
  - 두 축(대상·방식)으로 칸을 나누는 방식은 표·결재 칸이 늘어난다.
  - 결론: 이 방식이 되돌리기 가장 쉽다. 두 축 판정은 코드에서 읽는다(`tagRetain`·`tagPrivate`).
- 한계: 옛 이력의 '재유치 도전'·'신규유치 도전'도 새 이름으로 보인다. 사용자 결정상 같은 값이라 받아들였다.

**② 막히는 곳**
- 결재 승인 때 `TargetChangeService.java:382`가 사용 안 함 코드를 400 '더 이상 쓰이지 않습니다'로 막는다. 대기 중 REGAIN 항목은 승인할 때 NEW로 바꿔 반영해서 이를 피한다.
- 직접 저장·관심(♥)·결재 요청 쪽은 `BidTargetRules.java:96·270`이 ENABLED만 본다. 그래서 REGAIN은 새로 넣을 수 없다(400). 의도한 결과다.

**③ 성과 판정**
- `TargetResultRules.java:54`는 `"RETAIN".equals(tagCd)`로 판정한다. RETAIN_PRIVATE도 재유치로 세도록 대상 축으로 바꾼다.

**④ 수의계약 예외를 거는 곳**
- 서버가 판정하는 '입찰 끝남 근거'는 `BidTargetRules.bidClosedBasis`(201행) 한 곳이다. 이것을 쓰는 곳은 다음과 같다.
  - 목표 줄 `bid_closed`(`BidTargetService.java:197`)
  - 정리 필요 표시 `prep_cleanup_needed`(223행)
  - 올해 목표 409 `INST_BID_CLOSED`(`closedCheck` 649행, 호출 7곳)
  - 성과 판정 UNREGISTERED·`no_bid`(`TargetResultService.java:94·236`)
- 구분이 수의계약이면 이 함수에서 **'입찰 없음(NO_BID)' 근거만** 빼고 다음 근거(약정 확정)를 본다. '공고 종료(CLOSED)'와 '약정 확정(FUTURE)'은 그대로 둔다.
- 예상 공고일 알림, '아직 입찰 공고 전' 태그, [계속 작성] 팝업은 준비(6e) 쪽이다 → 이관.

**⑤ 이월**
- 이월은 구분을 그대로 복사한다(`BidTargetService.java:835`). 이관 뒤에는 REGAIN이 남지 않으니 고칠 것이 없다.

## 6. 보안·위험·되돌리는 법

**시스템 이관 기록 [security 확인 필요]**
- 권고: 업무 표에 '시스템 이관' REV를 새로 넣지 않는다. 바꾼 행은 MIG072 표(키·전·후·시각)에 남긴다.
- 새 REV를 넣지 않는 이유
  - 수정자 사번 칸(EDITOR_EMP_NO, 7자, NOT NULL)에 가짜 사번을 넣어야 한다.
  - `editedByOther`(BidTargetService 747행)가 '다른 사람이 고침'을 잘못 켠다.
  - 결재 대기 항목의 기준 REV(BASE_REV_NO)가 어긋나 승인이 `ITEM_CHANGED` 409로 막힌다.
- 대가 두 가지
  - 추가 전용인 INST_BID_TARGET에 DBA가 한 번 UPDATE한다. 앱 계정 권한은 그대로다.
  - 화면 이력에서 REGAIN 행이 '신규 입찰'로 보인다. 원래 값은 MIG072에만 있다.
- security가 추가 전용 예외를 받아들일지 정한다. 거부하면 새 REV 방식으로 다시 설계한다(가짜 사번 처리, 대기 결재가 있는 기관 제외가 필요하다).

**권한·결재**
- 수의계약 구분을 고르면 올해 목표의 '입찰 없음' 409가 풀린다.
  - 목표 넣기·연도 바꾸기는 그대로 결재 대상이다(`requireDirect`). 결재 문서에 구분이 보이니 결재자가 본다.
  - 구분만 고치기(결재 없음)는 연도를 바꾸지 않으므로 `closedCheck`를 타지 않는다.
- 담당이 구분을 수의계약으로 바꾸면 성과의 '미등록(끝남)'이 '대기'로 바뀐다. 사용자 결정(결재 없음, 이력 남음)대로다. 이력은 기존 REV와 접근 이력 `basis=value`로 남는다.
- 인증은 여전히 `X-Emp-No` 자기신고다. 이 변경으로 달라지지 않는다.
- 403 경로·접근 이력 형식은 바꾸지 않는다. 새 응답 키는 `audience_cd`·`private_contract` 둘이고 snake_case, 개인정보 없음.

**위험**
- 구 서버가 072 적용 DB를 읽으면 화면 칩이 새 코드 2개를 모른다. 배포 순서(서버 중지 → 072 → 새 서버)로 막는다.
- 결재 대기 중 REGAIN 항목은 결재자 화면에 '되찾기 도전'으로 보이지만 승인하면 '신규 입찰'로 들어간다. 사전 조회 ③이 0이 아니면 결재자에게 알린다.

**되돌리기**
- 072 헤더의 되돌리기 블록을 쓴다(MIG072로 REGAIN 복원, 코드 이름·사용 여부 복원, 수의계약 코드는 쓰인 행이 있으면 ENABLED=0).
- Java는 커밋을 revert한다. 테스트 설정의 072 줄도 함께 뺀다.

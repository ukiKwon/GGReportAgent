### 3. 지시에서 벗어났거나 내가 판단한 것

1. **구조 없이 cells 맵만 보낸 표는 전체 교체**를 유지했다.
   - cells에 없는 칸은 카탈로그 기본 문구로 돌아가고, 카탈로그에 없는 사용자 추가 칸은 빈 문구가 된다.
   - 기존 테스트 `보내지_않은_칸은_..._전체_교체`와 호환시키려는 선택이다.
   - 구조는 base 버전 것을 유지한다.
   - **프런트는 구조를 안 보내는 표라도 cells를 완전하게 보내야 한다.** 부분 맵을 보내면 이전에 고친 문구가 사라진다.
2. **표를 통째로 빼는 저장은 `UNMAP_CONFIRM_REQUIRED` 대상이 아니다.**
   - 기존 테스트가 B·C-2·C-3를 확인 없이 빼는 저장을 요구한다.
   - 판정은 base와 새 양식 모두에 있는 표만 본다.
   - 표 삭제 확인 UI는 프런트·기획 몫이다.
3. **연결 유지 규칙**: 카탈로그 연결 key 위치의 칸은 `header`·`input`이 둘 다 false일 때만 연결로 남는다. 머리글이나 입력 칸으로 바꾸면 연결이 풀리고 dropped로 센다.
4. **구조를 보내는 표에 cells 맵을 같이 보내면 400**(`BAD_STRUCT`). 계약의 "구조를 안 보내는 표만 cells"를 강제했다.
5. `confirm_unmapped`는 DTO에서 `Object`로 받고 `Boolean.TRUE`만 인정한다. "true" 문자열이나 1이 조용히 true로 바뀌는 것을 막기 위한 것이다. `fmt`와 같은 방식이다.
6. **표를 지웠다 다시 넣어도 카운터가 유지**되게 하려고 저장 JSON 루트에 `kept:[{ref,next_r,next_c}]`를 추가했다. 다시 넣은 표는 카탈로그 구조에서 시작하고 카운터만 이어받는다.
7. `limits`에 `max_table_cells:300`을 덧붙였다. 계약 4개 외의 추가 필드다.
8. `parse()`는 이제 타입만 확인하고, 구조 검증은 `build()`가 한다(저장본이 어긋나면 `EditException`→`docOf`에서 ISE). 그래서 `BoardDocEditTest`의 "구조가 카탈로그와 다르면 parse 실패" 단언을 build 기준으로 바꿨다. `next_r` 101이나 `r7` 같은 값은 이제 합법이다.
9. **카탈로그 순서 규칙**: 기본 양식 id(100 미만)끼리의 상대 순서만 유지하면 되고, 새 행·열은 어디든 가능하다. 위반하면 `EditException`이고, 문구에 "순서는 바꿀 수 없습니다"가 들어간다. 이 문구는 `BAD_STRUCT`가 아니다.
10. 읽을 수 없는 현재 버전(번역표 없음 등) 위에 저장하면 base 없이 카탈로그에서 다시 시작한다(기존 복구 동작 유지). 이때 dropped는 0이다.

### 4. 프런트가 알아야 할 응답·요청 계약

**PUT /board-forms/{id}**
- 성공: 기존 응답 + `changed` + `dropped_mapped`(정수, 변화 없음이면 0).
- 연결 칸이 사라지는데 `confirm_unmapped !== true`이면 400 `{detail:{code:'UNMAP_CONFIRM_REQUIRED', message, count, dropped:[{ref,key}(최대 50)]}}`.
- 구조 위반은 400이고 detail은 고정 문구 `BoardDocSpec.BAD_STRUCT`다("표 구조가 올바르지 않습니다. 화면을 새로 고친 뒤 다시 편집해 주세요.").
- 상한 위반은 각각 고정 문구다: "행은 1개 이상 40개…", "열은 1개 이상 12개…", "표 하나에 넣을 수 있는 칸은 300개…", "양식 전체에 넣을 수 있는 칸은 800개…". 문구 100자와 제어문자는 기존 칸 문구 검증 메시지를 쓴다.
- 저장 버전이 500개면 새 버전 저장이 400이다("저장 이력이 너무 많아…"). 바뀐 게 없으면 그대로 통과한다.

**요청 본문**
- cols/rows는 한 표에서 둘 다 보내거나 둘 다 생략한다. 한쪽만이면 400.
- 새 열 id는 임시값 `n1`, `n2`…(표 안 유일). 새 행 id는 null.
- 서버는 새 id를 `c{N}`/`r{N}`(100 이상)으로 발급한다. 응답의 `row_ids`/`col_ids`를 그대로 되돌려 보내면 된다.
- 각 칸의 `col`은 실제 격자 위치의 열 id(또는 임시 id)와 같아야 한다.
- `align`은 left/center/right만 허용한다. `header`와 `input`을 동시에 true로 보낼 수 없다.
- 병합 `colspan`은 1..열수, `rowspan`은 1..행수.

**GET 상세·catalog 응답**
- 상세(view): 모든 칸 `editable:true`, `limits{max_rows,max_cols,max_cell_chars,max_form_cells,max_table_cells}`가 추가됐다.
- catalog: 최상위에 `limits`가 추가됐다. 칸·표 모양은 기존과 같다(`key`, `row_id`, `col_id`, `input`, `mapped`, `row_ids`, `col_ids`).
- 엑셀 업로드 응답의 표마다 `unlinked_count`가 추가됐다.
  - `summary.total`에는 양식에 남은 연결 칸만 센다.
  - `sums[].of`는 남은 key와 합계 범위 안의 사용자 입력 칸 key를 합친 것이다.
  - 합계 칸은 `warnings[].code=SUM_HAS_MANUAL_PARTS`이고, 상태가 filled였다면 review가 된다.
  - 남은 부품이 하나도 없으면 합계 칸은 `status:manual, reason:MANUAL_INPUT`이다.
- 작성 모드 초안 docx(draft-docx)는 직접 입력 칸 key로도 값을 받는다. 머리글·라벨 key는 400 `BAD_VALUE`다.

**접근 이력(`API` 이벤트의 detail)**: 구조 변경 저장은 `board-form-save rows+N/-M cols+N/-M unmapped=K` 숫자만 남기고, 변화가 없으면 기록하지 않는다. 본문·문구는 넣지 않는다.

### 5. 남은 위험·되돌리는 법

- 컴파일과 테스트를 못 돌렸으므로 첫 실행에서 사소한 컴파일 오류가 나올 수 있다.
- 새 테스트의 기대값은 구현과 대조해 손으로 따져 만들었다. 특히 아래는 첫 실행에서 맞는지 확인이 필요하다.
  - `BoardStructureFillTest`: 시트 픽스처 값(57.40→42.30)과 `review` 상태 단언.
  - `BoardFormStructureApiTest`: 접근 이력 `detail` 단언.
- C-5(앵커 189칸)와 기본 양식 전체(346칸)는 800칸 상한 안이다. C-2와 C-3를 각각 300칸으로 키우면 상한에 걸리도록 테스트가 짜여 있다.
- 되돌리기: 저장 버전은 불변 행이라 이전 버전이 그대로 남는다. 이번 변경은 DB 스키마 변경이 없고, 옛 fmt2(PR-1) JSON도 그대로 읽힌다.
- 한계: 인증은 `X-Emp-No` 자기신고 그대로이며 권한 검사는 기존 `requireEdit`을 그대로 썼다.

### 6. 이관 메모

- [이관: 프런트] 구조를 안 보내는 표의 cells는 전체 맵으로 보낼 것. 표 삭제 확인 UI는 별도 필요 — 서버가 표 삭제는 확인 없이 허용한다.
- [이관: 프런트] 병합 갱신(행·열 삽입·삭제 시 rowspan·colspan 조정)은 프런트 몫이고 서버는 검증만 한다. `BoardStructureTest`와 `BoardFormStructureApiTest`의 구조 변환이 예시로 쓸 만하다.
- [이관: 기획] 직접 입력 칸을 합계 범위에 포함하는 규칙(서버는 값을 모르고 review 표시만)을 화면 문구로 안내할 것.
- [이관: 기획] 표 전체 삭제 시 연결 칸 소실을 확인 대상으로 넣을지 결정이 필요하다. 지금은 대상이 아니다.
- [이관: 데이터] 엑셀 지도(excel-map.json)는 수정하지 않았다.

MENU_ORDER(019)는 미확정·미적용 후보이므로 **번호를 비우지 않고 이 건이 019부터 쓴다. MENU_ORDER는 확정되면 `022`로 민다.** 파일명 변경 비용은 0이다. 둘 다 미적용이라는 전제는 호출자가 확인해야 한다.

| 번호 | 내용 | 단계 |

| 023 (후순위) | BOARD_REVIEW 의견·반려 | 재무 확장, 지금 만들지 않음 |

- 공통 규칙은 `db/README.md`를 따른다.
  - mysql·oracle 쌍, 외래키 없음, 부모 행 삭제 없음, 사번은 `VARCHAR2(7 CHAR)`, 시각은 `Times.nowIso`(`VARCHAR2(40 CHAR)`).
  - 코드 값은 `COMMON_CODE`로 검증하고 CHECK는 쓰지 않는다. 0/1 플래그만 예외로 두며 경로 A 기본이다.
  - 새 테이블 UNIQUE는 PK로 해결해 CHECK·UNIQUE 의존을 최소화했다.
- **MySQL 변환 규칙**
  - `VARCHAR2(n CHAR)`→`VARCHAR(n)`, `NUMBER`→`BIGINT`, `NUMBER(n)`→`INT`/`SMALLINT`, `CLOB`→`LONGTEXT`.
  - `GENERATED BY DEFAULT AS IDENTITY`→`BIGINT AUTO_INCREMENT`, 인덱스는 `CREATE TABLE` 안에 인라인(`014` mysql 방식).
  - MySQL 019~021은 013 같은 멱등이 아니라 번호 순서대로 한 번씩 실행한다.
- **이미 018까지 적용한 DB**: 019부터 순서대로 한 번씩 실행한다. 기존 테이블은 건드리지 않고 새 테이블만 추가하므로 재적용 위험이 없다. Oracle은 정본 작성까지만이고 적용은 DBA가 한다.
- 새 테이블이 늘면 `integrity_check.sql`(쌍)에 점검 쿼리를 추가한다.
  - BOARD_DOC.BID_CASE_ID가 BID_CASES에 있는지.
  - BID_ASSIGNMENT.EMP_NO가 USERS에 있는지.
  - BOARD_DOC_DRAFT·BOARD_DOC_SNAP의 DOC_ID가 BOARD_DOC에 있는지.
  - BOARD_TABLE_CHECK, BOARD_DOC_LOG, BID_ASSIGN_LOG도 마찬가지로 점검한다.

  - 중복 방지: `UPDATE BID_ASSIGNMENT SET PENDING_REQ_ID=? WHERE ... AND (PENDING_REQ_ID IS NULL OR PENDING_REQ_ID=기존값)`으로 비교 후 설정한다. 기존값이 가리키는 요청이 PENDING이면 409. 이미 끝난 요청이면 비워진 것으로 본다. 반려·취소 후크가 필요 없다.
  - `to_emp_no`: USERS(ACTIVE), 영업 계열(`Teams.isSalesFamily`), 현 담당자와 달라야 한다.
- **승인 후처리**(`applyApproved`에 분기 추가, 같은 트랜잭션)
  - 배정 행의 `ROW_VER`가 payload에 담긴 값과 같은지 다시 확인한다. 다르면 409를 던져 승인도 되돌아가게 한다(`:33-40` 주석의 기존 원칙).
  - `EMP_NO`를 갱신하고 `ROW_VER+1`, `PENDING_REQ_ID`를 비운다.
  - BID_ASSIGN_LOG에 ACTION=CHANGE, REQ_ID, ACTOR를 남긴다.
  - 요청 쪽에는 `result_note="담당자 변경 반영"`을 남긴다.
- **영업팀장 본인이 담당자를 바꾸려면**: 본인 요청은 본인이 결재할 수 없고(`eligibility :412-414`) 결재선이 영업부장으로 올라간다. `[기획]` 이 경우를 허용할지가 열린 질문이다.

### 3-5. 서비스 규칙
- **배정자 판정(한 곳)**: `BidAssignmentService.isAssignee(bidCaseId, roleCd, empNo)`가 `BID_ASSIGNMENT`를 한 번 조회한다. 쓰는 곳은 다섯이다: 이사회 쓰기, 담당자 변경 상신, write-done, final-submit 상신, 목록 `mine` 범위.
- **이사회 수정 권한 P2**: `BoardAccess.canWrite(actor, doc)` = `permissions.canWrite(empNo,"tasks")` AND `Teams.isSalesFamily(user.role)` AND `isAssignee(doc.bidCaseId, SALES_OWNER, empNo)`.
  - 배정 조건이 필수이므로 `canWrite`의 "관리자면 true" 분기(`PermissionService:182`)가 배정 없이는 통하지 않는다. 관리자의 남의 건 수정 금지가 자연스럽게 지켜진다.
  - 단 **관리자가 담당자로 배정돼 있는 경우의 예외 여부는 `[보안]`이 결정한다.**
- **열람 판정**: `BoardAccess.canView` = `tasks` 조회 + 영업 계열. 디자이너·영업부장 포함 여부와 관리자 열람 가부는 `[보안]`이 정한다. 상수 한 곳만 바꾸면 되도록 만든다.
- **동시 저장 거절**
  - 초안 저장: `UPDATE BOARD_DOC_DRAFT SET VALUES_JSON=?, WORK_VER=WORK_VER+1, ... WHERE DOC_ID=? AND WORK_VER=?`가 0행이면 409 `{code:"VERSION_CONFLICT", work_ver:<현재 값>}`다. 새 값은 돌려주지 않는다.
  - 머리 칸·상태 변경은 `ROW_VER`로 같은 방식이다.
  - 버전 저장은 `base_ver`가 현재 `WORK_VER`와 같아야 한다.
  - 같은 CLOB 갱신은 MyBatis `jdbcType=CLOB` 명시(README 타입 대응표).
- **자기신고 사번**: 로그·행의 `EMP_VERIFIED` 칸은 `Actor`가 앞단 인증인지를 기록한다. 응답·화면에 "검증됨" 표현을 쓰지 않는다.
- **접근 이력**: `req.setAttribute(AccessLogInterceptor.DETAIL, "board-case code=… doc=…")` 형태로 코드·id·크기만 남긴다. 값·메모·쿼리값·파일명·해시는 넣지 않는다(`BoardWriteController:98-101` 방식과 같음).

| S6 | 021 DDL + `write-done` + 예산 제외 상수 + `FINAL_SUBMIT` 상신·후처리 + `/complete` 닫기 + `CompleteApiTest` 교체 | S4 (가결 판정 전에 complete 검사 넣지 말 것) |

- **S6의 `/complete` 닫기는 가결 판정(S4)이 들어간 뒤에만 한다.**

## 6. 보안·위험·되돌리는 법
- **자기신고 사번**
  - 담당자·팀장 판정이 모두 `X-Emp-No` 위에 있다. 앞단 인증이 없으면 남의 사번으로 배정자 행세가 가능하다. 설계가 이를 가리면 안 된다.
  - `EMP_VERIFIED=0` 기록이 사후 추적 장치이고 보안 경계가 아니다.
  - 응답·화면에 "검증됨"을 쓰지 않는다.
- **403 경로**: 쓰기 전부(배정 PUT, 초안·버전·표 확인·상태·수익성·사후 등록, write-done, 상신). 읽기는 비영업 계열에 403.
- **접근 이력**: 본문·쿼리값·값 JSON·메모·파일명·해시를 넣지 않는다. 코드·doc id·크기만 남긴다.
- **위험**
  1. **사후 등록으로 가결 기록을 만들면 "예외 해제 없음"을 우회하는 통로가 된다.** 등록자와 FINAL_SUBMIT 승인자가 같은 영업팀장일 수 있어 이중 통제가 약하다. 권장은 영업팀장 한정 + 근거 필수 + 로그이며 `[보안][기획]` 판단이 필요하다.
  2. **CAN_WRITE 사용자 예외 행이 모든 담당자에게 필요하다.** 역할 기본값에는 작성 권한이 없다(`PermissionService:166`). 권한 신청(PERM_REQUEST) 경로로 해결할지 `[기획]`이 정한다. 배정만으로 자동 부여하지 않는다.
  3. 영업팀장이 0명 또는 2명 이상인 DB에서 결재선을 정하지 못한다. 400으로 막고 안내한다.
  4. 같은 CLOB 값의 최대 길이 상한이 미정이다. DB 부하와 개인정보 노출 면적을 가늠하기 위해 확정이 필요하다.
  5. 수익성 확정 업로드는 서버가 파일을 한 번 받는다. 기존 xlsx 업로드와 같은 크기 상한·동시 처리 슬롯·로그 규칙을 적용해야 한다.
  6. 기존 `/tasks/{id}/approve`·`/checkpoint`의 선점·`body.by` 구멍은 이 설계가 쓰지 않으며 고치지도 않는다. 보안이 따로 판단한다.
- **되돌리는 법**
  - 코드는 커밋 단위로 되돌린다.
  - DB: `DROP TABLE BID_ASSIGNMENT, BID_ASSIGN_LOG, BOARD_DOC, BOARD_DOC_DRAFT, BOARD_DOC_SNAP, BOARD_TABLE_CHECK, BOARD_DOC_LOG, BID_CASE_FLOW` + COMMON_CODE `ASSIGN_ROLE`·`BOARD_STATUS` 행 삭제(데이터 소멸 주의).
  - `/complete` 닫기는 한 줄 되돌리기로 풀 수 있지만 가결 검사가 사라지는 것이므로 사용자 승인 사항이다.

## 8. 열린 질문 (사용자가 답하면 진행되는 것만)
1. 담당자 변경은 현 담당자만 올릴 수 있나요, 담당자가 부재일 때 영업팀원 누구나 올릴 수 있나요? 권장: 현 담당자 + 영업팀장(팀장은 영업부장 결재).

3. 이사회 자료 목록의 '기간'은 개최일 기준인가요, 연도 기준인가요? 권장: 개최일 구간(없으면 연도).

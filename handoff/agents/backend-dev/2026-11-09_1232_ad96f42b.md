### 3-1-B. 경로 B (DBA가 CHECK·UNIQUE도 막을 때) — 014에 한정한 완성형

`oracle/014` 제약 부분만 아래로 바꾼다(MySQL도 동일 의미로).
```
-- BOARD_FORM
    CONSTRAINT PK_BOARD_FORM PRIMARY KEY (FORM_ID)
);
-- BOARD_FORM_VER
    CONSTRAINT PK_BOARD_FORM_VER PRIMARY KEY (FORM_ID, VER_NO)
);
-- BOARD_FORM_USE
    CONSTRAINT PK_BOARD_FORM_USE PRIMARY KEY (USE_ID)
);
CREATE INDEX IDX_BFU_REQ  ON BOARD_FORM_USE (REQ_ID);        -- UQ_BFU_REQ 대체(조회용, 비유니크)
CREATE INDEX IDX_BFU_FORM ON BOARD_FORM_USE (FORM_ID, VER_NO);
```
대체 보장은 아래와 같다.
- `STATUS IN ('ACTIVE','ARCHIVED')`는 서비스의 상수 검증으로 옮긴다.
- 요청 1건당 양식 1개는 상신 서비스가 `APPROVAL_REQUEST` 행을 `SELECT … FOR UPDATE`로 잠근 뒤 `BOARD_FORM_USE`를 조회하고 INSERT한다. 같은 트랜잭션에서 처리한다(상신 연계는 후속이라 지금 호출하는 코드는 없다).

**공통 규칙: CHECK·UNIQUE 경로 분기표(001~014 전체)**

| 경로 A(쓴다) | 경로 B(안 쓴다) |
|---|---|
| 현재 정본 유지(FK만 제거) | CHECK 10줄 삭제, UNIQUE 10개는 "비유니크 인덱스 + 아래 대체 보장" |
| 값 검증은 앱 + DB 이중 | 값 검증은 앱 하나(`Enum`/`COMMON_CODE`) |

**UNIQUE 대체 보장(경로 B 전용)**

| 제약 | 대체 | 동시성 위험 |
|---|---|---|
| `UK_ORCH_RUN_ACTIVE`(기관당 활성 실행 1) | 3-4 참조 | **높음**(다중 WAS) |
| `UK_TASKS_CASE_TEAM` | 작업 생성 전에 `BID_CASES` 부모 행 `SELECT … FOR UPDATE` 후 존재 확인, 그 뒤 INSERT(`BidCaseCommandService:255` 부근) | 중 |
| `IDX_BID_CASES_NOTICE`(반입 중복) | 반입은 `InboxService` 단일 경로라 기관 행 잠금 후 존재 확인, 정합성 점검 쿼리(아래 Q7)로 사후 탐지 | 중 |
| `UQ_AS_REQ_STEP` | 요청과 단계를 같은 트랜잭션에서 한 번에 INSERT(`ApprovalRequestService:158~161`), 동시 작성자 없음 | 낮음 |
| `UK_ORCH_STEP_SEQ` | 한 기관에 활성 실행 1건 보장 아래에서 실행 엔진이 SEQ_NO를 단일 흐름으로 부여 | 낮음 |
| `UQ_BFU_REQ` | 위 3-1-B | 낮음(미사용) |
| `UK_*_SEQ` 4개 | SEQ_NO는 DB가 부여하는 IDENTITY/AUTO_INCREMENT(MySQL은 키가 필요해 인덱스로 남긴다) | 낮음 |
| `UK_INSTITUTION_NAME`(007) | 저장 전 이름 조회 + 잠금 | 낮음 |

경로 B가 되면 조회용 인덱스로 `IDX_ORCH_STEP_RUN(RUN_ID, SEQ_NO)`, `IDX_AS_REQ(REQ_ID, STEP_NO)`, `IDX_BFU_REQ`를 추가하고(MySQL은 `IDX_TASKS_BID_CASE`도 필요), 기존 UNIQUE 정의를 인덱스로 치환하는 별도 diff를 DBA 회신 후 작성한다. 이번에는 14번 전체를 B로 만들지 않고 분기만 제시했다.

### 3-3. `015_drop_foreign_keys.sql` (이미 FK가 걸린 DB용, 멱등)

**MySQL** (`mysql` CLI 전제 — `DELIMITER` 사용. 이미 적용된 로컬 DB·새 DB 둘 다 안전)
```sql
-- 015 (MySQL): 이미 FK 가 걸린 DB 에서 FK 18개를 뗀다. FK 가 없으면 아무 일도 안 한다(멱등).
-- Windows MySQL 은 information_schema 의 이름이 소문자일 수 있어 LOWER() 로 비교한다.
DROP PROCEDURE IF EXISTS P_DROP_FK;
DELIMITER //
CREATE PROCEDURE P_DROP_FK(IN p_table VARCHAR(64), IN p_fk VARCHAR(64), IN p_new_idx VARCHAR(64))
BEGIN
  IF EXISTS (SELECT 1 FROM information_schema.TABLE_CONSTRAINTS
              WHERE TABLE_SCHEMA = DATABASE() AND LOWER(TABLE_NAME) = LOWER(p_table)
                AND LOWER(CONSTRAINT_NAME) = LOWER(p_fk) AND CONSTRAINT_TYPE = 'FOREIGN KEY') THEN
    SET @sql = CONCAT('ALTER TABLE ', p_table, ' DROP FOREIGN KEY ', p_fk);
    PREPARE s FROM @sql; EXECUTE s; DEALLOCATE PREPARE s;
    -- FK 가 자동으로 만든 인덱스(이름 = FK 이름)가 남아 있으면 조회용 이름으로 바꾼다.
    IF p_new_idx IS NOT NULL
       AND EXISTS (SELECT 1 FROM information_schema.STATISTICS
                    WHERE TABLE_SCHEMA = DATABASE() AND LOWER(TABLE_NAME) = LOWER(p_table)
                      AND LOWER(INDEX_NAME) = LOWER(p_fk))
       AND NOT EXISTS (SELECT 1 FROM information_schema.STATISTICS
                    WHERE TABLE_SCHEMA = DATABASE() AND LOWER(TABLE_NAME) = LOWER(p_table)
                      AND LOWER(INDEX_NAME) = LOWER(p_new_idx)) THEN
      SET @sql = CONCAT('ALTER TABLE ', p_table, ' RENAME INDEX ', p_fk, ' TO ', p_new_idx);
      PREPARE s FROM @sql; EXECUTE s; DEALLOCATE PREPARE s;
    END IF;
  END IF;
END//
DELIMITER ;
```

### 3-4. `UK_ORCH_RUN_ACTIVE` 동시성 보장

**경로 A**(UNIQUE 허용): 현재 그대로가 가장 강하다. 변경 없음.

**경로 B**(UNIQUE 불허). DDL 보장이 아니라 앱 보장이 되고, 동시성 규칙을 서비스에 못박아야 한다. 단일 JVM 메모리 잠금은 쓰지 않는다. 설계 헤더가 "WAS는 재기동·다중 인스턴스"라고 이미 적었다.

| 안 | 방법 | 장점 | 위험 |
|---|---|---|---|
| **B1 (권장)** | 잠금 표 `ORCH_ACTIVE(INSTITUTION_ID PK, RUN_ID, STARTED_AT)`. 실행 시작 시 INSERT(기본키 중복 = 이미 실행 중 → 409 `already running`), 종료·실패 시 같은 트랜잭션에서 DELETE | PK(UNIQUE 불필요)로 DB가 보장, 두 DB 동일 동작, `ACTIVE_INSTITUTION_ID` 낯선 칼럼 불필요 | 종료 누락 시 잠금 행이 남음 → 정합성 점검 쿼리 Q9와 수동 해제 절차 필요, 새 표 1개 |
| B2 | `start()` 트랜잭션 맨 앞에서 `INSTITUTIONS` 행을 `SELECT … FOR UPDATE`한 뒤 활성 실행 조회·INSERT | DDL 변경 없음 | **MySQL REPEATABLE READ 함정**: 같은 트랜잭션에서 잠금 전에 일반 SELECT를 했으면 옛 스냅샷으로 활성 실행을 못 볼 수 있다 → 잠금이 첫 쿼리여야 하고 활성 실행 확인도 `FOR UPDATE`로 읽는다. 기관 편집이 잠깐 대기 |
| B3 | 애플리케이션 재시도 + 사후 점검만 | 단순 | 보장이 아니다(비권장) |

테스트: `OrchestratorCoreTest.한_기관에_활성_실행은_하나뿐이다`는 경로 B에서 "서비스 수준 동시 시작 2건 중 1건만 성공"으로 바꾼다.

**코드의 두 부류를 나눈다(권장 규칙)**
1. **업무 마스터 코드**(공고 상태·협약 구분·금고 은행·기관 유형·제안 단계·입찰 결과 등)는 `COMMON_CODE`에서 읽어 검증하고, 값을 늘려도 배포가 필요 없다.
2. **분기 로직이 달린 고정 값**(`USERS.STATUS`, 결재 등급, 결재 요청·단계 상태, 실행 상태)은 Java `enum`이 정본이다. 값을 늘리려면 코드가 바뀌므로 코드 테이블에 넣어도 이중 관리일 뿐이다. 표시명 용도로만 시드할 수 있다.

- 코드 값은 영문 대문자·숫자·밑줄만 허용한다. 길이는 30자 이내로 한다.

### 3-6. **공고 예정일 경과 처리 이력 `NOTICE_FOLLOWUP`** (`018_notice_followup.sql`)

**설계 결정(되돌리기 쉬움, 근거 포함)**
- **단위 = 기관 × 회차(공고 예정일)**: 키는 `(INSTITUTION_ID, DUE_DATE, REV_NO)`. 같은 예정일에 상태를 바꿀 때마다 `REV_NO`가 1씩 늘어나는 **추가 전용(이력 보존)** 구조다.
- **현재 상태 = 그 회차에서 `REV_NO`가 가장 큰 행.** 별도 "현재" 표를 두지 않는다(기관 129+곳이라 부하가 없고 이중 쓰기가 사라진다).
- **복합 PK가 곧 동시성 보장**: UNIQUE 없이 PK만으로 같은 `REV_NO`가 두 번 들어가지 못한다. 클라이언트가 읽은 `base_rev`를 보내면 서버가 `REV_NO = base_rev + 1`로 INSERT하고, PK 충돌은 409(`conflict`)로 돌려준다. 경로 A·B 어느 쪽이든 같다. CHECK도 쓰지 않는다.
- **새 회차는 새 키**: 공고 종료 처리한 기관이 다음 회차 예정일을 넘기면 `DUE_DATE`가 달라 자동으로 다시 미처리(행 없음)가 된다(planner 3절). 단, 16건 정정처럼 **예정일이 바뀌면 같은 건이 새 회차로 보여 미처리로 되살아난다**(열린 질문 U5).
- **미처리 = 경과했지만 행이 없는 건**, **지연 대기 + `NEXT_CHECK_DATE` 경과 = 다시 미처리 취급**이다. 이 판정은 서버 쿼리·화면이 하고 DB에는 저장하지 않는다.
- **담당자명·사번·처리 시각은 서버가 채운다.** 요청 본문의 값은 받지 않고 `Actor`와 `USERS`에서 읽는다. `HANDLER_NAME`은 그 시점의 이름 스냅샷이다(이름이 바뀌어도 이력은 그대로).
- **`EMP_VERIFIED`**: 현재 인증이 `X-Emp-No` 자기신고라, 앞단 주체로 확인된 건인지 `ACCESS_LOG.EMP_VERIFIED`와 같은 뜻으로 남긴다. 0이면 위조 가능한 기록이다. 화면은 "검증됨"이라고 표시하지 않는다.

Oracle 정본:
```sql

--  참조(서비스 확인): INSTITUTION_ID -> INSTITUTIONS, HANDLER_EMP_NO -> USERS(ACTIVE), STATUS_CD -> COMMON_CODE(NOTICE_STATUS)

-- ⚠️ OPINION 은 자유 글이라 개인정보·원문 주소를 넣지 않도록 화면이 안내한다. 접근 이력에는 본문을 넣지 않는다.

    STATUS_CD        VARCHAR2(20 CHAR)  NOT NULL,   -- COMMON_CODE NOTICE_STATUS (IN_PROGRESS/CLOSED/DELAYED)

    HANDLED_AT       VARCHAR2(40 CHAR)  NOT NULL,   -- Times.nowIso
    CONSTRAINT PK_NOTICE_FOLLOWUP PRIMARY KEY (INSTITUTION_ID, DUE_DATE, REV_NO)
);
CREATE INDEX IDX_NF_STATUS  ON NOTICE_FOLLOWUP (STATUS_CD, NEXT_CHECK_DATE);   -- 지연 대기 재확인일 조회
```

- `RefChecks`(또는 서비스 공통 헬퍼): `requireInstitution(id)`, `requireActiveUser(empNo)`, `requireCode(group, code)`.

- 오류 메시지에 SQL·테이블명·키 값을 싣지 않는다(예: "그런 기관이 없습니다").
- 쓰기 경로는 모두 `@Transactional` 안에서 부모 조회 → 자식 INSERT 순서를 지킨다.

**`NOTICE_FOLLOWUP` 쓰기 API 검증 제안(2단계, 먼저 security 검토)**
1. `Actor` 확인 + 영업팀 수정 권한(`canEditInstitution` 재사용 검토). 실패 시 403이며 접근 이력에 `DENIED` 기록(본문 제외).
2. 기관 존재(404). 단 서울 25구 밖은 기관 정본 DB 전환 전에는 404가 된다(U1).
3. `due_date`가 `YYYY-MM-DD` 형식·유효 날짜·`today` 이전(경과)인지 확인. 서버가 해당 기관의 예정일을 직접 계산하지 못하면(`logic.js`·화면 추정) 클라이언트가 보낸 날짜를 믿게 된다는 한계를 문서에 남긴다(U4).
4. `status_cd`가 `NOTICE_STATUS`에 있고 사용 중인지 확인.
5. `DELAYED`면 `next_check_date`가 오늘 이후여야 한다(팀 기본값 "다음 확인일 필수"). `CLOSED`·`DELAYED`는 의견이 필수다(팀 기본값). 의견은 500자 이내이고 제어 문자는 제거한다.
6. `base_rev`로 낙관적 락을 건다. 첫 처리는 `base_rev=0`, 이후 `REV_NO = base_rev + 1`이며 PK 충돌은 409다.
7. 응답 키는 snake_case(`institution_id`, `due_date`, `rev_no`, `status_cd`, `opinion`, `next_check_date`, `handler_emp_no`, `handler_name`, `emp_verified`, `handled_at`).
8. 접근 이력에는 경로·상태 코드만 남기고 `opinion`·쿼리값은 넣지 않는다.

## 4. 테스트

**깨질 가능성이 있는 기존 테스트**
- 경로 A + 제자리 FK 제거: 영향 예상 없음. `src/test/resources/application.properties:34`의 H2 DDL이 FK 없이 로드된다. FK 위반을 기대하는 테스트는 grep으로 못 찾았다(`OrchestratorCoreTest`의 `DataIntegrityViolation`은 UNIQUE 때문이라 유지).

- `/menus`·골든 04·05, `Menus.MENUS` 8개 키, `roles.js`는 이번 DDL과 무관하다.

**추가할 테스트(2단계, 입력 → 기대)**
1. `DdlRulesTest`(파일 스캔): `db/oracle/*.sql`·`db/mysql/*.sql`에서 `--` 주석 줄을 제거한 뒤 `FOREIGN KEY`와 `REFERENCES`가 한 번도 없어야 한다(`015_drop_foreign_keys.sql`만 제외). FK 재도입을 막는 회귀 방어선이다. MySQL 파일도 같이 검사된다.
2. `NoForeignKeySchemaTest`(H2 메타): `INFORMATION_SCHEMA`의 참조 제약 건수가 0이다(H2 2.x의 제약 종류 문자열은 'FOREIGN KEY'/'REFERENTIAL'을 모두 허용).
3. `CommonCodeSchemaTest`: 016·017 로드 후 `NOTICE_STATUS` 3건, 같은 `(그룹, 코드)` 중복 INSERT는 `DataIntegrityViolationException`.

## 5. 보안·위험·되돌리는 법

- **무결성 보장이 DB에서 앱·점검으로 이동한다.** 수동 SQL이나 앱 버그가 고아를 만들면 DB가 막지 못한다. 완화: 물리 삭제 금지 원칙(현재 코드에 DELETE 없음), `DdlRulesTest`로 FK 재도입 방지, 정기 점검 쿼리 Q1~Q11(최소 배포·월 단위로 DBA 또는 시스템 관리 화면에서 실행).
- **MySQL 함정 두 가지.** (a) REPEATABLE READ에서 잠금 읽기 전에 일반 SELECT를 하면 옛 스냅샷으로 동시 생성을 놓친다(경로 B2). (b) `RENAME INDEX`는 8.0 이상이다. 이 PC의 MySQL 8.0 사용은 README 기준이며 버전은 확인 필요.
- **경과 처리 쓰기는 다른 팀에 공유되는 쓰기 기능이다.** 처리자 사번이 자기신고(`X-Emp-No`)라 `EMP_VERIFIED=0`인 기록은 위조될 수 있다. 그래서 서버가 Actor로 처리자를 정하고 `EMP_VERIFIED`를 같이 저장하며, 화면에 "검증됨"이라고 표시하지 않는다. 이력이 추가 전용이라 사후 감사에는 쓸 수 있지만 본인 부인 방지(부인 방지)는 못 한다. 2단계 착수 전 `security` 설계 검토가 필요하다(NEXT 35).
- **자유 글(`OPINION`)**은 개인정보가 들어올 수 있다. 500자 제한, 화면 안내, 접근 이력에는 본문 제외. 실제 인물·비밀번호·원문 주소를 시드에 넣지 않는다.
- **README 갱신과 번호 갈림**: MySQL 007 부재로 두 DB 번호가 어긋나 있는 채라 새 번호가 양쪽에서 같은 의미를 갖도록 위 3-0 표를 정본으로 삼는다.
- **DBA에 보낼 때**: 수정한 `oracle/014`와, 같은 기준으로 고친 001·006·008·010·012(아직 적용 전이라면). 이미 일부가 적용됐으면 015(Oracle)가 필요하다. 어느 쪽인지 DBA 회신 전에는 알 수 없다.
- **되돌리는 법**
  - 수정한 DDL: git revert.
  - 이미 015를 실행한 DB에 FK를 다시 걸려면 먼저 점검 쿼리 Q1~Q8이 0행인지 확인하고, git 이력의 원래 `ADD CONSTRAINT … FOREIGN KEY` 정의를 `ALTER`로 다시 적용한다.
  - 016~018 롤백: `DROP TABLE NOTICE_FOLLOWUP; DROP TABLE COMMON_CODE;`(데이터 소멸, 이력은 복구 불가).

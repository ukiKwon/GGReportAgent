- 1단계 LINE 뒤에 2단계 ADMIN이 붙는 조건은 신청에 권한관리(admin)나 결재(approve) 권한이 들어 있을 때(`ApprovalRequestService.java:309-311`), 그리고 상위 결재자가 없을 때(`:334`)입니다. 그런데 2단계는 관리자면 아무나 승인할 수 있습니다(`:672-673`). 033 이후 전산팀장도 관리자라서 같은 사람이 1·2단계를 다 승인하게 됩니다.

        if (me.getEmpNo().equals(requester.getEmpNo())) {

// new
    private String eligibility(SysUser me, SysUser requester, ApprovalStep step, ApprovalRequest r) {
        String reqType = r.getReqType();
        if (me.getEmpNo().equals(requester.getEmpNo())) {
            return null;
        }
        if ("ADMIN".equals(step.getKind())) {
            return permissions.canAdmin(me.getEmpNo()) ? "SELF" : null;
        }
        String how;
        if (me.getEmpNo().equals(step.getApproverEmpNo())) {
            how = Ranks.mayApprove(requester, me) ? "SELF" : null;
        } else if (ApprovalTypes.NO_PROXY.contains(reqType)) {      // 담당자 변경은 결재자 본인만(대결 불가)
            how = null;
        } else {
            how = Ranks.mayDecide(requester, me)
                    && deputies.principalsOf(me.getEmpNo(), Times.todayKst()).contains(step.getApproverEmpNo())
                    ? "DEPUTY" : null;
        }
        // 관리자 확인을 상위 결재자 결재로 갈음한 권한 신청: 결재하는 사람(본인·대결자)이 지금도 관리자여야 한다.
        if (how != null && adminByLine(r) && !permissions.canAdmin(me.getEmpNo())) {
            return null;
        }
        return how;
    }

    /** 상신 때 상위 결재자가 관리자여서 ADMIN 단계를 붙이지 않은 권한 신청인가(payload 는 서버가 만든 값만 담는다). */
    private static boolean adminByLine(ApprovalRequest r) {
        return ApprovalTypes.PERM_REQUEST.equals(r.getReqType())
                && read(r.getPayload()).path("admin_by_line").asBoolean(false);
    }

## 5. 결재함 화면·알림 영향, 보안·위험, 되돌리는 법
- **화면**: 이 신청은 결재선 칩이 '오전산 · 대기' 하나만 나옵니다. 지금 일반 메뉴 신청과 같은 모양이라 frontend 변경이 필요 없습니다. `approvals.js:158-161`은 payload의 `reason`·`changes`만 읽으므로 `admin_by_line`이 더 붙어도 무시됩니다. "관리자 확인 생략" 같은 표시를 넣을지는 디자인/기획 몫입니다(이관).
- **알림**: ADMIN 단계가 없으니 "관리자 전원에게 2단계 결재알림"(`notifyStep` 498~504)이 이 건에는 나가지 않습니다. 상신 때 전산팀장 본인과, 관리자인 유효 대결자에게만 갑니다. 결과 쪽지는 그대로입니다.
- **다른 역할에 미치는 영향(일반 규칙이라서)**: 판정 기준이 팀이 아니라 "상위 결재자가 관리자인가"입니다. 그래서 다음도 한 번 결재로 끝납니다.
  - ① 예산팀장·영업팀장 등에게 사용자 예외로 admin 보기를 준 경우, 그 팀원의 결재·권한관리 신청
  - ② 관리자가 권한관리 화면에서 다른 역할(예: 영업부장)의 admin을 켠 경우, 그 아래 결재선
  - ③ 마스터처럼 전산팀 소속 관리자가 누군가의 지정 결재자인 경우

  모두 "결재자가 관리자라 관리자 검토가 이미 된 것"이라는 논리는 같습니다. 그러나 관리자 권한을 받은 한 사람이 자기 팀원에게 결재 권한을 혼자 줄 수 있게 됩니다(두 사람 통제가 사라짐). 전산팀으로만 좁히는 대안도 있습니다. 조건을 `Teams.teamOf(me.getRole())`가 '전산'이고 결재자도 관리자일 때로 바꾸는 것인데, 이 경우 Teams 문자열에 의존하게 됩니다. 어느 쪽인지는 기획 결정입니다. 기본안은 메인 권장(일반 규칙)대로 썼습니다.
- **403 경로**: 표시가 있는 건에서 관리자가 아닌 사람은 본인 결재자든 대결자든 `decide`가 403이고, 결재함 목록과 `can_decide`에서도 빠집니다. 상신 뒤 결재자가 관리자에서 빠지면 그 건은 아무도 결재할 수 없습니다. 신청자 본인이나 관리자가 취소하고 다시 상신하면 그때는 ADMIN 단계가 붙습니다. 결재함에서 갑자기 사라지는 것이 혼란스러울 수 있습니다(이관: 프런트 문구).
- **자기신고 인증의 한계**: `X-Emp-No`는 자기신고입니다. 오전산의 사번만 대면 누구든 이 한 번 결재로 권한을 반영할 수 있습니다. 이전에는 관리자 사번까지 한 번 더 대야 했으므로, 2인 확인이라는 형식상의 방어 한 겹이 이 경로에서 사라집니다. 사용자 결정의 결과이며 인증 자체는 바뀌지 않습니다.
- **변조**: `admin_by_line`은 서버가 payload에 쓰는 키입니다. 요청 DTO에는 이 필드가 없어 신청자가 넣을 수 없습니다(`ApprovalIn.PermRequest`는 reason·changes만 받는 것으로 읽었습니다. 적용 전에 DTO에 이 필드가 없는지 한 번 확인해 주세요).
- **감사**: 결재 단계 기록(acted_by·acted_as_deputy)과 권한 변경 이력(`approval:REQUEST #id`)은 그대로 남습니다. 접근 이력에 새 값은 넣지 않습니다.
- **되돌리는 법**: 3-1의 `if (needsAdmin && canAdmin…)` 블록만 지우면 결재선이 예전으로 돌아갑니다. 이미 1단계로 상신된 PENDING 건은 eligibility 조건(3-2)이 남아 있는 한 안전합니다. 3-2·3-4까지 되돌리면 그 건들은 비관리자 대결자도 결재할 수 있게 되므로, 먼저 `admin_by_line` 건을 취소한 뒤 되돌립니다.

## 6. 이관 메모
- [이관: 기획] 관리자 확인을 생략하는 범위를 정해야 합니다. 상위 결재자가 관리자인 모든 경우(현 패치)인지, 전산팀 결재선에만 한정할지입니다. 기다리는 것: 사용자 확인. 근거: 5절 "다른 역할에 미치는 영향".
- [이관: 기획] 결재 권한(approve) 신청까지 전산팀장 한 번으로 끝내는 것이 사용자 결정 범위에 맞는지 확인이 필요합니다. 결정 문장은 "권한을 신청하면"이라 둘 다 포함한 것으로 해석했습니다.
- [이관: 프런트·디자인] 결재 시점에 관리자가 아니어서 결재함에서 빠진 건과 403 안내 문구가 필요합니다. 현재 403 메시지(`:400-401`)에는 '관리자여야 함' 사유가 없습니다. 서버 문구를 바꿀지도 함께 정하면 됩니다.
- [이관: 프런트] 필요하면 `payload.admin_by_line`이 참일 때 결재선 옆에 "관리자 확인 겸함" 같은 보조 표시를 넣습니다(선택).

## 7. 열린 질문
- 생략 범위가 "상위 결재자가 관리자이면 어느 팀이든"인지 "전산팀만"인지 정해 주세요. 답에 따라 3-1의 조건 한 줄만 바뀝니다.

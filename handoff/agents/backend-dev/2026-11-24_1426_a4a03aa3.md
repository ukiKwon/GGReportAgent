## 목표·관심·제안 준비 현황 초기화 조사 (읽기 전용, 실행 안 함)

**방법·못 본 것**: 코드·마이그레이션 SQL만 읽었다. 로컬 DB의 실제 행 수·값은 못 봤고, 외부 `.n7.log`는 보지 않았다. 결재 `REQ_TYPE` 값의 전체 목록은 확정하지 못해(grep 실패), 아래 결재 삭제는 "건을 가리키는 REQ_ID"로만 골랐다. 확인은 DB에서 `SELECT DISTINCT REQ_TYPE FROM APPROVAL_REQUEST`.

### 1. 화면 → 표
| 화면 | API → 서비스 → 매퍼 | 채우는 표·조건 |
|---|---|---|
| 목표 기관 | `GET /bid-targets?year=` → BidTargetService → BidTargetMapper.xml `selectActiveByYear` | `INST_BID_TARGET` 중 `KIND_CD='GOAL'`, 기관·번호별 최신 REV, `ACTION_CD<>'CANCEL'`. 임기 시작일은 `INST_BID_TERM` |
| 관심 기관 | 같은 `/bid-targets` 응답의 `watch_items` (`selectActiveWatch`) | `INST_BID_TARGET` 중 `KIND_CD='WATCH'` (같은 표, 종류만 다름. 연도 무관) |
| 제안 준비 현황 | `PrepBoardController` → `PrepBoardService.list` → `PrepMapper.selectList` + `PrepBoardMapper` | `BID_PREP`이 행의 뿌리(모든 STATE 포함, 취소 건은 조회 범위로 거름). 열은 `BID_PREP_TASK`, `BID_ASSIGNMENT`(담당), `BID_PREP_CHECK`(수기 체크 최신 REV), `TASKS`(디자인 최종), `INST_BANK_CONTRACT`(읽기만) |

(참고: 화면 이름 "입찰 기관 확인"은 코드에 없다. 가장 가까운 것은 메뉴 '입찰 공고 현황'이고 `dashboard.js`가 그린다. 목표·관심 표시는 '입찰 현황판' 막대의 '목표·관심 기관' 전환에서 `/bid-targets`를 쓴다.)

### 2. 지울 표 (BID_CASE_ID / REQ_ID / 기관 키 참조)
"제안 확정"이 만든 건은 `BID_PREP`의 `BID_CASE_ID`가 뿌리다. 확정 때 `BidCaseCommandService.create`가 **`BID_CASES` 행도 새로 만든다**(`SOURCE_SLUG·NOTICE_ID`가 NULL — 공고 원본이 아님).

| 구분 | 표 | 키 | 비고 |
|---|---|---|---|
| 목표·관심 | `INST_BID_TARGET` | INSTITUTION_ID | 전부 지우면 목표·관심 모두 초기화. 목표만 지우려면 `KIND_CD='GOAL'`, 관심만은 `'WATCH'` |
| | `INST_BID_TERM` | INSTITUTION_ID | 임기 시작일 기록(목표 쪽). 선택 |
| | `INST_BID_TARGET_REQ_ITEM`, `INST_BID_TARGET_REQ_ACT` | REQ_ID | 목표 변경 결재 항목·감사 |
| 제안 준비 | `BID_PREP`, `BID_PREP_TASK`, `BID_PREP_CHECK`, `BID_PREP_FORM`, `BID_PREP_FORM_VER`, `BID_PREP_ATTACH`, `BID_PREP_LOG`(변경 이력), `BID_PREP_ACT`(감사) | BID_CASE_ID | `BID_PREP_ATTACH.STORE_KEY`가 가리키는 **디스크 파일은 SQL로 안 지워진다** |
| 담당 | `BID_ASSIGN_CASE`, `BID_ASSIGNMENT`, `BID_ASSIGN_LOG` | BID_CASE_ID | 확정 때문에 재확정 시 `requireNoAssignHead`(옛 배정 머리가 있으면 409)에 걸리므로 반드시 같이 지운다 |
| 이사회 | `BOARD_MATERIAL`(+`_SNAP`·`_LOG`·`_ACT`), `BOARD_MINUTES` 계열 8개 | BID_CASE_ID → MATERIAL_ID → MINUTES_ID | 자식은 MATERIAL_ID/MINUTES_ID로 따라 지운다 |
| 작업(task) | `TASKS`, `MESSAGES`(TASK_ID), `DESIGN_ROUND`·`_RECIP`·`_COMMENT`·`_ACK`(TASK_ID) | BID_CASE_ID → TASK_ID | 개설·작성 시작 뒤 생김 |
| 분석 실행 | `ORCH_RUN`(BID_CASE_ID null 허용), `ORCH_STEP`(RUN_ID) | | 참여 결정으로 시작된 건만 |
| 알림 | `NOTIFICATIONS` | TASK_ID, INSTITUTION_ID | 기관·작업 키로만 매칭. 의미 중복 위험 있음 |
| 결재 | `APPROVAL_REQUEST`, `APPROVAL_STEP`(REQ_ID) | REQ_ID | `BID_PREP.OPEN_REQ_ID/PLAN_REQ_ID`, `BOARD_MATERIAL.SUBMIT_REQ_ID`, `BID_ASSIGN_CASE.PENDING_REQ_ID`, `INST_BID_TARGET_REQ_ITEM.REQ_ID`, 각 LOG의 REQ_ID로 찾는다. 대기 중인 건이 남으면 결재함에 유령 카드가 뜬다 |
| 공고 건 | `BID_CASES` | BID_CASE_ID | **SOURCE_SLUG IS NULL AND NOTICE_ID IS NULL**인 행만 삭제 후보(확정이 만든 것). 공고 수집이 넣은 행은 유지 |
| 기타 | `PREP_NOBID_ACK` | BID_CASE_ID, EMP_NO | "입찰 없음 확인" 알림 재노출. 지우면 팝업이 다시 뜬다(시험엔 오히려 좋음) |

### 3. 지우면 안 되는 것
`INSTITUTIONS`, `INST_HEAD*`(기관장), `INST_PLAN*`·`INST_NEWS*`·`INST_BANK_CONTRACT`·`EXT_CHECK*`(수집·약정), `NOTICE_ROUND(_LOG)`(공고 원본·상태), 공고 수집으로 만든 `BID_CASES`, `USERS`·`USER_MENU_PERMS`·`COMMON_CODE`·`PREP_TASK_DEF`·`BOARD_FORM*`·`ROLE_MENUS`, `ACCESS_LOG`·`PERM_CHANGE_LOG`(접속·권한 감사).

**감사 행(`*_ACT`, `*_LOG`, `ACCESS_LOG`) 처리 — 두 안**
| 안 | 내용 | 영향 |
|---|---|---|
| A. 감사 보존(권장) | `BID_PREP_ACT`, `BID_PREP_LOG`, `BID_ASSIGN_LOG`, `BOARD_*_ACT/LOG`, `INST_BID_TARGET_REQ_ACT`는 남긴다 | 같은 BID_CASE_ID가 다시 생기지 않으므로 충돌 없음(새 건은 새 ID). 기관별 이력 화면에 옛 건이 고아로 남을 수 있음. "결재 끝난 건 감사는 잊지 마" 원칙과 일치. 단 `INST_BID_TARGET`은 감사 컬럼(EDITOR 등)이 행 자체에 있어 지우면 그 감사도 사라진다(백업이 유일한 근거) |
| B. 전부 삭제 | 위 감사·이력 표도 지운다 | 시험 데이터는 깨끗하나 감사 소멸. 백업 필수, 로컬 시험 DB에만 |

### 4. SQL 초안 (MySQL, 실행 금지. 시험 DB 전용, 단일 세션에서만)

```
(비밀번호는 프롬프트로 입력, 명령줄에 쓰지 않는다. `-p` 뒤에 값을 붙이지 않는다.)

**4-0' CTAS 백업(표별, 같은 DB 안)** — 예시 형식, 위 표 전부에 반복:
```
CREATE TABLE bak_20261124_inst_bid_target AS SELECT * FROM INST_BID_TARGET;
CREATE TABLE bak_20261124_bid_prep        AS SELECT * FROM BID_PREP;
CREATE TABLE bak_20261124_bid_prep_task   AS SELECT * FROM BID_PREP_TASK;
-- … 나머지도 bak_20261124_<소문자표이름>
```
CTAS는 인덱스·PK를 복사하지 않고, 이름 규칙이 `bak_` 접두라 스키마 마이그레이션과 안 겹친다. 원복은 `INSERT INTO <표> SELECT * FROM bak_…`.

**4-1 삭제 순서(자식 → 부모, 한 트랜잭션, 먼저 건 목록을 임시표에)**
```
START TRANSACTION;
CREATE TEMPORARY TABLE tmp_case AS SELECT BID_CASE_ID FROM BID_PREP;               -- 지울 건
CREATE TEMPORARY TABLE tmp_task AS SELECT TASK_ID FROM TASKS WHERE BID_CASE_ID IN (SELECT BID_CASE_ID FROM tmp_case);
CREATE TEMPORARY TABLE tmp_mat  AS SELECT MATERIAL_ID FROM BOARD_MATERIAL WHERE BID_CASE_ID IN (SELECT BID_CASE_ID FROM tmp_case);
CREATE TEMPORARY TABLE tmp_min  AS SELECT MINUTES_ID FROM BOARD_MINUTES WHERE MATERIAL_ID IN (SELECT MATERIAL_ID FROM tmp_mat);
CREATE TEMPORARY TABLE tmp_req  AS
  SELECT OPEN_REQ_ID AS REQ_ID FROM BID_PREP WHERE OPEN_REQ_ID IS NOT NULL
  UNION SELECT PLAN_REQ_ID FROM BID_PREP WHERE PLAN_REQ_ID IS NOT NULL
  UNION SELECT SUBMIT_REQ_ID FROM BOARD_MATERIAL WHERE SUBMIT_REQ_ID IS NOT NULL
  UNION SELECT PENDING_REQ_ID FROM BID_ASSIGN_CASE WHERE PENDING_REQ_ID IS NOT NULL
  UNION SELECT REQ_ID FROM INST_BID_TARGET_REQ_ITEM
  UNION SELECT REQ_ID FROM BID_PREP_LOG WHERE REQ_ID IS NOT NULL
  UNION SELECT REQ_ID FROM BID_ASSIGN_LOG WHERE REQ_ID IS NOT NULL;

-- 이사회
DELETE FROM BOARD_MINUTES_UTTER WHERE MINUTES_ID IN (SELECT MINUTES_ID FROM tmp_min);
-- SEG, ITEM, SCOPE, REV, SPEAKER 도 같은 식 (SPEAKER 의 키 컬럼은 058 에서 확인)
DELETE FROM BOARD_MINUTES WHERE MINUTES_ID IN (SELECT MINUTES_ID FROM tmp_min);
DELETE FROM BOARD_MATERIAL_SNAP WHERE MATERIAL_ID IN (SELECT MATERIAL_ID FROM tmp_mat);
DELETE FROM BOARD_MATERIAL WHERE MATERIAL_ID IN (SELECT MATERIAL_ID FROM tmp_mat);
-- 작업
DELETE FROM MESSAGES WHERE TASK_ID IN (SELECT TASK_ID FROM tmp_task);
DELETE FROM DESIGN_ACK / DESIGN_COMMENT / DESIGN_ROUND_RECIP / DESIGN_ROUND WHERE TASK_ID IN (SELECT TASK_ID FROM tmp_task);
DELETE FROM NOTIFICATIONS WHERE TASK_ID IN (SELECT TASK_ID FROM tmp_task);
DELETE FROM TASKS WHERE BID_CASE_ID IN (SELECT BID_CASE_ID FROM tmp_case);
DELETE FROM ORCH_STEP WHERE RUN_ID IN (SELECT RUN_ID FROM ORCH_RUN WHERE BID_CASE_ID IN (SELECT BID_CASE_ID FROM tmp_case));
DELETE FROM ORCH_RUN  WHERE BID_CASE_ID IN (SELECT BID_CASE_ID FROM tmp_case);
-- 사전 준비·담당
DELETE FROM BID_PREP_CHECK, BID_PREP_FORM_VER, BID_PREP_FORM, BID_PREP_ATTACH, BID_PREP_TASK, BID_PREP, BID_ASSIGNMENT, BID_ASSIGN_CASE, PREP_NOBID_ACK  -- 각각 WHERE BID_CASE_ID IN (SELECT … FROM tmp_case)
-- 감사 보존 안(A)이면 BID_PREP_LOG/ACT, BID_ASSIGN_LOG, BOARD_*_LOG/ACT 는 건너뛴다. 삭제 안(B)이면 같은 WHERE로 지운다.
-- 결재(안 B 또는 결재도 비울 때)
DELETE FROM APPROVAL_STEP WHERE REQ_ID IN (SELECT REQ_ID FROM tmp_req);
DELETE FROM APPROVAL_REQUEST WHERE REQ_ID IN (SELECT REQ_ID FROM tmp_req);
-- 목표·관심 (전부 비움; 목표만이면 WHERE KIND_CD='GOAL')
DELETE FROM INST_BID_TARGET_REQ_ITEM;  DELETE FROM INST_BID_TARGET;  DELETE FROM INST_BID_TERM;
-- 확정이 만든 공고 건만
DELETE FROM BID_CASES WHERE SOURCE_SLUG IS NULL AND NOTICE_ID IS NULL AND BID_CASE_ID IN (SELECT BID_CASE_ID FROM tmp_case);
COMMIT;
```
(`DELETE FROM a, b, c`는 MySQL 문법이 아니다 — 표마다 한 문장씩 쓴다. 위는 요약. 이 SQL은 파일로 확정하지 않았고, 호출자가 표 목록 그대로 문장을 펼쳐 쓴다.)

디스크 첨부 파일은 `SELECT STORE_KEY FROM BID_PREP_ATTACH`로 목록을 먼저 뽑고, 삭제 뒤 서버 업로드 폴더(설정 `config/application.properties`의 첨부 경로, 값은 읽지 않음)에서 사람이 정리한다.

**4-2 확인**
```
SELECT 'INST_BID_TARGET', COUNT(*) FROM INST_BID_TARGET
UNION ALL SELECT 'BID_PREP', COUNT(*) FROM BID_PREP
UNION ALL SELECT 'BID_PREP_TASK', COUNT(*) FROM BID_PREP_TASK

그리고 `db/mysql/ops/integrity_check.sql`(읽기 전용)을 돌려 0행(고아 없음)인지 본다. 서버는 재기동하지 않아도 되나(조회가 `flushCache`) 화면은 새로고침한다.

### 5. 지운 뒤 후보로 다시 보이는가
- 공고(`NOTICE_ROUND`)와 `INSTITUTIONS`, `BID_CASES`(공고 수집분)가 남으면 '입찰 공고 현황'에는 기관이 그대로 보이고, 활성 건이 없으니(`countActiveByInstitution=0`) **[제안 확정]이 다시 열린다**. 근거: `PrepService.confirm`의 활성 건 검사.
- 단, 공고 상태가 `NO_BID`(입찰 없음)·종료로 닫혀 있거나 접수 기한이 지났으면(`dashboard.js:396-430` — nobid/closed/past) 버튼이 막힌다. 그건 `NOTICE_ROUND(_LOG)`가 정하므로 이번 초기화로는 안 풀린다. 그 상태까지 되돌릴 거라면 `NOTICE_ROUND`·`NOTICE_ROUND_LOG`를 별도로 정해 지워야 하는데, **공고 원본·상태 기록이라 이번 요청 범위로 보지 않았다.** 사용자가 정해야 한다.
- 공고가 아직 없는 기관은 "올해 목표 기관" 예외(`dashboard.js:353`)로만 확정되므로, 목표(`INST_BID_TARGET`)를 지웠다면 다시 목표로 등록해야 공고 전 확정이 된다. 관심만 있고 공고가 없으면 확정이 안 된다.

### 보안·위험·되돌리는 법
- 되돌림: 4-0 백업이 유일한 근거. 시험 중 서버가 같은 DB를 쓰면 안 된다 — 서버를 끄고 한 세션에서만.
- 안 B는 감사(`*_ACT`·`ACCESS_LOG`가 아닌 업무 감사)를 소멸시키므로 운영 DB에는 쓰지 않는다. 자기신고 인증(X-Emp-No)이라 이 감사들의 행위자는 "검증됨"이 아니라 `EMP_VERIFIED` 값으로만 구분된다.
- 코드·마이그레이션 변경 없음(운영 스크립트는 마이그레이션 번호에 넣지 않고, 필요하면 `db/mysql/ops/`에 둔다. Oracle 쌍 스크립트는 만들지 않았다 — 로컬 시험 전용).

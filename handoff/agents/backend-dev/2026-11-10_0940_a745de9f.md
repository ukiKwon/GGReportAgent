    public static boolean isLeadOwned(java.util.List<SysUser> all, String team, String assignee) {
        if (assignee == null || assignee.trim().isEmpty()) {
            return false;
        }
        String leadRole = Teams.leadOf(team);
        for (SysUser u : all) {
            if (!"ACTIVE".equals(u.getStatus()) || u.getRole() == null

            }
        }
        return false;

## 5. 보안·위험·되돌리는 법
- **자기신고 한계**: 모든 새 문지기는 `X-Emp-No` 자기신고 위에 선다. 헤더 위조로 영업부장을 사칭하면 통과한다. "실수·선착순 방지"이지 사칭 방지가 아니다. 접근 이력은 `verified=false`로 남는다.
- **DENIED 기록**: `MenuGuard.deny`가 경로(쿼리 제외)와 고정 문구만 남긴다. 본문, 쿼리값, 비밀번호는 남지 않는다.
- **403 경로**: 신원 없음 401, 권한·역할 불일치 403, 사용자 없음 403. 모두 DENIED로 남는다. 서비스 403(역할·본인결재)도 ④로 DENIED가 된다.
- **S-1 잔여**: 담당자가 자유 문자열이라 팀장이 다른 이름을 적어 본인결재를 우회할 수 있다. 사번 기반 담당자 저장(63)과 묶어 닫는다. 임시 조치는 `draft`, `submit`에도 `guard.require`를 거는 것인데 골든 15, 16, 18, 19, 21, 22에 영향이 있다.
- **이어받기 부작용**: `APPROVER`, `FINAL_APPROVER` 컬럼은 처음 잡은 사람 값으로 남는다. 이어받은 사람은 컬럼에 기록되지 않는다. 반려 쪽지 발신자(`actor`)와 알림 이력에는 남는다.
- **`isLeadOwned`가 이름으로도 맞춘다**: 같은 이름의 일반 팀원이 담당이면 영업부장 결재로 올라간다. 안전한 방향의 과대 상향이다.
- **되돌리는 법**: 코드는 `git revert`이면 된다. DB는 변경 없음이다. 골든은 `git checkout golden/api/11… 12… 13… 14… 24… 25…`로 되돌린다.

## 6. 이관 메모
- [이관: 기획] 참여결정 단계별 역할을 확정한다. 권장안은 1단 영업팀 / 2단 영업팀장 / 3단 영업부장, `/finalize`는 영업부장이다. 영업부장 기본 메뉴에 `workflow`가 없어 3단 버튼 화면이 안 보이는 문제도 있다. — 기다리는 것: 역할 확정, 영업부장 메뉴 정책 — 근거: `BidCaseCommandService.decisionRole` 제안, `Menus.java:96`, `system-overview.html:625`

- [이관: 프런트] 워크플로 참여결정 버튼을 단계별 역할일 때만 활성화하고 403 문구를 표시한다. 게이트 승인·반려 버튼은 영업부장일 때만 활성화하고 `wf-by` 입력을 없앤다. 영업부장 결재함에 팀장 담당 작업이 `task` 카드로 온다. 문구는 팀장 담당이므로 영업부장이 직접 결재한다는 안내가 필요하다. — 기다리는 것: 이 패치 커밋 — 근거: `workflow.js:680-712`, `ApprovalsService` 패치
- [이관: 데이터] 골든 11, 12, 13, 14, 24, 25 응답의 `by`, `role`, `finalized_by`를 B안 값으로 갱신해도 되는지 확인한다. — 기다리는 것: 사용자 OK(B안 채택 시) — 근거: 위 골든 영향 절

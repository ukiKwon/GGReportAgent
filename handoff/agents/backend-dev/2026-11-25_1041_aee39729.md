## 2. 보안 반영 결과 (팀 결정 1~6)
1. **start 권한**
   - 확정자 본인, 또는 `sameTeamLead(확정자) == 나`인 영업팀장만 가능하다.
   - 다른 팀 팀장, 확정자가 영업팀장인 건의 다른 팀장, 부장, 디자이너는 403이다.
   - 시험 대상: S4 (LEAD2 포함), S12.
2. **알림 대상 fail-closed**
   - 알림 대상은 확정자의 같은 팀 팀장과 (시작한 사람·확정자·지명자 중 팀장이 있으면) 영업부장이다. 본인은 뺀다.
   - 하나도 못 정하면 쓰기 전에 409 `NOTIFY_TARGET_NOT_RESOLVED`를 낸다. 문구에 사번·이름은 없다.
   - 응답의 `notified_count`는 실제 발송 수다.
3. **성공 감사 줄**
   - `PrepService.start` 안에서 `audit.record(..., ui)`로 마지막에 같은 트랜잭션으로 쓴다.
   - 컨트롤러는 이 경로에서 실패 줄만 남긴다. 서비스 실패 줄은 기존 `auditFailure`가 별도 커밋한다.
4. **스위치 기본값**: 위 신규 파일 설명대로이며, 시험 setter는 유지했다.
5. **패치 B**: 위에 적용했다. D50은 `done` 한 건만 열린 상태라 3줄 그대로일 걸로 보지만 실행으로 확인이 필요하다.
6. `forStart`는 start의 ui로만 쓴다(`run`에도 같은 값을 넘긴다). `lockPrep`에는 `flushCache="true"`를 붙였다.

## 3. 설계와 달라진 점 (숨김 없이)
- **스위치 구조**: 설계는 단순 필드였다. 보안 4번 때문에 `BidTargetSettings`를 주입해 실시간으로 계산한다. 그래서 `setForTest(false)`의 뜻이 "강제 해제"가 됐다.
- **권한 함수**: 설계의 static `hasStartAuthority`(= 확정 취소 권한 재사용)를 인스턴스 메서드로 바꿨다. `users`와 `assignments.sameTeamLead`가 필요해서다. `hasUnconfirmAuthority`와 `PrepNobidService` 호출부는 건드리지 않았다.
- **start 시그니처**: 설계는 `start(me, actor, bid, in)`이었다. 감사용으로 `ui`를 인자로 받는 5인자다.
- **S14 기대값**: 200에서 409 `NOTIFY_TARGET_NOT_RESOLVED`로 바꿨다.
- **추가한 시험(설계에 없음)**: S3b(팀장이 확정하고 스스로 시작), S4에 LEAD2(다른 팀 팀장) 추가, S11b(목표 결재 꺼짐이면 start는 409 `OPEN_APPROVAL_ON`), S15(화면 값 UNKNOWN 처리).
- **감사 롤백 시험**: 테스트 트랜잭션 안에서는 롤백을 못 본다. 그래서 비트랜잭션 클래스(`PrepRollbackApiTest`)에 넣었다. 임시 CHECK 제약 `TMP_NO_START_OK`(OPEN_START의 OK 줄만 거부)를 만들고 `finally`에서 반드시 지운다. 상태·배정·과제·이력·쪽지가 모두 원복되는지, 실패(ERROR) 줄이 한 줄 남는지 단언한다. **이 시험은 H2의 ALTER TABLE CHECK 문법에 기대고 있어 실행 확인이 꼭 필요하다.**
- **지켜지지 않은 것**: 설계의 "기존 5개 시험 단언 수정 0건"은 D29 한 곳이 예외다.

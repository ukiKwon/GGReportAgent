### 2. 지시서와 다르게 한 곳
- **탭 위치를 타입 클래스로 쓰지 않았다.**
  - 처음 `CTTabStop`과 `STTabJc`로 썼더니 IDE가 "cannot be resolved"를 냈다. poi-ooxml-lite에 없는 것으로 보인다.
  - 그래서 `XmlCursor`로 pPr 맨 앞(`spacing` 앞)에 `<w:tabs><w:tab w:val="left" w:pos="left값"/></w:tabs>`를 직접 끼웠다. `addPageBorder`와 같은 방식이다.
- **`■` 뒤 탭은 `clean()`을 거치지 않는다.**
  - `clean()`이 `\t`를 공백으로 바꾸므로 "■\t"를 문자열로 넘기면 공백이 된다.
  - 그래서 '■' run, `<w:tab/>` run, 본문 run으로 따로 냈다.
- 시험 헬퍼 `squareLine(xml, text)`는 정규식으로 `■</w:t></w:r><w:r><w:rPr>…</w:rPr><w:tab/></w:r><w:r><w:rPr>…</w:rPr><w:t …>text` 순서를 확인한다.
  - Layout, Dates 시험은 package-private static이다.
  - API 시험 두 개는 private static이다. 클래스마다 복사해 뒀다.
- 나머지 지시서 old 문자열은 현재 파일과 일치했다. `manyRows`, `jpeg`, `render`, `BOX_W`, `BOX_H`, `act`, `docx`, `periodItem`, `documentXml`, `DESIGNER`는 모두 실제로 있었다.

### 6. 컴파일·실행이 불확실한 곳
- **srcRect 타입 사용:** `CTBlipFillProperties`와 `CTRelativeRect`는 IDE가 해석했다(import 오류 없음). `XWPFPicture.getCTPicture().getBlipFill()`과 `XmlCursor.setAttributeText`의 동작은 실행해 봐야 안다. 시험 `crop()`이 속성 값을 바로 검증한다.
- **w:tab 직렬화:** `squareLine` 정규식은 run 사이가 정확히 `</w:t></w:r><w:r><w:rPr>…</w:rPr><w:tab/></w:r><w:r><w:rPr>…</w:rPr><w:t …>` 모양이라고 가정한다. 이 가정과 pPr 안 `w:tab` 속성 순서(`w:val`, `w:pos`)는 실행 전에는 확인하지 못했다. 직렬화가 다르면 Layout, Dates 단언이 한꺼번에 실패한다. 그러면 정규식이나 `<w:tab w:val="left" w:pos="312"/>` 문자열을 맞춘다.
- **`?mode=` 빈 값:** 시험 `mode_경계값…`은 `?mode=`가 200이라고 가정한다. 컨트롤러는 확인하지 않았다. 400이면 시험 기대를 고치거나 컨트롤러 정책을 정해야 한다.
- **pPr 요소 순서:** `tabs`는 `spacing` 앞에 직접 끼웠다. 스키마 순서 위반이면 Word가 손상 경고를 낼 수 있어서 실물 확인이 필요하다.

import com.kbstar.kgi.ggreport.web.domain.BidPrep;

/**
 * 입찰 대상(064 BID_CASES.BID_SUBJECT_CD, 코드표 BID_SUBJECT) — NEXT 125.
 * 1단계는 표시 이름만 만든다. 확정 입력 검증·제목 추정은 2·3단계에서 여기 더한다.

public final class BidSubjects {
    public static final String GROUP = "BID_SUBJECT";
    public static final String MAIN_BANK = "MAIN_BANK";
    public static final String FUND_MGMT = "FUND_MGMT";
    public static final String CORP_CARD = "CORP_CARD";
    public static final String ETC = "ETC";

    private BidSubjects() {
    }

    public static String label(BidPrep p) {
        return p == null ? null : label(p.getBidSubjectCd(), p.getBidSubjectEtc(), p.getBidSubjectCodeName());
    }

    /** ETC 이고 손 이름이 있으면 그 이름, 아니면 코드표 이름, 코드표에 없으면 코드 그대로. 코드가 없으면 null. */
    static String label(String cd, String etc, String codeName) {
        if (cd == null || cd.trim().isEmpty()) {
            return null;
        }
        String c = cd.trim();
        if (ETC.equals(c) && etc != null && !etc.trim().isEmpty()) {
            return etc.trim();
        }
        if (codeName != null && !codeName.trim().isEmpty()) {
            return codeName.trim();
        }
        return c;
    }
}

## 5. 보안·위험·되돌리는 법
- **1단계 권한**: 새 검사 없음. 열람 규칙은 기존 경로 그대로다(`/preps` 403 = 영업·부장·디자이너 밖, 상세 404 = 볼 수 없는 건, 현황판 403 = 영업부서 밖). 입력도 없다. 입찰 대상은 민감 정보가 아니다.
- **2단계 동시성**
  - 같은 기관의 두 건을 동시에 확정해도 기관 행 `FOR UPDATE`(PrepService.java:242)가 순서를 정한다. 대상이 다르면 둘 다 통과, 같으면 두 번째가 409.
  - DB 유일 제약은 두지 않는다. MySQL은 부분 인덱스를 지원하지 않고, H2도 함수 인덱스를 지원하지 않는다. 대신 잠금 규칙을 유지하고 ops 점검 쿼리를 더한다.
    `SELECT p.INSTITUTION_ID, b.BID_SUBJECT_CD, COUNT(*) FROM BID_PREP p JOIN BID_CASES b ON b.BID_CASE_ID=p.BID_CASE_ID WHERE p.STATE_CD IN (진행 6개) GROUP BY p.INSTITUTION_ID, b.BID_SUBJECT_CD HAVING COUNT(*)>1`
  - 대상을 확정 뒤 바꾸지 못하게 해서, 잠금 밖에서 키가 바뀌는 경로를 없앤다.
- **권한 번짐**: 기관 단위 판정은 옛 흐름 `/run` 하나뿐이고, 실행이 기관 단위라 그대로 둔다(2절 ③). 2단계에 `/run`이 `bid_case_id`를 받게 되면 '그 건이 이 기관 건인가 + 그 건의 활성 담당자인가'로 좁힌다. 403은 `guard.denied`(감사 기록) 경로 그대로 둔다.

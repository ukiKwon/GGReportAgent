## 2. 원인·근거
- `BankYears.java:68-72`: `lines_now`에는 `termState == CURRENT`인 줄만 넣는다.
- `FUTURE` 판정은 `BankContractRules.java:104`(`from`이 오늘 이후)이다. `BidTargetRules.java:145`에서 이미 같은 판정을 쓴다.
- "취소된 줄 제외"는 이미 쿼리에서 처리된다. `BidTargetMapper.xml:108-110` `lineFrom`이 `ACTION_CD='SAVE'`이면서 같은 약정의 더 높은 `REV_NO`가 없는 줄만 읽는다. 최신 리비전이 취소(CANCEL)인 약정은 입력에 오지 않으므로 별도 코드가 필요 없다.
- "끝난 줄 제외"는 `FUTURE`만 고르면 저절로 된다. `PAST`·`UNKNOWN`은 빠진다.
- 권한·노출은 컨트롤러가 `guard.require(req, VIEW_MENU)`를 지난 뒤 `BankYears.summary` 결과를 그대로 내보낸다. `summary`에 키만 더하면 `lines_now`와 규칙이 같고, 컨트롤러와 서비스는 고칠 것이 없다.
- 접근 이력은 `"bank-summary n=<items 수>"`이다(컨트롤러 27행). 본문이나 값이 들어가지 않으므로 그대로 둔다.
- `BankYears.summary`는 `bankSummary()`(181행)와 `bankYears`(156행)에서 쓴다. 키 추가이므로 `/institutions/{id}/bank-years`의 `summary`에도 `lines_next`가 같이 생긴다. 호환상 문제는 없다.

### BankYears.java 패치
```java
// old (64-75)
    static Map<String, Object> summary(List<BankContract> lines, LocalDate today) {
        Map<String, Object> m = new LinkedHashMap<String, Object>();
        m.put("kb_now", nowState(lines, today));
        m.put("last_kb_year", lastKbYear(lines));
        List<Map<String, Object>> now = new ArrayList<Map<String, Object>>();
        for (BankContract c : safe(lines)) {
            if ("CURRENT".equals(BankContractRules.termState(c.getTermFrom(), c.getTermTo(), today))) now.add(line(c, true));
        }
        m.put("lines_now", now);
        m.put("record_count", safe(lines).size());
        return m;
    }

// new
    static Map<String, Object> summary(List<BankContract> lines, LocalDate today) {
        Map<String, Object> m = new LinkedHashMap<String, Object>();
        m.put("kb_now", nowState(lines, today));
        m.put("last_kb_year", lastKbYear(lines));
        List<Map<String, Object>> now = new ArrayList<Map<String, Object>>();
        List<BankContract> next = new ArrayList<BankContract>();
        for (BankContract c : safe(lines)) {
            String st = BankContractRules.termState(c.getTermFrom(), c.getTermTo(), today);
            if ("CURRENT".equals(st)) now.add(line(c, true));
            else if ("FUTURE".equals(st)) next.add(c);
        }
        m.put("lines_now", now);
        m.put("lines_next", nextLines(next));
        m.put("record_count", safe(lines).size());
        return m;
    }

    /** 시작 전(FUTURE) 줄 — 시작일 오름차순(같으면 약정 번호 순). term_from 은 YYYY·YYYY-MM·YYYY-MM-DD 이고 앞부분이 같으면 짧은 쪽이 앞이라 문자열 비교로 충분. */
    private static List<Map<String, Object>> nextLines(List<BankContract> next) {
        Collections.sort(next, new Comparator<BankContract>() {
            public int compare(BankContract a, BankContract b) {
                int r = a.getTermFrom().compareTo(b.getTermFrom());   // FUTURE 는 from != null 이 보장됨(termState)
                return r != 0 ? r : Integer.compare(a.getContractNo(), b.getContractNo());
            }
        });
        List<Map<String, Object>> out = new ArrayList<Map<String, Object>>();
        for (BankContract c : next) out.add(line(c, true));
        return out;
    }
```
- `java.util.*`를 이미 import하므로 `Comparator`와 `Collections`는 추가 import가 필요 없다.
- `getContractNo()`의 타입이 `int`인지 `Integer`인지는 확인하지 못했다. `Integer`여도 오토언박싱으로 컴파일되지만, null이면 NPE가 난다. 시험 데이터는 `setContractNo(1)`로 항상 값이 있다. 불안하면 `r != 0 ? r : 0`으로 줄여 타이브레이크를 뺀다. 이 경우 정렬은 안정 정렬이라 쿼리의 약정 번호 순이 유지된다.
- 출력 필드는 `line(c, true)`가 만들며 `lines_now`와 같다. 키는 `contract_no`, `rank_cd`, `bank_cd`, `bank_name`, `term_from`, `term_to`이다. 화면이 기대하는 `{rank_cd, bank_name, term_from, term_to}`를 포함한다.
- `kb_now`와 `last_kb_year`는 건드리지 않았다.

## 4. 테스트
- 깨질 기존 시험: 없다. 키 추가뿐이고 `lines_now`와 `kb_now`는 그대로다. 응답 전체를 문자열로 비교하는 시험은 `bank-contracts/summary` 관련으로는 찾지 못했다.
- 기준일은 `LocalDate.of(2025, 5, 1)`이다. `c(bank, from, to)` 헬퍼를 그대로 쓴다.

`BankYearsTest`에 추가한다.
```java
    @Test public void summary_lines_next_는_시작_전_줄만_그리고_lines_now_는_불변() {
        LocalDate t = LocalDate.of(2025, 5, 1);
        List<BankContract> l = Arrays.asList(c("B02", "2019", "2022-12-31"),   // PAST
                c("B04", "2023", "2026-12-31"),                                // CURRENT
                c("B02", "2027", "2030-12-31"));                               // FUTURE
        Map<String, Object> s = BankYears.summary(l, t);
        assertEquals(1, ((List<?>) s.get("lines_now")).size());
        List<?> nx = (List<?>) s.get("lines_next");
        assertEquals(1, nx.size());
        assertEquals("2027", ((Map<?, ?>) nx.get(0)).get("term_from"));
        assertEquals("OTHER", s.get("kb_now"));            // 계산 불변
        assertEquals(Integer.valueOf(2030), s.get("last_kb_year"));   // 불변(미래 끝 해도 포함하는 현재 동작 그대로)
    }

    @Test public void summary_lines_next_없으면_빈_배열() {
        Map<String, Object> s = BankYears.summary(Arrays.asList(c("B04", "2023", "2026-12-31")), LocalDate.of(2025, 5, 1));
        assertTrue(((List<?>) s.get("lines_next")).isEmpty());
        assertTrue(((List<?>) BankYears.summary(null, LocalDate.of(2025, 5, 1)).get("lines_next")).isEmpty());
    }

    @Test public void summary_lines_next_시작일_오름차순_끝난줄_제외() {
        BankContract a = c("B04", "2029", "2031"); a.setContractNo(1);
        BankContract b = c("B02", "2027-03", "2030"); b.setContractNo(2);
        BankContract d = c("B04", "2027", "2028"); d.setContractNo(3);
        BankContract past = c("B02", "2010", "2012"); past.setContractNo(4);
        List<?> nx = (List<?>) BankYears.summary(Arrays.asList(a, b, d, past), LocalDate.of(2025, 5, 1)).get("lines_next");
        assertEquals(3, nx.size());
        assertEquals("2027", ((Map<?, ?>) nx.get(0)).get("term_from"));
        assertEquals("2027-03", ((Map<?, ?>) nx.get(1)).get("term_from"));
        assertEquals("2029", ((Map<?, ?>) nx.get(2)).get("term_from"));
    }
```
- `last_kb_year` 단언(2030)은 현재 `lastKbYear`가 미래 줄의 끝 해도 포함한다는 사실을 고정한다. 이 동작 자체는 이관 메모 ①을 본다.
- API 시험(선택, `BidTargetApiTest` 189행 뒤)은 다음과 같다. 기존 시험처럼 `line(1,"B04",Y+1,...)`을 FUTURE로 넣고 `getAs(SALES,"/bank-contracts/summary")`를 호출한다. 기대값은 `items[0].lines_next.length==1`, `items[0].lines_now.length==0`이다. 이미 있는 `line()`·`body()` 헬퍼를 써야 하므로 메인이 시그니처를 확인해 맞춘다.
- 호출자가 실행할 명령: `cd kgi-ggreport-web && mvn -q -o test -Dtest=BankYearsTest,BidTargetApiTest`. 전체는 `mvn -q -o test`(380건 이상)로 한다. 8080 서버가 `target/`을 쓰고 있으면 테스트 뒤에 재기동한다.

## 5. 보안·위험·되돌리는 법
- 권한: `/bank-contracts/summary`는 `VIEW_MENU` 조회 권한이 필요하다. 권한이 없으면 `MenuGuard`가 403을 내고 DENIED 이력을 남긴다. 기존 `BidTargetApiTest` 296행이 이 경로의 403을 이미 확인한다. 새 노출 경로는 없고 필드도 `lines_now`와 같다. 개인정보와 메모는 포함하지 않는다.
- 접근 이력은 변경이 없다(건수만 기록).
- 응답 크기 증가는 미미하다. 줄 수 상한 `SUMMARY_MAX`가 `lines_now`와 같은 입력에 걸려 있다.
- 불완전 입력: 상한을 넘으면 마지막 기관을 빼는 기존 규칙이 `lines_next`에도 그대로 적용된다.
- 자기신고 `X-Emp-No` 인증의 한계는 기존과 같다. 이 패치가 바꾸는 것은 없다.
- 되돌리는 법: `summary()`와 `nextLines`를 old로 되돌리면 된다. DB 변경은 없다.

## 6. 이관 메모
- `[이관: 기획]` 화면 CONTRACT_DECIDED 판정에서 `last_kb_year`가 미래 끝 해(예: 2030)를 가리킬 수 있다. 시작 전 국민은행 약정이 있으면 `last_kb_year`가 미래가 된다. 그러면 '되찾기(예전엔 국민은행)' 표시 조건 `last_kb_year < 올해`가 거짓이 되어 의도와 맞는지 확인이 필요하다. 이번 패치는 요구대로 계산을 바꾸지 않았다. 화면은 `lines_next`에 국민은행(B02)이 있으면 CONTRACT_DECIDED로 먼저 처리하면 겹치지 않는다.
- `[이관: 프런트]` `lines_next`의 국민은행 판정은 `bank_cd`로 하는 편이 안전하다. 요구한 필드 모양에 `bank_cd`는 없지만 실제 응답에는 포함되어 있다. `bank_name` 문자열 비교는 '기타 은행' 입력에 취약하다.
- `[이관: 프런트]` `/institutions/{id}/bank-years`의 `summary`에도 `lines_next`가 생긴다. 무시해도 되지만 알아 둔다.

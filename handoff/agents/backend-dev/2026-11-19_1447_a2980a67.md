## 3. 설계

### 3-1. 상태 표 (값은 계약이라 그대로, 화면 이름표만 바꿈)

| TASKS.STATUS | phase_cd(새 응답 키) | 화면 이름표(디자인 결정) |
|---|---|---|
| 대기·작성중 | DESIGNING | 디자인 작업 중 |
| 1차완료 | IN_REVIEW | 의견 받는 중(n차본) |
| 2차완료 | HEAD_REVIEW | 영업부장 검토 |
| 최종완료 | FINALIZED | 제출본 확정 |

전이는 모두 `UPDATE TASKS SET STATUS=:to WHERE TASK_ID=:id AND STATUS=:from`의 조건부 갱신이다. 0행이면 409 `STATE_CHANGED`. TASKS 행 잠금이 직렬화를 맡는다.

| 동작 | 누가 | from → to | 회차 |
|---|---|---|---|
| [디자인 작업 완료] | 디자이너(미배정이면 선점, 아니면 본인) | 대기·작성중 → 1차완료 | n = max+1로 열고 수신자를 박제 |
| [다시 수정] | 디자이너 본인 | 1차완료 → 작성중 | n을 닫음(REVISE) |
| [영업 검토 완료·부장께 올림] = 기존 승인 | 영업팀장(팀장 본인이 담당이면 영업부장) | 1차완료 → 2차완료 | n을 닫음(FORWARD) |
| 영업팀장 반려(API는 남아 있음) | 영업팀장 | 1차완료 → 작성중 | n을 닫음(LEAD_RETURN) |
| [제출본 확정] = 기존 최종 승인 | 영업부장 | 2차완료 → 최종완료 | 이미 닫힘. 감사만 DSN_FINAL |
| [돌려보내기(사유)] = 기존 최종 반려 | 영업부장 | 2차완료 → 작성중 | 사유 필수(디자이너 최종 단계에만 새로 거는 규칙) |

### 3-2. 수신자 계산 ([디자인 작업 완료] 때 한 번, 회차에 박제)

`DesignReviewService.recipients(bidCaseId, me)`가 순서대로 모은다. 사번 기준 `LinkedHashMap`, 먼저 들어온 사유가 남는다.
1. `BidAssignmentMapper.selectActiveAssignees(bid)` → `ASSIGNEE_SALES`
2. 그 건 TASKS의 영업·전산·예산 ASSIGNEE를 사람으로 바꾼다 → `ASSIGNEE_<팀>`
   - 사번 형식(`MenuPerms.isEmpNo`)이면 그 사번의 사용자.
   - 이름이면 `teamOf(role)==팀`이고 ACTIVE이며 이름이 같은 사람이 **정확히 1명**일 때만 받는다.
   - 0명이거나 2명 이상이면 `unresolved_teams`에 팀 이름만 넣는다. 이름은 응답에 싣지 않는다.
3. ACTIVE이고 `Teams.LEAD_ROLES`(영업·전산·예산 팀장)인 **전원** → `LEAD`
   - 시드에는 영업팀장이 2명이라 둘 다 받는다(7절 질문).

제외하는 사람
- 비ACTIVE
- 호출한 디자이너 본인
- 영업부장(사용자 답 ⓐ)

결과가 0명이면 409 `NO_REVIEWERS`.

| `GET /tasks/{id}/design-review` | 담당 디자이너(미배정이면 디자이너 역할), 어느 회차든 수신자, 영업팀장, 영업부장 | `{task_id, bid_case_id, institution_name, status, phase_cd, current_round, round_open, unresolved_teams?, viewer:{can_complete, can_revise, can_comment, can_ack, can_forward, can_finalize, can_return}, rounds:[{round_no, opened_at, opened_by_name, closed_at, close_cd, recipients:[{emp_no, name, reason_cd, response_cd: COMMENTED/ACKED/NONE, acked_at}], comments:[{emp_no, name, seq_no, body, created_at}]}]}` | 404(디자이너 작업이 아니거나 없음), 403 DENIED |
| `POST /tasks/{id}/design/complete` | 디자이너 ∧ (미배정 ∨ ASSIGNEE ∈ {사번, 이름}) | 200 `{task_id, status:"1차완료", round_no, recipients_count, unresolved_teams}` | 403, 409 `STATE_CHANGED`·`TEAMS_NOT_DONE`·`NO_REVIEWERS` |
| `POST /tasks/{id}/design/revise` | 디자이너 본인 | 200 `{status:"작성중", closed_round}` | 403, 409 `ALREADY_FORWARDED`(2차완료 이상), 409 `STATE_CHANGED` |
| `POST /tasks/{id}/design/comments` `{round_no, body}` | 그 회차 수신자 ∧ ACTIVE | 201 `{round_no, seq_no}` + 디자이너에게 "의견이 달렸습니다" 쪽지(본문은 싣지 않음) | 400(빈 값, 1000자 초과, 제어·서식 문자, round_no 형식), 422 `PII_DETECTED`(종류만), 403, 409 `ROUND_CLOSED`·`ROUND_MISMATCH`·`TOO_MANY_COMMENTS`(1인 1회차 30건)·`RETRY` |
| `POST /tasks/{id}/design/ack` `{round_no}` | 같음 | 200 `{saved:true\|false}`(이미 했으면 false) | 403, 409 `ROUND_CLOSED`·`ROUND_MISMATCH` |
| `POST /tasks/{id}/approve`(기존, 응답 그대로) | 기존 역할 규칙 | 영업팀장 승인 = 부장께 올림, 영업부장 승인 = 제출본 확정, 반려 = 돌려보내기 | 기존 + 409 `STATE_CHANGED`, 디자이너 최종 반려에 400 `REASON_REQUIRED` |

**[디자인 작업 완료] 한 트랜잭션의 순서**
1. 세 팀 2차완료 재확인(`requireTeamsDone`과 같은 규칙)
2. `claimAssigneeIfUnset(이름)`
3. `updateStatusIf(대기·작성중 → 1차완료)`
4. 회차 INSERT(PK 중복이면 409)
5. 수신자마다 `notifications.create(사번, "쪽지", "{기관명} 디자인 작업 완료({n}차본) — 확인하고 의견을 남겨 주세요.", inst, taskId, null, stage, 디자이너 이름)`와 RECIP INSERT
6. 기존대로 영업팀장 역할 쪽지함에 `결재요청` 1건(결재 신호. 결재함과 같은 뜻)
7. 감사 `DSN_COMPLETE` OK

### 3-6. 감사 코드 (BID_PREP_ACT. 본문·사유·이름·파일명은 넣지 않는다)

| ACTION_CD | 기록 시점 |
|---|---|
| `DSN_OPEN` | 작업 자리 열기 |
| `DSN_VIEW` | 검토 화면 성공 열람(응답 전) |
| `DSN_COMPLETE` | [디자인 작업 완료] |
| `DSN_COMMENT` | 의견 남기기 |
| `DSN_ACK` | 확인함(이미 했으면 남기지 않음) |
| `DSN_REVISE` | [다시 수정] |
| `DSN_FORWARD` | 영업팀장 승인(부장께 올림) |
| `DSN_LEAD_RETURN` | 영업팀장 반려 |
| `DSN_FINAL` | [제출본 확정] |
| `DSN_RETURN` | [돌려보내기] |
| `TASK_SUBMIT` / `TASK_APPROVE` / `TASK_REJECT` | 세 팀 작업(보강) |

- 실패는 DENIED / HIDDEN / BLOCKED / INVALID로 남긴다.
- 디자인본 내려받기(`DSN_DOWNLOAD`)는 화면이 `window.open`이라 사번이 오지 않는다. 화면을 fetch→blob(X-Emp-No)으로 바꾼 뒤에 붙인다(6절 이관).

### 3-7. 단계 순서 (커밋 단위)
1. **S6-a**: 051 쌍 + DesignReviewMapper + `TaskMapper.updateStatusIf` + approve 조건부 갱신(골든 확인)
2. **S6-b**: DesignReviewService·Controller·DesignUiIds + submit 위임 + 파일 잠금
3. **S6-c**: 팀 작업 결재 감사 보강(TASK_*)
4. 그 뒤 security → design-reviewer(이름표·회차·의견 목록·확인/미확인 사람 표시) → frontend-dev → qa
5. 로컬 MySQL 051 적용은 사용자 명령으로 한다.

  - `GoldenWriteScenarioTest`: BID_PREP_ACT에 TASK_* 줄이 늘어도 단언은 특정 ACTION_CD만 본다(`:114-118`).
  - `TaskFilesApiTest`: 대기 상태라 파일 잠금에 걸리지 않는다.

**추가할 테스트** — 새 `DesignReviewApiTest`, `@Transactional`. 시드 사번은 아래와 같다.

| 역할 | 사번 |
|---|---|
| 영업팀 | 3918264 |
| 영업팀장 | 5047192, 5640327 |
| 전산팀장 | 6295038 |
| 예산팀장 | 9026715 |
| 영업부장 | 2674805 |
| 디자이너 | 7130526 |

1. **열기**
   - 세 팀 2차완료 + 디자이너 → 201, 다시 → 200 `created:false`
   - 한 팀이 1차완료면 409 `TEAMS_NOT_DONE`
   - 영업팀 → 403, ACCESS_LOG DENIED +1(증분)
   - 사번 없으면 401
2. **완료** → 200, 1차완료, round 1
   - NOTIFICATIONS가 RECIPIENT=사번으로 수신자 수만큼(BID_ASSIGN 영업 + 전산·예산 TASKS 담당 + 활성 팀장 전원, 중복 1회)
   - 디자이너·영업부장·비활성은 없음
   - 영업팀·전산팀·예산팀 역할 쪽지함은 늘지 않음
   - 영업팀장 결재요청 1건
   - BID_PREP_ACT DSN_COMPLETE OK 1행(screen·button, UI_VALID=1)
3. **사람별 읽음**: A가 자기 쪽지를 읽으면 B의 READ_AT은 null. A가 `?recipient=B사번` → 403
4. **동명이인**: 전산 TASKS 담당이 동명이인 이름이면 `unresolved_teams:["전산"]`, 쪽지 없음
5. **완료 거부**
   - 남이 담당한 디자이너 → 403
   - 1차완료에서 다시 완료 → 409 `STATE_CHANGED`
6. **의견**
   - 수신자 201, 디자이너 쪽지 +1(본문 미포함)
   - 비수신자 403
   - 빈 값 400 / 1001자 400 / `\u0007` 400
   - 전화번호 → 422 `PII_DETECTED`(응답에 값이 없음)
   - round_no 틀림 → 409 `ROUND_MISMATCH`
   - 31번째 → 409 `TOO_MANY_COMMENTS`
7. **확인함**: true → false, 비수신자 403
8. **다시 수정** → 작성중, 회차 1 CLOSE_CD=REVISE
   - 회차 1에 의견 → 409 `ROUND_CLOSED`
   - 다시 완료 → round 2, 쪽지가 수신자 수만큼 다시 감
9. **부장께 올림**: 영업팀장 approve → 2차완료, 회차 FORWARD. 디자이너 revise → 409 `ALREADY_FORWARDED`, 의견 → 409
10. **최종 단계**
    - 영업부장 반려(사유 없음) → 400 `REASON_REQUIRED`, 상태 2차완료 그대로
    - 사유가 있으면 → 작성중, 디자이너에게 사유 쪽지 → 완료 시 round 3
    - 영업부장 승인 → 최종완료, DSN_FINAL
11. **경합**: approve 직전 상태를 바꿔 두면(`updateStatus`) → 409 `STATE_CHANGED`. 선택: 두 스레드로 revise ∥ forward를 돌려 한쪽만 성공하는지 본다(`PlanCollectTxTest`처럼 트랜잭션 없이)
12. **파일 잠금**: 디자이너 작업이 1차완료일 때 업로드·삭제 → 409 `TASK_LOCKED`. 세 팀 작업은 그대로
13. **열람**: 수신자·영업부장·영업팀장 200, 비수신 전산팀 403
14. **예전 경로**: 디자이너 작업에 `/tasks/{id}/submit` → round 1과 사람별 쪽지(위임 확인), 팀 쪽지함은 0건
15. 머리글이 허용 목록 밖이면 UNKNOWN, UI_VALID=0
16. 골든 흐름 뒤 BID_PREP_ACT TASK_APPROVE 3행(5047192, 9026715, 6295038)

## 5. 보안·위험·되돌리는 법

**인증 한계**
- 모든 신원은 `X-Emp-No` 자기신고(`Actor`)다. 남의 사번을 대면 그 사람으로 의견·확인함·완료를 할 수 있다.
- EMP_VERIFIED=0이 정상값이다. "검증됨"으로 표시하지 않는다.
- 기존 `/tasks/{id}/draft|files|submit`(세 팀)은 `by`/`X-User-Id` 자유 문자열이라 더 약하다. 디자이너 submit만 이번에 X-Emp-No가 필수가 된다.
- 운영 전에 SSO가 필요하다(NEXT 35).

**403 경로**
- 모두 `guard.denied`나 `requireActiveUser`로 ACCESS_LOG DENIED를 남긴다. 사유는 고정 문구다.
- 업무 감사는 BID_PREP_ACT에 남긴다.
- 의견 본문·반려 사유는 감사·접근 이력에 넣지 않는다.

**개인정보·크기**
- 의견에 `Pii.scanLoose`를 적용한다(422에는 종류만).
- 1000자, 1인 1회차 30건 상한.
- 디자이너에게 가는 쪽지에는 본문을 싣지 않는다.

**동작 변화(의도한 것)**
- approve가 경합하면 409가 날 수 있다.
- 디자이너 작업 파일은 의견 단계부터 잠긴다.
- 디자이너 최종 반려는 사유가 필수다.
- 디자이너 제출 때 가던 팀 쪽지함 쪽지 3건이 사람별 쪽지로 바뀐다.

**남는 위험**
- 디자이너 담당이 이름 문자열이다(`designer.js` 호환). 동명이인 디자이너는 서로의 작업을 만질 수 있다.
- 회차마다 파일을 보관하지 않아, 앞 회차 의견이 가리키는 파일은 덮어써질 수 있다.
- 오케스트레이터가 나중에 이관되어 `taskUpdate("디자이너", …)`를 부르면 상태를 덮어쓴다(`Recorder.java:17-21`). 지금은 부르는 곳이 0건이다.

**되돌리는 법**
- 서버 커밋을 revert한다. 회차 행이 없으면 approve 훅은 아무것도 하지 않으므로 DB를 남겨 둬도 안전하다.
- DB는 051 머리말의 DROP 4줄로 지운다(데이터 소멸, 운영 금지).

## 6. 이관 메모
- [이관: 기획] '세 팀 팀장'의 범위를 정해야 한다. 활성 팀장 전원으로 할지(시드 영업팀장 2명), 그 건 결재 체인의 팀장만으로 할지. 기본값은 전원으로 구현한다. 근거 3-2 ③.
- [이관: 기획] 회차 도중 담당자가 바뀌면 새 담당자는 다음 회차부터 받는다(수신자 박제). 이대로 좋은지 확인 필요.
- [이관: 기획] [제출본 확정]이 BID_PREP 상태나 현황판 표시를 바꿔야 하는지 정해야 한다. 이번 설계는 TASKS만 바꾼다. 바꾼다면 fa(Prep*) 쪽 일이다.
- [이관: 디자인] 다음 규격을 정해야 한다.
  - phase_cd 이름표 4개
  - 회차 표시, 사람별 COMMENTED/ACKED/NONE 표시
  - 버튼과 X-Screen-Id/X-Button-Id 최종 이름(3-4 DesignUiIds 후보)
  - 반려 사유 입력
  - `unresolved_teams` 안내 문구
- [이관: 프런트] 해야 할 일
  - designer.js 제출을 `/tasks/{id}/design/complete`로 바꾼다(그전까지는 서버 위임으로 동작).
  - 열기·준비 목록·검토 화면을 붙인다.
  - 디자인 파일 내려받기를 fetch→blob(X-Emp-No)으로 바꿔야 DSN_DOWNLOAD 감사가 가능하다. 화면 규격이 나온 뒤에 한다.
- [이관: 보안] 검토할 것
  - BID_PREP_ACT 재사용과 DESIGN_ACT 분리 중 무엇을 쓸지
  - 의견 상한 30건
  - 디자이너 이름 기반 담당
  - 세 팀 `/tasks` 쓰기 경로에 인증이 없는 문제(기존 문제지만 이번에 드러남)

## 2. 요구·원인 요약 (근거)

### 1) 7·8 통합이 서버에 요구하는 것: 사실상 0

- **단계 번호·순번**: 서버 어디에도 계산·저장·검증하는 곳이 없습니다.
  - `PrepStage5`는 `PROPOSAL_SUBMIT·RESULT·CEREMONY·AGREE_LEGAL` 4칸만 봅니다(`PrepMapper.xml:32`, `PrepBoardService.java:83`).
  - grep `[78]단계|24단계|BOARD_DOC`의 결과는 `BoardUiIds.java:31-33` 주석 3줄뿐입니다.
- **칸 체크 관문·감사 이름**: 칸 코드 `BOARD_SECRETARIAT·BOARD_AUDIT·BOARD_COMPLIANCE`와 감사 `CK_BOARD_*`가 그대로라 바뀌지 않습니다(`PrepBoardColumns.java:55-57`).
- **이름 변경**: '가격결정위원회(재무)'·'출연금심의위원회(사업부)'는 작업 폴더에 **이미 들어가 있습니다**(`PrepBoardColumns.java:53-54`, 미커밋). 옛 이름을 단언하는 시험은 없습니다(grep 0건).
- **합친 단계의 완료·대상 아님·진행 판정**: 지금도 단계 상태는 화면이 계산합니다. 입력은 상세의 `tasks`와 현황판 행의 `cells`입니다(`prep.js:1774`).
  - 서버에 두 번째 판정을 두면 진실이 둘이 됩니다. 그래서 **화면 계산을 유지**합니다.
  - 서버는 입력값만 정확히 줍니다: T5 상태(새로 `NOT_APPLICABLE`가 가능), `board_na`, 3칸.

### 2) ⑥ '대상 아님' 묶음: 기존 길로는 안 됨

- **T5를 '해당 없음'으로 두는 기존 길이 없습니다.**
  - NOT_APPLICABLE은 `KIND_CONDITIONAL && !condApplies`일 때만 생깁니다(`PrepService.java:1293`). 판정기는 `RFP_REGISTERED` 하나뿐입니다(`:1266-1271`).
  - T5는 `REQUIRED`·FACT `BOARD_CONFIRMED`, T6은 `OPTIONAL`·`READY_YN=0`(준비 중)입니다(`024_bid_prep.sql:112-114`).
  - KIND_CD는 개설 때 건별 행으로 복사됩니다. 그래서 T5를 CONDITIONAL로 바꾸려면 기존 행 이행이 필요합니다. 이 방법은 기각했습니다.
- **'칸 체크 PUT 3회 + 과제 변경' 조합으로는 안 됩니다.**
  - T5는 FACT라 `setTask`가 409 `NOT_MANUAL`로 막습니다(`PrepService.java:887-889`).
  - 원자성도 없습니다.
  - 그래서 **묶음 엔드포인트 하나**가 필요합니다.
- ⚠️ **업무 영향**: T5는 REQUIRED라 '대상 아님'이 되면 필수 과제 목록(`ev.missing`)에서 빠집니다(`:1312-1320`).
  - 그러면 [제안서 작성하기] 조건(`ev.ready`, `:1441`)이 이사회 자료 결재 없이 풀립니다.
  - 의도와 맞다고 봅니다(이사회를 안 열면 자료도 없음). 다만 **팀장 결재로 확정되던 관문을 담당 혼자 끌 수 있다**는 뜻입니다. 이관 메모와 열린 질문에 올렸습니다.

### 3) 이사회 결과 코드는 PENDING이 아니라 SCHEDULED

- 실제 값은 `SCHEDULED`(의결 예정)·`PASSED`·`REJECTED`이고 코드표는 `BOARD_RESULT`입니다(`BoardMaterialService.java:89-93`, `020_board_material.sql:100-104`).
- 위원회도 이 코드표를 그대로 씁니다.
- 새 코드 그룹을 만들면 `CommonCodeSchemaTest.java:54`의 '나머지 그룹 4행' 단언이 깨집니다. 그래서 위원회 코드(FIN·BIZ)는 054처럼 **서버 상수**로 둡니다.

### 4) 안건 번호 규칙(068)

- 자유 문자열 30자, 가결·부결 때만 받습니다.
- 줄바꿈·제어문자는 400, 개인정보 모양은 422입니다(`BoardMaterialService.java:376-394`, `checkedText :1172-1194`).
- 위원회 '의안번호'도 같은 수준입니다. '2026-00-00'은 `Pii.scanLoose` 어느 패턴에도 걸리지 않습니다(`Pii.java:23-31`).

### 5) 첨부

- `UPLOAD_KINDS`에 4개를 더하면 나머지 규칙이 그대로 적용됩니다(`PrepAttachService.java:79-82`).
  - 형식 검사, 개인정보 검사, hwpx 검사, 담당 올리기
  - 열람: 담당·자기 팀 팀장·부장(`:430-440`)
  - 무효: 올린 담당 또는 자기 팀 팀장(`:373-418`)
- `TASK_CD` 칸은 20자라 들어갑니다(`025:20`).
- 한도는 건당 50개·300MB이고 종류와 상관없이 함께 셉니다(`:62-63, :459-464`).

### 6) 권한·쓰기 관문

- 칸 체크 저장 순서는 '건 행 FOR UPDATE를 첫 문장으로 → 담당 아니거나 건이 없으면 403 → 상태 409'입니다(`PrepBoardService.java:461-501`).
- 새 쓰기 3개는 이 순서를 **`PrepWriteGate` 한 곳**으로 모읍니다.
- 팀장 권한: 쓰기는 담당만입니다. 팀장·부장도 담당이 아니면 403입니다(칸 체크와 같음).
- 열람:
  - 상세 응답에 실리므로 `canSee`를 따릅니다. 자기 팀 팀장만 보고 다른 팀은 404입니다(`PrepService.java:1146-1149`).
  - 첨부는 `requireViewer`를 따릅니다.

### 7) DB 번호

- 실제 파일은 068까지 있습니다.
- 069~071은 NEXT 133, 072는 ca 세션 예약입니다(코디네이터 지시).
- 그래서 **073_prep_committee.sql** 하나로 묶습니다.

### 8) 시험 컨텍스트

- `PrepController` 생성자는 `PrepAuditIsolationTest.java:88,316`가 직접 `new`로 만듭니다.
- 그래서 새 엔드포인트는 **새 컨트롤러 `PrepStageController`**에 둡니다. 이러면 `PrepController`를 건드리지 않습니다.

## 3. 구현안

### 3-1. 저장 자리 선택지와 권장

| 안 | 내용 | 판단 |
|---|---|---|
| **A (권장)** | 새 표 `BID_PREP_COMMITTEE`<br>키 `(BID_CASE_ID, COMMITTEE_CD, REV_NO)`, 추가 전용(054 `BID_PREP_CHECK`와 같은 틀) | 개정마다 누가·화면·버튼·값이 그대로 이력이 됩니다(00_공통 '이전 값'). `base_rev` 409가 자연스럽습니다. DB 권한은 SELECT·INSERT만입니다. |
| B | `BID_PREP`에 `FIN_*`·`BIZ_*` 칸 6~8개 | 덮어쓰기라 이력 표가 따로 필요합니다. `BID_PREP` SELECT 3곳을 모두 고쳐야 합니다. 기각합니다. |

**'대상 아님' 표시 자리**

- 고른 곳: `BID_PREP_TASK`에 `NA_YN·NA_BY·NA_AT`를 더하고 T5·T6 행에 씁니다.
- 기각한 대안:
  - `BID_PREP`에 칸: SELECT 3곳 수정 필요
  - 054 표에 가짜 칸 코드: 현황판 목록에 섞임

**판정 규칙**: `NA_YN=1`이고 미완료면 `NOT_APPLICABLE`입니다. **사실 완료(확정)가 있으면 완료가 이깁니다.**

    private final PrepMapper preps;
    private final BidAssignmentService assignments;

    public PrepWriteGate(PrepMapper preps, BidAssignmentService assignments) {

        }
        return state;
    }

        String state = gate.lockForAssigneeWrite(me, bidCaseId, "이 입찰 건의 담당자만 이사회 '대상 아님'을 고를 수 있습니다.");
        BidPrepTask t5 = t5Of(bidCaseId);
        if (t5.getNaYn() == 1) {
            throw stateChanged();
        }
        String block = naBlockReason(bidCaseId, t5);
        if (BOARD_DOC_DONE.equals(block)) {
            throw coded(409, BOARD_DOC_DONE, "이사회 자료가 확정된 건은 '대상 아님'으로 바꿀 수 없습니다.");
        }
        if (block != null) {
            throw coded(409, BOARD_DOC_IN_FLIGHT, "결재 중이거나 확정된 이사회 자료가 있어 '대상 아님'으로 바꿀 수 없습니다.");
        }
        String now = Times.nowIso();
        if (preps.setBoardNa(bidCaseId, me.getEmpNo(), now) < 1) {
            throw stateChanged();
        }
        Map<String, Object> cells = new LinkedHashMap<String, Object>();
        for (String col : BOARD_COLS) {
            PrepBoardCheck cur = boardMapper.selectCurrentOne(bidCaseId, col);
            if (cur == null || !PrepBoardService.NA.equals(cur.getMarkCd())) {
                cur = insertCheck(bidCaseId, col, cur, PrepBoardService.NA, me, actor, ui, now);
            }
            cells.put(col, PrepBoardService.manualCell(cur));
        }
        preps.insertLog(bidCaseId, EV_BOARD_NA, state, state, T5, null, null, me.getEmpNo(), BoardMaterialService.verified(actor), now);
        audit.record(bidCaseId, ACT_BOARD_NA, "OK", state, T5, actor, ui);
        return naOut(bidCaseId, true, cells, null, null);
    }

    /**
     * 되돌리기 — 관문 → 대상 아님이 아니면 409 STATE_CHANGED → T5·T6 NA_YN=0 → 3칸 중 '묶음이 쓴 NA 가 아직 현재 값'(MARK=NA 이고 SAVED_AT=NA_AT)인 칸만
     * 묶음 전 값(PREV_MARK_CD, 없으면 NONE)으로 새 개정. 그 뒤 사람이 바꾼 칸·원래 NA 였던 칸은 그대로(kept). 이력 BOARD_NA_CLEAR·감사 BOARD_NA_CLEAR.
     */
    @Transactional
    public Map<String, Object> clearBoardNa(SysUser me, Actor actor, BoardUiIds.Ui ui, String bidCaseId) {
        String state = gate.lockForAssigneeWrite(me, bidCaseId, "이 입찰 건의 담당자만 이사회 '대상 아님'을 해제할 수 있습니다.");
        BidPrepTask t5 = t5Of(bidCaseId);
        if (t5.getNaYn() != 1) {
            throw stateChanged();
        }
        String naAt = t5.getNaAt();
        String now = Times.nowIso();
        if (preps.clearBoardNa(bidCaseId) < 1) {
            throw stateChanged();
        }
        Map<String, Object> cells = new LinkedHashMap<String, Object>();
        List<String> restored = new ArrayList<String>();
        List<String> kept = new ArrayList<String>();
        for (String col : BOARD_COLS) {
            PrepBoardCheck cur = boardMapper.selectCurrentOne(bidCaseId, col);
            boolean ours = cur != null && PrepBoardService.NA.equals(cur.getMarkCd()) && naAt != null && naAt.equals(cur.getSavedAt());
            if (ours) {
                String back = cur.getPrevMarkCd() == null ? PrepBoardService.NONE : cur.getPrevMarkCd();
                cur = insertCheck(bidCaseId, col, cur, back, me, actor, ui, now);
                restored.add(col);
            } else {
                kept.add(col);
            }
            cells.put(col, PrepBoardService.manualCell(cur));
        }
        preps.insertLog(bidCaseId, EV_BOARD_NA_CLEAR, state, state, T5, null, null, me.getEmpNo(), BoardMaterialService.verified(actor), now);
        audit.record(bidCaseId, ACT_BOARD_NA_CLEAR, "OK", state, T5, actor, ui);
        return naOut(bidCaseId, false, cells, restored, kept);
    }

        SysUser me;

            me = guard.requireActiveUser(req);
        } catch (ApiException e) {

        }
    }

        return b.matches("[A-Za-z0-9._-]{1,64}") ? b : NO_CASE;
    }

## 5. 보안·위험·되돌리는 법

- **새 쓰기 API 3개**
  - 활성 담당만 쓸 수 있습니다.
  - 건이 없을 때와 비담당일 때는 같은 403입니다(존재 은닉, 칸 체크와 같음).
  - 잠금(FOR UPDATE)이 첫 문장입니다.
  - 상태 409, `base_rev`·PK로 낙관적 잠금을 겁니다.
  - 입력은 날짜 형식·코드 허용 목록·30자·제어문자·개인정보 422로 검사합니다.
  - 오류 문구에 값·이름이 없습니다.
- **감사**
  - 성공 줄은 저장과 같은 트랜잭션입니다. 감사가 실패하면 저장도 되돌아가고 500입니다.
  - 실패 줄은 따로 커밋합니다.
  - 칸 3줄은 `BID_PREP_CHECK` 자체에 화면·버튼(`prep_detail/board_na`)이 남습니다.
  - 접근 이력 DETAIL에는 건·상태·행위·`CM_FIN|T5`만 남깁니다. 값·의안번호·이름은 남기지 않습니다.
- **자기신고 인증의 한계**: `X-Emp-No`·화면·버튼은 모두 자기신고입니다. 담당 검사는 실수 방지용이지 사칭 방지가 아닙니다. `EMP_VERIFIED=0`이 정상값입니다.
- **업로드 종류 4개 추가**: 검사·권한 경로는 그대로입니다. 다만 **건당 50개·300MB 한도를 함께 씁니다**. 위원회 자료가 늘면 한도에 먼저 닿을 수 있습니다. security에서 한도를 볼 것을 권합니다.
- ⚠️ **관문 우회 가능성(security 판단 필요)**
  - '대상 아님'은 담당 한 사람이 결재 없이 T5(팀장 결재로 확정되는 필수 과제)를 필수 목록에서 뺍니다. 그러면 [제안서 작성하기] 조건이 풀립니다.
  - 남는 흔적: 이력 `BOARD_NA`(상세 이력에 행위자·시각 공개), `BID_PREP_ACT`, 상세 `board_na.by·at`. 팀장은 자기 팀 건 상세에서 볼 수 있습니다.
  - 결재나 쪽지를 붙일지는 기획 결정입니다(열린 질문).
- **남는 틈**
  - '대상 아님'인 동안에도 이사회 자료 작성·제출 길(`BoardMaterialService`)은 막지 않았습니다.
  - 확정되면 사실 판정상 '완료'가 이깁니다.
  - 막으려면 제출 관문에 `NA_YN` 검사를 더해야 합니다. 결재 흐름을 건드리는 일이라 이번 범위에서 뺐습니다.
- **요청 중 잠금(NEXT 136)**
  - 새 쓰기는 `PrepWriteGate` 한 곳을 지납니다.
  - 기존 쓰기 경로는 아직 각자 검사합니다: `PrepBoardService.save`·`PrepService.setTask/T3`·`PrepAttachService.upload/void`·`BoardMaterialService` 일정·결과·`PrepNobidService.ack`. 136이 잠금을 넣을 때 이 목록 전체를 관문으로 옮겨야 합니다.

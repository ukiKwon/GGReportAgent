## 2. 요구/원인 요약과 설계 결정
- **가드는 `tasks` 메뉴 조회로 걸 수 없다.** `Menus.java:92-98`에서 영업부장 기본 메뉴에 `tasks`가 꺼져 있다(`approvals`·`chat`·`workflow`만 켜짐). 재설계안 §3-4의 "가드는 `MenuGuard.require(tasks)`"를 그대로 따르면 영업부장이 열람에서 403이 된다. 그래서 **메뉴와 무관한 `MenuGuard.requireActiveUser`**를 새로 둔다.
  - 이 메서드는 사번 없음이면 401, USERS에 없거나 ACTIVE가 아니면 403이다. 둘 다 DENIED 이력에 남기되 고정 문구만 쓴다.
  - 그 위에 서비스가 **역할로 판정**한다. 열람은 `영업팀`·`영업팀장`·`영업부장`이다. 디자이너는 `Teams.isSalesFamily`로는 포함되지만 지시대로 제외한다. 관리자는 역할이 `전산팀`이라 걸러진다.
  - 최초 배정은 `영업팀장`만 가능하다. 관리자나 영업부장이 와도 403이다.
- 서비스가 던진 403(역할 위반)도 `guard.denied`로 DENIED에 남긴다. 컨트롤러에서 `TaskController:195-204`와 같은 방식으로 한다.
- **쓰기 판정**은 `BidAssignmentService.isActiveAssignee(bidCaseId, empNo)`다. 배정 테이블의 `ACTIVE_YN=1`만 조회한다. USERS ACTIVE 확인은 020 `BoardAccess`로 넘긴다.
- 영업팀장이 자기 자신을 넣는 것은 허용한다. 그 로그 행의 `REASON`에 "팀장 자기 포함 배정"을 남기고, 접근 이력에는 사번을 넣지 않는다.
- 담당자 대상 조건은 ACTIVE, 역할이 `영업팀` 또는 `영업팀장`, 1~10명, 사번 형식, 중복 불가다. 영업부장, 디자이너, 타 팀은 400이다.
- **응답 모양**: `/bidcases/{id}/assignments` GET은 `{bid_case_id, assigned, group_ver, assignees[], pending_change:null, viewer{is_assignee,can_assign,can_request_change}}`다. POST 201은 `{bid_case_id, group_ver, assignees[]}`, history는 배열, `/me/assignments`는 `[{bid_case_id, assigned_at}]`다. `pending_change`는 S2-b 전까지 항상 null이다.
- 응답은 `LinkedHashMap`에 snake_case 키를 직접 넣는다(`ApprovalDeputyService.view`와 같은 방식). `"검증됨"`이라는 단어는 쓰지 않고 `emp_verified`(boolean)만 둔다.
- 라우트 충돌은 없다. `/bidcases/latest`, `/bidcases/{id}`와 경로가 다르고, `/me/assignments`는 기존 `/me` 매핑이 없다(grep 확인).

package com.kbstar.kgi.ggreport.web.service;

import com.kbstar.kgi.ggreport.web.domain.BidAssignCase;

import com.kbstar.kgi.ggreport.web.mapper.SysUserMapper;
import com.kbstar.kgi.ggreport.web.support.MenuPerms;
import com.kbstar.kgi.ggreport.web.support.Teams;
import com.kbstar.kgi.ggreport.web.support.Times;
import com.kbstar.kgi.ggreport.web.web.Actor;
import com.kbstar.kgi.ggreport.web.web.ApiException;
import org.springframework.dao.DuplicateKeyException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

/**
 * 입찰 건 담당자 배정(019, S2-a) — 최초 배정·조회·이력·내 담당 건·쓰기 판정.
 *
 * <p>규칙(사용자 확정 2026-11-10): 담당자는 한 건에 1~10명, 영업팀·영업팀장만 지정 가능(영업부장·디자이너·타 팀 불가).
 * 최초 배정은 영업팀장만 하고(관리자·영업부장 403) 자기 자신을 넣어도 된다(이력에 표시). 열람은 영업팀 전원
 * (영업팀·영업팀장·영업부장 — 관리자·디자이너 403). 담당자 변경 결재(ASSIGNEE_CHANGE)는 S2-b 다.
 *
 * <p>⚠️ 호출자 사번은 X-Emp-No 자기신고일 수 있다({@link Actor}). 이 역할 검사는 <b>업무 규칙(실수 방지)</b>이지
 * 사칭 방지가 아니다. 이력의 {@code emp_verified} 는 "앞단 인증 주체였나"의 사실만 적는다.
 * 모든 쓰기는 한 트랜잭션이라 중간 실패 시 머리·배정·이력이 함께 되돌아간다.
 */
@Service
public class BidAssignmentService {

    public static final int MIN_ASSIGNEES = 1;
    public static final int MAX_ASSIGNEES = 10;

    static final String MEMBER_ROLE = Teams.DESIGNER_HOME_TEAM + Teams.TEAM_SUFFIX;   // 영업팀
    static final String LEAD_ROLE = Teams.leadOf(Teams.DESIGNER_HOME_TEAM);            // 영업팀장
    static final String HEAD_ROLE = Teams.FINAL_APPROVER;                              // 영업부장

    static final String ACTION_ASSIGN = "ASSIGN";
    static final String SELF_REASON = "팀장 자기 포함 배정";

    private final BidAssignmentMapper mapper;
    private final SysUserMapper users;

    public BidAssignmentService(BidAssignmentMapper mapper, SysUserMapper users) {
        this.mapper = mapper;
        this.users = users;
    }

    /**
     * 그 사번이 그 입찰 건의 <b>현재</b> 담당자인가 — 쓰기 판정의 단일 자리. 배정 테이블({@code ACTIVE_YN=1})만 본다.
     * 해제되면 다음 요청부터 false 다. 관리자 예외 없음. USERS ACTIVE 확인은 호출하는 쪽(020 BoardAccess)이 더한다.
     */
    @Transactional(readOnly = true)
    public boolean isActiveAssignee(String bidCaseId, String empNo) {
        if (bidCaseId == null || bidCaseId.isEmpty() || !MenuPerms.isEmpNo(empNo)) {
            return false;
        }
        return mapper.countActive(bidCaseId, empNo) > 0;
    }

    /** 배정 조회 — 영업팀 전원. 아직 배정 전이면 {@code assigned=false}, 담당자 빈 배열. */
    @Transactional(readOnly = true)
    public Map<String, Object> view(String bidCaseId, SysUser me) {
        requireSalesTeam(me);
        requireBidCase(bidCaseId);
        BidAssignCase head = mapper.selectCase(bidCaseId);
        List<BidAssigneeView> rows = mapper.selectActiveAssignees(bidCaseId);
        boolean assigned = head != null && !rows.isEmpty();
        boolean isAssignee = false;
        for (BidAssigneeView r : rows) {
            if (r.getEmpNo().equals(me.getEmpNo())) {
                isAssignee = true;
            }
        }
        boolean lead = LEAD_ROLE.equals(roleOf(me));
        Map<String, Object> viewer = new LinkedHashMap<>();
        viewer.put("is_assignee", isAssignee);
        viewer.put("can_assign", lead && !assigned);
        // 변경 신청 API 는 S2-b — 그 전에는 화면이 이 값으로 버튼을 만들지 않는다.
        viewer.put("can_request_change", assigned && (isAssignee || lead));
        Map<String, Object> m = new LinkedHashMap<>();
        m.put("bid_case_id", bidCaseId);
        m.put("assigned", assigned);
        m.put("group_ver", head == null ? 0 : head.getGroupVer());
        m.put("assignees", assigneeMaps(rows));
        m.put("pending_change", null);   // S2-b
        m.put("viewer", viewer);
        return m;
    }

    /** 최초 배정 — 영업팀장만. 이미 배정된 건은 409 {@code ASSIGNED_ALREADY}. */
    @Transactional
    public Map<String, Object> create(String bidCaseId, List<String> empNos, SysUser me, Actor actor) {
        if (!LEAD_ROLE.equals(roleOf(me))) {
            throw new ApiException(403, "최초 배정은 영업팀장만 할 수 있습니다.");
        }
        List<String> targets = validateTargets(empNos);
        requireBidCase(bidCaseId);
        if (mapper.selectCase(bidCaseId) != null) {
            throw alreadyAssigned();
        }
        String now = Times.nowIso();
        try {
            mapper.insertCase(bidCaseId, me.getEmpNo(), now);

        }
        Map<String, Object> m = new LinkedHashMap<>();

        m.put("group_ver", 1);
        m.put("assignees", assigneeMaps(mapper.selectActiveAssignees(bidCaseId)));

## 5. 보안·위험·되돌리는 법
- **권한 경로**
  - 사번 없음은 401, 미등록·비활성은 403이고 둘 다 `requireActiveUser`가 DENIED로 남긴다.
  - 역할 위반 403은 서비스가 던지고 `denyLogged`가 DENIED로 남긴다. 사유는 고정 문구뿐이다.
  - 접근 이력에는 본문·쿼리·사번 목록·사유·이름이 없다. 최초 배정 성공 때만 `assign case=… n=… code=ASSIGN`이 남는다.
  - 오류 문구에 사번 값을 싣지 않는다. 409는 `detail.code`가 `ASSIGNED_ALREADY`인 객체다.
- **자기신고 인증의 한계**: 모든 판정이 `X-Emp-No` 위의 업무 규칙이다. 앞단 인증이 없으면 남의 사번으로 영업팀장 행세와 최초 배정이 가능하다. `BID_ASSIGN_LOG.EMP_VERIFIED`는 사후 추적용이고, 응답에 "검증됨"이라는 표현은 없다. 근본 해결은 SSO(NEXT 35)다.
- **위험**
  1. 영업팀장은 DB에 2명이다(시드 5047192·5640327). 둘 중 누구든 최초 배정이 가능하고, 먼저 한 쪽이 이긴다(동시 요청은 PK 충돌로 409).
  2. `isActiveAssignee`는 USERS ACTIVE를 보지 않는다. 퇴직·잠금 처리된 담당자가 그 사이에 쓰기 판정을 통과할 수 있다. 020 `BoardAccess`에서 보강한다.
  3. 머리 행이 없는 입찰 건에서는 기존 `can_write` 경로가 그대로 동작한다(전환기 임시 허용). 020이 그 끝이다.
  4. `can_request_change`는 S2-b API가 생기기 전에는 의미가 없다. 화면은 S2-b 전까지 이 값으로 버튼을 만들지 않는다.
- **골든 영향 없음**: `/menus`, 골든 04·05, `Menus.MENUS` 8개 키, `roles.js`, Python `server/`, 기존 `/approvals`·`/tasks/{id}/approve` 동작을 건드리지 않았다. 기존 파일 수정은 `MenuGuard`에 메서드 추가, 테스트 2건 숫자, 테스트 properties 1줄뿐이다.
- **되돌리는 법**
  - 코드: 신규 파일 9개(domain 4, dto 1, mapper 인터페이스·XML 2, service 1, controller 1)와 `BidAssignmentApiTest`를 삭제한다. `MenuGuard`의 `requireActiveUser`를 지우고, 3-11의 세 수정을 되돌린다. 커밋 단위로 되돌려도 된다.
  - DB: 019 헤더의 `DROP TABLE BID_ASSIGN_LOG; DROP TABLE BID_ASSIGNMENT; DROP TABLE BID_ASSIGN_CASE;`와 `DELETE FROM COMMON_CODE WHERE CODE_GROUP='ASSIGN_ACTION';`를 쓴다. 데이터가 사라지므로 운영에서는 쓰지 않는다.

## 3. 요구/원인 요약과 설계 판단

**3-1. 팝업 대상 판정(서버 규칙).** 아래 3가지를 모두 만족할 때 `applicable=true`다.
- (a) 그 기관의 마지막 회차가 NO_BID로 닫혀 있다.
- (b) 기관 자료가 다음 회차로 넘어가지 않았다.
- (c) 그 기관에 활성 건이 있다.

(a)(b)는 `current()`와 같은 규칙이므로 `NoticeRoundRules.advanced`를 재사용한다.

**3-2. '다시 안 뜸' 판정은 서버가 한다.** 키는 사람+기관+회차+공고 기록의 `handled_at`이다. 공고 기록이 새로 저장되면 `handled_at`이 달라져 자동으로 다시 뜬다. `handled_at`은 `NoticeRoundLog.HANDLED_AT`의 최신 로그 값이다.

**3-3. [계속 작성] 기록이 기존 기록에 안 들어가는 이유**
- `BID_PREP_ACT`는 건 번호·행위·결과·화면·버튼을 담지만 '대상 공고 기록 시각'을 넣을 칸이 없다.
  - `TASK_CD`는 VARCHAR(20)이라 ISO 시각(약 25자)이 안 들어간다.
  - `STATE_CD`는 건 상태다.
  - 칸을 새로 더하려면 어차피 마이그레이션이 필요하다.
  - 또 `BID_CASE_ID`가 NOT NULL이라 건이 없으면 못 쓴다.
- `ACCESS_LOG.DETAIL`(300자)은 요청 로그다. 접근 이력 규칙은 값·본문을 넣지 않는 것이고, 이것을 '다시 안 뜸' 판정의 원본으로 쓰면 로그 정리·보존 정책에 업무 상태가 걸린다. 그 정책은 못 확인했다.
- 결론: 행위 기록 전용 표 1개(`PREP_NOBID_ACK`, 추가 전용)를 새로 둔다. 이 표가 '누가·언제·어느 화면·어느 버튼·대상 공고 기록 시각'을 한 줄로 갖는다. 업무 상태(BID_PREP·NOTICE_ROUND)는 건드리지 않는다.
- 접근 이력(`AccessLogInterceptor.DETAIL`)에는 `nobid-notice ack inst=… `처럼 코드·기관 번호만 남기고 `handled_at`·이름은 넣지 않는다.

**3-4. 마이그레이션 번호.** 046은 c0(설명회 기록용) 예약이다. 이 작업은 **047을 제안**하되 PM이 확정해야 한다(이관 메모). 아래 SQL 파일명은 `047_prep_nobid_ack.sql` 가칭이다.

### 4-2. API 설계 (새 컨트롤러 `NobidPrepNoticeController`, 새 서비스 `NobidPrepNoticeService`)

**GET `/institutions/{institutionId}/nobid-prep-notice`**
- 호출자 확인: `guard.requireActiveUser(req)`. 사전준비 목록과 같은 틀이다.
- 역할 확인: 영업팀·영업팀장·영업부장·디자이너만 통과하고, 그 밖은 403(`guard.denied`로 DENIED 기록). 사전준비 목록이 쓰는 규칙과 같다.
- 응답(snake_case):
```json
{
  "institution_id": "…",
  "applicable": true,
  "mode": "popup | fact_only | none",
  "notice": {"round_seq": 3, "rev_no": 2, "status_cd": "NO_BID", "handled_at": "2026-12-01T…", "handler_name": "홍길동", "emp_verified": false},
  "prep": {"bid_case_id": "…", "state_cd": "WRITING"},
  "acked": false,
  "can_ack": true,
  "can_view_notice": true,
  "can_cancel": true,
  "cancel_hint": "UNCONFIRM | CANCEL | RECALL_FIRST | NONE"
}
```
- `applicable=false`이면 `notice`·`prep`은 null이다.
- `mode`
  - 영업팀·영업팀장·영업부장이고 `applicable`이고 `acked=false` → `popup`.
  - 같은 조건에서 `acked=true` → `fact_only`(화면은 사실 한 줄만, 팝업 없음).
  - 디자이너 → `fact_only`(`can_ack=false`, 버튼 없음).
  - `applicable=false` → `none`.
- `can_ack` = `HeadRules.isSales(role)`. `can_view_notice`는 사전준비 화면의 열람 권한 기준이다. 읽기용 '공고 상태 보기'이므로 영업·디자이너 모두 true로 두되, 실제 이동 화면(입찰 공고 현황 = 메뉴 `map`) 권한이 없으면 화면이 안내만 띄워야 한다(이관 메모).
- `can_cancel`·`cancel_hint`는 위 2절 표를 서버가 계산한다(건 상태와 사용자 역할로).
  - CONFIRMED이고 확정자 본인 또는 영업팀장 → `UNCONFIRM`.
  - IN_PROGRESS·WRITABLE·WRITING이고 영업팀장 → `CANCEL`.
  - OPEN_PENDING·APPROVAL_PENDING → `RECALL_FIRST`(`can_cancel=false`).
  - 그 밖은 `NONE`.
  - 최종 판정은 기존 API가 한다. 이 값은 버튼 노출용이다.
- 접근 이력 DETAIL: `nobid-notice view applicable=Y/N`.

**POST `/institutions/{institutionId}/nobid-prep-notice/acks`**
- 요청 본문: `{"round_seq": 3, "handled_at": "…"}`.
- 접근 순서: 헤더 `X-Screen-Id`·`X-Button-Id`를 새 `NobidUiIds`의 허용 목록(화면 3개 가칭 + 버튼 `nobid_continue`)에 맞추고, 밖은 UNKNOWN·UI_VALID=0으로 저장한다.
- 검증 순서
  1. 호출자 활성 확인.
  2. `HeadRules.isSales` 아니면 403(DENIED 기록).
  3. 서버가 지금 상태를 다시 읽는다. `applicable`이 아니면 409 `NOT_APPLICABLE`.
  4. `round_seq`·`handled_at`이 지금 것과 다르면 409 `NOTICE_CHANGED`. 이때 화면은 GET을 다시 해서 새 팝업을 띄운다.
  5. 같은 사람+기관+회차+`handled_at`의 행이 이미 있으면 200 `saved=false`(멱등).
  6. 새 행이면 INSERT 후 201.
- 응답: `{saved, institution_id, acked_at}`. 이름·본문은 담지 않는다.
- 접근 이력 DETAIL: `nobid-notice ack inst=… `(코드·기관 번호만).
- 같은 사람이 동시에 두 번 눌러도 중복 행만 생기고 판정은 같다. 판정은 EXISTS이므로 UNIQUE는 두지 않는다(추가 전용 감사 성격).

### 4-3. 패치 윤곽 (파일별, 새 파일 위주)

① `mapper/NoticeRoundMapper.xml` — 한 기관 한정 NO_BID 현황 쿼리 추가
```xml
<!-- 신규 (selectClosedNoBidCurrent 와 같은 조건 + 기관 한 곳). 기관 자료 이동 판정은 서비스가 한다 -->
<select id="selectClosedNoBidCurrentOne" resultType="NoticeRoundView" flushCache="true">
  SELECT r.INSTITUTION_ID, r.ROUND_SEQ, r.ANCHOR_LAST_BID, r.CLOSED_LAST_BID, r.CLOSE_REASON_CD, i.LAST_BID AS CUR_LAST_BID,
         l.REV_NO, l.STATUS_CD, l.NEXT_CHECK_DATE, l.HANDLER_NAME, l.EMP_VERIFIED, l.HANDLED_AT
    FROM NOTICE_ROUND r
    JOIN NOTICE_ROUND_LOG l ON l.INSTITUTION_ID = r.INSTITUTION_ID AND l.ROUND_SEQ = r.ROUND_SEQ
    LEFT JOIN INSTITUTIONS i ON i.INSTITUTION_ID = r.INSTITUTION_ID
   WHERE r.INSTITUTION_ID = #{institutionId}
     AND r.CLOSED_AT IS NOT NULL AND r.CLOSE_REASON_CD = 'NO_BID'
     AND NOT EXISTS (SELECT 1 FROM NOTICE_ROUND m WHERE m.INSTITUTION_ID = r.INSTITUTION_ID AND m.ROUND_SEQ > r.ROUND_SEQ)
     AND NOT EXISTS (SELECT 1 FROM NOTICE_ROUND_LOG n WHERE n.INSTITUTION_ID = l.INSTITUTION_ID AND n.ROUND_SEQ = l.ROUND_SEQ AND n.REV_NO > l.REV_NO)
</select>
```
`NoticeRoundMapper.java`에 `NoticeRoundView selectClosedNoBidCurrentOne(@Param("institutionId") String institutionId);` 추가.

② `mapper/PrepMapper` — 활성 건 한 건(번호·상태·확정자) 조회 추가. 기존 `selectActiveStatesByInstitution`과 같은 6개 상태 목록을 쓴다(주석대로 목록이 어긋나지 않게 같은 값으로).
```xml
<select id="selectActiveByInstitution" resultType="BidPrep" flushCache="true">
  SELECT BID_CASE_ID, INSTITUTION_ID, STATE_CD, CONFIRMED_BY FROM BID_PREP
   WHERE INSTITUTION_ID = #{institutionId}
     AND STATE_CD IN ('CONFIRMED','OPEN_PENDING','IN_PROGRESS','APPROVAL_PENDING','WRITABLE','WRITING')
   ORDER BY UPDATED_AT DESC
```

## 6. 보안·위험·되돌리는 법
- **자기신고 인증의 한계**: 사번·역할은 `X-Emp-No` 자기신고 위의 업무 규칙이다. [계속 작성]은 감사 기록이지 본인 확인이 아니다. 응답·화면에 '검증됨'을 쓰지 않는다(`emp_verified=false`가 정상값).
- **권한 검사 순서**: 역할 검사(403)를 건 조회보다 먼저 한다(`PrepService` security F4와 같은 이유). 403은 DENIED로 접근 이력에 남기고, 사번 없는 401은 ACCESS_LOG에만 남긴다.
- **정보 노출**: GET은 기관 하나와 그 기관의 활성 건 상태만 내준다. 기록자 이름은 입찰 공고 현황이 이미 내주는 값이다. 다른 사람이 누른 [계속 작성] 기록은 응답에 담지 않는다.
- **위험 1**: 서버가 '다시 안 뜸'을 판정하므로 `handled_at` 문자열이 안정적이어야 한다. 공고 기록을 다시 저장하면 새 시각이 생기는 것이 의도다. 같은 판정을 다시 저장하면 `NO_CHANGE`로 끝나 시각이 안 바뀐다(`NoticeRoundService` 210~217행). 이 경우 팝업이 다시 안 뜨는 것이 맞는지 기획이 확인하면 좋다.
- **위험 2**: ack에는 기관 행 잠금을 쓰지 않는다. 판정 도중 공고가 바뀌면 NOTICE_CHANGED(409)로 정리된다.
- **위험 3**: 팝업 판정이 `INSTITUTIONS.LAST_BID`에 의존한다(`NoticeRoundRules.advanced`). 기관 자료가 넘어가면 팝업이 사라지는 것은 `current()`와 같은 동작이다.
- **위험 4**: 047이 먼저 안 적용된 DB에 서버를 올리면 이 GET이 500이다. 배포 순서(DB 먼저)를 헤더와 PM에게 알린다. 다른 화면은 영향이 없다.
- **되돌리기**: 서버 변경은 새 파일과 쿼리 2개 추가이므로 새 파일 삭제로 끝난다. DB는 `DROP TABLE PREP_NOBID_ACK;`(기록이 사라지므로 운영 금지).

## 7. 이관 메모
- [이관: PM] 마이그레이션 번호 047(가칭)로 가도 되는지, 046(c0 설명회 기록용)과 겹치지 않는지 확인 — 기다리는 것: PM 번호 확정 — 근거: 호출자 지시, 3-4절
- [이관: 기획] '공고 상태 보기'로 가는 입찰 공고 현황(메뉴 `map`)을 볼 권한이 없는 사람(영업부장·디자이너 등)에게 그 버튼을 어떻게 할지 정책 결정 — 기다리는 것: 기획 — 근거: 4-2절 `can_view_notice`. 서버는 사전준비 화면 쪽 권한만으로 true를 내므로, 이 분기는 정책이 정해지면 서버에서 `permissions`를 확인해 true/false를 나눌 수 있다.
- [이관: 기획] 영업부장은 취소 API를 쓸 수 없다(`unconfirm`은 영업팀·영업팀장, `cancel`은 영업팀장만). 팝업에서 영업부장에게 [제안 진행 정리하기]를 어떻게 보일지(숨김·안내) — 기다리는 것: 기획 — 근거: 2절 표
- [이관: 기획] 같은 공고 기록을 같은 판정으로 다시 저장해 `NO_CHANGE`가 되면 `handled_at`이 안 바뀌어 팝업이 다시 안 뜬다. 이 동작이 의도에 맞는지 확인 — 기다리는 것: 기획 — 근거: 6절 위험 1
- [이관: 프런트] 팝업을 띄울 입구가 몇 곳이든 GET은 `{institutionId}` 하나로 부르면 되므로 입구 전수 목록이 필요하다. `X-Screen-Id`에 쓸 화면 id 후보(예: 목록·상세·현황판 팝업)를 정해 알려 줄 것 — 기다리는 것: 프런트 — 근거: `NobidUiIds` 허용 목록
- [이관: 프런트] `mode=popup`일 때만 팝업, `fact_only`는 사실 한 줄, `none`은 아무것도 안 띄운다. `can_ack=false`면 [계속 작성] 숨김. `cancel_hint`로 취소 버튼 문구·노출 결정. ack 409 `NOTICE_CHANGED`면 GET을 다시 한다 — 근거: 4-2절
- [이관: 디자인] 버튼 셋이 [계속 작성]·[공고 상태 보기]·[제안 진행 정리하기]이고, 영업부장·디자이너는 일부 버튼이 숨거나 사실 한 줄만 보인다. 규격은 디자인이 정한다 — 근거: 4-2절 `mode`·`can_*`

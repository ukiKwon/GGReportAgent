## 2. 추가 응답 필드(HWPX TABLE일 때만)
기존 `found`, `attach_id`, `file`, `kind`, `rows`, `total`, `page`, `files` 는 그대로다. PDF(LINES)와 못 찾은 경우에는 새 필드가 없다.

```json
"cells": [{"r":1,"c":0,"rs":3,"cs":1,"text":"1. 신용도"}, ...],
"row_count": 5,
"col_count": 4,
"table": 0,
"candidate_count": 2,
"candidate_heads": ["부문 | 세부 항목 | 배 점 | 평가 방법", "구분 | 배점(점)"]
```

- r, c는 0부터이고 rs, cs는 병합 수다. 병합 속성이 없으면 span은 1이다.
- cellAddr가 없으면 행은 tr 순번, 열은 앞 칸 누적(c + cs)으로 둔다.
- `row_count`, `col_count` 는 cells의 최댓값으로 계산한다.
- 칸 상한은 기존 MAX_ROWS 200, MAX_COLS 12를 그대로 쓴다. 칸 수는 최대 2400이고, 병합 span도 이 범위로 자른다.

## 3. 후보 고르기
`GET /bidcases/{id}/prep/notice-scoring?table=n`

- 아래 경우는 400을 돌려준다.
  - 정수가 아닌 값
  - 음수
  - 20 이상
  - 파일의 후보 수 이상(`scoringFound` 에서 던진다)
- 인자가 없으면 0이다(첫 표, 지금 동작 그대로).
- 400은 `requireViewer` 뒤에 검사한다. 권한이 없는 사람은 먼저 404를 받는다.

## 5. 시험(`mvn -q -o test -Dtest=ScoringTableMergeTest,PrepAttachApiTest`)
- `ScoringTableMergeTest` 새 시험 3건
  - `병합_표의_위치와_병합_수를_복원하고_기존_필드는_그대로다`: 부문 rowspan 3, 배점 10이 세부 3줄을 묶음, 평가 방법 열 rowspan 3, '계' 칸 colspan 2, total=100을 확인한다. rows는 행별 칸 수 4, 4, 1, 1, 3이고, 병합 아래 줄은 열 위치 c=1로 남는다. 칸 수 13, `row_count` 5, `col_count` 4도 확인한다.

- 기대: 기존 `ScoringConsistencyTest` 와 PrepAttachApiTest의 나머지 시험은 그대로 통과한다.

## 6. 지시와 다르게 판단한 것
- 후보 수집이 첫 표에서 멈추지 않는다. 지시 2항(후보 수를 돌려줌)을 위해 구역 전체를 훑고, 후보가 20개가 되면 멈춘다. 첫 표만 찾던 때보다 파싱 시간이 늘 수 있지만, 15초 상한과 60MB 구역 상한 안에 든다. 실제 HWPX 33개로 시간을 확인해 보길 권한다.
- `table` 이 범위를 벗어난 경우의 400을 서비스의 `scoringFound` 에서 던진다. 첫 파일의 후보 수만 보고 판정하므로, 여러 파일이 있을 때는 처음 표가 잡히는 파일 기준이다.
- 새 필드는 PDF(LINES)에는 넣지 않았다(기존 응답을 그대로 두라는 지시에 따라).

## 7. 이관 메모
- [이관: 프런트] `preptask.js` 는 건드리지 않았다. `instsummary.js` 편집 표는 `cells` 로 `rowspan`/`colspan` 을 그리고, `candidate_count` > 1이면 `?table=n` 고르기를 둔다.
- [이관: 기획] 2쪽 내용(표·제목·출처)을 INST_SUMMARY 판에 저장하는 일(판 번호 올림, 크기 상한 확인)은 이번 지시 범위 밖이라 하지 않았다. planner 질문 1(원본 표 그대로인지)의 답이 필요하다.
- [이관: 데이터] 실제 HWPX 33개에서 첫 배점 표가 선정 평가표가 맞는지, 병합 속성이 실제로 `hp:cellAddr`/`hp:cellSpan` 로 들어 있는지 표본 확인이 필요하다. 시험은 내가 만든 최소 HWPX로만 했고, 실파일은 못 봤다.

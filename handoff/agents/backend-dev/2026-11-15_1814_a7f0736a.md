    /**
     * 실패 시도를 BID_PREP_ACT 에 남긴다. before 가 null 이면(앞단 거부·확정 실패) 여기서 건 상태를 읽는다(건 없음이면 NONE).
     * 기록이 실패해도 원래 응답(403·404·409…)을 덮지 않는다 — 서버 로그에 예외 종류만(ApprovalLineController.auditPrepFailure 와 같음).
     */
    private void auditFailure(String bid, String action, String outcome, String before, String taskCd, Long attachId,
                              Actor actor, BoardUiIds.Ui ui) {
        try {
            String st = before != null ? before : NO_CASE.equals(bid) ? NO_CASE : prep.stateOf(bid);
            audit.record(bid, action, outcome, st, taskCd, attachId, actor, ui);
        } catch (RuntimeException ex) {
            LOG.warn("사전준비 실패 감사를 남기지 못했다: action={} outcome={} cause={}", action, outcome, ex.getClass().getSimpleName());
        }
    }

    /** 제안 확정 실패 줄의 건 칸 — 본문 bid_case_id 가 건 번호 형식이면 그 값, 아니면 NONE. 기관 id·자유 문구는 넣지 않는다. */
    private static String confirmKey(PrepIn.Confirm body) {
        String b = body == null || body.getBidCaseId() == null ? "" : body.getBidCaseId().trim();
        return b.matches("[A-Za-z0-9._-]{1,64}") ? b : NO_CASE;
    }

### 5. 보안·위험·되돌리는 법
- **403 경로**:
  - 앞단 비활성·미등록 403은 ACT DENIED와 ACCESS_LOG DENIED(MenuGuard)에 둘 다 남습니다.
  - 서비스 403은 ACT DENIED와 `guard.denied`(고정 문구)에 남습니다.
  - 401은 ACCESS_LOG에만 남습니다.
  - 응답 상태·본문은 바뀌지 않습니다(같은 예외 객체를 다시 던짐).
- **자기신고 한계**: "미등록 사번" 403도 형식만 맞으면(`MenuPerms.isEmpNo`) 그 사번으로 ACT 줄이 생깁니다. 아무 사번이나 지어 보내 기록을 부풀릴 수 있습니다. BoardMaterial·ApprovalLine과 같은 기존 수준이고 새로 생기는 위험은 아닙니다(security 11-15 판정 ① 근거 3).
- **감사 칸 입력**:
  - 확정 본문 bid는 형식 허용 목록으로 거릅니다.
  - 기관 id·사유·본문 원문은 ACT·ACCESS_LOG 어디에도 넣지 않습니다.
  - warn 로그에는 고정 행위 코드, 결과, 예외 클래스 이름만 남습니다.
- **남은 비대칭(하, 기존 그대로)**:
  - ① `requireActiveUser`·`prep.stateOf`가 ApiException이 아닌 예외(DB 오류)를 내면 감사 없이 500이 됩니다. ApprovalLine 98-105행도 같고, DB가 죽었으면 감사도 실패하므로 실익이 작습니다.
  - ② 성공 줄 기록이 실패하면 쓰기는 이미 커밋된 채 500이 됩니다. 기존 의도는 읽기에서 데이터가 나가지 않게 하는 것이었는데, 확정·체크 같은 쓰기에서는 화면에 '실패'로 보이지만 실제로는 반영됩니다. 이번 범위 밖입니다.
- **security가 볼 포인트**:
  - (a) 'NONE' 키를 공유하는 것이 감사 조회 목적에 충분한지(기관 단위 추적은 안 됨).

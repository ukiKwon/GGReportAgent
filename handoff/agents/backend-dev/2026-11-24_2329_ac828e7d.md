## 5. 보안·위험·되돌리는 법
- **권한 경로는 바뀌지 않는다.**
  - `requireEditor` 두 줄(기관 수정 권한 + 영업 계열)이 먼저 403 DENIED로 막고 ACCESS_LOG에 남긴다.
  - `insert()`가 영업 계열을 다시 확인한다(`BidTargetService.java:441`).
  - 줄어든 것은 "영업 계열 안에서의 결재"뿐이다.
- **자기신고 한계**: X-Emp-No 자기신고 위의 업무 규칙이다. 사칭을 막지 못하고, EMP_VERIFIED로 자기신고 여부만 남는다. 화면·버튼 ID도 클라이언트 자기신고다(허용 목록 밖이면 UNKNOWN·UI_VALID=0).
- **우회 가능성 점검**: 연도나 주 담당을 바꾸려면 반드시 403이 난다. 판정은 서버가 cur와 비교해 하고, 본문의 "op"나 버튼을 믿지 않는다.
  - 일괄에서 `EDIT`로 보낸 항목도 같은 비교를 거친다.
  - kind 변경은 `KIND_EDIT_MSG` 400(`:290`)으로 막힌다.
- **동시성**: 기관 행 FOR UPDATE → `requireNoPending` → STALE(base_rev) → REV PK, 이 순서는 변하지 않는다. 결재 승인 쪽 `replan`은 base_rev 불일치를 ITEM_CHANGED로 막는다. 결재 중에는 바로 고치기가 409라 그 사이에 바뀔 수 없다.
- **업무 위험**
  - 현황판 위 '재유치·신규·되찾기' 숫자가 결재 없이 바뀐다. planner가 수용했고, 이력(REV)으로 추적한다.
  - 메모는 기존 `parse` 검사(100자 등)를 그대로 받는다.
- **접근 이력**: 고정 낱말 `basis=value`만 더하고 태그·메모 값은 넣지 않는다.
- **되돌리는 법**
  - 3-2의 `:308` 한 줄을 원래대로 돌리고, 3-5를 `plan(in, !direct)` + `if (direct)`로 돌린다. 데이터 정리는 필요 없다(쌓인 REV 행은 일반 기록).
  - 새 응답 키(`mode`·`direct_basis`·`value_edit_mode`)는 남겨도 해가 없다.

## 6. ② 설계 초안: 목표 기관이면 [개설 신청](BID_OPEN) 팀장 결재 생략 (Q1ⓐ 답 대기, 패치 아님)

**판정 '그해 결재 끝난 목표 기관'**(서버, 기관 행 잠금 안에서):
- 그 기관의 GOAL 중 ACTION≠CANCEL이고 `TARGET_YEAR = 올해(KST)`인 기록이 있다.
- `countPendingByInst = 0`이다.
- 그 기록이 **목표가 된 REV**(ADD·TO_GOAL·연도를 올해로 바꾼 EDIT)에 `APPROVAL_REQ_ID IS NOT NULL`이 있다.

열린 쟁점:
- 부장이 바로 넣은 행(REV에 역할이 남지 않음), 자동 이월(CARRY, 사람 결재 없음), 스위치를 끈 시기(11-23 이전)에 들어간 행은 "결재 끝남"을 증명할 수 없다. 기본은 불인정(결재 유지)으로 하고 기획에 묻는다.

**흐름**: 같은 `POST` 개설 신청 엔드포인트에서 `planOpen` 검증(지명 1~10명·활성·의견 검사·결재자 계산)은 그대로 하고, 판정이 참이면 다음과 같이 처리한다.
- `BID_PREP` CONFIRMED → IN_PROGRESS를 새 조건부 UPDATE `markOpenedDirect`(`WHERE STATE_CD='CONFIRMED'`)로 한다. OPENED_BY = 신청자.
- `assignInitial(bid, targets, 신청자, verified, null)`, 과제 행 생성.
- `BID_PREP_LOG`에 `OPEN_DIRECT`(CONFIRMED→IN_PROGRESS)와 근거 목표 번호를 남긴다. 값은 남기지 않는다.
- 팀장(계산된 결재자)에게 '개설 알림'을 보낸다. `notes.approvalRequestEnabled()`가 꺼져 있으면 결재 알림 채널이 막혀 있으므로 별도 종류가 필요하다.
- 응답에 `mode:"DIRECT"`·`open_basis:"GOAL_APPROVED"`(아니면 `mode:"APPROVAL"`)를 담는다. ①과 같은 모양이다.

**권장 제한**: `leadInvolved`(신청자나 지명자 중 영업팀장)면 생략하지 않는다(부장 결재 유지). 팀장이 자기를 지명해 부장 결재를 건너뛰는 길을 막기 위해서다.

**마이그레이션 초안**(번호는 적용 시점에 다시 확인 — 현재 마지막 060, 다른 세션이 061을 쓰면 뒤로 민다):
```sql
-- db/mysql/061_prep_open_basis.sql
ALTER TABLE BID_PREP ADD COLUMN OPEN_BASIS_CD VARCHAR(16) NULL COMMENT 'APPROVAL|GOAL_DIRECT, NULL=기존(결재)';
-- db/oracle/061_prep_open_basis.sql (정본, 적용은 DBA)
ALTER TABLE BID_PREP ADD (OPEN_BASIS_CD VARCHAR2(16));
COMMENT ON COLUMN BID_PREP.OPEN_BASIS_CD IS 'APPROVAL|GOAL_DIRECT, NULL=기존(결재)';
```
- 이미 060까지 적용한 DB는 061만 한 번 실행하면 된다. 기존 행은 NULL이며 '결재로 개설'로 읽는다.
- 로그만으로도 감사는 되지만, 102 집계와 113 정의에서 쓰려면 컬럼이 낫다.

**영향 범위**
- **NEXT 110 대결**: 생략 경로에는 결재가 없으니 대결도 없다. `mayDeputizeOpen`과 충돌하지 않는다. 결재가 유지되는 경우(목표 밖·leadInvolved)에는 그대로 적용된다.
- **NEXT 113 '팀·부서 = 개설 승인 끝난 건'**: 정의를 "개설 끝난 건(OPENED_AT IS NOT NULL — 승인 또는 목표 기관 바로 개설)"으로 바꿔야 한다. 범위 조회 SQL이 OPEN_REQ_ID나 결재 상태를 보면 바로 개설 건이 빠진다. 대시보드 세션이 확인할 거리다.
- **NEXT 102 집계**: '개설 승인' 수를 셀 때 GOAL_DIRECT를 포함할지, 따로 셀지 정해야 한다.
- **결재함 BID_OPEN 카드**: 바로 개설 건은 요청 행이 없어 카드가 안 생긴다. 팀장은 알림으로만 안다. "결재 끝난 목록"에 안 보이는 것이 맞는지는 기획이 정한다.
- **사후 담당 변경**: 지금 담당자 변경은 ASSIGNEE_CHANGE 결재 흐름이다. "팀장이 사후에 바로 바꿈"은 새 규칙이라 별건으로 다룬다(Opus 설계 + security).
- **위험**
  - 목표 판정을 잘못하면 결재 없는 개설이 생긴다. 판정은 반드시 잠금 안에서 서버가 하고, 화면 값은 믿지 않는다.
  - planner가 지적한 '서버 confirm은 공고·목표 게이트를 검사하지 않음'(acc23bb0)과 겹치는 우회가 있는지 security가 함께 봐야 한다.

## 7. 이관 메모
- [이관: 프런트] `tchange.js`·`kbboard.js`가 쓸 서버 계약 (기다리는 것: design-reviewer 규격, 근거 이 보고 3-7)
  - 줄 구분 칩·메모는 `GET /bid-targets`의 `value_edit_mode==="DIRECT"`이면 바로 `POST /institutions/{id}/bid-targets`.
    - 버튼 ID: 구분 `change_target_tag`, 메모 `edit_bid_target`.
    - **연도와 `owner_emp_no`는 cur 값을 그대로 보내야 한다**(빼먹으면 주 담당이 null로 "바뀐" 것이 되어 403).
  - 성공 판정: `saved===true && direct_basis==="VALUE_EDIT"`이면 "결재 없이 반영되고 기록에 남습니다" 알림. `NO_CHANGE`는 조용히 둔다. 409 `CHANGE_PENDING`이면 잠금 안내.
  - 일괄 [수정하기]: `/bid-targets/changes`에 `X-Button-Id: save_target_values`, 사유 없이 EDIT만 보낸다. 응답 `mode==="DIRECT" && direct_basis==="VALUE_EDIT"`.
  - 섞어 보내면 서버가 결재로 돌리고 사유 400을 낸다. 그러니 화면에서 섞지 못하게 막는다.
  - 결재 요청은 지금처럼 `mode==="APPROVAL"`.
- [이관: 기획] ② 판정에서 '결재 끝난 목표'에 부장 바로 넣기·자동 이월·스위치 끈 시기 행을 인정할지, leadInvolved는 결재 유지가 맞는지, 바로 개설 건을 102 집계·113 범위·결재함에 어떻게 보일지 정해야 한다. 기다리는 것: 사용자 Q1 답. 근거: 6절.
- [이관: 기획] 주 담당 변경은 ①에서 결재로 남겼다(사용자 목록·planner 범위 밖, 화면 칸도 불명). 결재 없이 해도 되는지 확인이 필요하다. 근거: planner 4절 끝.
- [이관: 보안] security 확인 거리
  - ⓐ `valueOnlyEdit` 판정 우회: 일괄 EDIT·단건 모두 서버가 cur와 비교하는지
  - ⓑ 결재 중 잠금 순서(`:304`가 `:308`보다 먼저)
  - ⓒ 접근 이력 DETAIL에 값이 없는지(`basis=value`만)
  - ⓓ 바로 반영 REV에 EMP_VERIFIED·SCREEN/BUTTON·UI_VALID가 빠짐없이 남는지
  - ⓔ `save_target_values`를 허용 목록에 추가한 것
  - ⓕ ②의 목표 판정 우회와 confirm 게이트 부재(acc23bb0)
- [이관: 대시보드 세션] ②가 채택되면 113 범위 SQL과 102 집계의 '개설' 정의를 OPENED_AT 기준으로 맞출지 확인한다.

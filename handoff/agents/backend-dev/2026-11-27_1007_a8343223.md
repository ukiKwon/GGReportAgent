**2. 066 내용**
- 설계서 최종판(`2026-11-26_1802_a12c06a4.md`)의 066 절과 보완판(1737)의 oracle 헤더를 합쳤다. 헤더에는 1802의 기타 4줄을 더했다. 형식은 063·064·065 관례(정본 헤더, 멱등 아님, INSERT 블록 마커)를 따랐다.
- INST_BID_TARGET에 `BID_SUBJECT_CD`(VARCHAR(20) NOT NULL DEFAULT 'MAIN_BANK'), `BID_SUBJECT_ETC`(50), `BID_CASE_ID`(64), `AIM_RANK_ETC`(30)를 더했다. 뒤의 셋은 NULL 허용이다. `IDX_IBT_CASE` 색인도 만든다.
- INST_BID_TARGET_REQ_ITEM에 `BID_SUBJECT_CD`(DEFAULT 'MAIN_BANK' NOT NULL), `BID_SUBJECT_ETC`, `AIM_RANK_ETC`를 더했다.
- REQ_ITEM의 PK를 (REQ_ID, INSTITUTION_ID)에서 (REQ_ID, ITEM_NO)로 바꾼다. 설계서 기준 066 몫이고 065·067에는 없어서 포함했다. oracle은 `DROP CONSTRAINT PK_IBT_REQ_ITEM` 뒤 `ADD CONSTRAINT`이고, mysql은 `DROP PRIMARY KEY, ADD PRIMARY KEY` 한 문장이다.
- COMMON_CODE에 `TARGET_AIM_RANK` / `OTHER` / '기타' / 정렬 5 / 사용 1 / `'2026-11-26T00:00:00+09:00'` 1행을 더했다. 두 파일의 INSERT 블록은 글자 그대로 같다.
- 백필 UPDATE는 없다. DEFAULT 'MAIN_BANK'가 기존 행을 채우고 나머지는 NULL이다. 설계서도 그렇게 정해 두었다.
- 헤더에는 적용 직전 `(REQ_ID, ITEM_NO)` 중복 조회(0줄 필수), 서버 정지 창에서 적용, oracle 문장별 커밋 위험, 되돌리기를 적었다. 되돌리기에는 `AIM_RANK_ETC` 칸 삭제와 `OTHER` 행 삭제(값이 든 행이 있는지 먼저 확인)가 들어 있다.
- 외래키는 없다.

**3. 메인이 실행할 것**
- `cd kgi-ggreport-web && mvn -q -o test`
  - 기대: 통과. 새 칸은 NULL 허용이거나 DEFAULT가 있다.
  - 063 쌍 시험은 063 파일만 본다. 설계서에 따르면 CommonCodeSchemaTest도 TARGET_AIM_RANK를 이미 제외하므로 영향이 없다.
  - **H2 위험**: H2가 PK 교체를 못 받으면 첫 실패가 스키마 로딩에서 난다(설계서가 예상한 것). 그러면 H2 호환 문장으로 바꿔야 하니 알려 달라.
  - `TargetChangeApiTest` 623행이 금고 방식 4개를 단언한다. 시험 DB에 OTHER가 들어가므로 5개가 되어 이 시험이 깨질 것이다. 설계서는 `assertEquals(5, …)`와 `get(4).path("name")`="기타" 추가를 지시한다. 이 시험은 이번 지시 목록에 없어 고치지 않았다. S2에서 고치거나 별도 지시를 달라.
- 로컬 MySQL 적용 순서는 사전 조회(PK 중복 0줄) 후 `node tools/db/apply-mysql.mjs --dry-run`으로 목록을 확인하고 적용한다. 번호 역전 때문에 대기 목록에 066이 들어 있어야 한다(4번 참고).

**4. apply-mysql의 번호 순서 역전 판단**
- `tools/db/apply-mysql.mjs`(`kgi-ggreport-web/` 안)는 번호 순서를 검사하지 않는다. 적용 여부는 기록표 SCHEMA_MIGRATION의 VERSION 유무로만 판정한다(`planMigrations`, 141-152행). 기록에 없는 파일은 pending이고 번호순으로 적용한다.
- 그래서 068이 이미 적용된 DB에서도 066은 pending으로 잡혀 그냥 실행된다. 'N번보다 뒤 번호가 있으면 막는' 로직은 없다.
- 이미 적용된 파일의 체크섬이 다르면 전체가 중단된다. 066은 기록이 없는 새 파일이라 영향이 없다.
- 066은 INST_BID_TARGET·REQ_ITEM·COMMON_CODE만 건드리고, 068에는 이 이름이 없다(grep 0건). 이 이력은 049/051 선례를 직접 확인하지 못했다. 코드 동작으로 보면 같은 결과다.
- 주의 두 가지:
  - 066은 한 번 적용한 뒤에는 고치면 체크섬 불일치로 중단되니 확정 전에 다듬어야 한다.
  - oracle은 DBA 수동 적용이라 번호 순서 규칙을 DBA에게 알려야 한다. 헤더에 '065 뒤 한 번만'이라고 적었고, 068 이후에 적용해도 의존성은 없다.

**5. 지시와 달리 판단한 것**
- 파일명은 설계서대로 `066_bid_target_case.sql`로 했다. 지시에 파일명이 따로 없었다.
- mysql 헤더에는 설계서 보완판 문구에 더해 기타 칸 요약 2줄을 넣었다. 되돌리기 줄은 설계서를 따랐다.
- 1802 설계서에는 067 헤더 문구 수정 지시(1737)가 있는데, 067은 6e 몫이며 이미 커밋된 파일이라 건드리지 않았다.

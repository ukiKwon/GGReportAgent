## 2. 원인 (근거 파일:줄)
- **`GET /workflow/overview`가 403인 이유**: `WorkflowController.java:27`의 `guard.require(req, "workflow")`가 메뉴 조회 권한을 봅니다. 그런데 `Menus.java:104-105`에서 디자이너 기본값은 `row("chat","knowledge","tasks","approvals")`로 workflow가 꺼져 있습니다. 시험 `WorkflowOverviewApiTest.java:79`도 디자이너 403을 기대합니다.
- **`GET /preps`가 403인 이유**: `PrepController.java:71`의 `requireActiveUser`는 통과합니다. 막는 곳은 `PrepService.java:124`의 `if (!isSales(me) && !isHead(me)) throw 403`입니다. 시험 `PrepApiTest.java:599`가 디자이너 403을 기대합니다.
- **메뉴 기본값을 바꾸면 안 되는 이유**: `Menus.java:113`에 "이 기본 격자는 골든 04·05·server/menus.py 와 같아야 한다"고 적혀 있습니다. 바꾸면 되돌리지 말아야 할 계약이 깨집니다. ROLE_MENUS 저장값으로 켜는 방법도 있지만, 그러면 '워크플로' 탭까지 디자이너에게 보입니다. 이번 결정은 현황판에서 보기만이므로 이 방법은 쓰지 않았습니다(메뉴는 별개 판단, 6절).
- **응답에서 민감할 수 있는 칸**:
  - `/preps`(`PrepService.java:134-145`): 기관명·상태·진척·담당자 **이름**·`can_view`·입찰예상일. 사번·과제 내용·확정자·사유·결재 의견은 원래 들어 있지 않습니다(`PrepApiTest.java:616-618`에서 확인).
  - `/workflow/overview`의 `assignees`(`WorkflowOverviewService.java:76-90, 115`): TASKS.ASSIGNEE 원문이라 **사번이 섞일 수 있습니다**. 시험 `WorkflowOverviewApiTest.java:160`이 실제로 사번을 담당자 칸에 넣습니다.
  - 현황판은 overview의 `assignees`를 쓰지 않습니다(kbboard.js에서 grep으로 확인). 이름 표시는 `/preps`의 `assignee_names`로 합니다(kbboard.js:287 `listRowModel`).
- **상세·이력은 이미 막혀 있습니다**: `canSee`(`PrepService.java:717-726`)는 영업 계열이 아니고 담당도 아니면 false를 줍니다. 그래서 디자이너의 상세·이력은 404로 남습니다(`PrepApiTest.java:583, 632, 856`). 목록의 `can_view`도 false로 나갑니다.

     * 메뉴 조회 권한 또는 정확히 {@code role} 인 활성 사용자면 통과(읽기 전용 화면을 메뉴와 따로 여는 용도).

     * ⚠️ X-Emp-No 자기신고 위의 업무 규칙이다 — 사칭 방지가 아니다. 역할 예외는 그 메뉴를 권한관리에서 꺼도 열린다.

    public boolean requireMenuOrRole(HttpServletRequest req, String menuKey, String role) {
        Actor actor = Actor.of(req);
        if (!actor.isKnown()) {
            deny(req, actor, 401, "no employee number");
            throw new ApiException(401, "로그인이 필요합니다.");
        }
        if (permissions.canView(actor.getEmpNo(), menuKey)) {
            return true;
        }
        SysUser u = users.selectByEmpNo(actor.getEmpNo());
        if (u != null && "ACTIVE".equals(u.getStatus())
                && role.equals(u.getRole() == null ? null : u.getRole().trim())) {
            return false;
        }
        deny(req, actor, 403, "no view permission: " + menuKey);
        throw new ApiException(403, "이 기능을 쓸 권한이 없습니다.");
    }

## 5. 보안·위험·되돌리는 법
- **403 경로**:
  - 사번 없으면 401, 미등록·잠김이면 403, 디자이너·workflow 권한자가 아니면 403입니다. 모두 기존과 같은 고정 문구·같은 사유 문자열의 DENIED로 접근 이력에 남습니다. 본문·쿼리값은 남기지 않습니다.
  - `/preps`의 서비스 403은 기존 `denyLogged`로 DENIED가 남습니다.
- **자기신고 인증의 한계**: `X-Emp-No`만 알면 누구나 디자이너 사번을 사칭해 목록을 읽을 수 있습니다. 이번 변경은 업무 규칙이지 보안 경계가 아닙니다(`MenuGuard.java:14`와 같은 한계).
- **위험 1**: 역할 예외라서 전산팀이 권한관리에서 디자이너의 workflow를 꺼도 overview가 열립니다. Javadoc에 적어 두었습니다. 끄는 수단이 필요하면 7절 질문 대상입니다.
- **위험 2**: `/preps`의 `assignee_names`(직원 이름)는 디자이너에게도 나갑니다. 현황판의 담당 표시가 이 값을 쓰고 사번은 없기 때문에 유지했습니다. overview의 `assignees`는 사번이 섞일 수 있고 현황판이 쓰지 않으므로 비웠습니다.
- **위험 3**: 디자이너 화면에서 [제안 확정] 같은 쓰기 버튼이 보일 수 있습니다(kbboard.js:942-943 `actionKind`). 눌러도 서버가 403을 줍니다. 화면 확인은 6절 프런트 이관입니다.
- **되돌리는 법**: 3-2를 `guard.require(req,"workflow")`, `overview(actor)`로 되돌리고, 3-4의 `&& !isDesigner(me)`를 빼고, 시험 2건을 403으로 되돌립니다. 3-1·3-3 메서드는 남겨도 해가 없습니다. DB 변경이 없어 데이터 되돌림은 필요 없습니다.

## 6. 이관 메모
- [이관: 프런트] 디자이너 계정에서 현황판의 [제안 확정]·행 열기 같은 쓰기·상세 동작이 숨겨지거나 비활성인지 확인해야 합니다. 서버 패치 적용을 기다립니다. 근거: kbboard.js:942-943, kbboard.js:828 `prepDenied403`(이제 403이 오지 않음), `can_view=false`.
- [이관: 기획] 사전준비(workflow) 메뉴 탭을 디자이너에게 보일지는 별개 결정입니다. 이번 패치는 메뉴를 바꾸지 않습니다. 켠다면 기본 격자가 아니라 ROLE_MENUS 저장값으로 해야 합니다(새 마이그레이션 번호 필요, 골든 보호). 근거: Menus.java:104-105, 113.
- [이관: 기획] 디자이너에게 담당자 이름(`assignee_names`)을 보여도 되는지 확인이 필요합니다. 현재는 보이는 안입니다. 빼려면 3-4에서 디자이너일 때 빈 목록을 주면 됩니다.

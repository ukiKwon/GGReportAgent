# 추가 패치안: 중-2 (사용자 결정 2026-11-10, 권장안)

이 보고는 직전 패치안(중-1, 하-1, 하-4·5)에 이어 붙는 추가분입니다. 직전 패치와 겹치는 파일의 `old → new`는 서로 독립이어서 둘 다 적용해도 충돌하지 않습니다. 서버·DB·테스트를 실행하지 못했으므로 미검증입니다.

## 1. 대상·방법·못 본 것
- 읽은 파일: `ApprovalRequestService.java`의 `list`/`cancel`/`view`, `ApprovalLineController.java`의 매핑. 매핑은 grep으로만 확인했습니다.
- `/approval-requests` 아래 GET은 `/types`, `""`(목록), `/my-perms`뿐입니다. **요청 단건을 조회하는 GET 경로는 없습니다.** 단건 규칙은 따로 만들 필요가 없습니다.
- 응답이 요청 내용을 돌려주는 곳은 세 군데이고, 모두 아래에서 막힙니다.
  - 목록(`list`): `box=all`만 고칩니다.
  - `decide`: 결재자만 통과합니다. ASSIGNEE_CHANGE는 ADMIN 단계가 없는 LINE 단계라 관리자는 `eligibility`에서 403입니다(`ApprovalRequestService.java:461-470`).
  - `cancel`: 이번에 관리자를 403으로 막습니다.
- 못 본 것: 프런트가 `box=all` 화면에서 이 유형을 어떻게 쓰는지는 보지 않았습니다.

## 2. 요구/원인 요약
- `list`의 `all`은 `canAdmin`이면 전 유형을 최근 200건까지 돌려줍니다(`:390-397`). `view()`가 ASSIGNEE_CHANGE의 `payload`(사유 포함)와 `people`(이름·직위)까지 싣습니다(`:584-587`).
- `cancel`은 상신자 또는 `canAdmin`이면 허용합니다(`:269`). `view`의 `can_cancel`도 같습니다(`:609-610`).
- 입찰 건 담당자 정보는 영업팀 전원만 열람하는 규칙(관리자·디자이너 403)과 어긋납니다.

## 3. 권장안: 가리지 않고 목록에서 제외
- **근거**: 내용 필드만 가리면 제목 `담당자 변경 — <입찰건ID>`, 상신자, 상태, 결재자 같은 메타가 남아 입찰 건이 배정·변경 중임이 드러납니다. 제외하면 노출이 0입니다.
- **영향**: 상신자와 결재자는 `mine`과 `inbox`로 계속 봅니다. 관리자의 전체 목록은 권한 신청 감사용이라 그 용도는 그대로 유지됩니다.
- **권한 신청(PERM_REQUEST)** 의 관리자 목록·취소는 변하지 않습니다.
- 취소는 신청자 본인만 가능합니다. `can_cancel`도 같은 규칙으로 맞춥니다.

## 4. 구현안 — `ApprovalRequestService.java`

(a) `list`의 `all`: 200건 상한을 걸기 전에 먼저 걸러 냅니다.
```java
// old
            rows = requests.selectAll();
            if (rows.size() > 200) {
                rows = rows.subList(0, 200);
            }
// new
            rows = new ArrayList<>();
            for (ApprovalRequest x : requests.selectAll()) {
                if (!ApprovalTypes.ASSIGNEE_CHANGE.equals(x.getReqType())) {   // 담당자 변경은 영업팀 내부 정보 — 관리자 전체 목록에서 제외(mine·inbox 는 유지)
                    rows.add(x);
                }
            }
            if (rows.size() > 200) {
                rows = rows.subList(0, 200);
            }
```
javadoc `all(관리자 전용, 최근 200건)`을 `all(관리자 전용, 담당자 변경 제외, 최근 200건)`으로 고칩니다.

(b) `cancel`: 담당자 변경은 신청자 본인만 취소할 수 있습니다. 상태 확인보다 앞이라 오류 순서는 기존과 같습니다.
```java
// old

            throw new ApiException(403, "상신자 본인 또는 관리자만 취소할 수 있습니다.");
        }
// new
        boolean own = r.getRequesterEmpNo().equals(me.getEmpNo());
        if (!own && ApprovalTypes.ASSIGNEE_CHANGE.equals(r.getReqType())) {
            throw new ApiException(403, "이 요청은 신청자 본인만 취소할 수 있습니다.");   // 관리자도 불가(영업팀 내부 정보)
        }
        if (!own && !permissions.canAdmin(me.getEmpNo())) {
            throw new ApiException(403, "상신자 본인 또는 관리자만 취소할 수 있습니다.");
        }
```

(c) `view`의 `can_cancel`: 화면 단추가 서버 규칙과 어긋나지 않게 맞춥니다.
```java

    private boolean inBox(String box, String emp, long id) throws Exception {
        MvcResult r = mockMvc.perform(as(get("/approval-requests").param("box", box), emp)).andReturn();
```

## 7. 보안 메모·한계
- `cancel`은 존재하지 않는 요청 id는 404, 타인의 요청은 403으로 구분합니다. 이는 기존부터 있던 동작이며, 요청 id는 순번이라 추측이 가능합니다. 이번 범위 밖입니다.

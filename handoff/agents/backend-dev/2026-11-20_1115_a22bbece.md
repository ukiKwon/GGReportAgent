### 1-4. 헬퍼 `isOutage` 추가 (P3-2)
`notifyBatch` 바로 위에 넣는다.
```java
    /**
     * DB 연결·트랜잭션 장애인가 — 예외 자신과 원인 체인(최대 8단계)에 DataAccessResourceFailureException(CannotGetJdbcConnectionException 포함)·TransactionException·
     * SQLTransientConnectionException·SQLNonTransientConnectionException·SQLRecoverableException(MySQL 통신 장애) 중 하나가 있으면 true.
     * MyBatisSystemException·UncategorizedSQLException 은 그 자체로는 장애가 아니고 원인이 위 종류일 때만 장애다(SQL 문법·제약 오류와 구분).
     */
    static boolean isOutage(Throwable e) {
        Throwable t = e;
        for (int i = 0; t != null && i < 8; i++, t = t.getCause()) {
            if (t instanceof DataAccessResourceFailureException || t instanceof TransactionException
                    || t instanceof SQLTransientConnectionException || t instanceof SQLNonTransientConnectionException
                    || t instanceof SQLRecoverableException) {
                return true;
            }
            if (t.getCause() == t) break;
        }
        return false;
    }
```
- `CannotGetJdbcConnectionException`은 `DataAccessResourceFailureException`의 하위 클래스라 따로 쓰지 않는다. 쓰면 오히려 중복이 된다. 만약 쓰는 Spring 버전에서 하위 관계가 아니라면 `|| t instanceof org.springframework.jdbc.CannotGetJdbcConnectionException`을 한 줄 더 넣는다.
- 위험: `SQLRecoverableException`을 넣은 것은 내가 더한 판단이다. MySQL 연결 라이브러리의 통신 장애 예외가 그 계열이라서다. 지나치게 넓다고 보면 지워도 시험(아래)은 통과한다.

- `doThrow` import는 쓰지 않으니 컴파일 경고만 난다. 빼도 된다.
- 알려진 가정 3개
  - `mapper.insertReq`는 `int` 반환이라 `.thenReturn(1)` 뒤에 `.thenThrow(...)`를 붙였다.

- 기관당 독립 트랜잭션 자체(2번째에서 일반 오류 → 1·3번째 커밋)는 모의 관리자로는 커밋을 증명하지 못한다. 위 `한_기관에서_일반_오류…` 시험은 "나머지 기관을 계속 처리한다"까지만 확인한다. 실제 커밋 독립성은 `PlanCollectTxTest`(비트랜잭션 실DB)에 같은 시나리오를 더해야 한다. 이번에는 제안만 하고 패치는 만들지 않았다(그 시험의 헬퍼를 읽지 못했다).

### 2-3. 제안만 (main 적용) — `BoardWriteLimitFilterTest`의 batch 413
이 파일은 main 공유라 적용하지 않는다. 기존 `plan-collect/export.csv` 413 시험이 있으면 같은 방식으로 복제하라는 제안이다(그 시험을 열어 보지 못했다).

## 4. 보안·위험
- **중단 시 쪽지 시도**: 장애로 중단하면서 `notifyBatch`를 부르므로, DB가 죽은 상태라면 쪽지 쪽도 실패하고 `WARN` 로그(고정 코드·건수·예외 종류만)가 한 줄 남는다. 쪽지 실패가 원래 장애를 덮지 않는 것은 시험으로 못 박았다.
- **`isOutage`가 넓어질 위험**: `SQLRecoverableException`까지 장애로 보면 일시적 통신 오류 한 번에도 일괄이 중단된다. 이미 커밋된 건은 유지되고 응답은 500이라, 사용자가 현황을 다시 읽고 재시도하게 된다.
- **좁아질 위험**: 원인 체인이 8단계를 넘거나 위 종류가 아닌 장애 형태(예: Oracle의 `SQLRecoverableException` 외 오류코드)는 일반 `error`로 처리되고 루프가 계속된다. 그래도 일괄 한도가 50곳이라 피해는 최대 감사 ERROR 50행이다.
- **자기신고 한계**: 사번은 `X-Emp-No` 자기신고다. 이 변경은 권한을 건드리지 않는다.
- **되돌리기**: `Requested`의 `label` 필드와 `isOutage`, 루프의 catch 구조를 앞 보고의 버전으로 되돌리면 된다. DB·응답 모양은 바뀌지 않는다.

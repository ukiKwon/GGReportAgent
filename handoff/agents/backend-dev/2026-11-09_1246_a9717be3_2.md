## backend-dev-write 보고: DB 마이그레이션·테스트 적용 완료 (경로 A)
서버 Java 코드(Mapper·Service)는 건드리지 않았습니다. 빌드·테스트·DB 실행은 못 했습니다.

### 바꾼 파일 (모두 C:\github\GGReportAgent\kgi-ggreport-web\ 아래)
**① FK 18개 제거 (oracle·mysql 쌍, 제자리 수정)**
- src/main/resources/db/{oracle,mysql}/001_schema.sql
  - FK 4개를 지우고 쉼표를 정리했고, 헤더에 FK 부재 안내를 넣었습니다. Oracle 인덱스 주석은 "조회용"으로 바꿨습니다.
  - MySQL 001에는 KEY IDX_BID_CASES_INST와 KEY IDX_MESSAGES_TASK를 CREATE TABLE 안에 추가했습니다. 3절 인덱스 주석도 갱신했습니다.

- 008_system_admin.sql: FK 1개 제거.
- 010_approval_line.sql: FK 1개 제거. Oracle은 ALTER 줄을, MySQL은 ADD CONSTRAINT 줄을 삭제했습니다.
- 012_approval_workflow.sql: FK 4개 제거.
- 014_board_form.sql: FK 6개 제거. Oracle은 헤더에 참조 목록을 넣고 CREATED_BY·UPDATED_BY에 주석을 달았습니다.
- 확인: 새 파일을 쓰기 전에 돌린 grep에서 db/**/*.sql의 FOREIGN KEY·REFERENCES는 0건이었습니다. 이후에 만든 MySQL 015는 FK 이름 문자열 때문에 FOREIGN KEY가 들어 있습니다(DdlRulesTest 제외 대상). 이 점은 새 파일 작성 뒤 grep으로 다시 확인하지 못했습니다.

**② ~ ⑥ 신규 SQL**
- db/mysql/015_drop_foreign_keys.sql: 프로시저 P_DROP_FK로 18번 호출합니다. 멱등이고, 조회용 인덱스 2개는 이름을 바꿉니다.

### 메인이 실행할 명령
1. `cd kgi-ggreport-web && mvn -q -o test`
   - 기대 결과는 기존 380건과 새 테스트 약 15건이 모두 통과하는 것입니다.
   - 8080 서버가 같은 target/을 쓰면 테스트 뒤에 재기동합니다.
   - 기존 테스트는 FK에 기대지 않고, OrchestratorCoreTest가 쓰는 UNIQUE는 유지되므로 깨질 것으로 보지 않습니다.
2. 로컬 MySQL(ggreportdb)에는 한 세션만 쓰는 조건으로 번호 순서대로 한 번씩 적용합니다. 015는 DELIMITER를 쓰므로 mysql CLI로 실행해야 합니다.
   ```
   mysql -u root -p ggreportdb < src/main/resources/db/mysql/015_drop_foreign_keys.sql
   mysql -u root -p ggreportdb < src/main/resources/db/mysql/016_common_code.sql
   mysql -u root -p ggreportdb < src/main/resources/db/mysql/017_seed_common_codes.sql
   mysql -u root -p ggreportdb < src/main/resources/db/mysql/018_notice_followup.sql
   ```
3. 015 적용 뒤 확인합니다.
   - `SELECT TABLE_NAME, CONSTRAINT_NAME FROM information_schema.TABLE_CONSTRAINTS WHERE TABLE_SCHEMA='ggreportdb' AND CONSTRAINT_TYPE='FOREIGN KEY';`는 0행이어야 합니다.
   - `SHOW INDEX FROM BID_CASES`, `SHOW INDEX FROM MESSAGES`에 IDX_BID_CASES_INST·IDX_MESSAGES_TASK가 있어야 합니다.
   - MySQL 버전이 8.0 이상인지도 확인해 주세요(RENAME INDEX 때문입니다).
4. 016~018 적용 뒤 mysql/ops/integrity_check.sql을 한 번 돌려 전부 0행인지 봅니다.

### 지시에서 벗어난 판단
- Q6 UNION의 키 칼럼은 숫자 키도 문자로 맞췄습니다(Oracle은 TO_CHAR(r.REQ_ID)로, 보고서 원문에서 빠져 있던 REQ_ID 쪽에도 변환을 넣었습니다). 집계 칼럼에는 AS N을 붙였습니다.
- Oracle 017 끝에 COMMIT;을 넣었습니다(SQL*Plus용). H2 init에서는 무해합니다. MySQL 017에는 넣지 않았습니다.
- 017은 일반 INSERT라 멱등하지 않습니다(보고서와 같습니다). test properties에 "컨텍스트가 하나로 캐시되는 전제" 주석을 달았습니다.
- 018 Oracle 인라인 주석에서 따옴표를 풀어 썼습니다(스크립트 분할기의 따옴표 상태 추적 위험 회피).
- 다음 파일에도 짧은 헤더 안내를 넣었습니다. 모두 주석이라 동작에는 영향이 없습니다.
  - Oracle 008·010·012
  - MySQL 001·006·008·010·012·014
- README "담긴 것" 표는 제목("11 테이블")을 그대로 두고 행만 추가했습니다. 제목과 현재 테이블 수가 맞지 않는 기존 문제는 건드리지 않았습니다.

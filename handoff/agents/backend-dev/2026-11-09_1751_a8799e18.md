**3. 사전 확인 결과**
- ① ROLE_MENUS 저장값
  - mysql과 oracle `db/**`에는 ROLE_MENUS를 채우는 INSERT가 없다. 테이블 정의(001)와 `RoleMenuMapper.xml`뿐이다. 그래서 시드와 마이그레이션은 필요 없고 새 SQL도 추가하지 않았다.
  - 다만 운영·로컬 DB에 사용자가 권한관리 화면에서 저장한 행이 있으면 그 값이 기본값을 이긴다. 그런 역할은 결재함이 계속 꺼져 있을 수 있다.
  - 로컬 DB는 메인이 `SELECT ROLE, MENU, ENABLED FROM ROLE_MENUS WHERE MENU='approvals' AND ENABLED=0`으로 확인하면 된다.
  - 행이 있으면 권한관리 화면에서 켜도록 안내한다. 필요하면 DB 담당이 `UPDATE ROLE_MENUS SET ENABLED=1 WHERE MENU='approvals'`를 실행하되, 반드시 먼저 확인하고 실행한다. 나는 DB를 건드리지 않았다.
- ② 개인 결재 권한(내 권한 신청)과 메뉴 노출
  - `/menus`는 역할 기본값에 ROLE_MENUS 저장값을 얹은 결과만 준다. 개인 권한(`USER_MENU_PERMS`)은 `/menus` 응답에 들어가지 않는다.
  - 개인 권한은 `PermissionService.effective()`와 `GET /approvals/me`류의 `myPerms().menus`에만 반영된다. 그중 `can_approve`는 approvals 메뉴의 approve 값이다.
  - 따라서 이번 변경 뒤에는 개인 권한으로 결재함 노출이 바뀌지 않는다. 노출은 전원 켜짐이고, 개인 권한은 승인 여부와 안내 문구를 고르는 데만 쓰인다.
  - 개인 예외로 view를 false로 저장하면 `effective()`는 꺼짐이 되지만 `/menus`는 그대로다. 화면이 어느 쪽을 쓰는지는 frontend에서 확인해야 한다.
- ③ 결재 화면 서버 API
  - **`GET /approvals?role=`(제안서 작업물 결재함)**: 권한 검사가 없고 403도 없다. 팀장·영업부장이 아니면 `queueFor`가 빈 목록을 주고 `gatesFor`도 영업부장 외에는 비어 있다. 그래서 일반 팀원은 빈 응답(200)을 받는다.
    - 이 API는 role 파라미터를 그대로 믿는 자기신고 방식이라, 팀장 역할을 대고 부르면 카드가 보인다.
  - **`GET /approval-requests?box=mine`(내가 올린 요청)**: 403 없이 호출자 본인의 상신 목록(`requester` 기준)만 준다.
    - `inbox`는 호출자가 결재 자격(`eligibility`)을 가진 건만 주고, 자격이 없으면 빈 목록이다.
    - `all`만 관리자 권한(`canAdmin`) 없으면 403이다. 화면이 mine과 inbox만 부르면 문제없다.
  - **승인**: `decide()`가 `eligibility()`로 결재자 또는 유효한 대결자인지, 직급, 본인 요청이 아닌지를 검사하고, 아니면 403을 준다. 권한 없는 사람은 남의 결재를 승인할 수 없다.
    - 메뉴 노출을 전원에게 열어도 서버 승인 경로는 열리지 않는다.
    - 단 `/tasks/{id}/approve` 쪽 검사는 이번에 읽지 않았다. 기존 동작 그대로라고만 알고 있다.

## 2. 요구/원인 요약
- 칸 key는 `r{행}c{그 행에서 보이는 셀 순번}`이다(`BoardDocSpec.java:203-206`). 순번은 병합으로 가려진 칸을 건너뛰므로 같은 열이 행마다 다른 번호를 받는다. 예: 표 A의 제공금액은 1행에서 `r1c2`, 2행에서 `r2c1`이다. 행이나 열을 넣거나 빼면 아래가 모두 틀어진다.
  - 저장 문구: `BoardFormJson.java:35-43`
  - `excel-map.json`의 `lines.row`/`cells` 순서/`derive_sum.of`("r1c2"…)
  - `BoardExcelMap.java:437,443`
  - 작성 모드 값 key
- 구조는 저장하지 않고 항상 카탈로그에서 만든다(`build`, `BoardDocSpec.java:260-309`). 그래서 행/열을 저장할 자리가 없다.
- 값 칸(mapped)은 `editableKeys`에서 빠져 편집이 거부된다(`:209-220, :282`).
- docx 열 너비는 표 id별 고정 비율이고 열 수가 다르면 균등분배로 떨어진다(`BoardDocDocx.java:109-123`).
- 저장 요청 본문은 크기 제한이 없다. `BoardWriteLimitFilter`는 POST excel/draft-docx만 본다(`:35-36, :58-66`).

## 3. 구현안 (권장안 하나)

### 3.0 핵심 결정 요약
1. 행/열에 안정 id를 붙이고, 칸 key를 `r{행id번호}_c{열id번호}`로 바꾼다. 예: `r2_c2`.
   - key는 칸의 앵커(병합 칸의 좌상단) 행 id와 열 id의 쌍이다. 위치 순번에는 의존하지 않는다.
   - 밑줄 `_`을 넣어 옛 `r1c2`와 모양을 다르게 했다. 낡은 화면이 보낸 옛 key는 조용히 엉뚱한 칸에 적용되지 않고 400으로 거부된다.
2. 양식은 표 구조(열 id 목록, 행 id와 행별 앵커 칸)를 자기 JSON에 담는다(저장 포맷 `fmt:2`).
   - 카탈로그는 새 표를 고르는 원본과 "어느 칸이 엑셀 연결인가"의 기준으로만 남는다.
   - 엑셀 연결 여부는 저장하지 않고 `(표 ref, 행 id, 열 id)`를 카탈로그와 대조해 매번 계산한다.
3. PUT은 표 구조 전체를 보낸다(현재의 "전체 교체"와 같은 방식). 서버는 검증만 한다. 행/열 삽입·삭제 때 병합 범위를 어떻게 고치는지는 §3.2 규칙이고, 화면이 이를 수행한다. 서버는 `layout()` 검증으로 틀린 병합을 막는다.
4. `CATALOG_VER`는 이번에 올리지 않는다. 대신 저장 포맷 상수 `FORM_FMT=2`를 새로 둔다(§3.1).
5. 엑셀 연결이 끊기는 저장은 `confirm_unmapped:true` 없이는 400(`UNMAP_CONFIRM_REQUIRED`)이다. 엑셀 채우기는 연결이 살아 있는 칸만 처리하고, 없는 칸은 건너뛰며 건수를 알린다.
6. 표 A 합계: 서버는 값을 자동으로 덮어쓰거나 보정하지 않는다. 다만 합계 범위 안에 사용자가 추가한 입력 칸이 있으면 `sums.of`에 포함하고 합계 칸에 경고를 단다. 프런트의 합계 재검산이 그 칸들을 합산해 차이를 경고한다.
7. DB 스크립트는 없다. `SPEC_JSON`은 LONGTEXT/CLOB이고, 옛 버전은 읽을 때 변환한다(불변 행을 고치지 않음).

### 3.1 ① 안정 id, 키 이행, CATALOG_VER 이중 올림 방지
- id 규칙
  - 행 id `r{N}`, 열 id `c{N}`(정규식 `[rc][0-9]{1,4}`).
  - 카탈로그가 가진 id는 N<100이다. 기본 id는 기존 위치다(행은 원래 행 번호, 열은 원래 격자 열 번호).
  - 사용자가 만든 행/열은 N≥100을 받는다. 표마다 `next_r`/`next_c` 카운터를 저장하고 단조 증가시킨다. 지운 id는 재사용하지 않는다(지운 행의 엑셀 연결이 새 행에 붙는 것을 막기 위해).
  - 이후 카탈로그에 열이나 행을 더할 때(NEXT 37 S5의 C-3 '사업초기' 열, C-5)는 명시 id를 쓴다(예: `c6`, 기존 id 재사용 금지). 구현은 Table 두 번째 생성자(id 목록을 받음)다.
- 칸 key 예시(카탈로그, 표 A)
  - 1행: 기관명 `r1_c0`, 출연금 `r1_c1`, 제공금액 `r1_c2`, 비고 `r1_c3`
  - 2행: 예비비 `r2_c1`, 값 `r2_c2` / 3행: 같은 모양 / 4행: 합계값 `r4_c2`
  - 옛 `r2c1`은 값 칸이었고 새 `r2_c1`은 라벨 칸이다. 그래서 옛 key를 새 key로 착각하지 않도록 모양을 바꿨다.
- 저장 JSON `fmt:2`(옛 포맷은 `fmt` 없음 + `tables[].cells` 맵)
```json
{"catalog_ver":1,"fmt":2,"tables":[{"ref":"A","title":"…","next_r":100,"next_c":100,
 "cols":["c0","c1","c2","c3"],
 "rows":[{"id":"r0","cells":[{"c":"c0","t":"기관명","h":true,"a":"center"},{"c":"c1","t":"구분","h":true,"a":"center"}]},
         {"id":"r1","cells":[{"c":"c0","t":"…","rs":4,"i":true,"a":"center"}]}]}]}
```
  - 생략 가능한 값: `cs`/`rs`(기본 1), `h`(머리글), `i`(입력 칸), `a`(기본 left).
  - 가려진 격자 칸은 저장하지 않는다. 현재 화면 JSON 규칙과 같다.
- 마이그레이션(DB 변경 없음)
  - `BoardFormJson.parse`가 `fmt` 없는 JSON을 만나면 `TableEdit.legacy()` 표시를 달고, 서버가 카탈로그 구조 위에 옛 `r{행}c{순번}` key를 새 key로 번역해 문구를 얹는다(`legacyKeyToKey`). 번역은 결정적이므로 같은 옛 버전은 항상 같은 Doc이 된다. 결재 건이 참조하는 불변 버전도 안전하다.
  - 다음 저장부터 `fmt:2`로 쓴다. 저장하려는 내용이 현재 버전을 새 포맷으로 직렬화한 것과 같으면 새 버전을 만들지 않는다(§3.4 `changed:false`).
  - `excel-map.json`은 수정하지 않는다. `BoardExcelMap`이 `lines`의 위치 순서를 카탈로그의 새 key로, `derive_sum.of`의 옛 key를 `resolveKey`로 번역한다. `mapping_ver` 1(`blocks`) 분기도 같은 번역을 3곳에서 거친다(§3.5 패치).
- CATALOG_VER(권장: 올리지 않음)
  - 카탈로그의 표, 열, 연결 칸 집합은 이번에 변하지 않는다. 바뀌는 것은 저장 포맷과 key 모양이므로, 그 신호는 새 상수 `FORM_FMT=2`가 맡는다.
  - 그러면 NEXT 37 S5(C-3 사업초기 열, C-5)가 `CATALOG_VER`를 1→2로 한 번만 올린다. 이중 올림은 생기지 않는다.
  - S5가 먼저 나가도 충돌이 없다. 새 열 id만 명시하면 되고, 이미 만든 양식은 `catalog_outdated:true`로 "기본 양식에 새 열이 생김"을 알린다.
  - `BoardExcelMap`은 `catalog_ver` 일치 검사를 그대로 유지한다.
- 롤백 안전장치(PR-1 한정, PR-2에서 삭제): `fmt:2` JSON에 옛 `cells` 맵(카탈로그 모양일 때)도 같이 쓴다. PR-1을 되돌려도 옛 코드가 사용자 문구를 읽을 수 있다. 옛 코드는 `fmt`/`rows`를 무시하고 `cells`만 읽는다.

### 3.2 ② 병합(gridSpan/vMerge) 규칙
- 모델은 지금과 같다. 행마다 앵커 칸만 두고 가려진 칸은 생략한다(`BoardDocSpec`의 layout 규칙). docx의 gridSpan/vMerge 출력(`BoardDocDocx.java:138-239`)은 그대로 쓴다.
- 서버 검증: `layoutOf()`가 겹침, 범위 초과, 미채움을 거부한다. 그 위에 "각 칸이 선언한 `col`의 격자 위치 = layout이 계산한 시작 위치"인지도 검사한다. 즉 칸을 열 순서대로 보내야 한다.
- 화면이 지킬 규칙(서버 테스트에도 같은 사례로 박는다. 서버 참조 구현은 `BoardGrid`가 아니라 테스트 전용 헬퍼로 충분하다.)
  - 행 삽입(경계 p, 행 p-1과 p 사이): 경계를 가로지르는 rowspan 칸은 rowspan+1 하고 새 행에는 그 칸 자리에 칸을 두지 않는다. 나머지 격자 칸은 폭 1짜리 새 칸을 둔다. 서식은 템플릿 행(바로 위 행. 위 행이 전부 머리글이면 바로 아래 행)을 따른다. 입력 칸이던 자리는 `input:true` 빈 문구, 라벨 자리는 빈 라벨로 둔다.
  - 행 삭제 r: 앵커가 r이고 rowspan>1인 칸은 r+1의 같은 열로 앵커를 옮기고 rowspan-1 한다. 이때 key가 바뀌므로 엑셀 연결은 끊긴다(드문 경우). 위에서 r을 가로지르는 칸은 rowspan-1 한다. rowspan=1인 칸은 삭제한다. 마지막 1행은 못 지운다.
  - 열 삽입, 열 삭제: 위와 대칭이다(colspan). 마지막 1열은 못 지운다.
  - 병합과 해제: `colspan`/`rowspan` 조정이다. 병합으로 가려지는 칸은 목록에서 빼고, 해제하면 가려졌던 자리에 기존 id 쌍으로 칸을 되살린다. 칸 key는 `(앵커 행 id, 앵커 열 id)`이므로 병합과 해제는 id를 새로 받지 않고 key가 예측 가능하다. 해제로 되살린 칸의 key는 병합 전에 쓰던 key와 같다.
  - 구분 헤더 2열 쪼개기(예: 표 A): 열 삽입으로 새 열을 만들고(임시 id `n1`), 머리글 행의 '구분'을 `colspan:2`로 하고, 아래 행들은 라벨 칸을 새 열에 하나씩 둔다. 표 B의 '구분'이 이미 같은 모양이다. 이 흐름은 별도 서버 기능 없이 서버 검증만으로 성립한다.
- 병합 칸이 연결 칸이면 앵커 id 쌍이 같은 한 연결이 유지된다.

### 3.3 ③ 연결된 행/열 삭제·이동
- 이동: id가 안정이므로 행 순서를 바꿔도 연결은 유지된다(순서 변경 UI는 이번 요구에 없고, 서버는 PUT 순서대로 받는다). 합계 범위(§3.4)는 순서에 영향을 받는다.
- 삭제: 연결(mapped)된 칸이 사라지면 저장은 `confirm_unmapped:true`가 있어야 한다. 없으면 400으로 거부하고 어떤 칸이 끊기는지 알려 준다. 허용 후에는 그 칸을 건너뛰고 경고한다.
  - 판정: 직전 현재 버전에서 `mapped`였던 `(ref, key)` 중 새 구조에서 `mapped`가 아닌 것. 표 전체를 삭제하는 경우는 지금과 같이 확인을 요구하지 않는다(`droppedMappings`는 양쪽에 있는 표만 비교).
  - 오류 응답 예: `400 {"detail":{"code":"UNMAP_CONFIRM_REQUIRED","message":"엑셀과 연결된 칸 2개가 끊어집니다. 확인한 뒤 다시 저장해 주세요.","count":2,"dropped":[{"ref":"A","key":"r2_c2"}]}}`. `dropped`는 최대 50개이고 내부 정보는 싣지 않는다.
  - 저장 성공 응답에 `dropped_mapped`(건수)를 싣는다.
- 엑셀 채우기(`BoardExcelFill`/`BoardExcelNamedFill`): 양식에 연결 칸으로 남아 있는 key만 평가한다. 없는 key는 건너뛰고 표 응답에 `unlinked_count`를 싣는다. `summary.total`에도 세지 않는다. 표 단위 경고는 새로 만들지 않는다.

### 3.4 ④ 표 A 합계
- 서버가 입력 칸 값을 자동 합산하지 않는다. 2026-10-30 확정 규칙("합계 불일치는 경고만, 자동 보정 금지")과 같다. 그리고 새 행의 값은 엑셀에 없고 사용자가 채우는 시점이 다르다.
- 엑셀 채우기의 `derive_sum`: `of` 중 양식에 남은 key만 합산한다. 하나도 안 남으면 `manual`(`MANUAL_INPUT`)로 처리한다.
- 합계 범위 확장 규칙: 합계 칸 T(행 Rt, 열 g)의 `sums.of`에, 남아 있는 `of` 중 가장 위 행부터 Rt 바로 위 행까지 사이의 같은 열(g)에 앵커된 입력 칸(`input`이고 `mapped`가 아님, 머리글 아님, `colspan=1`)을 더한다.
  - 합계 아래나 맨 위에 추가한 행은 범위 밖이다.
  - 추가 칸이 있으면 T에 경고 `SUM_HAS_MANUAL_PARTS`를 달고 `filled`였다면 `review`로 낮춘다.
  - 프런트는 이 경고를 새 코드로 알아야 한다(§6). `sums`는 이미 작성 모드의 재검산 입력이다.
- 구현은 `manualPartsInSum`(§3.5 패치).

### 3.5 파일별 패치 (old → new, 요지)

**(a) `BoardDocSpec.java`** — 모델·검증·id·병합 검증. 핵심 추가분은 아래 그대로다.

    this.rowIds=Collections.unmodifiableList(rowIds==null?seqIds("r",rows.size()):new ArrayList<>(rowIds));
    this.colIds=Collections.unmodifiableList(colIds==null?seqIds("c",columns):new ArrayList<>(colIds));
    if(this.rowIds.size()!=rows.size()||this.colIds.size()!=columns) throw new IllegalStateException("table "+id+" ids");
    int[][] st=layoutOf(id,columns,rows);                       // 병합 규칙 위반이면 만들 때 실패
    List<List<Cell>> keyed=new ArrayList<>();

            kr.add(rows.get(r).get(i).withKey(cellKey(this.rowIds.get(r),this.colIds.get(st[r][i]))));

}

private static Doc assemble(String id,String name,List<TableEdit> edits,Doc base,boolean restoring){

        Table prev=base==null?null:base.table(cat.getId());

static int[] gridWidths(BoardDocSpec.Table t){
    int cols=t.getColumns(); double[] p=catalogPct(t.getId()); double[] w=new double[cols]; double sum=0; boolean pristine=p!=null&&p.length==cols;
    for(int c=0;c<cols;c++){

        w[c]=Math.max(5.0, p!=null&&k>=0&&k<p.length?p[k]:12.0); sum+=w[c]; }
    double denom=pristine?100.0:sum;           // 안 건드린 표는 지금과 똑같은 너비(합이 99.9인 표 B 포함), 고친 표는 합계 100% 로 정규화
    int[] out=new int[cols]; int used=0;
    for(int c=0;c<cols-1;c++){ out[c]=(int)Math.round(BODY_W*w[c]/denom); used+=out[c]; }
    out[cols-1]=BODY_W-used; return out; }
// fill(): int[] gw = gridWidths(t.getId(), cols);  →  int[] gw = gridWidths(t);

- 입력 검증: 제어문자(줄바꿈·탭 포함), 짝 없는 서로게이트, U+FFFE/FFFF 거부는 기존 `clean`을 그대로 쓴다. `align` 화이트리스트, 병합 범위 1..열/행 수, `header`와 `input` 동시 true는 거부, 같은 열 id/행 id 거부, 기존 id는 현재 버전에 있는 것만 인정(없던 `r1` 등을 만들어 연결을 위조하지 못함), 새 열은 서버가 번호 부여.
- DoS: 큰 격자 배열을 만들기 전에 행·열·칸 수 상한을 먼저 확인한다(40×12는 어차피 작다). 본문은 필터가 컨테이너 파싱 전에 차단한다. 저장은 낙관적 락 `base_version`이라 폭주해도 버전 행만 쌓이므로 새 쓰기 지점이 없다. 같은 요청의 반복은 `changed:false`로 버전이 안 늘어난다.
- 오류 메시지는 고정 문구뿐이다. 사용자 입력이나 id를 되돌려 싣지 않는다.
- XSS: 서버는 문구를 일반 텍스트로만 저장한다. docx는 `XWPFRun.setText`(필드 코드·하이퍼링크 아님, `withValues` 보안 메모 유지). 화면은 `textContent`로 그려야 한다(이관: 프런트). `<`/`>` 자체는 지금과 같이 허용한다.
- 권한: PUT/copy/archive/restore는 컨트롤러의 `requireEdit`(tasks 수정, `BoardFormController.java:100,107,113,119`)를 그대로 지난다. 권한 없음 403, 남의 팀 양식 404(존재 은닉), 오래된 `base_version` 409, 보관된 양식 400은 변경 없음. 새 권한 경로를 만들지 않는다. 접근 이력은 본문·쿼리를 담지 않는다. 필터가 거부하면 크기와 코드만 남긴다(기존 방식).
- 자기신고 한계: 인증은 `X-Emp-No` 자기신고이므로 수정 권한과 팀 범위 판정도 위조된 사번에 속는다. 이번 변경은 이 한계를 바꾸지 않으며 "검증된 사용자" 같은 표현을 쓰지 않는다. 구조 편집은 양식을 훼손할 수 있어 영향이 커지므로 버전이 불변으로 남는 점(복구 가능)이 완화책이다.
- 결재 건: 상신 시점 버전은 불변이고, 옛 버전은 읽을 때 번역되므로 보존된다.

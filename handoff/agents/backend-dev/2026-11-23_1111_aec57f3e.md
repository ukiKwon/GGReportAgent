## 디자이너 샘플 작업 1건 만들기 — 절차 (파일·DB 미접촉, 읽기만 함)

### 1. 대상·방법·못 본 것
- 대상은 로컬 MySQL의 TASKS, BID_CASES, BID_ASSIGNMENT 흐름이다. 코드와 DDL만 읽었다.
- 못 본 것: 로컬 DB의 현재 데이터(노원 건이 이미 있는지), `config/application.properties`의 `ggreport.legacy-flow.open` 값, NOTIFICATIONS 표의 TASK_ID 칸 이름.
- `ggreport.legacy-flow.open`은 저장소의 어떤 properties에도 없다. 기본값은 true다(LegacyFlowSwitch.java:24). 로컬이 true인지는 확인이 필요하다.

### 2. 결론과 근거
**API만으로는 만들 수 없고, 만들어도 과하게 길다. 디자이너 작업 자체를 API로 만드는 길은 있지만, 그 앞단(건과 3팀 작업)이 길다. 그래서 실제 흐름과 같은 SQL(서버 테스트가 쓰는 방식)을 1순위로 권한다. 사유는 아래와 같다.**

- 디자이너 작업을 만드는 API는 `POST /bidcases/{bid}/design-task`다(DesignReviewController.java:52).
  - 디자이너 역할만 호출할 수 있다(DesignReviewService.java:290).
  - 그 건에 BID_ASSIGNMENT 행이 1개 이상 있어야 한다(같은 파일 :293).
  - 영업·전산·예산 3팀이 모두 `2차완료`여야 한다(:304, pendingTeams는 :736).
  - 새로 만들면 201, 이미 있으면 200이다. 만든 작업의 ASSIGNEE는 비어 있다(`tasks.insert(id,bid,team)`, TaskMapper.xml:246).
- 담당은 첫 업로드·임시저장·제출 때 선점된다(`claimKey`, :210-213). 이름이 유일하면 이름 "최디자이너"가 들어가고, 아니면 사번이 들어간다.
  - "담당 = 7130526"으로 못 박으려면 SQL로 넣거나, open 뒤에 UPDATE를 해야 한다.
  - ASSIGNEE가 사번이어도 본인으로 인정된다(:191).
- 3팀 작업을 2차완료로 만드는 API 흐름은 이렇다.
  - 건 생성: `POST /bidcases` `{"institution_id":"nowon"}` (BidCaseController.java:97). 레거시 흐름이 열려 있으면 인증 없이 되고, 닫혀 있으면 관리자만 된다(:100-108).
  - 참여 결정 3단(영업팀 → 영업팀장 → 영업부장): `POST /bidcases/{id}/participation-decisions`. 3단째에 `createTasksForBidCase`가 3팀 작업을 만든다(BidCaseCommandService.java:253). 레거시가 닫혀 있으면 410이라 쓸 수 없다(BidCaseController.java:129-133). 그 경우 "제안 확정"(Prep) 흐름을 써야 한다.
  - 각 팀 작업은 담당 선점(`PATCH /tasks/{id}/draft`) → 제출 `POST /tasks/{id}/submit`(담당 본인만, TaskCommandService.java:93) → 그 팀 팀장의 `POST /tasks/{id}/approve`(:149-152)를 거친다. 3팀이면 9번 호출이다.
  - 팀장이 담당인 팀 작업은 1차 결재를 영업부장이 한다(:146-150). 시드 팀원 사번을 담당으로 쓰면 이 경우를 피한다.
  - 건 생성부터 합치면 15번 안팎이고, 알림 쪽지와 "분석 시작 못 함" 쪽지가 부수로 생긴다(BidCaseCommandService.java:292).
- SQL로 만드는 방식은 서버 테스트가 그대로 쓴다(DesignReviewApiTest.java:68-86, DocCheckApiTest.java:57-61).
  - BID_CASES에 `(BID_CASE_ID, INSTITUTION_ID)`를 넣고, TASKS에 `(TASK_ID, BID_CASE_ID, TEAM, STATUS, ASSIGNEE)`를 넣고, BID_ASSIGNMENT를 넣는다.
  - FK는 없다(015_drop_foreign_keys). SEQ_NO는 AUTO_INCREMENT라 안 넣는다(002_seq_no.sql). TASKS는 (BID_CASE_ID, TEAM)이 유일하다(001_schema.sql:82).
- 목록 `GET /tasks?team=디자이너`는 TASKS와 BID_CASES와 INSTITUTIONS를 조인한다(TaskMapper.xml:213-221). 노원 기관 행(`nowon`)이 INSTITUTIONS에 있어야 한다(테스트가 쓰는 값).
- 받는 사람(recipients)은 다음 셋의 합이다(DesignReviewService.java:665-712).
  - 그 건의 BID_ASSIGNMENT 활성 영업 담당.
  - 3팀 TASKS의 담당(사번이면 그 사용자, 이름이면 그 팀 ACTIVE 중 유일할 때만).
  - 활성 3팀 팀장 전원(시드: 이영업 5047192, 오전산 6295038, 한예산 9026715).
  - 디자이너 본인과 영업부장은 제외한다. 팀장이 시드에 있으니 NO_REVIEWERS(409)는 나지 않는다.

### 3. 구현안 — 실행 절차

사전 확인(읽기). 같은 입찰건이 있으면 재사용한다.
```sql
SELECT B.BID_CASE_ID, B.INSTITUTION_ID, T.TASK_ID, T.TEAM, T.STATUS, T.ASSIGNEE
  FROM BID_CASES B LEFT JOIN TASKS T ON T.BID_CASE_ID = B.BID_CASE_ID
 WHERE B.INSTITUTION_ID = 'nowon' ORDER BY B.SEQ_NO, T.SEQ_NO;
SELECT INSTITUTION_ID, NAME_KO FROM INSTITUTIONS WHERE INSTITUTION_ID='nowon';
```

**절차 B — 업로드·점검만 되게 하기 (제출 버튼은 닫힘)**
- 3팀이 2차완료가 아니면 `/design/complete`가 409(`teamsNotDone`)를 낸다. 업로드와 점검은 이 조건과 무관하다.
- 새 건에 디자이너 작업만 넣는다.
```sql
INSERT INTO BID_CASES (BID_CASE_ID, INSTITUTION_ID, PARTICIPATION_STATUS, PARTICIPATION_DECISION)
VALUES ('bc-sample-dsn1', 'nowon', '참여확정', '[]');
INSERT INTO TASKS (TASK_ID, BID_CASE_ID, TEAM, STATUS, ASSIGNEE)
VALUES ('task-sample-dsn1-d', 'bc-sample-dsn1', '디자이너', '작성중', '7130526');
```
- 노원 건이 이미 있고 그 건에 디자이너 작업이 없으면, 위 BID_CASES INSERT를 건너뛰고 기존 `bid_case_id`로 TASKS만 넣는다.

**절차 A — 제출 확인창까지 열리게 하기 (3팀 2차완료 필요)**
```sql
-- 위 B의 BID_CASES INSERT를 먼저 실행한 뒤(이미 실행했다면 건너뜀)
INSERT INTO TASKS (TASK_ID, BID_CASE_ID, TEAM, STATUS, ASSIGNEE) VALUES
 ('task-sample-dsn1-s','bc-sample-dsn1','영업','2차완료','3918264'),
 ('task-sample-dsn1-i','bc-sample-dsn1','전산','2차완료','4482971'),
 ('task-sample-dsn1-b','bc-sample-dsn1','예산','2차완료','1857403'),
 ('task-sample-dsn1-d','bc-sample-dsn1','디자이너','작성중','7130526');
INSERT INTO BID_ASSIGNMENT (BID_CASE_ID, EMP_NO, ACTIVE_YN, ASSIGNED_BY, ASSIGNED_AT)
VALUES ('bc-sample-dsn1','3918264',1,'5047192','2026-11-23T00:00:00.000000+00:00');
```
- 담당 사번은 009_seed_users.sql의 시드 팀원이다: 김영업 3918264, 권전산 4482971, 정예산 1857403.
- 이들은 팀장이 아니라서 "팀장 담당이면 1차 결재를 부장이 한다"(TaskCommandService.java:146)는 분기에 걸리지 않는다.
- 기존 노원 건을 재사용하려면 INSERT 대신 `UPDATE TASKS SET STATUS='2차완료' WHERE BID_CASE_ID='<기존>' AND TEAM IN ('영업','전산','예산');`을 쓴다. 이 UPDATE는 실행 전에 원래 상태를 적어 둔다(되돌릴 때 필요).
- 기존 건에 ASSIGNEE가 비어 있으면 받는 사람 계산에서 `unresolved`가 되지만, 팀장이 있어 막히지는 않는다.

**절차 A'(디자이너 작업만 실제 API로 만들기)**
- 3팀 2차완료와 BID_ASSIGNMENT 행을 SQL로 만든 다음, 디자이너 작업 INSERT만 API로 바꿀 수 있다. 위 A에서 `task-sample-dsn1-d` 한 줄을 뺀 뒤 실행한다.
```
curl -s -X POST http://localhost:8080/bidcases/bc-sample-dsn1/design-task \
  -H "X-Emp-No: 7130526" -H "X-User-Id: web-user" \
  -H "X-Screen-Id: design_open" -H "X-Button-Id: design_open"
```
- 응답은 201 `{"task_id":"task-…","created":true}`다. 이때 ASSIGNEE는 비어 있다. 담당을 7130526으로 고정하려면 다음을 실행한다.
  `UPDATE TASKS SET ASSIGNEE='7130526' WHERE BID_CASE_ID='bc-sample-dsn1' AND TEAM='디자이너';`
- 이 호출은 BID_PREP_ACT 감사 행(DSN_OPEN)을 남긴다. 헤더 `X-Screen-Id`·`X-Button-Id`는 선택이다. 허용 목록 밖이거나 없으면 unknown으로 기록된다(DesignUiIds).

### 4. 확인 방법 (호출자가 실행)
```
curl -s "http://localhost:8080/tasks?team=%EB%94%94%EC%9E%90%EC%9D%B4%EB%84%88" -H "X-Emp-No: 7130526"
curl -s http://localhost:8080/tasks/task-sample-dsn1-d/design-review -H "X-Emp-No: 7130526"
```
- 첫 번째는 1건이어야 한다. 한글 쿼리값이 깨지면 `--data-urlencode`와 `-G`를 쓴다.
- 두 번째의 `viewer.can_complete`는 절차 A에서 true, 절차 B에서 false다(DesignReviewService.java:520).
- 파일 업로드는 `POST /tasks/task-sample-dsn1-d/files`다(TaskController.java:126). 디자이너 작업은 등록된 활성 디자이너이면서 담당 본인일 때만 허용된다. X-Emp-No가 필요하다.
- 제출 확인창 이후 실제 제출을 누르면 상태가 `1차완료`가 되고 DESIGN_ROUND, 쪽지, DOC_CHECK_LOG 행이 생긴다. 이는 정상 흐름이다.

### 5. 되돌리는 법과 위험
- 모두 로컬 개발 DB 전용이다. 자기신고 인증이라 "검증됨" 표현은 쓰지 않는다. 가상 데이터만 쓴다.
- 샘플 id는 `bc-sample-dsn1`, `task-sample-dsn1-*`이고, 실제 흐름이 만드는 `bc-xxxx` 모양과 달라 쉽게 구분된다.
- 삭제는 자식 표 먼저, 건과 작업은 마지막에 한다.
```sql
DELETE FROM DESIGN_ACK            WHERE TASK_ID LIKE 'task-sample-dsn1-%';
DELETE FROM DESIGN_COMMENT        WHERE TASK_ID LIKE 'task-sample-dsn1-%';
DELETE FROM DESIGN_ROUND_RECIP    WHERE TASK_ID LIKE 'task-sample-dsn1-%';
DELETE FROM DESIGN_ROUND          WHERE BID_CASE_ID='bc-sample-dsn1';
DELETE FROM DOC_CHECK_HIT         WHERE TASK_ID LIKE 'task-sample-dsn1-%';
DELETE FROM DOC_CHECK_LOG         WHERE TASK_ID LIKE 'task-sample-dsn1-%';
DELETE FROM DOC_CHECK             WHERE TASK_ID LIKE 'task-sample-dsn1-%';
DELETE FROM BID_PREP_ACT          WHERE BID_CASE_ID='bc-sample-dsn1';
DELETE FROM BID_ASSIGN_LOG        WHERE BID_CASE_ID='bc-sample-dsn1';
DELETE FROM BID_ASSIGNMENT        WHERE BID_CASE_ID='bc-sample-dsn1';
DELETE FROM TASKS                 WHERE BID_CASE_ID='bc-sample-dsn1';
DELETE FROM BID_CASES             WHERE BID_CASE_ID='bc-sample-dsn1';
```
- 제출·업로드까지 해 봤다면 아래도 추가한다. 실행 전에 해당 표의 `TASK_ID` 칸이 있는지 확인한다.
  - NOTIFICATIONS: `WHERE TASK_ID LIKE 'task-sample-dsn1-%'`
  - 올린 파일: 서버의 task-files 폴더 아래 task-sample-dsn1-d 폴더는 `DELETE /tasks/{id}/files/{name}` API로 지우거나 직접 지운다.
- ACCESS_LOG와 BID_PREP_ACT는 감사 기록이다. 테스트용 건이어도 지우는 것은 호출자가 판단한다. BID_PREP_ACT의 자식 행은 건 번호로 걸러 삭제하는 것이 안전하다.
- 기존 건을 재사용해 UPDATE했다면 되돌리는 DELETE가 아니라 원래 STATUS로 UPDATE해야 한다. 그래서 UPDATE 전에 적어 두라고 했다.

### 3-2. Pii 확장 패치 (`support/Pii.java`, 기존 `scan`·`scanLoose` 출력은 바꾸지 않는다. 신규 메서드만 추가)
```java
// 추가: MOBILE 아래
private static final String MK = "[\\d*xX#○●]";
private static final String SP = "[\\s\\-./]*";
private static final String CC = "(?:(?:\\+|00)?82" + SP + "(?:\\(0\\))?" + SP + "0?|\\(?0)";   // 국가번호 또는 0
/** 휴대폰 — 부분 가림·+82·괄호·사선·점 포함. 가렸든 아니든 존재하면 거부 대상. */
private static final Pattern MOBILE_ANY = Pattern.compile(
        "(?<!\\d)" + CC + "(1[016789])\\)?" + SP + "(" + MK + "{3,4})" + SP + "(" + MK + "{4})(?!\\d)");
/** 유선 — 02, 031~033, 041~044, 051~055, 061~064, 070. 대표번호(1xxx)는 시작이 1이라 걸리지 않는다. */
private static final Pattern LANDLINE = Pattern.compile(
        "(?<!\\d)(?<!\\d[-./])" + CC.replace("0?|", "|") + "(2|3[1-3]|4[1-4]|5[1-5]|6[1-4]|70)\\)?" + SP
        + "(" + MK + "{3,4})" + SP + "(" + MK + "{4})(?!\\d)");

/** 외부 확인 반입용(서버 안전망). value 는 항상 "[가림]" — 검사 결과가 2차 유출 경로가 되지 않게 한다. */
public static List<Finding> scanExternal(String text) {
    List<Finding> out = new ArrayList<Finding>();
    if (text == null || text.isEmpty()) return out;
    String f = fold(text, true);                       // NFKC·서식문자 제거·대시류 통일
    Matcher m = MOBILE_ANY.matcher(f);
    while (m.find()) out.add(new Finding("휴대폰", "[가림]"));
    Matcher l = LANDLINE.matcher(f);
    while (l.find()) {                                  // 국번 뒤 두 묶음이 모두 가림표이면 통과
        if (hasDigit(l.group(2)) || hasDigit(l.group(3))) out.add(new Finding("유선전화", "[가림]"));
    }
    for (Finding x : scanLoose(text)) {                 // 주민·외국인·카드·이메일(기존 규칙)
        if (!"휴대폰".equals(x.getKind())) out.add(new Finding(x.getKind(), "[가림]"));
    }
    return out;
}
private static boolean hasDigit(String s) { for (int i = 0; i < s.length(); i++) if (Character.isDigit(s.charAt(i))) return true; return false; }
```
- 가림표는 NFKC 뒤 `* x X # ○ ●`로 본다. 전각 `＊`는 NFKC가 `*`로 바꾼다.
- 줄바꿈으로 갈라진 번호(`010-1234-\n5678`)는 구분자 클래스 `\s` 덕에 잡힌다. 줄이 다른 숫자까지 이어져 걸리는 오탐은 감수한다. 안전망이므로 과잉 제외 쪽이 낫다.
- 날짜 `2026-12-02`나 문서번호 `2026-0212-3456`은 `(?<!\d[-./])`로 제외한다. 이 부분은 시험표에서 반드시 확인한다.
- 서버 호출 지점은 manifest의 모든 문자열 값, 파일명, 첨부 추출 텍스트다. 추출 텍스트는 본문·메타·주석·양식·책갈피·미리보기를 각각 `locator`(body·meta·annot·form·bookmark·preview·filename·manifest)로 구분해 센다.

### 3-3. 서버 재검사 흐름 (`ExtCheckService`, 새 클래스. 기존 `InboxService.importBatch`의 records 경로는 건드리지 않는다)
1. **형식 검사 — 오류면 배치 422, DB·파일 변화 없음**
   - 스키마(`checks[]`), `check_id` 유일성.
   - `schema_minor`: 서버 최대값(1)보다 크거나 없는데 `checks`가 있으면 422 `UNSUPPORTED_MINOR`.
   - `attachments[].path` 허용 목록:

   - `sha256` 불일치는 422.
2. **내용 검사 — check 단위, 걸리면 그 check를 제외**
   - 제외 사유 코드와 `locator`를 응답의 `excluded[]`로 돌려준다. 예: `{check_id, reason:"PII_MOBILE", locator:"body", count:2}`. 값은 싣지 않는다.
   - 대상 manifest 문자열(제목·보도 제목 등)과 `institution.name_ko`에 `scanExternal`을 돌린다.
   - **공통 매직 넘버 확인**: PDF는 `%PDF`, HWPX는 zip(`PK`), HWP는 OLE(`D0 CF 11 E0`). 확장자와 다르면 `FORMAT_MISMATCH`.
   - **PDF** (pdfbox 2.0.29, `MemoryUsageSetting.setupMixed`):
     - 거부 조건:
       - 암호화(`isEncrypted`).
       - Catalog의 `/Names/JavaScript`·`/OpenAction`·`/AA`·`/EmbeddedFiles`·XFA.
       - 주석 중 FileAttachment·Launch·JavaScript·URI 액션 중 JS/Launch.
       - 쪽수 200 초과.
     - 추출 대상 텍스트: 쪽별 `PDFTextStripper`, 문서 정보 전 항목과 XMP, 주석의 `/Contents`·`/T`·`/Subj`, AcroForm 필드의 값·기본값, 책갈피 제목.
   - **HWPX** (JDK `ZipInputStream`/`javax.xml`, hwpx용 외부 라이브러리 없음):
     - zip 폭탄 상한: 항목 500개, 항목당 풀린 크기 50 MiB, 합계 100 MiB, 압축비 100:1 초과 시 중단. 읽을 때 바이트를 세어 헤더 값은 믿지 않는다.
     - 항목명에 `..`·절대경로·`\`·`:`가 있으면 거부한다.
     - `mimetype`은 `application/hwp+zip`이어야 한다.
     - 거부: `Scripts/*`, `BinData/*` 중 이미지가 아닌 것, 중첩 zip, `META-INF`의 암호화 표시.
     - 텍스트 검사: `Contents/section*.xml`, `header.xml`, `docProps/*`, `Preview/PrvText.txt`의 텍스트 노드와 속성값.
     - XML 파서 설정: `FEATURE_SECURE_PROCESSING` + `disallow-doctype-decl=true`, 외부 일반/매개변수 엔티티 false, `load-external-dtd=false`, XInclude 끔. DOCTYPE이 있으면 `XXE_REJECTED`.
   - **HWP** (hwplib, 아래 §3-4):
     - 읽기 전에 FileHeader 속성 비트를 먼저 본다. 암호(bit1)·배포용(bit2)·스크립트 저장(bit3)·DRM(bit4)·인증서 암호(bit8)·인증서 DRM(bit10)이면 `ENCRYPTED`/`SCRIPT`로 거부한다. 읽지 않고 거부하는 경로다.
     - `BinData`의 OLE 등 이미지가 아닌 내장물은 `EMBEDDED`로 거부한다.
     - 본문 문단 텍스트와 SummaryInformation(작성자)을 검사한다. 미리보기(`PrvText`)도 포함한다.
   - **시간 한도**: 파일당 20초. 별도 데몬 스레드풀(2개)에서 `Future.get(timeout)`으로 돌리고, 넘으면 `TIMEOUT`으로 제외한다. pdfbox·hwplib는 인터럽트에 약해 스레드가 남을 수 있다. 추출 글자 수도 파일당 200만 자로 자른다.
3. **처리 순서(보상 포함)**

   - ② 제외된 check의 첨부는 즉시 `Files.delete`한다. 삭제에 실패하면 해당 `reason`과 별도로 `DELETE_FAILED`를 오류 이력에 남기고 배치를 오류 처리한다. 개인정보 파일이 inbox에 남지 않게 하기 위해서다.

   - ⑤ 제외된 check의 manifest 항목은 `{"check_id":..,"excluded":true}`로 다시 써서 보관한다. 제목에 남은 개인정보가 보관 사본에 남지 않게 하기 위해서다.

### 3-4. HWP 읽기 도구 제안 (결정·반입은 메인)
- 후보는 `kr.dogfoot:hwplib`(neolord0/hwplib)다. 1.1.x 계열이고 Apache-2.0, Java 8 빌드 대상으로 알고 있다.
  - **정확한 버전은 확인하지 못했다.** 메인이 Maven Central에서 가장 최근 안정 1.1.x를 골라야 한다.
- 반입 전에 메인이 확인할 것:
  - `mvn dependency:tree`에서 `poi` 계열 버전 충돌(이 프로젝트는 poi-ooxml 사용 중).
  - 알려진 CVE와 라이선스 전이 의존성.
  - Java 8 클래스 버전.
- 위험: hwplib은 압축 스트림을 내부에서 풀어 폭탄 상한을 걸 수 없다. 그래서 파일 크기 20 MiB, 시간 20초, FileHeader 선검사, 별도 스레드로 막는다. 힙 압박은 남는 위험이다.
- 대안: 서버에서 HWP를 읽지 않고 HWPX만 받게 하는 것이다. 사용자가 HWP를 받겠다고 결정했으므로 기본안은 아니다.

### 3-5. DDL — `db/mysql/041_external_check.sql` / `db/oracle/041_external_check.sql` (v1 보정)
- v1 기본키가 `(기관, 시각, 종류, slug)`였는데, 열람 API에서 기관·시각이 URL에 노출되어 추측이 쉽다. 서버가 만든 무작위 `CHECK_KEY`(`SecureRandom` 16바이트, hex 32자)를 기본키로 바꾼다. Oracle에 시퀀스 없이도 같은 DDL이 된다.
- 제외 로그 표를 추가했다. 건수만 있고 값은 없다.
```sql

CREATE TABLE EXT_CHECK (
    CHECK_KEY      CHAR(32)     NOT NULL,        -- 서버 발급 무작위, URL용
    INSTITUTION_ID VARCHAR(64)  NOT NULL,
    BATCH_ID       VARCHAR(80)  NOT NULL,
    CHECK_ID       VARCHAR(40)  NOT NULL,
    CHECKED_AT     VARCHAR(40)  NOT NULL,        -- ISO 8601 +09:00
    SOURCE_KIND    VARCHAR(10)  NOT NULL,        -- notice / press
    SOURCE_SLUG    VARCHAR(30)  NOT NULL,

    ERROR_CD       VARCHAR(30),
    MATCH_CONF     VARCHAR(5),
    MATCH_BASIS    VARCHAR(200),
    NOTICE_NO      VARCHAR(60),
    NOTICE_TITLE   VARCHAR(300),
    POSTED_AT      VARCHAR(10),
    DEADLINE_AT    VARCHAR(10),
    NOTICE_URL     VARCHAR(500),
    IMPORTED_AT    VARCHAR(40)  NOT NULL,
    PRIMARY KEY (CHECK_KEY),
    UNIQUE KEY UQ_EC_BATCH (BATCH_ID, CHECK_ID),
    KEY IDX_EC_LATEST (INSTITUTION_ID, SOURCE_KIND, CHECKED_AT)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE EXT_CHECK_FILE (
    CHECK_KEY   CHAR(32)     NOT NULL,
    FILE_SEQ    SMALLINT     NOT NULL,
    FORMAT_CD   VARCHAR(5)   NOT NULL,           -- pdf / hwp / hwpx (매직 넘버로 정한 값)
    STORED_NAME VARCHAR(100) NOT NULL,           -- <check_id>_<순번>.<ext>, 서버 생성

CREATE TABLE EXT_CHECK_EXCL (                    -- 제외 이력: 종류·위치·건수만
    BATCH_ID    VARCHAR(80) NOT NULL,
    CHECK_ID    VARCHAR(40) NOT NULL,

    EXCLUDED_AT VARCHAR(40) NOT NULL,
    PRIMARY KEY (BATCH_ID, CHECK_ID, REASON_CD, LOCATOR_CD)

```
- Oracle 쌍은 같은 열 구성으로 쓴다: `VARCHAR2`, `NUMBER(19)`, `NUMBER(5)`, `CHAR(32)`. `KEY`·`UNIQUE KEY`는 쓰지 않고 `CONSTRAINT ... PRIMARY KEY/UNIQUE`와 별도 `CREATE INDEX`로 쓴다. `COMMENT ON COLUMN`은 한글로 단다. 정본 작성까지만 하고 적용은 DBA 몫이다.
- 이미 적용한 DB는 040 뒤에 041을 한 번 더 실행하면 된다. 039·040은 건드리지 않는다.

### 3-6. 열람 API 설계 (security "4요건"을 이렇게 해석했다 — 원문 대조 필요)
1. **역할 허용 목록 + 403**: `InboxController`와 같은 방식이다. 허용하지 않는 역할은 403, 사번 없음은 401. 둘 다 접근 이력 `DENIED`(고정 문구)로 남긴다. 허용 역할 자체는 기획이 정한다. 아래 이관 메모 참조.
2. **DB 키만으로 접근**: 클라이언트가 보내는 경로·파일명은 쓰지 않는다. `GET /ext-checks?institution_id=` 목록과 `GET /ext-checks/{check_key}/files/{seq}` 다운로드만 둔다. 서버가 `EXT_CHECK_FILE`에서 `STORED_NAME`을 찾아 ext_check 루트의 realPath 아래인지 확인한 뒤 읽는다. 없거나 벗어나면 404이고, 내부 정보는 싣지 않는다.
3. **접근 이력**: 누가(`Actor`, 자기신고)·언제·`check_key`·`seq`만 남긴다. 파일 내용·질의값은 남기지 않는다. 오류 응답에도 `X-Error-Ref` 규칙만 쓴다.
4. **응답 헤더**: 다운로드는 `Content-Disposition: attachment; filename="<서버 생성명>"`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Content-Type: application/octet-stream`을 쓴다. 인라인 표시는 하지 않는다.
- 응답 키는 snake_case로 한다: `check_key`, `status`, `checked_at`, `match_confidence`, `notice_title`, `files[]{seq, format}`. `/menus` 계약은 건드리지 않는다.
- `.gitignore`에 `corpus/inbox/`, `corpus/inbox/batches/`, `corpus/ext_check/`를 추가한다. 기존 규칙과 겹치는지는 메인이 diff로 본다.

## 4. 단계 나눔과 시험
- **1단계**: Pii `scanExternal`과 위 시험표, SCHEMA 문안(§3-1), `checks[]` 형식 검사(py·java 둘 다), minor 422. → **security 재검토 ①**
- **2단계**: 경로·realPath·junction·매직 넘버·크기·sha, PDF 검사, 처리 순서와 보상.
- **3단계**: HWPX, HWP(hwplib 반입 뒤). → **security 재검토 ②**(라이브러리 포함)
- **4단계**: 041 DDL 쌍, 저장, 제외 로그, 열람 API. 5단계는 화면(디자인 → 프런트).
- 1~2단계는 패치가 가능하다. HWP 코드는 hwplib 반입과 버전 확인 뒤에 쓴다.
- 추가할 시험:
  - `checks`만 있는 배치를 반입하면 `bid_cases` 변화 0, `EXT_CHECK` 행 생성.
  - 휴대폰이 든 check는 제외되고, 같은 배치의 다른 check는 반입되며, 제외 check의 첨부 파일이 없고, 응답에 번호가 없다.
  - `files/../x`, `files/a:b.pdf`, 한글 경로, junction, sha 불일치는 422.
  - 확장자와 매직 넘버 불일치는 제외.
  - 암호화 PDF, JS가 든 PDF, 내장 파일 PDF는 제외.
  - DOCTYPE이 든 HWPX는 `XXE_REJECTED`. zip 폭탄 표본은 중단.
  - `schema_minor` 없음 또는 2 + `checks` 있음은 422.
  - 열람: 허용되지 않는 역할 403, 존재하지 않는 키 404, 헤더 4종.
  - 기존 `InboxApiTest`가 그대로 통과하는지 확인한다(기존 380건 + 신규).
- 호출자가 실행할 명령: `cd kgi-ggreport-web && mvn -q -o test`. 8080 서버가 같은 `target/`을 쓰면 테스트 뒤 재기동한다. 이 패치는 아직 적용 전이라 테스트를 돌리지 않았다.

## 5. 보안·위험·되돌리는 법
- **자기신고**: `X-Emp-No`는 자기신고라 열람 이력의 "누가"는 사칭이 가능하다. 화면·문서에 "검증됨"이라고 쓰지 않는다. `reported_*`도 같다.
- **서버가 못 막는 것**:
  - 이미지에 든 번호는 읽지 못한다. 전처리 6번과 수집기 책임으로 남긴다.
  - 스캔 PDF나 이미지 위주 HWP를 이렇게 반입하면 안전망이 비어 있다. 이 위험은 사용자에게 한 번 알릴 필요가 있다.
- **되돌리기**: 041의 DROP 세 줄이다. 코드는 `checks`를 무시하면 v1과 같다. `ext_check/` 파일은 폴더째 지운다.
- 격리 폴더는 만들지 않는다. 개인정보가 든 파일을 보관하는 것 자체가 위험하기 때문이다. 대신 건수만 `EXT_CHECK_EXCL`에 남긴다.

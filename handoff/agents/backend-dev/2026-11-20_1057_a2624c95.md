```java
/**
 * 목표 기관 변경(TARGET_CHANGE, 056). ⚠️ 첫 DB 문장은 기관 행 잠금(정렬 순서) — MySQL RR 일관 읽기가 잠금 뒤에 잡히게 callers.require 보다 먼저.
 * 검증·결재자 계산은 targetChanges.plan, 항목 정본은 INST_BID_TARGET_REQ_ITEM, payload 는 카드 표시용 요약만.
 */
@Transactional
public Map<String, Object> submitTargetChange(TargetChangeIn in, Actor actor) {
    targetChanges.lockAll(in);                       // 400(형식)·404(기관) 가능, 잠금만
    SysUser me = callers.require(actor);
    TargetChangeService.Plan plan = targetChanges.plan(in, me);
    ApprovalRequest r = new ApprovalRequest();
    r.setReqType(ApprovalTypes.TARGET_CHANGE);
    r.setRequesterEmpNo(me.getEmpNo());
    r.setTitle(plan.getTitle());                     // "목표 기관 변경 — ○○구청 외 n곳"
    String payload = write(plan.getPayload());
    if (payload.length() > 3800) throw new ApiException(400, "한 번에 올리기에 항목이 너무 많습니다. 나눠서 요청해 주세요.");
    r.setPayload(payload);
    r.setStatus("PENDING");
    r.setCurrentStep(1);
    r.setCreatedAt(Times.nowIso());
    requests.insert(r);
    ApprovalStep s = step(1, "LINE", plan.getApprover().getEmpNo());
    s.setReqId(r.getReqId());
    requests.insertStep(s);
    targetChanges.claim(plan, r.getReqId());         // 항목 행 INSERT
    notifyStep(r, s, me);
    return view(requests.selectById(r.getReqId()), me);
}
```

### 3-6. `BidTargetService` 변경
```java
// 상수
static final String ACTION_CARRY = "CARRY";
static final String APPROVAL_MSG = "목표 기관을 빼거나 옮기려면 팀장 결재가 필요합니다. [결재 요청]으로 올려 주세요.";

static boolean directGoal(SysUser u) { return u != null && HeadRules.ROLE_HEAD.equals(HeadRules.roleOf(u.getRole())); }

// 잠금 뒤 공통 검사
private void requireNoPending(String inst, BidTarget cur) {
```

**`save()`**
- 넣기(`cur == null`)와 연도가 바뀌는 고치기는 `checkOverlap` 바로 앞에서 `requireNoPending(inst, cur)`.
- 메모·태그·주 담당만 바꾸는 고치기는 그대로 둡니다.

**`cancel()`**
- 사유 검사(`parseCancel`)와 LIMIT 검사 뒤에 `requireNoPending(inst, cur)`.
- 그다음, 목표 기록이면 `if (GOAL && !directGoal(me)) throw conflict("APPROVAL_REQUIRED", APPROVAL_MSG, cur);`.
- 관심 기록이면 지금처럼 바로 뺍니다.
- 쓰는 부분은 `applyCancel(cur, cp, actor, ui, null)`로 추출해 `TargetChangeService`가 재사용합니다.

**`move()`**
- `closedCheck` 뒤에 `requireNoPending` 그리고 `if (!directGoal(me)) throw conflict("APPROVAL_REQUIRED", …)`. 옮기기는 어느 방향이든 목표가 관련됩니다.
- 쓰는 부분은 `applyMove(cur, to, year, actor, ui, reqId)`로 추출합니다.
- `me`는 `users.selectByEmpNo(actor.getEmpNo())`로 구합니다. 이미 `insert()`가 같은 조회를 합니다.

**`insert(row, actor, ui)` → `insert(row, actor, ui, Long reqId)`**
- `row.setApprovalReqId(reqId)` 한 줄을 추가합니다. `BidTarget`에 `approvalReqId`·`carryFromNo` 필드를 두고, XML `insertRow`와 `cols`에 두 칸을 추가합니다.

**`list()`**
- 항목마다 `change_pending`(위 맵 값 또는 null)과 `change_mode`를 추가합니다. `change_mode`는 목표면 `"DIRECT"`(부장) 또는 `"APPROVAL"`, 관심이면 `"DIRECT"`.
- 바깥에 `carry_due`(이월 대기 건수, 아래 3-7)를 추가합니다.
- 기존 `can_cancel` 뜻은 바꾸지 않습니다. 화면이 `change_mode`로 넘어가기 전까지 호환됩니다.

**`view()`**
- `withAction`일 때 `"approval_req_id"`와 `"carry_from_no"`를 추가합니다(사번 아님).

### 3-7. 이월 — 화면 진입 때 영업 사용자가 굳히는 방식(배치 금지 제약 때문)

**언제 실행되나**

**어떻게 쓰나**

### 추가할 시험 (입력 → 기대)
1. 영업팀원이 목표 `/cancel` → 409 `APPROVAL_REQUIRED`, 행 수 그대로. 관심 `/cancel` → 201.
2. 영업팀원이 `/move`를 어느 방향으로든 → 409 `APPROVAL_REQUIRED`. 영업부장 → 201.
3. 결재 요청 3건(빼기·관심으로·목표로) → 200, `req_type = TARGET_CHANGE`, 결재자 = 영업팀장, 항목 3행, 목표 기록은 그대로.
4. 같은 기관을 다시 요청 → 409 `CHANGE_PENDING`. 그 기관 넣기·옮기기·빼기 → 409 `CHANGE_PENDING`. 메모 고치기 → 201.
5. 항목 0개·21개 이상·같은 기관 두 번·이상한 op_cd → 400. 없는 기관 → 404. 옛 rev → 409 STALE(요청 행 없음, 롤백).

9. 반려·회수 → 목표 기록 그대로, 잠금 풀림(다시 요청 200).
10. 대결자 승인 → 403(NO_PROXY). 관리자 `box=all`에 안 보이고, 관리자 취소 → 403.

## 5. 보안·위험·되돌리는 법

**security가 볼 점**
- **(가) 자기신고 인증.** 사번은 `X-Emp-No` 자기신고라, 영업부장 사번을 대면 결재 없이 바로 빼고 옮길 수 있습니다. 결재 역시 결재자 사번 사칭을 막지 못합니다. 이번 변경은 업무 절차 강제일 뿐 보안 경계가 아닙니다. 행마다 `EMP_VERIFIED`와 접근 이력으로 사후 추적만 됩니다.
- **(나) 우회 경로.** 관심 기록을 빼고(결재 없음) 목표를 새로 넣으면(결재 없음) 관심→목표 결재를 건너뜁니다. 목표 연도를 바꾸는 고치기(`goal_next_year` 버튼)도 사실상 올해 목표에서 빼는 효과인데 결재가 없습니다. 둘 다 Q3에 걸려 있습니다.
- **(다) 409를 쓴 이유.** `APPROVAL_REQUIRED`를 403이 아닌 409로 둔 것은 권한은 있고 절차만 다르기 때문입니다. 그래서 ACCESS_LOG DENIED에는 안 남고 failDetail의 `409 APPROVAL_REQUIRED`로만 남습니다. 403이 맞다면 `guard.denied`로 바꾸면 됩니다.
- **(라) 오류 상세.** 오류 detail에는 `item_no`·`code`·기관 이름만 넣고 입력값이나 사번은 넣지 않습니다.
- **(마) 반영 행의 화면·버튼.** 반영 행의 화면·버튼은 결재 화면의 `PrepUiIds.of(req)` 값입니다. 허용 목록에 목표 변경 버튼이 없으면 UNKNOWN과 `ui_valid = 0`이 됩니다. `-write`가 `PrepUiIds`를 확인하고 필요하면 `approve`/`reject` 공용 버튼으로 맞춰야 합니다.
- **(바) 이월 POST의 작동 범위.** 이월 POST는 영업 계열 누구나 부를 수 있지만 서버가 대상을 계산하므로 임의 기관을 넣을 수 없고 멱등입니다.
- **(사) 동시성.** 상신과 직접 쓰기는 기관 잠금으로 직렬화됩니다. 승인 경로는 잠금 전에 스냅샷이 잡히지만, 결재 중 잠금과 PK(같은 REV)가 마지막 방어선입니다. 결재 중 잠금은 요청 상태로 계산하므로 반려·취소 때 따로 풀 일이 없습니다.

**되돌리는 법**
- 코드를 되돌리면 056 칸은 null로 남아 무해합니다. 표를 지우는 것은 056 헤더의 DROP 순서대로 합니다.
- 결재 없이 쓰던 예전 동작으로 임시로 돌아가려면 `directGoal`이 영업 계열 전체에 대해 true를 돌려주게 하면 됩니다(상수 한 줄).

## 7. 열린 질문 (사용자에게, 업무 언어)

- **Q1. 목표 '달성'은 무엇을 보고 판정하나요?** 이월은 "올해 목표를 이루지 못한 기관을 내년 목표로 자동으로 넘기는 것"입니다. 무엇을 '이뤘다'로 볼지에 따라 넘어가는 기관이 달라집니다. 이 질문은 성과 보고서(NEXT 104)의 성공 정의와 같으니 함께 묻는 것을 권합니다.
  - ⓐ 기관 상세의 '금고 약정'에 국민은행이 다음 기간 금고로 기록됨 (권장 — 지금 시스템에 있는 근거)
  - ⓑ '입찰 결과 등록' 화면에서 낙찰로 기록됨 (그 화면은 아직 준비 중)
  - ⓒ 입찰이 그 해에 없었던 기관(다음 회차가 몇 년 뒤)도 이월할지 함께 알려 주세요.
- **Q2. 팀장·부장 본인이 목표를 뺄 때도 결재를 받아야 하나요?** 지금 설계는 영업부장만 바로 바꾸고, 영업팀장은 부장 결재를 받습니다.
  - ⓐ 이대로
  - ⓑ 팀장도 바로 바꿈 (빠르지만 팀장 혼자 결정)
  - ⓒ 부장도 기록만 남기고 다른 부장이나 관리자가 확인
- **Q3. 목표를 '새로 넣기'와 '목표 연도를 내년으로 미루기'에도 결재가 필요한가요?** 지금은 둘 다 결재 없이 됩니다. 그런데 이렇게 두면 "관심 기관을 빼고 목표로 새로 넣는" 방법으로 관심→목표 결재를 건너뛸 수 있고, 연도를 미루면 올해 목표에서 빠지는 효과가 납니다.
  - ⓐ 둘 다 결재 (권장 — 목표는 팀 결정이라는 원칙과 맞음)
  - ⓑ 미루기만 결재
  - ⓒ 둘 다 지금처럼 결재 없이

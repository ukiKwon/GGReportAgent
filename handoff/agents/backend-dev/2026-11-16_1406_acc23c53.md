### 2. 설계 요약 (권장안과 근거)
- **파일 이름 규칙**: 요약 md 경로에서 끝의 `.md`를 `.full.txt`로 바꾼다. 예: `…_20260923.md` → `…_20260923.full.txt`. DB 컬럼은 추가하지 않는다(DDL 0, 스키마 무변경안 유지). 경로는 DB의 output_path에서만 계산하고 사용자 입력은 쓰지 않는다. 같은 이름 충돌 때 md에 `_2`가 붙으면 full도 같은 접미사를 따른다. md를 먼저 쓴 뒤 실제 md 경로로 full 경로를 계산하기 때문이다.
- **저장 시점**: parseRfp에서 md 저장 직후 1회 저장한다. 조회 때는 재추출하지 않는다. 재분석(reparse)은 이전 md와 full을 함께 지운 뒤 새로 만든다.
- **실패 처리**: full 저장이 실패해도 요약 분석은 성공으로 둔다. 요약이 본 산출물이기 때문이다. 경고 로그만 남기고, 조회에서는 "원문 없음"으로 구분된다.
- **크기 상한**: 설정값 `upload.rfp-fulltext-max-chars`, 기본 1,000,000자. 근거: 공고문은 보통 100~500쪽, 쪽당 약 1,500자라 0.15~0.75M자다. 1M자는 UTF-8로 약 3MB다. 읽을 때 `readAllBytes`로 메모리에 올리는 크기가 3MB를 넘지 않게 하려는 값이다. 넘으면 앞에서부터 자르고(서로게이트 쌍은 쪼개지 않는다) 끝에 고정 표지 줄 `[※ 원문이 길어 여기서 잘렸습니다 …]`를 붙인다. 조회 때 이 표지를 보고 응답 헤더 `X-Fulltext-Truncated: true`를 단다.
- **창구**: `GET /api/rfps/{id}/fulltext`(text/plain; UTF-8)를 권장한다. `?format=fulltext`가 아니다. 이유는 셋이다.
  1. 기존 `format`과 Accept 협상 규칙(`wantsRawMarkdown`)에 섞이지 않아 요약 응답 호환(③)이 구조적으로 보장된다.
  2. 크기가 다른 응답이라 경로별로 접근 제한(IP·토큰)을 거는 것이 쉽다.
  3. 접근 이력을 경로로 구분할 수 있다.
- **응답 상태 구분**:
  - 200: 본문은 text/plain. 잘렸으면 `X-Fulltext-Truncated: true`. 항상 `Cache-Control: no-store`.
  - 404 `{"error":"찾을 수 없습니다."}`: 없음·반려·삭제·RFP 아님·파싱 미성공. 한 문구이고 id·경로는 싣지 않는다(0dc4c73 방식).
  - 404 `{"error":"원문이 없습니다. 재분석이 필요합니다.","code":"fulltext_missing"}`: 활성 RFP인데 full 파일이 없는 옛 분석 건. `code`로 "없는 id"와 구분한다. 이 건은 이미 활성 목록에서 id가 노출되는 건이라 정보가 새지 않는다. 클라이언트가 404를 일괄 "없음"으로 처리할 우려가 있어 409로 하는 대안도 있으나, 기본은 404+code로 둔다.
  - 500 `{"error":"원문 읽기 실패"}`: 고정 문구, 예외는 로그에만.
- 요약 JSON에 `hasFulltext` 키를 더하는 것은 하지 않았다. ③ 무변경 지시를 지켰다. 필요하면 추가 키 하나라 호환에는 안전하다(선택).

### 5. 보안·위험·되돌리는 법
- **무인증 노출**(⑤): `/api/rfps/**`는 기존에도 무인증이다. 이 창구는 요약보다 훨씬 많은 원문 글자를 한 번에 준다(최대 약 3MB). 문의 03-4ⓒ(공개 범위)가 정해지기 전에는 위험이 요약보다 크다. 원본 공고문이 폐쇄망 내부 자료라는 맥락이다. 자기신고·IP 외 인증 수단이 없다는 한계가 그대로이므로 "검증됨"이라고 쓰지 않는다.
- **임시 완화 후보**(구현은 선택. 아래 중 택일 또는 병행):
  - (a) 공유 토큰 헤더: 설정값 `upload.fulltext-token`이 비어 있으면 기존대로 열림, 값이 있으면 `X-Api-Token`이 일치(`MessageDigest.isEqual`, 상수시간)해야 하고 불일치는 `/fulltext`에 한해 **404 일반 문구**(존재 여부 비노출)로 응답한다. 컨트롤러에 `@Value("${upload.fulltext-token:}") String token`과 `@RequestHeader(name="X-Api-Token", required=false) String given` 두 개만 더하면 된다. 비밀 값은 `config/`에만 두고 저장소에 올리지 않는다. 토큰이 전용 설정값 하나이므로 다른 사용자에게 같은 효과를 내려면 호출 주체와 공유해야 한다는 점이 운영 부담이다.
  - (b) 호출 IP 허용 목록: 설정값 `upload.fulltext-allow-ips`(쉼표 구분)이면 `request.getRemoteAddr()` 검사. 프록시·WAS 앞단이 있으면 `getRemoteAddr()`가 프록시 IP일 수 있어 운영 구성을 먼저 확인해야 한다(내가 구성을 보지 못했다).
  - (c) 인프라: L7/WAF에서 `/api/rfps/*/fulltext` 경로만 호출 서버에 제한. 코드 변경이 없고 가장 단순하다. 권장 순서는 (c) → (a) → (b)다.
- **입력·경로**: 경로는 DB 값에서만 계산하고 `{id}`는 Long이다. 경로 조작이 불가능하다. 오류 문구에 파일명·예외·id를 싣지 않는다. 접근 이력 로그는 id만 남기고 본문·쿼리값은 넣지 않는다.
- **개인정보**: 공고문은 공개 문서가 대부분이나 담당자 이름·연락처가 원문에 있을 수 있다. 원문 전체 보관은 이 값을 그대로 담는다. 자동 삭제가 없으니(사용자 결정) 반려·삭제 건의 full 파일이 디스크에 남는다. API에서는 404로 가려지지만 파일은 남는다. 삭제 정책에서 full도 지울지 기획 결정이 필요하다(§6).
- **디스크**: 건당 0.5~3MB. 업로드 건수 × 위 크기를 DBA·운영이 용량 계획에 반영한다.
- **되돌리는 법**: 파일 3개의 diff를 되돌린다. `.full.txt` 파일은 남아도 어떤 코드도 읽지 않으며 삭제해도 무해하다. DDL이 없어 DB는 변경 없다. 옛 분석 건은 재분석 때까지 `fulltext_missing` 상태다.

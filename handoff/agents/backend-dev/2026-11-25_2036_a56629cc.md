## 2. 판정 요약
- **스키마 변경 불필요(063 없음).** MySQL 026:45-46 `VAL_FROM VARCHAR(7)`, `VAL_TO VARCHAR(7)` NOT NULL 아님. Oracle 026:58-59도 `VARCHAR2(7 CHAR)`, NOT NULL·CHECK 없음(주석 "NULL=현재·미상"). 026 이후 VAL_FROM/VAL_TO를 건드린 스크립트 없음(resources 전체 grep으로 026뿐). 옛 395줄이 이미 NULL을 담고 있다는 메인의 추정과 일치.
- **검사 위치는 한 곳**: InstitutionHeadService.fillValue(358-360)의 `HeadText.requireStart`. confirmItem·머리 확정에는 EDU 날짜 재검사가 없다(BIRTH_DATE만 재검사, 886-888). 따라서 확정 재검사·'년생' 차단(noAge는 value·src_title에만)·금지어(rejectAny)와 충돌하지 않는다.
- **중복 방지**: 서버에는 EDU/CAREER 중복 검사가 없다(addItem: multi면 항상 confirm=true, 같은 값 대체 로직은 단일 칸 전용). 날짜에 기대지 않으므로 그대로 성립(= 같은 학력 줄을 두 번 보내면 두 줄). 상한 EDU_MAX=10은 날짜 무관. 중복 방지는 import.mjs:56-58의 value 기준 클라이언트 쪽뿐이다.
- **Word**: 바꿀 것 없음. datesOf(512-522)는 from·to 둘 다 비면 "" → 괄호 없이 내용만. dateText는 빈 값을 ""로. sortKey(551-555)는 to·from 모두 비면 "0000-00|" → 내림차순 맨 아래, oldestIndex(574)도 "날짜 없는 줄이 가장 먼저 빠짐"이라고 이미 명시. 기존 옛 줄과 같은 처리. to만 있고 from 없는 경우(옛 줄엔 가능)도 "(졸업연도)"로 이미 처리되나 신규 입력은 거절한다.
- 응답: itemMap(235-236)이 `i.getValFrom()`을 그대로 넣음 → 빈 입력은 DB NULL로 저장되어 `"from": null, "to": null`로 나간다(빈 문자열 아님. requirePeriod가 ""→null로 바꿈). 키는 항상 존재.

## 5. 보안·위험·되돌림
- 권한(403 경로)·접근 이력(INST_HEAD_LOG ITEM_ADD, ACT) 판정은 무변경. 연도가 빈 줄도 감사 필드는 동일(id·코드·역할). 오류 메시지에 입력값을 싣지 않는다(새 문구도 고정 문장).
- 위험: 날짜 없는 학력이 늘면 같은 학력 중복 줄이 쌓일 수 있음(서버 중복 방지 없음) — 기존과 같은 상태. 필요하면 후속으로 "같은 value 학력 재입력 시 대체" 설계를 기획과 논의.
- 되돌림: 위 서비스 수정 3줄을 requireStart 원형으로 복원 + 새 시험 파일 삭제. DB 변경 없음.
- 자기신고 인증 한계는 기존과 동일(검증 아님).

## 6. 이관 메모
- `[이관: 프런트]` 학력 입력 폼에서 입학(from)·졸업(to) 둘 다 비워 제출 허용(경력은 시작 필수 유지). 서버 계약: 학력의 `from`·`to`는 `null`(키는 항상 존재, 빈 문자열 아님) 가능, "끝만 있고 시작 없음"은 400 INVALID_DATE이므로 폼에서 막거나 문구 처리. 카드 표시는 null일 때 괄호 없이 내용만(Word와 같게)·정렬은 맨 아래(headcard.js sortPeriod가 null from/to를 이미 다루는지 확인 — 옛 줄 때문에 이미 처리됐을 가능성 큼) — 기다리는 것: headcard.js 확인 — 근거: Word 쪽 datesOf/sortKey가 같은 규칙.
- `[이관: 데이터/메인(도구)]` tools/head-transfer: 서버가 이제 날짜 없는 EDU를 받으므로 import.mjs:59 `if (!it.from) { log.old_sql++; continue; }`와 README 7단계·export.mjs:73의 old-items.sql 분리는 EDU에 한해 불필요해짐(EDU는 from 없이 API로 POST 가능, 중복은 value 기준 56-58줄 skip이 이미 막음). 단 CAREER 날짜 없는 옛 줄은 여전히 400이라 old-items.sql 경로가 계속 필요. 지금은 바꾸지 말 것(요청대로). 바꾸게 되면: EDU만 API 경로로, CAREER만 old-items.sql로, README 문구 수정.

## 7. 확신 못 하는 점·열린 질문
- 982줄 이후(머리 확정 A8·반입/매칭)에서 EDU from을 다시 검사하는지 못 읽었다. 위 grep 결과로 requireStart 호출은 fillValue뿐이라 문제없다고 판단하나, 후보 머리 경로가 항상 addItem→fillValue를 거친다는 가정이다.
- `from`만 있고 `to` 없음 = Word에서 "(2001 ~ 현재)"로 나오는 기존 동작(학력에 어색할 수 있음). 이 변경과 무관한 기존 동작이라 건드리지 않았다. 학력에서 to 없는 경우 "~ 현재"를 빼야 하는지는 기획 결정 사항.

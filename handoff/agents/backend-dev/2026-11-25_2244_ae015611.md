## 2. 프런트가 쓸 v3 본문 JSON(저장 때 보내는 모양)
`PUT .../draft` 는 기존처럼 `{base_ver, fields, lists, tables}` 이고, 키는 아래와 같습니다. FACT 칸(`inst_name`·`inst_type`·`head_name`·`current_bank`)은 보내면 400 FIELD_READONLY 입니다.
```json
{
 "base_ver": 5,
 "fields": {
  "bid_kind":   {"val":"주거래은행 선정","note":null},
  "head_title": {"val":"원장","note":null},
  "budget":     {"val":"1조원","note":null},
  "staff":      {"val":null,"note":null},
  "supervisor": {"val":"가상부","note":null},
  "address":    {"val":"가상시 가상로 1","note":null},
  "org_note":   {"val":"[본사] 3국 20과","note":null}
 },
 "lists": {
  "overview":    ["현황 1"],
  "mmda_basis":  [{"text":"평잔 산정 기준 가","note":"각주 하나"}, {"text":"기준 나","note":null}],
  "competition": ["경쟁 1"],
  "effect":      []
 },
 "tables": {
  "biz":  {"rows":[{"group":"고유사업(A)","sub":"a1","lines":[{"text":"굵은 줄","bold":true},{"text":"보통 줄","bold":false}]}]},
  "fund": {"rows":[{"kind":"일반회계","lines":[{"lv":0,"text":"운영 1"},{"lv":1,"text":"세부 1"}]}]},
  "years":{"unit":"억원","from":2027,"to":2031,"end":2029,
           "mmda":{"2027":"1200","2030":"10000"},"income":{"2027":"12.5","2030":"30"},"notes":["공고일 기준 가정"]},
  "scoring": {
   "row_count":4, "col_count":3, "total":100,
   "source":{"attach_id":7,"file":"공고.hwpx","table":0},
   "cells":[{"r":0,"c":0,"rs":2,"cs":1,"text":"부문"}, {"r":0,"c":1,"rs":1,"cs":1,"text":"항목"}, {"r":0,"c":2,"rs":2,"cs":1,"text":"배점"},
            {"r":1,"c":1,"rs":1,"cs":1,"text":"세부"},
            {"r":2,"c":0,"rs":2,"cs":1,"text":"1. 신용도"}, {"r":2,"c":1,"rs":1,"cs":1,"text":"a"}, {"r":2,"c":2,"rs":2,"cs":1,"text":"10"},
            {"r":3,"c":1,"rs":1,"cs":1,"text":"b"}]
  }
 }
}
```
- **`scoring` 은 `tables.scoring` 입니다.** 지시문의 "새 칸 scoring"을 최상위 키로 하지 않았습니다. `PrepFormIn` DTO 를 바꾸지 않기 위해서입니다.
- **`scoring` 값은 `GET …/prep/notice-scoring` 응답에서 가져옵니다.**
  - 응답의 `cells`·`row_count`·`col_count`·`total` 을 그대로 쓰면 됩니다.
  - `source` 는 `{attach_id, file, table}` 로 직접 만들어야 합니다. 응답의 `table` 필드를 쓰세요.
  - 저장 때 `cells` 를 `(r,c)` 순으로 정렬합니다.
  - 격자에 빈 자리가 있어도 저장됩니다(Word 가 빈 칸으로 채웁니다).
  - 칸이 없거나 `null` 이면 `null` 로 저장되어 1쪽만 나옵니다.
- **`tables` 를 보낼 때는 `scoring` 도 항상 같이 보내야 합니다.** 다른 표처럼 전체 교체라서, 빠뜨리면 `scoring` 이 `null` 로 지워집니다. 프런트가 현재 값을 되보내야 합니다.
- **줄 입력은 옛 모양도 받습니다.** `mmda_basis` 줄과 사업 `lines` 줄은 문자열로 보내도 `{text,note:null}`·`{text,bold:false}` 로 정규화해 저장합니다.
- **GET 응답(`view.content`)은 저장 판이 v1·v2 여도 v3 모양으로 올려서 돌려줍니다.** 문자열 줄은 객체로, `head_title`·`scoring` 이 빠져 있으면 빈 값으로 채웁니다. `content.tpl_ver` 도 3으로 보입니다. 저장본 문자열·해시는 그대로이고, 확정된 v2 판의 Word 는 옛 조립 그대로 나옵니다.

### v2 대비 바뀐 칸
- 추가: `fields.head_title`(20자 이하, 한 줄, 개인정보 검사), `tables.scoring`.
- 모양 변경: `lists.mmda_basis` 가 문자열에서 `{text, note}` 로, 한 줄은 300자 이하이고 각주는 300자 이하 한 줄입니다. 줄 수는 최대 10입니다.
- 모양 변경: 사업 줄이 문자열에서 `{text,bold}` 로, 줄당 200자 이하이고 행당 최대 5줄입니다.
- 검증 완화: 연도 `mmda`·`income` 은 `from~to` 안이면 협약 종료 뒤 연도 값도 저장됩니다. 서버는 원래 허용했고 Word 만 비웠던 것이어서 코드 변경은 없습니다.
- `current_bank` 는 값이 그대로 저장·조회되지만 v3 Word 에는 나가지 않습니다.
- 그 밖 칸은 변경이 없습니다.

### 새 오류 코드와 검증 규칙
- 새 오류 코드는 `400 BAD_SCORING`(`key=scoring`, 위치·병합 범위 밖, 겹침, 행·열 상한, 합계 범위, 원본 표 번호 범위)입니다.
- 행은 1~200, 열은 1~12, `rs`·`cs` 는 1 이상이고, `r`/`c` 는 0 이상이며 `r+rs ≤ row_count`, `c+cs ≤ col_count` 입니다.
- 칸 수가 `row_count×col_count` 를 넘으면 400 TOO_MANY 입니다.
- 칸 글자는 500자 이하이고 줄바꿈을 허용하며 개인정보는 422 PII_DETECTED 입니다.
- 모르는 키는 400 UNKNOWN_KEY, 형이 다르면 400 BAD_TYPE 입니다.
- 전체 크기는 기존 `MAX_CONTENT_BYTES`(120KB)가 그대로 적용됩니다(400 CONTENT_TOO_LARGE). 평가표 전용 별도 크기 상한은 두지 않았습니다.

- B8: 기대효과 규칙은 그대로입니다.
- C: 1쪽 제목은 v2 와 같은 조립입니다("참고자료 1. 「기관」 {bid_kind} 관련 요약", `bid_kind` 가 비면 생략).

2쪽은 `tables.scoring` 에 칸이 있을 때만 나옵니다.
- 쪽 나눔 뒤 "참고자료 2. 「기관」 {bid_kind} 평가 기준표"(14pt)와 "■ 평가 항목 및 배점 기준"이 나옵니다.

## 5. 지시와 다르게 판단한 것
1. **`scoring` 위치:** 최상위 `scoring` 이 아니라 `tables.scoring` 입니다(위 2절 참고).
2. **'·' 글머리:** `DocxKit` 에 '·' 글머리가 없고 수정이 금지돼 있어서, 전각 공백과 '· ' 를 글자로 넣었습니다. 들여쓰기는 되지만 둘째 줄 내어쓰기는 없습니다. 이 서술 줄이 길어질 때 Word 에서 어떻게 보이는지는 실물 확인이 필요합니다.
3. **합계 줄:** 표 안에 '계·합계·총점·총계' 칸이 없고 `total` 이 있을 때만 표 아래에 오른쪽 맞춤 "합계 N점"을 덧붙입니다. 있으면 중복을 피해 덧붙이지 않습니다.
4. **머리 줄 수:** 첫 행 칸 중 세로 병합이 2인 칸이 있거나, 가로 병합이 있고 3행 이상이면 2줄, 아니면 1줄(표가 1행이면 0)입니다. 머리 줄은 음영·굵게·가운데 맞춤이며 쪽마다 반복됩니다. 휴리스틱이므로 디자인 확인이 필요합니다.
5. **`mmda_basis` 줄 정규화:** 글자가 빈 줄은 각주째 버립니다.
6. **`view` 응답 변경:** `view` 가 모든 판을 v3 모양으로 올려 돌려줍니다. 프런트가 문자열 줄과 객체 줄을 둘 다 처리하지 않아도 되게 하려는 것입니다.

## 6. 이관 메모
- [이관: 프런트] 위 JSON 모양에 맞춥니다.
  - 서술 줄 각주, 사업 줄 굵게, 직함 칸, 종료 뒤 연도 입력 허용(안내 문구 '빗금으로 칠해집니다' 수정).
  - 2쪽 편집 표(`cells` 로 `rowspan`/`colspan` 을 그립니다).
  - `notice-scoring` 응답에서 `scoring` 만들기. `source.table` 은 응답의 `table` 값입니다.
  - 후보가 여럿이면 `?table=n` 고르기.
  - 저장 때 `tables.scoring` 도 항상 같이 보내기.
- [이관: 디자인·e4] `DocxKit` 에 '·' 글머리와 내어쓰기가 필요하면 추가가 필요합니다. 지금은 `InstSummaryDocBuilder` 안에서 글자로 해결했습니다. 2쪽 표 칸 맞춤과 열 너비도 지금은 균등입니다.
- [이관: 데이터] 실제 HWPX 33개에서 `row_count`/`col_count` 가 12열·200행 안에 드는지, `cells` 병합이 맞는지 표본 확인이 필요합니다(이전 보고에서 이월).
- [이관: qa·security] 평가표 칸 글자에 개인정보 검사가 걸려 있습니다. 공고 표의 숫자열(예: 배점 나열)이 `Pii.scanLoose` 에 오탐되는지 실제 평가표로 확인이 필요합니다. 오탐이면 422 로 저장이 막힙니다.
- 건드리지 않은 파일(지시대로): `PrepService`, `PrepAttachApiTest`, `ScoringTable`, `PrepAttachService`, `PrepController`, `HeadDocBuilder`, `DocModel`, `DocxKit`, `frontend/`.

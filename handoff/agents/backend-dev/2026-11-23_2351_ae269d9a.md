## 3. 설계 결정 (요지)
1. **판정은 한 곳**: 새 메서드 `PrepService.mayDeputizeOpen(r, 신청자, 대결자, 원결재자)`를 결재함·결재·알림·승인 후처리가 모두 부른다. 아래 조건을 모두 만족해야 허용하고, 모르는 값이 있으면 막는다.
   - ① 대결자가 활성이고 ROLE 영업팀이며 직급 ≥ 수석차장(`Ranks.SENIOR_DEPUTY_MIN`=5)
   - ② 대결자가 신청자·원 결재자·지명자가 아님
   - ③ 오늘 유효한 대결 지정이 있음(`principalsOf`)
   - ④ 원 결재자 == `sameTeamLead(신청자)`. 직급 방향은 원 결재자 기준(mayApprove)이라 신청자가 수석차장이어도 된다.
   - ⑤ `sameTeamLead(대결자)`도 원 결재자. 다른 팀 수석차장을 막는다.

   일반 대결 규칙(`mayDecide`)은 이 유형에 쓰지 않는다(사용자 결정: 직급 비교는 원 결재자 기준).
2. **NO_PROXY는 그대로 두고 좁은 예외만 추가**: `ApprovalTypes.LEAD_DEPUTY_ONLY = {BID_OPEN}`. eligibility에서는 NO_PROXY보다 먼저 본다. 나머지 NO_PROXY 4개 유형과 일반 유형의 동작은 바뀌지 않는다.
3. **applyOpen**: 결재 단계 결재자가 아닌 사람이 처리하면 대결로 보고 `mayDeputizeOpen`을 다시 검사해 403으로 막는다(eligibility와 같은 판정). 결재자 본인이면 기존 역할 검사, 409 APPROVER_ROLE_MISMATCH·APPROVER_TEAM_MISMATCH 검사를 그대로 거친다.
4. **지정 단계는 경고만(권장)**: 대결 지정 하나가 모든 결재 유형에 쓰인다. 지정 단계에서 막으면 차장 대결자의 권한 신청 대결까지 깨진다. 또 직급·팀은 지정 뒤에 바뀔 수 있어 승인 때 판정하는 것이 정본이다. 그래서 영업팀장이 영업팀 수석차장 미만을 지정하면 `warning`에 "수석차장 이상만 대신 승인" 문구를 덧붙인다.
5. **영업팀장끼리의 대결(같은 직급 팀장)은 개설 신청에서 403(권장)**: 사용자 결정의 대상은 '같은 팀 수석차장'이고, Q-2026-11-20-01은 "다른 팀 팀장으로 넘기지 않는다"였다. 권한 신청 등 다른 결재의 팀장 대결은 그대로 된다. → 열린 질문 1
6. **본부장 추가**: LIST를 9개로 늘린다(계장 1 … 부장 7, 본부장 8, 대표 9).
   - `of()`의 등급 매핑은 `{1, 6, 7, 9}`로, EXECUTIVE=대표(최상위)로 둔다.
   - `ApproverRules.level`에서 본부장은 **부장급(2)**이다. 최상위(3)로 두면 `lineApprover`가 결재자 없이 상신을 통과시킨다(`ApprovalRequestService.java:719`). 부장급으로 두면 팀장 자동 결정에서 부장·본부장이 함께 있을 때 AMBIGUOUS가 되어 수동 지정으로 넘어간다(안전한 쪽).
   - APPROVER_MIN(=6)과 USUAL_DEPUTY_MIN(=3)은 값이 그대로다.
7. **DB 스크립트는 없다**: 스키마·시드 변경이 없다(POSITION_TITLE은 VARCHAR, 검증은 코드에서만 함). MySQL·Oracle 모두 할 일이 없다.

## 5. 보안·위험·되돌리는 법
- 인증은 X-Emp-No 자기신고다. 대결 수석차장의 사번을 대며 승인하는 것은 막지 못한다(기존 결재와 같은 한계). 이 검사는 업무 규칙이지 사칭 방지가 아니다.
- 403 경로:
  - 기간 밖, 직급 부족, 다른 팀, 영업팀장 대결, 지명자, 비활성이면 eligibility가 403을 낸다(쓰기 전).
  - applyOpen에서 다시 403을 낸다(우회 방어).
  - 결재 단계 팀장이 바뀐 경우, 본인 결재는 409이고 대결은 ④에 걸려 403이다.
- 접근 이력: 기존 `audited`(BID_PREP_ACT)와 ACCESS_LOG 그대로다. 본문·의견·사번을 새로 기록하지 않는다. 오류 문구에도 사번·이름을 넣지 않았다.
- 알림: 조건을 통과한 대결자에게만 "(팀장님의 대결자로 받았습니다)" 쪽지가 간다.
- 성능: 결재함 목록에서 BID_OPEN 대기 건마다 판정한다. 싼 조건(역할·직급)을 먼저 보므로 대부분 바로 빠진다. 통과하면 `selectAll`을 두 번 부른다(대기 건 수 × 대상자 수가 작아 허용 범위로 판단).
- 되돌리기: 이 패치의 커밋만 revert하면 된다. DB 변경이 없다. 이미 대결로 승인된 건은 APPROVAL_STEP에 남는다.

    public boolean mayDeputizeOpen(ApprovalRequest r, SysUser requester, SysUser deputy, String principalEmp) {
        if (r == null || requester == null || deputy == null || principalEmp == null
                || !ApprovalTypes.LEAD_DEPUTY_ONLY.contains(r.getReqType())) {
            return false;
        }
        String d = deputy.getEmpNo();
        if (!"ACTIVE".equals(deputy.getStatus()) || !BidAssignmentService.MEMBER_ROLE.equals(roleOf(deputy))
                || Ranks.of(deputy) < Ranks.SENIOR_DEPUTY_MIN
                || d.equals(requester.getEmpNo()) || d.equals(principalEmp)
                || textList(readJson(r.getPayload()).path("nominee_emp_nos")).contains(d)) {
            return false;
        }
        if (!deputies.principalsOf(d, Times.todayKst()).contains(principalEmp)) {
            return false;
        }
        SysUser lead = assignments.sameTeamLead(requester);
        SysUser mine = assignments.sameTeamLead(deputy);
        return lead != null && mine != null && principalEmp.equals(lead.getEmpNo()) && principalEmp.equals(mine.getEmpNo());

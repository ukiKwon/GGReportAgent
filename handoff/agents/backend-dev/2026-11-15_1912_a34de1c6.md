### 3. 설계에서 달라진 점 (숨기지 않음)
1. **`buildRows(muni, nonmuni, seoul, opts)`**: `normalizeExtra`는 `opts.extra`일 때만 호출한다. 설계는 항상 호출이라, 029 모드가 새 칸 경고를 내거나 unknown 상태에서 throw할 수 있었다. 029 출력은 그대로다.
2. **`validUrl`은 boolean**이고 새 `checkUrl`이 검증값(`href`)을 돌려준다. 시드 링크는 정규화된 href로 들어간다. 예: `https://x.kr`는 `https://x.kr/`.
3. **`InstUiIds`**: B3의 "허용 목록에 화면 id 추가"를 다르게 했다. `csv_import`·`inbox_apply`는 `SCREENS` 목록에 넣지 않았다. 대신 서버 고정 팩토리 `csvImport()`·`inboxApply()`(버튼 `import_upsert`)를 썼다. 그래야 PUT 헤더로 반입 이력을 흉내 낼 수 없다. 시험에도 있다.
4. **inbox 반입의 actor는 null**이다(ACTOR_EMP_NO NULL). 배치 경로에 사번이 없다.
5. **`updateFromImport` 조건식**: 설계의 `#{x} IS NOT NULL`은 H2·Oracle·MySQL의 파라미터 타입 추론이 불안해서 `<sql id="importDateChanged">`로 바꿨다. 기존 값 NULL이면 `LENGTH(COALESCE(x,''))>0`, 아니면 `COALESCE(x,기존)<>기존`으로 판정한다.
6. **`updateFields`의 확정 칸**은 `getContractEndConfirmedInt()`로 넣는다. 설계의 Boolean→NUMERIC 바인딩 대신 int로 바꿨다.
7. **L5 처리기**는 `ApiExceptionHandler`가 아니라 `@RestControllerAdvice(assignableTypes=InstitutionController.class)`인 별도 `InstitutionExceptionHandler`다. 게시판 쪽 `BoardWriteExceptionHandler`와 같은 선례이고, 다른 컨트롤러 동작은 그대로다. 단 `POST /institutions`의 깨진 JSON 본문도 Boot 기본에서 `{"detail":"요청 내용을 읽을 수 없습니다…"}`로 바뀐다. 기존 시험 중 이 본문을 검사하는 것은 찾지 못했다.
8. **DDL 시험 이름**: 설계는 INST_EDIT_LOG 칸을 13개라 했으나 실제는 14개라 시험은 14개로 단언한다.
9. **L3**(`selectByIdForUpdate`)는 선택 사항이라 넣지 않았다.

### 4. 컴파일·실행이 의심되는 곳
- **H2(Oracle 모드)**: 030의 `ALTER TABLE ... ADD ( ... DEFAULT ... NOT NULL ...)` 다중 칸 구문과 `GENERATED BY DEFAULT AS IDENTITY`가 컨텍스트 로딩에 영향을 줄 수 있다. 실패하면 모든 `@AppTest`가 깨지므로 가장 먼저 `mvn`에서 볼 곳이다.
- **MyBatis XML**: `updateFromImport`의 `<include>` 3회와 `<sql>` 안의 `&lt;&gt;`·`&gt;`. MySQL은 로컬 적용으로 확인한다. 031의 CASE(`ON DUPLICATE KEY UPDATE`)도 적용 시에 확인한다.
- **`InstitutionEditLogger`가 package-private**인데 public 클래스(`InstitutionCommandService`·`InboxDbApplier`)의 public 생성자 인자다. 컴파일은 되고 Spring 주입도 되지만, 경고나 리플렉션 문제가 나면 이 클래스를 public으로 바꾼다.
- **`InstitutionScheduleApiTest`**: `MockMvcRequestBuilders.put/get`을 정규화된 이름으로 호출한다(헬퍼 이름이 static import와 겹치지 않게). JSON 안의 `\\u202e`·`\\\"` 이스케이프는 의도대로 U+202E 문자와 따옴표가 되도록 썼다.
- **Jackson**: `contract_end_confirmed:"yes"`가 정말 `HttpMessageNotReadableException`이 되는지(시험이 확인한다). `contract_end:123`은 문자열로 강제 변환되어 `date()`의 400이 난다.
- **`InstitutionColumnsDdlPairTest`**: 정규식 파서라 DDL 모양에 민감하다. 실패하면 시험 정규식 문제인지 SQL 문제인지 먼저 구분한다.
- **`InstitutionColumnsSeedPairTest`**: id 접두(`org-`)·ORG_CODE 규칙이 실제 번들 데이터와 어긋나면 실패한다. 이는 데이터 문제를 잡는 시험이다(orgCode가 20자를 넘으면 `normalizeExtra`가 NULL로 만들어 id와 달라진다).

### 5. 이관 메모
- **[이관: 데이터]**: 번들 `confirmed:true`의 noticeUrl·noticeNo 채우기. 강등 건수는 2단계 `--check`에서 나온다. 개원 예정 기관의 openDate도 함께 본다.
- **[이관: 프런트]**: 규칙은 설계 §6과 같다.
  - 날짜를 바꿀 때 `contract_end_confirmed`를 반드시 같이 보낸다.
  - 확정에는 출처가 필요하다.
  - `op_status` 변경에는 출처가 필요하고, `PLANNED`에는 `open_date`가 필요하다.
  - 헤더 값은 `X-Screen-Id`(`institution_edit`·`map_popover`·`bid_board`)와 `X-Button-Id`(`save_basic`·`save_schedule`·`save_open_status`·`open_edit`)다.

  - 링크는 `safeHttpUrl`·`esc`·`rel="noopener noreferrer"`로만 그린다.
- **[이관: 기획]**: 확정·운영 상태를 영업 계열 전체에 계속 열어 둘지(M1), 개원일만 바꾸는 저장의 출처 필수 여부, `open_check_needed`의 마지막 날 기준 해석이 맞는지.
- **[이관: 메인]**:

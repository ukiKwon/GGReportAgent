## 2. 설계와 다르게 한 곳
- 공고명(`bid_title`)은 사용자 11-26 추가 지시대로 더했습니다.
  - 실제 칸 이름은 `BID_CASES.TITLE`입니다(001_schema.sql:65 `VARCHAR2(500 CHAR)`, BidCaseMapper.xml:30·37).
  - 목록과 현황판은 `selectList`의 `bc.TITLE AS BID_TITLE`로, 상세는 `selectBidSubject`의 `b.TITLE AS BID_TITLE`로 채웁니다.
  - 공백뿐이거나 비면 `BidSubjects.blankToNull`이 null로 바꿉니다. 이 보조 메서드는 지시에 없던 추가입니다.
- 설계 문자열은 실제 코드와 모두 맞아서 바꾼 곳이 없습니다.
- `BidSubjectApiTest`는 설계의 3개 시나리오를 3개 `@Test`로 나눴습니다. 공고명 단언은 아래 둘로 넣었습니다.
  - 확정으로 만든 건: 목록·상세·현황판 세 응답 모두 `bid_title` 키가 있고, DB의 TITLE이 비면 null, 있으면 같은 값입니다.
  - TITLE을 '가상 공고명'으로 바꾼 뒤: 세 응답이 그 값을 줍니다.
- 시험은 `GET /preps`에 화면 헤더를 붙이지 않았습니다. 설계에 헤더가 없었고, 필요하면 메인 시험 결과에서 고칩니다.

## 3. apply-mysql 등록
- 따로 등록할 것이 없습니다. `tools/db/apply-mysql.mjs`는 `db/mysql/NNN_*.sql`을 `readdirSync`로 읽어 번호순으로 적용하고(파일명 규칙 `^\d{3}_[A-Za-z0-9_]+\.sql$`), 체크섬도 파일에서 계산합니다.
- `PROBES` 표는 `--mark`로 이미 적용된 DB를 표시할 때만 씁니다. 061~063은 이미 항목이 없으므로 064도 더하지 않았습니다. 로컬 DB에 064를 수동으로 먼저 적용했다면 그때만 `--mark` 검사가 필요합니다.

## 4. 메인이 돌릴 것
- 순서는 DB 먼저, 서버 나중입니다.
  1. 로컬 MySQL에 `node tools/db/apply-mysql.mjs`로 064를 적용합니다.
  2. `SELECT BID_SUBJECT_CD, COUNT(*) FROM BID_CASES GROUP BY BID_SUBJECT_CD`가 MAIN_BANK 한 줄이어야 합니다.
  3. 8080 서버를 재기동합니다.
- 시험은 `cd kgi-ggreport-web && mvn -q -o test -Dtest=BidSubjectDdlPairTest,BidSubjectsTest,BidSubjectApiTest`를 먼저 돌리고, 이어서 전체 `mvn -q -o test`를 돌립니다.
  - 기대 결과: 새 시험은 DdlPair 3개·Subjects 6개·Api 3개가 통과합니다.
  - 기존 시험(골든 04·05·10·14·25, DomainJsonContractTest)은 그대로 통과해야 합니다.
- 확인 포인트: H2의 `ADD (... DEFAULT 'MAIN_BANK' NOT NULL)` 문법. 063 형태와 같아 통과할 것으로 보지만, 실행해서 확인한 것은 아닙니다.

## 5. 화면이 쓸 응답 키
- `GET /preps` 목록 줄, `GET /bidcases/{id}/prep` 상세, `GET /prep-board` 줄 세 곳에 모두 실립니다.
  - `bid_subject_cd`: `MAIN_BANK`, `FUND_MGMT`, `CORP_CARD`, `ETC`.
  - `bid_subject_name`: 표시 이름. ETC에 손 이름이 있으면 그 이름, 아니면 코드표 이름입니다. 화면에서는 이스케이프해야 합니다.
  - `bid_title`: 공고명. 없거나 비면 null입니다.
- 기존 키는 그대로이고 키만 늘었습니다.

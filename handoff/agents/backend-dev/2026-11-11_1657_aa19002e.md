## 2. 요구와 근거
- **기관장 칸·마스킹·보존·충돌 해소·후보** (NEXT.md:322, 338)
  - 항목 칸만 둔다. 자유 서술·경조사·연락처는 받지 않는다.
  - 열람은 영업팀 전원. 값 충돌 해소는 영업팀장이 하고, 본인이 낸 값은 본인이 해소하지 못한다.
  - 반입값은 '후보'이고 사람이 확정한다.
  - 목록·엑셀은 이름을 홍*동으로 가린다. 학력·경력은 상세에서만 보이고 상세 열람은 기록한다.
  - 이전 기관장은 숨기고 보존한다.
- **임기 칸·사진** (NEXT.md:409)
  - 임기 칸: 첫 취임일·현 임기 시작일·임기 만료일·권한대행. 칸마다 출처를 단다.
  - 사진은 실제 사진을 쓰고 없으면 실루엣. 담당자가 올릴 수 있어야 한다.
- **기관 번호** (NEXT.md:337): 번호는 행정표준 기관코드 7자리이고 별도 칸이다. 코드가 없는 곳은 TMP-nnnn이고, 1:N 매칭은 사람이 판정한다.
- **security C1~C8, S3** (NEXT.md:321): S3는 `GET /institutions`에 가드가 없다는 지적이다. 그래서 기관장 정보는 별도 표·별도 API로 둔다.
- **영업 역할 집합**: `InboxController.java:38-39` {영업팀, 영업팀장, 영업부장}. 영업팀장 상수는 `BidAssignmentService.java:60`.
- **재사용할 업로드 패턴**:

## 3. 구현안

### 3-0. 기관 키
- **기관장 표는 지금의 `INSTITUTION_ID`(VARCHAR 64)를 키로 쓴다. 기관코드(ORG_CD)로 키를 잡지 않는다.**
  - 기관코드는 아직 칸이 없다(76 이관 몫).
  - 코드가 없는 곳(TMP)과 판정 대기가 있다.
  - 분할·통합은 별칭·이력 표로 처리하는 것이 정본이다.
  - `INSTITUTION_ID`는 재사용·삭제하지 않는 내부 키다.
- 기관코드는 조회할 때 INSTITUTIONS를 조인해 함께 내보낸다(76 이관 뒤).
- 반입 후보는 수집 쪽이 보낸 기관코드·기관명을 원문 칸(`SRC_ORG_CD`·`SRC_ORG_NAME`)에 두고 `INSTITUTION_ID`는 비운 채 '매칭 대기'로 받는다.
  - 1단계(지금): 사람이 기관을 골라 넣는 API만 둔다.
  - 2단계(76 뒤): `/inbox` 반입이 기관코드로 자동 매칭한다. 한 건만 맞을 때만 자동이고, 애매하면 대기로 남긴다.

**MySQL 미러** `db/mysql/027_inst_head.sql`:
- 같은 다섯 표를 만든다. 칸 대응은 024·025 미러와 같은 규칙이다.
  - `NUMBER GENERATED … IDENTITY` → `BIGINT NOT NULL AUTO_INCREMENT`
  - `VARCHAR2(n CHAR)` → `VARCHAR(n)`, `NUMBER(1)` → `SMALLINT`, `NUMBER(5)` → `INT`, `NUMBER(12)` → `BIGINT`, 그 밖 `NUMBER` → `BIGINT`
  - 인덱스는 `KEY IDX_… (…)`로 테이블 안에, `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`
- COMMON_CODE INSERT 48행은 Oracle과 글자 그대로 같고 `COMMIT;`만 없다.
- 헤더에 "⚠️ 정본이 아니다. 025 적용 후 한 번만, 멱등하지 않다"를 적는다.

- **사진 응답 헤더(A12)**:
  - `Content-Type: image/jpeg`(항상 서버 재인코딩본)
  - `Content-Disposition: inline; filename="photo.jpg"`(고정 이름)
  - `Cache-Control: no-store`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`
  - `Content-Security-Policy: default-src 'none'; sandbox`
- **사진 노출 규칙**: CURRENT 기관장의 ACTIVE 사진만 낸다. REPLACED·VOIDED이거나 FORMER 기관장 사진이면 404 HIDDEN이다. 옛 사진은 보관만 하고 1단계에는 열람 API가 없다.
- **사진 표시 방법**: 인증이 `X-Emp-No` 헤더 방식이라 `<img src>`로는 받을 수 없다. 화면은 fetch → blob → objectURL로 띄운다(프런트 이관).
- **새 컨트롤러** `InstitutionHeadController`(A3~A5·A11~A13은 `/institutions/{id}/head…`): 기존 `InstitutionController`의 경로(`/{institutionId}`, `/status` 등)와 겹치지 않는다. 골든 00·01·02·08·09와 `/menus`는 건드리지 않는다.

### 3-3. 확정·충돌 규칙
- **칸 종류**
  - 단일 칸: NAME·POSITION·ACTING·FIRST_TAKE_OFFICE·TERM_START·TERM_END
  - 여러 개 칸: EDU·CAREER
- **충돌의 정의**: 단일 칸 후보 X에 대해 같은 머리의 확정값이 있는데 값이 다르거나, 같은 칸의 다른 열린 후보와 값이 다르면 충돌이다.
  - 값 비교 기준: 앞뒤 공백·연속 공백·전각 문자를 정규화한 뒤 비교한다.
  - 충돌 여부는 저장하지 않고 확정할 때와 A3 응답에서 계산한다(낡은 표시가 남지 않게).
- **직접 입력(A5)**
  - 여러 개 칸은 바로 CONFIRMED.
  - 단일 칸이 비어 있거나 값이 같으면 CONFIRMED. 값이 같을 때는 출처·확인일을 갱신하고 이전 행은 SUPERSEDED가 된다.
  - 값이 다르면 CANDIDATE가 되어 충돌 처리로 넘어간다.
- **비충돌 후보 확정·기각**: 영업팀 누구나(**팀 기본값, 열린 질문 Q1**).
- **충돌 후보 확정·기각**: 영업팀장만, 그리고 X를 낸 사람(직접 입력자, 반입이면 반입 버튼을 누른 사람)이 아닐 것.
  - 위반하면 403 `SELF_RESOLVE` 또는 403 `LEAD_ONLY`이고, 둘 다 DENIED로 기록한다.
  - 같은 사람이 같은 이름을 두 번 내도 마찬가지다.
- **후보 머리(새 인물) 확정(A8)**: 현 기관장이 있으면 충돌 규칙을 따른다(팀장, 본인 제외). 없으면 영업팀 누구나.
- **이름이 다른 후보**: 수집 결과의 이름이 현 기관장과 다르면 칸 후보가 아니라 **후보 머리**로 만든다. 동명이인 판정은 사람이 한다.
- **본인 후보 회수**: 낸 사람은 언제든 자기 후보를 기각(회수)할 수 있다.
- **무효(A10·A13)**: 그 값·사진을 낸 사람 또는 영업팀장. 사유 1~200자, 개인정보가 나오면 422.
- **사진 교체**: 영업팀 누구나. 옛 사진은 REPLACED로 보관한다(Q4).
- **동시성**: 기관 하나에 대한 머리·칸 확정·교체·사진 교체는 `INSTITUTIONS` 행 `FOR UPDATE`로 줄을 세운다(024 BID_PREP과 같은 방식). 잠금은 느린 사진 검사 **뒤에** 잡는다.
  - 잠금 뒤에 상태를 다시 확인하고, 바뀌었으면 409 `STATE_CHANGED`.

### 3-4. 입력 검사(서버)
- 공통: 제어·서식 문자는 400. `Pii.scanLoose`에서 어떤 종류든 걸리면 422 `PII_BLOCKED`(연락처 비수집이므로 이메일·휴대폰도 차단). 금지어 패턴이 나오면 422 `HEAD_FORBIDDEN`. 오류에는 종류만 싣고 값은 싣지 않는다.
  - 금지어 목록은 서버 상수이고 기획 확정 대상이다(경조사·가족·종교·건강 등).
- 칸별 형식:
  - NAME 1~30자, 숫자 금지
  - POSITION 1~40자
  - EDU·CAREER 1~60자 한 줄
  - 날짜는 `YYYY-MM-DD` 실재 날짜(만료일은 미래 허용). CAREER 기간은 `YYYY` 또는 `YYYY-MM`.
  - ACTING은 true/false
- 출처: `src_kind`는 사용 중인 코드만. `src_title` 1~100자 필수. `src_url`은 http/https만, userinfo·제어문자 금지, ≤1000자. `checked_on`은 오늘 이하이고 2000-01-01 이상.
- 칸 수 상한: 머리당 EDU 10개, CAREER 20개(넘으면 409 `ITEM_LIMIT`). 머리당 열린 후보 50개.

### 3-5. 사진 검사·재인코딩 (`HeadPhotoInspector`, 패키지 내부 final 클래스)
- **판단: 메타데이터를 골라 지우지 않고 재인코딩한다.**
  - 바이트 단위로 골라 지우면 EXIF/XMP/ICC/PNG tEXt·iTXt/폴리글롯 꼬리를 하나씩 따라가야 해서 빠뜨리기 쉽다.
  - 디코드 → 다시 인코딩하면 화소만 남는다. JDK 8 `ImageIO`만으로 되고 외부 라이브러리가 필요 없다.
- **검사 순서**:
  1. 확장자 jpg/jpeg/png(대소문자 무시)
  2. 크기 ≤ **5MB**(413 `FILE_TOO_LARGE`)
  3. 매직 바이트: JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`. 확장자와 다르면 400 `FORMAT_MISMATCH`.
  4. `ImageReader`로 **머리글만 읽어** 가로·세로 확인. 각 변 ≤ 6000이고 화소 ≤ 2,500만이어야 한다. 아니면 400(압축 폭탄 방지).
  5. 전용 2스레드 풀에서 10초 제한으로 디코드(`PrepAttachInspector` PDF 풀과 같은 방식).
     - CMYK·손상 파일은 400 "일반 JPG/PNG로 다시 저장해 올려 주세요".
  6. RGB로 그린다. 투명 배경은 흰색.
  7. **600×800 안에 맞춰 축소**(비율 유지, 확대 없음).
  8. JPEG 품질 0.85로 다시 쓴다(메타데이터 노드 없이).
  9. 결과의 SHA256과 원본 SHA256을 함께 기록하고 원본은 버린다.
- **최소 크기**: 120×160 미만은 400.
- **파일 이름**: 원래 이름은 저장하지 않는다(이름에 사람 이름이 들어 있는 경우가 많다).
- **알려진 한계**: EXIF 회전 정보가 사라지므로 휴대폰 사진이 눕혀 보일 수 있다. 1단계는 "바로 세운 사진을 올려 주세요" 안내로 처리하고, 회전 값만 읽어 돌리는 것은 2단계 후보로 둔다.
- **HEIC·WebP·GIF·SVG**: 거부한다(400 `UNSUPPORTED_FORMAT`).
- **저장**: 설정 키 `ggreport.head-photo-dir`(기본 `data/head-photo`)를 `AppProperties`에 추가한다. 키 생성·임시 파일 → 이동·`toRealPath` 루트 검사·롤백 시 삭제는 `PrepAttachService`와 같다.
  - 1단계에서 공용 클래스로 뽑아내지는 않는다. 중복은 cleaner 후보로 넘긴다.
- **본문 상한**: `BoardWriteLimitFilter`에 `(?:^|/)institutions/+[^/]+/+head/+photos/*$`(POST, 5MB + 여유 1MB) 패턴을 추가한다. 길이가 없으면 411.

## 5. 보안·위험·되돌리는 법 (security 검토 요청 항목)
1. **자기신고 인증**: `X-Emp-No`를 바꾸면 누구나 영업팀장으로 행세해 충돌을 해소하거나 상세·사진을 볼 수 있습니다. "본인 해소 불가"는 업무 규칙이지 사칭 방지가 아닙니다. 감사의 사번도 자기신고이고(`EMP_VERIFIED=0`), 운영 노출 전 SSO가 필요합니다(NEXT 35).
2. **이미지 디코더 공격면**: JDK 8 `ImageIO`(JPEG/PNG)의 알려진 취약점에 대비해 JDK 패치 수준을 확인해야 합니다. 머리글 화소 상한·10초 제한·2스레드 풀로 묶습니다. `ImageIO.setUseCache(false)`를 쓰면 전역 설정이 바뀌는데, 다른 기능에 영향이 있는지 검토가 필요합니다.
3. **메타데이터 제거 보증**: 재인코딩으로 EXIF·GPS·XMP·ICC·PNG 텍스트·꼬리 데이터를 없앤다는 판단의 검토와, 위 테스트 10의 마커 검사로 충분한지 봐 주세요.
4. **사진 응답**: 고정 Content-Type, nosniff, CSP sandbox, inline 고정 이름, no-store. 저장 경로는 서버 키뿐이고 원래 파일 이름은 버립니다.
5. **출처 URL**: http/https만 받지만 화면은 링크를 텍스트로 그리고 `rel="noopener noreferrer"`를 붙여야 합니다(프런트). 폐쇄망이라 대부분 열리지 않습니다.
6. **마스킹 강도**: 표시용 마스킹입니다. 상세 API는 영업 역할 모두에게 원문을 줍니다. 300개 기관 상세를 반복 호출하는 대량 열람은 막지 않고 기록만 합니다.
   - `ops/integrity_check.sql`에 "사번별 하루 VIEW 수" 점검 쿼리를 추가하는 것을 제안합니다(값 없이 건수만).
7. **금지 칸·패턴**: 허용 칸 밖은 저장하지 않습니다. 60자 한 줄에도 민감정보가 들어갈 수 있어 `Pii` 전 종류 차단과 금지어 목록을 둡니다. 목록 내용은 기획이 확정해야 합니다.
8. **보존**: FORMER 기관장·REPLACED 사진·SUPERSEDED 값을 무기한 보관합니다. 삭제 주기는 NEXT 35입니다. 사진 폴더는 백업 대상에 넣어야 합니다.
9. **DB 권한**: 앱 계정에 `INST_HEAD_ACT`·`INST_HEAD_LOG`의 UPDATE/DELETE를 주지 않도록 DBA에 전달해야 합니다(27과 같음).
10. **사진의 법적 근거**: 76에서 사용자가 말한 "기관영업 추진·보존 계속" 근거가 초상 사진까지 덮는지 정보보호 확인이 필요합니다.
11. **되돌리기**:
    - 코드: 새 컨트롤러·서비스 파일 삭제, 필터 패턴 한 줄 제거, `AppProperties` 키 제거. 기존 API는 변경이 없습니다.
    - DB: 스크립트 머리말의 DROP·DELETE를 쓰면 데이터가 사라지므로 운영에서는 금지합니다. 운영에서는 API를 비활성화하는 쪽이 안전합니다.

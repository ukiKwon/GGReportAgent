### 3. 지시에서 벗어난 것과 판단
- **시험 번호**: `PrepBoardServiceTest`에는 U7(체크 허용 상태)과 U8(목록 감사 대상)이 이미 있다. 그래서 요청한 U7은 **U12**(`inScope` 조합표), U8은 **U13**(`resolveScope`·`scopeTag`)으로 넣었다. U9~U11도 이미 있어서 다음 빈 번호가 12다. API 시험의 D44~D51과 LEAD2는 겹치지 않아 그대로 썼다.
- **old 코드 차이**: 보고서의 old 코드가 실제와 의미상 같아서 같은 의미로 적용했다. 컨트롤러는 old 코드의 `...` 부분을 실제 줄에 맞춰 편집했다.
- **U12에 조합 1개 추가**: 설계에 없던 "진행 중 건은 옛 담당 이력(ever)을 보지 않는다" 조합을 mine에 한 줄 넣었다.
- **D45 메시지 검사**: 메시지에 "MINE"이나 "all"이 없는지만 확인한다.
- **D47**: 개설 대기 건은 `/prep/open-requests` 호출 뒤 승인하지 않는 방식으로 만들었다.
- **그 밖의 기존 시험**: D1·D3·D4·D6·D24·D27·D29·D30·D32·D33~D41을 읽어 보고 기본 범위로도 통과한다고 판단했다(MEMBER는 확정자, MEMBER2는 활성·옛 담당, LEAD 팀에 MEMBER2가 있음). 실행으로 확인한 것은 아니다.
- **시드 전제**: D48은 시드 전제에 기댄다. 영업팀 전원이 5047192 아래에 수동 지정돼 있고(`011_seed_approvers.sql:15`), 5640327은 영업팀장이며 아래 팀원이 없다는 것이다. 5640327의 역할은 `011_seed_approvers.sql`의 팀장 목록(11행)으로 확인했을 뿐, 역할 칸을 직접 읽지는 않았다. D48이 실패하면 이 전제부터 본다.
- **열린 질문**: 1번(부장의 팀 작업은 부서 작업과 같게)과 2번(확정 취소는 팀·부서 작업에 넣지 않음)은 지시대로 설계 그대로 적용했다.

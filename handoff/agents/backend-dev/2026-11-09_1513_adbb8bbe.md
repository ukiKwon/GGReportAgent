### 기존 `/menus`와 골든 04·05

### 테이블 (COMMON_CODE 재사용 여부)
- **`COMMON_CODE`로도 억지로 담을 수는 있다.**
  - `CODE_GROUP`에 `MENU_ORDER:<부모키>`를 두고 `CODE`에 자식 키, `SORT_NO`에 순번을 담는 방식이다.
  - `SORT_NO NUMBER(4)`, `ENABLED`, `UPDATED_AT/BY`는 이미 있다.
  - 한계: `CODE_GROUP`이 30자라 `MENU_ORDER:`(11자)를 붙이면 부모 키는 19자 이내여야 한다. `CODE_NAME NOT NULL`을 채워야 한다.
  - 016의 "코드 값은 영문 대문자·숫자·밑줄만" 규칙과도 충돌한다(소문자 키).
  - 코드 목록 의미와 섞여 `integrity_check`와 화면 의미가 흐려진다.
- **권장은 전용 테이블 `MENU_ORDER`**(안 B)다. 개념이 다르고 키가 소문자·콜론 등을 쓴다.
  ```
  MENU_ORDER (PARENT_KEY VARCHAR2(30), MENU_KEY VARCHAR2(60), SORT_NO NUMBER(4) NOT NULL,
              UPDATED_AT VARCHAR2(40) NOT NULL, UPDATED_BY VARCHAR2(7),
              PK(PARENT_KEY, MENU_KEY))
  ```
  - FK 없음, CHECK·UNIQUE는 유지 가능.
  - **행이 없으면 코드 기본 순서**를 쓴다. `Menus`의 "행 없음은 아직 정하지 않음" 원칙과 같다.
  - 기본값 복원은 부모 단위 DELETE다. 서버에 DELETE가 없다는 `README`의 설명은 부모 데이터 얘기이고, 설정 테이블이라 허용 가능하다(추측).
  - **번호:** `db/oracle/019_menu_order.sql`과 `db/mysql/019_menu_order.sql` 쌍으로 둔다. 시드는 없다.
  - **이미 적용한 DB:** 019만 한 번 실행하면 된다. 018까지 적용된 DB가 그대로 이어진다. MySQL은 멱등하지 않아도 된다.
  - 번호 규칙대로 018 뒤에 붙이면 된다. 단 `DdlRulesTest`(FK 금지)와 테이블 목록 테스트가 있으면 같이 갱신한다(미확인).

### API (별도 경로)
- `GET /menu-order` — 부모별 `[{parent_key, items:[{menu_key, sort_no}]}]`. 저장분이 없으면 `custom:false`와 기본 순서를 돌려준다.
- `PUT /menu-order` — `{parent_key, items:[menu_key…]}`. 배열 순서가 곧 순번이다(중복 순번 문제를 구조로 막는다).
- `DELETE /menu-order/{parent_key}` — 기본값으로 복원한다.
- 응답 키는 snake_case.

## 4. 권한·검증
- **권한:** 저장·복원은 `AdminGuard.require(req)`로 admin만 허용한다(401/403, DENIED 이력). 기존 `PUT /menus`와 같은 방식이다. 조회는 전원 허용으로 둔다(탭을 그릴 때 필요).
- **한계:** `X-Emp-No` 자기신고라 보안 경계가 아니다. 사번을 알면 누구나 바꿀 수 있고, 앞단 SSO 전까지는 같다. 문서에 "검증됨"이라고 쓰지 않는다.
- **접근 이력:** 본문과 쿼리값은 넣지 않는다.
- **입력 검증:**
  - 알 수 없는 `parent_key`나 `menu_key`는 400. 서버 허용 목록과 대조한다.
  - 중복 키는 400.
  - 항목 수 상한(예: 50)을 둔다.
  - **누락 키:** 부모의 전체 자식 목록과 정확히 같은 집합만 받을지, 누락분은 끝에 덧붙일지 정해야 한다. 권장은 "누락분은 기본 순서로 뒤에 붙임"이다. 새 메뉴가 추가돼도 사라지지 않는다.
  - 오류 메시지에 내부 정보를 싣지 않는다.

## 5. ④ 키 없는 준비중 항목
- **전제:** 서버가 허용할 키 목록(부모→자식)이 필요하다. 하위 메뉴 키 정본이 서버에 없으므로 **서버 상수 `MenuOrders.CHILDREN`을 신설**해야 한다. 프런트와 이중 관리가 되어, 키 이름이 어긋나면 400이 난다.
- **임시 키 규칙(제안):** `<부모키>.<슬러그>` 식으로 `regions.pending_1`처럼 쓴다. 정규식은 `^[a-z][a-z0-9_.]{1,59}$`이고, 의미 있는 슬러그가 정해지면 교체한다. 번호 재사용은 금지하고 한 번 쓴 임시 키는 폐기해도 번호를 비워 둔다.
- **교체 방식:** 임시 키가 정식 키로 바뀌면 기존 행이 고아가 된다. 서버가 목록에 없는 키의 저장 행은 무시하고, 필요하면 마이그레이션 SQL로 UPDATE한다.
- **확정은 프런트·기획 몫이다.** 프런트가 하위 메뉴마다 안정적인 키를 가지고 있는지 확인해야 한다.

## 6. 규모와 위험
- **규모(추정):** 서버는 DDL 2개, DTO·컨트롤러·서비스·매퍼 XML, 상수 클래스, 테스트 약 8~10건이다. 약 0.5~1일이다. 프런트 드래그 UI는 별도다.
- **위험:**
  1. 키 목록의 이중 관리(서버·프런트 불일치).
  2. 역할별 순서가 필요한지 여부. 전사 공통이면 역할 축이 없어 단순하다. 역할별이면 PK에 `ROLE`이 추가돼 규모가 커진다. 기획이 정한다.
  3. 자기신고 인증이라 순서가 임의로 바뀔 수 있다.
  4. 잘못된 순서 저장으로 화면이 혼란스러워질 수 있다. 복원 API로 완화한다.
  5. 순서는 표시용이라 권한(켜짐·꺼짐)과 분리해 유지한다.
- **되돌리는 법:** 엔드포인트 비활성화나 테이블 DROP. `/menus`와 골든에 영향이 없다.

## 7. 테스트
- **깨질 기존 테스트:** `/menus`를 건드리지 않으므로 없다. 테이블 목록이나 DDL 개수를 검증하는 테스트가 있으면 갱신한다(`DdlRulesTest` 확인 필요).
- **추가할 테스트(입력→기대):**
  - 비관리자 PUT → 403, 헤더 없음 → 401.
  - 알 수 없는 키 → 400.
  - 중복 키 → 400.
  - 정상 저장 → 200이고, 이어서 GET이 그 순서를 돌려준다.
  - DELETE 뒤 GET이 기본 순서를 돌려준다.
  - 저장 전 GET은 `custom:false`와 기본 순서다.
  - 골든 04·05 불변.
- **실행:** `cd kgi-ggreport-web && mvn -q -o test`(8080을 같은 `target/`에 쓰고 있으면 재기동).

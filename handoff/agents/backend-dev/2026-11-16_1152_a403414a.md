## 6. ⑥ b안 — ZipGuard 목차 대조를 POI 와 같은 구현(commons-compress)으로

### 6-1. HWPX 두 구현 대조 여부: 판단
**결론: 용도별로 하나씩만 쓴다(2배 비용 없음).**
- xlsx·pptx 는 POI(`ZipSecureFile` = commons-compress `ZipFile`, 메인 javap 확정)가 여니 **commons-compress** 로 대조한다.
- HWPX 는 `FileContentService.extractHwpxText:147` 이 `new java.util.zip.ZipFile(storedPath)` 로 직접 열고, `RfpExtractor.extractHwpx` 는 `HWPXReader.fromFile` 로 연다. 앞의 것은 java.util.zip 이 확정이고 **그쪽은 현재 `verifyDirectory` 가 이미 같은 구현**이다.

## 7. 보안·위험·되돌리는 법
- 인증은 `X-Emp-No` 류 자기신고(`SystemUserInterceptor`)이며 이 패치는 접근 통제를 바꾸지 않는다. `/api/files/search` 의 호출 인증 여부는 보지 못했다.
- ①: `content` 키를 읽던 호출자는 조용히 깨진다(Q2). 응답에서 본문이 빠져 노출·부하(파일 N회 읽기)가 줄어든다.
- ③: 비밀번호를 건 정상 엑셀·ppt 도 거부된다(정책, Q1). 암호 xls(BIFF RC4)는 zip 이 아니므로 거부하지 않는다. 로그에는 코드(`ENCRYPTED`/`BROKEN`)만 남긴다. 업로드 화면이 거부 사유를 사용자에게 어떻게 보이는지는 보지 못했다.
- ⑥: commons 로 읽으면 같은 파일의 판정이 달라질 수 있는데, 달라지는 쪽은 BROKEN(거부)이 되도록 짰다. 정상 xlsx·pptx 가 commons 에서 거부되면 시험이 잡는다. 대용량 시 메모리는 목록 생성 정도만 늘어난다.
- 되돌리기: ①②③⑥ 각 diff 는 독립이다. ① 은 컨트롤러·DTO·시험 3개 파일 원복, ③ 은 `FileContentService.guardZip`·`PptExtractor` 두 호출부만 원복해도 되고 ZipGuard 메서드는 남겨도 무해하다. ⑥ 은 `checkOoxmlFile` 호출을 `checkUploadFile` 로 되돌리면 JDK 경로로 돌아간다. pom 의 commons-compress 직접 선언은 지워도 전이 의존으로 컴파일된다.

### 3-0. 사용자 확정 규칙의 서버 표현 (팀 결정 포함)

| 규칙 | 서버 동작 |
|---|---|
| 정본 = 확정 판 | 확정 = 헤더의 `CONFIRMED_VER`·`CONFIRMED_SHA256`이 가리키는 판. 판 행은 추가만 하고 바꾸지 않는다. docx는 그 판의 JSON으로 매번 다시 만든다(RENDER_VER 분기). |
| 사실 칸은 원 화면 하나로 씀 | FACT 칸이 PUT `/draft`에 들어오면 400 `FIELD_READONLY`. 값은 서버가 원본에서만 채운다. [고치기] → 원 화면 편집 창 → 저장 → 화면이 POST `/prefill {keys:[그 칸]}`. |
| 낡은 칸 있으면 확정 막음 | confirm에서 `stale_keys`가 비어 있지 않으면 409 `FORM_STALE`과 칸 키 목록. POST `/prefill {keys: 없음}` 한 번으로 FACT 칸을 모두 다시 채운다. 서술 칸은 보존한다. |
| 승인 요청 중 수정 불가 | 모든 쓰기는 사전준비 상태 `IN_PROGRESS`에서만. 아니면 409 `FORM_LOCKED`(state_cd 포함). 회수하면 IN_PROGRESS로 돌아오므로 그때 확정 취소 → 고침 → 재확정. |
| 승인 뒤 고정 + '바뀜' | WRITABLE·WRITING에서는 쓰기 409. GET은 `confirmed_changed_keys`(확정 판 기준 원본 바뀜)를 낸다. |
| 확정된 양식 고치기 | 확정 상태에서 draft·prefill은 409 `FORM_CONFIRMED`. 먼저 [확정 취소](사유 1~200)를 해야 한다. **팀 결정**: 확정 취소 사유 공개 규칙이 성립하려면 명시적 취소 행위가 있어야 하고, 확정 판이 몰래 흔들리지 않는다. |
| 쓰기 권한 | 영업팀·영업팀장 **이면서** 그 건의 활성 담당자. 확정 취소만 추가로 영업팀장(비담당 포함)도 할 수 있다. 기존 UNCONFIRM 권한(1195)과 같은 모양이다. |
| 담당 디자이너 | 추정 표를 포함해 전부 열람하고 docx도 받는다. 쓰기는 403. |
| 전산팀(·예산팀) | 활성 담당자라면 화면 열람만 된다. docx는 403(팀 결정, 넓히기 쉬움). 쓰기는 403. |

쓰기 공통 틀(@Transactional):
1. `requireWriter(me, bid)`: 활성 담당 ∧ (MEMBER_ROLE ∨ LEAD_ROLE), 아니면 403.
2. formCd가 `INST_SUMMARY`가 아니면 404.
3. `prepMapper.selectStateForUpdate(bid)`: null이면 404, IN_PROGRESS가 아니면 409 `FORM_LOCKED`(+state_cd). 잠금 순서는 BID_PREP → BID_PREP_FORM(FOR UPDATE).
4. 헤더가 없고 base_ver==0이면 INSERT(CUR_VER 0). BID_PREP 행 잠금이 직렬화하므로 경합은 없고, `DuplicateKeyException`은 방어로 409 VER_CHANGED.
5. base_ver ≠ CUR_VER면 409 `VER_CHANGED`. CONFIRMED_VER ≠ null이면(draft·prefill) 409 `FORM_CONFIRMED`.
6. 새 내용을 만든다. 정규 JSON 바이트가 MAX_CONTENT_BYTES를 넘으면 400 `CONTENT_TOO_LARGE`. 판 수가 MAX_VERSIONS 이상이면 409.
7. `insertVer(next=CUR_VER+1, kind, base, TPL_VER, RENDER_VER, json, sha, bytes, …)` → `bumpCurVer(bid, form, base, next)`가 1행이 아니면 409 VER_CHANGED.
8. 응답은 `view()`와 같은 모양이다(왕복을 줄인다).

- **saveDraft**:
  - 본문의 fields·lists·tables를 템플릿 키로 하나씩 검사한다.
    - 모르는 키는 400 `UNKNOWN_KEY`(keys). FACT 키는 400 `FIELD_READONLY`(keys).
    - 글자는 `checkedText(raw,max,label,required=false)`. 400·422를 잡아 `key`를 붙여 다시 던지고, 값은 싣지 않는다.
    - LIST·lines 항목에 '\n'이 있으면 400.
    - years는 `Groups.yearColumns(from,to)`를 부르고, `IllegalArgumentException`이면 400 `BAD_YEARS`(고정 문구). 연도 키가 from~to 밖이면 400.
  - 새 내용 = 이전 판의 FACT 칸과 `tables.biz.src`를 그대로 + 본문의 편집 칸 전체(빠진 편집 칸은 빈 값). KIND=DRAFT.
  - 저장은 전체 교체(patch가 아님)이고, 판 번호 비교로 덮어쓰기를 막는다.
- **prefill**:
  - keys가 null이면 FACT 4칸 전부 + 씨앗(biz 행이 비었을 때만, years가 null일 때만).
  - keys를 주면 그 칸만. 허용값은 FACT 키, "biz", "years"이고, 명시한 "biz"는 행을 교체한다. 밖의 값은 400.
  - 결과가 이전 판과 글자까지 같으면 새 판을 만들지 않고 `changed:false`로 낸다.
  - KIND=PREFILL. src.at = 지금 시각.
- **confirm**:

- **unconfirm**:

## 5. 보안·위험·되돌리는 법

**403 경로**
- 쓰기의 역할·담당 검사가 건 조회와 판 번호 비교보다 먼저 온다. 그래서 비담당은 건이 있는지 없는지와 관계없이 403이다.
- 읽기는 비대상이면 404로 존재를 숨긴다.
- docx는 읽기 대상 중 영업·팀장·부장·디자이너만 받는다.
- 모든 거부는 BID_PREP_ACT(DENIED·HIDDEN·BLOCKED·INVALID)와 접근 이력 DENIED에 남는다. 사번 없는 401은 접근 이력에만 남는다.

**감사**
- 행위 코드는 FORM_VIEW, FORM_HISTORY, FORM_PREFILL, FORM_SAVE, FORM_CONFIRM, FORM_UNCONFIRM, FORM_DOCX, FORM_DRAFT_DOCX다(접두어 `FORM_` 예약).
- 성공한 읽기와 파일은 응답 전에 기록하고, 기록이 실패하면 500이며 파일은 나가지 않는다.
- 업무 이력(BID_PREP_LOG)에는 확정과 확정 취소만 남긴다. 저장 판 이력은 VER 표 자체다.

**자기신고의 한계**
- 사번·화면·버튼은 모두 X-Emp-No·X-Screen-Id·X-Button-Id 자기신고다.
- 이 권한 검사는 업무 실수 방지이지 사칭 방지가 아니다. `*_VERIFIED`에는 사실만 적는다.
- 확정본의 무결성(SHA)은 DB 직접 수정을 드러낼 뿐, 누가 눌렀는지를 증명하지 않는다.

**민감 정보**
- 내부 추정치가 CONTENT_JSON에 평문으로 남는다. DB 백업 범위와 접근 권한은 DBA 몫이다.
- 내려받은 파일의 보호는 회사 DRM에 맡긴다(사용자 11-19).

**미리 채움의 감사 공백**
- 기관장 이름이 양식에 들어갈 때 INST_HEAD_ACT에는 남지 않고 BID_PREP_ACT FORM_PREFILL·FORM_VIEW로만 남는다.
- 디자이너도 이 경로로 기관장 이름(공개 정보)을 보게 된다. security 판단이 필요하다(이관).

**위험**
- 판이 쌓인다(저장마다 최대 120KB). 상한 2000판이고, 화면은 자동 저장하지 않는다(이관). 운영에서는 건당 수 MB 수준이다.
- 표 속 표가 쪽을 넘을 때 Word에서 어떻게 보이는지는 실물로 확인해야 한다.
- 049가 051보다 늦게 적용되는 번호 역전: 헤더에 밝혔다. DBA 적용 목록에서 빠지지 않게 PM이 표시해 달라.

**되돌리기**
- 코드: 새 파일과 필터 두 줄뿐이라 revert 한 번이면 된다.
- DB: 049 헤더의 되돌리기를 쓴다(데이터 소멸). 운영에서는 DROP하지 말고 서버 revert만 한다. 표가 남아도 무해하다.

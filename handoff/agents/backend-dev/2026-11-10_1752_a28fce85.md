# 추가 요구 7) 배정 이력의 HANDOVER 행 가림 (security 하-3, 기존 패치 1~6에 추가)

앞서 보낸 보고서의 §3~§7에 이어 붙이는 패치다. 새 SQL·DB 스크립트는 없다. 읽기 전용 설계안이라 컴파일과 테스트는 돌리지 못했다.

## 규칙
- HANDOVER 행은 **그 입찰 건의 현재 담당자**(`mapper.countActive`로 판정하는 `isActiveAssignee`), **활성 영업팀장**, **활성 영업부장**에게만 보인다. 그 외 영업팀원 등에게는 응답에서 뺀다.
- ASSIGN·ADD·RELEASE 등 다른 행은 그대로다.
- "활성"은 컨트롤러의 `guard.requireActiveUser`가 이미 보장한다(비활성이면 403). 그래서 서비스는 `me`의 역할과 담당 여부만 본다.
- "영업팀장"은 이 입찰 건에 배정되지 않은 팀장도 포함한다. 사용자 문구("활성 영업팀장")를 글자 그대로 따랐다.
- 인증은 `X-Emp-No` 자기신고다. 이 규칙은 존재 은닉을 위한 업무 규칙이지 사칭 방지가 아니다.

## 기존 테스트 영향
`BoardMaterialApiTest.담당에서_빠진_사람의_작성본은…`은 `MEMBER2`(그 건의 현재 담당자)로 이력을 조회하고 HANDOVER가 보이기를 기대한다. MEMBER2는 담당자이므로 그대로 통과한다. 다른 테스트의 이력 조회는 HANDOVER를 기대하지 않는다.

## 새 테스트 — `BoardMaterialApiTest` (인계 구역에 추가)
```java
    @Test
    public void 배정_이력의_인계_행은_담당자_영업팀장_영업부장에게만_보이고_비담당_영업팀원에게는_빠진다() throws Exception {   // security 하-3
        String bc = newCase();
        assign(bc, MEMBER, MEMBER2);
        create(MEMBER, bc, 2026);
        long req = requestChange(LEAD, bc, new String[]{M3}, new String[]{MEMBER});
        assertEquals(200, decide(HEAD, req).getResponse().getStatus());
        assertEquals(1, count("SELECT COUNT(*) FROM BID_ASSIGN_LOG WHERE BID_CASE_ID=? AND ACTION_CD='HANDOVER'", bc));
        // 보이는 사람: 현재 담당자(남은·새로 추가된), 영업팀장, 영업부장
        for (String emp : new String[]{MEMBER2, M3, LEAD, HEAD}) {
            MvcResult r = read("/bidcases/" + bc + "/assignments/history", emp);
            if (r.getResponse().getStatus() != 200) {
                continue;   // 부장이 이 API 의 영업팀 한정에 걸리면 403 — 그 판정은 이번 변경이 아니다
            }
            assertTrue(emp, hasAction(json(r), "HANDOVER"));
        }
        assertTrue(hasAction(json(read("/bidcases/" + bc + "/assignments/history", MEMBER2)), "HANDOVER"));
        assertTrue(hasAction(json(read("/bidcases/" + bc + "/assignments/history", LEAD)), "HANDOVER"));
        // 안 보이는 사람: 이 건의 담당이 아닌 영업팀원(M4), 담당에서 빠진 사람(MEMBER)
        for (String emp : new String[]{M4, MEMBER}) {
            MvcResult r = read("/bidcases/" + bc + "/assignments/history", emp);
            assertEquals(emp, 200, r.getResponse().getStatus());
            assertFalse(emp, hasAction(json(r), "HANDOVER"));
            assertTrue(emp, hasAction(json(r), "ASSIGN"));   // 다른 행은 그대로
            assertFalse(emp, text(r).contains(M3 + "\",\"from"));   // 인수자·해제자가 다른 경로로 새지 않는다(HANDOVER 행째 없음)
        }
    }

    private static boolean hasAction(JsonNode rows, String action) {
        for (JsonNode n : rows) {
            if (action.equals(n.path("action_cd").asText())) {
                return true;
            }
        }
        return false;
    }
```
- 부장 조회는 `r.getResponse().getStatus() != 200`일 때 건너뛰므로, 부장이 이 API에서 403이어도 테스트가 깨지지 않는다. 부장 200 여부를 단정하려면 호출자가 현재 동작을 확인한 뒤 단정으로 바꾼다.
- `MEMBER`는 담당에서 해제된 사람이다. 이력 조회는 `requireSalesTeam`만 통과하면 200이므로, 해제된 사람은 HANDOVER 행을 못 본다. 이 점이 규칙의 핵심 효과다.
- M4(`2189346`)는 이 건의 담당자가 아니다. 위 `assign`·`requestChange`에서 M4를 쓰지 않았다.
- `assertFalse(... text.contains(M3 + "\",\"from"))` 줄은 약한 보조 단정이다. 이상하면 지워도 된다.

## 응답 계약·프런트
- `GET /bidcases/{id}/assignments/history`의 키·모양은 그대로다. 비담당 영업팀원과 담당에서 해제된 사람의 응답에서 `action_cd=HANDOVER` 행이 빠진다.
- 배열 길이가 사람마다 달라질 수 있다. 화면이 "이력 n건"을 서버 길이에 의존하면 그 표시가 달라지는 것을 안다.
- 골든 04·05, `/menus`, `/approvals`는 영향이 없다.

## 보안·되돌리기
- 403·404 경로, 접근 이력, 감사는 변하지 않는다. 이 필터는 조회 응답에서만 행을 뺀다.
- 남는 틈: 이력 조회가 `requireSalesTeam`을 통과하는 비담당자는 ASSIGN·ADD·RELEASE 행으로 배정 변동은 계속 볼 수 있다. 자료 존재 여부만 가려진다. 결정 범위(HANDOVER만)와 일치한다.
- 되돌리기: 위 `if (!seesHandover …) continue;`와 그 앞 4줄을 지운다.

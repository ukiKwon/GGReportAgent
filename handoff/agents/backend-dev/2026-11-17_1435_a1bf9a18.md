## 2. 원인 (근거)
**확인한 사실**
- 세 시험 클래스(InboxApiTest:52-54, InboxExtCheckApiTest:46-48, InboxTxRollbackTest:38)가 모두 같은 고정 폴더 `target/inbox-test/{inbox,batches,rfp,ext_check}`를 씁니다. 이 경로는 src/test/resources/application.properties:59-62에 박혀 있습니다.
- 두 시험은 @Before에서 폴더 전체를 지우고 다시 만듭니다(InboxApiTest:65-71, InboxExtCheckApiTest:58-62). 같은 JVM에서 차례로 돌면 서로를 덮지 않습니다.
- 서비스는 호출 때마다 `properties.getXxxRoot()`를 읽습니다(InboxService:80,266,304, ExtCheckImporter:241,310). 그래서 시험에서 AppProperties 값을 바꾸면 바로 적용됩니다.
- `Menus`나 DB 상태는 원인이 아닙니다. 시험은 @Transactional 롤백입니다. InboxTxRollbackTest는 직접 정리합니다. static 상태와 @DirtiesContext는 없습니다.
- 증상은 `rfp_files` 크기 0입니다. 정상 경로에서는 `moveAttachments`가 항상 항목을 더합니다(InboxService:287). 크기 0이면 import가 오류(422·500) JSON을 돌려준 것이고, 이 시험 한 건만 깨진 것으로 보아 사번·권한 문제도 아닙니다. 이 시험만 파일 이동(`Files.move`, InboxService:280)과 첨부 파일 존재 검사에 의존합니다.

**가설 (우선순위순, 코드만으로는 확정 못 함)**
1. 같은 target/inbox-test를 다른 프로세스가 동시에 지웠을 가능성입니다. 다른 세션이나 에이전트가 `mvn test`를 돌렸거나, 8080 서버와 target/을 공유했을 수 있습니다. CLAUDE.md §6이 이미 경고하는 상황입니다. 이때 방금 쓴 `files/N-3_*.pdf`가 사라지면 검증 422나 이동 500이 나는데, 이는 증상과 맞고 "전체 실행에서만, 한 번만, 단독은 통과"와도 맞습니다.
2. Windows의 삭제 대기 폴더와 백신·인덱서 잠금입니다. InboxApiTest에만 AccessDenied 재시도가 있고(:74-92), InboxExtCheckApiTest:58-62에는 재시도가 없습니다. 그리고 `Files.move`(InboxService:280)는 방금 쓴 파일을 옮기다 일시 잠금에 걸릴 수 있습니다. 고정 이름 폴더를 지웠다 다시 만드는 구조가 이 위험을 키웁니다.
3. 실행 순서가 시험 간섭의 직접 원인이라는 증거는 코드에서 못 찾았습니다. ExtCheck 시험이 inbox/rfp를 오염시키는 경로는 없습니다. ExtCheck는 rfp 폴더를 건드리지 않고, 잔여물은 InboxApiTest의 @Before가 지웁니다.

가설 1·2는 시험마다 실행마다 고유한 폴더를 쓰면 함께 없어집니다. 운영 코드는 바꾸지 않아도 됩니다.

## 3. 구현안 (시험만, 운영 코드 무변경)
AppProperties는 setter가 있는 싱글턴 빈이고 호출 때 값을 읽습니다. 그래서 **@TestPropertySource를 쓰지 않습니다**(컨텍스트가 둘이 되어 DDL이 중복됩니다, InboxApiTest:43 경고). 대신 @Before에서 빈 값을 고유 폴더로 바꾸고 @After에서 되돌립니다.

**새 파일** `kgi-ggreport-web/src/test/java/com/kbstar/kgi/ggreport/web/web/InboxTestRoots.java`
```java
package com.kbstar.kgi.ggreport.web.web;

import com.kbstar.kgi.ggreport.web.config.AppProperties;

import java.io.IOException;
import java.nio.file.FileVisitResult;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;
import java.nio.file.SimpleFileVisitor;
import java.nio.file.attribute.BasicFileAttributes;

/**
 * 반입 계열 시험이 시험마다(실행마다) 고유한 폴더를 쓰게 한다 — 고정 폴더 target/inbox-test 를 여러 시험 클래스·
 * 다른 mvn 실행이 같이 쓰며 서로 지우던 것을 끊는다. AppProperties 싱글턴 값을 바꿨다가 close() 에서 되돌린다.
 * (@TestPropertySource 는 컨텍스트가 둘이 되어 DDL 이 중복되므로 쓰지 않는다.)
 */
final class InboxTestRoots {

    final Path base, inbox, rfp, batches, ext;
    private final AppProperties props;
    private final String oInbox, oRfp, oBatches, oExt;

    private InboxTestRoots(AppProperties props, Path base) throws IOException {
        this.props = props;
        this.base = base;
        this.inbox = Files.createDirectories(base.resolve("inbox"));
        this.rfp = Files.createDirectories(base.resolve("rfp"));
        this.batches = Files.createDirectories(base.resolve("batches"));
        this.ext = Files.createDirectories(base.resolve("ext_check"));
        oInbox = props.getInboxRoot();
        oRfp = props.getRfpRoot();
        oBatches = props.getBatchesRoot();
        oExt = props.getExtCheckRoot();
        props.setInboxRoot(inbox.toString());
        props.setRfpRoot(rfp.toString());
        props.setBatchesRoot(batches.toString());
        props.setExtCheckRoot(ext.toString());
    }

    static InboxTestRoots open(AppProperties props) throws IOException {
        Path parent = Files.createDirectories(Paths.get("target", "inbox-test-run").toAbsolutePath());
        return new InboxTestRoots(props, Files.createTempDirectory(parent, "r-"));
    }

    void close() {
        props.setInboxRoot(oInbox);
        props.setRfpRoot(oRfp);
        props.setBatchesRoot(oBatches);
        props.setExtCheckRoot(oExt);
        deleteQuietly(base);          // 못 지워도 시험은 실패시키지 않는다(고유 폴더라 다음 시험에 영향 없음)
    }

    static void deleteQuietly(Path p) {
        try {
            if (!Files.exists(p)) {
                return;
            }
            Files.walkFileTree(p, new SimpleFileVisitor<Path>() {
                @Override public FileVisitResult visitFile(Path f, BasicFileAttributes a) {
                    try { Files.delete(f); } catch (IOException ignore) { }
                    return FileVisitResult.CONTINUE;
                }
                @Override public FileVisitResult postVisitDirectory(Path d, IOException e) {
                    try { Files.delete(d); } catch (IOException ignore) { }
                    return FileVisitResult.CONTINUE;
                }
            });
        } catch (IOException ignore) { }
    }
}
```

## 4. 테스트
- 깨질 기존 시험은 없을 것으로 봅니다. 앞서 말한 InboxExtCheckApiTest 후반부의 경로 문자열 단언만 확인이 필요합니다.
- 추가 시험은 불필요합니다. 격리 자체가 대책입니다.
- 호출자가 실행할 명령입니다(8080 서버가 target/을 쓰지 않을 때, 한 세션에서만 실행).
  - `cd kgi-ggreport-web && mvn -q -o test -Dtest='InboxExtCheckApiTest,InboxApiTest,InboxTxRollbackTest'`
  - 순서 반대: `-Dtest='InboxApiTest,InboxExtCheckApiTest'` 및 `-Dsurefire.runOrder=reversealphabetical`
  - 전체: `mvn -q -o test`(380건 유지). 이어서 `target/inbox-test-run/`에 잔여 폴더가 남지 않았는지 확인합니다.
- **동시 실행 검증**(가설 1의 확인): 서로 다른 두 세션이 같은 모듈에서 같은 시험을 동시에 돌려도 통과해야 합니다. 이전에는 한쪽이 깨졌을 것입니다. 다만 동시에 `mvn`을 돌리면 target/classes 충돌이 생기므로 권하지 않습니다. 실제로는 반복 실행(`for i in 1..5`)으로 확인하는 편이 안전합니다.

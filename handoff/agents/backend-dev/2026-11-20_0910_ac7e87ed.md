## 1) close_reason 삼항식: 정리 가능, 동작 변화 없음

- **디자이너 차단은 그대로입니다.** 차단은 266행의 break와 `last_closed` 자체를 비우는 동작이 맡습니다. `PlanCollectApiTest:387-388,406`이 이를 확인합니다.

## 2) PLAN_COLLECT_REQ(CLOSED_AT) 인덱스: 지금은 불필요 (판정: 보류)

- **쿼리**: `selectRecentClosed`는 `WHERE OPEN_INST_ID IS NULL AND CLOSED_AT >= #{since} ORDER BY INSTITUTION_ID, REQ_SEQ DESC`입니다(`PlanCollectMapper.xml:48-50`).
- **기존 인덱스**: `PK(INSTITUTION_ID, REQ_SEQ)`, `UQ_PCR_KEY`, `UQ_PCR_OPEN`, `IDX_PCR_STATUS(STATUS_CD, REQUESTED_AT)`가 있습니다(045 mysql 33~36행, oracle 47~51행). CLOSED_AT이나 OPEN_INST_ID IS NULL로 탈 수 있는 인덱스는 없습니다.
- **규모 추정**: 닫힌 건은 누적되지만 사업계획 수집 요청은 기관당 가끔 1건입니다. 기관이 수백 곳이고 요청이 수년간 쌓여도 수천 행 정도로 봅니다. 이 숫자는 추정이며 실측하지 않았습니다.
- **정렬**: ORDER BY가 `INSTITUTION_ID, REQ_SEQ DESC`라 PK 순서와 맞습니다. 옵티마이저가 PK를 스캔하며 필터할 수 있어 filesort도 필요 없을 수 있습니다.
- **호출 빈도**: 기관 사업계획 화면 상태 조회 때만 호출합니다. 수천 행 풀스캔은 밀리초 단위입니다.
- **판정**: 인덱스는 필요하지 않습니다. 인덱스를 더하면 INSERT·UPDATE(닫을 때)에 쓰기 비용이 늘고, 마이그레이션 번호와 Oracle DBA 적용 부담이 생깁니다.
- **재검토 기준**: 닫힌 행이 대략 10만 건을 넘거나 status 응답이 느려지면 다시 봅니다. 아래는 그때를 위한 초안입니다. 번호는 NNN으로 비우고 외래키는 쓰지 않았습니다.

**초안 (현재는 적용 비권장)**
```sql
-- db/mysql/NNN_plan_collect_closed_idx.sql  (한 번만 실행)
CREATE INDEX IDX_PCR_CLOSED ON PLAN_COLLECT_REQ (CLOSED_AT);
-- 되돌리기: DROP INDEX IDX_PCR_CLOSED ON PLAN_COLLECT_REQ;

-- db/oracle/NNN_plan_collect_closed_idx.sql  (정본, 적용은 DBA)
CREATE INDEX IDX_PCR_CLOSED ON PLAN_COLLECT_REQ (CLOSED_AT);
-- 되돌리기: DROP INDEX IDX_PCR_CLOSED;
```
- OPEN_INST_ID는 NULL이 열린 건이라 NULL은 인덱스에서 제외됩니다. Oracle B-tree는 NULL만 있는 행을 담지 않으므로, 이 쿼리의 `IS NULL` 조건은 인덱스로 풀지 못합니다. CLOSED_AT 범위만 인덱스를 탑니다.
- 단일 칸 CLOSED_AT 인덱스는 열린 건(CLOSED_AT NULL)을 담지 않으므로 오히려 닫힌 건만 가려내 줍니다.
- 045는 적용 후 수정 금지(체크섬)이므로, 필요해지면 반드시 새 번호 파일로 추가합니다.

## 2. 요구/원인 요약 (근거)
- v1은 `records[]`에 `notice_id`·`title`·`evidence`를 필수로 요구한다(`contract/batch_schema.py:25`, `SCHEMA.md` §④ 필드 규칙). 그래서 '찾지 못함·조회 실패·보도'는 records에 못 들어간다.
- 더 중요한 점: records를 반입하면 `bid_cases`의 일정(`expected_date`·`schedule_confidence`)을 갱신한다(`SCHEMA.md` §⑥-4). 외부 확인은 지도 색·예정일을 바꾸면 안 된다. 그래서 새 결과를 records에 섞지 말고 별도 배열 `checks[]`로 분리하는 것이 핵심이다.
- 하위 호환: `SCHEMA.md` §⑨는 선택 필드 추가에 버전을 올리지 않고, 모르는 필드는 무시한다고 정한다. 그래서 `checks[]`는 `schema_version: 1` 그대로 둘 수 있다.
  - 구 서버는 `checks`를 조용히 무시한다. 즉 배치는 통과하지만 결과가 저장되지 않는다.
  - 이를 막으려면 `schema_minor: 1`을 두고, 신 서버가 `checks`가 있는데 minor를 모르는 상황을 경고하게 하는 방법이 있다(§4 질문).
- 기관 id는 망 밖에서 발급하지 않는다(`SCHEMA.md` §⑩-2). 결과는 `기관명 + region_code`로 보내고, 서버가 `selectIdByName`처럼 id를 찾는다.
- 검사 코드는 파이썬(`contract/`)과 자바(`BatchSchema.java`) 두 곳에 있다. 둘을 같이 고쳐야 한다.

### 3-2. 반입 개인정보 재검사
- **재사용**: `Pii.scanLoose(text)`가 휴대폰·주민·외국인등록·카드·이메일을 잡는다(`Pii.java:119`). manifest의 모든 문자열 값(제목·보도 제목·basis 등)에 적용한다.
  - 하나라도 걸리면 그 check 한 건을 거부하고 배치에는 오류를 낸다. 값은 로그에 쓰지 않고 종류와 건수만 쓴다. `Pii.Finding`은 이미 마스킹된 값이다.
  - 마스킹된 이메일은 `a***@x.kr` 모양이다. 정규식상 `*`가 로컬파트 문자 집합에 없어 재검출되지 않는 것으로 읽힌다. 단위 테스트로 확인이 필요하다.
- **유선 전화는 `Pii`에 없다.** `foldLoose`는 026 기관장 정보용이다. 담당자 유선은 "마스킹 허용"이므로 `02-1234-5678`처럼 끝 4자리를 노출하는 것도 막을지는 정책 질문이다(§4).
  - 최소 규칙은 "마스킹 패턴(`****`)이 아닌 유선 번호가 있으면 거부"이다. 휴대폰은 마스킹 여부와 상관없이 존재하면 거부한다. 사용자가 "무조건 삭제"라고 했기 때문이다.
- **첨부 본문 검사는 서버가 못 할 수 있다.** JDK 8 서버에 PDF·HWP 파서가 있는지 모른다. 이 부분이 가장 큰 열린 문제다.
  - 안 A: 외부 쪽이 첨부마다 평문 추출본 `files/c-0001_공고문.txt`를 함께 내고, 서버는 이 txt에만 `scanLoose`를 돌린다. 추출본과 실제 PDF가 같다는 보증은 없다.
  - 안 B: 서버는 첨부를 검사하지 않고 `redaction`만 기록한다. 이 경우 "서버가 검증했다"고 쓰면 안 된다. 외부 자기신고일 뿐이다.
  - 안 C: 외부 쪽이 PDF를 이미지로 만들어 연락처 영역을 지운다. 서버는 크기·형식만 본다.
- **첨부 제한(제안값, 결정은 이관)**: 확장자는 `pdf`·`hwp`·`hwpx`·`txt`만 허용한다. 파일당 20 MiB, check당 5개, 배치 합계 200 MiB.
  - 서버는 첫 바이트(매직 넘버)도 확인한다: PDF는 `%PDF`, HWPX는 zip. 확장자와 다르면 거부한다.
  - `sha256`이 맞지 않으면 거부한다. 이름 충돌은 `check_id` 접두로 막는다(`InboxService`의 `REPLACE_EXISTING` 주의).
  - 실행 파일·매크로 파일(`docm` 등)·압축 파일은 거부한다. 기존 `precheck`의 심볼릭 링크 거부는 그대로 쓴다.
- **실패 시**: 기존 `importBatch`와 같은 순서다. 먼저 검증한다. 오류가 있으면 422에 `errors`만 돌려주고 DB·파일은 건드리지 않는다. 배치는 inbox에 남는다.
  - 개인정보 거부만 "해당 check 제외 후 나머지 반입"으로 할지, 배치 전체 거부로 할지는 질문이다. 기본은 전체 거부(보수적)다.
  - 오류 문구에는 경로·값을 싣지 않는다(NEXT 72 규칙).
- **접근 이력**: 반입 호출은 기존 `Actor`(자기신고)를 쓴다. 이력에는 batch_id·건수만 남기고 본문·값은 남기지 않는다.

### 3-3. 서버 저장 — DDL 초안 (적용 아님)
새 테이블이 필요하다. `bid_cases`를 재사용하면 일정을 오염시킨다. 두 표로 나눈다.

`db/mysql/041_external_check.sql`(관례에 따라 외래키·CHECK 없음, 멱등하지 않음, 040 다음에 한 번):
```sql
CREATE TABLE EXT_CHECK (
    INSTITUTION_ID  VARCHAR(64)  NOT NULL,
    CHECKED_AT      VARCHAR(40)  NOT NULL,   -- ISO 8601 +09:00
    SOURCE_KIND     VARCHAR(10)  NOT NULL,   -- notice / press
    SOURCE_SLUG     VARCHAR(30)  NOT NULL,
    STATUS_CD       VARCHAR(10)  NOT NULL,   -- found / not_found / error
    ERROR_CD        VARCHAR(30),
    MATCH_CONF      VARCHAR(5),              -- high / mid / low
    MATCH_BASIS     VARCHAR(200),            -- 코드 쉼표 구분
    NOTICE_NO       VARCHAR(60),
    NOTICE_TITLE    VARCHAR(300),
    POSTED_AT       VARCHAR(10),
    DEADLINE_AT     VARCHAR(10),
    NOTICE_URL      VARCHAR(500),
    BATCH_ID        VARCHAR(80)  NOT NULL,
    CHECK_ID        VARCHAR(40)  NOT NULL,
    IMPORTED_AT     VARCHAR(40)  NOT NULL,
    PRIMARY KEY (INSTITUTION_ID, CHECKED_AT, SOURCE_KIND, SOURCE_SLUG),
    KEY IDX_EC_LATEST (INSTITUTION_ID, SOURCE_KIND, CHECKED_AT)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE EXT_CHECK_FILE (
    INSTITUTION_ID VARCHAR(64) NOT NULL,
    CHECKED_AT     VARCHAR(40) NOT NULL,
    SOURCE_KIND    VARCHAR(10) NOT NULL,
    SOURCE_SLUG    VARCHAR(30) NOT NULL,
    FILE_SEQ       SMALLINT    NOT NULL,
    STORED_PATH    VARCHAR(300) NOT NULL,   -- 리포 상대, corpus/ext_check/ 아래
    SHA256         VARCHAR(64)  NOT NULL,
    FILE_SIZE      BIGINT       NOT NULL,
    PRIMARY KEY (INSTITUTION_ID, CHECKED_AT, SOURCE_KIND, SOURCE_SLUG, FILE_SEQ)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
-- 되돌리기: DROP TABLE EXT_CHECK_FILE; DROP TABLE EXT_CHECK;
```
- Oracle 쌍 `db/oracle/041_external_check.sql`은 정본으로 쓴다. `VARCHAR2`, `NUMBER(19)`, 한글 `COMMENT`를 쓰고 적용은 DBA 몫이다. 일부러 MySQL 전용 구문(`KEY`·`ENGINE`)을 피했으므로 컬럼 구성은 같다.
- 보도 본문 칸은 없다. `낮음` 매칭은 저장하지 않고 배치 응답의 건수로만 돌려준다. `mid`는 저장하되 표시는 상세에서만 한다.
- 조회(최신 1건, 높음 공고만 행에 표시) 형태. 이식 가능한 NOT EXISTS 형태다:
```sql
SELECT e.* FROM EXT_CHECK e
 WHERE e.INSTITUTION_ID = ? AND e.SOURCE_KIND = 'notice'
   AND NOT EXISTS (SELECT 1 FROM EXT_CHECK n WHERE n.INSTITUTION_ID = e.INSTITUTION_ID
                    AND n.SOURCE_KIND = 'notice' AND n.CHECKED_AT > e.CHECKED_AT)
```
  - 현황판 행에는 `STATUS_CD='found' AND MATCH_CONF='high'`이거나 `not_found`/`error`의 시각만 보인다. 응답 키는 `external_check: {status, checked_at}` 같은 snake_case로 쓴다. `/menus` 계약은 건드리지 않는다.
  - 'error'가 이전 'found' 표시를 덮어쓸지는 질문이다(§4).
- 첨부는 `corpus/ext_check/<기관id>/<check_id>_…`에 두고 `corpus/rfp/`로 보내지 않는다. 그렇지 않으면 `institutions.rfp_path`(제안서 근거)를 덮어쓴다. `moveAttachments`는 이 용도에 쓰면 안 된다.
- 이미 적용한 DB는 040 다음에 041을 한 번 더 돌린다. 013만 멱등이므로 041은 두 번 돌리면 실패한다.

- 인증은 `X-Emp-No` 자기신고다. 반입 권한은 기존 Inbox 엔드포인트의 허용 역할을 그대로 쓰고, 403 경로는 기존 것을 재사용한다(이번 설계에서 새로 만들지 않음).

- 되돌리기: 041의 DROP 두 줄이다. 코드는 `checks[]`를 무시하면 v1과 동일하게 동작한다.

## 6. 이관 메모
- [이관: 기획] 담당자 유선 번호 마스킹 허용 범위(끝 4자리 노출 가능 여부)와, 개인정보 1건 발견 시 그 건만 제외할지 배치 전체를 거부할지 — 기다리는 것: 정책 확정 — 근거: §3-2.
- [이관: 기획] 최신 결과가 `error`(조회 실패)일 때 이전 `found`의 표시를 유지할지, 행에 '조회 실패'로 덮을지 — 근거: §3-3 조회.
- [이관: 기획] `mid`는 상세에만 표시하고 `low`는 건수만 남기는지 재확인 — 근거: planner 보고서 67줄.
- [이관: 데이터] 외부 확인 대상 기관 목록의 정본과 `region_code`·`sub_region_code`를 어디서 채울지 — 근거: 동명 기관(중구·동구·고성군 등).
- [이관: 프런트·디자인] 행 한 줄 `외부 확인 MM-DD HH:mm`과, 찾음·찾지 못함·조회 실패의 표시 문구 — 기다리는 것: 조회 응답 키 확정(§3-3).
- [이관: security] 검토 질문:
  1. 첨부 본문을 서버가 검사하지 못하면(안 A·B·C) 어느 안이 허용 가능한가?
  2. 휴대폰 전수 삭제와 유선 마스킹 규칙을 서버가 어디까지 강제해야 하는가?
  3. 확장자 허용 목록·크기 한도(20 MiB·5개·200 MiB)가 적정한가?
  4. `redaction` 자기신고 값을 이력에 남겨도 되는가?
  5. 외부 확인 파일이 `corpus/rfp/`와 분리된 `corpus/ext_check/`에 놓이면 접근 제어가 충분한가?
  6. 보도 제목·출처 URL에 개인 이름이 들어갈 수 있는데 어떻게 할 것인가?

## 7. 열린 질문 (사용자 답으로 진행되는 것만)
- 한 배치에 개인정보가 든 check가 있으면 "그 건만 빼고 반입"과 "배치 전체 거부" 중 어느 쪽이 업무에 맞는가?
- 공고문 파일이 폐쇄망에서 열려야 하는 형식은 무엇인가(PDF만 / 한글 HWP 포함)? 이에 따라 서버가 읽을 수 있는 검사 범위가 달라진다.
- 참고(질문 아님): `uploader/README.md`와 RPA 쪽 파일 크기 한도는 이번에 확인하지 못했다. 한도가 20 MiB보다 작으면 §3-2의 제안값을 낮춘다.

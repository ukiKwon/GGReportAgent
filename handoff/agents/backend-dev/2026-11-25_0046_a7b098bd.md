## 3. 구현안

### 판정 규칙 (기관 잠금과 활성 건 확인 뒤, 같은 트랜잭션)

- 살아 있는 올해 목표가 **있으면**:
  - 그 기관에 목표 변경 결재가 하나라도 PENDING이면 → 409 `GOAL_CHANGE_PENDING` (빼기·연도 변경이 걸려 있을 수 있음)
  - 아니면 → 통과
- 올해 목표가 **없으면**:
  - 올해를 목표로 만드는 결재(ADD·TO_GOAL·EDIT 중 TO_YEAR=올해)가 PENDING이면 → 409 `GOAL_CHANGE_PENDING`
  - 아니면 → 409 `NOT_GOAL_TARGET`
- 검사 순서: 403 역할 → 400 입력 → 404 기관 → 409 `PREP_ALREADY_ACTIVE` → **목표 검사(신규)** → 건 지정 경로(404/409).
  - 활성 건 검사를 먼저 둬서, 이미 진행 중인 건이 있으면 목표 여부와 관계없이 지금처럼 `PREP_ALREADY_ACTIVE`가 나갑니다(소급 없음).
- 이미 확정된 건, 개설 신청 등 확정 뒤 흐름에는 목표 조건을 걸지 않습니다.
- 개설 전 확정 취소 건을 되살리는 경로와, 옛 공고 건(`bid_case_id` 지정)도 새 확정이므로 목표 조건을 거칩니다.
- 공고 여부는 검사하지 않습니다(Q1 대기).

    private void requireGoalTarget(String inst) {
        int year = LocalDate.parse(Times.todayKst()).getYear();
        if (mapper.countGoalForYear(inst, year) > 0) {
            if (mapper.countTargetPending(inst) > 0) {
                throw coded(409, GOAL_CHANGE_PENDING, GOAL_PENDING_MSG);
            }
            return;
        }
        throw mapper.countPendingGoalForYear(inst, year) > 0
                ? coded(409, GOAL_CHANGE_PENDING, GOAL_PENDING_MSG)
                : coded(409, NOT_GOAL_TARGET, NOT_GOAL_MSG);
    }

## 5. 보안·위험·되돌리는 법

**권한 판단**
- 확정 자격(영업팀·영업팀장, `requireSales`)은 그대로입니다. 영업부장 확정은 지금처럼 403이고 DENIED로 남습니다.
- 새 조건은 409라서 접근 이력의 DENIED 줄이 아닙니다. 감사표(`BID_PREP_ACT`)에는 `OUTCOME=BLOCKED`로 남고, 접근 이력 DETAIL에는 `prep confirm 409 NOT_GOAL_TARGET|GOAL_CHANGE_PENDING`처럼 상태와 코드만 남습니다(기관 id·본문·사번 없음). `BID_PREP_ACT`에는 코드 칸이 없어 BLOCKED 사유(활성 건인지 목표 밖인지)를 거기서는 구분할 수 없습니다. 칸을 추가하는 일은 이번 범위 밖입니다.

**자기신고의 한계**
- `X-Emp-No`는 자기신고입니다. 이 조건은 실수를 막는 업무 규칙이지 사칭 방지가 아닙니다.
- `X-Screen-Id`도 자기신고입니다. 'bid_board만'은 **감사 표시일 뿐 강제가 아닙니다**. 다른 화면 값이면 UNKNOWN·ui_valid=0으로 남고 요청은 처리됩니다. 실제로 막는 장치는 목표 조건입니다.
- 그래서 '현황판에서만'은 서버가 보장할 수 없고, 서버가 보장하는 것은 '목표 기관만'입니다. 사용자에게 이 차이를 숨기지 않습니다.

**동시성**
- 판정이 기관 행 잠금 안에 있고, 목표 넣기·빼기·옮기기·결재 상신·승인 반영이 모두 같은 행을 먼저 잠급니다. 그래서 목표 빼기와 확정이 동시에 들어와도 순서가 정해집니다.
- MySQL RR에서도 첫 일관 읽기가 잠금 뒤(`countActiveByInstitution`)에 일어나므로 낡은 스냅샷 문제가 없습니다.
- 예외 하나: 결재 반려·회수는 기관을 잠그지 않습니다. 이때 생길 수 있는 것은 '대기 중'으로 보수적으로 409가 나는 쪽뿐입니다(다시 누르면 됩니다).

**노출 범위**
- `pending_goal_items`는 map 조회 권한자 전원(디자이너·전산 포함)에게 기관 id와 연도만 줍니다. 지금 `change_pending`(결재 중 여부, S8 '모두에게')과 같은 수준이고, 요청자·사유·결재 번호는 주지 않습니다.
- 다만 **줄이 없는 기관이 목표 후보로 결재 중이라는 사실**이 새로 보이게 됩니다. security가 이 범위를 확인해야 합니다(아래).

**위험**
- 056 미적용 DB에서는 confirm이 500이 됩니다. 현황판 결재가 이미 056을 요구하므로 실제로 일어날 가능성은 낮습니다.
- 문구가 화면 매핑 없이 그대로 노출돼도 내부 정보는 없습니다.

**되돌리는 법**
- DB 변경이 없으므로 이 커밋을 `git revert`하면 끝입니다.
- 급하게 조건만 끄려면 `PrepService.confirm`의 `requireGoalTarget(inst);` 한 줄을 지우면 됩니다. 이때 시험의 `@Before` 시드는 남겨도 무해합니다.
- 응답 키 `pending_goal_items`는 추가만 했으므로, 프런트가 아직 안 쓰면 그대로 둬도 됩니다.

**security 확인 거리**
1. `pending_goal_items`를 map 조회 권한자 전원에게 줘도 되는가, 아니면 영업 계열(can_edit)·영업부장으로 좁힐까. 좁히려면 `edit || HEAD`일 때만 넣는 한 줄입니다.
2. 확정 화면 값을 UNKNOWN 기록에 그치게 할지, 400으로 거절할지. 나는 기존 규칙(허용 밖 → UNKNOWN, 400 아님)을 따랐습니다.
3. 목표가 있는데 결재가 걸려 있으면 동작과 관계없이 막는 것(주 담당만 바꾸는 결재도 포함)이 지나치지 않은가. 호출자 지시('결재 대기 없음')대로 넓게 막았습니다.
4. 오류 문구에 값이 없는지.

### 패치 D — 상세 `viewer.view_until`·`view_until_at`
`BoardMinutesService.java` — `detail()`의 `out.put("viewer", viewer(d));`를 `out.put("viewer", viewer(d, head, me));`로 바꾼다. `viewer`는 static을 떼고 다음처럼 고친다. import에 `java.time.OffsetDateTime`, `java.time.ZoneId`, `java.time.temporal.ChronoUnit`을 더한다.
```java
    private Map<String, Object> viewer(BoardMinutesAccess.Decision d, BoardMinutes head, SysUser me) {
        Map<String, Object> v = new LinkedHashMap<String, Object>();
        // … 기존 9줄 그대로 …
        String untilAt = null;
        String until = null;
        if (d.via == BoardMinutesAccess.Via.UPLOADER) {          // 올린 시각 + uploader-days 까지
            untilAt = uploaderUntilAt(head.getCreatedAt());
            until = untilAt == null ? null : OffsetDateTime.parse(untilAt).atZoneSameInstant(ZoneId.of("Asia/Seoul")).toLocalDate().toString();
        } else if (d.via == BoardMinutesAccess.Via.GRANTEE) {    // 공개범위 종료일(그날 포함)
            until = grantUntilOf(head.getMinutesId().longValue(), me.getEmpNo());
        }
        v.put("view_until", until);       // yyyy-MM-dd(KST) — 부장급·기본 열람자는 null(기한 없음)
        v.put("view_until_at", untilAt);  // 등록자만 정확한 끝 시각(ISO), 그 밖 null
        return v;
    }

    private String uploaderUntilAt(String createdAt) {
        if (createdAt == null) {
            return null;
        }
        try {
            return Times.iso(OffsetDateTime.parse(createdAt).toInstant().plus(settings.getUploaderDays(), ChronoUnit.DAYS));
        } catch (DateTimeParseException e) {
            return null;
        }
    }

    private String grantUntilOf(long id, String empNo) {
        for (BoardMinutesScope s : mapper.selectScope(id)) {
            if (empNo.equals(s.getGrantValue())) {
                return s.getGrantUntil();
            }
        }
        return null;
    }
```

    private BoardMinutes lockAndRecheck(SysUser me, BoardMinutes head, Predicate<BoardMinutesAccess.Decision> allowed) {

### 패치 H — 미리보기 확인값에 가림 단어·해제 포함(중복 검사 값은 그대로)

    /**
     * 미리보기 확인값 = H(내용 확인값 + 정렬·trim 한 가림 단어 + 해제 목록). 저장 때 이 값이 같아야 한다 —
     * 미리보기 뒤에 해제를 늘리거나 가림 단어를 빼고 저장하지 못하게(PREVIEW_CHANGED). 중복 검사·CONTENT_DIGEST 는 digest 그대로.
     */
    public static String previewDigest(String digest, Collection<String> terms, Collection<String> release) {
        char sep = '\u0001';
        StringBuilder sb = new StringBuilder("p1:").append(digest).append(sep);
        for (String t : sortedTrim(terms)) {
            sb.append(t).append(sep);
        }
        sb.append('\u0002');
        for (String t : sortedTrim(release)) {
            sb.append(t).append(sep);
        }
        return sha256Hex(sb.toString());
    }

    private static List<String> sortedTrim(Collection<String> in) {
        TreeSet<String> s = new TreeSet<String>();
        if (in != null) {
            for (String x : in) {
                if (x != null && !x.trim().isEmpty()) {
                    s.add(x.trim());
                }
            }
        }
        return new ArrayList<String>(s);
    }

### 패치 I — multipart 임시 파일: 문턱값 강제(fail-closed)
업로드 요청 전체는 `3×max-file + 1MB`(기본 7MB)를 넘지 못한다(`MinutesLimitFilter.java:82`). 문턱값이 그 이상이면 회의록 파트는 디스크에 써지지 않는다.

`MinutesSettings.java`

+    @Autowired(required = false)
+    private MultipartProperties multipart;
 …

         uploaderDays = …;
         maxFileKb = …;
         if (enabled && !Charset.isSupported(…)) { … }
+        long need = 3L * getMaxFileBytes() + 1024L * 1024L;   // MinutesLimitFilter 업로드 상한과 같은 식
+        long threshold = multipart == null || multipart.getFileSizeThreshold() == null ? 0L : multipart.getFileSizeThreshold().toBytes();

설정 키는 값 없이 키와 권장값만 적는다:

- 대안(채택하지 않음): `spring.servlet.multipart.location`을 전용 폴더로 두고 기동할 때 비우기. 요청 처리 중에는 원문이 디스크에 남아 '원본 미보관' 원칙과 어긋난다.

## 5. 보안·위험·되돌리는 법
- **자기신고 한계**: `X-Emp-No`·화면·버튼 값, `rules_ack`는 모두 자기신고다. RULES_ACK 기록은 "그 사번으로 체크를 보냈다"는 뜻이지 본인이 읽었다는 증명이 아니다. 서버가 저장에 필수로 걸어 화면을 우회해도 빠지지 않게 했을 뿐이다.
- **403·404 경로**: 후보 API는 부장급만 쓴다. 볼 수 있으나 권한이 없으면 403이고 `guard.denied`로 ACCESS_LOG DENIED와 ACT DENIED가 남는다. 볼 수 없으면 404(HIDDEN)다. 쓰기 재판정에서 나는 403·404도 컨트롤러 관문(`exec`)을 지나므로 같은 방식으로 기록된다.
- **후보 목록 노출 범위**: 부장급에게 활성 사용자 전체의 사번·이름·역할·직위가 간다. 관리자·전산·디자이너 포함이다. `scopeAdd`가 이미 받아 주는 범위와 같지만 목록으로 한꺼번에 보인다는 차이가 있다 → security 확인, 범위 축소는 기획 이관.
- **접근 이력**: 새 detail은 번호·코드·`ack=1`뿐이다. 본문·이름·가림 단어·파일명은 없다.
- **multipart 문턱값은 전역 설정이다**: 8MB 미만 파트는 모든 업로드에서 메모리에 머문다. TaskFiles 50MB·자료 5MB 업로드도 포함된다. 문턱값이 모자라면 회의록은 스스로 꺼진다(fail-closed). 그래서 **사용자 로컬 `config/application.properties`에 키를 넣지 않으면 적용 뒤 재기동했을 때 회의록 탭이 404가 된다.** 세션 시작 점검(키 이름 대조)이 out-local과의 차이로 잡아낸다.
- **배포 순간의 영향**: 패치 H로 배포 전에 만든 미리보기 확인값이 무효가 된다. 진행 중이던 저장은 한 번 409 PREVIEW_CHANGED가 나고, 다시 미리보기하면 해결된다.
- **동시성**: 패치 G는 회의록 쓰기마다 `BID_ASSIGN_CASE` 행을 잠깐 잠근다. 같은 건의 배정 변경 승인·020 쓰기와 직렬화된다. 교착 순서 검토는 3절 패치 G에 있다. 관리자의 역할 변경은 이 잠금으로 직렬화되지 않는다. 그래서 그 경우는 "트랜잭션 안에서 사용자를 다시 읽는다"까지만 막고 창을 좁힐 뿐이다(잔여 위험).
- **되돌리기**: 코드만 바꾸므로 커밋 revert면 된다. DB는 그대로다. 남은 `RULES_ACK` LOG 행은 무해한 이력이다. 설정 키는 남겨 둬도 된다.
- **security가 꼭 볼 점**
  1. 후보 범위(전체 활성 사용자)가 맞는지
  2. 전역 문턱값 8MB의 힙 영향과 운영 JVM 힙 크기
  3. 기능이 꺼져도 회의록 경로의 multipart는 DispatcherServlet이 해석한다(디스크 쓰기는 꺼진 상태에서만 가능, 요청 끝에 삭제)
  4. 재판정의 잠금 순서
  5. preview_digest 계산에서 가림 단어를 해시로만 쓰는지(응답·기록에 원문이 없음)

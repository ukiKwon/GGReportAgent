  - 서버·시험은 실행하지 않았습니다.

## 2. 요구/원인 요약
- 순위 코드는 039 INSERT(`039_bank_contract.sql:61-64`)에 있고 FIRST·SECOND·NONE·JOINT 4개입니다. 허용 규칙은 `rankAllowed`(`Rules:52-56`)입니다. `rankChecked`(`Rules:65-67`)가 FIRST·SECOND일 때만 true라서 지자체·교육청 쪽을 판정하는 단일 지점입니다.
- 겹침 비교는 `p.rank.equals(c.getRankCd())`(`Service:235`)와 `c.getRankCd().equals(o.getRankCd())`(`Service:247`)입니다. 순위가 같은 줄끼리만 비교하므로, SINGLE이 FIRST·SECOND와 충돌하려면 이 두 줄을 바꿔야 합니다.
- **표시 순서는 서버가 정렬합니다.**
  - 코드표 목록은 `ORDER BY SORT_NO, CODE`(`Mapper:110`)입니다. 그래서 SORT_NO=5이면 지자체·교육청은 1금고, 2금고, 단수 금고 순으로 나옵니다. NONE 3, JOINT 4와도 겹치지 않습니다.
  - 목록 줄 정렬은 Java `RANK_ORDER`(`Rules:29`)이므로 거기에도 SINGLE을 추가합니다.
- 화면은 서버가 준 `codes.ranks`로 라디오를 그립니다(`bankcontract.js:339-357`). 이름은 서버의 `name`을 우선 쓰므로(`:150-152`) 변경이 필요 없습니다. 이관 메모는 6절에 있습니다.

```java
    /**
     * 두 순위가 겹침 비교 대상인가. 같은 순위끼리는 항상, 단수 금고는 한 은행이 전부 맡으므로 1·2금고·단수 금고 어느 쪽과도
     * (1금고 vs 2금고는 비교 안 함). 공동 지정의 같은 은행 조건은 overlapScope 가 따로 본다.
     */
    static boolean rankClash(String a, String b) {
        if (a == null || b == null) return false;
        if (a.equals(b)) return true;
        return (RANK_SINGLE.equals(a) && rankChecked(b)) || (RANK_SINGLE.equals(b) && rankChecked(a));
    }

### 3-3. `BankContractService.java`
`[충돌]` 232·245행의 NONE 검사와 230-254행 전체를 다른 에이전트가 고칩니다. 아래 두 줄만 바꾸면 되며, 합친 뒤 줄 번호는 달라질 수 있습니다.

+ 235:  if (BankContractRules.rankClash(p.rank, c.getRankCd())
```

+ 247:  if (o.getContractNo() != c.getContractNo() && BankContractRules.rankClash(c.getRankCd(), o.getRankCd())

- `overlapScope(p.rank, …)`는 p.rank가 SINGLE이면 true입니다. p.rank가 FIRST·SECOND이고 c가 SINGLE이어도 true입니다. JOINT끼리는 종전대로 같은 은행만 봅니다. 그래서 `overlapScope`는 수정하지 않았습니다.
- 규칙이 대칭이라 `overlap_with`(화면 겹침 표시)도 양쪽 줄에 같이 나옵니다.
- `Service:324` 주석 "1금고→2금고→순위 없음→공동"은 "1금고→2금고→단수 금고→순위 없음→공동"으로 고칩니다(주석만).
- 고칠 때 자기 줄은 `excludeLine`으로 이미 빠집니다. FIRST 줄을 SINGLE로 바꾸는 경우도 자기 줄과는 충돌하지 않습니다.

## 5. 보안·위험·되돌리는 법
- **권한 경로 변경 없음**: 저장 권한(403)·접근 이력·자기신고(`X-Emp-No`) 경로는 그대로입니다. 새 입력 필드가 없고 `rank_cd`는 기존 `code()` 검사(정규식 + `ENABLED=1` 코드표)를 통과해야 합니다. 오류 문구는 고정 문구입니다.
- **배포 순서 안전**: 041을 적용하기 전에 코드가 먼저 나가면 SINGLE은 `countEnabledCode`=0이라 400 "허용되지 않는 금고 순위"로 막힙니다. 반대로 DB만 먼저 적용하면 화면에 SINGLE 라디오가 보이지만 서버는 이미 받아 줍니다. 어느 순서든 깨지지 않습니다.
- **기존 데이터 영향 없음**: SINGLE은 새 코드라 기존 줄은 달라지지 않습니다. 기존 FIRST·SECOND 줄 사이의 겹침 규칙도 그대로입니다.
- **정책 위험(기획 확인 대상)**: 같은 기관의 FIRST와 SINGLE이 겹치면 409지만 `confirm_overlap`으로 저장할 수 있습니다. 완전 금지가 아니라 기존 S2 흐름과 같은 확인 저장입니다. 이것이 사용자 의도(공존 불가로 봄)와 맞는지는 6절에 올렸습니다.
- **되돌리기**: 코드는 위 패치를 되돌리면 됩니다. DB는 `DELETE FROM COMMON_CODE WHERE CODE_GROUP='BANK_RANK' AND CODE='SINGLE'`이며, RANK_CD='SINGLE' 줄이 없을 때만 합니다. 줄이 있으면 삭제 대신 `ENABLED=0`을 쓰는데, 그러면 새로 고를 수는 없고 기존 줄 표시용으로만 남습니다.

## 6. 이관 메모
- **[이관: 프런트]** 서버가 주는 `codes.ranks`로 라디오는 자동으로 늘어납니다. 아래 둘은 선택 사항입니다.
  - `bankcontract.js:30` `RANK_NAME`에 `SINGLE: '단수 금고'` 폴백을 더할지.
  - `bankcontract.js:375` 겹침 안내 문구가 "같은 순위에 기간이 겹치는 약정이 있습니다."라서 SINGLE과 FIRST의 충돌에는 어색합니다. 서버 `dupRank` 메시지(`Service:271`)도 같은 문구입니다.
  - 문구 변경은 시험에 영향이 없습니다(시험은 `code`만 봅니다). 서버 문구는 합의되면 제가 한 줄 패치로 드리겠습니다.
  - 수집 슬롯 비교(`bankcontract.js:215-216`)는 slot 1·2만 보므로 SINGLE 줄은 항상 "같음"이 아닙니다. 의도한 동작이면 변경이 필요 없습니다.
- **[이관: 기획]** SINGLE과 FIRST·SECOND가 같은 기간에 겹칠 때 확인 저장(`confirm_overlap`)을 허용할지, 아니면 완전히 막을지 정해 주세요. 지금은 사용자 지시("공존 불가로 봄")를 기존 S2 방식(409, 확인 후 저장)으로 옮겼습니다.
- **[이관: 데이터]** 없음. 단수 금고인 실제 기관 레코드의 값과 출처는 데이터 담당 몫입니다.

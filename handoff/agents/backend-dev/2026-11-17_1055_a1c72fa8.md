# backend-dev-write 보고서 (자동 보존)

> SubagentStop 훅이 에이전트의 최종 메시지를 그대로 저장했다(2026-11-17 1055 KST, agentId a1c72fa839c858dc4). 에이전트 출력이므로 사용자 결정이 아니다. 지시 내용·주제는 이 파일에 없다 — 필요하면 handoff/NEXT.md 항목이나 커밋 메시지로 찾는다.

---

1. 수정 파일은 두 개다. `InboxService.java`는 importBatch의 manifest 읽기 직후(검증 통과 뒤, dbApplier·파일 이동 전)에 checks 거부 코드를 넣었다(약 146~152줄). `InboxApiTest.java`는 "첫 번째 첨부" 시험 바로 앞에 시험 1건을 더했다(`checks가_있는_배치는_반입_422이고_아무것도_바뀌지_않는다`).
2. 동작은 이렇다. manifest에 checks가 있고 null이 아니면 422를 던진다. 본문은 `{detail:{errors:["CHECKS_NOT_YET_SUPPORTED: 외부 확인(checks) 반입은 아직 지원하지 않습니다"]}}`이고, 기존 422와 같은 형식이며 입력값은 싣지 않는다. checks가 없거나 null이면 기존 records 배치와 동작이 같다. /validate는 그대로 ok:true이고, 시험도 이를 확인한다.
3. 시험은 checks만 있는 유효 배치(schema_minor 1, records 빈 배열, 첨부 파일 포함)를 쓴다. 기대 결과는 /import 422와 그 코드 포함, inbox 배치 폴더와 첨부가 그대로 남음, batches 보관 폴더 없음, BID_CASES 건수 불변이다.
4. 메인이 `cd kgi-ggreport-web && mvn -q -o test -Dtest=InboxApiTest,BatchSchemaChecksTest`를 실행한다. 전부 통과가 기대 결과이고, 마지막에는 전체 `mvn -o test`도 돌린다. 실행은 못 했다. 시험의 manifest는 기존 `manifest()` 문자열에서 schema_minor와 checks를 끼워 넣어 만든다. 컴파일과 BatchSchema 통과 여부는 실행 때 확인이 필요하다.
5. 지시를 벗어난 판단은 없다. 이관 메모도 없다. 2단계에서는 이 거부 블록을 지우고 checks 반영으로 바꾸면 되고, 시험도 그에 맞춰 바꾼다.

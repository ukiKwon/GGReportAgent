### 3. 지시와 다르게 판단한 것
- `BoardMaterialService.checkedValues`는 보고서의 줄 번호(688~781)와 현재 코드의 줄 번호가 달랐다. 한 번에 통째로 바꾸는 대신 같은 내용을 4번에 나눠 Edit했다. 결과는 보고서 §3-5(e)와 같다.

### 4. 컴파일 의심 지점
- `BoardFormService.structureForStored`와 `docForStoredAny`는 `forms.selectForm(Long)`, `forms.selectVersion(Long,int)`, 정적 `parseId`, 인스턴스 `docOf(BoardForm, BoardFormVer, boolean)`을 쓴다. 같은 파일에 이미 있는 것들이라 컴파일될 것으로 본다.
- `BoardMaterialController.run`에서 `me`를 try 밖에서 선언하고 catch에서 항상 던진다. 이후 `call.apply(me)`가 effectively final을 요구하지는 않는다.
- `catch (ApiException)` 뒤에 `catch (RuntimeException)`이 오므로 `ApiException`이 `RuntimeException`의 하위여야 한다. 확인하지 못했다.
- `BoardMaterialAudit.recordList`가 `BoardMaterialService.CONFIRMED`를 쓴다. 같은 패키지이고 기존 코드도 쓰므로 접근은 가능하다. 목록 항목의 키 `material_id`·`status_cd`·`confirmed_snap`·`bid_case_id`·`result_cd`는 `BoardMaterialService` 622~635행에서 확인했다.
- `BoardMaterialService.create`의 `selectIdsByCaseYear(bid, year)`는 `Integer year`를 `int`로 언박싱한다. `parseYear(..., true)`는 null이 아닌 값을 돌려준다고 본다.
- 테스트는 `BoardDocSpec.find(DEFAULT_ID, true)`와 `getTables()`가 있다는 가정을 쓴다. 나머지 가정(500 변환, mapped 칸 2개 이상, `find` null 아님)은 보고서 §1 그대로이고 깨지면 해당 테스트만 고친다.
- HANDOVER 테스트에서 영업부장(HEAD)이 `/bidcases/{id}/assignments/history`에서 403이면 건너뛰도록 되어 있어 부장 200은 단정하지 않는다. 필요하면 실행 결과를 보고 단정으로 바꾼다.
- 기존 테스트에서 같은 입찰 건·연도를 중복 생성하는 곳은 없는 것을 grep으로 확인했다. 다른 테스트 클래스 중 `POST /board-materials`를 직접 부르는 곳이 있는지는 보지 않았다.

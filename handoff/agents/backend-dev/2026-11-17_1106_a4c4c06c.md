## 2. 요구·원인 요약
- ① view()(Service 347~378줄)에는 최신 수정자(editor_name·saved_at)만 있다. 처음 입력자는 canChangeLine이 `selectFirstEditor`(Mapper.xml 80~82줄)로 줄마다 따로 조회한다. 응답에 싣는데 줄마다 쿼리를 돌리면 N+1이 된다. 그래서 `cols`/`from` 조각에 REV_NO=1 행을 PK로 LEFT JOIN한다. 모든 select(최신·이력·단건)가 이 조각을 공유해 한 번에 해결된다.
- ② save()의 겹침 블록(Service 146~151줄)은 `confirm_overlap`이 없으면 무조건 409 DUP_RANK를 낸다. 그래서 비고만 고쳐도 다시 묻는다. 직전 rev가 OVERLAP_CONFIRMED=1이고 은행·순위·기간이 같으면 확인을 이어받게 한다.

### (3) BankContractRules.java — same() 바로 뒤에 추가
```java
    /** 겹침 확인 이어받기(NEXT 89②): 직전 rev 가 겹침을 확인했고(OVERLAP_CONFIRMED=1) 순위·은행·기간이 그대로면 true. 하나라도 바뀌면 false. */
    static boolean carriesOverlap(BankContract prev, Parsed p) {
        return prev != null && prev.getOverlapConfirmed() == 1 && !ACTION_CANCELLED(prev)
                && Objects.equals(prev.getRankCd(), p.rank) && Objects.equals(prev.getBankCd(), p.bank)
                && Objects.equals(prev.getBankNameEtc(), p.bankEtc)

    }
```

## 5. 보안·위험·되돌리는 법
- 권한 경로는 바뀌지 않는다. 컨트롤러 403(`canEdit`)·줄 권한(`canChangeLine`)·접근 이력(DENIED, 본문·값 없음) 그대로이고, 이어받기는 save() 내부 분기라 새 우회로가 없다.
- 이어받기 위험: 본인이 겹침을 확인한 줄을 다른 팀원이 비고만 고치면 그 사람은 겹침 경고를 못 본다. 사용자가 정한 규칙이고 이력(rev마다 editor_name과 overlap_confirmed=true)에 남는다. 기간·은행·순위가 바뀌면 다시 묻는다. 선행 줄이 그사이 취소되어 겹침이 사라지면 `over`가 비어 `OVERLAP_CONFIRMED=0`으로 저장된다(기존 동작).
- 처음 입력자 이름은 자기신고(X-Emp-No) 기반 값이다. `emp_verified`가 있으니 화면 표지는 프런트가 기존대로 한다. 사번·화면·버튼 값은 내보내지 않는다.
- 되돌리기: 위 패치 5개 파일을 원복하면 된다. DB는 그대로다. 조인이 느려지면(수만 행 이상) `f`에 PK 인덱스를 이미 쓰니 문제 없다고 본다.

## 6. 이관 메모
- [이관: 프런트] first_editor_name·first_saved_at 표시 위치, 그리고 "겹침 확인을 이어받았다"는 안내 문구가 필요한지(이어받은 줄은 overlap_confirmed=true만 온다) — 기다리는 것: 설계안 승인 뒤 화면 반영 — 근거: 본 패치.
- [이관: 기획] 화면이 사번 대신 `can_cancel`(서버 계산 불리언)을 받는 것이 필요한지 — 근거: 사번 비노출 원칙, 취소 버튼 노출 판단.

## 5. 사용자 안내 명령 (읽기 전용 단계 → 기록 단계)
판단: **`--baseline 060`은 쓰지 말 것.** baseline은 실제 DB를 검사하지 않고 046~060 전부를 "적용됨"으로 적는다. 047~059를 "도구 밖에서 직접" 적용했다면 한 파일이라도 빠졌을 때(예: 반쯤 적용된 표, 052 UPDATE 누락) 영영 발견되지 않는다. `--mark-applied`는 표·칸·코드 행을 실제로 검사하고 통과한 것만 기록하므로 이쪽이 맞다. 결번(046·050·053)은 파일이 없어 기록 대상이 아니다.

1) 현재 상태 확인(변경 없음): `node kgi-ggreport-web/tools/db/apply-mysql.mjs --status`
   - 047~060 전부 '대기', 045까지 '적용됨'이면 예상대로. 비밀번호는 프롬프트에서 입력.
2) 검사만(변경 없음):
   `node kgi-ggreport-web/tools/db/apply-mysql.mjs --mark-applied 047,048,049,051,052,054,055,056,057,058,059,060 --dry-run`
   - "검사 통과, 기록 예정" 12개가 나오면 3으로. "다음 파일은 적용된 흔적이 없습니다 — NNN"이면 그 번호만 mysql로 적용하거나, 이미 적용했다고 확신하면(특히 052처럼 이름을 나중에 바꾼 경우) 그 번호를 빼고 따로 확인.
3) 기록(실행 없이 기록만): 2번 명령에서 `--dry-run`만 뺀 같은 명령.
4) 확인: `--status` 다시 → '적용됨 …/ 대기 0', 옵션 없이 실행하면 "적용할 파일이 없습니다. (이미 최신)".
주의: 기록되는 체크섬은 **현재 파일**의 sha256이다. 이후 이 파일들을 고치지 않는다(고치면 '변경됨!'으로 중단).

## 6. 보안·위험·되돌리는 법
- 도구는 로컬 MySQL 전용(DB 쓰기는 SCHEMA_MIGRATION INSERT만). 새 검사는 SELECT뿐, 사용자 입력이 SQL에 안 들어간다(고정 문자열). 비밀번호 처리 경로 변경 없음. 인증·권한 영향 없음(Actor 무관한 개발 도구).
- 한계: 검사는 "대표 흔적"이라 칸 하나 단위의 부분 적용(예: 047 표는 있으나 인덱스 누락)은 못 잡는다. 표 전체·칸·코드 행까지 본 것으로 합의한 수준. 049의 FORM_VER 칸·056의 3칸은 포함해 ALTER 누락도 잡는다. 052는 이름 값 의존(위 설명).
- 되돌리기: 코드는 git revert. 잘못 기록했으면 `DELETE FROM SCHEMA_MIGRATION WHERE VERSION IN (...)`을 사람이 mysql로 실행(기록표만 지움, 스키마 영향 없음).
- Oracle 쌍: 이 변경은 MySQL 도구 한정이라 Oracle 스크립트 쌍 없음.

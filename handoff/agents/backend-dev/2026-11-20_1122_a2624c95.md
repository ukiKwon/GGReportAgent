### 3-0. 규칙 (보정 반영)

| 쟁점 | 결정 |
|---|---|
| 결재 유형 | `TARGET_CHANGE` "목표 기관 변경". 대결 불가, 영업팀 내부 정보(관리자 전체 목록·관리자 취소에서 제외) |
| 항목 동작 `op_cd` | `ADD`(새 목표: 기관·연도·태그·메모·주 담당), `EDIT`(목표 고치기: 연도·태그·메모·주 담당 전체 새 값), `CANCEL`(빼기), `TO_WATCH`(목표→관심), `TO_GOAL`(관심→목표, 연도) |
| 일괄 | 1~20건, **한 요청에 같은 기관은 한 번만**. 요약 payload가 3800자를 넘으면 400 |
| 직접 호출 차단 | `POST …/bid-targets`(목표 넣기·목표 고치기), 목표 `/cancel`, `/move`(어느 방향이든)는 영업부장이 아니면 **409 `APPROVAL_REQUIRED`**. 모든 입력 검사(400/422/STALE/겹침/공고 종료)와 NO_CHANGE 판정 **뒤**, 쓰기 직전에 판정합니다. 관심 넣기·고치기·빼기는 바로 됩니다 |
| 우회 경로 | 관심 빼기 → 목표 새로 넣기 우회는 목표 넣기에 결재가 붙어 닫힙니다 |
| 결재 중 잠금 | 그 기관에 PENDING 항목이 있으면 **그 기관의 모든 쓰기**(목표·관심 넣기·고치기·옮기기·빼기, 영업부장 직접 쓰기, 이월)를 409 `CHANGE_PENDING`으로 막습니다. 앞 설계에서는 메모 고치기를 허용했는데, 이제 목표 메모도 결재 대상이고 관심 기록이 TO_GOAL 대상일 수 있어 기관 전체를 잠급니다 |
| 반영 방식 | 전부 반영하거나 하나도 안 함. 한 항목이라도 바뀌었으면 409 `ITEM_CHANGED`(item_no·기관 이름). 같은 REV PK가 마지막 방어선 |
| 감사 | 반영 행: 수정자 = 승인한 사람(사번·이름 스냅샷·검증 여부), 화면·버튼 = 결재 화면 ui, `APPROVAL_REQ_ID` = 요청 번호. 내용 작성자(요청자)의 사번·이름 스냅샷·검증 여부는 항목 표에 남고, 화면에는 `requested_by_name`으로 보입니다 |
| 이월 | 작년 목표 중 `judge(...) ≠ SUCCESS`(FAIL·PENDING·UNREGISTERED)이고 살아 있고 아직 이월 안 됐고 결재 중이 아니고 올해 목표가 없는 기관 → 새 TARGET_NO, `ACTION_CD = CARRY`, `CARRY_FROM_NO`. 미리 잡아 둔 올해 목표가 있으면 그대로 둡니다. 이월은 사용자가 정한 자동 규칙이라 결재 대상이 아닙니다 |

- **결재 카드.** `view()`에서 `TARGET_CHANGE`이면 `m.put("target_items", targetChanges.itemsOf(r.getReqId()))`. 담는 것은 기관 이름·동작·이전→이후 연도·태그 이름·메모·주 담당 이름·빼는 사유 이름이고, 사번은 넣지 않습니다.
- **새 상신 함수.** 생성자에 `TargetChangeService targetChanges`를 주입합니다.
```java
/** 목표 기관 변경(TARGET_CHANGE, 056). ⚠️ 첫 DB 문장은 기관 행 잠금(정렬) — MySQL RR 일관 읽기를 잠금 뒤로 미루려고 callers.require 보다 먼저. */
@Transactional
public Map<String, Object> submitTargetChange(TargetChangeIn in, Actor actor) {
    targetChanges.lockAll(in);                       // 400 형식 · 404 기관 — 잠금만
    SysUser me = callers.require(actor);
    TargetChangeService.Plan plan = targetChanges.plan(in, me);
    ApprovalRequest r = new ApprovalRequest();
    r.setReqType(ApprovalTypes.TARGET_CHANGE);
    r.setRequesterEmpNo(me.getEmpNo());
    r.setTitle(plan.getTitle());                     // "목표 기관 변경 — ○○구청 외 n곳"
    String payload = write(plan.getPayload());       // 요약만(기관 id·이름·op·연도) — 메모·사유는 항목 표
    if (payload.length() > 3800) throw new ApiException(400, "한 번에 올리기에 항목이 너무 많습니다. 나눠서 요청해 주세요.");
    r.setPayload(payload);
    r.setStatus("PENDING");
    r.setCurrentStep(1);
    r.setCreatedAt(Times.nowIso());
    requests.insert(r);
    ApprovalStep s = step(1, "LINE", plan.getApprover().getEmpNo());
    s.setReqId(r.getReqId());
    requests.insertStep(s);
    targetChanges.claim(plan, r.getReqId(), me, actor);   // 항목 행 INSERT(요청자 이름 스냅샷·검증 여부)
    notifyStep(r, s, me);
    return view(requests.selectById(r.getReqId()), me);
}
```

반려·회수 때는 할 일이 없습니다. 잠금은 요청 상태로 계산하므로 자동으로 풀립니다.

### 3-6. `BidTargetService` 변경
```java
static final String ACTION_CARRY = "CARRY";
static final String APPROVAL_MSG = "목표 기관 정보를 바꾸려면 팀장 결재가 필요합니다. [결재 요청]으로 올려 주세요.";

static boolean directGoal(SysUser u) { return u != null && HeadRules.ROLE_HEAD.equals(HeadRules.roleOf(u.getRole())); }
private void requireNoPending(String inst, BidTarget cur) {
    if (!mapper.selectPendingByInst(inst).isEmpty()) throw conflict("CHANGE_PENDING", PENDING_MSG, cur);
}
private void requireDirect(SysUser me, BidTarget cur) {
    if (!directGoal(me)) throw conflict("APPROVAL_REQUIRED", APPROVAL_MSG, cur);
}
```

**`save()`** — 기관 잠금은 지금처럼 첫 문장입니다. NO_CHANGE 반환 뒤, `checkOverlap` 앞에 다음을 넣습니다.
- 모든 경우: `requireNoPending(inst, cur)`
- 목표(`!watch`)일 때: `closedCheck`까지 끝낸 뒤 `requireDirect(me, cur)`
- 관심이면 결재 없음

**`cancel()`** — `parseCancel`·LIMIT 뒤에 `requireNoPending`, 그다음 목표이면 `requireDirect`.

**`move()`** — `closedCheck` 뒤에 `requireNoPending`·`requireDirect`(옮기기는 항상 목표가 관련됨).

**쓰기 추출(TargetChangeService 재사용)**
- 위 세 함수의 쓰기 부분을 `applySave(row, actor, ui, reqId)`·`applyCancel(cur, cp, actor, ui, reqId)`·`applyMove(cur, to, year, actor, ui, reqId)`로 추출합니다.

- `me`는 기존 `insert()`의 `users.selectByEmpNo` 결과를 앞으로 당겨 한 번만 조회합니다.

**`list()`**

**`view()`**

## 5. 보안·위험·되돌리는 법

**security가 볼 점**
- **(가) 자기신고 인증.** `X-Emp-No` 자기신고라, 영업부장 사번을 대면 결재 없이 바로 바꿀 수 있고 결재자도 사칭할 수 있습니다. 이번 변경은 업무 절차 강제이지 보안 경계가 아닙니다. 행마다 `EMP_VERIFIED`·`REQ_EMP_VERIFIED`와 접근 이력으로 사후 추적만 됩니다.
- **(나) 409를 쓴 이유.** `APPROVAL_REQUIRED`·`CHANGE_PENDING`·`USE_DIRECT`는 403이 아닌 409라 ACCESS_LOG DENIED에는 안 남고 failDetail(`409 CODE`)에만 남습니다. 403이 맞다면 `guard.denied`로 바꿉니다.
- **(다) 메모의 개인정보 노출.** 메모·사유는 항목 표와 결재 카드(`target_items`)에 보입니다. 결재함은 결재자·요청자만 볼 수 있습니다. 개인정보·금지어는 상신 때 `MemoScreen`·`checkedText`로 막습니다.
- **(라) 이월 POST.** 누구나(영업 계열) 부를 수 있지만 서버가 대상을 계산하고 멱등입니다.
- **(마) 동시성.** 상신·직접 쓰기·이월은 기관 잠금으로 직렬화되고, 결재 중에는 기관 전체가 잠깁니다. 승인 경로의 오래된 스냅샷은 PK(같은 REV)로 막습니다. ADD는 승인 때 `MAX+1`로 번호를 매기며, 같은 기관에 결재 중인 다른 요청이 없어 충돌하지 않습니다.
- **(바) 운영 위험.** 결재가 오래 걸리면 그 기관의 관심 기록과 영업부장 직접 수정도 묶입니다. 회수 경로(요청자 취소)는 있습니다.

**되돌리는 법**
- 코드를 되돌리면 056 칸은 null로 남아 무해합니다. 표 삭제는 056 헤더의 순서대로 합니다.
- 결재를 임시로 끄려면 `directGoal`을 영업 계열 전체로 넓힙니다(한 줄).
- 이월만 끄려면 `ggreport.bid-target.carry.enabled=false`로 둡니다.

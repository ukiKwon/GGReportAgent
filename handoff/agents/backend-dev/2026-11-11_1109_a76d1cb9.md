## 3. 구현안

### 상태기계 (DDL 변경 없음 — 시드 코드 PREP/DRAFT/SUBMITTED/CONFIRMED 재사용)
```
PREP --(첫 버전 저장)--> DRAFT --submit(담당자, 버전>=1)--> SUBMITTED --팀장(또는 팀장 관련이면 부장) 승인--> CONFIRMED
DRAFT <--withdraw(담당자 누구나)-- SUBMITTED        DRAFT <--결재자 반려-- SUBMITTED
DRAFT <--rework(부장, 사유 1~200자)-- SUBMITTED | CONFIRMED (결과·개최일·확정정보 해제)
CONFIRMED --result(담당자)--> CONFIRMED (RESULT_CD: SCHEDULED/PASSED/REJECTED, 반복 변경 가능)
```
- 새 상태 코드는 만들지 않는다. "반려됨/재작성 요구됨"은 상태가 아니라 DRAFT + `last_return`(§3-1 ⑤)로 표현한다.
- **새 DDL 스크립트 없음.** `BOARD_MATERIAL_LOG.EVENT_CD`·`ACT.ACTION_CD`는 제약 없는 VARCHAR(20)이고, `APPROVAL_REQUEST.REQ_TYPE`은 VARCHAR(30)이며 CHECK가 없다(012 확인).
  - mysql/oracle 모두 이번에는 스크립트를 더하지 않는다.
  - 이미 020을 적용한 DB는 그대로 이어 간다.
- **이벤트 코드(문서용)**
  - LOG: `CREATE SUBMIT WITHDRAW REJECT CONFIRM REWORK RESULT HANDOVER`
  - ACT: `VIEW LIST SNAPSHOT_LIST SNAPSHOT_VIEW HISTORY ACTS REVIEW SAVE SUBMIT WITHDRAW REWORK RESULT CONFIRM`(`CREATE`는 id 없음이라 ACT 없음)
- `ACT.STATUS_CD` = **행위 직전** 상태다. 확정에서 재작성 요구하면 `CONFIRMED`로 남는다.

### 프런트 계약 (다음 걸음)
- `GET /board-materials/{id}` (담당자·부장)과 `GET /board-materials/{id}/review` (결재자)의 `viewer`

- `status_cd`와 한글 이름(`status_name`, 이미 응답)
  - `PREP` 준비 중 / `DRAFT` 작성 중 / `SUBMITTED` 제출(결재 중) / `CONFIRMED` 확정.
  - `result_cd`: `SCHEDULED` 의결 예정 / `PASSED` 가결 / `REJECTED` 부결.
- `last_return`(DRAFT일 때만, 없으면 null): `{event_cd: REJECT|REWORK, req_id, reason, actor_name, logged_at}`. "팀장이 반려했어요 / 부장이 재작성을 요구했어요" 배너용이다. 사유는 `esc`로만 그린다.
- 쓰기 POST는 모두 `X-Screen-Id`/`X-Button-Id` 필수다. 없거나 목록 밖이면 400 `UI_ID_REQUIRED`(detail.code).
  - 화면·버튼 값(권장)
    - 작성 화면(`board_write`): `save_version`·`submit`·`withdraw`·`result_save`
    - 검토 화면(`board_review`): `rework`·`review_open`·`acts_open`
    - 결재함: `approvals_inbox` + `approve`/`reject`, `approvals_mine` + `cancel_request`
  - 결재함이 헤더를 안 보내면 UNKNOWN으로 남는다.
- 오류 코드(응답 `detail.code`, 문구에 내부 정보 없음)
  - 409 `MATERIAL_LOCKED` / `ALREADY_SUBMITTED` / `NO_SNAPSHOT` / `NOT_SUBMITTED` / `NOT_CONFIRMED` / `NOT_APPLICABLE` / `CONFLICT` / `APPROVER_ROLE_MISMATCH`
  - 400 `APPROVER_NOT_RESOLVED` / `MEETING_DATE_REQUIRED`
  - 403은 담당 아님·부장 아님(문자열 detail).
- 감사 기록 열람: `GET /board-materials/{id}/acts`. 항목은 `action_cd`·`outcome`·`status_cd`(행위 직전)·`result_cd`·`snap_no`·`actor_emp_no`·`actor_name`·`emp_verified`·`screen_id`·`button_id`·`ui_valid`·`logged_at`이다.

## 5. 보안·위험·되돌리는 법
- **자기신고 한계**: `X-Emp-No`·`X-Screen-Id`·`X-Button-Id`는 모두 클라이언트 자기신고다.
  - 담당자·결재자·부장 판정은 업무 규칙(실수 방지)이지 사칭 방지가 아니다.
  - ACT의 `emp_verified=false`가 이 사실을 그대로 보여 준다.
  - 감사 화면에서 "검증됨"처럼 읽히게 쓰지 않는다.
- **접근 이력·ACT에 넣지 않는 것**: 값·메모·사유·본문·비밀번호·이름. `ACCESS_LOG.detail`은 자료 번호·코드·`req`·`snap`뿐이다.
- **403 경로**: 쓰기 거부는 `guard.denied`로 `ACCESS_LOG` DENIED + 확정 건이면 ACT DENIED. 비담당은 404(HIDDEN), 락 충돌은 409(BLOCKED).
- **쓰기와 감사의 원자성**
  - 쓰기가 이미 커밋된 뒤 ACT 기록이 실패하면 쓰기는 되돌지 않는다(서버 로그만).
  - 읽기는 응답 전 기록이라 실패 시 500이고 데이터가 나가지 않는다(fail-closed). 기존 설계 그대로다.
  - `recordApproved`도 같은 한계를 가진다.
- **동시성**
  - 제출 선점(`claimSubmit`), 승인(`confirm`), 회수·반려·재작성(`backToDraft*`), 결과(`updateResult`)는 모두 상태 조건부 UPDATE다. 0행이면 409로 롤백한다.
  - 제출·결과·승인은 `lockAssignCase`(락 먼저, 배정 읽기는 뒤)로 담당 변경 승인과 직렬화한다.
  - 회수·재작성은 교착 방지를 위해 일부러 락하지 않는다(위 §3-1 ③).
  - 제출 뒤 결재자가 담당자가 되면 승인이 403/409로 막히고, 그 요청은 반려·회수로 풀린다.
- **되돌리는 법**: 코드는 git revert. DDL이 없어 DB 되돌릴 것이 없다.
  - 되돌리기 전에 진행 중인 `BOARD_SUBMIT`(PENDING)을 회수·취소하고, SUBMITTED 자료를 DRAFT로 정리한다.
  - 코드만 되돌리면 유형명을 모르는 결재 카드가 생길 수 있다.

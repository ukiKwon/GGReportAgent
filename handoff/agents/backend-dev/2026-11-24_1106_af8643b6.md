### 설계 결정
| | 결정 |
|---|---|
| ① 파라미터 | `scope=mine\|team\|dept`. **파라미터가 없을 때만** 역할 기본값(팀원 mine·팀장 team·부장 dept). `""`·`MINE`·`all`·`" mine"`은 모두 400 `BAD_SCOPE`. 403 판정(canList)이 400보다 먼저다. |
| ② 팀 정의 | **구조상 팀장** = 수동 지정 사용자의 결재선 첫 영업팀장(활성·직급 무관 — 열람 묶음이지 결재 권한이 아니어서 `mayApprove`는 빼고, 자동 지정 제외는 sameTeamLead와 같게 둠). 팀장 시점의 팀 = 나 + 구조상 팀장이 나인 영업팀원. 팀원 시점의 팀 = 내 구조상 팀장 + 그 팀장 아래 영업팀원 + 나. 팀장을 못 정하면 '나 혼자'로 좁히고 `team_resolved:false`를 준다(넓히지 않음). **부장의 team은 dept와 같다**(열린 질문 1). 부서 = 영업부서 전체. |
| 건↔팀 | 진행 중인 건: 활성 담당 중 한 명이라도 팀에 있으면 팀 건. 끝난 건: 배정 이력 중 한 명이라도 있으면 팀 건. |
| 상태 | team/dept: `IN_PROGRESS·APPROVAL_PENDING·WRITABLE·WRITING`(허용 목록이라 모르는 상태는 빠짐). include_ended이면 **CANCELLED ∧ OPENED_AT 있음(개설 뒤 중단)**만 더한다. 확정 취소(개설 전)는 결재가 없었으므로 제외한다. mine: CONFIRMED_BY=나 또는 활성 담당이면 개설 전도 포함. include_ended이면 확정자 본인 또는 옛 담당인 CANCELLED를 더한다. |
| ③ 거르는 곳 | **서버**. 열람 경계가 아니라 편의 거르기다(영업부서 누구나 dept를 요청할 수 있다). 그래도 서버에서 거르는 이유: (a) 감사 DASH_LIST_ROW가 '사용자가 본 표'와 일치한다. (b) 응답이 작아진다. (c) 팀 판정(결재선)은 프런트가 할 수 없다. |
| 상세 열람 | `can_view`(canSee)·`is_mine`(활성 담당)·이름 가림 규칙은 그대로다. mine 범위에는 확정만 한 건(is_mine=false)도 실린다. |
| ④ 감사 | 성공 요약 줄(DASH_LIST/DASH_LIST_ENDED) TASK_CD = 실제 적용 범위. 건 줄(DASH_LIST_ROW)은 지금처럼 NULL. 실패 줄은 파라미터 형식이 맞을 때만 SCOPE_*, 아니면 NULL(입력값을 싣지 않음). 접근 이력 DETAIL은 그대로 둔다(쿼리값 금지 규칙). |
| 응답 | 새 키 `scope`(적용값)·`scope_default`(역할 기본값)·`team_resolved`. 기존 키는 그대로다. |

    public static final String SCOPE_MINE = "mine", SCOPE_TEAM = "team", SCOPE_DEPT = "dept";
    static final List<String> SCOPES = Collections.unmodifiableList(Arrays.asList(SCOPE_MINE, SCOPE_TEAM, SCOPE_DEPT));
    /**
     * 팀·부서 작업에 실리는 상태 — 팀장 결재(개설 승인)가 끝난 건(사용자 11-24). 허용 목록이라 모르는 상태는 빠진다.
     * CHECK_STATES 와 값은 같지만 뜻이 달라 따로 둔다(체크 허용 ≠ 열람 범위) — 한쪽을 바꿀 때 다른 쪽을 따라 바꾸지 말 것.
     */
    static final Set<String> SCOPE_OPENED_STATES = Collections.unmodifiableSet(new HashSet<String>(Arrays.asList(
            PrepService.IN_PROGRESS, PrepService.APPROVAL_PENDING, PrepService.WRITABLE, PrepService.WRITING)));

    /** 역할 기본값(팀 결정 11-24): 영업부장 dept, 영업팀장 team, 영업팀 mine. */
    static String defaultScope(SysUser u) {
        String r = u.getRole() == null ? "" : u.getRole().trim();
        if (BidAssignmentService.HEAD_ROLE.equals(r)) { return SCOPE_DEPT; }
        if (BidAssignmentService.LEAD_ROLE.equals(r)) { return SCOPE_TEAM; }
        return SCOPE_MINE;
    }

    /** 파라미터가 없을 때만 역할 기본값. 빈 값·대소문자 다름·공백 포함은 400(입력값을 메시지에 되풀이하지 않는다). */
    static String resolveScope(SysUser u, String raw) {
        if (raw == null) { return defaultScope(u); }
        if (!SCOPES.contains(raw)) {
            throw coded(400, "BAD_SCOPE", "조회 범위는 내 작업·팀 작업·부서 작업 중 하나여야 합니다.");
        }
        return raw;
    }

    /** 감사 TASK_CD 값 — 형식이 맞을 때만 SCOPE_*, 아니면 null(입력값을 감사에 싣지 않는다). */
    public static String scopeTag(String scope) {
        return scope != null && SCOPES.contains(scope) ? "SCOPE_" + scope.toUpperCase(java.util.Locale.ROOT) : null;
    }

    /**
     * 범위 판정. active: 그 건의 활성 담당 사번, ever: 끝난 건의 배정 이력 사번, team: 팀 사번(null 이면 팀 제한 없음 — 부장의 team).
     * mine = 확정자 본인 또는 활성 담당(개설 전 포함) + 끝난 건은 옛 담당도.
     * team/dept = 개설 승인 뒤(SCOPE_OPENED_STATES) + 끝난 건은 개설 뒤 중단(OPENED_AT 있음)만 — 확정 취소(개설 전)는 결재가 없어 빠진다.
     */
    static boolean inScope(String scope, BidPrep p, String meEmp, Set<String> active, Set<String> ever, Set<String> team) {
        boolean ended = PrepService.CANCELLED.equals(p.getStateCd());
        if (SCOPE_MINE.equals(scope)) {
            return meEmp.equals(p.getConfirmedBy()) || active.contains(meEmp) || (ended && ever.contains(meEmp));
        }
        boolean opened = ended ? p.getOpenedAt() != null : SCOPE_OPENED_STATES.contains(p.getStateCd());
        if (!opened) { return false; }
        if (SCOPE_DEPT.equals(scope) || team == null) { return true; }
        for (String e : ended ? ever : active) {
            if (team.contains(e)) { return true; }
        }
        return false;
    }

## 5. 보안·위험·되돌리는 법
- **열람 경계가 아니다.** 영업부서 누구든 `scope=dept`를 요청하면 개설 승인 뒤의 전 건을 본다(지금도 전 건을 보므로 넓어지는 곳은 없다). 상세 열람(`canSee`)·체크 권한·이름 가림은 바뀌지 않는다. 사번은 X-Emp-No 자기신고라 범위도 자기신고에 기댄다.
- **403 경로**: 영업부서 밖은 범위 값과 무관하게 먼저 403이고 DENIED 감사가 남는다(D51). 400은 영업부서 안에서만 난다.
- **감사**: 요약 줄에 실제 적용 범위를 남긴다. 입력 원문은 어디에도 싣지 않는다(형식 밖이면 NULL). 접근 이력은 줄 수만 그대로다.
- **팀 판정 위험**: 관리자가 결재자를 수동 지정하지 않은 팀원은 '팀 작업'이 자기 건만 보인다(`team_resolved:false`로 화면이 안내할 수 있다). 결재선을 바꾸면 다음 조회부터 팀 묶음이 바뀐다(기록은 남지 않는다 — 판정 근거가 USERS 현재값).
- **비용**: 팀 조회 때 `users.selectAll()`이 1회 더 돈다(사용자 수 소규모 전제). include_ended일 때 배정 이력 묶음 질의가 1회 더 돈다.
- **되돌리기**: DDL이 없으므로 코드 커밋을 되돌리면 끝이다. 이미 쌓인 TASK_CD=`SCOPE_*` 감사 줄은 남아도 읽는 코드가 없다.

## 7. 열린 질문 (답하면 바로 반영할 수 있는 것만)
1. **영업부장의 '팀 작업'**: 지금 안은 부서 작업과 같다(부장 1명 전제). 시드처럼 영업부장이 2명이고 각자 아래 팀장이 다르면, 부장의 '팀 작업'을 '내 결재선 아래 팀들'로 나눌지 정해 주면 된다. 나누면 `salesTeamEmpNos`에 부장 분기를 하나 더한다.
2. **'확정 취소'(개설 전에 취소된 건)**: 지금 결정대로면 이 건은 확정한 사람의 '내 작업'(끝난 건 포함)에만 보이고, 영업팀장·부장의 대시보드에서는 사라진다. 상세 화면에서는 팀장·부장이 계속 볼 수 있다. 지금은 끝난 건 보기를 켜면 팀장·부장에게도 보인다. 팀장·부장이 대시보드에서 계속 봐야 하면 '팀·부서 작업 + 끝난 건 포함'에 확정 취소를 더할지 정해 주면 된다.

## 2. 원본 패치안과 달라진 점
- **설정 의존을 모두 뺐다.** 뺀 것은 `BidTargetSettings` 변경, 설정 키, 4인자 `valueOnlyEdit`, `aimChangeNeedsApproval`, `aim_change_mode`다. 응답에서 `aim_change_mode`는 아예 없앴고, 지시대로 `aim_mode`만 남겼다.
- **`aim_mode` 규칙:** 쓰기 자격이 없으면 null, 영업부장은 DIRECT, 그 밖은 지난해 목표면 APPROVAL, 아니면 DIRECT다.
- **일괄 EDIT도 `valueOnlyEdit`를 부른다.** 지난해 목표는 결재 그대로다.
- **ADD에서 aim을 400으로 막는다.** 단건은 `save()`에서 `parse` 전에 막고(영업부장·팀원 모두 400이 403보다 먼저 나온다), 일괄은 `shape()`에서 DB 잠금 전에 막는다. 메시지는 "금고 방식은 목표로 넣은 뒤 표에서 고릅니다."이고, 빈 값("")은 '비움'이라 통과한다. 관심 줄에 aim 값을 보내면 별도 문구로 400이다.
- **tag NULL(D):** `common()`이 tag를 선택값으로 바꿨다. 빈 값은 NULL, 모르는 코드는 400이다. 관심 기록의 직접 저장도 같은 파서라 tag 없이 된다. ♥ 켜기는 기존대로 기본 태그를 쓴다. `same()`·`TargetResultRules`는 `Objects.equals`나 `"RETAIN".equals`라 NULL 영향이 없었다.
- **REQ_ITEM의 TAG_CD는 056부터 이미 NULL 허용**이라 ALTER를 넣지 않았다.
- **`replan` 코드 검사를 두 가지 바꿨다(원본 패치안에도 없던 판단).**
  - tag가 NULL이면 검사를 건너뛴다.
  - aim은 요청 때 새로 고른 값(현재 기록과 다른 값)만 다시 검사한다. security 보고서의 "이어받기만 한 aim 코드를 비활성화하면 무관한 결재까지 실패하는 문제"를 피하려는 것이다.
- **접근 이력의 aim 표기는 원본대로 남겼다.** 지시에 따로 언급이 없었다.
- **DDL 번호:** `db/mysql`·`db/oracle` 최대가 062였고 063 파일은 없었다. 적용 직전에 063이 겹쳤는지 한 번 더 확인해 달라. 겹치면 파일명, `BidTargetAimRankDdlPairTest`, 시험용 properties 세 곳을 064로 바꾼다.

## 3. 시험
**깨질 기존 시험:** `BidTargetApiTest.태그_코드는_코드표만`의 "tag 없으면 400" 단정을 ADD 201로 바꾸고 이유 주석을 달았다. 그 밖에 깨질 곳은 못 찾았다(memo 단정, `watchOn`의 `MEMO IS NULL` 단정은 영향이 없다).

**추가한 시험**
- `BidTargetRulesTest`(단위)
  - tag는 비워도 통과하고 모르는 코드는 400.
  - aim 코드표 밖과 관심 줄 값은 400, 빈 값은 null.
  - `requireNoAimOnAdd`.
  - `keepUnsent`(빠지면 잇고 ""이면 지움).
  - `aimEdit` 종류.
  - `same`의 aim 비교.
  - `valueOnlyEdit`가 aim과 무관하고 지난해 목표는 false.
- `BidTargetApiTest`: 구분을 빈 값으로 보내도 ADD 201이고 NULL 저장, 고치기에서 비우기, 모르는 코드는 400.
- `TargetChangeApiTest`
  - 단건 고르기·바꾸기·지우기가 결재 없이 201, REV 이력, 접근 이력에 종류만 남음.
  - 일괄 `set_target_aim_rank`가 바로 반영, `aim=1`.
  - ADD에 aim을 실으면 400(단건·일괄, 팀원·영업부장).
  - ADD에서 tag를 비우면 NULL(영업부장 바로, 팀원 결재 승인, 목록 tag_cd null).
  - 결재 EDIT(주 담당 변경) 승인 뒤에도 aim이 유지됨.
  - TO_WATCH 카드의 '이후' aim이 이전 값.
  - 지난해 목표 aim만 고치면 403, 목록 aim_mode APPROVAL.
  - 관심 줄 aim은 400, 결재 중이면 409.
  - memo·aim을 안 보내면 잇고 ""이면 지움(단건·일괄).
  - 목록의 aim 칸·`codes.aim_ranks`·DESIGNER null.
  - 목표→관심→목표로 옮겨도 aim을 이어받음.
- `BidTargetAimRankDdlPairTest`: DDL 쌍 시험(1절 참고).
- 설정 관련 시험 줄은 넣지 않았다. 자동 이월이 aim을 잇는지 보는 시험은 넣지 않았다(코드는 반영함).

## 5. 이관 메모
- [이관: 프런트] 다음을 반영해야 한다.
  - 표의 금고 방식 열은 `aim_rank_cd`/`aim_rank_name`(NULL이면 '-')과 `codes.aim_ranks`를 쓴다.

  - 고치기 본문에서 memo를 빼면 지금 값이 유지되고, 지울 때만 `""`를 보낸다.
  - tag_cd는 비워도 되고, 목록의 `tag_cd`가 null이면 '-'로 표시한다.
  - 결재 카드는 `aim_rank_name`과 `before.aim_rank_name`을 읽는다. TO_GOAL·TO_WATCH·CANCEL은 이전과 같은 값이다.
- [이관: 데이터] 기존 MEMO 값을 금지어 규칙(정당·전화번호)으로 한 번 점검한다. `keepUnsent`는 이어받은 memo를 다시 검사하지 않는다(security 보고서 항목).
- [이관: 문서] `kgi-ggreport-web/README.md`의 API·DDL 목록은 고치지 않았다(지시 목록에 없음). `ops/integrity_check.sql`도 못 봤다. 필요하면 메인이 정한다.
- 보안 권장 1~5 반영 상태: 1(설정·4인자 제거)·2(ADD aim 400)·3(REQ_ITEM aim 유지)·4(카드 '이후' 보정)·5(시험)를 모두 반영했다.

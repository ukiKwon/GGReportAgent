## 3. 지시와 다르게 판단한 것
1. 건당 50개·300MB는 무효 처리한 것도 센다. 파일을 물리 삭제하지 않아서다. 무효로 돌려 한도를 비울 수 없다.
2. 무효 처리는 지시대로 "올린 사람이면서 지금 활성 담당자"만 한다. 올린 사람이 담당에서 빠지면 아무도 무효 처리하지 못한다(아래 TODO).
3. UNCHECKED 첨부도 T3 확정본으로 지정할 수 있다. 저장됐다면 검사를 통과한 것으로 봤다. 막으려면 `setConfirmedFile`에 조건 한 줄이면 된다.
4. 업로드 파일 이름에도 차단 대상 개인정보 검사(422)를 건다. 이름이 DB에 남기 때문이다. 요청에 없던 추가다.
5. 무효 처리된 첨부도 담당자·부장이 내려받을 수 있다(원본 보관). 업로드·내려받기·지정 시 이름은 감사 표에 넣지 않고 attach_id만 넣는다.
6. 무효 처리의 사유는 필수(1~200자, 개인정보면 422)로 했다. 설계표의 `{reason}`을 필수로 읽었다.
7. PDF 원문 바이트 검사 목록에서 `/JS`를 뺐다. 3바이트라 30MB급 압축 PDF에서 우연히 걸린다. `/JS`는 객체 사전 검사가 본다.
8. 같은 첨부를 다시 지정하는 PUT은 200으로 아무것도 바꾸지 않는다. 해제할 지정이 없을 때 DELETE는 409 STATE_CHANGED다.
9. `PrepApiTest`는 "범위 밖" 목록에 없고, T3 판정이 첨부 유효성을 보게 되어 고쳐야 했다.

## 4. TODO·위험
- **일부 PDF 오탐·미탐**
  - 객체 스트림 안에 숨긴 /JS는 놓칠 수 있다(PDFBox 2.0이 지연 로딩).
  - 이름 트리·열 때 동작은 3단계까지만 본다. 첨부 한정 CVE 재확인은 security 몫이다.
- **숫자 칸 오탐**: xlsx의 날숫자 13자리(1조 원 이상, 월·일이 맞는 값)가 주민번호로 걸려 422가 날 수 있다. 사용자가 서식을 바꿔 올려야 한다.
- **PDF 검사 상한**: 쪽 수 500, 시간 20초, 동시 스레드 2개다. 모두 막히면 새 업로드가 줄을 선다.
- **파일 정리 한계**: 커밋 후 서버가 죽으면 고아 파일이 남을 수 있다. 업로드 중 임시 `up-*.tmp`도 같다. 정리 배치는 없다.
- **운영 폴더**: `data/prep-attach`가 웹 루트·정적 경로 밖인지, OS 권한, 백업 포함을 운영·DBA가 확인해야 한다(열린 질문 2).
- **무효 처리 막다른 길**: 올린 담당자가 해제되면 무효 처리할 사람이 없다. 팀장·부장 예외가 필요하면 기획 결정이다.
- **T3 확정본 이후 T5**: `stale_basis`는 여전히 TODO(false)다.
- **MyBatis 1차 캐시**: JdbcTemplate으로 값을 바꾸는 테스트는 기존처럼 `flushCache()`가 필요하다(내 테스트에 반영).
- **README**: `kgi-ggreport-web/README.md`는 024도 없어서 건드리지 않았다. 025·`ggreport.prep-attach-dir` 안내는 후속이다.
- **`ApprovalRequestService`**: 중단된 건의 기획승인·개설 쪽 후크는 이번 범위 밖이라 손대지 않았다.

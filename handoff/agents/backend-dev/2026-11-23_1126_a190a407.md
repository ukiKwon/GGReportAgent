**3. 사용자 결정의 범위 해석 (권장)**
- 권장은 결재자에게 가는 `결재알림`(신규 계열)과 `결재요청`(옛 계열)만 끄는 것이다.
- 요청자에게 가는 `결재결과`(승인·반려·취소·재작성)는 유지한다. 근거는 이렇다.
  - 결재함 숫자는 내가 처리할 결재를 세므로 요청자는 거기에 잡히지 않는다.
  - 반려 사유는 `결재결과` 쪽지 본문으로 전해진다. 쪽지가 없으면 요청자가 결과를 알 방법이 없다.
  - 사용자가 든 이유(같은 일을 두 번 알린다)는 결재자 쪽에만 해당한다.
- 감사 기록은 쪽지와 별개로 유지된다. `ApprovalRequestService`의 `auditPrep`(:834)과 `DesignReviewService`의 `audit.record`는 쪽지를 만드는 코드 앞뒤에서 따로 호출되고, 쪽지 테이블에 의존하지 않는다.
  - 다만 `notifyStep`은 `@Transactional` 안이라, 코드를 지우면 이 부분의 정합성은 달라지지 않는다. 설정으로 건너뛰는 쪽이 더 안전하다.
  - 결재 목록·진행 단계는 쪽지가 아니라 결재 요청과 단계 테이블에서 만들어지므로, 쪽지가 없어도 결재함 숫자는 정확히 계산된다.
- 옛 작업 결재 계열(`결재요청`)을 함께 끌지는 사용자에게 확인이 필요하다. 사용자 결정은 "결재 알림은 머리 띠 숫자만으로"이고, 옛 계열도 결재함에 잡히는지는 내가 확인하지 못했다.
  - 잡힌다면 같이 끄는 것이 결정에 맞다.
  - 안 잡힌다면 끄면 영업팀장·부장이 제출 사실을 알 길이 없어진다. 이 경우에는 `결재요청`을 유지해야 한다.

**4. 끄는 방법 패치안 (권장: 설정 키, 기본 `false`)**
- 코드 삭제 대신 설정 키를 권장한다. 이유는 키 하나로 되돌릴 수 있고, 시험도 `true`로 켜면 기존 단언이 그대로 통과하기 때문이다.
- 신규 계열은 `ApprovalRequestService`의 `notifyStep` 맨 앞에서 반환한다.

```java
// old
private void notifyStep(ApprovalRequest r, ApprovalStep step, SysUser requester) {
    List<String> to = new ArrayList<>();

// new
@Value("${ggreport.notify.approval-request.enabled:false}")
private boolean notifyApprovalRequest;

private void notifyStep(ApprovalRequest r, ApprovalStep step, SysUser requester) {
    if (!notifyApprovalRequest) {
        return;   // 결재 알림은 머리 띠 [결재함 n] 숫자로만 (사용자 결정 11-23). 결과 통지(notifyResult)는 유지.
    }
    List<String> to = new ArrayList<>();
```

- `@Value` 필드는 생성자 주입 클래스에서도 동작하지만, 기존 코드가 `AppProperties`를 쓰므로 그쪽에 항목을 두는 편이 일관된다. 어느 쪽이든 기본값은 `false`다.
- 옛 계열을 함께 끌 때는 `결재요청` 종류만 걸러 내면 된다. `NotificationCommandService.create` 안에서 `kind`가 `결재요청`이고 키가 `false`이면 만들지 않고 반환하는 방법이다. 5곳을 따로 고치지 않아도 되고, 사람이 보내는 쪽지는 `kind`를 못 정하므로 영향이 없다. 단 `create`의 반환값(`DesignReviewService:367`처럼 `Notification`을 쓰는 곳)은 `결재요청` 종류가 아니라서 영향이 없다.
  - 반환값이 `null`이 되어도 `결재요청` 호출 5곳은 반환값을 쓰지 않는다. grep에서 반환값을 받는 곳은 `:367` 하나뿐이고 종류가 `쪽지`다.
- 설정 파일에는 `config-envs/out-local/application.properties`와 서버 설정 쪽에 키를 같이 올려야 한다. CLAUDE.md의 로컬 설정 키 대조 규칙 때문이다. 키가 빠지면 값은 `false`가 된다.
- DB 스크립트 변경은 없다.

**5. 서버 시험 영향**

`notifyStep`을 끄면 깨지는 시험 (`ApprovalLineApiTest`)
- :272, :504~522, :557~559: `결재알림`이 1건 간다고 단언한다. 키가 `false`이면 0건이 된다.
- :265, :509~510, :522, :529, :557, :630: 0건을 단언한다. 이쪽은 계속 통과한다.
- 처리 방법은 두 가지다. 테스트 `application.properties`에 키를 `true`로 두면 기존 단언이 모두 통과한다. 또는 기본 `false`에 맞춰 1건 단언을 0건으로 바꾼다. 권장은 후자가 아니라, 새 동작을 단언하는 시험을 하나 추가하는 것이다.
- `결재결과` 단언(:535~572)은 영향이 없다. `BoardMaterialApiTest:1472~1479`도 `결재결과`만 본다.

`결재요청` 종류까지 끄면 깨지는 시험
- `DesignReviewApiTest:231`과 `:529`는 `NOTIFICATIONS`에서 `KIND='결재요청'`이 1건이라고 센다.
- `GoldenWriteScenarioTest:108~142`는 제출 뒤 각 팀장 쪽지함의 첫 항목 종류가 `결재요청`이라고 단언한다. 이 시험은 골든 계약을 보는 시험이라 되돌리면 안 되는 쪽에 가깝다. 옛 계열을 끄려면 먼저 이 시험을 어떻게 할지 정해야 한다.
- `OrchestratorCoreTest:104`는 `recorder.notify`를 직접 부르는 시험이라 `DbRecorder`를 거치지 않으면 영향이 없다.
- `NotificationWriteApiTest:47`은 사람이 `kind: 결재요청`을 위조하는 시도를 막는지 보는 시험이다. 서버 쪽 `kind` 검증은 건드리지 않으므로 통과한다.

추가할 시험
- 키가 `false`일 때 상신하면 결재자 쪽지 수가 0이다. 그리고 요청자가 승인·반려를 받으면 `결재결과`는 그대로 1건 간다.
- 같은 요청이 결재함 `inbox`에는 여전히 나타난다. 결재함 숫자의 근거가 쪽지가 아님을 보이기 위해서다.

호출자가 실행할 명령
- `cd kgi-ggreport-web && mvn -q -o test`. 8080 서버가 같은 `target/`을 쓰면 테스트 뒤 재기동한다.
- 첫 확인은 `-Dtest=ApprovalLineApiTest+DesignReviewApiTest+GoldenWriteScenarioTest`로 좁혀 돌리면 빠르다.

**6. 보안·위험·되돌리는 법**
- 권한 검사(403 경로)는 건드리지 않는다. 쪽지를 안 만드는 것뿐이고, 결재 가능 여부는 `eligibility`와 `Ranks`가 정한다.
- 접근 이력과 감사 기록은 그대로다. 본문·쿼리값은 어디에도 새로 쓰지 않는다.
- 위험은 쪽지가 알림 구실을 하던 사용자가 결재 요청을 놓치는 것이다. 머리 띠 숫자가 제대로 안 올라오면 알 방법이 없다. 프런트 숫자가 `inbox` 건수와 같은지 먼저 확인해야 한다.
- 이미 만들어진 `결재알림` 쪽지는 쪽지함에 남는다. 지우려면 DB 정리가 필요하고, 이번 제안에는 넣지 않았다.
- 되돌리는 법은 설정 키를 `true`로 바꾸는 것이다.
- 인증은 `X-Emp-No` 자기신고라는 한계가 그대로이고, 이 변경과는 무관하다.

- 테스트 `ApprovalLineApiTest`와 `src/test/resources/application.properties`는 git status에 이미 수정 표시가 있는 파일(`application.properties`)이 있다. 이 파일은 다른 세션이 만지는 중이니 키 한 줄만 더하고, 적용 전에 최신으로 다시 읽어야 한다.

### 인덱스 — 두 번 뒤집었다

사용자 질문("복합 인덱스는 컬럼 순서가 중요하지 않냐")이 계기였다. 맞는 지식이고,
**테이블의 컬럼 순서(성능 무관)와 인덱스의 컬럼 순서(결정적)는 다른 얘기**임을 정리했다.

1. `(업로드일시)` + `(기관명, 분류상태구분)` → 최신순 정렬을 **PK 로** 바꿔 앞엣것을 없애고
   3열 `(기관명, 분류상태구분, 업로드일시)` 제안
2. 구현 중 **3열이 주 조회를 못 받는 것을 발견** — `WHERE 기관명=? ORDER BY 업로드일시` 는
   가운데 열 때문에 정렬이 되살아난다 → **2열 `(기관명, 업로드일시)`** 로 정정
3. 사용자가 "파일처리상태 화면에도 적용되냐" 고 물어 확인해 보니 **안 된다.**
   `분류상태구분 = ?` 을 부르는 곳이 **여섯**이었다(화면 둘 · 잡 · 서비스 둘).
   앞서 "잡이 꺼져 있으니 보류"라 뺐던 판단이 틀렸다 →
   **`(분류상태구분, 업로드파일일련번호)` 복구.** 두 번째 열이 PK 라 정렬까지 받는다.

최종 2개. 그 과정에서 **`findByStatus` 에 `ORDER BY` 가 없던 결함**도 함께 고쳤다.

⚠️ 최신순 정렬을 PK 로 둔 전제는 **시퀀스 NOCACHE** 다. 캐시를 켜면 깨진다(주석에 적음).

표준 검사에서 개명. 두 단계를 거쳤다 — 먼저 `기관영업분류`(속성명이
`기관영업분류구분코드` 로 길어짐) → 다시 `기관영업분류코드` + `코드2` 로.
**컬럼명이 어근으로 끝나게 지으면 속성명이 컬럼명과 같아진다**(광역지자체코드 예시와 같은 형태).

🔵 **인덱스 열 순서를 바꿀지 논의했고 바꾸지 않기로 했다.** 사용자 의견은
"분류가 큰 범주이니 앞에 오는 게 맞지 않나" 였는데, 근거 둘로 유지를 택했다:
ⓐ 선행 컬럼 규칙상 분류를 앞에 두면 **주 조회인 `WHERE 기관명 = ?` 가 인덱스를 아예 못 탄다**
ⓑ 분류는 값이 5개뿐이라 **선택도가 낮다**(1/5 만 걸러짐). 분류별 목록 화면 계획도 없다.

**PK 도 복합으로 바꾸지 않기로 했다.** 사용자 제안은
`(기관일련번호, 기관영업분류, 기관명)` 이었는데 세 이유로 권하지 않았다 —
ⓐ 일련번호가 이미 유일해 조합의 유일성이 늘지 않는다 ⓑ "기관에 대한 유일성"은
PK 가 아니라 UNIQUE 제약(`UK_TSKGIAF02_기관명`)이 표현할 일이다
ⓒ 🔴 **`findByName` 이 기관명만으로 1건을 찾으므로 기관명이 유일하지 않게 되면
분류 로직 전체가 깨진다**(`TooManyResultsException`).

### ③ 시퀀스 개명 — 여기만 소스가 함께 바뀐다

```

TSKGIAF02_SEQ → SQ_KGI_AGENTGIGANTABLE   (22자)
```

⚠️ **시퀀스는 매퍼가 직접 부르는 유일한 DB 이름**이다. 제약·인덱스 이름은 앱이 참조하지
않아 바꿔도 무해했지만 이건 다르다 — 두 매퍼의 `<selectKey>` 를 함께 고쳤다.
틀리면 `ORA-02289` 로 **업로드·기관등록만** 실패하고 조회는 멀쩡해 눈에 덜 띈다.

⚠️ 이제 **테이블 이름과 시퀀스 이름이 서로 안 닮았다.** DDL 주석에 대응을 남겼다 —
`AGENTFILE=TSKGIAF01`, `AGENTGIGAN=TSKGIAF02`.

### 🔴 감사 2열 — 여기서 자바가 크게 바뀐다

| 컬럼 | 널리티 | 채우는 규칙 |
|---|---|---|
| `시스템사용일시`(일시14) | AF01 NULLABLE / **AF02 NOT NULL**(옛 수정일시 자리) | 업로드=업로드일시 · 분류=분류일시(없으면 now) · 삭제/반려=now |
| `시스템사용자번호`(사용자번호7) | 둘 다 NULLABLE | 화면번호 앞 K 를 뗀 7자 · 배치는 `BATCH01` |

**문제**: 매퍼는 어느 화면에서 불렸는지 모른다. 한 SQL 이 여러 화면에서 불려
리터럴로 박을 수도 없다.
**해법**: 컨트롤러 클래스명이 이미 화면번호를 담고 있다(`KGI11100$UploadAction`).
거기서 자동으로 뽑는다 — `code/SystemUser`(ThreadLocal + 도출) ·
`config/SystemUserInterceptor`(요청마다 넣고 지움) · `config/WebMvcConfig`(등록).
**화면이 늘어도 손댈 곳이 없다.**

⚠️ **ThreadLocal 은 반드시 지운다.** 인터셉터의 `afterCompletion` 과 배치의 `finally`
두 곳에서 지운다 — WAS 가 스레드를 재사용하므로 안 지우면 다음 작업이 이전
화면번호를 물려받아 **감사 기록이 조용히 틀어진다.**

⚠️ **감사 시각은 DB 함수가 아니라 자바에서 정해 넘긴다.** 처음엔 삭제·반려에
`TO_CHAR(SYSDATE)`/`DATE_FORMAT(NOW())` 방언 분기를 넣었다가, 사용자가 "분류일시가
없으면?" 을 짚어 주면서 **`UploadedFile.systemUsedAt` 필드로 바꿨다.** 방언 분기가
도로 없어졌고, 값이 업로드일시·분류일시와 **정확히 일치**하며, 테스트로 확인된다.

**덤**: 카테고리 목록 3중 복제가 사라진 데 이어, 옛 4종이 새 5종으로 교체됐다.
안 고치면 TypeHandler 가 "코드로 옮길 수 없는 값" 으로 **기관 등록을 막는다.**

### 스키마 접두어 `INST1.` — **가이드에만**

사내 표준이 `FROM INST1.TSKGIAF01` 을 요구한다. 사용자 지시로 **리포 소스는 그대로 두고
내부망 가이드(문서 ①② · DBA 요청서)에만** 붙였다 — 리포에 붙이면 외부망 테스트(H2)에
`INST1` 스키마가 없어 62건이 깨진다.

접두어는 **객체 참조에만** 붙였다(FROM/INTO/UPDATE/CREATE TABLE/DROP TABLE/ON/
CREATE SEQUENCE/NEXTVAL). 제약·인덱스 이름은 객체명 자체라 건드리지 않았고,
MySQL 미러는 제외했다. 누락 검사 결과 **접두어 없는 객체 참조 0건**.

곁들여 **적용 확인 쿼리도 고쳤다** — 접속 계정이 소유자가 아니면 `user_tables` 에
안 보인다. `all_tables`/`all_sequences` + `owner='INST1'` 로 바꿨다.

🔴 **그 대가로 내부망 파일과 리포 파일이 갈렸다.** 두 문서 앞머리에 경고를 넣었다 —
